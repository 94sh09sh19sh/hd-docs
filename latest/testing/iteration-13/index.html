    迭代 13 手動測試 — AI 閘道與實驗室實際測試¶

    《完整手動測試手冊》的分冊之一，對應《實作規格書》4.11 節。 共用的環境準備、啟動與疑難排解都在主手冊，這一冊只寫迭代 13 的部分。 操作端色籤（護理端／病人端／終端機／資料庫）的意思見主手冊 §00；本冊另加 ［實驗室］。

    這一冊驗的是「換推論端點、換模型，只改閘道的一個設定檔」。 後端所有 AI 請求都經 services/ai-gateway， 閘道照實驗室規範以 LangChain 呼叫推論端點；推論端點、模型與參數全部寫在閘道的 config.yaml。 過渡期接實驗室的 GPU 伺服器（院外，只准合成資料），正式接院內 GPU API。 步驟見《部署手冊》第十三冊，閘道本身見 repo 的 services/ai-gateway/README.md。

    標記 意思
    🖥 開發機 平常的開發環境（有 Node.js 與 Docker），不需要實驗室
    🔬 實驗室 要連上實驗室的 GPU 伺服器（第十三冊第 1～4 節）。校外連不到
    🐳 開發機，只用 Git 與 Docker 院內那一份閘道的部署實測

    13.1 · 閘道本體（FR-S13）🖥¶

    • w1 ［終端機］ 看 services/ai-gateway/。 → 有 gateway/（app.py、config.py、llm_factory.py、selftest.py）、Dockerfile、requirements.txt、兩份設定範本；沒有 config.yaml。
    • w2 ［終端機］ 開 gateway/app.py，找所有 @app. 開頭的行。 → 只有 GET /health、GET /v1/models、POST /v1/chat/completions 三個。沒有任何下載、刪除、載入模型的端點。
    • w3 ［終端機］ 開 gateway/llm_factory.py。 → provider: ollama 建 ChatOllama、provider: openai 建 ChatOpenAI——規範的兩種方法，其他 provider 一律拒絕。
    • w4 ［終端機］ 開 requirements.txt。 → 每一行都是 套件==版本，含間接相依。
    • w5 ［終端機］ docker build -t hd-ai-gateway-test services/ai-gateway → 建置過程最後有七段自我測試、全部 ✓，印出 全部通過。這一步不需要任何推論端點。
    • w6 ［終端機］ docker run --rm hd-ai-gateway-test id → uid=10001(gateway)：不是 root。
    • w7 ［終端機］ docker run --rm hd-ai-gateway-test env | Select-String TRACING → LANGSMITH_TRACING=false、LANGCHAIN_TRACING_V2=false。
    • w8 ［終端機］ 在 apps/ 與 packages/ 裡搜 langchain、ollama。 → 找不到（DEP-41：後端不直接連推論端點）。

    13.2 · 整條路徑在假推論端點上走一次（驗收 1～5）🖥¶

    • w9 ［終端機］ npm run verify:iteration13:api（不必先啟動後端） → 腳本自己建暫存資料庫、起閘道容器與假推論端點、另起一個 LLM_PROVIDER=lab 的後端。約兩分鐘，結尾 全部通過。
    • w10 ［終端機］ 看 [2] 那一段。 → 健康檢查通過；「閘道只列出 config.yaml 設定的一個模型：stub-model-a」；呼叫紀錄的模型是 stub-model-a， 後端沒有設定任何模型名稱（腳本起後端時 LLM_MODEL_ID 是空的）。
    • w11 ［終端機］ 看 [3]。 → 看似真實的病人：工作失敗、紀錄是「已擋下」、假推論端點一個請求都沒收到。
    • w12 ［終端機］ 看 [4]。 → 改 config.yaml 之後下一次呼叫就換成 stub-model-b；改成 provider: openai 也跑得通； 後端 PID 從頭到尾同一個。
    • w13 ［終端機］ 看 [5]。 → 閘道停掉：健康檢查不通過、衛教產生失敗並說明原因、SOP 查詢回「模型未能回答」但原文段落照樣列出； 病人清單、事件記錄與簽核、排班全部照常；閘道再起來之後 AI 自己恢復。
    • w14 ［終端機］ 腳本跑完後 docker ps -a 與 BACKUP_DIR 的上一層。 → 沒有 hd-verify13-gateway-… 容器、沒有 hd-v13-scratch-… 資料夾：腳本收乾淨了。

    13.3 · 實驗室：連線與個人容器（DEP-42）🔬¶

    照第十三冊 Z-01～Z-10 做，每一步對照下列結果。

    • w15 ［終端機］ ssh -G hd-lab → 位址、埠、帳號都對；這些值只在 %USERPROFILE%\.ssh\config 與專案目錄外的 lab.env 裡。
    • w16 ［實驗室］ ssh hd-lab 登入後 ls -la ~/.ssh。 → 與登入前一樣：沒有為了省打密碼去改共用帳號的設定檔。
    • w17 ［實驗室］ ls <指定路徑>/<個人資料夾>/hd-ai-gateway → 只有 Z-05 傳上去的五樣，加上 Z-07 的 config.yaml。
    • w18 ［實驗室］ 容器外 ollama list。 → 列得出模型；挑定的那一個與備用的那一個記在開發機的筆記，不寫進 repo。
    • w19 ［實驗室］ docker build 的輸出結尾。 → 全部通過：套件裝在映像檔裡，沒有裝在實驗室伺服器上。
    • w20 ［實驗室］ docker port <個人前綴>-hd-ai-gateway → 8000/tcp -> 127.0.0.1:<閘道埠>：只綁本機介面。（host 網路的起法沒有這一行，改看 ss -ltn | grep <閘道埠> 只有 127.0.0.1）
    • w21 ［實驗室］ 從實驗室伺服器的另一個網路介面連閘道：curl -m 3 http://<伺服器的區網位址>:<閘道埠>/health → 連不上。別人的機器連不到你的閘道。
    • w22 ［實驗室］ 容器內 curl Ollama 的 /api/tags（Z-08）。 → 印出模型清單。這是規範第 4 項「容器內以 curl 確認連線」。
    • w23 ［實驗室］ 填好 config.yaml 存檔，不重新啟動容器，docker exec … curl -s 127.0.0.1:8000/health → "status":"ok"、"model" 是剛填的那一個。
    • w24 ［終端機］ 開著 Z-10 的轉送，curl.exe -s http://127.0.0.1:18000/health → 同一行 JSON，在開發機上看到。

    13.4 · 實驗室：真模型跑通、換模型、換方法（驗收 1～4）🔬¶

    • w25 ［終端機］ npm run verify:iteration13:api -- --gateway http://127.0.0.1:18000/v1 --report <專案目錄外>\ai-lab-trial.md → 全部通過。第一次衛教產生要等模型載入，可能一兩分鐘。
    • w26 ［終端機］ 看 [2]。 → 「呼叫紀錄的模型為『<實驗室上的模型>』，與閘道回報的一致」——驗收 1：ai_invocations 記下的是實驗室上的實際模型。
    • w27 ［終端機］ 看 [3]。 → 看似真實的病人被擋下、紀錄「已擋下：院外供應者不得送真實病人資料」——驗收 2。
    • w28 ［實驗室］ config.yaml 的 model 改成備用模型，存檔。［終端機］ 同一條指令加 --expect-model <備用模型>，去掉 --report。 → 全部通過，「與 --expect-model 一致」那一行 ✓——驗收 3：只改 config.yaml，後端沒重建、閘道沒重新啟動。
    • w29 ［實驗室］ 改成 provider: openai、base_url 結尾加 /v1，存檔。［終端機］ 再跑一次。 → 全部通過——驗收 4：規範的兩種方法都跑得通。改回 ollama。
    • w30 ［護理端］（選做，第十三冊 Z-13）開發機 .env 改成 lab、npm run dev，「系統管理」的 AI 區塊。 → 供應者「實驗室 API（院外，僅得送合成資料）」、模型識別字是 config.yaml 那一個、健康檢查通過。看完改回 mock。

    13.5 · 繁體中文品質、耗時與失敗樣態 🔬¶

    w25 產生的報告，每一項照四點判讀，品質欄填「可用／需修改／不可用」加一句理由： 通順嗎、有沒有簡體字或中國大陸用語、有沒有捏造提示裡沒有的事、格式照不照提示。

    • w31 個人化衛教內容。 → 判讀完填入報告；模型耗時記下（第一次含載入時間，另跑一次看暖機後的耗時）。
    • w32 離院衛教重點。 → 同上。另看：有沒有提到今天實際發生的事（合成病人的測驗與紀錄）。
    • w33 護理記錄草擬。 → 同上。另看：有沒有自己加上勾選以外的症狀或處置——有就是不可用。
    • w34 SOP 查詢回答。 → 同上。另看：有沒有標出處 [S1] 這類標記；結果是「已依文件回答」還是「查無資料」。
    • w35 把四項的結論、耗時與模型寫進《部署演練紀錄》第 10 節。 → 報告原檔留在專案目錄外；演練紀錄只寫結論，不寫實驗室的任何連線資訊。

    13.6 · 收尾：repo 沒有連線資訊、實驗室沒有留東西（驗收 6、7）🖥＋🔬¶

    • w36 ［終端機］ npm run verify:iteration13 -- --secrets $HOME\hd-lab\lab.env → 每一個名稱都是「檔案、歷史、提交訊息都找不到」——驗收 6。值本身沒有印出來。
    • w37 ［終端機］ 故意把 lab.env 裡的某一個值貼進 repo 裡任一個檔案（不要提交），再跑一次。 → 那一項變 ✗，指出是哪個檔案。刪掉貼上的內容，回到全綠。
    • w38 ［實驗室］ 第十三冊 Z-14 的四條檢查。 → 容器、映像檔都已移除；家目錄沒有本專案的檔案；本專案只剩個人資料夾底下那一份（或整個刪除）——驗收 7。

    13.7 · 院內那一份閘道（部署規範 5.3）🐳¶

    在迭代 11 分冊 §11.3 那一套暫存部署上做，照第十三冊 Z-20～Z-22。

    • w39 ［終端機］ 暫存設定目錄建 ai-gateway\config.yaml（院內範本），docker compose --env-file <暫存 .env> --profile ai build ai-gateway → 建置最後 全部通過。
    • w40 ［終端機］ … --profile ai up -d ai-gateway，再 docker compose --env-file <暫存 .env> ps → ai-gateway 那一列沒有任何 ->8000：不對外開埠。
    • w41 ［終端機］ 第十三冊 Z-21 最後那一條（從 api 容器裡 fetch 閘道的 /health）。 → 503 {"status":"error","config":"error","detail":"base_url 尚未填寫（推論端點的位址）"}：這是院內首波的正確狀態。
    • w42 ［終端機］ docker compose --env-file <暫存 .env> up -d（不帶 --profile ai）。 → 閘道不受影響、其餘三個服務照常；只有第一次要帶 profile 才起得來。
    • w43 ［終端機］ … --profile ai stop ai-gateway，護理端登入、病人清單、排班。 → 全部照常（DEP-24）。
    • w44 ［終端機］ 迭代 11 分冊裡驗過的 DEP-40：正式環境設定＋LLM_PROVIDER=lab。 → 後端拒絕啟動，訊息寫明實驗室在院外——與合成資料檢查是兩道防線，這一道擋「送往哪裡」。

    13.8 · 自動化驗收 🖥¶

    • w45 ［終端機］ npm run verify:iteration13 → 閘道本體、DEP-41、compose 三段全部 ✓；最後列出在別處驗的幾項。
    • w46 ［終端機］ npm run verify:iteration13 -- --live --env-file <暫存的 config\.env> → 加上 compose 實測：建置、啟動、主機上沒有對外的埠、api 經私有網路連得到閘道。
    • w47 ［終端機］ npm run check:all → 六支全綠；「零院外連線」的 AI 閘道那一節改為實際掃描閘道的程式與範本（不再是「尚無程式碼」）。
