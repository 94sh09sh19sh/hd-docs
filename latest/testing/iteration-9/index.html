    迭代 9 手動測試 — 導覽版位、功能開關與內容資料化¶

    《完整手動測試手冊》的分冊之一，對應《實作規格書》4.7 節。 共用的環境準備、啟動與疑難排解都在主手冊，這一冊只寫迭代 9 的部分。 操作端色籤（護理端／病人端／終端機／資料庫）的意思見主手冊 §00。

    這一冊要驗的是一句話：「哪些功能出現、出現在哪裡、選項有哪些」全部變成可設定的資料，不必改程式。

    自動化腳本（npm run verify:iteration9）驗得了後端的行為：關閉的端點回不回 404、版本號有沒有遞增、 「其他」能不能停用。它看不到畫面。 護欄有三條是畫面上的事，只能用眼睛看：

    護欄 腳本驗得到嗎 在這一冊的哪裡
    識別碼欄位建立後不可編輯 只驗得到「格式不合的擋下」 §9.4 s18
    停用是唯一的移除方式，沒有刪除按鈕 驗得到沒有刪除端點 §9.4 s19
    每一組的「其他」不可停用 驗得到後端擋下 §9.4 s20
    改動會產生新版本這件事要寫在按下去之前 驗不到 §9.5 s24

    9.1 · 導覽列重新編排（基準 3.3、FR-S11）¶

    0919 之前護理端是 17 條連結一字排開，沒有層級也沒有順序邏輯，每天用的跟半年用一次的並列在一起。

    • s1 ［護理端］ 以最高權限帳號登入，看最上面那一排。 → 主列只有 7 項，由左到右依序是：即時總覽、緊急通報、排班與指派、裝置管理、病人、輪播內容、總覽螢幕模式。 這個順序是一天的工作流程，不是字母也不是功能分類。
    • s2 ［護理端］ 主列最右邊有一個「更多」。點一下。 → 展開 7 項：帳號審核、護理紀錄、衛教、SOP 查詢、臨床數值、病人趨勢、稽核軌跡。
    • s3 ［護理端］ 「更多」展開後，按一下畫面別的地方。→ 選單收起來。再按 Esc 也要收得起來。 滑鼠滑過去不應該展開——護理站的滑鼠常常只是路過。
    • s4 ［護理端］ 畫面最右邊：使用者名稱與工號、系統管理、變更密碼、登出。 → 這四個是固定的，不受版位設定影響。
    • s5 ［護理端］ 主列上看不到班表、成效基準、離院衛教。 → 首波這三項是關閉的（DEP-29）。它們不在「更多」裡，也不是灰色的按鈕——整個不在。

    9.2 · 「關閉」是整個不提供（3.13、DEP-34）⚠️¶

    這一節是整個迭代最容易做半套的地方。 只把連結藏起來等於沒關：知道網址的人直接打得進去。

    • s6 ［護理端］ 在網址列直接輸入 /shifts 並按 Enter。 → 畫面回到即時總覽。沒有「功能未啟用」的空白頁，也沒有壞掉的畫面——那個路由不存在。
    • s7 ［終端機］ 用登入後的權杖直接打後端： curl -H "Authorization: Bearer <權杖>" http://localhost:3000/api/shifts?from=2026-09-01&to=2026-09-02 → HTTP 404。前端藏起來只是第一層，後端這一層才是真的擋下。
    • s8 ［護理端］ 系統管理 → 功能與版位。找到「班表」，按「更多選單」，填一句理由，送出。 → 上面的導覽列立刻多出「班表」（在「更多」裡），不必重新整理。再打一次 s7 的指令 → 這次通了。
    • s9 ［護理端］ 把「班表」改回「關閉」。改成關閉時會先問一次， → 第二段寫的是後果：「關閉後，護理端看不到『班表』，直接輸入網址也打不開」， 不是「確定要關閉嗎」。
    • s10 ［護理端］ 稽核軌跡 → 動作選「調整功能的導覽版位」。 → 查得到剛才那兩次改動，每一筆都寫得出從哪個版位改到哪個版位、誰改的、理由是什麼。 半年後有人問「這個功能什麼時候不見的」，答案在這裡。
    • s11 ［護理端］ 稽核軌跡 → 動作選「功能已關閉，端點擋下」。 → 查得到 s7 那一次被擋下的紀錄。「已實作但關閉」與「根本沒有這個功能」在軌跡上是兩件事： 前者查得到這一筆，後者連路由都不存在。
    • s12 ［護理端］ 系統管理 → 功能開關，找「需要手持裝置的功能（目前是「我到床邊了」）」。 → 預設關閉。緊急通報畫面上沒有「我到床邊了」這顆按鈕。 DEP-29：護理師手上還沒有行動裝置，硬留著只會得到事後補按的假資料。

    9.3 · 求助類別重新設計並資料化（附錄 C.2）¶

    • s13 ［病人端］ 按求助區進入求助畫面。 → 分成兩組：「身體不舒服」11 項、「其他需要」4 項。臨床組第一項是「頭暈、冒冷汗、快昏倒」 ——最常發生、最需要快速反應的排最前面，不是依字母排序。
    • s14 ［病人端］ 點「頭暈、冒冷汗、快昏倒」。 → 下面的急迫度自動選好「非常緊急，請馬上過來」。再自己改成「不急」→ 改得動， 而且之後再換類別也不會被蓋回去。病人選的優先於分派表的預設值。
    • s15 ［護理端］ 系統管理 → 內容與選項 → 求助類別。找「抽筋」，按「改文字」， 改成「抽筋（測試）」，填理由後儲存。
    • s16 ［病人端］ 回到求助畫面（或重新整理）。→ 立刻看到「抽筋（測試）」。 改的是資料，不必重新部署。
    • s17 ［護理端］ 緊急通報 → 看 s14 之前送出的舊紀錄。 → 那一筆仍顯示按下當時的文字（「抽筋」），不是改名後的。 事後回頭看，要知道病人按的是哪一個按鈕上的哪幾個字。 測完把文字改回「抽筋」。

    9.4 · 內容與選項的四條護欄（附錄 C.8）⚠️¶

    • s18 ［護理端］ 內容與選項 → 求助類別 → 任一列按「改文字」。 → 可以改的是顯示文字與預設急迫度；識別碼那一格是純文字，不是輸入框。 識別碼一改，這個選項之前累積的所有紀錄就與之後的對不起來。
    • s19 ［護理端］ 同一個畫面，找找看有沒有「刪除」。 → 整頁沒有任何刪除按鈕，四塊都沒有。停用是唯一的移除方式。
    • s20 ［護理端］ 找「身體其他地方不舒服」（臨床組的「其他」）與「其他，請有人過來一下」。 → 那兩列沒有停用按鈕。不是按了才說不行——按鈕根本不出現。 處理方式與處理結果那一塊的「其他（請說明）」「無法處理（請說明）」也一樣。
    • s21 ［護理端］ 新增一個類別，識別碼填「測試 A」（中文）。 → 擋下，並說明識別碼只能用大寫英文字母、數字、底線與連字號，而且建立之後不能再改。
    • s22 ［護理端］ 內容與選項最上面那一塊。 → 四條護欄列在畫面上，不是寫在說明文件裡。
    • s23 ［護理端］ 累積一段時間之後再看這一塊。 → 某一組選項的「其他」超過設定比例（預設 15%）時，畫面上會出現一條提醒 「這份清單可能不夠用」。清單品質不靠一次設計對，靠上線後看得見它哪裡不對。 （剛部署時資料量不足，這一條不會出現，屬正常。）

    9.5 · 版本號（附錄 C.5～C.7）⚠️¶

    • s24 ［護理端］ 內容與選項 → 透析前問卷。 → 標題帶著目前的版本號；上面有一條提示「這會產生一個新的版本編號，之前的作答仍以舊版本留存」。 這句話要在按下去之前就看得到，不是按完才說。
    • s25 ［護理端］ 改一題的文字，填理由後儲存。 → 標題的版本號遞增（例如 PRE-DIALYSIS-v2 → PRE-DIALYSIS-v3）。
    • s26 ［護理端］ 病人趨勢（或護理紀錄）→ 看改版之前送出的那一份作答。 → 它顯示的仍是當時那一版的題目文字，而且標記的版本號是舊的。 沒有版本號，改過題目之後的趨勢圖就是把兩種不同的問題畫在同一條線上。
    • s27 ［病人端］ 若平板停在問卷畫面沒有重新整理，這時按送出。 → 被擋下，並說「題目改過了，請重新整理畫面後再填一次」。 拿新題目去解讀舊答案，比拒收更危險。
    • s28 ［護理端］ 衛教題庫與回饋題目兩塊，各做一次 s25。 → 同樣是版本號遞增、舊作答不受影響。把題目文字改回去再繼續。

    9.6 · 透析前問卷的新結構（附錄 C.5）¶

    原本 10 題全部必答，對躺著、手不能動的長者太長。

    • s29 ［病人端］ 主畫面 →「填寫透析前問卷」。 → 第一頁 5 題，標題右邊寫「第 1 / 2 頁」。5 題就是每次都有的那一組基準。
    • s30 ［病人端］ 「打針的地方有沒有狀況」選「有」。 → 底下立刻展開追問「是哪一種狀況」，可以複選（流血止不住／紅腫熱痛／摸不到震動／其他）。 選回「沒有」→ 追問收起來。
    • s31 ［病人端］ 「會不會喘」選「中等」或「嚴重」。 → 展開「晚上睡覺要不要墊高枕頭才睡得著」。選「輕微」→ 不展開。
    • s32 ［病人端］ 按「下一頁」→ 第二頁 4 題（發燒、胸悶、皮膚癢、上次洗完到現在有沒有去急診／住院／跌倒）。 第二頁不是選填，分頁是為了第一頁能一眼看完。
    • s33 ［病人端］ 送出。［護理端］ 即時總覽 → 這位病人。 → 列出的症狀是中文的題目與答案（例如「會不會頭暈・嚴重」），畫面上看不到 Q_DIZZY 或 SEVERE。
    • s34 ［病人端］ 拔掉網路，重新開啟平板的應用程式，進問卷。 → 題目照樣出得來（上一次取到的那一份存在平板上）。填完送出 → 暫存在平板，恢復連線後補傳。 題目與選項不是病人資料，因此不在「解除綁定要清掉」的範圍內。

    9.7 · 介面上不再有內部技術識別（FR-S10、基準 3.4）¶

    • s35 ［護理端］ 逐頁看過：即時總覽、緊急通報、排班與指派、裝置管理、病人、輪播內容、 以及「更多」裡的七項、系統管理的六個分頁。 → 看不到任何 FR-xxx、Q-xx、DEP-xx、「迭代 N」、PENDING／ACTIVE 這類英文列舉值、 AI_FEATURES 這類開關識別字、MockMdmProvider 這類類別名。
    • s36 ［護理端］ 排班與指派的狀態欄、帳號審核的狀態欄。 → 中文：已排定／進行中／已完成／已取消；待審核／已核准／已駁回／已停用。
    • s37 ［護理端］ 系統管理 → 功能開關。 → 每一列只有中文名稱與一句開啟條件，沒有 AI_FEATURES 這種識別字，也沒有需求編號。
    • s38 ［護理端］ 系統管理 → 內容與選項。 → 這裡是唯一看得到識別碼的地方，而且是刻意的：護理長要看得到它， 才知道自己改的是文字（安全）還是新增了一個選項（會讓歷史資料斷開）。

    9.8 · 自動化驗收¶

    • s39 ［終端機］ npm run verify:iteration9（需先 npm run dev:api） → 十個步驟全過。它涵蓋十條驗收標準裡的後端部分。
    • s40 ［終端機］ npm run check:all → 五支全綠。介面技術識別這一支的基準線自本迭代起是 0（迭代 8 時是 22）。
    • s41 ［終端機］ npm run verify:acceptance、verify:iteration2～verify:iteration8 → 全部通過。內容改成資料之後，這幾支都改成先向後端問「現在生效的是哪一版」再填答案—— 把一份答案寫死在腳本裡，護理長改過題目之後那支腳本就會開始亂報。
