    01 · 從 clone 到跑起來¶

    • a1 ［終端機］ Clone 專案並進入目錄。 → 取得 apps/、packages/、demand_v1/ 三個資料夾。
    git clone https://github.com/94sh09sh19sh/hd-tablet-care.git
cd hd-tablet-care
    • a2 ［終端機］ 確認 Node 版本 ≥ 20.11。 → node -v 顯示 v20.11 以上（開發環境用 v24）。版本太舊會在後續步驟出現語法錯誤。
    • a3 ［終端機］ 安裝相依套件。 → npm workspaces 會一次裝好 api、兩個 PWA 與 shared 套件，過程無紅字錯誤。
    node -v
npm install

    注意｜npm install 出現權限錯誤（EPERM／EACCES／operation not permitted）

    Windows 上最常見的三個原因，依序排查：① 有 node 行程正抓著 node_modules — 關掉還在跑的 dev server 與編輯器再重試。② 專案放在 OneDrive／雲端同步資料夾底下，同步程式會鎖檔 — 把專案移到不同步的路徑。③ 防毒即時掃描擋住寫入 — 把專案資料夾加入排除清單。都試過還是不行，再以系統管理員身分開啟 PowerShell 重跑；若已經裝壞了，先刪掉 node_modules 資料夾，執行 npm cache clean --force 後重來。

    建立 .env¶

    • a4 ［終端機］ 複製環境變數範本。 → 專案根目錄出現 .env（已列入 .gitignore，不會被提交）。
    cp .env.example .env
# PowerShell：Copy-Item .env.example .env

    說明｜資料庫誰來建？你只要決定它放哪裡

    這一步要填的 DATABASE_URL 是「我希望資料庫檔案出現在哪裡」，不是「請填入現有資料庫的位置」。本系統的資料庫是一個 SQLite 檔案，沒有資料庫伺服器、沒有帳號密碼、不必事先安裝或建立任何東西。 資料夾與檔案都不必先建：下一小節的 npm run prisma:migrate（a7）會依你填的路徑，把中間缺的資料夾與 hd.db 一起建出來。所以填完 .env 時磁碟上還看不到任何東西，是正常的 — a13 會回頭確認它真的生出來了。

    順序只有一條規則：先 prisma:migrate，再 npm run dev。 跳過 migrate 直接啟動後端，後端不會幫你建檔案，只會噴 Error code 14: Unable to open the database file。

    以下兩個變數是後端的硬性必填（缺了直接拒絕啟動），SUPER_ADMIN_* 兩個照本手冊走也等於必填， BACKUP_DIR 強烈建議一併填，其餘留空即用預設值：

    變數 怎麼取得
    DATABASE_URL（硬性必填） SQLite 連線字串：file: 加絕對路徑，例如 file:D:/hd-data/hd.db。路徑必須在專案目錄外的本機磁碟（不得為網路磁碟或 OneDrive 等同步資料夾），否則後端與 seed 會拒絕啟動。資料夾與檔案都不必事先建立，a7 的 migration 會一起建出來
    JWT_SECRET（硬性必填） 自行產生，見下方指令
    SUPER_ADMIN_WORK_ID 初始最高權限帳號的工作ID，例如 ADMIN001（英數字、底線、連字號，3–32 字元）。這兩個留空後端照樣起得來，但資料庫裡不會有任何帳號，護理端登不進去
    SUPER_ADMIN_INITIAL_PASSWORD 至少 8 字元。首次登入後會被強制變更
    BACKUP_DIR（建議） 備份輸出目錄，同樣須在專案目錄外的本機磁碟，例如 D:/hd-data/backups，目錄不必先建。未填時無法備份：§12 的備份還原演練、迭代 3 分冊 §3.8、verify:iteration3 與 verify:iteration4 都會卡住

    在終端機執行 — 這是指令，不是要貼進 .env 的值

    node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

    注意｜這一行是指令，不是設定值

    把整行貼到終端機執行（PowerShell、cmd、Git Bash 都可以），它會印出一串長長的亂碼。那串印出來的東西才是要填進 .env 的值： JWT_SECRET=印出來的那一串 不要把 node -e ... 這行本身貼進 .env — 那樣後端啟動時會把整行當成金鑰，雖然不會壞掉，但等於用了一把人人都猜得到的鑰匙。

    • d9 ［護理端］ 看表格最下方的說明文字。 → 「以上為病人自行填寫之症狀原樣彙整，僅供決策輔助，非風險評估或診斷結果。」— SRS 第 8 章的要求。系統不做任何風險分層。

    FR-P06 求助按鈕¶

    • d10 ［病人端］ 回主畫面 → 點畫面最下方那一條紅色的「我需要協助」。 → 進入求助頁：上半是 7 種求助類型，下半是 3 種急迫度。
    • d11 ［病人端］ 只選類型不選急迫度，觀察底部按鈕。 → 「通知護理站」是停用狀態。兩項都選完才會啟用 — 避免不完整的通報。
    • d12 ［病人端］ 選「打針處或管路有狀況」＋「非常緊急，請馬上過來」，補充說明可填可不填，按「通知護理站」。 → 回主畫面，顯示「已通知護理站，護理人員將盡快過來。」底部出現「您的求助：待處理」。

    FR-N03 緊急通報接收¶

    • d13 ［護理端］ 留在任何一頁觀察（不必切到緊急通報頁）。 → 頁面頂端跳出紅色橫幅：病人姓名與病歷號、求助類型、急迫度、平板序號，右側有「前往處理 / 稍後」。導覽列的「緊急通報」出現紅色數字徽章 1。
    • d14 ［護理端］ 回到「即時總覽」。 → 「待處理求助」與「其中標示非常緊急」兩張統計卡變成紅底並顯示 1；該病人那列被移到最上方並以紅底highlight，求助欄出現紅色標籤。
    • d15 ［護理端］ 按橫幅上的「前往處理」。 → 跳到「緊急通報」頁，卡片為紅底，右上三個標籤：急迫度、「分派：緊急處置團隊」、「待處理」。
    • d16 ［護理端］ 確認卡片中間那行摘要。 → 顯示「本次療程問卷（時間）：身體水腫・中等、發燒或畏寒・有」— 護理師到場前就掌握背景，這正是 FR-P06 的重點。
    • d17 ［護理端］ 點「查看近期症狀趨勢摘要」。 → 展開表格：症狀 / 自述次數（如 1 / 1）/ 最近一次 / 時間，下方再次出現非診斷結果的提示。預設統計近 30 天、最多 10 筆回報。
    • d18 ［護理端］ 按「我接手」。 → 狀態標籤變「已接收，前往中」，「我接手」按鈕消失，只剩「處理完成 / 取消」。
    • d19 ［病人端］ 等約 10 秒觀察病人端底部。 → 「您的求助」由「待處理」變成「已接收，前往中」。病人知道有人要來了。
    • d20 ［護理端］ 按「處理完成」。 → 該卡片從待處理清單消失，導覽列徽章歸零，總覽的兩張紅色統計卡回到 0 並恢復灰底。

    05 · 離線韌性¶

    SRS 4.4 對離線行為有兩條方向相反的要求：症狀回報必須能暫存並自動補傳；求助則必須明確告知無法通知護理站。這一節同時驗證兩者。

    注意｜為什麼求助不做離線暫存

    讓病人誤以為護理站已收到，比誠實說明送不出去更危險。因此離線時求助按鈕直接停用並引導改用床邊呼叫鈴。這是刻意的設計取捨，不是缺漏。

    • e1 ［病人端］ 在病人端按 F12 開 DevTools → Network 分頁 → 把 Throttling 下拉選成「Offline」。 → 只影響這個分頁，護理端不受影響。
    • e2 ［病人端］ 等 3–5 秒觀察主畫面。 → 出現黃字「目前沒有網路連線。症狀問卷仍可填寫並暫存於本平板；求助請改用床邊呼叫鈴。」求助按鈕副標變成「目前無法即時通知護理站」。
    • e3 ［病人端］ 點進「我需要協助」。 → 頂端橘色警示框：「目前無法即時通知護理站。請改用床邊呼叫鈴，或直接出聲呼叫附近的護理人員。」底部按鈕顯示「離線中，無法通知」且停用。
    • e4 ［病人端］ 回上一頁 → 點進「填寫透析前症狀問卷」。 → 頂端黃字：「目前沒有網路連線。您仍可以填寫，送出後會暫存在這台平板，恢復連線時自動傳送給護理站。」問卷本身完全可用（題庫打包在前端，不需連線）。
    • e5 ［病人端］ 把「呼吸會喘」點成嚴重，按「送出給護理站」。 → 回主畫面顯示綠字「已暫存在這台平板。恢復連線後會自動送給護理站，資料不會遺失。」以及「尚有 1 筆症狀回報等待傳送」。
    • e6 ［病人端］ 把 Throttling 改回「No throttling」，等約 10 秒。 → 離線提示消失，出現綠字「已將 1 筆離線暫存的症狀回報送出給護理站」，等待傳送的計數歸零。
    • e7 ［護理端］ 看即時總覽該病人列。 → 病人自述症狀更新為「呼吸會喘・嚴重」（顯示的是最新一份回報）。
    • e8 ［護理端］ 「稽核軌跡」→ 篩選「病人送出症狀問卷」→ 看最新一列的說明欄。 → 包含「送出方式 離線暫存後補傳」。系統把即時送出與離線補傳分開記錄，且保留病人當初填寫的時間，不會被補傳時間覆寫。

    說明｜資料為什麼不會掉

    病人按下送出時，資料是先寫進 IndexedDB 佇列、再嘗試上傳，成功才移除。就算平板在上傳途中斷電或被 Kiosk 重新載入，資料仍在。後端再用平板產生的識別碼去重，所以重複補傳也不會變成兩筆。

    06 · 細節功能逐項¶

    主線走通之後，這一節把每個分支、每個錯誤路徑都掃過一遍。可以分次做完。

    6.1 身份驗證與帳號¶

    • f1 ［護理端］ 用已存在的工作ID 再次申請註冊。 → 409「此工作ID 已被註冊或已提出申請」。
    • f2 ［護理端］ 註冊時密碼只輸入 5 個字。 → 400「密碼長度至少 8 字元」。
    • f3 ［護理端］ 註冊時工作ID 輸入中文（例如「護理師01」）。 → 400「工作ID 僅能包含英數字、底線與連字號，長度 3–32 字元」。
    • f4 ［護理端］ 用正確帳號但錯誤密碼登入。 → 401「工作ID 或密碼錯誤」。
    • f5 ［護理端］ 用不存在的工作ID 登入。 → 完全相同的 401 訊息。刻意不透露帳號是否存在；後端連回應時間都對齊了（不存在時仍比對一次假雜湊）。
    • f6 ［護理端］ 以管理者查「稽核軌跡」→ 篩選「登入失敗」。 → 剛才兩次失敗都有記錄，整列以紅底顯示（outcome = FAILURE）。密碼錯誤與帳號不存在的說明文字不同 — 內部可追查，對外不洩漏。
    • f7 ［護理端］ 再申請一個帳號 N002，然後在「帳號審核」按「駁回」，於彈出視窗輸入原因。 → 狀態變 REJECTED；該帳號登入被拒（403「此帳號目前無法登入，請洽護理站管理者」）。稽核記錄含駁回原因。
    • f8 ［護理端］ 右上「變更密碼」→ 目前密碼與新密碼填一樣。 → 400「新密碼不可與目前密碼相同」。
    • f9 ［護理端］ 正常變更一次密碼。 → 完成後顯示所有既有登入階段已撤銷，必須重新登入。這是自建 Session 才做得到的主動撤銷。
    • f10 ［護理端］ 按「登出」。 → 回到登入頁；原權杖立刻失效（可用 §08 的 curl 驗證：登出後再帶舊 token 呼叫 /auth/me 會得到 401）。

    • f18 ［護理端］ 建立病人時病歷號輸入 ab（少於 4 字元）。 → 400「病歷號格式不正確」。合法格式為英數字與連字號、4–32 字元。

    重複病歷號目前沒有被特別處理，資料庫的唯一鍵衝突直接冒成 500，而不是像其他地方一樣回 409 加中文訊息。資料本身沒有寫壞（唯一鍵擋住了），只是錯誤訊息不友善。已記錄，待後續迭代修。

    • f22 ［護理端］ 用相同序號 TB-99 再註冊一次。 → 409「此平板序號已註冊」。
    • f23 ［護理端］ 對一台未綁定的已納管平板按「遠端鎖定」。 → MDM 欄變成「已納管・鎖定中」。

    • f26 ［護理端］ 對某台平板按「解除註冊」。 → MDM 欄變「未納管」，按鈕變回「MDM 註冊」；該平板同樣不可指派（400「此平板尚未納入 MDM 管理，不可指派給病人」）。
    • f27 ［護理端］ 檢查稽核軌跡的 MDM 事件。 → 五種動作都有獨立記錄：MDM 裝置註冊、MDM 解除註冊、MDM 遠端鎖定、MDM 解除鎖定、MDM Kiosk 模式設定，說明欄前綴 [mock] 標示目前的 provider。

    6.5 排班（FR-N01）¶

    • f28 ［護理端］ 為同一位病人、同一天、同一時段重複建立排班。 → 409「該病人在此日期時段已有排班」。（病人＋日期＋時段是資料庫唯一鍵）
    • f29 ［護理端］ 同一位病人改成不同時段（早班→午班）建立。 → 成功。同一天可以有多個時段。
    • f30 ［護理端］ 把日期選成昨天或明天。 → 顯示該日期的排班（可能是空的）。日期切換只影響「排班與指派」頁。

    補充｜只有 API 有、UI 尚未提供的功能

    「取消排班」（POST /api/treatment-sessions/:id/cancel）目前只有後端端點，護理端畫面上還沒有按鈕。要測它請用 §08 的 curl。規則是：該排班若仍有進行中的綁定，取消會被擋（409）。

    6.6 裝置綁定例外情況（SRS 4.4）¶

    • f31 ［護理端］ 同一位病人建立兩筆排班（早班、午班），先指派 TB-01 給早班，再試著指派 TB-02 給午班。 → 紅色橫幅「該病人已有進行中之綁定（平板 TB-01），請先解除後再指派」（409）。這是 SRS 4.4 明列的重複綁定阻擋。
    • f32 ［護理端］ 把另一位病人的排班指派給已被佔用的 TB-01。 → 409「平板 TB-01 目前已指派給其他病人，請先解除後再指派」。（實務上下拉選單已濾掉，用 curl 可直接打到這條）
    • f33 ［護理端］ 「稽核軌跡」→ 篩選「綁定遭阻擋：病人已有進行中之綁定」。 → 被擋下的嘗試本身也留下紅底記錄，含操作者、病人與平板序號。阻擋不是靜默失敗。
    • f34 ［護理端］ 對已「下機結束」（COMPLETED）的排班嘗試指派平板。 → 400「此排班狀態為 COMPLETED，無法指派平板」。

    6.7 綁定逾時自動失效¶

    第三種失效條件是「超過療程時間上限」，預設 6 小時。不必真的等六小時 — 直接把到期時間改到過去即可。

    • f35 ［終端機］ 先建立一組進行中的綁定並開著病人端，然後另開一個終端機啟動 Prisma Studio。 → 瀏覽器開啟 http://localhost:5555。
    • f36 ［資料庫］ 在 Prisma Studio 開啟 device_bindings 資料表 → 找到 status = ACTIVE 的那一列 → 把 expires_at 改成過去的時間 → Save。 → 存檔成功。
    • f37 ［病人端］ 回到病人端等 3 秒（下一次輪詢）。 → 立刻回到等待畫面並顯示資料已清除。平板每次查詢綁定狀態時也會自行檢查到期，不必等背景掃描。
    • f38 ［護理端］ 「稽核軌跡」→ 篩選「綁定逾時自動失效」。 → 有一列記錄，操作者是 SYSTEM（不是護理師），說明欄註明超過療程時間上限。排班狀態變 COMPLETED。

    6.10 求助分派規則（FR-N03）¶

    分派只看病人自選的類型與急迫度，不讀歷史資料、不做推論 — 所以不落入已排除的風險分層範疇。規則表如下，可逐格驗證：

    急迫度 ＼ 類型 臨床類（身體不舒服／打針處或管路有狀況／機器在叫） 非臨床類（需要上廁所／環境調整／口渴或肚子餓／其他）
    非常緊急，請馬上過來 緊急處置團隊 緊急處置團隊
    不太舒服，請盡快過來 護理師 護理師
    不急，方便時再過來 護理師 護佐／行政支援
    • f48 ［病人端］ 送出「需要上廁所」＋「不急，方便時再過來」。 → 護理端卡片顯示「分派：護佐／行政支援」— 降低對護理師的無效打斷。
    • f49 ［病人端］ 送出「需要上廁所」＋「非常緊急，請馬上過來」。 → 「分派：緊急處置團隊」。急迫度優先於類型。
    • f50 ［病人端］ 送出「機器在叫」＋「不急，方便時再過來」。 → 「分派：護理師」。臨床類型即使不急也不會下放給護佐。
    • f51 ［護理端］ 對一筆通報按「取消」而非「處理完成」。 → 從待處理清單消失，稽核記錄動作為「緊急通報取消」。

    08 · 收工 — 正確關閉與重新啟動¶

    測試告一段落時，把服務關乾淨比想像中重要：Windows 上 Ctrl+C 有機會沒把子行程一起帶走，下次啟動就會撞 EADDRINUSE，而且你會以為是程式壞了。

    正常關閉¶

    • j1 ［終端機］ 回到執行 npm run dev 的那個終端機視窗，按一次 Ctrl+C。 → concurrently 會一併停掉後端與兩個 Vite，三色 log 停止輸出，提示字元回到你手上。後端有註冊 shutdown hook，會正常中斷資料庫連線後才結束，不是硬砍。
    • j2 ［終端機］ 如果你另外開了視窗跑 Prisma Studio（§06.7），那個視窗要各按一次 Ctrl+C。 → port 5555 釋出。它是獨立行程，不會被 npm run dev 的 Ctrl+C 帶走。
    • j3 ［病人端］ 關掉病人端與護理端的瀏覽器分頁。 → 病人端每 3 秒輪詢一次、護理端持有一條 SSE 長連線。不關不會壞（後端一起來它們會自動接回），但排查問題時這些背景請求會干擾你判讀 log。

    確認真的關乾淨¶

    這一步別跳過。四個 port 分別是：後端 3000、護理端 5173、病人端 5174、Prisma Studio 5555。

    PowerShell

    Get-NetTCPConnection -LocalPort 3000,5173,5174,5555 -State Listen -ErrorAction SilentlyContinue |
  Select-Object LocalPort, OwningProcess

    Git Bash / cmd.exe

    netstat -ano | findstr /R /C:":3000 " /C:":5173 " /C:":5174 " /C:":5555 "
    • j4 ［終端機］ 執行上面任一版本。 → 沒有任何輸出＝已經關乾淨。若列出 port 與 PID，代表有行程沒被帶走（Windows 上這其實蠻常見的）。
    • j5 ［終端機］ 有殘留的話，用上一步查到的 PID 精準結束它。 → 再查一次應該就沒有輸出了。

    用 PID 結束（把 33244 換成你查到的數字）

    # PowerShell
Stop-Process -Id 33244 -Force

# cmd.exe
taskkill /PID 33244 /F

# Git Bash 要用雙斜線
taskkill //PID 33244 //F

    地雷｜不要一次砍光所有 node

    Get-Process node | Stop-Process -Force 這種寫法非常危險。一般開發機上通常同時有十幾個 node 行程 — 編輯器、語言伺服器、其他專案、甚至 Claude Code 本身都可能是 node。一定要先查出 port 對應的 PID，再針對那個 PID 結束。

    關掉之後，哪些東西還在¶

    項目 關閉服務後會怎樣
    所有資料（帳號、病人、排班、綁定、問卷、求助、稽核） 都在 DATABASE_URL 指向的 SQLite 檔案裡，完全不受影響。要搬移或備份時，主檔與 -wal／-shm 是一組，不要只拿主檔。
    進行中的綁定 不會因為關掉服務而失效，資料庫裡仍是 ACTIVE。下次啟動照常運作；若一直沒人管，超過 BINDING_MAX_HOURS（預設 6 小時）後，背景掃描會自動讓它逾時失效。
    病人端未送出的離線回報 存在瀏覽器的 IndexedDB，關掉分頁不會遺失。下次用同一台平板開啟、且該筆綁定仍有效時會自動補傳。但綁定若已被解除，補傳會被拒絕，資料會在清除流程中一併移除。
    .device-keys.json 留在 apps/api/，下次還能用。除非你重跑 db:seed 或重置資料庫。
    登入權杖 存在瀏覽器 localStorage，下次開啟仍是登入狀態（除非超過 JWT_EXPIRES_IN，預設 8 小時）。

    收工前建議做的兩件事¶

    • j6 ［護理端］ 看即時總覽，把還在「療程進行中」的綁定按「下機結束」。 → 不是必要步驟，但下次進來時資料狀態乾淨，也比較貼近真實流程（病人下機才離開）。
    • j7 ［病人端］ 看病人端有沒有「尚有 N 筆症狀回報等待傳送」。 → 若有，先確認網路正常、等它顯示「已將 N 筆離線暫存的症狀回報送出給護理站」再關 — 否則那筆資料可能會隨著綁定解除被清掉。

    下次重新啟動¶

    • j8 ［終端機］ 在專案根目錄執行 npm run dev 就好。 → 不需要重跑 prisma:migrate 或 db:seed — 資料都還在。build:shared 也不用手動跑，npm run dev 會自動先跑一次。
    • j9 ［終端機］ 若啟動時出現 EADDRINUSE :::3000。 → 就是上次沒關乾淨。回到本節「確認真的關乾淨」，查 PID 然後結束它，再啟動一次。

    補充｜只重新啟動後端

    改了後端程式碼時，npm run dev 用的是 nest start --watch，會自動重新編譯並重新啟動，不必手動關。此時護理端的即時總覽會短暫顯示「串流中斷，改為定時更新」，後端起來後自動變回「即時連線中」。

    怎麼帶憑證¶

    護理端用 JWT；病人端平板用三個標頭（序號＋金鑰，寫入資料時再加 Session Token）。

    取得護理端權杖並呼叫（bash）

    TOKEN=$(curl -s -X POST http://localhost:3000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"workId":"ADMIN001","password":"你的密碼"}' | node -pe 'JSON.parse(require("fs").readFileSync(0)).accessToken')

curl -s http://localhost:3000/api/overview -H "Authorization: Bearer $TOKEN"

    平板端呼叫

    curl -s http://localhost:3000/api/device/session \
  -H 'x-device-serial: TB-01' \
  -H 'x-device-key: <金鑰>'

# 寫入資料時再加上 Session Token
curl -s http://localhost:3000/api/device/symptom-reports/mine \
  -H 'x-device-serial: TB-01' \
  -H 'x-device-key: <金鑰>' \
  -H 'x-session-token: <上一步回應中的 sessionToken>'

    注意｜PowerShell 使用者

    上面兩段的 curl 全部要改成 curl.exe，否則 PowerShell 會用 Invoke-WebRequest 的別名去解析，參數對不上。取權杖那段用了 bash 語法（$(...)、單引號），在 PowerShell 建議改用 Git Bash 執行，或改寫成 Invoke-RestMethod。

    PowerShell 執行 curl 噴「找不到符合參數名稱 i 的參數」 PowerShell 的 curl 是 Invoke-WebRequest 的別名。改打 curl.exe，或改用 Git Bash。
    prisma:migrate 噴 getaddrinfo ENOTFOUND binaries.prisma.sh Prisma 的執行引擎不在 npm 套件裡，是安裝套件時由安裝後腳本另外下載的（約 40MB）。只要 node_modules 是在沒有成功下載引擎的情況下產生的——離線安裝、跳過安裝後腳本、或從別處複製過來而排除了二進位檔——第一次用到 Prisma 指令時就會現場去下載
    病人端在本機開了好幾個分頁，結果只有最後一個認得出自己是哪一台平板 同一個瀏覽器的所有分頁共用同一份儲存空間，後佈建的裝置序號與金鑰會蓋掉先佈建的。這是本機測試環境特有的，正式環境一台平板一支 App、各自獨立
    護理端找不到「解除綁定」的按鈕，但裝置管理頁看得到那台平板正綁著人 解除的入口原本只掛在「當日排班」清單上，而那份清單依排班日期篩選（預設今天）。綁定的排班日期不是今天時，那一列不會出現
    npm install 出現 EPERM／權限不足 ① 關掉還在跑的 node 行程與編輯器；② 專案不要放在 OneDrive 等同步資料夾；③ 把資料夾加入防毒排除清單。仍失敗再以系統管理員身分開 PowerShell 重跑。
    用 .env 的帳密登入卻說「工作ID 或密碼錯誤」 最常見是中文輸入法把 ! 打成全形 ！ — 改用複製貼上。其次是你已經走過強制變更密碼那步（.env 的初始密碼從此失效）。用 §03 的 node 指令可直接判斷是哪一種。
    後端起不來，噴 Error code 14: Unable to open the database file 多半是跳過了 npm run prisma:migrate 就直接 npm run dev。 建資料夾與建檔案是 migration 在做，後端自己不會建。先補跑 a7、a8（a13 確認檔案出現）再啟動。其次才是 DATABASE_URL 打錯：要是絕對路徑、用正斜線、含空白時整串加引號。
    後端起來了，但護理端怎麼登都不行，log 有黃字說未設定 SUPER_ADMIN_* .env 漏填 SUPER_ADMIN_WORK_ID 或 SUPER_ADMIN_INITIAL_PASSWORD，資料庫裡沒有任何帳號。補進 .env 後重新啟動即可，資料庫不必重建（那段邏輯只在「資料庫尚無任何使用者」時執行）。
    病人端一直「裝置尚未佈建」，但金鑰是從 .device-keys.json 複製的 那份檔案對應的是最後一次 seed 的那顆資料庫。中途換過 DATABASE_URL 或在別的資料庫上跑過 prisma:migrate／db:seed，檔案就被覆蓋了，明文金鑰拿不回來（資料庫只存雜湊）。在「裝置管理」重新註冊一台取得新金鑰（f20），或照 §11 重置資料庫。
    每個動作都要等好幾秒 本機 SQLite 單次往返約 2 ms，慢下來多半是資料庫檔案放在網路磁碟機、OneDrive 之類的同步資料夾，或被防毒即時掃描。換到本機磁碟並加入防毒排除清單。
    prisma migrate reset 噴 database disk image is malformed，資料庫剩 0 byte 清空成功、建表失敗（多半是後端還開著，WAL 檔被抓住）。照 §11 的地雷框：關乾淨 → 把 hd.db 與 -wal／-shm 三個一起刪 → prisma:deploy + db:seed 重建。
    後端 log 出現 SQLITE_BUSY 有第二個行程在寫同一個檔案（多半是上次沒關乾淨的後端，或開著的 Prisma Studio）。照 §08 查出 PID 收乾淨，後端是唯一的寫入者。
    EADDRINUSE :::3000（或 5173／5174） 上次沒關乾淨，有殘留行程佔著 port。照 §08 查出 PID 再精準結束；不要一次砍光所有 node 行程。
    前端出現 CORS 錯誤 CORS_ORIGINS 沒包含前端網址。預設是 http://localhost:5173,http://localhost:5174。
    操作到一半一直跳 401 權杖過期（JWT_EXPIRES_IN 預設 8h），或你剛變更密碼／被降權 — 兩者都會主動撤銷既有登入階段。重新登入即可。
    病人端一直停在「裝置尚未佈建」 序號或金鑰不對，或該平板還沒在後端註冊。用 .device-keys.json 的值，或在護理端重新註冊一台取得新網址。
    指派平板的下拉選單是空的 平板需同時符合：已 MDM 納管、未被鎖定、未被其他病人佔用。seed 出來的 15 台預設未納管。
    改了 packages/shared 沒生效 要重跑 npm run build:shared。npm run dev 啟動時會自動跑一次。
    稽核軌跡少了某筆記錄 稽核寫入失敗不會中斷主流程，只在後端 log 留下 error。去終端機找 稽核軌跡寫入失敗。

    地雷｜會刪除所有資料

    下面的指令會清空整個資料庫並重建。只在測試環境執行。

    反覆測試會累積大量帳號、病人與平板。想從乾淨狀態重走一遍手冊時：

    cd apps/api
npx dotenv -e ../../.env -- prisma migrate reset
    • i1 ［終端機］ 先照 §08 把服務關乾淨，再執行重置（會要求你打字確認）。 → 刪除所有資料表 → 重新套用五個 migration → 自動重跑 seed（8 位病人、15 台平板、新的 .device-keys.json）。 後端沒關就跑，多半會停在下面那個 malformed。
    • i4 ［終端機］ 重置後確認資料庫檔案不是 0 byte。 → DATABASE_URL 指向的位置有一個數百 KB 的 hd.db。若看到 0 byte，代表 i1 中途失敗了，照下方的地雷框收拾。
    • i2 ［終端機］ 重新啟動後端。 → 因為資料庫已無任何使用者，後端會依 .env 重新建立 SUPER_ADMIN，並且 passwordChangeRequired 回到 true — 下次登入會再次強制變更密碼。
    • i3 ［護理端］ 從 §03 重新走一遍。 → 全新環境，所有步驟的預期結果與手冊一致。

    地雷｜重置噴 database disk image is malformed，資料庫變成 0 byte

    migrate reset 是兩段動作：先清空、再建表。撞到殘留的 -wal／-shm 檔時，它會清完才失敗，於是你得到一個 0 byte 的 hd.db——舊資料已經沒了，新的也還沒建起來。看起來很嚇人，其實只是做到一半。

    最常見的成因是後端還開著（SQLite 只容許一個寫入者，WAL 檔還被它抓著），其次是上一次不正常結束留下的 WAL 檔。收拾方式固定三步，資料反正已經沒了，刪掉沒有損失：

    ```bash

    ① 先照 §08 確認 3000／5173／5174／5555 都沒有行程監聽¶

    ② 把主檔與兩個附屬檔一起刪掉（路徑換成你的 DATABASE_URL） rm -f /d/hd-data/hd.db /d/hd-data/hd.db-wal /d/hd-data/hd.db-shm¶

    PowerShell：Remove-Item D:\hd-data\hd.db*¶

    ③ 回專案根目錄重建（不必再跑 reset） npm run prisma:deploy -w @hd/api npm run db:seed ```¶

    跑完的結果與 i1 成功時完全相同：五個 migration、8 位病人、15 台平板、新的 .device-keys.json。 三個檔案一定要一起刪，只刪主檔的話，殘留的 WAL 會再讓下一次建表失敗一次。

    補充｜你目前這個資料庫

    2026-09-10 改用本機 SQLite 時是從零開始建立的，Supabase 上的舊資料依《資料庫使用規範》第 15 條不遷移、直接捨棄。之後殘留的少量資料是驗收腳本留下的（工作ID 以 VERIFY／V2～V6 開頭、病歷號以 HD-VERIFY／HD-V2／HD-TEST-V3 之類的前置字開頭），不影響功能。

    說明｜Supabase 已撤出

    測試資料庫曾放在 Supabase（2026-09-07 由孟買搬到東京）。2026-09-10 起改為開發者本機的 SQLite 檔案，Supabase 專案已於 2026-09-11 刪除。原本本節的「更換 Supabase 區域」步驟已不適用，改為以下內容。

    換一個新的資料庫檔案¶

    • k1 ［終端機］ 先照 §08 把服務關乾淨。 → 3000／5173／5174／5555 都沒有行程監聽。後端是唯一的寫入者，換檔案前一定要先停。
    • k2 ［終端機］ 把 .env 的 DATABASE_URL 改成新的絕對路徑（專案目錄外、本機磁碟）。 → 檔案不必事先存在。
    • k3 ［終端機］ 建表並灌測試資料。 → 資料夾與檔案自動建出來，套用五個 migration、8 位病人、15 台平板，並產生全新的 apps/api/.device-keys.json。舊的佈建網址全部作廢 — 這一步是單向的，原本那顆資料庫的平板明文金鑰不會留下副本（見 §01 a13 下方的地雷框）。要留著回頭用的話，先把舊的 .device-keys.json 另存一份再往下走。
    • k4 ［終端機］ 啟動並看後端 log。 → 出現「已連線至 SQLite：journal_mode=WAL、foreign_keys=ON、busy_timeout=5000ms、synchronous=FULL」與「已建立初始最高權限帳號」。第一次登入會再次強制變更密碼。

    步驟 k3–k4

    npm run prisma:deploy -w @hd/api
npm run db:seed
npm run dev

    線上備份與還原演練¶

    • k5 ［護理端］ 以護理站管理者登入 →「系統管理」→「資料庫與備份」→「立即備份」。 → 備份歷程多一列「成功」，有檔名、大小與 SHA-256；稽核軌跡多一筆「資料庫線上備份」。 BACKUP_DIR 裡備份檔旁邊多一個同名的 .sha256（0929 起）。服務起不來、查不到備份歷程時，雜湊從這個檔拿。
    • k6 ［終端機］ 把剛才那份備份還原到另一個路徑。 → 依序印出雜湊比對相符、完整性檢查 ok、各資料表筆數。不會碰到使用中的資料庫。

    步驟 k6

    npm run db:restore -- --from <BACKUP_DIR 裡的備份檔> --to <新的絕對路徑> --sha256 <備份旁邊同名 .sha256 檔的第一欄>

    地雷｜不要直接複製資料庫檔案

    服務執行中直接複製 .db 可能拿到不一致的狀態，而且 WAL 模式的 -wal／-shm 與主檔是一組，只拿主檔會漏資料。備份一律用上面的線上備份（VACUUM INTO），備份檔也不得放到雲端硬碟或個人隨身碟（《資料庫使用規範》8.1）。
