    迭代 25 手動測試 — 緊急通報：頂端橫幅、床邊前速覽、護理紀錄連動¶

    《完整手動測試手冊》的分冊之一，對應《實作規格書》4.25 節。共用的環境準備、啟動與疑難排解都在主手冊，這一冊只寫迭代 25 的部分。操作端色籤（護理端／病人端／終端機／資料庫）的意思見主手冊 §00。項次用 ai（實作規格書 4.25：手動測試分冊 ai），從 ai1 起。

    摘要¶

    這一冊驗四件事（項次 ai1～ai34，自動化另跑 npm run verify:iteration25）：

    • 專業版頂端的求助橫幅接手後藏起來、結案或取消之後不再冒回來，斷線期間的求助照樣出現
    • 簡易版點紅框或還沒人接的求助只開床邊前速覽、不確認，速覽裡的「我接手」才確認
    • 速覽上的數值與院方資料一致、不上色、不判讀、讀到 0 不顯示，1366×768 不捲動、不蓋紅框列
    • 臨床組求助結案時同時建好「求助處置」護理紀錄草稿，事件時間是按下求助的時間，結果補改時草稿跟著改、簽核後不動
    • 分析與七題答覆在《緊急通報的處理流程與護理紀錄連動》
    標記 意思
    🛠 開發機 npm run dev:hospital-sim、後端帶 HOSPITAL_API_BASE_URL=http://localhost:8090/dialysislist.php 啟動、npm run dev:nurse；資料庫先套用新遷移（npm run prisma:deploy -w @hd/api 或 db:update）
    📐 目標尺寸 護理站 1366×768 與 1920×1080
    🖥 兩個視窗 同一台電腦開兩個瀏覽器視窗：一個簡易版、一個專業版（或兩台電腦），看一邊的動作在另一邊怎麼顯示

    §25.1 頂端求助橫幅¶

    • ai1 ［護理端］ 🖥 一個視窗開專業版（任何一頁），另一個開簡易版；把兩位正在透析的模擬病人各配一台平板。［病人端］ 其中一台按「我需要協助」→「頭暈、冒冷汗、快昏倒」→「非常緊急」。 → 專業版頂端出現那一則求助橫幅；簡易版上面一條紅框出現那一床。
    • ai2 ［護理端］ 簡易版點紅框，在速覽裡按「我接手」。 → 專業版的橫幅消失（已接手的不佔位置，迭代 14.4 的規則）。
    • ai3 ［護理端］ 簡易版點那一格的求助、點一個處理方式（等 8 秒送出）。 → 專業版的橫幅不再出現（1015 以前結案之後會冒回來，見規畫文件第 2.2 節）。
    • ai4 ［病人端］ 再按一次求助。［護理端］ 專業版緊急通報頁那一筆按「取消」。 → 橫幅出現後，取消之後不再出現。
    • ai5 ［護理端］ 專業版拔掉網路線（或瀏覽器開發者工具設離線）約 30 秒，期間［病人端］按一次求助；接回網路。 → 先出現斷線示警；接回來之後那一則照樣出現在頂端（比求助舊的快照找不到不拿掉）。之後照 ai2、ai3 收掉。
    • ai6 ［終端機］ npm run verify:iteration14-4。 → 照樣全部通過（橫幅元件本身沒動）。

    規則寫在 realtime-context.tsx 的 pruneAlerts：伺服器在求助送到之後產生的狀態裡找不到它才拿掉；送到後 5 秒內的狀態不算（後端寫進資料庫到快取更新之間的寬限）。所以在 5 秒內就取消的那一則，最晚在下一次輪詢（15 秒）拿掉。

    §25.2 看是看、接是接¶

    • ai7 ［病人端］ 按一次緊急求助。［護理端］ 📐 簡易版點紅框。 → 中間的平板區被一張「床邊前速覽」蓋住；上面的紅框列與右邊兩框照舊看得到，紅框照閃。
    • ai8 ［護理端］ 按 Esc 關掉速覽，再點同一個紅框、按 ×；再開一次、點速覽外面。 → 三種都關得掉；那一則仍是待處理（紅框還在、格子上還是沒人接的樣子）。［終端機］ GET /api/help-requests/:id 的 status 是 PENDING，稽核軌跡沒有「接收通報」。
    • ai9 ［護理端］ 點格子上那一則求助（不是紅框）。 → 一樣只開速覽，不會展開處理方式。
    • ai10 ［護理端］ 速覽裡按「我接手」，記下按的時間。 → 速覽關掉；格子變成已接手的樣子，右邊多一顆 id-card 小圖示。［終端機］ 那一則的 acknowledgedAt 是按下那一刻；稽核軌跡多一筆「接收通報」，時間相同。
    • ai11 ［護理端］ 點格子的 id-card。 → 同一份速覽重新開啟；上面沒有「我接手」，改寫「○○ 已接手」。
    • ai12 ［護理端］ 點已接手的那一格求助。 → 照舊展開處理方式的圖示列（結案的操作沒變）。
    • ai13 ［護理端］ 專業版緊急通報頁，每一筆多一顆「病人簡介」；點它。 → 開出來的與簡易版同一份內容（同一個元件）；卡片上原本的「我接手」照舊在，速覽裡的「我接手」也能用。

    §25.3 速覽的內容與版面¶

    • ai14 ［護理端］ 📐 1366×768 開速覽，對照模擬院方 API 那一位病人的資料（［終端機］ curl http://localhost:8090/dialysislist.php）。 → 左欄：最新一筆的血壓與脈搏（附時間）、體溫、透析前與理想體重與兩者的差（「多 2.4 kg」這樣的文字）、設定脫水量與它的組成（目標＋輸液＋食物）、血流速與透析液流速、透析液溫度、Ca、傳導度、Heparin、透析器、血管通路、透析前問卷、院方資料最後一筆的時間——逐欄與院方資料一致。
    • ai15 ［護理端］ 看兩張折線圖。 → 血壓那一張有收縮壓、舒張壓、靜脈壓、脈搏四條線，線型都不一樣、線尾寫名稱與數值；脫水量那一張有累積脫水量與一條橫的虛線「設定 N L」；兩張都有一條直的虛線「求助 HH:MM」，位置在按下求助的時間；點數與本次透析的紀錄筆數一致（全是 0 的那一筆不算）。
    • ai16 ［護理端］ 看整份速覽有沒有判讀。 → 沒有預測機率、風險分層、高中低圖示、輕重長條、低於門檻的塗色、正常範圍、AI 摘要；數字與線都是同一種顏色。院方回 0 的欄位（例如模擬丙的體溫）整列不出現。
    • ai17 ［護理端］ 看下面的近期求助與待追蹤。 → 近期求助只列本次與前 3 次療程（每一列：日期時間、類別、處理方式／結果，同一類別的標「同類別」）；超過 6 則寫「還有 N 則」。待追蹤列這位病人還沒結束的追蹤事項。沒有的時候各寫一句（「本次與前 3 次療程沒有其他求助」「沒有待追蹤事項」「這次還沒填透析前問卷」「這次療程沒有院方資料」），不留空白區塊。
    • ai18 ［護理端］ 📐 1366×768 與 1920×1080 各開一次速覽，近期求助塞滿（同一位病人前幾次療程多按幾次求助）。 → 整頁不捲動、速覽本身也不捲動；紅框列與右邊兩框都沒被蓋住。

    §25.4 結案時建好求助處置草稿¶

    • ai19 ［病人端］ 按「頭暈、冒冷汗、快昏倒」，附註寫幾個字。［護理端］ 接手，等院方資料多一筆量測之後，結案：點「調整姿勢」（簡易版）或專業版結案登記選兩個處理方式、勾追蹤事項「需加強衛教」。 → ［護理端］ 護理紀錄頁選那一次療程：多一筆「求助處置」草稿，卡片寫「來自 HH:MM 的求助」，事件時間是病人按下求助的時間（不是結案、不是現在）。
    • ai20 ［護理端］ 看那一筆的四段（DART）。 → D：「HH:MM 病人以平板求助：頭暈、冒冷汗、快昏倒，附註：「…」」、透析前問卷有症狀的題目（標明病人自述）、按下求助前最近一筆量測；A：「HH:MM 按下求助、HH:MM 接手；處理方式：…」（依點選順序）；R：「處理結果：…」與按下之後的量測；T：「已列追蹤事項：需加強衛教」。
    • ai21 ［護理端］ 看整份文字。 → 沒有姓名、病歷號、病名；沒有任何「到達」字樣（到達床邊的開關關著，也不拿接手時間頂替）。
    • ai22 ［護理端］ 系統管理把護理紀錄格式改成 SOAP，再跑一次 ai19（換一個臨床組類別）。 → 草稿是 S／O／A／P；A（評估）段是空的；S 是病人自述、O 是量測與問卷、P 是時間線、處理方式與結果。做完把格式改回 DART。
    • ai23 ［病人端］ 分別按「口渴」（非臨床組）、「頭痛」後護理師結案時結果選「病人自行取消」、「皮膚癢」後護理師直接「取消」。 → 這三則都沒有草稿。

    §25.5 一則一筆、補改、簽核後不動¶

    • ai24 ［護理端］ ai19 那一則結案後 60 分鐘內，簡易版點格子上的「已結案」標記補改結果（或 ［終端機］ POST /api/help-requests/:id/outcome）。 → 護理紀錄頁那一筆草稿的 R 段跟著改；事件時間不變；稽核「補改處理結果」寫明草稿已跟著重組。
    • ai25 ［護理端］ 把那一筆簽核，再補改一次結果。 → 已簽核的記錄一個字都沒變。
    • ai26 ［資料庫］ SELECT source_help_request_id, COUNT(*) FROM nursing_records WHERE source_help_request_id IS NOT NULL GROUP BY 1 HAVING COUNT(*) > 1。 → 沒有任何一列（一則求助最多一筆，唯一鍵擋著）。「草稿建不起來時結案也不成立」由 verify:iteration25:api 步驟 6 驗（先放一筆佔位再結案，回 409、求助仍是已接手）。

    §25.6 護理紀錄頁：來源、依求助建立、改套範本¶

    • ai27 ［護理端］ 護理紀錄頁點「來自 HH:MM 的求助」。 → 開出那一則的床邊前速覽（唯讀，沒有「我接手」）。
    • ai28 ［護理端］ 右上「依求助建立」。 → 列出這次療程已結案但沒有記錄的求助（ai23 的口渴與病人自行取消的頭痛）；點「建立求助處置記錄」，多一筆草稿、事件時間是按下求助的時間，那一列從清單消失。取消的「皮膚癢」不在清單裡。
    • ai29 ［護理端］ 一筆求助處置草稿按「改套範本」，選「透析中低血壓處置」補勾，按「套用範本」。 → 段落改由範本的勾選組出，D（或 S）段最前面仍是病人按下求助的那一句；事件時間不變、量測照事件時間前後帶；稽核多一筆「求助處置記錄改套範本」。之後補改結果不再重組這一筆。
    • ai30 ［護理端］ 左邊「新增事件記錄」的事件時間欄。 → 欄位底下寫「請改成發生的時間」。
    • ai31 ［護理端］ 系統管理開啟 AI 總開關（模擬模型即可），在一筆求助處置草稿按「AI 潤飾」。 → 初稿照四段回來，沒有新增勾選與求助以外的事實、數值或判斷（提示照迭代 17.8 的規則）；關掉 AI 總開關之後整條照樣走得完。

    §25.7 自動化驗收¶

    • ai32 ［終端機］ npm run verify:iteration25（不需要後端）。 → 全部通過（實際跑橫幅修剪、院方欄位解析、求助處置的段落組法，再檢查簡易版與專業版的接法、速覽的版面與用字、遷移只做加法，與 14、14.4、17.2、17.8 的回歸、check:ui、check:ui:design、check:egress）。
    • ai33 ［終端機］ 🛠 模擬院方 API 與後端照檔頭說明啟動、AI 總開關與手持裝置的功能關著：npm run verify:iteration25:api。 → 八個步驟全部通過；結束時模擬服務切回依時間產生、平板解除綁定並停用、床位清單與護理紀錄格式還原。
    • ai34 ［終端機］ npm run verify:iteration15:api、npm run verify:iteration16:api、npm run verify:iteration17-8:api。 → 照樣通過（多收的欄位不上病人平板，迭代 16 那一支的「不顯示的欄位一個都找不到」照樣成立）。
