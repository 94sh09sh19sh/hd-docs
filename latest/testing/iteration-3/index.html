    迭代 3 手動測試 — 封閉網路化與資料層遷移¶

    《完整手動測試手冊》的分冊之一，對應《實作規格書》v2.0 4.1 節。 共用的環境準備、啟動、關閉與疑難排解都在主手冊，這一冊只寫迭代 3 的部分。 操作端色籤（護理端／病人端／終端機／資料庫）的意思見主手冊 §00。

    迭代 3 不新增任何病人看得到的臨床功能，做的是後面每個迭代都踩在上面的地基：資料層搬到本機 SQLite、系統不得連向院外、模型供應者與臨床資料來源兩個介面層、功能開關中心、備份與還原，以及取代推播的常駐總覽螢幕。 地基壞掉時上層功能不會出錯，只會慢慢歪掉，所以這一冊的每一項都值得走過一次。

    3.1 · 資料層：SQLite 必開設定與資料庫位置¶

    • l1 ［終端機］ 啟動後端，看第一段 log。 → 出現「已連線至 SQLite：journal_mode=WAL、foreign_keys=ON、busy_timeout=5000ms、synchronous=FULL」。四項缺一都算沒過。
    • l2 ［護理端］ 以護理站管理者進「系統管理 → 資料庫與備份」，看「資料庫運作狀態」。 → 九格逐項顯示：journal_mode ✓ WAL、外鍵檢查 ✓ 開啟、忙碌等待 ✓ 5000 ms、synchronous ✓ FULL、統計與報表唯讀連線 ✓ query_only、資料庫檔案與 WAL 檔案大小、每日排程備份、最近一次成功備份。畫面上看不到資料庫檔案的實際路徑。
    • l3 ［護理端］ 看「統計與報表唯讀連線」那一格。 → 值是 query_only 而不是「可寫入」。這條通道是給統計與報表用的，寫不進去才是對的（規範 7.1）。
    • l4 ［終端機］ 確認資料庫檔案在專案目錄外，且 repo 是乾淨的。 → .env 的 DATABASE_URL 指向專案外的絕對路徑；git status --short 沒有任何 .db、.db-wal、.db-shm 冒出來（規範 7.2）。
    • l5 ［終端機］ 看 migration 目錄。 → 五個目錄，第一個是 20260910110540_init、第二個是 20260910111354_iteration3_closed_network。遷移時整組重建過，Supabase 時期的 migration 已經不在。
    grep DATABASE_URL .env
git status --short
ls apps/api/prisma/migrations

    說明｜為什麼 synchronous 要 FULL

    開發環境放寬成 NORMAL 只影響「斷電當下那一筆」，但臨床現場的斷電不會事先通知。畫面上這一格若顯示 ✗ NORMAL，代表環境變數被改過，正式環境不得如此。

    3.2 · 三台裝置同時操作不出現 SQLITE_BUSY¶

    • l6 ［病人端］＋［護理端］ 三處同時動作：一台平板送症狀問卷、另一台平板按求助、護理端開著常駐總覽螢幕，連續操作一分鐘。 → 每一個動作都成功，沒有任何一筆出現「資料庫忙碌中」或 500；總覽螢幕照常即時更新。
    • l7 ［終端機］ 回頭看後端 log。 → 全程沒有 SQLITE_BUSY。WAL 加上 5 秒忙碌等待就是為了這件事；真的出現就要回頭確認 l1 的四項設定。

    3.3 · 零院外連線盤點（FR-S07）¶

    • l8 ［終端機］ npm run check:egress → 「發現 0 筆院外連線」。掃描範圍含原始碼與前端資源（字型與 CDN 也算）、建置產物、套件相依、推播訂閱、.env 與 .env.example、Dockerfile 與 docker-compose。
    • l9 ［終端機］ 故意在護理端的 index.html 加一行指向 Google Fonts 的 <link>，重跑一次。 → 這次掃得出來，逐列指出檔案與網址，結束狀態為 1。確認完把那一行刪掉再跑一次，回到 0 筆。
    • l10 ［病人端］ 拔掉網路線（或關閉 Wi-Fi），重新整理護理端與病人端。 → 兩端畫面、字型與圖示都正常，沒有等待外部資源造成的空白或方框字。全部資源都在院內。

    說明｜哪些東西不算

    文件同步工具（scripts/docs-*.mjs）是開發者電腦上的工具，不屬於系統、不會部署到院內，不在掃描範圍。LLM_PROVIDER=onprem 時的 LLM_ENDPOINT 是 SRS 第 6 章明列的唯一例外，腳本會列出但不計入。

    3.4 · 唯讀角色預設全擋（實作規格書 3.1）¶

    • l11 ［護理端］ 以最高權限帳號進「帳號審核 → 帳號與權限」，把一個測試帳號的角色改成「醫院管理層（唯讀）」。 → 角色欄變更並寫入稽核；該帳號既有的登入階段一併作廢。
    • l12 ［護理端］ 以那個帳號重新登入。 → 登得進去，但沒有任何臨床操作可用 — 醫院管理層在 L1 聚合儀表板（迭代 8）之前沒有任何權限。
    • l13 ［終端機］ 以那個帳號的權杖直接打一支沒有標示開放給唯讀角色的 API（例如建立病人）。 → 403。預設全擋：後端只放行明確標示開放的端點，不是靠前端少畫幾顆按鈕。
    • l14 ［護理端］ 把角色改成「稽核／法規（唯讀）」再登入一次。 → 查得到稽核軌跡與 AI 呼叫紀錄，其餘一律擋下；唯讀角色也不得被授予審核權限。測完把角色改回原本的。

    3.5 · 功能開關中心（FR-S08）¶

    • l15 ［護理端］ 進「系統管理 → 功能開關」。 → 十個開關分四群：高風險功能（風險分層提示、療程中預警、劑量調整參考）、AI 輔助功能（總開關、允許真實病人資料進入 AI 流程）、閒置輪播（三層）、績效與獎勵（個人層級績效 L3、獎勵計分）。乾淨的環境裡全部是關閉。
    • l16 ［護理端］ 嘗試開啟「風險分層提示」。 → 被擋下：「未符合開啟條件：規則引擎與規則版本管理於迭代 7 實作，目前沒有附書面依據的規則版本；FR-R08 書面確認亦尚未登記（Q-02、Q-03）。」另外兩項高風險功能同理。
    • l17 ［護理端］ 隨便開一個開關，但核准依據留空（或只打一個字）。 → 送不出去。開與關都要登記依據，不是只有開啟才要。
    • l18 ［護理端］ 以最高權限帳號開啟「AI 輔助功能總開關」，依據填「迭代 4 驗收」。 → 開得起來（開啟條件是「模型供應者已設定且健康檢查通過」，預設的模擬供應者會通過）；「目前是否符合」欄顯示 ✓ 符合。
    • l19 ［護理端］ 嘗試開啟「允許真實病人資料進入 AI 流程」。 → 在預設的模擬供應者下被擋：開啟條件是「模型供應者為院內地端推論（onprem）」。這是資料不出院的最後一道閘門，不靠人記得。
    • l20 ［護理端］ 把 l18 開起來的總開關關掉。 → 立刻關閉，不檢查任何條件 — 出事時要能馬上停損（FR-R07）。
    • l21 ［護理端］ 以一般護理師 N001 登入看「系統管理」，再以護理長看同一頁。 → N001 看不到系統管理；護理長切得動輪播與高風險等開關，但 AI 那兩項標「僅限系統管理者」。
    • l22 ［終端機］ 在輪播三層全關的狀態下，用平板的 Session Token 直接打輪播端點。 → 404，不是 403、也不是空清單。開關關閉時介面與端點一起消失（實作規格書 3.7）。
    • l23 ［護理端］ 進「稽核軌跡」查剛才這幾步。 → 查得到「開啟功能開關」「關閉功能開關」與「功能開關切換遭拒：未符合開啟條件」，內容包含開關名稱、前後狀態與填的依據。被擋下的嘗試也留紀錄。

    3.6 · 模型供應者介面層（FR-S06）¶

    • l24 ［護理端］ 進「系統管理 → 模型供應者」。 → 顯示目前供應者、資料是否離開院內（模擬供應者為「否」）、模型識別字、端點主機、健康檢查 ✓ 通過、可用模型。
    • l25 ［護理端］ 在「介面層連線測試」輸入一段合成提示（例如「請用三句話說明透析後量體重的用意」），不勾核取方塊，送出。 → 看得到模型回應，以及「送出的提示（已去識別化，移除 N 處）」。這條測試走的是與正式功能完全相同的閘道。
    • l26 ［護理端］ 勾選「此內容含真實病人資料（用來確認閘道會擋下）」再送一次。 → 被擋下，不會有模型回應；下方呼叫紀錄多一列，結果欄是「已擋下」、資料類別欄是「真實病人資料」。
    • l27 ［護理端］ 看「呼叫紀錄」表頭。 → 時間、功能、供應者／模型、結果、去識別化（是／否與處數）、資料類別、操作者、耗時共八欄；下方註明提示與輸出只存去識別化後的版本。
    • l28 ［終端機］ 把 .env 的 LLM_PROVIDER 改成 lab，LLM_ENDPOINT 與 LLM_MODEL_ID 照下面填，重新啟動後端，回到同一頁。 → 後端 log 出現「模型供應者：實驗室 API（院外，僅得送合成資料）」與黃字「目前模型供應者位於院外：帶真實病人資料的請求一律擋下」。頁面上「目前供應者」跟著變，「資料是否離開院內」顯示「院外：僅得送合成資料」。只改設定，一行程式都沒有動（《實作規格書》4.2 驗收 3）。
    • l29 ［護理端］ 在 lab 之下重做 l26。 → 一樣被擋，稽核軌跡查得到「AI 呼叫遭擋下：真實病人資料」（4.2 驗收 4）。確認完把三個變數改回原值（LLM_PROVIDER=mock，另外兩個留空）並重新啟動。

    .env 這兩行：本機不會有人接的位址即可，這兩步都不需要真的叫得動模型

    LLM_ENDPOINT=http://127.0.0.1:9/v1
LLM_MODEL_ID=stub-model

    注意｜健康檢查顯示「失敗」是預期的

    這兩步驗的是閘道，不是模型：l28 驗「換供應者只要改設定」，l29 驗「真實病人資料在送出之前就被擋下」—— 擋下的判斷發生在呼叫端點之前，所以端點連不連得上都不影響結果。頁面上健康檢查那一格顯示失敗、 可用模型是空的，都是正常的；真要在 lab 之下跑一次合成資料的完整呼叫，verify:iteration4 第 12 步 已經用本機假端點自動做過同一件事，不必自己架一台。

    地雷｜這一節請只輸入合成內容

    「介面層連線測試」不是沙盒，它與正式功能共用同一條閘道，紀錄一樣會留。《資料庫使用規範》第 10 條：絕對禁止輸入任何接近真實病人的資訊。

    3.7 · 臨床資料來源介面層：人工輸入（FR-S05）¶

    • l30 ［護理端］ 以護理站管理者或護理長進「臨床數值」，選一位病人，新增一列乾體重但資料時間留空，送出。 → 被擋下並指出是哪一列缺資料時間。每一筆都必須帶「何時量的」，病人端看到數值時會一併顯示。
    • l31 ［護理端］ 把乾體重填成 62.55（超過該項允許的小數位數）。 → 逐列標出問題，不會自作主張四捨五入。
    • l32 ［護理端］ 一次送三列，其中一列故意填錯。 → 整批退回，另外兩列也沒有寫進去。臨床數值只對一半，比完全沒有更危險。
    • l33 ［護理端］ 修正後送出，接著對同一資料時間再送一次不同的值，勾選「同一資料時間已有數值時，覆蓋並保留前一版」。 → 成功，清單上舊值標「已被覆蓋（保留前一版）」、新值標「現行」。舊值不會消失。
    • l34 ［護理端］ 不勾那個核取方塊，再送一次同一資料時間。 → 被擋下並要求確認，不會默默覆蓋。
    • l35 ［護理端］ 以一般護理師 N001 開同一頁。 → 沒有寫入表單；直接打 API 回應 403（缺 clinical-value:manage）。
    • l36 ［護理端］ 「稽核軌跡」查最近紀錄。 → 查得到「臨床數值匯入」與（l32 那次）「臨床數值匯入遭拒（整批未寫入）」，含批次編號與筆數。

    檔案匯入（Excel／CSV）與欄位對應是迭代 6 才加上的，測試項在《迭代 6 分冊》§6.11、§6.12。

    3.8 · 備份與還原（FR-S09）¶

    • l37 ［護理端］ 「系統管理 → 資料庫與備份」看「每日排程備份」那一格。 → 有設 BACKUP_DIR 時顯示每日排程時刻；沒設時顯示「未設定 BACKUP_DIR」且該格為 ✗。
    • l38 ［護理端］ 按「立即備份」。 → 備份歷程多一列：開始時間、方式、狀態「成功」、檔名、大小、SHA-256、執行者、耗時；「最近一次成功備份」跟著更新。
    • l39 ［護理端］ 看該表下方的說明。 → 寫明備份一律以線上備份機制產生、放在伺服器的 BACKUP_DIR、不得移到雲端或個人隨身碟，以及留存世代數定案前不自動刪除舊備份。
    • l40 ［終端機］ 還原演練：照主手冊 §12 的 k6、k7 走一次。 → 雜湊比對相符、完整性檢查 ok、各資料表筆數印出；把 DATABASE_URL 指向還原檔重新啟動後，帳號、病人與稽核紀錄都在。
    • l41 ［護理端］ 以一般護理師開「系統管理」。 → 沒有「資料庫與備份」分頁；直接打 API 回應 403（缺 backup:manage）。

    3.9 · 常駐總覽螢幕（FR-N12，P0）¶

    推播在 0910 需求改版時整個移除，這台螢幕因此是唯一保證通報被看見的地方。它的每一個失效狀態都必須大聲顯示出來，而不是默默停住。

    • l42 ［護理端］ 以具「即時總覽」權限的帳號登入 →「總覽螢幕模式」。 → 進入前的畫面說明「按下後會啟用通報音效、進入全螢幕，並要求螢幕不休眠」，並註明瀏覽器規定音效必須由人按一下才能啟用，每次開啟這個畫面都要按一次。
    • l43 ［護理端］ 按「開始」。 → 進入全螢幕；底部狀態列顯示「最後更新」時間、「防休眠：已啟用」與「音效：開啟」。防休眠只在 HTTPS 或 localhost 下可用，顯示「不支援」或「被拒絕」時畫面會常駐提示要改在作業系統關閉螢幕休眠與螢幕保護程式。
    • l44 ［護理端］ 按「試播一聲，確認喇叭有聲音」。 → 聽得到提示音。聽不到就先解決喇叭或瀏覽器的音效權限，不要等到真的有通報才發現。
    • l45 ［護理端］ 看畫面配置。 → 上半「待處理求助」、下半「療程進行中」，兩區各有筆數；字級明顯大於一般畫面，站在護理站看得清楚；每筆顯示床號、按下時間與「按下，尚未接收」，平板沒回應時另標「平板未回應」。
    • l46 ［病人端］ 用兩台平板先後按求助，其中一台選「非常緊急」。 → 非常緊急那筆排在最前，其次是尚未有人接收的，同級依按下時間先後；每來一筆都會發出提示音（第一次載入既有的通報不會響，避免一開螢幕就大作）。
    • l47 ［護理端］ 放著不要接收，等一分鐘。 → 未接收的通報每 60 秒再提醒一次。
    • l48 ［終端機］ 停掉後端。 → 最慢 45 秒內整個畫面出現紅框閃爍與「連線中斷」橫幅，並顯示「正在自動重新連線（第 N 次）・請同時留意床邊呼叫鈴」。拔網路線的話另外顯示「本機網路已離線」。
    • l49 ［終端機］ 把後端啟動回來。 → 不必手動重新整理，橫幅自動變回「即時連線中」，「最後更新」繼續前進。
    • l50 ［護理端］ 讓登入權杖過期（或在另一個分頁登出）。 → 全螢幕蓋住「登入已逾時，總覽螢幕已停止更新／新的通報不會再出現在這台螢幕上，請立即重新登入」，並有「重新登入」按鈕。不會默默停在舊畫面上。
    • l51 ［護理端］ 按「關閉音效」，再按「離開總覽螢幕」。 → 關閉音效後畫面常駐提示「音效已關閉：新通報不會發出聲音」；離開後回到一般護理端畫面，螢幕不休眠的要求一併解除。
    • l52 ［護理端］ 看畫面上的內容有沒有做分級判斷。 → 沒有。總覽螢幕原樣呈現病人自己填的內容與自選的急迫度，不標任何風險等級 — 那屬於迭代 7 的高風險功能，閘門未開。

    3.10 · 稽核軌跡的四類新事件（FR-S02）¶

    • l53 ［護理端］ 「稽核軌跡」依動作篩選，確認迭代 3 新增的四類都查得到。 → 開關切換（開啟功能開關／關閉功能開關／功能開關切換遭拒）、備份（資料庫線上備份）、匯入（臨床數值匯入／臨床數值匯入遭拒）、AI 呼叫（AI 模型呼叫／AI 呼叫遭擋下：真實病人資料）。每一筆都有操作者、時間與內容摘要。

    3.11 · 自動化驗收¶

    • l54 ［終端機］ npm run verify:iteration3 → 十個步驟全部 ✓，最後顯示「驗收結果：全部通過 ✓」，並在結尾提醒驗收 1 與驗收 5 需人工執行。涵蓋 SQLite 必開設定與唯讀連線、資料庫檔案位置、功能開關、模型供應者閘道、臨床資料來源介面層、唯讀角色、三處併發、備份與還原、零院外連線、稽核四類事件。
    • l55 ［終端機］ 重跑 npm run verify:acceptance 與 npm run verify:iteration2。 → 兩支全綠。遷移不得改變任何既有行為（4.1 驗收 2），這兩支就是那條界線。

    3.12 · 實機驗收（兩項尚未執行）¶

    說明｜為什麼另外列

    4.1 節七條驗收標準中，第 1 條（全新環境離線建置）與第 5 條（常駐總覽螢幕連續 4 小時、拔網路示警與自動重連）需要實機與實際時間，無法由驗收腳本代勞，其餘五條已由 verify:iteration3 涵蓋並通過。 狀態：兩項皆尚未執行（2026-09-11）。 開發環境已先做過模擬：停掉後端後總覽螢幕數秒內出現紅框與斷線橫幅，後端恢復後自動回到「即時連線中」；伺服器不在時重新載入頁面，也不會掉回登入畫面。

    驗收 1 · 全新環境只設 DATABASE_URL，全程離線建置¶

    • m1 ［終端機］ 在專案目錄外的一個全新位置 clone 專案並安裝相依套件。 → 這一步需要網路（下載套件），是整個驗收唯一允許連網的步驟。
    • m2 ［終端機］ 中斷網路（拔網路線或關閉 Wi-Fi），確認真的連不出去。 → 開瀏覽器連任何外部網站都失敗。之後的步驟全程維持離線。
    • m3 ［終端機］ 建立 .env，只填 DATABASE_URL（指向一個尚不存在、專案目錄外的檔案）、JWT_SECRET 與兩個 SUPER_ADMIN_*。 → 其餘一律留空，採程式內預設值。
    • m4 ［終端機］ 依序執行 build:shared、prisma:migrate、db:seed。 → 三個步驟都成功，沒有任何連線逾時或下載失敗；DATABASE_URL 指向的檔案被建立出來。
    • m5 ［終端機］ 執行 npm run dev，看後端 log。 → 出現「已連線至 SQLite：journal_mode=WAL、foreign_keys=ON、busy_timeout=5000ms、synchronous=FULL」與「已建立初始最高權限帳號」；三個網址都能開啟並登入。
    • m6 ［終端機］ 執行零院外連線盤點。 → 結果為「發現 0 筆院外連線」。

    步驟 m1–m6

    # m1（需網路）
git clone <專案 repo> hd-offline-test
cd hd-offline-test
npm install

# m2 之後全程離線
cp .env.example .env   # 填 m3 的四個變數
npm run build:shared
npm run prisma:migrate
npm run db:seed
npm run dev

# 另開一個終端機
npm run check:egress

    驗收 5 · 常駐總覽螢幕連續 4 小時，拔網路明顯示警、恢復後自動重連¶

    用預定放在護理站的那台螢幕或平板做（位置與硬體待 Q-10 確認；確認前可用任一台會長時間開著的電腦）。

    • m7 ［護理端］ 以具「即時總覽」權限的帳號登入 →「總覽螢幕模式」→ 按「開始」。 → 進入全螢幕；畫面底部顯示「防休眠：已啟用」「音效：開啟」。防休眠只在 HTTPS 或 localhost 下可用，顯示「不支援」時要改在作業系統關閉螢幕休眠與螢幕保護程式。
    • m8 ［護理端］ 放置 4 小時，期間不碰這台機器。 → 螢幕沒有休眠、沒有出現斷線橫幅，底部「最後更新」時間持續前進。
    • m9 ［病人端］ 4 小時期間，用一台已綁定的平板按一次求助。 → 總覽螢幕在數秒內出現該筆通報並發出提示音；無人接收時每 60 秒再提醒一次。
    • m10 ［護理端］ 拔掉總覽螢幕那台機器的網路線（或關閉 Wi-Fi）。 → 最慢 45 秒內整個畫面出現紅框閃爍與「連線中斷」橫幅，並顯示正在第幾次重新連線。
    • m11 ［護理端］ 斷線期間用平板再按一次求助，然後接回網路。 → 十幾秒內自動回到「即時連線中」，不需要任何人操作，斷線期間的那筆通報也補上畫面。

    注意｜登入權杖 8 小時到期

    JWT_EXPIRES_IN 預設 8 小時。4 小時的驗收不受影響，但總覽螢幕若全天開著，到期後會出現全螢幕的「登入已逾時」提示，需要重新登入。長時間顯示帳號的做法待 Q-10 一併確認。

    驗收完成後，把日期、機器、瀏覽器與結果記進當週週報，並把本節標題的「尚未執行」拿掉。
