    迭代 15 手動測試 — 院方 API 介接與自動化¶

    《完整手動測試手冊》的分冊之一，對應《實作規格書》4.13 節。 共用的環境準備、啟動與疑難排解都在主手冊，這一冊只寫迭代 15 的部分。 操作端色籤（護理端／病人端／終端機／資料庫）的意思見主手冊 §00。 項次用 y（迭代 14 那六冊用到 x151）。

    1006（迭代 17.1）起不再有「配一次、之後自動接上」的固定平板：§15.3 的配平板改成每次透析把病人拖到平板上（《迭代 17.1 分冊》§17.1.2），平板自動放到院方資料的床；病人頁「配給的平板」一欄拿掉（y17）；「平板不在線上，沒有自動接上」不會再出現（y16）。下機、更正不改回去、未更新提示、數值與生命徵象各節照舊有效。

    這一冊驗一句話：能用院方 API 判斷的，就不要求護理師操作（SRS FR-S15）。病人、床位、療程開始與下機、四種數值由院方資料自動完成； 護理師只做 API 判斷不了的事——每位病人配一次平板、更正、處理「判斷不了」的情形；護理師改過的，同步不改回去。

    標記 意思
    🖥 開發機 平常的開發環境，npm run dev，加上模擬院方 API（npm run dev:hospital-sim）
    🧪 模擬部署 開發機上照部署手冊第十五冊以容器部署（DEP-22）
    🏥 院內 第三次進院；只探測、不啟用

    15.1 · 準備（4.13 工作項 2）🖥¶

    • y1 ［終端機］ 開一個新視窗打 npm run dev:hospital-sim。 → 印出「模擬院方 API 已啟動：埠 8090，路徑 /dialysislist.php」與「病人全是虛構的合成資料」。
    • y2 ［終端機］ 專案根目錄的 .env 加一行 HOSPITAL_API_BASE_URL=http://localhost:8090/dialysislist.php，重新啟動後端（npm run dev:api）。 → 後端日誌出現「院方資料同步已啟用」，日誌裡沒有印出位址。約 5 秒後自動抓第一次。
    • y3 ［終端機］ 把 .env 那一行拿掉、重新啟動後端。 → 日誌出現「未設定院方 API 的位址……不抓院方資料」。做完再把那一行加回去、重新啟動。
    • y4 ［終端機］ curl -s http://localhost:8090/dialysislist.php | head -c 120 → 開頭是 <meta charset="UTF-8" />{"data_list":[[，病歷號 99 開頭、姓名是「模擬甲」這類。這是模擬資料才能這樣看；院方的 API 不准用 curl 直接打（§15.8）。

    15.2 · 不碰護理端，自動出現（驗收 1、4）🖥¶

    • y5 ［護理端］ 用護理長帳號登入簡易版，什麼都不要點。 → 床位圖在原本的床之後多出 A1、A2、A3、A5、B1……；院方資料說正在透析的病人畫在他那一床（治療中、折線圖示），沒有平板也在床上。
    • y6 ［護理端］ 看病人框。 → 沒有「＋」（新增病人）；框裡是今天要透析、還沒配平板的病人，虛線框，只有名字。
    • y7 ［護理端］ 找「模擬辛」。 → 床位圖與病人框都沒有她：她在院方資料裡每一列都少兩欄，那一次透析整個不寫入；其他病人照常出現。
    • y8 ［護理端］ 專業版「排班與指派」看今天。 → 院方資料的病人都有排班：還沒開始的「已排定」，進行中的「進行中」，結束的「已完成」。
    • y9 ［護理端］ 專業版「臨床數值」查一位進行中的病人與「模擬丙」。 → 進行中的病人有理想體重、目標脫水量（毫升），來源是「院方 API」；「模擬丙」沒有理想體重（院方回的是 0，不建立）；還沒下機的沒有結束體重。
    • y10 ［護理端］ 專業版「系統管理 → 營運參數與選項清單」。 → 營運參數多四列（院方資料抓取頻率、多久未更新就提示、過了預計結束多久標示待確認下機、院方床位轉床號的方式）； 「院方資料同步」卡片寫著「目前接的是模擬院方 API」，最近幾次抓取的結果是「成功」、格式不符 1；卡片上沒有位址。床位清單多了院方的床號。

    15.3 · 配平板、自動進入療程（驗收 2）🖥¶

    • y11 ［護理端］ 簡易版：從平板框拿起開著的那台平板，放到病人框裡一位還沒開始透析的病人身上。 → 8 秒復原列出現「平板 … → 某某」；那位病人從病人框消失（配好了）。平板還不會進入療程——他還沒開始透析。
    • y12 ［護理端］ 按復原。 → 那位病人回到病人框。再配一次。
    • y13 ［護理端］ 換一台平板，點平板、再點病人（不拖曳）配給一位正在透析的病人。 → 那台平板當下就接上（不必等下一次抓取）：床位格底下出現平板圖示，平板被放到那位病人的床。
    • y14 ［病人端］ 看那一台的畫面。 → 幾秒內進入療程：首頁床號是院方資料的床號；療程進度條從院方的開始時間算起（已經走了一段，不是從零）。
    • y15 ［終端機］ 等模擬院方 API 那位「還沒開始」的病人開始透析（relative 排法約啟動後 20～35 分鐘；不想等就 HOSPITAL_API_SIM_SCHEDULE=fixed 重開模擬服務、挑一位鐘點已過的），或到專業版系統管理按「立即同步」。 → y11 配的那台平板一個抓取週期內自動進入療程，不必碰護理端也不必碰平板。
    • y16 ［護理端］ 把一台從沒開過的平板配給一位正在透析的病人。 → 那一床（與病人框裡那位病人）帶一個斷開的鏈圖示，滑鼠停上去是「平板不在線上，沒有自動接上」。稽核軌跡多一筆「透析已開始，平板沒有自動接上」。
    • y17 ［護理端］ 專業版「病人」頁。 → 多一欄「配給的平板」，y11～y16 配過的都看得到；在這裡換一台或選「不配平板」與簡易版是同一件事。
    • y18 ［終端機］ 開發者工具的網路分頁看病人端。 → 有一條 device/stream 的連線一直開著；接上療程那一刻收到 SESSION_CHANGED，之後院方有新紀錄時收到 VITALS_UPDATED，事件裡沒有任何數值。

    15.4 · 下機（驗收 2、3）🖥¶

    • y19 ［終端機］ 等第一組（快結束那組）的病人過了預計結束 10 分鐘（院方資料出現結束體重）。 → 一個抓取週期內自動下機：床位格空出來，有平板的那台回到等待畫面；專業版「臨床數值」多了結束體重與實際脫水量。
    • y20 ［護理端］ 簡易版：把一位有平板的病人的平板拖到另一張空床（手動換床）。 → 病人跟著平板換床。按「立即同步」或等下一次抓取：病人不會被換回院方資料說的那一床。
    • y21 ［護理端］ 把那位病人拖到「下機」（提前結束），等 8 秒。 → 下機。下一次同步之後他不會再出現在床上，平板也不會再自動接上（院方資料仍說他在透析）。
    • y22 ［護理端］ 把一位沒有平板、正在透析的病人拖到「下機」，等 8 秒。 → 一樣結束；專業版排班頁那一筆變成「已完成」。
    • y23 ［護理端］ 把營運參數「過了預計結束多久標示待確認下機」改成 10（填理由）。等一位「結束時間已填」的進行中病人過了預計結束 10 分鐘、院方資料卻還沒有結束體重（模擬服務的奇數位病人在預計結束後 10 分鐘才出現結束體重，時間窗很短；趕不上就看 verify:iteration15:api 步驟 8）。 → 那一床出現「待確認下機」（時鐘圖示、褐色框）。改回 60。
    • y24 ［護理端］ 點「待確認下機」。 → 8 秒復原列；8 秒後下機。下一次同步不改回去。
    • y25 ［護理端］ 專業版排班頁，一位沒有平板、進行中的病人那一列。 → 有「下機結束」按鈕；按了一樣結束（這是院方判斷不了下機時，專業版的處理方式）。

    15.5 · 院方不通與恢復（驗收 5、6）🖥¶

    • y26 ［終端機］ 停掉模擬院方 API（那個視窗按 Ctrl+C），到專業版系統管理按「立即同步」。 → 約 6 秒後回「同步沒有完成：連線被拒，院方服務沒有開」；訊息裡沒有位址。卡片的抓取紀錄多一筆「失敗」。
    • y27 ［護理端］ 把「院方資料多久未更新就提示」改成 2，等 2 分鐘，看簡易版。 → 上面那一條出現「院方資料已 N 分鐘未更新」（斷掉的雙箭頭圈、褐色框）；床上的病人、平板上的療程都還在，不會自己下機。整頁沒有捲軸。
    • y28 ［護理端］ 稽核軌跡查「院方資料抓取失敗」。 → 只有一筆（狀態變了才寫），不是每次失敗都寫。
    • y29 ［終端機］ 重新 npm run dev:hospital-sim，按「立即同步」。 → 成功；簡易版的未更新提示消失；稽核多一筆「院方資料恢復更新」；有平板的病人在停掉期間的紀錄補進來（抓取紀錄的「新增生命徵象」不是 0）。把門檻改回 10。
    • y30 ［護理端］ 連按兩次「立即同步」。 → 第二次的「新增生命徵象」是 0；臨床數值沒有多出新的匯入批次；排班沒有多出來（同一份回應抓兩次不重複）。

    15.6 · 專業版與稽核（驗收 9、10）🖥¶

    • y31 ［護理端］ 稽核軌跡查「療程開始」與「裝置綁定」。 → 自動開始、自動接上的那幾筆，操作者是「院方資料同步」；y13 那一次的「配給病人的平板」是你本人。
    • y32 ［護理端］ 專業版「排班與指派」看自動接上的那一筆綁定。 → 指派者顯示「院方資料同步」，不是一串系統帳號的識別字。
    • y33 ［護理端］ 帳號審核與帳號清單。 → 看不到「院方資料同步」這個帳號。
    • y34 ［護理端］ 登入畫面用工作 ID SYSTEM-HOSPITAL-SYNC 隨便打一組密碼登入。 → 登入失敗。
    • y35 ［護理端］ 專業版「病人」新增一位病人；「臨床數值」人工輸入一筆理想體重。 → 照樣可以（專業版的人工操作留著當備援）。
    • y36 ［終端機］ .env 拿掉 HOSPITAL_API_BASE_URL、重新啟動後端，登入簡易版。 → 簡易版回到迭代 14 的樣子：病人框有「＋」、病人可以拖上床；沒有未更新提示。做完加回去。

    15.7 · 低血壓範本、病人端時點（4.13 工作項 10、11）🖥¶

    • y37 ［護理端］ 專業版「護理紀錄」選一位有平板、正在透析的病人的療程，事件範本點「透析中低血壓處置」。 → 補充說明自動帶入「當下血壓 …/… mmHg（院方紀錄 HH:MM），處置時間：」，可以改。補充說明已經有字時不會被蓋掉。
    • y38 ［護理端］ 同一個範本，換成一位沒有平板的病人。 → 補充說明是空的（只收有平板的病人的紀錄），護理師照舊自己填。
    • y39 ［病人端］ y15 那一台：把「心情問卷出現時點（透析開始後）」改成「現在距院方開始時間的分鐘數減 1」。 → 一分鐘內心情問卷自動出現——時點從院方的透析開始時間起算，不是從平板接上的那一刻。改回 120。

    15.8 · 探測工具（驗收 8、4.19）🖥 🏥¶

    • y40 ［終端機］ 🖥 npm run probe:hospital-api → 印出連線成功、「模擬標頭：有」、每列欄數、透析次數與格式不符的原因、51 欄的型態分布、床位樣式 A9、透析進行中的結束時間與結束體重、數字欄的數值大小分布。
    • y41 ［終端機］ 🖥 把 y40 的輸出存成檔案，搜尋 SIM-CANARY、模擬、99000、localhost。 → 一個都找不到：探測工具不印任何一個值，也不印位址。
    • y42 ［終端機］ 🏥 第三次進院，照第十五冊 V-30a 在 api 容器裡跑一次（位址當場輸入，不寫進 .env）。 → 整段抄進演練紀錄。帶回來之後依「透析進行中的結束時間／結束體重」定下機判定、依床位樣式定「院方床位轉床號的方式」、依累積量的大小分布確認單位。

    15.9 · 模擬部署與正式設定的拒絕（驗收 7）🧪¶

    • y43 ［終端機］ 🧪 照第十五冊之二 1.9 填好 .env，docker compose --env-file $cfg --profile simulation up -d。 → 多一個 hospital-api-sim 容器，沒有對外開埠（docker compose ps 的 PORTS 欄空白）。
    • y44 ［護理端］ 🧪 用開發機的區網 IP 開護理端簡易版，替一位院方資料的病人配那支開發手機，等模擬透析開始。 → 不碰護理端，病人與床位自動出現；手機自動進入療程（部署規範第 9 章第 8 項前半）。
    • y45 ［終端機］ 🧪 把 .env 的 HD_SIMULATION_DEPLOYMENT 清空，up -d api，看 logs --tail 20 api。 → 後端拒絕啟動，訊息指出 DEP-46，訊息裡沒有位址。改回 yes、再 up -d api。

    15.10 · 自動化驗收 🖥¶

    • y46 ［終端機］ npm run verify:iteration15（不需後端） → 7 個步驟全部通過：簡易版接了院方 API 的版面與只用既有端點、圖示登記、兩端用同一支端點、病人端時點與推送、compose 與設定範本、不再預設 15 床、介面與遷移檢查。
    • y47 ［終端機］ 模擬院方 API 與後端都開著（y1、y2），npm run verify:iteration15:api → 12 個步驟全部通過。午夜前後一小時不執行（院方資料以當天為單位，腳本會自己擋下）。腳本會把模擬服務切成指定的列，跑完切回原本的模式。
