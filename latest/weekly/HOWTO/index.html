    每週紀錄維護流程（人用）¶

    這頁寫給隔了一週回來、細節已經忘光的自己。從「這週做完了」到「別人點得到」，全部步驟在這裡。給 AI agent 執行的版本是專案 repo 裡的 skill .claude/skills/hd-docs/（2026-10-26 起取代 AGENT.md）；文件為什麼這樣分、哪些值交給程式算，見《文件架構與 token 成本》。

    摘要¶

    • 真本在 repo 的 docs/，對外是 GitHub Pages 文件站；一律先改 repo 再 docs:sync，不要回頭改鏡像或站台
    • 週中改到哪推到哪，「修訂中」、定版欄、份數、測試項數、週報側欄由 npm run docs:gen 自動算（2026-10-26 起）；週三定版才補版本歷程，先 docs:sync 再 docs:freeze
    • 三個網址：現行版（永遠最新）、凍結版（每週定版，之後不變）、鏡像 repo（只有工具在用）
    • 舊站 HackMD 只在你明確開口時才同步
    • 「踩過的坑」是一張症狀、原因、解法對照表，出事先查這裡
    • 新增文件、子文件、分冊、截圖、改介面基準、改維護流程各有固定做法（「什麼時候不只是加一篇週報」）
    • md 格式照全域省 token 規則：一段一行、表格不補空白、長文件開頭要有摘要（2026-10-23 起）
    • 首頁只有四塊、兩張表列序固定，不准長回去
    • 定版日多跑 npm run docs:readership：這週哪些頁面被看見、看了幾次、什麼時候看、看了多久，寫成站上的《文件閱讀統計》，可一鍵切換含不含自己（2026-10-26 起；收集端要先做「一次性設定」第 4 項）

    一次講完的全貌¶

    文件的真本在 repo（docs/），對外看得到的是 GitHub Pages 文件站。所有內容都先改 repo，再同步過去，不要反過來去改鏡像 repo 或站台——同步是整份覆蓋。

    週中  改 docs/<文件>.md
        ↓  npm run docs:gen            首頁那幾列自動標「0909 · 修訂中」
        ↓  npm run docs:check          連結、格式、側欄有沒有漏
        ↓  npm run docs:preview        本機先看長什麼樣（可略）
        ↓  npm run docs:sync           讀者看得到進行中的內容
        ↓
週三  寫 docs/weekly/2026-09-16.md，首頁最近三週插一段
      npm run docs:pending 列出的文件補版本歷程一列   ← 只有這天做
      npm run docs:readership 產生這週的閱讀統計頁    ← 只有這天做
        ↓  npm run docs:gen            修訂中拿掉、日期換 0916、側欄補週報
        ↓  npm run docs:sync           先把內容推上去
        ↓  npm run docs:freeze          再凍結，建立該週凍結版
        ↓
GitHub Pages                            別人看到的

    順序不能顛倒：先 docs:sync 再 docs:freeze。 凍結版是在鏡像上打一個週次 tag， tag 釘住的是當下那個 commit——內容沒先推上去，凍到的就是舊的。（HackMD 時代是相反的，別照舊記憶做事；腳本會擋，但別靠它擋。）

    三個網址，各自負責一件事¶

    網址 內容 誰在用
    現行版 …/hd-docs/latest/ 永遠是最新的 首頁的連結、你給別人的連結
    凍結版 …/hd-docs/0916/ 0916 那天定版的樣子，之後不再變 回頭對帳「當初談定的是哪一版」
    鏡像 repo github.com/94sh09sh19sh/hd-docs 站台的原始內容 只有工具在用，人不必進去

    站台右上角有版本下拉選單，讀者可以自己在各週定版之間切換。凍結版只會往回指：它凍的是當時的內容，當時還不存在的後續版本，它的版本歷程裡自然沒有那一列。要從舊版跳到新版，用那個選單。

    凍結版住在鏡像 repo，本地只留現行版。

    每一版 = 鏡像 main 上的一個週次 tag（內容來源）＋ gh-pages 裡建好的 /<週次>/。 本地 repo 不再收任何舊版目錄——同一份內容擺兩處，遲早有人改了其中一處，之後就分不出哪一份才是當初定版的那一份。

    要看某一版，開站上的 /<週次>/；要原始檔，從鏡像的 tag 取： git -C .docs-mirror show <週次>:docs/<路徑>。首頁只掛現行版，所以你給出去的連結永遠不會過期，也不必每週重發。

    公開範圍：鏡像 repo 是 public、站台是公開網址，知道網址就看得到（跟以前的 HackMD 自訂網址一樣）。 robots.txt 擋掉搜尋引擎收錄。程式碼、README.md、.env 都留在私有 repo，同步腳本只複製 docs/ 與 docs-site/ 兩個目錄，這條界線是結構上的，不是靠記得。

    一次性設定¶

    做過就不必再做。

    1. 鏡像 repo（只做一次）：
    gh repo create hd-docs --public --description "血液透析平板照護輔助系統 文件鏡像"
npm run docs:sync

    第一次 docs:sync 會把鏡像 clone 到 .docs-mirror/（已 gitignore），之後每次沿用。

    1. GitHub Pages 來源：第一次 docs:freeze 或 docs:sync 跑完，Actions 會建出 gh-pages 分支。到鏡像 repo 的 Settings → Pages，Source 選 Deploy from a branch、分支選 gh-pages / (root)。這一步只做一次，之後都自動。

    2. 本機預覽用的工具（可略，不預覽就不必裝）：

    pip install -r docs-site/requirements.txt

    1. 閱讀統計的收集端（2026-10-26 起，不做就沒有統計，站台照常）：站台是純靜態，沒有地方記「誰看了什麼」，所以借你 Gmail 底下的一份 Google 試算表當後端。要登入網頁，agent 不代做。

    2. 用要存資料的 Gmail 帳號開一份新的 Google 試算表，名稱例如「hd-docs 閱讀統計」

    3. 選單「擴充功能 → Apps Script」，把 repo 裡 scripts/readership/collector.gs 整份貼上、存檔
    4. 左側齒輪「專案設定 → 指令碼屬性」，新增屬性 READ_KEY，值是自己產的一串亂碼（node -e "console.log(crypto.randomUUID())"）
    5. 右上「部署 → 新增部署作業」，類型選「網頁應用程式」，執行身分「我」、存取權「所有人」，部署並照提示授權，複製 …/exec 結尾的網址
    6. 網址填進 docs-site/mkdocs.yml 的 extra.readership.endpoint；同一串 READ_KEY 寫進 .env 的 READERSHIP_KEY=
    7. 照收尾順序 commit、docs:sync；站台建好後，你自己用的每個瀏覽器（電腦、手機、Claude in Chrome 用的那個 Chrome）各開一次 …/hd-docs/latest/?me=1，看到「已標記為我自己」的提示就好；?me=0 取消
    8. 隨便看幾頁，再跑 npm run docs:readership -- --dry-run，終端機印得出剛才那幾次就通了

    「存取權：所有人」只代表誰都能寫入一筆閱讀紀錄；讀資料要帶 READ_KEY，網址本身寫在公開設定裡沒有關係。READ_KEY 跟 HACKMD_API_TOKEN 一樣只放 .env。

    為什麼是「標記瀏覽器」而不是認 Gmail 帳號：靜態網頁讀不到訪客登入了哪個 Google 帳號（瀏覽器刻意不給），所以改成每個瀏覽器標一次。Claude 開的無頭 Chrome 不必標，自動算成你；Claude 用網頁抓取工具讀文件、或「問 AI」帶去的 AI 只讀 Markdown 原檔，不執行網頁程式，本來就不會被算到。某個瀏覽器只要標記過，它在標記之前的紀錄也一併算成你。

    新站不需要任何第三方 API 權杖，同步走的是 git push，沒有每月額度這回事（閱讀統計的 READ_KEY 是自己產的讀取金鑰）。 .env 裡的 HACKMD_API_TOKEN 刻意留著——舊站還在，你開口時還要用它同步（見下一段）。

    舊站（HackMD）¶

    換到新站之後，HackMD 不再是每週流程的一部分，但沒有廢掉：
    什麼時候同步 只有你明確開口時。每週例行流程只推新站
    指令 npm run docs:hackmd 產生 .hackmd-build/ → npm run docs:hackmd:push 推上去（加 -- --dry-run 先看清單）。要出凍結版再跑 npm run docs:hackmd:freeze
    權杖 HACKMD_API_TOKEN 留在 .env，不要刪，也不要貼進任何文件、截圖或訊息
    額度 免費方案每月 400 次，目前已用盡，訊息裡寫 Resets at 2026-10-01。收到 429 quota_exceeded 就停手，重試只會再吃掉配額
    凍結版 0909 那批已取回並發佈到新站（只存在於鏡像 repo，本地不留），版本歷程一律指向新站，不再依賴舊站；0916 那批因額度用盡沒有推成功，不影響新站

    手貼舊站時一律貼 .hackmd-build/ 底下的檔案，不要貼 docs/ 原始檔——兩者肉眼難辨，貼錯不會有任何錯誤訊息，但那篇的內部連結會全部變成死連結。分辨法：build 版第一行一定是 ---，原始檔第一行一定是 #。

    每週怎麼走¶

    分兩段：週中隨時改、週三收成定版。差別只有一件事——版本歷程與 docs:freeze 只在定版日做。

    週中：改到哪推到哪¶

    1. 改 docs/ 底下的文件。
    2. npm run docs:gen：首頁與其他文件總表標上修訂中，讓讀者知道這幾份正在動。它拿每份文件跟鏡像上最新一次定版的內容比，有差就標：
    3. 頂部變成 **本週定版**：0909｜**0916 修訂中**
    4. 表格裡動過的那幾列，定版欄變成 0909 · 修訂中；全新的文件還沒有過第一次定版，寫 新增 · 修訂中
    5. 以前這一步是手改，1018 與 1021 之後都漏標過；程式比對不會漏，所以這些值不要再手改
    6. 進度多的時候，該週週報可以週中就先建起來當草稿維護，不必等到週三一次補寫。檔名照樣用該週的星期三，檔頭狀態寫「進行中（…週中草稿，MMDD 定版時收尾）」，首頁「最近三週」插一段；那段標題的 · 修訂中 與側欄的那一列由 docs:gen 補。版本歷程與 docs:freeze 一樣不能碰。
    7. npm run docs:check，有 ✗ 就修到通過
    8. npm run docs:sync（開頭會先確認 docs:gen 跑過，沒跑就擋下）

    交給 agent 改的話，這一步它會自己跑完再回報清單，不會停下來等你點頭（2026-09-10 起）。定版日建立凍結版那次仍會先問，因為凍下去改不回來。

    想先看長什麼樣就跑 npm run docs:preview，瀏覽器開 http://127.0.0.1:8000，存檔會自動重整，按 Ctrl+C 結束。預覽完全在本機，不會推任何東西出去。

    讀者這時點進去看到的是進行中的內容，但表格明白標著修訂中，不會被日期誤導。

    ⚠️ 週中絕對不要補版本歷程那一列，也不要跑 npm run docs:freeze。 一旦打了 tag，那一週的凍結版就定型了，而凍結版建立後不再更新，救不回來。定版是週三的事。

    週三：收成定版¶

    1. 開一份新的週報¶

    cp docs/weekly/_template.md docs/weekly/2026-09-16.md

    檔名用該週開會日（星期三）的 ISO 日期。開會日就是報告日，這樣檔案列表的排序就是時間序。內容照範本填。第一行 # MMDD 週報 — 一句話標題 很重要，它會成為站上那一頁的標題。

    2. 首頁收尾¶

    開啟 docs/index.md，「最近三週」最上方插入一段（新的排在上面；週中已開草稿就跳過），檔案裡有註解標出插入點：

    ### [0916 — 一句話標題](weekly/2026-09-16.md)

進度：

- 三到五條重點

    插完如果超過三段，把最舊的那一段整段刪掉；歷次週報（docs/weekly/archive.md）由 docs:gen 自動補上那一週。首頁永遠只有三週，這是這套結構最需要自律的地方（docs:check 會擋第四段）。

    頂部的「本週定版」、兩張表的定版欄，等第 4 步補完版本歷程後由 docs:gen 一起換成 0916，不手改。

    3. 新的一頁要進側欄¶

    站台側欄的列序寫在 docs-site/mkdocs.yml 的 nav，它也是「有哪些文件」的唯一清單。週報與測試分冊由 docs:gen 自動加；其他新文件要手動加一列，否則站上點不到（頁面仍會建出來，但沒有入口），docs:check 會抓出漏掉的。列序照首頁那兩張表的讀者思考順序，不要重排。

    這一步取代了 HackMD 時代「在對應表裡加一行網址」。差別是：現在忘了加只是側欄少一列，不會像以前那樣整篇連結失效。

    4. 改過的文件補版本歷程¶

    npm run docs:pending 列出上次定版之後改過、還沒補的文件。逐份在末尾「版本歷程」表的最上面加一列（只做格式整理的不補）：

    | 0916 | 2026-09-16 | 補上 FR-N08 的離線重送規則 |

    第一欄只寫四位數週次，不要寫網址——同步時會自動換成該週凍結版的連結。第二欄的日期一定要寫，docs:gen 靠它比新舊。異動摘要寫「改了什麼」，不是「改了哪一節」，這一欄是給半年後的人看的。

    補完跑 npm run docs:gen：頂部變成 **本週定版**：0916，有補列的那幾份定版欄換成 0916，修訂中拿掉。外殼契約的版本歷程記的是契約版本、沒有週次，它若這週改過，首頁那一欄手改成 0916。

    5. 這週的閱讀統計¶

    npm run docs:readership           # 定版日是星期三就統計上週三 00:00 到今天 00:00
npm run docs:readership -- 0916   # 定版日不是星期三，指定週次

    終端機先印兩份摘要（「不含我自己」「包含我自己」，各列前 15 頁的次數與閱讀時間合計），這就是「這週誰在看哪幾份」的答案。同時把 docs/weekly/readership.md 整份重寫成站上的《文件閱讀統計》：各頁閱讀次數、星期 × 時段的熱度圖、近八週趨勢、逐頁明細（裝置數、合計、每次中位數、最近一次），每一次閱讀的開始時間與長度收在可展開的區塊；頁首一個切換鈕切換含不含自己。這一頁不手改。

    前幾週的統計不累積在這一頁，留在各週凍結版（版本選單切過去看）。收集端還沒設定時頁面寫「尚未設定」，照樣跑不會出錯；設定好之後 docs:freeze 會檢查統計頁是不是這一週的，不是就擋下，確定這週不放才加 -- --no-readership。

    6. 先同步，再凍結¶

    npm run docs:check    # 先確認沒有漏
npm run docs:sync     # 內容先推上去，現行版更新
npm run docs:freeze   # 再打週次 tag，建立凍結版

    docs:freeze 會掃過所有文件的版本歷程，把出現過、鏡像上還沒有同名 tag 的週次建出來。已經存在的一律不動，它只會印一行「凍結版已存在，不動」。

    不確定會做什麼就先看：npm run docs:freeze -- --dry-run。只想處理某一週：npm run docs:freeze -- 0916。

    凍結版建好之後再跑一次 npm run docs:sync：版本歷程第一欄的週次，要等該週凍結版真的存在，同步時才會換成連結；還不存在的維持純文字，不留死連結。

    7. Commit¶

    git add docs docs-site scripts package.json && git commit -m "docs: 週報 0916" && git push

    .docs-mirror/ 與 .docs-preview/ 已經 gitignore，不會進版控——它們隨時可以重新產生。

    症狀 原因 解法

    凍結版的內容是舊的 先跑了 docs:freeze 才跑 docs:sync 順序一律是先 sync 再 freeze。腳本會擋下沒同步就凍結的情況，但別靠它
    週次 tag 打錯了 版本歷程那一欄寫錯週次 趁還沒 push 才救得回來。已經建出去的凍結版視為既成紀錄，要修正就在新的一週寫明
    改了 docs/ 但站上沒變 只改了 repo，沒跑 docs:sync。git push 不會更新公開站——站台只看鏡像，私有 repo 推了也沒用 跑 npm run docs:sync。跑完 Actions 還要一兩分鐘才建完。交給 agent 時，它的收尾順序寫在 skill hd-docs 的「收尾順序」

    什麼時候不只是加一篇週報¶

    • 週中改了需求文件或進度報告 → docs:gen（首頁那一列自動標修訂中）→ docs:sync。不要碰版本歷程與 docs:freeze
    • 週三定版 → 版本歷程加一列 → docs:gen（拿掉修訂中、換週次）→ docs:sync → docs:freeze，缺一步凍結版就不會出現
    • 新增一種文件（不是週報）→ 建檔（文末要有「版本歷程」表）→ 首頁表格加一列（照下面的列序放進去，不要一律加在最後；定版欄由 docs:gen 填 新增 · 修訂中） → docs-site/mkdocs.yml 的 nav 加一列 → docs:check → docs:sync
    • 新增一份「其他文件」（不屬於需求、報告、參考、測試、部署五類的單篇方案評估、決策紀錄或修正紀錄，放 docs/notes/） → 掛到《其他文件總表》（docs/notes/index.md），不動首頁（2026-10-07 起）。總表分兩張：一般文件、小迭代文件（9.1、14.1、17.2 這類非整數迭代的修正紀錄） → nav「其他文件」底下對應的那一組加一列，順序與總表相同 → docs:gen（首頁的份數、定版欄）→ docs:check → docs:sync。維護指南不必跟著改（2026-10-26 起清單只在 nav 與總表）
    • 某份文件有一大段在條列（2026-10-15 起）→ 收進子文件、掛在原處，母文件留連結，連結上方或下方寫明收入方式與怎麼維護。收入分兩種：永久收入是那張表一直往下長、新的一筆也寫進子文件（測試手冊的路由表、實作規格書 1.1 的改動紀錄）； 一次性收入是做完的階段搬走、新的階段照舊寫在母文件（實作規格書的迭代 3～23、兩份進度報告的已完成部分）。搬的時候節號與標題一律不動，別處寫的「實作規格書 4.21」才找得到。子文件有版本歷程、不上首頁、nav 裡和母文件收成一組。細節與目前五份的清單在 skill hd-docs 的 references/new-doc.md
    • 改架構圖 → 改 requirements/architecture-diagrams.src.html（不要單獨修 PNG）→ 照 architecture-diagrams.md 文末的指令重新產生 PNG → docs:sync。 圖片走 repo 相對路徑，不必再另外上傳、不必換任何網址（這是換掉 HackMD 之後少掉的一整條規則）
    • 週報要附截圖（2026-10-07 起）→ PNG 放 docs/weekly/images/<週次>/，週報最後加一節「附錄：截圖」，每張圖上面一句話說是誰、哪個尺寸、看什麼。公開站看得到，只能是模擬資料的畫面（demo:patient 的虛構病人）；截圖前確認沒有網址列、平板金鑰、院內位址。病人平板只截橫放 1280×800（2026-10-14 起）：院內平板實際是橫放使用，直放的畫面不是病人會看到的樣子，不放進週報

    首頁不准長回去¶

    首頁在 2026-09-10 從 100 行砍到 51 行，砍掉的是目錄結構與附錄——那些是維護者的東西，不是讀者要的。行數本身不是上限（之後新增文件、換新的一週都會讓它長短變動），真正不准破的是下面這幾條。想加東西之前先讀一次：

    • 只有四塊：最近三週／實作文件／需求文件／其他文件。不要再開新的一塊，也不加開頭摘要。「實作文件」原叫「我要找…」，2026-10-23 依你的指示改名，表頭與列序不變。原本最上面還有一塊「現在到哪」，2026-09-22 拿掉了——它寫的全是週報已經寫過的事，越堆越長。 要速看進度，看「最近三週」每段底下的「進度」條列；頂部只留「本週定版」那一行，不要把現況摘要加回去。「其他文件」是 2026-09-19 加的，放不屬於前四塊的單篇方案評估（檔案在 docs/notes/）。它是刻意留的小出口，免得每有一份技術決策就要硬塞進需求文件、或是沒地方放就不寫；但正因為是出口，最容易長歪——果然長歪了：到 2026-10-07 已經十三份，每多一個小迭代就多一列，比其他三塊都長。使用者當天指示收進一份總表（docs/notes/index.md，分成一般文件與小迭代文件兩張表）， 首頁那一塊保留標題、只剩一行連結。之後新增 notes/ 底下的文件只改總表，首頁那一行不再變長；不要再把個別文件掛回首頁
    • 兩張表的列序是照讀者的思考順序排的，不要動（2026-09-10 定）：
    • 「實作文件」：臨床端進度報告 → 技術端進度報告 → 架構圖 → 資料字典 → 這套系統是用什麼蓋的 → 病人端外殼 App 契約 → 完整手動測試手冊 → 部署手冊。先知道進度到哪，再看系統長什麼樣、蒐了哪些資料，然後是名詞解釋與外殼的介面（0927 加，參考文件排在一起），最後兩列才是動手的兩份——先驗收，再部署。 測試手冊的迭代分冊與部署手冊的各冊（十八冊與八本子手冊）都不另占一列：它們從各自的索引進去，理由見下一段
    • 「其他文件」在首頁只有一行連結，沒有列序。總表裡兩張表，目前有哪幾份、各幾份就看總表本身（2026-10-26 起不在這裡另抄一份清單，docs:check 會比對總表與側欄的列序）：
      • 一般文件沒有閱讀動線，新增的排在表尾。 子文件例外（1010 起）：緊接在上層文件那一列下面、名稱前加 ↳，側欄裡和上層文件收成一組
      • 小迭代文件依迭代編號排
    • 「需求文件」：FDE 數位化評估報告 → SRS → 資料庫使用規範 → 實作規格書 → 部署規範 → 尚待確認事項清冊。前五份是從為什麼要做，讀到做什麼、資料怎麼管、怎麼實作，最後是怎麼部署；第六份（清冊）是進行中的問題總表，不在這條動線上，固定排最後一列。 這不是優先權順序——衝突時仍以實作規格書為準，優先權寫在「角色」欄，不要拿列序去推
    • 每週紀錄最多三段，每段三到五條
    • 細節一律留在週報或該文件裡，首頁只放連結與一句話
    • 維護用的說明（本頁與 AGENT.md 對照頁）只准出現在最後一行

    首頁一旦開始長內容，累積半年後就沒人讀得下去了，那時再砍要花的力氣是現在的十倍。
