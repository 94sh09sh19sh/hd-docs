# 文件架構與 token 成本

2026-10-26 重新規劃。目標：整個開發過程裡花在文件上的 token 降到最低，**靠改架構，不靠刪資訊**。人用的流程在 [HOWTO.md](https://94sh09sh19sh.github.io/hd-docs/latest/weekly/HOWTO/index.md)，agent 用的規則在專案 repo 的 skill `.claude/skills/hd-docs/`。

## 摘要

- 盤點 1010～1026 的 46 筆文件 commit：**37 筆動到「登記類」檔案**（首頁、總表、側欄、兩份維護指南），維護指南 AGENT.md 被改 28 次、HOWTO 27 次——多半只是因為多了一份文件、要改清單與份數
- 最大的固定成本是**每次動文件都要讀兩份維護指南**：AGENT.md 64 KB、HOWTO 29 KB，合計約 6 萬 token，而且讀進來之後每一輪對話都還帶著
- 第二大是**算得出來的值靠手寫**：定版欄、修訂中、份數、側欄、歷次週報；手寫還會漏（10-26 用程式一比，找出三處該標修訂中卻沒標）
- 第三是**大檔整份讀**：實作規格書 202 KB、資料字典 233 KB、清冊 147 KB、SRS 145 KB、介面設計基準 129 KB
- 新架構四件事：衍生值交給 `docs:gen`；一個清單只有一個真本（`nav` 與總表）；agent 規則改成「核心＋按任務分檔」的 skill；讀大檔先用 `docs:map` 拿到章節行號
- 驗收從一段手動指令改成 `docs:check` 一支；`docs:sync` 開頭自動確認衍生值沒過期
- 預估：一次普通的文件工作，維護規則的讀取量從約 6 萬 token 降到約 8 千；新增一份文件要動的檔案從 6 份降到 3 份
- 沒有刪任何規則：舊 AGENT.md 的每一條都搬進 skill，只拿掉「從別處算得出來」的清單與份數；AGENT.md 留一張舊章節對照表

## 2. 成本從哪裡來

1. **一份指南包辦所有任務**：寫週報、開測試分冊、改部署手冊的規則全在 AGENT.md，做任何一件事都整份讀進來，九成用不到
1. **同一份清單抄在五處**：AGENT.md 目錄樹、AGENT.md 列序清單、HOWTO 列序清單、其他文件總表、`nav`，外加首頁與兩份指南裡的份數。新增一份 `notes/` 文件要動 6 個檔案（上一輪新增《蒐集資料的完整取出》就是：本文、總表、首頁、`nav`、AGENT.md、HOWTO）
1. **衍生值靠手寫**：定版欄是「版本歷程最上面一列的週次＋內容跟上次定版比有沒有改」，份數是數檔案，側欄與歷次週報是照檔名排——全都算得出來，卻每次手改，還會漏
1. **大檔沒有地圖**：要讀實作規格書 4.25 一節（16 KB），沒有行號就只好讀一大段或整份
1. **驗收是一段手動指令**：連結檢查、格式檢查、三處列序是否一致都要自己跑、自己比

## 3. 設計原則

- **衍生值交給程式**：算得出來的不寫在指南、不手改，由 `docs:gen` 寫回、`docs:check` 擋過期
- **一個清單一個真本**：文件清單與側欄列序只看 `nav`；其他文件的列序與說明只看總表；兩者由 `docs:check` 互相比對
- **漸進讀取**：每次都讀的核心要小；只在做某件事時才需要的規則分檔，由核心的任務表指路
- **先拿地圖再讀**：大檔先用 `docs:map` 拿章節行號，只讀那一節
- **一件事一個家**：細節寫在它的家，別處一句話加連結；總表與首頁的說明欄寫範圍與結論，文件內容再改、範圍沒變就不動說明欄

## 4. 新架構

| 層                                           | 內容                                                                       | 誰在什麼時候讀                      |
| -------------------------------------------- | -------------------------------------------------------------------------- | ----------------------------------- |
| 記憶（`MEMORY.md`）                          | 一行指路：動文件先讀 skill `hd-docs`                                       | 每個 session 自動載入               |
| skill 核心 `SKILL.md`（約 6 KB）             | 每次都適用的授權與界線、收尾順序、讀檔省 token、寫入原則、真本對照、任務表 | 動 `docs/` 之前                     |
| skill 分檔 `references/*.md`（每份 2～9 KB） | 週報與定版、新增文件、迭代收尾、測試分冊、部署手冊、首頁、格式與站台       | 只在做那件事時                      |
| 工具 `scripts/docs-tool.mjs`                 | 衍生值、檢查、地圖、待補版本歷程                                           | 收尾、讀大檔、定版日                |
| HOWTO.md（人用）                             | 為什麼這樣做、踩過的坑                                                     | 人；agent 只在改流程時讀            |
| 本頁                                         | 架構與理由                                                                 | 要改架構時                          |
| AGENT.md                                     | 舊章節 → 新位置的對照表（2 KB）                                            | 舊文件裡寫「AGENT.md「…」」時查去處 |

skill 放在 `.claude/skills/`，不上公開站、不進定版週期；技能系統本來就是「描述常駐、內容用到才讀」，正好是漸進讀取。介面設計基準的 `hd-uiux` 早就是這樣做。

## 5. 工具

| 指令                                                   | 做什麼                                                                                                                                               | 取代了什麼                                                                                 |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `npm run docs:gen`                                     | 重算首頁與總表的定版欄、首頁頂部「本週定版」與修訂中、首頁最近三週的標題、其他文件份數、測試分冊本數與迭代範圍、`nav` 的週報與測試分冊兩組、歷次週報 | 週中標修訂中、定版日換週次、週報標題三處同步、多一本分冊改側欄與首頁、首頁滿三週補歷次週報 |
| `npm run docs:gen -- --check`                          | 只檢查不寫；`docs:sync` 開頭自動跑，過期就擋（`-- --force` 略過）                                                                                    | 「推上去才發現首頁沒改」                                                                   |
| `npm run docs:check`                                   | 衍生值、`nav` 涵蓋（每份都在、沒有死列）、總表與 `nav` 列序、總表收齊、首頁最多三段、版本歷程表、相對連結、每一份丟給 md-lint                        | 驗收段的連結檢查迴圈、md 格式迴圈、「三處逐字一致」的人工比對                              |
| `npm run docs:map -- <檔案> [--depth 3] [--grep 4.25]` | 列出章節、行號範圍與大小                                                                                                                             | 為了找一節而整份讀                                                                         |
| `npm run docs:pending`                                 | 列出上次定版之後改過、還沒補版本歷程的文件                                                                                                           | 定版日逐份回想這週改了什麼                                                                 |

定版欄怎麼算：值是版本歷程最上面那一列的週次（首頁那一列取母文件與子文件中最新的；測試、部署手冊取整個目錄）；內容跟鏡像上最新週次 tag 的版本不同（空白與版本歷程的連結不算）就加「修訂中」；還沒有任何週次列的是「新增 · 修訂中」。

和現有全域工具的搭配：

- `md-lint`：`docs:check` 直接拿它當格式檢查，規則只有一份
- `zhiyu-check`：照舊在寫入時把關，不另做
- `auto-ship`：照舊在回合結束前 commit、push；`docs:gen` 改到的檔案一起進 commit
- skill 機制：取代每次整份讀的 AGENT.md

## 6. 各類文件的讀寫規則（新）

| 類別                 | 寫、改                                                                                  | 讀                                            |
| -------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------- |
| 維護規則             | 只有規則或流程變了才改 skill 與 HOWTO；多一份文件不改                                   | 核心每次讀，分檔做那件事才讀，HOWTO 不讀      |
| 登記類               | 只手寫內容（說明欄、最近三週的進度條列、週報與分冊以外的 `nav` 列）；其餘 `docs:gen` 寫 | 不必為了改一格而讀                            |
| 需求文件、報告、參考 | 照舊；版本歷程定版日照 `docs:pending` 補                                                | `docs:map` → 只讀那一節；版本歷程只在補列時讀 |
| `notes/`             | 建檔時一次寫完；總表說明欄寫範圍與結論，之後範圍沒變不改                                | 同上                                          |
| 測試分冊             | 照舊；側欄、本數不手改                                                                  | 驗收時讀那一本                                |
| 部署手冊             | 照舊；各冊地位與同步規則改成一張表                                                      | 照任務讀 `references/deployment.md`           |
| 週報                 | 標題只改第一行                                                                          | —                                             |

## 7. 預估效果

以 1.5 bytes／token 估（中文為主的 md 實測值）：

| 情境                       | 以前                                           | 現在                                                            |
| -------------------------- | ---------------------------------------------- | --------------------------------------------------------------- |
| 任何一次文件工作的固定讀取 | AGENT.md＋HOWTO 約 6 萬 token                  | `SKILL.md` 約 4 千＋一份分檔約 2～6 千                          |
| 新增一份 `notes/` 文件     | 動 6 個檔案，其中兩份維護指南要先讀再改        | 動 3 個（本文、總表、`nav`），份數與定版欄 `docs:gen` 算        |
| 週中改一份需求文件         | 讀首頁、手改定版欄與頂部                       | 跑 `docs:gen`                                                   |
| 定版日                     | 逐份回想改了什麼、手改首頁三處、側欄、歷次週報 | `docs:pending` 列清單、補版本歷程、跑 `docs:gen`                |
| 讀實作規格書的一節         | 常整份或大段讀（202 KB 約 13 萬 token）        | `docs:map --grep` 拿行號，只讀那一節（例如 4.25 約 1 萬 token） |
| 迭代收尾的逐項對           | 埋在 AGENT.md 一段 2 KB 的長句裡               | 一份勾選清單，交給工具的另外列出                                |

讀進來的內容在之後每一輪對話都還在脈絡裡，所以固定讀取量省下的不只一次，而是乘上那個 session 之後的輪數。

## 8. 刻意沒做的與理由

- **不拆大檔**：節號被別份文件、程式註解與週報引用，機械拆檔會讓「實作規格書 4.21」失效；改用 `docs:map` 只讀一節
- **首頁最近三週的進度條列不自動產生**：它是週報摘要的再濃縮，要人判斷取捨
- **總表說明欄不從文件自動抽**：說明欄寫的是範圍與結論，與文件的摘要不同；改成「範圍沒變就不改」來降低改動頻率
- **測試項數不自動算**：分冊的項次寫法不完全一致，程式數出 1488、首頁寫 1490，要先查清楚差在哪兩項
- **部署手冊與其他文件的 `nav` 不自動產生**：冊名與分組是人訂的
- **小迭代範圍（9.1、14.1～14.5…）不自動產生**：寫法不一（23.1～23.3 來自切分文件），照舊手改
- **HOWTO 不刪**：它是給人看的理由與踩坑紀錄，agent 不必讀
- 改用程式判斷修訂中之後，**只做格式整理的文件也會被標修訂中**（以前不標）；定版日照 `docs:pending` 判斷時略過即可，凍結後自然消失
