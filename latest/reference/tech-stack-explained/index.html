    這套系統是用什麼蓋的 — 給非技術背景的人¶

    這頁不談程式，只用「蓋房子」把技術名詞講清楚，讓沒有工程背景的人也能聽懂會議上冒出來的那幾個詞。 需要精確定義與版本決策，請看實作規格書。

    本頁 2026-09-12 更新，對應迭代 6 完成時的系統。 0910 需求改版之後有兩件事跟 0909 版不一樣， 兩件都在下面說明：資料庫不再放雲端，以及對外的 AI 出口已經收掉。

    先講結論¶

    專案裡的名詞 蓋房子裡的角色 一句話
    TypeScript 建材 整套系統從頭到尾只用這一種建材
    React 19 蓋「前棟」的工法 病人與護理師看得到、摸得到的那兩棟
    NestJS 11 蓋「後棟機房」的工法 沒有人會走進去，但全部管線與門禁都在裡面
    Prisma 6 管線轉接頭 房子接到資料庫的標準接頭，換資料庫不必重拉全屋管路
    SQLite 自家地下室的水塔 資料庫就是院內那台主機上的一個檔案，不接外面的自來水
    Vite 6 施工機具 蓋的時候用，交屋後不留在房子裡
    PWA 組合屋式的門面 用網頁技術蓋的應用程式，不必送 App Store 審核
    離線安裝包 整棟預鑄後裝箱運過去 交屋時搬的是一整箱裝好的東西，不是在對方基地上重新叫料施工（0919 改：原本規劃的貨櫃形式已不適用，見第五章）

    一、基地上有三棟樓¶

          ┌──────────────┐        ┌──────────────┐
      │  病人端 PWA  │        │  護理端 PWA  │   ← 前棟：有門面，人在裡面操作
      │  床邊平板    │        │  護理站主控台│
      └───────┬──────┘        └──────┬───────┘
              └───────────┬──────────┘
                  ┌───────┴────────┐
                  │   後端 API     │             ← 後棟機房：沒有門面
                  │  （伺服器）    │
                  └───────┬────────┘
                  ┌───────┴────────┐
                  │    資料庫      │             ← 地下的市政管線
                  └────────────────┘
    • 前棟兩棟：病人端是床邊平板的畫面（不必登入，像大樓的公共大廳）；護理端是護理站的主控台（要驗證身分，像有門禁的辦公樓層）。
    • 後棟一棟：所有規則、驗證、稽核紀錄都在這裡執行。病人與護理師永遠不會直接碰到資料庫，一律要透過後棟轉手。
    • 資料庫：0909 版這裡寫「像市政的地下管線，房子只是接上去」——那個說法現在不對了。 0910 之後資料庫改成自家地下室的一座水塔：它就在後棟那台主機裡，是一個檔案，不接外面的水， 外面也接不進來。理由是資料一律不出醫院（見第六節）。

    二、建材：TypeScript¶

    整個專案，三棟樓都用同一種建材，所以工程師換棟工作不必重學一種語言。

    它跟一般建材（JavaScript）的差別在於：每一根都事先裁切好、貼上尺寸標籤。

    蓋的時候，工人拿一根梁要往柱子上裝，標籤對不起來就當場被擋下來，根本裝不上去 —— 這叫「編譯時檢查」。 房子蓋完交屋時，標籤會被撕掉，真正立在那裡的還是原本的建材。

    實務上的意義：很多錯誤在還沒交給臨床端使用之前，就已經被擋掉了，而不是等病人按下去才發現。

    三、工法：React 19 與 NestJS 11¶

    這兩個是同一層級的東西，都叫「框架」。框架不只是規範，它還附贈一整批預鑄件——牆板、樓梯、電箱都幫你做好，你只要組。

    React 19 NestJS 11
    負責 前棟（病人端、護理端） 後棟機房
    幫你準備好的預鑄件 畫面怎麼組、按下去畫面怎麼跟著變 門禁、路由、排程、稽核掛勾
    使用者感受得到嗎 感受得到，就是操作的手感 感受不到，但它壞了全樓停擺

    一個常見的誤會¶

    很多人會把它們理解成「React 管外觀、NestJS 管內部」。這個說法會誤導。

    護理端要排班、要即時更新病人狀態、要處理呼叫，這些邏輯又多又複雜，全部發生在前棟裡，一點都不「外觀」。 比較準的講法是前棟與後棟：差別在「人走不走得進去」，不在「複不複雜」。

    四、其他會聽到的名詞¶

    • PWA（漸進式網頁應用程式） 用網頁技術做的應用程式。可以像一般 app 一樣釘在平板首頁、全螢幕開啟，但不必上架 App Store、不必逐台更新——伺服器改好，平板下次開就是新版。對院內幾十台平板來說，這省掉的是每次改版逐台更新的人力。

    • Prisma 6（管線轉接頭） 房子接到資料庫的標準接頭。這個接頭已經證明過它的價值：測試階段資料庫本來放在雲端（在東京）， 0910 需求改版後整批搬回院內、換成 SQLite——換掉的是接頭與幾行設定，全屋管路沒有重拉。

    • SQLite（自家地下室的水塔） 資料庫的一種。與常見的「資料庫伺服器」不同，它不是一台要另外開機、另外維護的機器， 整個資料庫就是主機上的一個檔案。對一間透析中心的規模來說，這樣反而更好： 少一台機器要顧、少一個對外的門、備份就是複製一份檔案出來。 開發階段那個檔案在工程師的筆電上，正式上線後在院內主機的硬碟上。

    • 離線安裝包（交屋時的那一箱東西） 正式環境交付的不是「一包程式碼，請貴院自己安裝」，而是一整箱裝好的東西： 程式、它需要的執行環境、版本，全部封在裡面，送到現場解開就能運轉。 院內那台主機沒有對外連線，現場不可能臨時去下載缺的東西，所以交付的必須是完整的。

    0919 換了一次做法，理由值得記下來。 原本規劃的是「貨櫃」（容器）形式， 因為正式主機是一台與其他專案共用的機器，貨櫃可以互不干擾。 後來主機換成一台 Windows 電腦（還是共用的，只是院方會保留足夠的資源給本專案）， 「互不干擾」這個需求並沒有消失；但貨櫃在 Windows 上會讓那個裝著全部照護紀錄的 資料庫檔案躲進一個院方看不到、備份軟體掃不到的地方——那是不能接受的。

    所以改成「一整箱裝好的東西」，互不干擾改用別的方式達成：這一箱自己帶電力設備 （執行環境）、佔自己的房間（資料夾）、用自己的鑰匙（低權限帳號）、走講好的門牌號碼 （連接埠），不去動房子的公共設施。

    這是一個典型的例子：同一個需求換個做法一樣達得到；前提變了就要重新算一次， 不能因為已經做了就繼續用。

    • Vite 6（施工機具） 開發時用來即時預覽、打包的工具。像工地的升降機與鷹架，交屋後不會留在房子裡。

    • 共用零件廠（packages/shared） 兩棟前棟不是各做各的。共用的按鈕、共用的資料格式定義，統一在一個地方做好，兩邊都拿去用，樣式與規則才不會走鐘。

    五、「幾個服務」其實在同一棟樓裡¶

    文件上會看到好幾個名字：API Gateway、裝置綁定服務、照護業務模組、營運與排班模組、 臨床資料匯入、AI 閘道、即時狀態服務。

    聽起來像好幾棟樓，實際上是同一棟機房裡的幾個房間（就是架構圖 圖一中間那一排）。

            ┌──────────────── 後端機房（一個 NestJS 程式）────────────────┐
        │                                                              │
        │  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐      │
        │  │Gateway │ │裝置綁定│ │照護業務│ │營運排班│ │臨床匯入│ ⋯    │
        │  │總櫃檯  │ │平板配對│ │問卷求助│ │班表基準│ │數值進來│      │
        │  └────────┘ └────────┘ └────────┘ └────────┘ └────────┘      │
        └──────────────────────────────────────────────────────────────┘

    這樣做的理由很單純：現階段規模還小，先用隔間把職責分清楚就夠了。等哪天量體大到某個房間需要獨立的水電與樓地板，再把它拆出去蓋成獨棟（工程上叫「拆成微服務」）。因為隔間一開始就切乾淨了，將來要拆才不會牽一髮動全身。

    各房間現況：

    房間 它在做什麼 目前狀態
    API Gateway 總櫃檯。所有請求都先到這裡，驗身分、分派、留紀錄 已完成
    裝置綁定服務 把某一台平板配到某一位病人身上，時間到自動解除 已完成
    照護業務模組 問卷、求助、護理記錄、衛教、回饋，以及平板閒置時的輪播畫面 已完成
    營運與排班模組 護理師班表、床位分配、成效基準，以及那些「可以改的數字」 已完成
    臨床資料匯入 院方的臨床數值怎麼進來：人工輸入、Excel／CSV 檔案，或日後的院方 API 人工輸入與檔案已完成，院方 API 等對方決定
    AI 閘道 要問 AI 之前，先把病人可識別資訊拿掉，並把每一次呼叫記下來 已完成
    即時狀態服務 病人按了呼叫，讓護理站的畫面馬上跟著變 已完成

    兩個房間的變化值得單獨講¶

    推播通知服務：整間拆掉了。 0909 版這裡有一個「推播通知」的房間——就是讓護理師手機在院外也收得到 通知的那種。0910 改版後整條移除，因為那條線一定要經過院外的中繼站（Google 或 Apple 的伺服器）， 與「資料不出醫院」相抵觸。取而代之的是護理站的一台常駐總覽螢幕：它全天開著、不休眠， 通報一進來就在上面。等於把「推到每個人手機上」換成「掛在牆上大家都看得到」。

    AI Proxy：改名叫 AI 閘道，而且它現在守的是院內。 0909 版的設計是「對外的唯一關口」， 因為當時 AI 要問的是院外的服務商。現在 AI 模型跑在院內自己的主機上，這個房間仍然存在、 仍然做去識別化與呼叫紀錄，但它守的問題變成「哪些資料可以進 AI 流程」，而不是「什麼可以送出院外」。 過渡期還有一條通往實驗室 API 的線是院外的，程式強制那條線只准送假資料。

    六、有三件事，是這套房子跟一般房子最不一樣的地方¶

    這三件不是技術選擇，是需求端先定下的前提，技術只是配合：

    1. 水不出這棟樓。 病人的資料一律不離開醫院網路。所以資料庫搬回院內、AI 換成院內主機、 推播整條拿掉。工程上有一支可以重複執行的檢查，逐一盤點程式裡有沒有任何一條線指向院外， 目前是 0 筆。
    2. 每個開關都預設關著。 有風險或還沒談定的功能（例如依歷史資料做風險提示、 會用到護理師個人資料的績效），都各有一個開關，預設是關的， 要開必須填核准依據，而且開關動作本身也會被記下來。
    3. 每一個動作都留下紀錄。 誰、在什麼時候、對誰、做了什麼、結果如何。 這不是為了監看誰，而是出事時能重建當時的情況——這是醫療系統與一般軟體最大的差別之一。

    七、這個比喻到哪裡為止¶

    任何比喻都有極限，這幾點要記得：

    1. 房子蓋完就不動了，軟體會一直改。 這裡的每次改版，比較像整棟樓在正常營業的狀態下抽換管線，所以才需要那麼多測試與稽核紀錄。
    2. 兩棟前棟不是各蓋各的。 它們用同一種建材、同一批共用零件，比較像同一份設計圖蓋出來的雙胞胎，只是用途不同。
    3. 建材不會用完。 軟體的「材料」可以無限複製，成本幾乎都在設計與施工的時間上，不在材料本身。

    八、名詞速查¶

    看到這個字 就想成
    前端 / 前棟 人看得到、會操作的畫面
    後端 / 後棟 沒有畫面的伺服器，規則與資料都在這裡把關
    框架（React／NestJS） 工法規範＋一整批預鑄件
    編譯 施工前的尺寸總檢查，對不起來就不准開工
    部署 交屋，把蓋好的東西放上伺服器讓人使用
    微服務 把機房裡的某個房間拆出去，蓋成獨棟
    稽核軌跡 監視器紀錄，誰在什麼時候動了什麼，事後查得到
    離線安裝包 把整棟預鑄好裝箱運過去，解開就能用；院內主機沒有網路，現場不能臨時補料
    容器 另一種裝箱方式（把程式與它的作業系統一起封起來）。本專案 0919 起改用離線安裝包，容器設定留著當備案
    功能開關 牆上的一排開關，每項有風險的功能一個，預設全關，誰開的都有紀錄
    去識別化 送進 AI 之前，先把姓名、病歷號這類認得出是誰的欄位拿掉
    地端推論 AI 模型跑在醫院自己的機器上，資料不必送出去。0919 起那是另一台機器，本系統只透過院內網路呼叫它
    螢幕固定 Android 內建的功能，把畫面釘在單一程式上，病人退不出去，解除要輸入 PIN。本系統的平板鎖定靠它，不靠外部的裝置管理服務
