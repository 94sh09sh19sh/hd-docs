    同院 IDH 系統參考調查：臨床資料 API 與可借用的資訊¶

    版本：v0.1　文件狀態：草案（2026-10-04 開立，1005 補上使用者的決定）　適用讀者：FDE 工程團隊、使用者本人

    0. 本文件的定位¶

    本文件不是需求文件，是一份調查紀錄。院內同一個地方已經部署了另一套系統：另一個團隊做的「透析中低血壓（IDH）預警系統」，它每隔幾分鐘就向院方抓一次透析紀錄。2026-10-04 使用者指示：

    1. 讀那套系統的程式，釐清它取得病人臨床資料的 API 怎麼用
    2. 找出那套系統裡可以補足本系統的資訊

    調查的程式有兩份：成大版（使用者提供的那一個分支）與斗六版（使用者先前取得、放在本機的一份）。兩份都只讀不改：成大版 clone 到專案 repo 以外的參考資料夾，推送位址已改成無效值。

    閱讀時請記住三件事：

    • 第 2～6 節是從別人的程式「讀出來的」，不是院方的答覆。 程式寫的不一定等於 API 的實際行為。1005 起，第 9 節的十二件事都有了使用者的決定（例如本系統直接使用這支 API），已照決定改了文件與程式；那些是使用者的決定，同樣不是院方答覆，因此清冊裡沒有任何一題因此結案（見第 7 節）
    • 公開文件的界線照舊（AGENT.md「其他硬性規則」）：API 的院內位址、參考程式的 repo 網址、任何一筆真實資料，一律不寫進本文件。要找位址，看參考程式的 scripts/fetch_API.py
    • 與需求文件衝突時，以需求文件為準

    1. 調查範圍與做法¶

    範圍 做了什麼 結果
    成大版程式 讀 Django 專案的抓取、拆檔、匯入、資料模型、畫面邏輯與兩個預測模型 本文件第 2～6 節的主要來源
    成大版其他分支 比對各分支與提供者分支的差異 發現真實病人資料留在版本歷史中，見第 8 節
    斗六版程式 讀抓取程式與單一病人歷史查詢 多一種查詢方式；血壓欄位的位置與成大版互相矛盾，見第 5 節
    實際呼叫 API 從院外試連端點的連接埠 連不上（API 只在院內網路，預期中），沒有取得任何回應
    把成大版跑起來 沒有做 提供者分支缺 Django 的設定檔，原樣無法啟動
    回應格式的實證 從版本歷史中一份 2024 年的原始回應，只看遮罩後的結構（數字、中文全部換成佔位字元） 確認了回應外形與各欄型態；做到一半被權限機制擋下，已停手，抽出的暫存檔已刪除

    2. 臨床資料 API 怎麼用¶

    面向 內容
    形態 院內一台 PHP 伺服器上的 dialysislist.php，HTTP GET
    查詢一：某一天全中心 ?date=YYYY-MM-DD。成大版、斗六版都用這一種
    查詢二：某位病人一段期間 ?case_number=<病歷號>&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD。只有斗六版用過（抓 45 天歷史算統計值）；成大那一台是否也支援，未驗證
    位址 成大、斗六各一台，都是院內 IP（不寫進公開文件）
    認證 參考程式呼叫時沒有帶任何認證資訊，純 HTTP。1005 使用者決定本系統直接使用；要不要另向資訊室報備，見第 9.2 節
    回應外形 開頭一段 <meta charset="UTF-8" />，後面接 JSON：{"data_list": [[…51 個值…], [...], ...]}
    一列是什麼 一次透析中的一筆生命徵象紀錄。透析層級的欄位（體重、脫水量、設定值）在同一次透析的每一列重複出現
    欄位怎麼認 陣列沒有欄位名稱，只能靠位置。順序見第 3 節
    回傳範圍 每次都回傳當天到目前為止的全部紀錄，不是增量。呼叫端要自己去重
    速率限制 程式裡看不出來。成大版沒有逾時與重試；斗六版加了 30 秒逾時、最多重試 3 次

    2.1 值的格式（取自 2024 年那份回應的遮罩結構）¶

    種類 格式
    病歷號 8 碼數字字串
    生日 YYYY-MM-DD
    透析開始、結束、紀錄時間 YYYY-MM-DD HH:MM，沒有秒、沒有時區（當地時間）
    數值 大多是 JSON 浮點數，例如體重、血壓、流速；年齡與透析次數是整數；少數數值欄回的是字串（如沖水量 "100"）
    缺值 空字串 ""。參考程式寫進資料庫前另把缺值補成 -1。理想體重沒填時回的是 0.0，不是 ""
    文字欄 透析模式（如 HD）、透析器型號、血管通路是一整串自由文字、Heparin 是「Free / 數字 u / 數字 u」這類組合字串

    那份回應涵蓋 2024-11-06～12-12，共 1394 次抓取、約 11 萬列，每一列都是 51 個值。

    2.2 參考系統怎麼抓、怎麼存¶

    有人開著儀表板，且分鐘數是 3 的倍數
   └─ fetchData()      GET ?date=今天 → 原始回應整段附加到 YYYY-MM.txt（備份）
   └─ convertCSV()     51 欄放進表格，丟掉兩種列（見下）→ temp.csv
   └─ splitCSV()       拆成病人、透析、紀錄三份 CSV
   └─ saveData()       寫進 SQLite；病人以病歷號、透析以（病歷號＋透析次數）、
                       紀錄以（透析＋紀錄時間）判斷是否已存在
    • 沒有真正的排程：抓取是「頁面被開啟」時順便觸發的，沒人看畫面就不抓
    • 丟掉的兩種列：病歷號不是純數字的（註解寫「同一病人有兩個 ID」）、床位以數字開頭的
    • 原始回應每月一個 YYYY-MM.txt 留底，另有一支 refetch_from_txt.py 可從留底重建資料庫

    3. 51 個欄位與本系統的對應¶

    順序取自成大版 convertCSV 的欄位名稱清單。1005 起，本系統的數值名稱一律沿用下表「欄位」那一欄的稱呼（使用者決定），代號維持不變。

    位置 欄位 本系統的對應與已確定的事
    0 ID（病歷號） patients.medical_record_no
    1 姓名 patients.display_name。2024 年那份資料的姓名有一個字是「〇」，是不是 API 本身遮的不確定，見第 9.2 節
    2 性別 patients.gender（API 是一個中文字，本系統 seed 用 M／F）
    3 出生年月日 patients.birth_date
    4 年齡 —（整數）
    5 透析次數（本院） —（整數，數值很小，不是終生累計；意義不確定，見第 9.2 節）
    6～8 透析開始時間、透析結束時間、紀錄時間 結束時間可能是預排值，SESSION_MINUTES 暫不從這裡算，見第 9.2 節
    9 透析機編號 —
    10 床位 2024 年的格式是「數字＋英文字母」。本系統床號照醫院編號（1005 使用者決定），不從這一欄帶，見第 9.2 節
    11～12 體溫、開始體溫 —
    13 透析前體重（kg） —
    14 理想體重（kg） DRY_WEIGHT。即乾體重（人為判斷）；讀到 0 不顯示
    15 目標脫水量（L） UF_TARGET。不含輸液與食物的淨減重；API 是公升，本系統是 mL，要乘 1000
    16～19 輸液量、食物重量、預估脫水量、設定脫水量（L／kg） —
    20 結束體重（kg） WEIGHT_POST
    21 實際脫水量（L） UF_VOLUME（乘 1000 換成 mL）。等於透析前體重減結束體重
    22～25 Start_SBP、Start_DBP、End_SBP、End_DBP —（透析開始／結束血壓，人為判斷確定）
    26～31 透析模式、透析器、開始透析液流速、開始血液流速、透析液 Ca、傳導度 —（開始血液流速是設定值，不是第一筆量到的值）
    32～35 血管通路、Heparin、ESA、透析器凝血情況 —
    36～37 血壓（收縮）、血壓（舒張） —（每一筆紀錄的血壓，人為判斷確定）
    38～50 脈搏、呼吸、血流速、透析液流速、靜脈壓、透析液壓、膜上壓、脫水速率、累積量、透析液溫度、肝素注射量、沖水量、確認血管通路 —（累積量是機器累計的脫水量）

    這支 API 沒有任何抽血數值。 本系統的十種臨床數值裡：

    本系統的數值 這支 API 有沒有
    DRY_WEIGHT（理想體重）、UF_TARGET（目標脫水量） 有
    WEIGHT_POST（結束體重）、UF_VOLUME（實際脫水量） 有
    SESSION_MINUTES（透析時間） 要由開始、結束時間算；結束時間可能是預排值，暫不採用
    HEMOGLOBIN、ALBUMIN、BUN_PRE、BUN_POST 沒有，1005 起暫定拿不到，見第 10 節
    KT_V 沒有，也算不出來（缺 BUN），見第 10 節

    3.1 已確定的結論¶

    事項 結論
    兩組血壓 第 22～25 欄是透析開始／結束血壓，同一次透析每列相同；第 36～37 欄是每一筆紀錄的血壓。成大版正確（人為判斷）
    開始血壓 不等於第一筆紀錄的血壓，不能用第一筆紀錄代替
    理想體重 就是乾體重（人為判斷）。本系統一律沿用 API 的稱呼「理想體重」
    脫水量各欄 目標脫水量＋輸液量＋食物重量＝預估脫水量＝設定脫水量；透析前體重－結束體重＝實際脫水量。目標脫水量是淨減重，設定脫水量是機器上設的總量；機器累計的脫水量在第 46 欄
    開始血液流速 第 29 欄是設定值，第一筆紀錄量到的血流速可能比它低
    型態 年齡、透析次數是整數；沖水量可能是 "" 或字串；其餘數值是浮點數
    0 的意思 理想體重的 0 是沒填；膜上壓、累積量、肝素注射量在透析剛開始時的 0 是真的 0。本系統讀到 0 一律不顯示（1005 使用者決定），不必逐欄分辨

    4. 本系統 HospitalApiAdapter 會長什麼樣¶

    ClinicalDataSourcePort 的第三個實作。1005 使用者決定：本系統直接用這支 API 當院方來源，但介接程式暫時不寫。 寫的時候照下面做：

    1005 迭代 15 已實作（實作結果見實作規格書 4.13）：解析照第 5 節避開那幾個坑——從第一個 { 開始、每一欄容許數字與字串、不用透析次數去重、30 秒逾時加重試；血壓用第 36～37 欄（成大版）。

    1005 新版需求：使用者指示院方 API 全面取代手動輸入（SRS 0.3、FR-S15），介接程式排進迭代 15，而且不只寫下面的數值——病人主檔、床位、療程開始與下機也由它驅動。完整設計以《實作規格書》3.5 的 1005 段落為準，本節保留當時的寫法；第 5 點「只取四種」改為「四種數值，另收有綁定平板的病人的生命徵象紀錄」。

    1. GET ?date=今天，從第一個 { 開始解析 JSON（不要學參考程式用 strip，見第 5 節第 3 點）
    2. 依位置取欄位；同一次透析只取一次透析層級的值（取最後一列）；每一欄都要容許數字與字串兩種型態
    3. 單位換算（公升 → mL）、時間補上院內時區
    4. 讀到 0 的數值不建立，輪播也就不會播（輪播第三層另外也擋 0，1005 已實作）
    5. 只取 API 有的四種：理想體重、目標脫水量、結束體重、實際脫水量
    6. 輸出 NormalizedClinicalValue，measuredAt 用透析開始時間（透析前的數值）或結束時間（透析後的數值）
    7. 其餘照現行規則：病人不存在、重複、全有或全無，都交給 ClinicalDataImportService
    8. 抓取頻率預設每 3 分鐘，護理站可調（1005 使用者決定）。介接程式寫的時候一併做成營運參數

    要留意的一個上限：單一批次最多 200 筆（CLINICAL_BATCH_MAX_ROWS）。全中心 41 床、每人四種數值已接近上限，介接時要分批，或對 API 來源另訂上限。

    5. 寫介接程式前要避開的坑¶

    1. 血壓欄位的位置，兩份參考程式互相矛盾。 成大版把第 22～25 欄當透析開始／結束血壓、第 36～37 欄當每一筆紀錄的血壓；斗六版的歷史查詢剛好把這兩組對調。人為判斷成大版正確（第 3.1 節），斗六版的歷史查詢拿到的其實是開始／結束血壓
    2. 不要照抄成大版的匯入對應。 load_data.py 把「預估脫水量」寫進 expect_dehydration、「設定脫水量」寫進 estimate_dehydration，「目標脫水量」完全沒用到。本系統以第 3 節的位置表為準
    3. 去掉開頭那段 <meta> 要自己來。 參考程式用 Python 的 strip('<meta charset="UTF-8" />')，那是「逐字元刪除頭尾出現在這組字元裡的字」，碰巧可用。本系統應該從第一個 { 開始解析
    4. 床位格式可能改過。 2024 年那份回應的床位是「數字＋英文字母」的形式，而成大版現行程式會丟掉數字開頭的列，另外還留著一行被註解掉的「床號反轉」。本系統的床號照醫院編號、由護理長填（1005），不靠這一欄，影響只在要不要用它自動對床（第 9.2 節）
    5. 時間沒有秒，也沒有時區。 以（病歷號、透析開始時間、紀錄時間）去重時，同一分鐘內的兩筆會被當成同一筆。不要用透析次數去重，它的意義還不確定
    6. 成大版沒有逾時。 院方伺服器一慢，抓取就卡住整個頁面；斗六版補了逾時與重試，本系統照斗六版的做法即可

    6.2 低血壓的判定與門檻（對 Q-03）¶

    用途 規則
    交班回饋表標出「疑似低血壓」 任一筆 SBP ≤ 90，或比前一筆掉超過 20 mmHg
    EBM 模型判定「過去某次透析有低血壓」 開始 SBP < 160 用 90、≥ 160 用 100 當門檻（註解稱 Nadir90／100），任一筆有效 SBP 低於門檻即算
    EBM 模型跳出警示 預測機率 ≥ 0.85
    排除不合理讀數 SBP < 50 不採計；序列模型另有一組合理範圍（SBP 60～250、脈搏 30～150 等）

    EBM 模型的 16 個輸入：性別、年齡、過去 7 天與 28 天的低血壓次數、開始 SBP／DBP、脈搏、呼吸、開始體溫、透析前體重、理想體重、目標脫水量、脫水量占體重比、開始血液流速、開始透析液流速、透析液溫度。

    1005 使用者決定：低血壓門檻直接套用上表。 套用來源要寫明：院內同一處已部署的透析中低血壓（IDH）預警系統（成大版）程式——「疑似低血壓」取自它的交班回饋表，「過去某次透析有低血壓」與警示機率取自它的 EBM 模型。目前本系統還沒有地方用到這組門檻（規則引擎排在迭代 18，1005 重排），用到時規則版本的「書面依據出處」照這段寫。這能不能算高風險功能開啟前要的書面確認，見第 9.2 節。

    6.3 低血壓處置的選項（對 Q-25）¶

    成大版警示回饋表可勾選的內容：

    類別 選項
    口服藥物 Midodrine、其他
    針劑藥物 IV Glucose、其他
    調整透析設定 降低血流速、降低脫水量（UF）、降低透析液流速、其他
    護理處置 頭低腳高、降低透析液溫度、沖水（flush）、其他
    其他處理 持續觀察、其他
    另記 有無症狀、處置時間、當下 SBP／DBP、員工號

    1005 使用者決定：併入。 事件範本新增第六種「透析中低血壓處置」，升版為 EVENT-TEMPLATES-v2：有無症狀（單選）、處置（複選，上表各項，藥物與透析設定帶「依醫囑」）、處置後情形（單選）。當下血壓與處置時間寫在補充說明，員工號由登入身分自動帶入。

    6.4 斗六版的兩個做法（對 Q-06、Q-07）¶

    • 去識別化：斗六版在寫入 CSV 前，把病歷號與姓名用固定金鑰做可還原的固定式加密（同一個值每次加密結果相同，才能用來串接）。本系統送進 AI 前是直接移除識別欄位，兩種做法可以一起帶去問法務
    • 院內推論端點：斗六版的程式呼叫院內一台 Ollama 服務。那是斗六的網段，與本系統所在的院區無關。1005 使用者告知：成大這邊的推論端點尚未架設

    6.5 時段（對 Q-34，旁證）¶

    成大版交班回饋表用三個時間窗判斷「這一班的病人」：早 10～11 點、午 15～16 點、晚 20～21 點（另一個版本是 10～12、14～16、19～21）；沒有結束時間的透析一律補成開始後 4 小時。這只是查詢用的時間窗，不是班別定義，但可以推測三班大約的起點。

    8. 參考程式的資料保護問題¶

    調查時發現：參考程式的 repo 不需登入就能 clone，而其中一個分支的版本歷史裡，留著真實病人的原始回應與資料庫檔（含姓名、病歷號、生日）。提供者分支與主分支已經清掉，那個分支沒有。斗六版的本機資料夾裡也有一份病人資料 CSV 與一把金鑰檔，本次都沒有開啟。

    這件事不在本系統的範圍內，也不是本系統能處理的。是哪個分支、哪些檔案，刻意不寫在公開文件裡，已在對話中告知使用者。1005 使用者表示由使用者自行處理（第 9.1 節第 1 項）。

    9.2 延伸出來、要你決定的事¶

    # 要決定什麼 可走的路與影響 建議
    1 直接用這支 API，要不要仍向資訊室報備（1005 起另立清冊 Q-35） 參考程式不帶認證，技術上呼叫得到；但抓的是全中心的病人資料，日後院方查起來沒有任何同意紀錄，也對不上 Q-06 的資料使用範圍 寫介接程式前，用一封信向資訊室報備「本系統也要呼叫這一支、每 3 分鐘一次」，留下紀錄即可，不必等核准
    2 低血壓門檻的套用來源，能不能當作高風險功能開啟前要的書面確認（FR-R08、規則版本的「書面依據出處」） 能：療程中預警等功能可以在門檻寫進規則版本後開啟；不能：門檻照用，但開啟高風險功能仍要醫師書面確認 不能。另一個團隊的程式不是院方 protocol；門檻照用、出處照寫，開啟前仍請醫師簽一次
    3 全新環境預設長出的 15 床（01～15）要不要拿掉（1005 新版需求定案：拿掉，床位改由 API 帶入） 拿掉：新環境的床位圖是空的，要護理長先照醫院編號建床才能用；留著：床號與醫院對不上，等於寫死了一組假的編號 拿掉，床位圖空白時顯示「請先到床位清單建立床位」；屬程式改動，等你點頭再做。1005 迭代 15 已拿掉：後端不再預設；床位圖空白時，接了院方資料寫「床位會隨院方資料自動出現」、沒接寫「請到專業版系統管理建立」
    4 透析結束時間可能是預排值（1005 新版需求：下機改以結束體重出現判定，結束時間只當「預計」用；第三次進院探測確認）：透析時間（SESSION_MINUTES）要怎麼取；透析中抓到的列，結束時間、結束體重、結束血壓是空的還是預填 用結束時間減開始時間：可能永遠是 4 小時；用最後一筆紀錄時間：比較接近實際，但透析中途抓到時會偏短 下次進院時看一次透析進行中的回應再定；在那之前透析時間不從 API 取
    5 透析次數的意義（不像終生累計） 不知道它是本月第幾次、轉入後第幾次還是別的；拿它去重有風險 不用它：去重一律用（病歷號、透析開始時間、紀錄時間）；意義順帶問資訊室即可
    6 姓名欄的「〇」是不是 API 本身遮的（1005 新版需求定案：病人主檔以 API 為準，建議的「不從 API 覆寫」推翻；是不是遮的，第三次進院探測時看一次） 是：API 的姓名不能拿來顯示；不是：可以用，但也代表 API 會吐出完整姓名 不管是哪一種，病人姓名照現行由護理端建立，不從 API 覆寫；院內看一次回應就知道
    7 要不要用 API 的床位欄自動把病人放上床（1005 新版需求定案：要；床號格式的對照做成設定，第三次進院看過再定） 要：省一步，但床位格式（數字＋字母）與醫院編號可能不同，還要做對照；不要：照現行由護理師在床位圖上放 不要。平板跟著病人、床不固定，自動對床反而容易放錯
    8 一個班次最多 20 床（SHIFT_BED_MAX_PER_SHIFT）要不要一起拿掉 這是一位護理師一班負責幾床的防呆，不是床位數；拿掉後班表打錯床號清單時就擋不到 保留。它管的是班表，不是床位
    9 「護理站可調」的抓取頻率由誰調 跟其他營運參數一樣，護理長與護理站管理者可改；或開放給每一位護理師 跟其他營運參數一樣，改了要填理由、寫稽核
    10 已部署的環境要不要補一次改名 數值名稱與事件範本是常數，更新後立刻換新；但求助結案的選項（「調整脫水（依醫囑）」「建議重新評估理想體重」）與匯入欄位的預設名稱存在資料庫，舊環境只在第一次啟動時寫入，不會跟著改 下次部署前補一支一次性的更新，只改還沒被護理長改過的那幾列；屬程式改動，等你點頭再做

    10. 需要、但尚未取得的資訊¶

    1005 使用者決定：院方透析清單 API 沒有的資訊暫定拿不到，用到它們的功能先預設關閉。

    資訊 用在哪個功能 現況 開啟條件
    血紅素（Hb） 輪播第三層的抽血數值；劑量調整參考（FR-N06） 輪播：收進功能開關「需要抽血數值的功能」，預設關閉；劑量調整參考本來就是高風險功能，預設關閉 院方提供血紅素的來源；劑量調整參考另需 FR-R08 書面確認
    白蛋白 輪播第三層的抽血數值 同上開關，預設關閉 院方提供白蛋白的來源
    Kt/V（院方算好的） 輪播第三層；護理端「病人趨勢」的院方 Kt/V 曲線 同上開關，預設關閉 院方提供 Kt/V 的來源，或透析前後 BUN 到位後由本系統計算
    透析前後 BUN 透析適足性（URR、spKt/V，FR-N07） 同上開關，預設關閉；關閉時「病人趨勢」不出現適足性那一張卡，後端端點擋下 院方提供透析前後 BUN 的來源；開啟前再向醫師確認公式（Q-26）
    實際透析時間 透析適足性的輸入 API 的結束時間可能是預排值，暫不採用（第 9.2 節第 4 項） 確認透析中的回應長什麼樣

    開關切換照現行規則：護理長或護理站管理者在「系統管理 → 功能開關」切換，開與關都要填核准依據並寫入稽核軌跡。「院方是否已提供來源」系統驗不到，開啟條件由切換的人確認、寫在核准依據裡。
