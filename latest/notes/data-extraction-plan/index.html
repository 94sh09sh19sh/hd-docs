    蒐集資料的完整取出：程式更動與取資料手冊的規劃¶

    版本：v0.2　文件狀態：草案（2026-10-26 開立；同日加入三種取出範圍）　適用讀者：FDE 工程團隊、接手的工程師、院方資訊室與研究承辦人

    摘要¶

    • 院方要求：系統蒐集的資訊日後要全部取得出來，供後續計畫做資料分析與模型訓練。使用者定了三個前提：現在就寫好取法、人照文件手動做得完不靠任何 AI、只能在院內主機上操作（第 1 節）
    • 為什麼現在寫：交接者的 AI 可能因資安疑慮不協助「整包取出病人資料」；97 張表、多次遷移，事後讀 schema 拼查詢容易漏（第 2 節）
    • 與《資料庫使用規範》12.1「唯一合法釋出管道是對外報表」不衝突：12 管的是離開院內；本規劃的取出只寫到主機，要離開主機或出院另走院方核准（第 3 節）
    • 程式：新增一支只讀的取出指令，以一次性容器在主機上執行、沒有網路端點也沒有畫面按鈕；先做快照再匯出，api 不必停；輸出整包含 SQLite 快照、每表 CSV、說明檔與雜湊；分「完整」「假名化」兩級（第 5 節）
    • 三種取出範圍都要做（使用者 1026 定）：一次取全部（--all）、只取某幾類表（--category）、只取某幾張表（--tables）；後兩種可以合用，要合併分析的表要在同一次取（第 5.2 節）
    • 「全部」靠檢查守住：每張表都要歸到一類、每個欄位都要登記匯出分類，沒登記 check:all 就不過（第 5.5 節）
    • 不靠模型的保證：指令的 --help、輸出包裡的 讀我.txt、部署手冊新的一冊三處都寫得出完整步驟；取出指令壞了也有第二條路：拿最新一份備份檔，用任何 SQLite 檢視工具直接開（第 6 節）
    • 判斷：規劃與取資料手冊都放公開文件站；院內特定的值（主機位址、目錄、核准文號、經手人、假名化對照表）一律不進任何 repo，只留主機設定目錄（第 7 節）
    • 六題待院方答覆、要改的需求文件與迭代切分在第 8～10 節；需求文件與程式都還沒動

    1. 院方的要求與這份文件的範圍¶

    • 院方的意思：蒐集的資訊之後需要的時候全部都要取得出來，提供後續計畫的資料分析與模型訓練，這才是數位優化與數位轉型的精神
    • 使用者 1026 定的前提：
    • 取資料的方式現在開發時就寫好，不等到要用的那天
    • 要能手動取：照文件一步一步做得完，不依靠任何模型
    • 只能在院內主機上操作才安全
    • 本文件規劃兩件事：程式要改什麼（第 5 節）、取資料手冊寫什麼放哪裡（第 6、7 節）
    • 不在範圍：資料要怎麼分析、模型要怎麼訓練、研究計畫怎麼申請——那是後續計畫與院方的事；本系統只負責取得出來、取得完整、取的人留下紀錄

    2. 為什麼現在就要寫好、而且不能靠模型¶

    到時候才做的風險 現在寫好的做法
    交接者叫 AI「把病人資料整包匯出」，AI 因資安疑慮拒絕或只給模糊方向 一個寫好的指令加一份逐步手冊，複製貼上就做得完，不必問任何人
    97 張表、950 個欄位、多次遷移，事後讀 schema 拼查詢容易漏表、漏欄 每個欄位都登記匯出分類，新欄位沒登記就擋（第 5.5 節）
    直接複製執行中的資料庫檔案，拿到不一致的狀態（規範 8.1） 先用線上備份機制做快照，從快照匯出
    拿到 CSV 卻不知道每欄的意思、時間是哪個時區、哪一版的 schema 輸出包自帶資料字典快照、schema 副本與說明檔
    原開發者離開，沒人知道有這支指令 手冊放公開文件站，主機上的映像檔與輸出包也各帶一份

    3. 與現行規範的關係¶

    現行規定 會不會衝突 怎麼處理
    《資料庫使用規範》0.2 原則 1：資料不離開它該在的機器 不衝突 取出檔只寫到主機上的匯出目錄；要搬到院內分析機器、要出院，都是院方核准之後的事，系統只留紀錄
    規範 12.1：資料離開院內的唯一合法管道是對外報表，不得以資料庫複製或查詢結果取出 不衝突，但要加註 第 12 條管的是離開院內；本規劃取出的東西留在院內。12.1 加一句：研究用取出走第 20 條（新），出院仍只能走對外報表，或院方另行核准的去識別化流程
    規範 11.2：稽核軌跡算績效屬目的外利用 同一個問題 研究與模型訓練對臨床資料同樣是目的外利用，要院方或人體研究倫理審查委員會核准；指令要求填用途與核准文號才執行，並寫進稽核軌跡
    規範 8.2：留存期限到期刪除 會衝突 到期刪除後就「全部取得出來」不了。現況是期限未定案、只標記不刪；要不要在刪除前先封存一份研究用取出，列為待答（第 8 節第 3 題）
    規範 7.1：後端是唯一寫入者 要小心 取出指令只讀；它自己的紀錄不直接寫資料庫，交給 api 收（第 5.4 節）
    部署規範 DEP-38：能登入主機的人一律可信任 正好是前提 「只能在主機操作」的實作就是不開任何網路端點：只有登入主機、在主機上下 docker compose 的人跑得動
    部署規範 DEP-14：執行期不得連往院外 要守 取出用的一次性容器一條網路都沒有（network_mode: none）

    4. 「全部」是哪些¶

    來源 取不取 說明
    資料庫 97 張表 取 含病人自報症狀與求助、護理紀錄、院方 API 匯入的數值、遊戲紀錄、AI 呼叫紀錄（提示與輸出）、稽核軌跡、裝置連線紀錄
    歷代備份檔 可指定 指令可改從某一份備份取出（--from-backup），用來回到某一天的狀態，或在刪除到期資料之後取回
    規劃中的語音與逐字稿（《緊急求助的語音說明》） 實作時一起納入 若原音存成資料庫以外的檔案，取出指令要一起帶；這條寫進那一份文件的實作清單
    密碼雜湊、登入憑證、平板裝置金鑰的雜湊 不取 對分析沒有用，取出只增加風險；欄位照列、內容清空，CSV 標「刻意不取」
    金鑰資料卷（院內 CA、簽章私鑰）、設定目錄的 .env 不取 不是蒐集的資訊，是系統的鑰匙
    對外報表產出紀錄 取 本身就在資料庫裡

    5. 程式更動¶

    5.1 指令與執行方式¶

    • 新增一支取出指令，與 db-update.mjs 一樣以一次性容器在主機上執行，例如：docker compose --env-file <設定目錄>\.env --profile export run --rm data-export --all --purpose "<用途>" --approval "<核准文號>" --operator "<經手人>" --level full（範圍參數見第 5.2 節）
    • compose 新增一個 data-export 服務，放在 export 設定檔裡（預設的 up 不會帶到它）：network_mode: none、掛資料卷與匯出目錄、不掛金鑰資料卷
    • 不做 HTTP 端點、不在護理端放按鈕：網路上沒有任何地方叫得動它
    • 新設定 HD_EXPORT_DIR：主機上的匯出目錄，與備份目錄分開；啟動時沿用備份目錄的檢查（不在專案目錄、網路磁碟或雲端同步資料夾）
    • 執行前印出摘要（取哪一級、從哪一份資料、寫到哪裡、預估大小），要打 yes 才開始

    5.2 三種取出範圍¶

    使用者 1026 定：一次取全部、只取某類表、只取某幾張表三種都要做。

    範圍 參數 什麼時候用
    全部 --all 後續計畫還不知道要用哪些、或要整份封存（第 8 節第 3 題）
    某幾類表 --category 病人自述,臨床數值 研究題目對應得到一個主題，例如「透析中低血壓」只要臨床數值、求助與護理紀錄
    某幾張表 --tables help_requests,clinical_values 核准只涵蓋特定資料，或只缺一兩張表要補取
    • 三個參數一定要給一個，不給不跑：不讓「忘了寫範圍」變成整包取出
    • --category 與 --tables 可以合用，取兩者的聯集；--all 不能與它們合用
    • 個資法的最小必要原則：核准只涵蓋部分資料時，用後兩種取，不要取全部再自己刪
    • --list 只列出每一類有哪些表、各有幾筆、最早與最晚的日期，不寫任何檔案、不算一次取出；填參數前先看它
    • 表名或類名打錯：停下來列出最接近的名稱，不猜、不跳過
    • 從舊備份取出時，範圍照那份備份的 schema 判斷；那時還不存在的表會列為「這份備份沒有」，不算失敗

    表與表之間的關聯：只取部分表時，取出的表常指向沒取的表（例如求助指向病人、療程）。

    • 預設只取指定的表，manifest.json 列出「指向了但沒取」的表與欄位
    • --with-parents 連同被指向的上層表一起取（只往上一層，例如病人、療程、平板），讓取出的資料自己能接起來；上層表照樣經過假名化與「刻意不取」的欄位處理
    • 假名化的代號每次取出不同（第 5.6 節），分兩次取的表無法用代號接起來：要合併分析的表必須在同一次取出。手冊與 讀我.txt 都要寫這一條

    類別（每張表只歸一類，實作時逐表登記，類名用中文、指令接受中文）：

    類 包含（舉例，實作時逐表登記）
    病人與療程 病人、當日排班、裝置綁定
    病人自述 症狀問卷、求助與緊急通報、心情與滿意度回饋
    臨床數值 院方 API 匯入的批次與數值
    護理紀錄 護理紀錄、各段、勾選內容、透析適足性計算、求助的後續追蹤
    衛教與測驗 衛教內容、完成紀錄、測驗作答
    遊戲 小花園、麻將連連看、記憶相簿的紀錄與盤面快照
    AI AI 呼叫紀錄、生成工作、跑馬燈內容
    營運與績效 班表、床位分配、調班、成效基準、處理者指名、獎勵
    裝置與連線 平板、連線紀錄
    稽核 稽核軌跡、備份歷程、取出紀錄、對外報表產出紀錄
    系統設定 功能開關、營運參數、選項清單、SOP 文件
    帳號 護理端使用者（憑證欄刻意不取）

    5.3 取出的流程¶

    1. 檢查參數：範圍、用途、核准文號、經手人缺一不跑；範圍展開成表的清單，印出來
    2. 用 VACUUM INTO 做一份快照（與每日備份同一個機制，api 不必停、不鎖寫入）；有 --from-backup 時改用那份備份並比對備份歷程上的雜湊
    3. 對快照跑完整性檢查
    4. 只匯出範圍內的表，依等級處理（第 5.6 節），寫成一個以時間命名的資料夾
    5. 算每個檔案的 SHA-256，寫進清單
    6. 寫一筆取出紀錄（第 5.4 節），刪掉中間的快照（完整級 --all 直接把快照當成輸出；部分取出另建一個只含範圍內表的 SQLite 檔）

    輸出資料夾的內容：

    檔案 用途
    讀我.txt 純文字：這是什麼、怎麼開、時間欄的時區、各級差在哪、不准做什麼（不必任何程式就讀得懂）
    data.sqlite SQLite 檔（只有完整級有），任何 SQLite 檢視工具都開得了；--all 是整份快照，部分取出時只含範圍內的表
    tables/<表名>.csv 每張表一個 CSV，UTF-8、第一列是欄名；JSON 欄（遊戲盤面快照，規範 6.1 例外）照原文字輸出
    manifest.json 取出時間、系統版本（git tag）、遷移版本、範圍（照下的參數與展開後的表）、等級、用途、核准文號、經手人、每張表筆數、指向了但沒取的表
    schema.prisma、data-dictionary.md 這一版的 schema 與資料字典副本，日後 schema 改了仍讀得懂舊的取出
    SHA256SUMS.txt 每個檔案的雜湊，搬到別台機器後可以驗

    5.4 取出紀錄怎麼進稽核軌跡¶

    • 一次性容器若直接寫資料庫，就有第二個寫入者（規範 7.1），因此改成：指令把紀錄附加到匯出目錄的 export-log.jsonl，api 啟動時與每小時讀一次，收進稽核軌跡與新的 export_runs 表，收過的標記起來
    • api 沒開著時一樣取得出來，紀錄等 api 下次啟動補收
    • 護理端系統管理多一個唯讀的「資料取出紀錄」頁：誰、何時、什麼範圍（取了哪些表）、哪一級、什麼用途、核准文號、筆數；頁面上沒有取出按鈕

    5.5 欄位登記：讓「全部」一直是全部¶

    • 共用常數裡為每張表登記屬於哪一類（第 5.2 節），每個欄位登記一個匯出分類：一般、直接識別（姓名、病歷號、工作 ID、床號）、準識別（生日、精確時間）、自由文字（護理紀錄內文、AI 提示與輸出、逐字稿）、刻意不取（第 4 節的憑證欄）
    • 新增盤點腳本 check:export，納入 check:all：schema.prisma 裡有任何一張表沒歸類、任何一個欄位沒登記就不過，登記了卻已不存在的也報出來
    • 效果：之後任何迭代加表、加欄，沒順手登記就過不了檢查，取出指令永遠涵蓋全部
    • 資料字典每欄多一格「匯出分類」，與登記同步

    5.6 兩個等級¶

    等級 內容 可以去哪裡
    完整（full） 原值，含 SQLite 快照 只留主機；要搬到院內分析機器須院方核准（第 8 節第 2 題）
    假名化（pseudonymized） 直接識別欄換成代號（同一個人在同一次取出裡代號一致）；自由文字欄預設整欄移除，--keep-free-text 才保留；精確時間保留（分析要用） 院內分析；仍屬個人資料，出院要院方另行核准，不得稱為「去識別化」或「匿名」
    • 代號用 HMAC 產生，金鑰每次取出隨機產生、只寫在主機的匯出目錄，要回推真實身分時由院方授權的人在主機上對照；對照表不放進輸出包
    • 不做第三級「匿名」：真正的去識別化要看用途與資料組合判斷，由院方或倫理審查委員會決定，系統不替他們宣稱

    5.7 驗證¶

    • 新增 verify: 腳本（合成資料）：每張表筆數與快照一致；每個登記為直接識別的欄在假名化輸出裡找不到原值；憑證欄是空的；SHA256SUMS.txt 對得上；跑的時候沒有任何網路連線
    • 三種範圍各一項：--all 的表數等於 schema 的表數；--category 只出那幾類的表；--tables 只出那幾張；兩者合用是聯集；不給範圍、表名打錯、--all 與其他合用都被擋；--with-parents 帶到上一層而且照樣假名化
    • 從某一份備份取出、api 停著時取出、匯出目錄設在不安全位置被擋，各一項
    • check:egress 照舊全綠

    6. 取資料手冊¶

    6.1 放在哪裡¶

    • 部署手冊新增一冊（第十六冊「取出資料」）：它是照順序做的步驟，與其他各冊同一種東西；每一步照慣例寫出會怎麼壞、怎麼處理
    • 同一份內容另有兩個副本，讓不上網、沒有 AI 的人在主機上也找得到：
    • 指令的 --help 印出完整步驟（繁體中文）
    • 每一個輸出包裡的 讀我.txt
    • 交接文件（DEP-38 已要求寫信任邊界的那一份）加一行指向第十六冊

    6.2 第十六冊的章節¶

    1. 誰可以取、取之前要有什麼（院方核准、倫理審查文號、經手人）
    2. 取出：先 --list 看有哪些類與表，再選範圍（全部、某幾類、某幾張）；PowerShell 指令逐行可複製，三種範圍各一個範例；要合併分析的表為什麼要同一次取
    3. 從某一份備份取出
    4. 確認取出成功：看筆數、驗雜湊
    5. 開啟來看：CSV 用試算表開、data.sqlite 用 SQLite 檢視工具開；不必寫程式
    6. 搬到院內分析機器（院方核准之後；只寫院內做法，不寫院外）
    7. 用完刪掉匯出檔、在系統裡確認取出紀錄
    8. 指令本身壞了怎麼辦（第二條路）：拿備份目錄裡最新一份、雜湊驗過的備份檔，複製到匯出目錄，用 SQLite 檢視工具直接開——備份就是一份完整的資料庫；缺的只有假名化與紀錄，手冊寫明這時要另外手寫一筆紀錄交給院方

    7. 判斷：公開還是私人¶

    結論：這份規劃與第十六冊都放公開文件站（docs/）。院內特定的值不放公開站，也不放私人 repo，只留在主機上。

    理由：

    • 安全不靠藏步驟。指令沒有網路端點，只有能登入主機的人跑得動；能登入主機的人本來就能直接複製資料卷（DEP-38）。公開手冊不讓任何人多拿到一筆資料
    • 資料字典已經公開。97 張表 950 個欄位早就在站上，手冊多寫的只是指令
    • 公開才保證找得到。這份手冊的讀者是幾年後的交接者，他們不一定拿得到私人 repo 的權限；權限掉了，私人 repo 裡的手冊等於不存在。文件站任何人都開得了
    • 私人 repo 也不是放秘密的地方。它在 GitHub、在每一台開發機上，都在院外；真正要藏的東西放進去一樣不對

    只能留在主機上的（寫在主機設定目錄的 .env 或院方自己的紙本，不進任何 repo、不進任何文件）：

    • 主機位址與名稱、設定目錄與匯出目錄的實際路徑
    • 院內分析機器的名稱與位址
    • 倫理審查與院方核准的文號、經手人姓名
    • 假名化的金鑰與對照表
    • 任何一次取出的內容、筆數以外的統計

    公開手冊裡這些一律寫成 <設定目錄>、<核准文號> 這類佔位字。

    8. 要院方答覆的事¶

    排迭代時登記進《尚待確認事項清冊》：

    1. 研究與模型訓練用的取出，院方的核准流程是什麼、誰簽、要不要倫理審查文號
    2. 完整級的取出可不可以離開主機、搬到院內分析機器；可以的話是哪一台、誰管
    3. 留存期限到期刪除前，要不要先封存一份研究用取出（規範 8.2 的衝突）
    4. 假名化級預設移除自由文字欄（護理紀錄內文、AI 提示與輸出、語音逐字稿），院方同不同意
    5. 匯出檔在主機上可以留多久、誰負責刪
    6. 後續計畫若要把資料帶出院（例如交給合作學校訓練模型），院方要走的去識別化流程由誰做

    10. 實作順序¶

    一個迭代（編號排入時再定），分三步，每步可單獨驗：

    1. 表的類別與欄位登記、check:export：先把 97 張表歸類、登記完，檢查全綠
    2. 取出指令、data-export 服務、三種範圍與 --list、--with-parents、兩個等級、輸出包與 讀我.txt
    3. 取出紀錄進稽核軌跡、系統管理的唯讀頁、verify: 腳本、第十六冊
