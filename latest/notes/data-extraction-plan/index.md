# 蒐集資料的完整取出：程式更動與取資料手冊的規劃

版本：v0.1　文件狀態：草案（2026-10-26 開立）　適用讀者：FDE 工程團隊、接手的工程師、院方資訊室與研究承辦人

## 摘要

- 院方要求：系統蒐集的資訊**日後要全部取得出來**，供後續計畫做資料分析與模型訓練。使用者定了三個前提：**現在就寫好取法、人照文件手動做得完不靠任何 AI、只能在院內主機上操作**（第 1 節）
- 為什麼現在寫：交接者的 AI 可能因資安疑慮不協助「整包取出病人資料」；97 張表、多次遷移，事後讀 schema 拼查詢容易漏（第 2 節）
- 與《資料庫使用規範》12.1「唯一合法釋出管道是對外報表」不衝突：12 管的是**離開院內**；本規劃的取出**只寫到主機**，要離開主機或出院另走院方核准（第 3 節）
- 程式：新增一支只讀的取出指令，以一次性容器在主機上執行、**沒有網路端點也沒有畫面按鈕**；先做快照再匯出，api 不必停；輸出整包含 SQLite 快照、每表 CSV、說明檔與雜湊；分「完整」「假名化」兩級（第 5 節）
- 「全部」靠檢查守住：每個欄位都要登記匯出分類，新欄位沒登記 `check:all` 就不過（第 5.4 節）
- 不靠模型的保證：指令的 `--help`、輸出包裡的 `讀我.txt`、部署手冊新的一冊三處都寫得出完整步驟；**取出指令壞了也有第二條路：拿最新一份備份檔，用任何 SQLite 檢視工具直接開**（第 6 節）
- **判斷：規劃與取資料手冊都放公開文件站**；院內特定的值（主機位址、目錄、核准文號、經手人、假名化對照表）一律不進任何 repo，只留主機設定目錄（第 7 節）
- 六題待院方答覆、要改的需求文件與迭代切分在第 8～10 節；**需求文件與程式都還沒動**

## 1. 院方的要求與這份文件的範圍

- 院方的意思：蒐集的資訊之後需要的時候全部都要取得出來，提供後續計畫的資料分析與模型訓練，這才是數位優化與數位轉型的精神
- 使用者 1026 定的前提：
- 取資料的方式**現在開發時就寫好**，不等到要用的那天
- 要能**手動取**：照文件一步一步做得完，不依靠任何模型
- **只能在院內主機上操作**才安全
- 本文件規劃兩件事：程式要改什麼（第 5 節）、取資料手冊寫什麼放哪裡（第 6、7 節）
- 不在範圍：資料要怎麼分析、模型要怎麼訓練、研究計畫怎麼申請——那是後續計畫與院方的事；本系統只負責**取得出來、取得完整、取的人留下紀錄**

## 2. 為什麼現在就要寫好、而且不能靠模型

| 到時候才做的風險                                                   | 現在寫好的做法                                               |
| ------------------------------------------------------------------ | ------------------------------------------------------------ |
| 交接者叫 AI「把病人資料整包匯出」，AI 因資安疑慮拒絕或只給模糊方向 | 一個寫好的指令加一份逐步手冊，複製貼上就做得完，不必問任何人 |
| 97 張表、950 個欄位、多次遷移，事後讀 schema 拼查詢容易漏表、漏欄  | 每個欄位都登記匯出分類，新欄位沒登記就擋（第 5.4 節）        |
| 直接複製執行中的資料庫檔案，拿到不一致的狀態（規範 8.1）           | 先用線上備份機制做快照，從快照匯出                           |
| 拿到 CSV 卻不知道每欄的意思、時間是哪個時區、哪一版的 schema       | 輸出包自帶資料字典快照、schema 副本與說明檔                  |
| 原開發者離開，沒人知道有這支指令                                   | 手冊放公開文件站，主機上的映像檔與輸出包也各帶一份           |

## 3. 與現行規範的關係

| 現行規定                                                                        | 會不會衝突       | 怎麼處理                                                                                                                                              |
| ------------------------------------------------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 《資料庫使用規範》0.2 原則 1：資料不離開它該在的機器                            | 不衝突           | 取出檔只寫到**主機上的匯出目錄**；要搬到院內分析機器、要出院，都是院方核准之後的事，系統只留紀錄                                                      |
| 規範 12.1：資料離開院內的唯一合法管道是對外報表，不得以資料庫複製或查詢結果取出 | 不衝突，但要加註 | 第 12 條管的是**離開院內**；本規劃取出的東西留在院內。12.1 加一句：研究用取出走第 20 條（新），**出院仍只能走對外報表，或院方另行核准的去識別化流程** |
| 規範 11.2：稽核軌跡算績效屬目的外利用                                           | 同一個問題       | 研究與模型訓練對臨床資料同樣是目的外利用，要院方或人體研究倫理審查委員會核准；指令要求填**用途與核准文號**才執行，並寫進稽核軌跡                      |
| 規範 8.2：留存期限到期刪除                                                      | **會衝突**       | 到期刪除後就「全部取得出來」不了。現況是期限未定案、只標記不刪；要不要在刪除前先封存一份研究用取出，列為待答（第 8 節第 3 題）                        |
| 規範 7.1：後端是唯一寫入者                                                      | 要小心           | 取出指令**只讀**；它自己的紀錄不直接寫資料庫，交給 api 收（第 5.3 節）                                                                                |
| 部署規範 DEP-38：能登入主機的人一律可信任                                       | 正好是前提       | 「只能在主機操作」的實作就是**不開任何網路端點**：只有登入主機、在主機上下 `docker compose` 的人跑得動                                                |
| 部署規範 DEP-14：執行期不得連往院外                                             | 要守             | 取出用的一次性容器**一條網路都沒有**（`network_mode: none`）                                                                                          |

## 4. 「全部」是哪些

| 來源                                               | 取不取         | 說明                                                                                                             |
| -------------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------- |
| 資料庫 97 張表                                     | 取             | 含病人自報症狀與求助、護理紀錄、院方 API 匯入的數值、遊戲紀錄、AI 呼叫紀錄（提示與輸出）、稽核軌跡、裝置連線紀錄 |
| 歷代備份檔                                         | 可指定         | 指令可改從某一份備份取出（`--from-backup`），用來回到某一天的狀態，或在刪除到期資料之後取回                      |
| 規劃中的語音與逐字稿（《緊急求助的語音說明》）     | 實作時一起納入 | 若原音存成資料庫以外的檔案，取出指令要一起帶；這條寫進那一份文件的實作清單                                       |
| 密碼雜湊、登入憑證、平板裝置金鑰的雜湊             | **不取**       | 對分析沒有用，取出只增加風險；欄位照列、內容清空，CSV 標「刻意不取」                                             |
| 金鑰資料卷（院內 CA、簽章私鑰）、設定目錄的 `.env` | **不取**       | 不是蒐集的資訊，是系統的鑰匙                                                                                     |
| 對外報表產出紀錄                                   | 取             | 本身就在資料庫裡                                                                                                 |

## 5. 程式更動

### 5.1 指令與執行方式

- 新增一支取出指令，與 `db-update.mjs` 一樣以**一次性容器**在主機上執行，例如：`docker compose --env-file <設定目錄>\.env --profile export run --rm data-export --purpose "<用途>" --approval "<核准文號>" --operator "<經手人>" --level full`
- compose 新增一個 `data-export` 服務，放在 `export` 設定檔裡（預設的 `up` 不會帶到它）：`network_mode: none`、掛資料卷與匯出目錄、不掛金鑰資料卷
- **不做 HTTP 端點、不在護理端放按鈕**：網路上沒有任何地方叫得動它
- 新設定 `HD_EXPORT_DIR`：主機上的匯出目錄，**與備份目錄分開**；啟動時沿用備份目錄的檢查（不在專案目錄、網路磁碟或雲端同步資料夾）
- 執行前印出摘要（取哪一級、從哪一份資料、寫到哪裡、預估大小），要打 `yes` 才開始

### 5.2 取出的流程

1. 檢查參數：用途、核准文號、經手人缺一不跑
1. 用 `VACUUM INTO` 做一份快照（與每日備份同一個機制，api 不必停、不鎖寫入）；有 `--from-backup` 時改用那份備份並比對備份歷程上的雜湊
1. 對快照跑完整性檢查
1. 依等級匯出（第 5.5 節），寫成一個以時間命名的資料夾
1. 算每個檔案的 SHA-256，寫進清單
1. 寫一筆取出紀錄（第 5.3 節），刪掉中間的快照（完整級保留快照當成輸出的一部分）

輸出資料夾的內容：

| 檔案                                  | 用途                                                                                    |
| ------------------------------------- | --------------------------------------------------------------------------------------- |
| `讀我.txt`                            | 純文字：這是什麼、怎麼開、時間欄的時區、各級差在哪、不准做什麼（不必任何程式就讀得懂）  |
| `data.sqlite`                         | 完整的 SQLite 快照（只有完整級有），任何 SQLite 檢視工具都開得了                        |
| `tables/<表名>.csv`                   | 每張表一個 CSV，UTF-8、第一列是欄名；JSON 欄（遊戲盤面快照，規範 6.1 例外）照原文字輸出 |
| `manifest.json`                       | 取出時間、系統版本（git tag）、遷移版本、等級、用途、核准文號、經手人、每張表筆數       |
| `schema.prisma`、`data-dictionary.md` | 這一版的 schema 與資料字典副本，日後 schema 改了仍讀得懂舊的取出                        |
| `SHA256SUMS.txt`                      | 每個檔案的雜湊，搬到別台機器後可以驗                                                    |

### 5.3 取出紀錄怎麼進稽核軌跡

- 一次性容器若直接寫資料庫，就有第二個寫入者（規範 7.1），因此改成：指令把紀錄**附加到匯出目錄的 `export-log.jsonl`**，api 啟動時與每小時讀一次，收進稽核軌跡與新的 `export_runs` 表，收過的標記起來
- api 沒開著時一樣取得出來，紀錄等 api 下次啟動補收
- 護理端系統管理多一個唯讀的「資料取出紀錄」頁：誰、何時、哪一級、什麼用途、核准文號、筆數；**頁面上沒有取出按鈕**

### 5.4 欄位登記：讓「全部」一直是全部

- 共用常數裡為每張表、每個欄位登記一個匯出分類：`一般`、`直接識別`（姓名、病歷號、工作 ID、床號）、`準識別`（生日、精確時間）、`自由文字`（護理紀錄內文、AI 提示與輸出、逐字稿）、`刻意不取`（第 4 節的憑證欄）
- 新增盤點腳本 `check:export`，納入 `check:all`：`schema.prisma` 裡**有任何一個欄位沒登記就不過**，登記了卻已不存在的也報出來
- 效果：之後任何迭代加表、加欄，沒順手登記就過不了檢查，取出指令永遠涵蓋全部
- 資料字典每欄多一格「匯出分類」，與登記同步

### 5.5 兩個等級

| 等級                          | 內容                                                                                                                              | 可以去哪裡                                                                     |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **完整**（`full`）            | 原值，含 SQLite 快照                                                                                                              | 只留主機；要搬到院內分析機器須院方核准（第 8 節第 2 題）                       |
| **假名化**（`pseudonymized`） | 直接識別欄換成代號（同一個人在同一次取出裡代號一致）；自由文字欄預設整欄移除，`--keep-free-text` 才保留；精確時間保留（分析要用） | 院內分析；**仍屬個人資料**，出院要院方另行核准，不得稱為「去識別化」或「匿名」 |

- 代號用 HMAC 產生，金鑰每次取出隨機產生、**只寫在主機的匯出目錄**，要回推真實身分時由院方授權的人在主機上對照；對照表不放進輸出包
- 不做第三級「匿名」：真正的去識別化要看用途與資料組合判斷，由院方或倫理審查委員會決定，系統不替他們宣稱

### 5.6 驗證

- 新增 `verify:` 腳本（合成資料）：每張表筆數與快照一致；每個登記為直接識別的欄在假名化輸出裡找不到原值；憑證欄是空的；`SHA256SUMS.txt` 對得上；跑的時候沒有任何網路連線
- 從某一份備份取出、api 停著時取出、匯出目錄設在不安全位置被擋，各一項
- `check:egress` 照舊全綠

## 6. 取資料手冊

### 6.1 放在哪裡

- **部署手冊新增一冊（第十六冊「取出資料」）**：它是照順序做的步驟，與其他各冊同一種東西；每一步照慣例寫出會怎麼壞、怎麼處理
- 同一份內容另有兩個副本，讓**不上網、沒有 AI 的人在主機上也找得到**：
- 指令的 `--help` 印出完整步驟（繁體中文）
- 每一個輸出包裡的 `讀我.txt`
- 交接文件（DEP-38 已要求寫信任邊界的那一份）加一行指向第十六冊

### 6.2 第十六冊的章節

1. 誰可以取、取之前要有什麼（院方核准、倫理審查文號、經手人）
1. 取出：PowerShell 指令逐行可複製，參數怎麼填
1. 從某一份備份取出
1. 確認取出成功：看筆數、驗雜湊
1. 開啟來看：CSV 用試算表開、`data.sqlite` 用 SQLite 檢視工具開；不必寫程式
1. 搬到院內分析機器（院方核准之後；只寫院內做法，不寫院外）
1. 用完刪掉匯出檔、在系統裡確認取出紀錄
1. **指令本身壞了怎麼辦（第二條路）**：拿備份目錄裡最新一份、雜湊驗過的備份檔，複製到匯出目錄，用 SQLite 檢視工具直接開——備份就是一份完整的資料庫；缺的只有假名化與紀錄，手冊寫明這時要另外手寫一筆紀錄交給院方
1. 疑難排解

## 7. 判斷：公開還是私人

**結論：這份規劃與第十六冊都放公開文件站（`docs/`）。院內特定的值不放公開站，也不放私人 repo，只留在主機上。**

理由：

- **安全不靠藏步驟**。指令沒有網路端點，只有能登入主機的人跑得動；能登入主機的人本來就能直接複製資料卷（DEP-38）。公開手冊不讓任何人多拿到一筆資料
- **資料字典已經公開**。97 張表 950 個欄位早就在站上，手冊多寫的只是指令
- **公開才保證找得到**。這份手冊的讀者是幾年後的交接者，他們不一定拿得到私人 repo 的權限；權限掉了，私人 repo 裡的手冊等於不存在。文件站任何人都開得了
- **私人 repo 也不是放秘密的地方**。它在 GitHub、在每一台開發機上，都在院外；真正要藏的東西放進去一樣不對

只能留在主機上的（寫在主機設定目錄的 `.env` 或院方自己的紙本，**不進任何 repo、不進任何文件**）：

- 主機位址與名稱、設定目錄與匯出目錄的實際路徑
- 院內分析機器的名稱與位址
- 倫理審查與院方核准的文號、經手人姓名
- 假名化的金鑰與對照表
- 任何一次取出的內容、筆數以外的統計

公開手冊裡這些一律寫成 `<設定目錄>`、`<核准文號>` 這類佔位字。

## 8. 要院方答覆的事

排迭代時登記進《尚待確認事項清冊》：

1. 研究與模型訓練用的取出，院方的核准流程是什麼、誰簽、要不要倫理審查文號
1. 完整級的取出可不可以離開主機、搬到院內分析機器；可以的話是哪一台、誰管
1. 留存期限到期刪除前，要不要先封存一份研究用取出（規範 8.2 的衝突）
1. 假名化級預設移除自由文字欄（護理紀錄內文、AI 提示與輸出、語音逐字稿），院方同不同意
1. 匯出檔在主機上可以留多久、誰負責刪
1. 後續計畫若要把資料帶出院（例如交給合作學校訓練模型），院方要走的去識別化流程由誰做

## 10. 實作順序

一個迭代（編號排入時再定），分三步，每步可單獨驗：

1. 欄位登記與 `check:export`：先把 97 張表登記完，檢查全綠
