    迭代 17.1：停用統一、把病人拖到平板、一鍵展示病人端¶

    版本：v0.1　文件狀態：已完成（2026-10-06 開立）　適用讀者：FDE 工程團隊

    0. 本文件的定位¶

    本文件不是需求文件，是一份修正紀錄：2026-10-06 使用者一次提出七件事，指示歸在迭代 17.1 處理——

    1. 「鎖定」與「停用」用詞統一用「停用」
    2. 病人正在透析使用的平板不能停用
    3. 停用太不常用，放到系統管理
    4. 刪除病人頁「長期指定平板給病人」的功能
    5. 簡易版原本要把病人與平板拖到床位，改成把病人拖到平板，床號由院方資料自動補上——床位與病人已經由院方資料配好，護理師只需要配對平板與病人
    6. 進院前連不到院方 API，看不到病人端實際跑起來的樣子：要能在進院前就看到，並直接產生一張病人透析到一半的平板截圖（有跑了一段時間的折線圖、各種數字與跑馬燈）
    7. 護理端的「跑馬燈」改叫「公告與院內衛教」；護理端原本的「衛教」改叫「結束與離院衛教」，與院內衛教區別

    本文件記錄每一件改了什麼、開發端做的判斷，以及影響到哪些既有規則。

    • 功能需求來源仍是《軟體需求規格書》；本次改寫 FR-S15 的第 2 條界線與 5.2 補充說明「指派平板與病人」那一列（SRS 自己的版本歷程定版日補）
    • 範圍與技術選型仍以《實作規格書》為準（4.15.1 節是本文件的摘要；1.1 記下第四次刻意改動既有驗收腳本）
    • 介面規則仍以《介面設計基準》為準；本次改 3.3、3.5（新增 3.5.2）、4.6、6.2、6.4
    • 與需求文件衝突時，以需求文件為準

    為什麼叫 17.1 而不是迭代 18。 七件事都是改既有功能的做法與名稱，沒有新增需求；迭代 18（規則引擎）的內容一項都沒動。

    3. 逐項說明¶

    3.1 停用（第 1～3 項）¶

    原本的情形：程式裡有兩種「停用」——平板狀態 RETIRED（標籤「已停用」）與 MDM 鎖定 mdmLocked。 RETIRED 沒有任何流程會設定它；畫面上的「停用」其實都是 mdmLocked：簡易版把平板拖到停用區＝鎖定並從床位拿下，專業版叫「遠端鎖定」。 同一件事兩個名字，護理師分不出差別。另外，目前只有模擬 MDM，「鎖定」只是資料裡的記號，平板本身的畫面不會被鎖住。

    改成：

    • 畫面上一律叫「停用」，入口只有專業版系統管理 → 平板停用（要有裝置管理權限，沒有就整個分頁不出現）。 停用要確認一次（加上限制的方向才要阻力，基準 N-5）；解除停用按了就做
    • 正在服務病人的平板，後端擋下停用（409，「這台平板正在服務病人，不能停用。請先下機或解除配對」）。 分頁上那一列不畫停用按鈕，寫「先下機才能停用」。理由是接上真的平板管理系統之後，病人手上的平板會當場被鎖住、按不了求助
    • 停用的同時從床位拿下來（原本簡易版的停用區就是這樣做，這次搬進後端，任何呼叫者都一樣）。解除停用不放回原床：配給病人時會自動放到那位病人的床
    • 簡易版：沒有停用區，停用的平板不出現在平板框裡（迭代 14.2 讓停用的平板回到清單、帶鎖頭，這次反過來——停用的就是不能用，不必出現）
    • RETIRED 不動：它是預留給報廢的狀態，仍沒有流程會設定它，標籤仍是「已停用」（共用常數的註解寫明）

    3.2 拿掉長期指定平板（第 4 項）¶

    迭代 15 的設計是「每位病人配一次平板，系統記住；院方資料判定透析開始就自動以那一台開始療程」。這次拿掉：

    • 病人頁的「配給的平板」一欄、端點 PUT /patients/:id/preferred-device、護理端的 setPreferredDevice、共用型別的 preferredDeviceId 都拿掉
    • 院方資料同步不再自己建立綁定；療程的建立、開始、換床、下機、生命徵象照舊由院方資料決定
    • 資料表 patients.preferred_device_id 留著不刪（只做加法，《資料庫使用規範》第 18 條），程式不讀不寫；已經填過的值不清
    • 「沒有自動接上」的三個原因（平板不在線上、正在別人的療程中、停用或未佈建）不會再出現；床號認不出來、床是停用的床兩個原因照舊標示

    3.3 把病人拖到平板（第 5 項）¶

    做法：

    • 放置區是平板（TABLET_SLOT）：平板框裡的格子、床位格裡的平板圖示都是。拿起一位病人，只有能配的平板會亮（有佈建、沒停用、沒在服務別人）
    • 配平板走專業版本來就有的 POST /bindings（排班與指派頁「指派平板」同一支）。接了院方資料時，後端把平板放到這次療程的床—— 這就是「透過 API 自動補上床號」。自動放床不算護理師手動換床，之後院方資料說病人換床，平板照樣跟著走； 目的床上若有另一台平板正在服務別人就不搬（與同步的「平板跟著病人換床」同一條：判斷不了就不猜）
    • 接了院方資料時，床位圖上只畫正在服務病人的平板：沒在用的平板都在平板框裡（它的床號是上一位病人的，下一次配給誰就跟著誰走）
    • 沒接院方資料（使用者選的，見第 1 節）：平板已經在某一床，病人配給它就在那一床；平板在框裡，配好之後格子上寫病人的名字，接著把平板拖上床。 「＋」新增病人也拖到平板上，表單長在那台平板旁邊
    • 院方資料還沒判定開始就先配也可以（病人上床時就配）：配平板讓療程進入進行中；院方資料一判定開始，開始時間改成院方的那一刻（任務時點從真正開始透析起算，FR-P15）。 反過來，院方資料已經判定開始的療程，配平板不改開始時間
    • 復原＝解除這次配對；沒接院方資料時平板放回原本的床

    點選替代：平板同時是拿得起來的東西（拖到另一床＝換床）與放置區。手上拿著病人時點平板＝放下；手上沒東西時點平板＝拿起平板。 Pickable 帶 target 時同時登記成放置區，平板框與床位格共用一個 TabletChip。

    連帶改的兩處後端行為（不改的話新流程會出錯）：

    改了什麼 不改會怎樣
    手動解除（換平板、配錯了復原）不再標「護理師改過」；只有下機（含提前結束）才標 迭代 15 的規則是手動解除之後同步不再動那一筆療程。配錯了按復原，療程就從此不會被院方資料接回進行中，也不會自動下機
    先配好平板的療程，院方開始時間跨過班別界線時跟著換班別，不另建一筆 院方的開始時間先是預排值、開始後才是實際值；跨過 12 點或 17 點時，院方資料會另建一筆沒有平板的療程，平板留在舊的那一筆

    3.4 一鍵展示病人端（第 6 項）¶

    npm run demo:patient                                   # 啟動後一直開著，Ctrl+C 結束
npm run demo:patient -- --screenshot <檔名.png>          # 截一張 1280×800 的圖後自動結束
npm run demo:patient -- --screenshot <檔名.png> --portrait # 直式 800×1280

    一次啟動模擬院方 API（8091）、後端（3100）、病人端（5184）與護理端（5183），都與平常開發用的埠錯開，兩邊可以同時開著。

    • 另一個全新的資料庫，放在平常那個資料庫旁邊的 demo 目錄，每次重來；平常開發用的資料庫不受影響。 不放系統暫存目錄：後端拒絕把資料庫放在共用目錄底下（《部署規範》DEP-37 第 3 項），也拒絕放在專案目錄裡
    • 模擬院方 API 的「進行中」那一組已經透析了約 100 分鐘、每 10 分鐘一筆紀錄（新的環境變數 HOSPITAL_API_SIM_IN_PROGRESS_MINUTES，預設 60 不變），圖一開就有曲線
    • 準備資料全部用護理師會用的同一組端點：同步一次院方資料、註冊四台平板、把「模擬戊」配給第一台、再同步一次寫入生命徵象、 核准三則隨版本帶入的院內衛教、開啟病人端跑馬燈。展示用的資料庫裡夜間時段關掉，晚上跑也看得到跑馬燈
    • 病人先把透析前問卷填掉：否則一開畫面就是問卷，看不到首頁。100 分鐘時心情問卷（120 分）與衛教（180 分）還沒到，首頁不會被任務蓋住
    • 護理端用 .env 的最高權限帳號登入；展示用的資料庫是新的，第一次登入會要求改密碼，改的只是展示用的那一份
    • 截圖用本機的 Chrome 無頭模式。Windows 上從 node 直接叫 chrome.exe 會安靜地沒有輸出（與《架構圖》文末記的是同一個坑），所以經 PowerShell 的 Start-Process -Wait
    • 只用虛構的合成資料、只連本機

    1006 實際跑出來的畫面（23:05，模擬戊 B1 床，透析約 105 分鐘）：血壓圖 10 個點、最新 131／78；脫水量圖 10 個點、最新 1.3 公斤、「預計 2.9」虛線； 五格數字（脈搏 83、透析前體重 58.0、理想體重 55.6、相差 +2.4、目標脫水量 2.4，各帶資料時間）；底部跑馬燈正在跑一則院內衛教；求助區在最下方。 橫式與直式各截一張，兩個方向都不捲動。

    3.5 護理端改名（第 7 項）¶

    原本 1006 起 改在哪
    跑馬燈內容（導覽列、專業版那一頁、簡易版那一框） 公告與院內衛教 導覽定義、CarouselPage、ContentTray；稽核動作與 AI 用途的名稱一併改
    跑馬燈內容的種類「衛教」 院內衛教（「中心公告」不變） CAROUSEL_ITEM_KIND_LABELS
    衛教（導覽列） 結束與離院衛教；那一頁的第一張卡叫「結束衛教與測驗」 導覽定義、EducationPage
    離院衛教（獨立一頁，版位預設關閉） 併進「結束與離院衛教」頁，是那一頁裡的一段；預設仍關閉 導覽定義的 partOf、navigation.service.ts、DischargeEducationPage.tsx 刪除

    病人端不改：病人看到的仍是「跑馬燈」與「衛教」任務。

    離院衛教怎麼「併成一頁」又能單獨關：它在版位資料裡仍是一項（DISCHARGE_EDUCATION，原本的版位與切換紀錄都留著）， 定義多一個 partOf: EDUCATION——沒有自己的連結與路由；版位只有開放（更多選單）與關閉，放不上主列；所屬那一頁關了它也跟著不存在。 開放時，後端在導覽資料的 sections 裡告訴畫面，「結束與離院衛教」頁才畫那一段；後端端點照舊依它擋下（DEP-34）。 它在系統管理的版位清單裡叫「結束與離院衛教：離院衛教」，一看就知道是哪一頁裡的哪一段。

    4. 開發端在實作時做的判斷¶

    使用者要推翻時改右欄那一處即可。

    判斷 理由 寫在哪
    停用的同時從床位拿下來，搬到後端做 原本只有簡易版的停用區會拿下來，專業版的遠端鎖定不會；入口只剩一個之後，規則放在後端最不會走偏 DevicesService.setLocked
    接了院方資料時，沒在用的平板一律畫在平板框裡（不管它的床號） 平板的床號是上一位病人的；留在床上會讓人以為那一床還有平板可用，而下一次配給誰它就跟著誰走 simple/model.ts 的 tabletOnBed
    接了院方資料時，沒在用的平板不能拖到床上 放上去也沒有意義（下一次配平板就搬走），而且在床位圖上看不到 simple/model.ts 的 accepts
    手動解除不再標「護理師改過」 見 3.3 的表；提前結束走的是下機，不受影響（迭代 15 驗收 3 照驗） BindingService.releaseByNurse
    配平板時，院方已判定開始的療程不改開始時間 原本綁定一律把開始時間寫成綁定那一刻；迭代 15 自動接上時會帶院方的時間覆寫，護理師手動配沒有這一步 DeviceBindingRepository 的建立交易
    展示用的資料庫放在平常那個資料庫的旁邊 系統暫存目錄被 DEP-37 擋下；專案目錄也被擋下；放在一起好找、也好刪 demo-patient.ts 的 demoDataDir
    展示的病人先填掉透析前問卷 一開畫面就是問卷，就不是使用者要看的「透析到一半」；真實情形也是上機時就填了 demo-patient.ts
    離院衛教在版位清單裡仍是一項 它原本的版位與切換紀錄都在資料表裡；之後決定好帶回家的方式，護理長開它時要有地方開，也要查得到誰在什麼時候開的 NAV_ITEM_DEFINITIONS 的 partOf
    lock 圖示留在登記表 畫面上不再用（系統管理是文字按鈕），但刪掉要重產兩端的圖示資料，留著不影響任何畫面 scripts/sync-icons.mjs
