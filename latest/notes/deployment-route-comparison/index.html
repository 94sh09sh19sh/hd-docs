    部署路線比較：離線安裝包與容器¶

    版本：v0.1　文件狀態：歷史紀錄（0922 第一次進院後撰寫，用來詢問院方容器是否為硬性要求）

    0926：這一題已經有答案。 院方確認要以容器部署、程式以 git clone 取得，而且不准用隨身碟， 離線安裝包因此撤除（《部署規範》v3.0、實作規格書迭代 11）。本文保留當時的比較，不再更新； 現行做法看《部署手冊》第十一冊。

    第一次進院前，部署走的是《部署規範》DEP-07 定下的離線安裝包； 0922 進院當天，院方要求改為在容器內部署（經過見《第十冊 · 第一次進院紀錄》）。

    這份文件把兩條路線攤開來逐項比較，目的只有一個：帶著它去問院方，容器是不是硬性要求； 如果是，要求背後想解決的是哪一件事。 院方若在意的是「與同機其他專案隔離」，第 3 章說明安裝包路線已經做到， 而且在這台主機上做得比容器更完整；院方若另有理由（例如統一維運），容器路線也走得通，代價寫在第 4、5 章。

    這不是需求文件，與《部署規範》衝突時以部署規範為準。

    0. 先講結論¶

    離線安裝包（原本的路線） 容器（院方當天要求的路線）
    規範地位 正式路線（DEP-07） 備案，院方明確要求時啟用（規範 3.3）
    與其他專案隔離 做得到：執行期、目錄、帳號、連接埠四件事一起隔開（DEP-37，第 3 章） 做得到，但與同機另一個專案共用同一個 Docker，某些事反而綁在一起（第 3.3 節）
    斷電重開後自己回來 會：開機就啟動，不需要有人登入 不會：Docker Desktop 要有人登入 Windows 才啟動
    資料庫放哪 主機上看得到、備份軟體掃得到的目錄 WSL2 虛擬磁碟裡的具名資料卷，檔案總管看不到
    主機要不要連院外 全程不用 照第九冊在主機上建置時要，而且要開七個網域
    要院方裝什麼 什麼都不用（執行期隨包帶） Docker Desktop（已裝）、Git；Docker Desktop 的授權要院方確認
    準備狀態 安裝包已建好、驗收過（0.1.0，建自 3a4bde2） 開發端演練過一次，修正尚未合回 master

    建議向院方提出的問法：「貴院要求容器，是為了哪一件事？」——把第 6 章那張對照表帶去，讓院方勾選。 若答案是「隔離」，請院方評估第 3 章的做法是否足夠；若答案是其他理由，照院方的要求走容器，並把第 5 章那幾件事寫進書面例外。

    1. 兩條路線各長什麼樣¶

    1.1 離線安裝包¶

    開發端                                         院內主機（全程不連外）
建置 → 自帶 Node.js 與資料庫引擎 → 壓縮 →      隨身碟 → 核對雜湊 → 解壓到 C:\hd\<版本>\
逐檔雜湊 → 掃毒                                → 以專用低權限帳號註冊為開機排程工作 → 啟動
    • 程式、執行期、Prisma 引擎全部在安裝包裡，不用主機上任何全域安裝的東西
    • 資料庫、備份、.env 放在主機上安裝包目錄之外的固定目錄，換版時整包換、資料不動
    • 常駐方式是 Windows 內建的排程工作，觸發條件是「開機時」，以專用帳號執行，倒下後每分鐘重試、最多三次
    • 手冊：第一冊～第六冊

    1.2 容器（第九冊）¶

    院內主機（建置期間要連外）
git clone → docker build（下載基底映像、npm 套件、Prisma 引擎）→ 關閉連外
→ docker compose up -d → 三個容器：api、nurse-web、patient-web
    • 程式在映像檔裡；資料庫在具名資料卷 hd-tablet-care-data（WSL2 的虛擬磁碟內）；備份掛主機目錄
    • 常駐方式是 Docker 的重新啟動策略 unless-stopped
    • 手冊：第九冊

    0922 現場的做法不屬於這兩條的任何一條。 那天手動開了一個 python 容器、把整顆 C 槽掛進去，再在容器裡照第九冊做。 本文件比較的「容器路線」一律指第九冊的做法。

    2. 逐項比較¶

    # 比較面向 離線安裝包 容器（第九冊） 在這台主機上誰比較好
    1 對主機全域環境的要求 無。不需要 Node.js、不需要 Git 需要 Docker Desktop 與 Git 安裝包
    2 主機是否要連院外 不用。建置全在開發端（DEP-11、DEP-14） 建置時要開 GitHub、Docker Hub、Debian、npm、Prisma 七個網域；要寫書面例外 安裝包
    3 進院交付方式 隨身碟，一個壓縮檔加雜湊值，可逐檔掃毒 git clone；或在開發端建好映像檔再 docker save 帶進去（掃毒工具多半看不進去，規範 3.1） 安裝包
    4 資料庫位置 NTFS 上的一般目錄，看得到、備份得到、還原得回來 WSL2 虛擬磁碟裡的資料卷，要透過 docker 指令才碰得到；虛擬磁碟目前在個人資料夾 AppData 底下 安裝包
    5 SQLite 檔案鎖 本機 NTFS，沒有問題 資料卷沒有問題；若把資料放 Windows 目錄的繫結掛載就不可靠（DEP-23） 平手（前提是容器照第九冊做）
    6 斷電或重新開機後 排程工作「開機時」觸發，不需要任何人登入 Docker Desktop 要有人登入 Windows 才會啟動，容器才回來 安裝包（這台主機電源不穩、無人看管，見第 4 章）
    7 倒下後自動重新啟動 排程工作每分鐘重試，最多三次 unless-stopped，一直重試 容器略好
    8 與同機其他專案隔離 見第 3 章 見第 3 章 見第 3 章
    9 處理器與記憶體上限 沒有作業系統層級的上限 可以在 compose 設上限（目前沒有設）；但整個 WSL2 仍與另一個專案共用 容器略好
    10 更新 帶新安裝包進去、解壓到新目錄、備份並驗證還原、遷移、換版；全程不連外 開連外 → git fetch → 重建映像檔 → 關連外 → 備份與遷移 → 換版；每次更新都要開一次連外 安裝包
    11 回退 舊版目錄改名保留，換回去即可 舊版映像檔保留，改 .env 的標籤即可 平手
    12 授權 無第三方授權問題 Docker Desktop 對一定規模以上的組織要付費訂閱，要院方確認（第九冊 D-03 第 2 題） 安裝包
    13 院方維運人員的熟悉度 排程工作、資料夾、PowerShell，Windows 管理員都會 院方已有專案在用 Docker，可能比較熟悉容器 容器（待院方確認）
    14 準備狀態 安裝包已建好、驗收五項通過、開發端更新與回退各演練一次；乾淨機器全程演練仍待做 開發機上演練一次，抓到三個問題已修，但修正只在 docker-route 分支 安裝包

    3. 不用容器，為什麼也能與其他專案隔離¶

    這一章是這份文件的重點。 院方要求容器，最常見的理由是「同一台主機上有別的專案，要隔開」。 這個顧慮完全正確——《部署規範》v1.0 當初選容器，第一個理由也正是它。0919 改走安裝包時， 這條理由沒有被拿掉，而是換了一種做法達成（規範 3.1、DEP-37）。

    3.1 「隔離」要防的是哪幾件事¶

    先把「隔離」拆開。共用主機上，兩個專案互相傷害的方式只有這幾種：

    # 會出什麼事 例子
    ① 相依互相干擾 對方升級或移除全域的 Node.js，本系統跟著壞，而且看起來像本系統自己壞的
    ② 檔案互相碰到 對方的清理腳本掃到本系統的資料夾；或本系統的資料放在對方也會寫的共用目錄
    ③ 病人資料被別人讀到 對方的維運人員登得進這台主機，而資料庫目錄是人人可讀的預設權限
    ④ 連接埠互搶 兩邊都想用 3000，某次重新開機、啟動順序對調時才發作
    ⑤ 資源被吃光 對方把磁碟寫滿，SQLite 直接寫入失敗；或把記憶體吃光
    ⑥ 一起停擺 對方做維護、重新啟動某個共用的元件，本系統被連帶停掉

    容器不是魔法，它也只是分別處理這六件事的一種方式。下面逐件對照。

    3.2 安裝包路線怎麼做到¶

    # 做法 由誰把關
    ① 相依 Node.js 執行期與 Prisma 引擎隨安裝包攜帶，完全不用主機上的全域安裝；Prisma 版本鎖死（DEP-04、DEP-30、DEP-37 第 1 項）。主機上有沒有 Node.js、是哪一版，對本系統沒有任何影響 程式：check:offline 盤點；安裝包自帶執行期
    ② 檔案 安裝目錄、資料庫目錄、備份目錄都在本系統自己的路徑底下，資料與程式分開（DEP-08、DEP-37 第 3 項） 程式：資料或備份目錄指到暫存、公用、桌面、文件、下載等共用位置時拒絕啟動；註冊腳本拒絕把資料目錄放在安裝包目錄之內
    ③ 資料 服務以專用低權限帳號執行（排程工作 RunLevel Limited）；註冊時加 -LockDownDataDir，資料庫與備份目錄移除繼承權限，只留服務帳號、Administrators、SYSTEM 三者（DEP-12、DEP-37 第 4 項） 腳本：service-install.ps1 以 icacls 設定；沒加參數會出警告。部署當天人工確認（檢查清單 9.1 第 9 條）
    ④ 連接埠 三個埠向資訊室登記後寫進主機的 .env，不寫死在程式；正式環境沒填埠號就拒絕啟動（DEP-37 第 2 項） 程式：拒絕啟動；護理端「執行環境」顯示實際埠號
    ⑤ 資源 磁碟保留下限 DB_DISK_MIN_FREE_MB（預設 1GB），低於下限時版本更新在備份之前就停下；可用空間顯示在護理端 程式；磁碟門檻與監看人待資訊室議定
    ⑥ 停擺 本系統是自己的一個排程工作，不依附任何與其他專案共用的元件；別的專案重新啟動、更新、清理自己的東西，碰不到它 結構上就是分開的

    一句話：容器把「隔離」包成一個現成的盒子；安裝包是把盒子的六面牆一面一面自己砌起來，而且每一面都有程式或腳本在把關。

    3.3 同樣六件事，容器怎麼做¶

    # 容器的做法 與安裝包相比
    ① 相依 執行期在映像檔裡 一樣好
    ② 檔案 容器有自己的檔案系統；資料在具名資料卷 一樣好，前提是不掛主機目錄。0922 那一次掛了整顆 C 槽，就一點隔離都沒有了
    ③ 資料 容器裡以 node 身分執行；但任何能下 docker 指令的人（docker-users 群組）都能把資料卷掛出來整個讀走，不需要任何密碼 安裝包比較細：它能做到「別的專案的人登得進主機，但讀不到資料夾」；容器路線上，能用 Docker 的人就讀得到，而同機另一個專案本來就要用 Docker
    ④ 連接埠 容器內部的埠各自獨立；但對外的主機埠仍然是共用的，一樣要登記 一樣要登記。0922 現場 3000 已被佔用，容器沒有讓這件事消失
    ⑤ 資源 可以在 compose 設處理器與記憶體上限 容器較好（本系統目前沒設，負載也很小）。磁碟方面，資料卷在虛擬磁碟裡，看到的是虛擬磁碟的上限，實體磁碟反而要另外監看（第九冊 D-20）
    ⑥ 停擺 本系統與另一個專案共用同一個 Docker Desktop、同一個 WSL2 安裝包較好。對方更新或重新啟動 Docker Desktop、執行 wsl --shutdown、下 docker system prune -a，本系統都會跟著停或被清掉映像檔（第九冊 D-03 第 5 題）

    3.4 在這台主機上，兩者的隔離結果¶

    把 0922 現場看到的條件放進來（《第十冊》第 3 節）：

    • 同機另一個專案已經在用 Docker Desktop
    • docker-users 群組裡只有一個本機帳號，而那就是平常登入這台主機的帳號，也是系統管理員
    • 主機電源不穩、無人看管
    隔離面向 安裝包 容器
    ① 相依 ✓ ✓
    ② 檔案 ✓ ✓（照第九冊做的話）
    ③ 資料 ✓ 對非管理員的登入者有效；對系統管理員無效 能用 Docker 的人都讀得到；而這台主機上能用 Docker 的，就是那個唯一的登入帳號
    ④ 連接埠 ✓ 登記即可 ✓ 登記即可
    ⑤ 資源 磁碟有下限保護；處理器與記憶體沒有上限 可設上限；實體磁碟要另外看
    ⑥ 停擺 ✓ 不依附共用元件 ✗ 與另一個專案共用 Docker Desktop

    結論：在這台主機上，安裝包路線的隔離不比容器差，在 ③ 與 ⑥ 兩項還比較好；容器只在 ⑤ 的處理器與記憶體上限佔優。

    兩條路線都擋不住的一件事：系統管理員讀得到一切。這不是部署形態能解決的，是帳號管理的問題—— 目前這台主機只有一個帳號、而且就是管理員，不論走哪一條路線，都要先請院方處理帳號（《第十冊》F-12）。

    3.5 什麼情況下容器才真的必要¶

    《部署規範》3.3 列了三種啟用容器的情形，本文件建議院方從這三條裡確認是哪一條：

    規範 3.3 的條件 這一次的情形
    院方資訊室明確要求以容器形式交付 0922 現場的要求，待確認是否為硬性規定、理由為何
    安裝包層級的隔離經實際運行後證明不夠，院方要求作業系統層級的隔離 安裝包還沒在院內跑過，尚無運行結果可以證明不夠
    正式主機改為 Linux 不是，主機是 Windows 11

    4. 這台主機的條件，對兩條路線的影響¶

    0922 現場看到的 對安裝包 對容器
    電源不穩，碰到就斷電，要人手動開機；無人看管 開機後排程工作自己啟動，只要有人按下電源鍵就會回來 按下電源鍵還不夠，還要有人登入 Windows，Docker Desktop 才啟動、容器才回來。第九冊 D-26：「這條路線就不適合 24 小時運作的照護系統」
    同機另一個專案在用 Docker Desktop 無影響 共用同一個 Docker（3.3 ⑥）；Docker Desktop 的設定（使用統計回報、虛擬磁碟位置）不能只為本系統改
    主機當天連得到院外 不需要連外，不論連不連得到都一樣 建置與每次更新都需要連外；若院方之後把連線關掉，更新就要改成在開發端建好映像檔再帶進去
    3000 埠已被佔用 換一個登記過的埠，寫進 .env 同左，而且埠號會被建進映像檔，換埠要重建
    有一顆 RAM 磁碟、資料磁碟之一只剩約 4.6% 資料與備份目錄要避開這兩顆；程式會擋住共用目錄，但擋不住 RAM 磁碟，要人工避開 資料在 C 槽的虛擬磁碟裡，不受影響；備份目錄一樣要避開
    Docker Desktop 從 Microsoft Store 安裝 無影響 更新由市集設定決定，可能在透析班次中自己更新並重新啟動

    電源這一條會左右結論：如果院方能加不斷電系統並安排開機後自動登入，容器路線的最大缺點就消失； 如果不能，安裝包路線是這台主機上唯一能在斷電後自己回來的做法。

    5. 若院方確認容器是硬性要求¶

    照第九冊走，並把下列事項寫進書面例外（第九冊 D-06）：

    # 事項 為什麼要寫下來
    1 資料庫只放具名資料卷，不放 Windows 目錄 DEP-23，規範明定換路線時不得重新討論
    2 重新開機後由誰登入 Windows；或改用開機自動啟動的 Docker Engine 否則斷電後服務不會回來
    3 建置與更新時的對外連線：開哪些網域、誰開、誰關、怎麼證明關了 DEP-11 例外；零院外連線
    4 Docker Desktop 授權由院方確認 不是開發端能決定的事
    5 同機另一個專案不得執行 docker system prune -a、wsl --shutdown 等會連帶影響本系統的指令，或執行前先知會 共用 Docker 的代價（3.3 ⑥）
    6 docker-users 名單與加人時要知會誰 能用 Docker 就讀得到病人資料（3.3 ③）

    另有一個折衷做法可以一併提給院方：映像檔在開發端建好，以 docker save 匯出、隨身碟帶進去 docker load。 這樣容器照樣是容器，但主機不必為了建置開連外；代價是封存檔對掃毒工具不透明（規範 3.1），且開發端要先補上這條流程的手冊與演練。

    6. 要問院方的問題¶

    6.1 可以直接寄出的文字¶

    關於 0922 部署時提到「以容器方式部署」，想先確認貴院的要求，以便下次進院一次完成：

    1. 以容器部署是硬性規定嗎？若是，是基於哪一份規範或哪一項考量？（請參考下表勾選）
    2. 若主要考量是與同機其他專案隔離，我們原本的離線安裝包做法已在執行期、目錄、帳號權限、連接埠四方面個別隔離， 細節見附件第 3 章。請貴院評估這樣是否可以接受。
    3. 若仍須以容器部署：主機重新開機後由誰登入 Windows？Docker Desktop 的授權是否涵蓋本系統？ 建置期間需要對外連線，是否可以開放？或者由我們在院外建好映像檔再帶入？
    4. 資料庫檔案是否可以放在 Docker 的資料卷內（主機檔案總管看不到，但每日備份會輸出到主機上看得到的目錄）？
    5. 主機目前電源不穩，是否可以加裝不斷電系統，或設定恢復供電後自動開機？

    6.2 院方要求容器的理由對照¶

    請院方勾選，每一種理由對應的建議不同：

    院方的理由 安裝包是否滿足 建議
    與同機其他專案隔離 是（第 3 章） 走安裝包；若院方仍不放心，說明哪一項不足，再討論
    不希望在主機上裝任何執行期 是，執行期隨包攜帶，不裝進系統 走安裝包
    資訊室統一以 Docker 管理所有專案 否 走容器，照第 5 章寫書面例外
    方便日後移到別台主機 大致是：安裝包解壓即可，資料庫是單一檔案 兩者皆可
    院內資安規範明文要求 視規範內容 請提供規範條文，依條文決定
    限制處理器與記憶體用量 否 走容器，並在 compose 設上限
    其他 — 請說明
