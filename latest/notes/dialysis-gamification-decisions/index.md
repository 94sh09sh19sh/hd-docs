## 0. 本文件的定位

《透析中的遊戲化》（以下稱**上層文件**）是分析。這一份是它的子文件，記錄 1010 使用者對上層文件第 11 節的決定，以及兩段接續的分析：

- 存檔、跟護理師互動、跟其他病人互動的**技術代價**（第 3 節）
- 護理站會有幾個**功能開關**、各管什麼（第 4 節）

**這一份仍然不是需求文件，也沒有改動任何需求文件。** SRS、資料字典、實作規格書要改的地方列在第 6 節，進入實作時跟著各階段一次改齊。與需求文件衝突時，以需求文件為準。

上層文件的章節編號在本文件寫成「上層 7.1」這種形式。

## 3. 技術代價

以目前的程式為基準（迭代 17.7）。範圍已經照第 1、2 節縮小：沒有暗棋，所以沒有對弈。

### 3.1 存檔

| 可以直接沿用的                                                                                                                | 要新做的                                                   | 會卡的地方                                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 病人端 `offline-queue.ts` 的做法：資料一律先寫進平板本機（IndexedDB）再送出，以 clientId 讓後端不重複寫入。目前只用在症狀回報 | 每款遊戲的存檔資料表，加上每一步的操作紀錄（狀態評估要用） | **平板上那份存檔只在這次療程內有用。** 綁定解除時平板要清掉本機資料（SRS 4.3 步驟 8，`device_bindings.device_cleared_at`），所以換平板接著玩完全靠伺服器 |
|                                                                                                                               | 每一步帶序號，斷線補送時伺服器照序號排，不會新舊顛倒       | **《資料庫使用規範》6.1 不以 JSON 承載。** 牌局、花園的狀態用 JSON 存最自然；全部拆成欄位，存檔的代價明顯變高。實作前要決定這裡能不能開例外              |

**代價：中。** 大部分是存檔資料表的設計與序號處理。

### 3.2 跟護理師互動

| 功能                   | 可以直接沿用的                                                   | 要新做的                                                                                                    |
| ---------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 送花給護理師           | 護理端的即時推送（現在用來送求助）                               | 護理端多一種小訊息。**送給誰還沒決定**：照班表的床位分派送給負責這一床的護理師，或送給整個護理站（第 7 節） |
| 護理師回貼圖或預設回覆 | 下一次療程才顯示，存起來、開療程時讀出來即可，**不需要即時推送** | 貼圖與預設回覆的清單；回覆以病人為準存，不以平板                                                            |
| 病友小撇步             | 跑馬燈的核准流程（FR-N17）、長度上限                             | 病人端「我也是這樣做的」與預設小撇步的選單；護理端核准清單多一種來源；署名只到「本中心病友」                |
| 共通                   | 稽核軌跡                                                         | 護理師送給病人的內容要不要記進稽核軌跡，比照現有的護理師操作                                                |

另外有一件不花程式、但要刻意做的事：**上層 H-13 規定不能變成工作**，所以護理端不能有未讀紅點、待辦清單、催促。

**代價：低～中。**

### 3.3 跟其他病人互動（只有匿名的彙總）

| 可以直接沿用的                                                | 要新做的                                                                   | 會卡的地方                                                                                                            |
| ------------------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `treatment_sessions` 有排班日期與班別，「今天這一班」算得出來 | 共同花園、今日牌局完成人數、共同記憶三種彙總的計算                         | **固定班別群組在資料模型裡沒有。** 共同花園要跨很多次療程累積，要的是「一三五早班」這種固定群組，現在只有「某天某班」 |
|                                                               | 最低人數門檻：彙總的人數低於門檻就不顯示那一句（建議預設 3，做成營運參數） | **人數少時匿名會破功。**「今天這一班有 1 個人家裡也有大同電鍋」，鄰床猜得出是誰                                       |

**代價：中。** 若將來做暗棋的非同步對弈，代價會跳到**高**：邀請與同意、輪流下棋的狀態、對方沒來或換床、離線補送，以及第一次把別人的資料畫到自己的平板上（隱私模型要擴大）。這些這次都不做。

### 3.4 狀態評估資料的調閱（第 2 節第 6 題衍生）

| 要新做的         | 說明                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| 社工、醫師的角色 | 系統現有角色沒有這兩種。最小的做法是新增兩個角色，只能看病人詳細資訊與狀態評估彙整，不能操作臨床功能 |
| 調閱的稽核       | 比照現有病人資料的調閱                                                                               |
| 留存與同意       | 比照平板其他資料，寫進資料字典與資料庫使用規範，不另立一套                                           |

**代價：中。** 角色與權限是整個護理端都會碰到的地方，要連帶檢查每一頁的權限。

## 4. 功能開關

### 4.1 八個開關

照 FR-S08 的做法，**全部預設關閉**；切換要有 `FEATURE_FLAG_MANAGE` 權限，開和關都要登記理由，每次切換寫進稽核軌跡。

| #   | 開關                       | 管什麼                                                                                                   | 實作階段 |
| --- | -------------------------- | -------------------------------------------------------------------------------------------------------- | -------- |
| 1   | 病友小撇步                 | 病人端看完衛教後的「我也是這樣做的」與分享選單；護理端核准清單裡的小撇步來源。關掉時已核准上架的照樣播完 | 1        |
| 2   | 護理師回貼圖               | 護理端對心情問卷「想讓我們知道的事」回貼圖或預設回覆；病人端下一次療程開始時顯示                         | 1        |
| 3   | 透析小花園                 | 花園本身；問卷、衛教、遊戲做完給養分；**連動開關 4**                                                     | 2        |
| 4   | 送花                       | 病人把花送給護理師；護理端那則小訊息                                                                     | 2        |
| 5   | 病人之間的互動             | 三種匿名彙總：共同花園、今日牌局完成人數、共同記憶                                                       | 2        |
| 6   | 麻將連連看                 | 一般牌局與今日牌局                                                                                       | 3        |
| 7   | 狀態評估彙整（護理端顯示） | 護理端看不看得到由遊戲資料整理出的趨勢陳述（上層 9.2）。**關掉時資料照樣記錄**，只是不顯示               | 3        |
| 8   | 老台灣記憶相簿             | 相簿本身，加上護理端病人詳細資訊那格「回應主題」聊天話題                                                 | 4        |

不建立的開關：換位拼圖、暗棋（不做）、里程碑卡（第 7 題不做）。

### 4.2 送花與小花園的連動

| 動作               | 結果                                                             |
| ------------------ | ---------------------------------------------------------------- |
| 開小花園           | 送花**跟著開**                                                   |
| 關小花園           | 送花**跟著關**                                                   |
| 小花園開著，關送花 | 只關送花，花園照常                                               |
| 小花園關著，開送花 | **不允許**：送花的前提是有花園。開關中心顯示「要先開透析小花園」 |

一個後果要知道：小花園關了再開，送花會跟著重新開啟。若院方只想要花園、不要送花，每次開小花園之後要再關一次送花。

實作上，現有的開關中心已經有「開啟前提」的檢查（`feature-flags.service.ts` 的 `judge`），「要先開小花園」可以直接用它；**「跟著開、跟著關」的連動是新的行為**。連動造成的那一次切換也寫進稽核軌跡，理由記成「隨透析小花園開啟（或關閉）」。

### 4.3 不設開關的遊戲化

以下幾樣只是在現有流程裡改一句話或多一個畫面，不碰臨床、不碰隱私、不增加護理師的工作，所以不另設開關：

| 功能                 | 上層出處 | 為什麼不設                                          |
| -------------------- | -------- | --------------------------------------------------- |
| 問卷送出後的那一句話 | 4.3      | 只換送出後的一句                                    |
| 任務完成記號         | 4.4      | 只是完成色加勾選圖示；給小花園養分的部分歸開關 3 管 |
| 我的衛教小本子       | 4.4、4.6 | 只放病人端已核可的內容                              |
| 跑馬燈的「你知道嗎」 | 4.9      | 照樣走跑馬燈的核准流程，跑馬燈本身已有開關          |

遊戲圖示（第 2 節第 1 題）**至少有一款遊戲的開關開著才出現**；三款都關，基本資訊區跟現在一樣。

## 5. 實作順序

### 5.1 四個階段

| 階段                       | 做什麼                                                                                                                                             | 開關    | 先決條件                                                  |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | --------------------------------------------------------- |
| **1 平板現有功能的遊戲化** | 問卷送出後的一句話、任務完成記號、我的衛教小本子、病友小撇步、護理師回貼圖、跑馬燈的「你知道嗎」                                                   | 1、2    | 改 FR-P08、FR-N17 等條文（第 6 節）                       |
| **2 透析小花園**           | 遊戲圖示與遊戲框（沿用 `TaskFrame`）；存檔機制（第 3.1 節）；花園、圖鑑、養分接上階段 1 的完成事件；送花；固定班別群組與最低人數門檻，做出共同花園 | 3、4、5 | 存檔是否開 JSON 例外、送花送給誰、植物插畫來源（第 7 節） |
| **3 麻將連連看**           | 牌局、連線規則、自動洗牌、今日牌局與完成人數；每一步的操作紀錄；護理端的狀態評估彙整；社工與醫師的角色                                             | 6、7    | 深棕牌面                                                  |
| **4 老台灣記憶相簿**       | 相簿、共同記憶、護理端聊天話題                                                                                                                     | 8       | 主題篩選子文件（第 8 題）、AI 繪製的圖（第 9 題）         |

換位拼圖、暗棋先不做。

**為什麼這個順序**：上層 4.11 指出，第 1、3、5 角大多落在現有功能，**不必等遊戲就能先開始心理支援**；小花園是把其他功能串起來的骨幹，要在另外兩款之前，養分才有地方去；連連看程式量低、資料最乾淨，順便把狀態評估的資料管線做起來；相簿內容量最大，要等主題篩選與繪圖兩件前置工作。

### 5.2 記憶相簿的兩件前置工作

**主題篩選（第 8 題）**：實作前由 AI 先完整判斷，寫成子文件掛在上層文件底下，至少涵蓋：

- 主題分類（上層 7.1 的飲食、交通、家庭、遊戲、節慶、工作，可增減）與每類要畫哪些物件
- 要避開的題材（上層 7.1：創傷、政治、戰爭、重大歷史事件、選舉），以及判斷「可能讓人難過」的準則
- 每一張的「這是什麼？」選項與說明文字的寫法，照迭代 17.3 的用語把關

**AI 繪製（第 9 題）**：是記憶相簿實作的子任務，風格與分類照上面那份子文件。上層 7.1 的規則照舊：不畫可辨識的真人；另外**只畫物件、不畫商標**（大同電鍋畫的是那個樣子，不是它的商標）。要顧到上層第 5 節的四個階段：

| 階段     | 對圖的要求                                                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 發現     | 第一眼就認得：最先出現的是最常見的物件，畫風寫實、不幼稚                                                                                                            |
| 上手     | 起始的幾張難度最低（上層 7.1：常見的先出、少見的後出）                                                                                                              |
| 養成     | 起始約 200 張，涵蓋各主題，讓每次療程都有沒看過的                                                                                                                   |
| **終局** | **一做好幾年，圖要一直有新的**：每季加一包、節令主題（中秋、春節、端午……）、偶爾一張驚喜卡；分類要留得下以後新增的主題。上層第 5 節說這一段做不好，半年後就沒人玩了 |

## 7. 還沒決定的事
