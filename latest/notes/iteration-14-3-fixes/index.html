    迭代 14.3：斷線示警遍及專業版每一頁與簡易版¶

    版本：v0.1　文件狀態：已完成（2026-09-29 開立）　適用讀者：FDE 工程團隊

    0. 本文件的定位¶

    本文件不是需求文件，是一份修正紀錄：2026-09-29 使用者照部署手冊第十四冊 N-05 檢查院內主機的 Docker Desktop 設定時， 問到「Docker 自動更新、或主機斷電，護理端會不會有警告」。查下去發現只有常駐總覽螢幕會大聲示警， 使用者隨即指示：專業版所有畫面與簡易版，斷線都要有非常醒目的警告。接著查病人端時又發現一個缺口：病人端的請求沒有逾時上限， 主機斷電時要等很久才發現連不上（2.5），使用者指示併入 14.3。本文件記錄查出來的現況、決定怎麼改，以及影響到哪些既有規則。

    • 功能需求來源仍是《軟體需求規格書》，本文件不新增任何功能需求
    • 範圍與技術選型仍以《實作規格書》為準（4.12.3 節是本文件的摘要）
    • 介面規則仍以《介面設計基準》為準；本次在 4.4、6.2 各補一條，第 6.4 節的刻意決定第 1 條擴及每一個畫面
    • 與需求文件衝突時，以需求文件為準

    為什麼叫 14.3 而不是迭代 15。 這是護理端顯示層與病人端請求逾時的補強，後端一行都沒動，迭代 15（規則引擎）的內容一項都沒動。

    1. 起因：斷線時各畫面原本長什麼樣子¶

    院內主機的 Docker Desktop 是從 Microsoft Store 裝的（第十冊 F-16），更新由市集決定，可能在透析班中自己更新、自己重新啟動； 主機也可能斷電（第十冊 F-18、F-19）。這兩種情況下，護理端各畫面原本是：

    畫面 斷線時
    常駐總覽螢幕 紅框閃爍＋「連線中斷」橫幅（FR-N12）
    專業版即時總覽 一個小標籤「串流中斷，改為定時更新」，不醒目
    專業版其他頁面 什麼都沒有
    簡易版 什麼都沒有；要等護理師按下操作、送出失敗才知道

    畫面停在最後一刻的資料、看起來一切正常，新的求助卻進不來——看起來正常的斷線，是最危險的斷線。 而系統本來就不會在斷線時主動通知任何人（FR-S07 不准院外推播），唯一的線索只能在畫面上。

    2. 怎麼改¶

    2.1 判定（apps/nurse-pwa/src/connection-status.tsx）¶

    帳號 偵測方式 多快示警
    看得到病人的帳號（簡易版與專業版的一般使用者） 沿用既有的即時串流：心跳加 45 秒閒置看門狗 服務重新啟動幾乎立即；主機斷電最慢約 45 秒
    看不到病人的帳號（例如稽核／法規） 這類帳號沒有串流，改成每 15 秒探一次存活檢查（GET /api/health），逾時 8 秒 最慢約 23 秒
    任何帳號 瀏覽器回報本機離線 立即
    • 失敗過一次才算斷線。 剛開頁面時串流還沒連上，connected 本來就是 false；若直接拿它判斷，每次換頁或重新整理都會閃一下紅。 改成要等第一次連線失敗（reconnectAttempt > 0）才算。會被學會忽略的警示，等於沒有警示
    • 存活檢查一定要有逾時。 主機斷電時請求不會出錯，只會一直等；不設上限就等於不偵測
    • 三種情況分開寫，因為要做的事不一樣：「連線中斷」（等它自己重連，同時留意呼叫鈴）、「這台電腦沒有網路」（檢查網路線）、 「登入已失效」（附「重新登入」按鈕）

    2.2 長什麼樣子¶

    整個畫面外圍一圈閃爍的紅框，加上一條紅底白字、帶 wifi-off 圖示的橫幅，寫明「畫面上的資料不會更新，新的求助可能看不到」。

    • 紅框持續閃爍，理由同常駐總覽螢幕（基準第 6.4 節的刻意決定第 1 條）：斷線是持續存在的故障狀態，不是一則通報。 開了「減少動態效果」時閃爍會停，紅框與橫幅都留著
    • 紅框不擋點擊（pointer-events: none）：斷線時仍可能要看最後一刻的資料；擋住只會讓人去重新整理，而重新整理之後連頁面都載不到
    • 顏色不是唯一線索：有文字、有圖示；role="alert"，螢幕報讀會念出來
    • 用的都是既有語彙：--c-alert 底、--c-alert-ink 字，兩者的對比度本來就在 check:ui:design 的搭配清單裡；閃爍的另一格用既有的 --c-overlay-alert
    • 圖示沿用登記表的 wifi-off（沒有網路），病人端斷線時用的也是它，意思相同，所以是同一個圖示

    2.3 放在哪裡¶

    畫面 位置
    專業版 主框架裡、導覽列下方，所有頁面的路由之上——不是某一頁自己畫。與求助橫幅由同一層一起黏在上緣：示警在上、求助在下
    簡易版 工作台最上面獨占一列，緊急紅框那一條往下讓；床位圖那一列讓出高度（.wb:has(> .conn-lost) 改成三列），整頁仍不捲動。一開頁面就連不上、停在「載入中」時也看得到
    常駐總覽螢幕 不經過這裡，維持它自己那一套

    求助橫幅為什麼要跟著動：它原本自己 position: sticky; top: 0。示警若也各自黏在 top: 0，捲動時後來的會蓋住先來的—— 斷線時正是最不能蓋住求助的時候。改由外面一層 .shell-sticky 一起黏，層級維持 20（低於導覽列，「更多」選單照樣蓋得過它）。

    2.4 這是「專業版不動」的例外¶

    FR-N14 與基準都寫「專業版即 0919 的完整介面，功能與版面不更動」。這次是使用者 0929 明確指示的例外，範圍壓在最小： 只加一個共用元件與上緣那一層，各頁本身一行都沒改。技能檔與基準 4.4 都註明了這是唯一的例外。

    2.5 病人端：主機斷電時要及時改成「請按床邊呼叫鈴」¶

    病人端原本就有斷線處理，而且比護理端完整：每 3 秒輪詢一次，失敗就當作斷線（Wi-Fi 正常、伺服器停了也算）， 首頁出現黃色「沒有網路，需要時請按床邊呼叫鈴」，求助區改成「請按床邊呼叫鈴／目前無法通知護理站」； 求助不做離線暫存（SRS 4.4），問卷先存平板、恢復後補送。顏色用黃不用紅：病人端的紅色只給求助按鈕。

    缺口：所有請求都沒有逾時上限。

    情況 請求的結果 病人端多快發現
    Docker 更新時重新啟動、服務停掉 連線立刻被拒絕 約 3 秒，沒問題
    主機斷電 沒有回應，一直等，直到瀏覽器自己的連線逾時 可能數十秒以上（沒有實測）。這段時間求助區仍顯示「我需要協助」；病人若剛好送出求助，會一直停在「正在通知護理站」

    怎麼改：device.ts 新增 deviceFetch，16 個對後端的請求一律走它，8 秒逾時即中止。 每 3 秒一次的輪詢最慢約 11 秒發現連不上；送出求助最多約 8 秒就換成「沒辦法通知護理站，請按床邊呼叫鈴或出聲叫護理人員」。

    • 不用 AbortSignal.timeout()：外殼支援到 Android 5（minSdk 21），舊版 WebView 沒有它，改用 AbortController 加計時器
    • 求助逾時而後端其實已收到（只是回應回不來）：病人看到「請按呼叫鈴」、護理站也收到了求助——兩邊都去處理，是安全的那一個方向； 反過來（病人以為送到了、護理站其實沒收到）才危險
    • 問卷照舊先寫進平板的佇列再上傳；逾時的那一筆留在佇列，恢復後補送，後端以同一個識別碼去重，不會重複
    • 畫面一個字都沒改，只是讓既有的斷線處理及時啟動

    3. 驗收¶

    驗什麼 怎麼驗 結果（0929）
    判定、位置、醒目、不擋點擊、減少動態效果；病人端請求逾時 npm run verify:iteration14-3（6 步，不需後端） 全部通過
    既有驗收沒有被動到 build、check:all 六支、verify:iteration8、verify:iteration14、verify:iteration14-1、verify:iteration14-2 全部通過
    實際看過 停掉後端、暫停後端（模擬斷電）、拔網路線、讓登入失效，專業版幾頁、簡易版與病人端各看一次 待做（見下）

    還沒有在瀏覽器實際看過：做這次變更的那個 clone 沒有 .env、沒有資料庫，Docker 也沒有在跑。 要在手動測試的環境照《迭代 14.3 分冊》x111～x128 走一次，特別是：

    • 簡易版在 1366×768 出現橫幅時沒有捲軸（x116）——腳本只驗得到版面的規則，驗不到實際排出來的高度
    • 剛開頁面、換頁、切換兩版時不會誤閃（x119）
    • 病人端在暫停後端時最慢約 11 秒改成「請按床邊呼叫鈴」（x126）——停掉後端模擬不出斷電，要用暫停

    沒有改的：主機斷電時系統仍然不會主動通知任何人。示警只出現在已經開著的畫面上； 護理站的常駐總覽螢幕仍要一直開著、有人看得到。
