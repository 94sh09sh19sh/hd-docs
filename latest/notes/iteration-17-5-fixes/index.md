# 迭代 17.5：透析一律開始後四小時結束

版本：v0.1　文件狀態：已完成（2026-10-07 開立，同日追加調整）　適用讀者：FDE 工程團隊

## 0. 本文件的定位

本文件不是需求文件，是一份**修正紀錄**：2026-10-07 使用者決定把《[迭代 17.4 修正紀錄](https://94sh09sh19sh.github.io/hd-docs/latest/notes/iteration-17-4-fixes/index.md)》第 4 節那件既有的事歸在迭代 17.5 處理——

> **三處統一用開始後 4 小時。** 院方資料沒有預計結束時間時，本透析中心透析時間都是預設四小時；四小時不是建議，是院方硬性規定。

同日看完第一版之後，使用者追加：

> **專業版也要全面套用四小時的設定，不管院方資料有沒有預計結束時間，都要知道是四小時結束。**

所以最後的規則是：**一次透析一律在開始後四小時結束**。院方資料的預計結束時間照樣記在療程上，但**不拿來算進度、畫橫軸或判定「待確認下機」**。 本文件記錄改了什麼、開發端做的判斷。

- 功能需求來源仍是《[軟體需求規格書](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/srs/index.md)》；四小時這條規則 1007 補在 SRS 取捨表「透析開始、預計結束時間」那一列與 FR-S15 對照表「下機」那一列
- 範圍與技術選型仍以《[實作規格書](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/implementation-spec/index.md)》為準（4.15.5 節是本文件的摘要；1.1 記下**第七次**改動既有驗收腳本）
- 與需求文件衝突時，以需求文件為準

**為什麼叫 17.5 而不是迭代 18。** 只改「透析什麼時候結束」這一個時間怎麼算，沒有新的端點、資料表一欄都沒動；迭代 18（規則引擎）的內容一項都沒動。 追加的部分與 17.3 的前例相同（同日追加調整，仍算 17.5）。

## 1. 原本各算各的

17.4 截圖時發現，院方資料**沒有**預計結束時間時，三處畫面的終點不一樣；專業版總覽與常駐總覽螢幕又是另一種算的方式：

| 地方                                                                                | 改之前                                                                          | 例：08:20 開始、10:01 配上平板、10:04 看，沒有預計結束 |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 護理端簡易版平板格（`TabletCell.tsx` 的 `progressOf`）                              | 有預計結束：開始 → 預計結束；沒有：退回綁定進度（配上平板 → 綁定有效期限）      | 約 0%                                                  |
| 病人端基本資訊區的進度條（`App.tsx`）                                               | 有：開始 → 預計結束；沒有：開始 → 綁定有效期限（配上之後 6 小時）               | 約 23%                                                 |
| 病人端面板的橫軸（`TodayPanel.tsx`）                                                | 有：開始 → 預計結束；沒有：開始 → 開始後 4 小時（檔內常數，註解寫「不是規定」） | 約 42%                                                 |
| 專業版總覽、常駐總覽螢幕（`OverviewPage.tsx`、`WallDisplayPage.tsx`，進度由後端算） | 一律綁定進度：配上平板 → 綁定有效期限，不看透析開始                             | 約 0%                                                  |
| 「待確認下機」（後端 `awaitingDischargeConfirm`）                                   | 只在有預計結束時判定：過了預計結束再加門檻；沒有預計結束**永遠不標**            | —                                                      |

1007 使用者告知四小時是院方硬性規定，所以「開始後四小時」就是那一次透析的結束，不是猜。

## 3. 開發端的判斷

| 判斷                                                                                                          | 理由                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 院方的預計結束時間**照樣記**（`treatment_sessions.expected_end_at`、面板與總覽的 `expectedEndAt` 欄位都還在） | 院方資料寫了什麼仍要留得下來；第三次進院探測時也要知道它多常缺、是不是剛好四小時。只是不再拿它算任何東西             |
| 沒有院方資料的環境（開發機、院方資料斷掉時護理師手動配的）一樣用四小時，起點是平板配上的時間                  | 規定是「透析一律四小時」，與資料從哪裡來無關。原本這種情形畫到配上後 6 小時（綁定有效期限）；現在所有畫面都是 4 小時 |
| 綁定有效期限（`expiresAt`，配上後 6 小時）不改                                                                | 那是平板配對的安全期限（過了自動解除），不是透析的結束；改它會影響到期解除的行為，不在這次範圍                       |
| 四小時放 `@hd/shared`，不放營運參數                                                                           | 這是院方規定，不是現場要調的值；改的話是整個中心的規定改了，該走程式與文件一起改                                     |
| 營運參數「過了預計結束多久標示待確認下機」的名稱不改                                                          | 「預計結束」現在就是開始後四小時，名稱仍然正確；改名會動到既有的設定資料與驗收腳本                                   |
| 專業版總覽只有配了平板的病人才畫進度條，沒有平板的照舊畫「—」                                                 | 使用者指示的是「四小時」這個終點；沒有平板的病人要不要也畫進度，是另一件事                                           |

**追加之後在瀏覽器實際看過**：重開 `demo:patient`、配好同樣四位，後端回傳的綁定進度模擬戊 45%（09:40 開始、11:28 看；17.5 以前會接近 0%）；專業版即時總覽「療程進度」與總覽螢幕模式的磚塊都是「1小時48分」、約四成五，與簡易版一致。兩張圖補在週報附錄。

**沒有驗的**：院方真實資料的預計結束多常缺、是不是剛好四小時（第三次進院探測，Q-09 第 9 題）；「待確認下機」只由 `verify:iteration15:api` 驗，沒有在畫面上等到它出現。
