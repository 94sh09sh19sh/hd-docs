# 迭代 17.5：沒有預計結束時間時，三處進度統一用開始後四小時

版本：v0.1　文件狀態：已完成（2026-10-07 開立）　適用讀者：FDE 工程團隊

______________________________________________________________________

## 0. 本文件的定位

本文件不是需求文件，是一份**修正紀錄**：2026-10-07 使用者決定把《[迭代 17.4 修正紀錄](https://94sh09sh19sh.github.io/hd-docs/latest/notes/iteration-17-4-fixes/index.md)》第 4 節那件既有的事歸在迭代 17.5 處理——

> **三處統一用開始後 4 小時。** 院方資料沒有預計結束時間時，本透析中心透析時間都是預設四小時；四小時不是建議，是院方硬性規定。

本文件記錄改了什麼、開發端做的判斷，以及刻意沒有一起改的地方。

- 功能需求來源仍是《[軟體需求規格書](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/srs/index.md)》；四小時這條規則 1007 已補在 SRS 取捨表「透析開始、預計結束時間」那一列
- 範圍與技術選型仍以《[實作規格書](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/implementation-spec/index.md)》為準（4.15.5 節是本文件的摘要；1.1 記下**第七次**改動既有驗收腳本）
- 與需求文件衝突時，以需求文件為準

**為什麼叫 17.5 而不是迭代 18。** 只改三處畫面算進度的終點，沒有新的端點、資料表一欄都沒動；迭代 18（規則引擎）的內容一項都沒動。

## 1. 原本三處各算各的

院方資料有預計結束時間時，三處都是「開始 → 預計結束」，沒有問題。**沒有的時候**終點各不相同（17.4 截圖時發現）：

| 地方                                                     | 改之前                                               | 例：08:20 開始、10:01 配上平板、10:04 看 |
| -------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------- |
| 護理端平板格的進度條（`TabletCell.tsx` 的 `progressOf`） | 退回綁定的進度：從平板配上的時間算到綁定有效期限     | 約 0%                                    |
| 病人端基本資訊區的進度條（`App.tsx`）                    | 開始 → 綁定的有效期限（配上之後 6 小時）             | 約 23%                                   |
| 病人端面板的橫軸（`TodayPanel.tsx`）                     | 開始 → 開始後 4 小時（檔內常數，註解寫「不是規定」） | 約 42%                                   |

1007 使用者告知四小時是院方硬性規定，所以「開始後四小時」不是猜，就是那一次透析的預定結束。

## 2. 改了什麼

| #   | 改什麼                                                                                                                                                             | 檔案                                       |

| 2   | 病人端進度條的終點改用它，不再用綁定的有效期限（`expiresAt`）                                                                                                      | `apps/patient-pwa/src/App.tsx`             |

## 3. 開發端的判斷

| 判斷                                                                                         | 理由                                                                                                                                         |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 沒有院方資料的環境（開發機、院方資料斷掉時護理師手動配的）一樣用四小時，起點是平板配上的時間 | 規定是「透析一律四小時」，與資料從哪裡來無關。原本這種情形病人端畫到配上後 6 小時（綁定有效期限），護理端也是；現在兩端都是 4 小時，仍然一致 |
| 預計結束早於開始也當成沒有                                                                   | 院方資料讀到不合理的值時，原本病人端進度條停在 0%、護理端退回綁定進度；現在照規定畫，不會出現一條不動的進度條                                |
| 四小時放 `@hd/shared`，不放營運參數                                                          | 這是院方規定，不是現場要調的值；改的話是整個中心的規定改了，該走程式與文件一起改                                                             |

## 4. 刻意沒有一起改的

使用者指示的是「三處」，以下幾處行為相關但不在範圍內，**照舊**，列出來讓之後決定：

| 地方                                                                          | 現況                                                             | 為什麼留著                                                                                                                                       |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 專業版總覽與常駐總覽螢幕的進度條（`OverviewPage.tsx`、`WallDisplayPage.tsx`） | 一律畫「綁定經過時間 ÷ 綁定有效期限」，有沒有院方預計結束都一樣  | 它們畫的一直是綁定進度，不是這次三處的那種「有預計結束就用、沒有就各自退回」；要不要也改成透析進度待使用者決定                                   |
| 「待確認下機」的判定（後端 `awaitingDischargeConfirm`）                       | 只在**有**預計結束時間時才判定；沒有的話永遠不會標「待確認下機」 | 判定下機是另一件事（SRS FR-S15），而且要等第三次進院看院方資料多常缺這一欄。照四小時的規定，沒有預計結束時也可以用開始後四小時判定，待使用者決定 |
