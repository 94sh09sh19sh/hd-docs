    迭代 17.7：新增病人回到開關後面、平板管理、醫院格式的床號、衛教拖到平板¶

    版本：v0.1　文件狀態：已完成（2026-10-07 開立）　適用讀者：FDE 工程團隊

    0. 本文件的定位¶

    本文件不是需求文件，是一份修正紀錄：2026-10-07 使用者一次交代了四件事，歸在迭代 17.7 處理——

    專業版補回新增病人功能，跟簡易版都預設關閉。平板停用稱呼改成平板管理。 簡易版手選床位，不應該是 1~15，而是醫院病床名稱格式。 現在沒有床位不能拖曳衛教，但那是因為之前是拖到床位，現在改拖到平板，所以應該是有病人跟平板配對的就要可以播。

    本文件記錄改了什麼、開發端做的判斷。

    • 功能需求來源仍是《軟體需求規格書》；新增病人補在 SRS 院方 API 取代表「新增病人」那一列與簡易版任務表，衛教拖到平板補在同一張任務表「推送輪播內容」那一列
    • 範圍與技術選型仍以《實作規格書》為準（4.15.7 節是本文件的摘要；1.1 記下第九次改動既有驗收腳本；3.7 記下新開關與它的端點例外）
    • 介面規則同步在《介面設計基準》3.3（專業版）與 3.5.3（簡易版）
    • 新增的資料表寫在《資料字典》
    • 與需求文件衝突時，以需求文件為準

    為什麼叫 17.7 而不是迭代 18。 四件都是使用者看過護理端畫面之後當場提出的調整；迭代 18（規則引擎）的內容一項都沒動。 這一次多了一張資料表（第 4 件），但仍是只做加法、只服務「拖到平板」這一個動作，不是新的範圍。

    1. 改了什麼¶

    # 改什麼 檔案
    1 新增功能開關「護理師自己新增病人」（MANUAL_PATIENT_CREATE），預設關閉，功能開關頁上自成一組「院方資料以外的人工輸入」。開啟條件隨時成立（不涉及臨床判斷），切換照樣要登記理由、寫進稽核軌跡 packages/shared/src/platform.ts；開啟條件在 feature-flags.service.ts
    2 專業版補回新增病人：排班與指派「建立排班」的下一列——「院方資料裡沒有的病人」、病歷號、姓名、「新增病人」。建好之後自動選進上面那一列的病人選單，接著按「建立排班」即可。開關開著、而且有病人管理權限才出現；「病人」那一頁沒有加回來 apps/nurse-pwa/src/pages/ConsolePage.tsx
    3 簡易版病人框的「＋」改由同一個開關決定：開關開著（而且有病人管理權限）就有，不再看有沒有接院方 API；關著就沒有。拖到平板、填姓名與病歷號、建立並配這台平板，流程與迭代 14 相同 simple/Workbench.tsx、Trays.tsx、model.ts（World.manualPatient）
    4 系統管理的「平板停用」改名「平板管理」：分頁名稱與分頁裡那張卡的標題；畫面上其他提到它的字一起改（排班頁沒有可指派平板的提示、新增裝置頁底下的說明） SystemPage.tsx、SystemTabletsCard.tsx、ConsolePage.tsx、DevicesPage.tsx
    5 開發環境的床號改成醫院的寫法：seed 原本建 01～15，改成「區碼＋數字、沒有 4 號床」，取前 15 床——A1、A2、A3、A5、A6、A7、A8、A9、B1、B2、B3、B5、B6、B7、B8。簡易版沒接院方資料時點平板右上角選床，列的就是這些 packages/shared/src/beds.ts 的 DEFAULT_BED_NOS（只有 prisma/seed.ts 用）
    6 公告與院內衛教拖到平板＝只在那台平板播。原本放得上的只有「有床號的平板」，播放範圍是它那一床；改成有病人配著，或有床號就放得上，指定的是那台平板。已核准的內容拖上去：原本在全部床位播的變成只在這台播，原本指定了幾床、幾台的多加這一台（原本的床照留）；草稿卡拖上去：核准的同一個請求帶這台平板 simple/model.ts 的 tabletTakesContent、actions.tsx 的 pushContent、approveDraft
    7 新增資料表 carousel_item_device_targets（只做加法）：一則內容只在哪幾台平板播。核准（POST /carousel/items/:id/approve）與播放範圍（PUT /carousel/items/:id/targets）多收一個可不帶的 deviceIds；回應多一欄 targetDevices（識別碼與序號）。指定的平板不存在就擋下 schema.prisma、遷移 20261007180000_iteration17_7_device_targets、carousel.service.ts、兩支 DTO
    8 病人平板的跑馬燈帶著自己去查：兩張表都沒有列＝全部床位；有列時，床號對得上或平板對得上就播——平板沒有床號照樣收得到拖給它的內容 carousel-item.repository.ts 的 listPlayable；patient-home.service.ts
    9 播放範圍的寫法收成一支 describeCarouselScope（「A1、A2 床、平板 TB-03」）：簡易版內容卡、專業版公告與院內衛教頁、稽核紀錄同一種講法；平板格角落改成「只在這台平板播的內容 N 則」（含指定這台平板的，加上指定它那一床的） packages/shared/src/carousel.ts；Trays.tsx、CarouselPage.tsx、TabletCell.tsx

    2. 開發端的判斷¶

    判斷 理由
    「預設關閉」用功能開關，不用導覽版位 簡易版沒有導覽版位，兩個版本要同一個開關才說得清楚「開了就兩邊都有、關了就兩邊都沒有」。導覽版位只管得到專業版
    專業版的新增病人放在排班與指派，不把「病人」那一頁加回來 17.6 拿掉的病人頁只剩新增這件事；要新增病人的時候就是要排班、指派平板的時候，放在建立排班的下一列，建好直接選進病人選單。把 PATIENTS 識別碼加回來，舊環境資料表裡那一列版位會照它當年的設定冒出來
    簡易版的「＋」不再看有沒有接院方 API，只看開關 開關就是院方資料缺人時的備援；接了院方 API 還要開它，正是因為院方資料裡沒有這個人。17.6 以前「沒接院方 API 就有」的規則，在預設關閉之後等於開發機上也沒有「＋」，要用就開開關
    新增病人的端點不跟著開關擋（實作規格書 3.7「關閉時後端端點一併擋下」的例外） 十幾支驗收腳本與 seed 都用 POST /patients 建合成病人；開關要管的是護理師在畫面上會不會誤用。端點本來就要病人管理權限，誰建的、什麼時候建的照樣寫進稽核軌跡。例外寫在 3.7 與開關定義的註解裡
    人工新增的病人之後出現在院方資料裡，以院方資料為準 院方資料同步本來就以病歷號對應，有就更新（迭代 15）。所以開關的說明寫「院方資料缺人時才開」，畫面上那一列也這樣提醒
    床號只取醫院 41 床的前 15 床 開發機原本就是 15 床、15 台平板（SRS 第 9 章）；手選床位的面板要放得下。寫法照醫院：區碼在前、數字在後、沒有 4 號床（《同院 IDH 系統參考調查》6.1）
    只改 seed，不動已經建好的資料庫 已經在用的開發資料庫裡 01～15 有平板放著、有舊紀錄寫著；啟動時自動換床號等於系統自己改資料。要看新的床號就重建開發資料庫，或到系統管理的床位清單換。正式環境本來就沒有預設床位（1005 起由院方資料帶入）
    衛教拖到平板，指定的是平板，不是它那一床 使用者說「之前是拖到床位，現在改拖到平板」。平板沒有床號時沒有床可以指定；有床號時指定平板也比指定床貼近畫面上做的事。病人換床時平板跟著病人走，內容也就跟著走
    有床號、還沒配病人的平板照舊放得上 17.6 以前就可以（播放範圍是床），使用者只要求多放寬「有病人配著」這一種。沒有病人也沒有床號的平板放不上：放上去也沒有人看
    接了院方資料、沒配病人的平板不算有床號 沿用迭代 17.1 的判斷：那個床號是上一位病人的，標出來反而讓人以為它還在那一床（tabletBed）
    平板另開一張表，不改 carousel_item_targets 把 bed_no 改成可為空要重建表，違反「一次更新只做加法」（《資料庫使用規範》18.2）。兩張表並存，查詢條件寫在一處
    專業版沒有「指定平板」的操作 使用者這次說的是簡易版的拖曳。專業版公告與院內衛教頁照舊只顯示播放範圍，寫得出指定了哪幾台平板

    3. 驗收¶

    腳本 結果（1007）
    verify:iteration17-7（新增，5 步，不需後端）：開關定義與預設、兩個版本都看同一個開關、專業版新增病人那一列、平板管理改名、開發床號的格式（實際讀建置後的共用套件）、tabletTakesContent 拿假資料跑五種情形、指定平板的端點與查詢條件、遷移只做加法 全部通過
    verify:iteration3:api、4:api、9:api、14:api、17:api（要後端，開發機） 全部通過（開關數量照共用清單算、播放範圍只帶床號的舊請求照樣可用）
    verify:iteration14、14-2、15、17、17-1、17-6 依實作規格書 1.1 第九次改寫後全綠（createPatient 回到兩端都用、新增病人看開關、草稿與內容放得上有病人配著的平板、分頁改名）
    verify:iteration8、11、12、14-1、14-3、14-4、14-5、16、17-2、17-4、17-5、check:ui、check:ui:design、check:egress、check:migration 全綠，未改

    verify:iteration13（不需後端那一支）有一項不通過：它掃到 apps/api/scripts/verify-iteration13.ts 裡的「Ollama」字樣。這是改動之前就有的情形，與本次無關，沒有處理。

    在瀏覽器與後端實際看過（npm run demo:patient，無頭 Chrome 1366×768）：

    • 開關關著：專業版排班與指派沒有新增病人那一列，簡易版病人框沒有「＋」。開關開著：兩邊都出現（展示環境接了模擬院方資料，「＋」照樣有）；在專業版新增「人工新增測試」之後，病人選單自動選好他
    • 把 DEMO-01（配著模擬戊）從床位拿下來，格子上不再有床號；簡易版點「每天量體重」再點 DEMO-01，復原列寫「「每天量體重」→ 平板 DEMO-01」，格子角落「只在這台平板播的內容 2 則」
    • 以端點直接檢查：草稿核准帶 DEMO-01 → 回應的播放範圍是「床（無）、平板 DEMO-01」；DEMO-01 沒有床號，病人端跑馬燈有這一則；另一則改成只給 DEMO-02 之後 DEMO-01 看不到它；指定不存在的平板回 400「指定的平板不存在」；稽核紀錄寫「平板 DEMO-01」「全部床位 → 平板 DEMO-02」
    • 系統管理分頁叫「平板管理」，卡片標題相同；功能開關頁最下面一組「院方資料以外的人工輸入」

    沒有驗的：簡易版手選床位面板在新的 seed 床號下的樣子——展示環境接了模擬院方資料，床號由院方資料帶入、沒有手選面板；開發機的資料庫是改動之前建的，仍是 01～15。改動只在 seed 的那一份清單，由 verify:iteration17-7 第 3 步驗。
