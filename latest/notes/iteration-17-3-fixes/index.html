    迭代 17.3：所有 AI 生成內容禁用簡體字與中國大陸用語¶

    版本：v0.1　文件狀態：已完成（2026-10-07 開立）　適用讀者：FDE 工程團隊

    0. 本文件的定位¶

    本文件不是需求文件，是一份修正紀錄：2026-10-07 使用者指示歸在迭代 17.3 處理一件事——

    系統中所有 AI 生成的內容，禁用中國大陸用語與簡體字。

    本文件記錄做法、使用者決定的事、開發端做的判斷，以及影響到哪些既有規則。

    同日追加調整（1007，仍算 17.3）：使用者把「連續不合格就整次失敗」改成最後一次仍不合格也照樣交出， 並要求任何時候都不能讓前端出現這道把關的痕跡或訊息。下文已改成調整後的樣子，調整的經過見第 1 節第 5、6 題。

    • 功能需求來源仍是《軟體需求規格書》；本次在 FR-S06 補一段「AI 生成內容的用語」（SRS 自己的版本歷程定版日補）
    • 範圍與技術選型仍以《實作規格書》為準（3.4 加第 11 條硬性規則，4.15.3 節是本文件的摘要）
    • 與需求文件衝突時，以需求文件為準

    為什麼叫 17.3 而不是迭代 18。 只在既有的 AI 閘道加一道把關，沒有新的畫面、沒有新的端點、資料表一欄都沒動；迭代 18（規則引擎）的內容一項都沒動。

    這件事與開發端寫文件的規矩是同一套。 開發端交付的文件、註解、commit message 早就禁用支語與簡體字，由寫入前的 hook 把關（見維護指南）； 這次是把同一條規矩延伸到系統自己產生的內容——病人平板上的衛教、跑馬燈、離院衛教重點，護理師看到的護理記錄初稿與 SOP 查詢回答。

    1. 使用者的決定（1007）¶

    開工前問了四件事，使用者當場決定；第 5、6 題是同日追加調整時的決定：

    # 問題 決定
    1 查到時怎麼處理 照 Claude Code 的方式：擋下、告訴模型哪個詞要改成什麼、請它重寫（使用者問「有辦法像 Claude Code 一樣嗎？會不會變很慢？」，答覆見下方）
    2 詞庫用哪一份 另做一份醫療用的：從開發端的詞庫出發，拿掉醫療語境裡正常的詞，補上醫療與飲食的支語
    3 首頁「其他文件」那一塊 保留標題、只剩一行連結（這一項是文件整理，見週報；本文件不展開）
    4 台灣不這樣寫的繁體字形（OpenCC 繁體標準裡「為」「裡」「眾」的另一種寫法）要不要一起擋 一起擋
    5 （同日追加）重寫到最後一次仍不合格時 照樣交出，不算失敗；不再有「用語不合格而失敗」這種結果
    6 （同日追加）前端不能出現這道把關的痕跡，退回的那幾次要不要記 資料庫照記每一次（稽核完整），回給前端之前濾掉。開發端原本只想寫後端日誌、不寫呼叫紀錄與稽核，但那會少記稽核、違反實作規格書 3.4 第 5 條，提出三個方案請使用者選

    會不會變很慢（使用者第 1 題的追問，當場的答覆）：

    • 沒違規的輸出不會變慢：只是比對一次字表，不到 1 毫秒
    • 有違規的那一次多生成一輪（本機模型約多幾秒）。即時的 SOP 查詢最多只重寫一次，免得超過 10 秒的回應要求
    • 系統提示裡一開始就寫明「只用台灣的繁體中文與說法」，第一次就合格的機會比較大

    2. 做法一覽¶

    # 做了什麼 在哪裡
    1 三份字表：支語詞庫（人工維護，160 組）、只在簡體中文出現的字（3795 字）、台灣不這樣寫的繁體字形（41 字）。後兩份由 OpenCC 的字表產生 packages/shared/zh-tw/ 底下三個 txt；scripts/zh-tw-data.mjs 產生 packages/shared/src/zh-tw-data.ts（npm run zh-tw:data）
    2 檢查函式：找出一段文字裡的簡體字、中國大陸用語、台灣不這樣寫的字形，各給台灣的寫法 packages/shared/src/zh-tw.ts 的 findZhTwIssues
    3 AI 閘道的把關：每一次呼叫的系統提示最後附上規則；輸出查到問題就退回重寫，最後一次仍不合格也照樣交出 apps/api/src/modules/ai/ai-gateway.service.ts
    4 前端不留痕跡：退回的那幾次照記呼叫紀錄與稽核，但呼叫紀錄清單與稽核查詢不列；回給前端的提示截掉重寫附註 apps/api/src/common/zh-tw-retry.ts，兩個 repository 的 query、platform-mappers.ts
    5 驗收腳本 npm run verify:iteration17-3（新增，7 步，不需後端）

    3. 逐項說明¶

    3.1 為什麼放在 AI 閘道¶

    系統裡呼叫語言模型的只有 AI 閘道一處（實作規格書 3.4 第 1 條，verify:iteration17-3 步驟 7 會掃一次確認）。 衛教內容、離院衛教重點、護理記錄初稿、SOP 查詢回答、跑馬燈的衛教與公告草稿、連線測試，六種用途全部經過它。 一處把關就涵蓋全部，以後新增的 AI 功能也自動涵蓋，不必每個功能各寫一次。

    3.2 閘道的流程¶

    呼叫端的系統提示 ＋「輸出中文時，一律使用台灣的繁體中文與台灣的說法，不得使用簡體字或中國大陸用語。」

     送給模型
        ↓
  輸出查一次字表 ──── 沒問題 ──→ 成功，交出（與以前完全相同）
        │
     有問題
        ↓
  已是最後一次？── 是 ──→ 照樣交出，記成成功（後端日誌留一行警告）
        │
        否
        ↓
  記一筆失敗的呼叫紀錄（留輸出原文、錯誤訊息寫哪個詞改成什麼）與一筆失敗的稽核
        ↓
  原提示 ＋「上一次的輸出用了…：「甲」→「乙」…。請改用台灣的繁體中文與台灣的說法重寫，其餘要求不變。」→ 再送一次
    背景生成（衛教、離院衛教、護理記錄、跑馬燈） SOP 查詢（即時）
    最多送幾次（含第一次） 3 2
    最後一次仍不合格時 照樣交出，與第一次就合格的一樣進「待核准」或成為初稿 照樣回答
    • 每一次送出都各記一筆呼叫紀錄與稽核（實作規格書 3.4 第 5 條不變）：退回的那幾次記成失敗、留下模型寫的原文，錯誤訊息開頭固定是「輸出含簡體字或中國大陸用語」
    • 前端看不到這道把關（使用者 1007 追加的要求）：
    • 系統管理的「AI 呼叫紀錄」與「稽核軌跡」不列退回的那幾筆——查詢時濾掉，資料庫裡都在（HIDE_ZH_TW_REJECTED_INVOCATIONS、HIDE_ZH_TW_REJECTED_AUDITS）
    • 交出那一筆的提示若是重寫過的，資料庫記實際送出的那一份；回給前端時截掉重寫附註（withoutZhTwRetryNote），連線測試的結果也一樣
    • 交出那一筆的稽核說明與沒重寫過的完全相同，看不出送了幾次
    • 沒有用語相關的錯誤訊息、沒有 422，畫面上也沒有任何用語相關的文字（verify:iteration17-3 步驟 7 掃兩端原始檔）
    • 要查退回的情形只能直接看資料庫（分冊 aa90、aa93）
    • 跑馬燈超過字數的重新生成另外算（迭代 17 的 generateWithinLimits）：閘道一律交出內容，所以一份草稿超過字數時每一輪都可能再各重寫用語，最壞情況共送 9 次。背景工作不急，模擬模型也不會違規，沒有另外設上限
    • 衛教內容可能要英語、越南語、印尼語（FR-P04）：規則寫的是「輸出中文時」，字表也只認得中文，其他語言不受影響

    3.3 三份字表¶

    支語詞庫（packages/shared/zh-tw/words.txt，格式與開發端的 hook 詞庫相同：一行一組，支語<TAB>建議用語，# 開頭為註解）：

    • 出發點是開發端寫文件用的詞庫（使用者電腦上的 hook，不在 repo 裡），複製一份進 repo，從此兩份各自維護
    • 37 個詞標「放行」（註解掉，留著看得出放行了什麼）：
    • 在醫療、公文與日常語境裡是台灣正常用法的：描述檢查結果、列出檢查內容、法律上的撤回、對外的聯絡人、診斷編碼這類詞——開發端的詞庫是照資訊科技的語境收的，原封不動拿來用，衛教與護理記錄的正常句子會被擋
    • 會在兩個詞相連時跨詞誤抓的：例如「自動化」後面接「驗收」，中間會湊出一個詞庫裡的詞
    • 檔尾補 43 組：醫療（24 組，例如透析、瘻管、衛教、回診的大陸說法）與飲食生活（19 組，例如馬鈴薯、番茄、優格、鳳梨的大陸說法——透析病人的鉀、磷衛教一定會寫到食物）
    • 詞庫本身必然寫滿支語，開發端寫文件用的 hook 會擋下這種內容；這份是從 hook 詞庫複製、再以行號註解與追加產生的，不是手打

    只在簡體中文出現的字（simplified.txt，3795 字）：由 OpenCC 的簡轉繁字表產生。條件是「簡轉繁字表的鍵，而且它自己不是任何一個繁體字」—— 兩岸共用的字（例如「后」「里」「台」「干」「面」「只」）不算。OpenCC 的繁體標準與台灣不同：台灣的「峰」「床」「群」它用另一種字形寫，簡轉繁字表因此把台灣的這三個字當成簡體； 產生時另把台灣異體字表的值也算進繁體，這三個字才不會被誤擋（1007 實際踩到，見第 4 節）。

    台灣不這樣寫的繁體字形（variants.txt，41 字）：OpenCC 的台灣異體字表，剔除六個台灣其實也通行的字形（VARIANT_KEEP），補上十個本地模型輸出繁體時常帶出來的字形（VARIANT_EXTRA）。

    改詞庫：改 words.txt → npm run zh-tw:data → commit 兩個檔案。verify:iteration17-3 步驟 1 會比對 zh-tw-data.ts 與 txt 是否一致，忘了重新產生會被抓到。 要更新 OpenCC 的字表：把 OpenCC repo data/dictionary/ 底下的 STCharacters.txt、TSCharacters.txt、TWVariants.txt 放到一個目錄，跑 npm run zh-tw:data -- --opencc <目錄>。 只在開發機上做：產生出來的資料檔隨 repo 帶進院內，院內不需要 OpenCC，也不連外。

    誤擋的驗證：verify:iteration17-3 步驟 3 拿既有的 181 份文件與程式（docs/ 全部、衛教題庫、兩端的介面文案、共用常數）跑一次，一處都不能查到； 隨版本帶入的 14 則跑馬燈衛教草稿也查不到。以後放行或補詞，這一步就是回歸。

    3.4 隨版本帶入的跑馬燈草稿¶

    院內推論端點就位之前（Q-07），衛教草稿是開發端事先生成、隨版本帶進去的（迭代 17）。它們生成時就經過閘道（npm run marquee:bundle 走正式功能那一條路）， 所以本來就會被把關。匯入時不另查用語：最初的版本匯入時再查一次、查到的不匯入並寫進稽核，但那會讓稽核軌跡出現「因用語未匯入」， 1007 追加調整時拿掉了。現有的 14 則全部合格（verify:iteration17-3 步驟 3 照樣查）。

    3.5 沒有做的事¶

    • 不自動替換：一個簡體字可能對到兩個繁體字（頭髮的「髮」與發生的「發」在簡體是同一個字），一個大陸用語在台灣也可能有兩種說法，機械替換會換錯；交給模型依上下文重寫
    • 護理師自己寫的、改的字不查：使用者說的是「AI 生成的內容」。護理師修改後核准的跑馬燈、手寫的護理記錄不經過閘道，不在這次範圍
    • 病人端與護理端的畫面沒有任何改動：用語不合格不會造成失敗，畫面上也沒有任何地方提到這道把關

    4. 開發端在實作時做的判斷¶

    使用者要推翻時改右欄那一處即可。

    判斷 理由 寫在哪
    背景生成最多送 3 次、SOP 查詢最多 2 次 背景工作不急，多給一次機會；SOP 查詢有 10 秒的回應要求（SRS 第 6 章） ai-gateway.service.ts 的 ZH_TW_DEFAULT_MAX_ATTEMPTS、ZH_TW_MAX_ATTEMPTS
    退回的那幾次記成「失敗」，不另開一種結果 呼叫紀錄的結果欄沿用成功、失敗、擋下三種，資料表不動；錯誤訊息開頭固定寫「輸出含簡體字或中國大陸用語」，查得出來，也是前端濾掉時認的記號 同上；common/zh-tw-retry.ts 的 ZH_TW_REJECTED_MESSAGE
    濾掉的條件只認「AI 模型呼叫、失敗、說明含那句話」（稽核）與「失敗、錯誤訊息以那句話開頭」（呼叫紀錄） 連線失敗、被擋下等其他失敗照常列出；錯誤訊息或說明為空的紀錄不會被誤濾（條件拆成 OR，SQL 的 NULL 不會讓整列消失） common/zh-tw-retry.ts
    濾在 repository 的 query，不在前端 前端收不到就不可能顯示；這兩支 query 只給系統管理的清單用 ai-invocation.repository.ts、audit-log.repository.ts
    最後一次仍不合格時，後端日誌留一行警告 那一筆在資料庫裡記成成功，日後要查「交出去的有沒有違規」可從日誌找，或拿 outputText 重跑 findZhTwIssues ai-gateway.service.ts
    稽核沿用「AI 模型呼叫」這個動作，不新增稽核動作 退回重寫是一次呼叫的結果，不是新的事件；稽核動作的種類數（109）不變 同上
    退回時留下模型寫的原文 要查「模型到底寫了什麼才被退回」只能看原文；與成功的輸出一樣留存 12 個月（實作規格書 3.4 第 5 條） 同上
    字表放在共用套件、用產生的 TS 檔，不在執行時讀 txt 共用套件也給前端用，前端讀不了檔案；解析延到第一次用到才做，用不到的畫面不必付成本 packages/shared/src/zh-tw.ts
    詞庫在 repo 裡另存一份，不直接讀開發端的 hook 詞庫 hook 詞庫在使用者的電腦上、不在 repo，院內主機拿不到；兩者的語境也不同（一份管文件，一份管病人衛教） packages/shared/zh-tw/words.txt
    簡體字表由 OpenCC 產生，不手寫 手寫的清單（hook 那份約 400 字）漏字是必然的；OpenCC 是兩岸轉換的事實標準，Apache-2.0 授權 scripts/zh-tw-data.mjs
    產生簡體字表時，把台灣異體字表的值也算進繁體 1007 第一次產生時，既有文件裡的「峰」「床」「群」被當成簡體（OpenCC 的繁體標準用另一種字形寫這三個字）；不排除的話，病人端每一個「床」字都會被擋 同上
    台灣異體字表裡剔除六個字形 這六個在台灣也通行（例如「污染」「排泄」的寫法）；擋了會誤傷正常的衛教用語 同上的 VARIANT_KEEP

    5. 驗收¶

    腳本 結果（1007）
    verify:iteration17-3（新增，7 步，不需後端；閘道用替身組起來，實際跑一次「不合格 → 重寫 → 合格」與「一直不合格 → 最後一次照樣交出」，並把前端的過濾條件套在替身的紀錄上，確認前端只看得到交出的那一筆） 全部通過（1007 追加調整後重跑）
    verify:iteration3、verify:iteration4、verify:iteration17:api（對著開發機的後端，模擬模型） 全部通過，未改
    check:all 六支 全綠

    沒有驗的：實驗室的真模型實際會不會寫出大陸用語、多常被退回——要接實驗室時看（分冊 aa92、aa93）。模擬模型寫的是固定範例，不會違規。
