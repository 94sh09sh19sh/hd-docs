## 1. 先懂三件事

三件事的白話說明在[《護理站登不進去與主機位址》](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-login/index.md)，這裡只留結論：

- 按下登入時，瀏覽器先問後端「收不收這個網頁的來源」；後端收的來源寫在 `.env` 的 `CORS_ORIGINS`（這一冊叫它「**放行名單**」）。名單上沒有，瀏覽器自己擋下來，畫面就是 `Failed to fetch`——**帳號密碼根本還沒被看過**
- 「來源」是網址列最前面的 `http://` ＋ 主機 ＋ 埠，**一個字一個字比**：`localhost`、IP、多了 DNS 尾碼、埠不同、`https`，都算另一個來源
- `.env` 改了不會自己生效：`CORS_ORIGINS` 改了要 `up -d`；`HD_PUBLIC_API_URL`（網頁要去連的後端位址）在建置時寫死進網頁，改了要 `build` 再 `up -d`

## 3. 直接原因：放行名單裡沒有護理端

### 3.1 現場那三條指令說了什麼

| 指令在問什麼                                                     | 結果                | 白話                           |
| ---------------------------------------------------------------- | ------------------- | ------------------------------ |
| 第一條：`.env` 裡的 `CORS_ORIGINS`、`HD_PUBLIC_API_URL` 寫了什麼 | **沒有帶回來**      | 不知道                         |
| 第二條：用 `<主機>:13000` 連後端的 health                        | `{"status":"ok",…}` | 後端活著，用這個位址找得到它 ✓ |
| 第三條：假裝自己是 `http://<主機>:18080` 來的網頁，問後端收不收  | **什麼都沒印出來**  | **後端不收** ✗                 |

第三條如果後端收，會印出一行 `Access-Control-Allow-Origin: http://<主機>:18080`（意思是「我收這個來源」）。**沒印出來就是不收。** 光這一條就足以讓登入出現 `Failed to fetch`。

### 3.2 為什麼不收：兩種可能

> **1029 判斷結果（E-13）：兩種都不是。** 第三次進院照 E-06 先抄了三樣：`.env` 的 `CORS_ORIGINS`、日誌最後一行（10/01 17:11 那一次啟動）都是 `http://<主機>:18080`，網頁裡的後端位址也與 `.env` 一致——落在下面方框那張表的第三列「名單沒問題」。1001 登不進去，剩下的原因是 3.3 節第一個坑（網址列用 `localhost` 開）或護理站查不到 `<主機>` 這個名稱；1029 改成 IP 後護理站直接登得進去，兩者已無法再分辨。詳見[《第三次進院紀錄（1029，部分成功）》](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/record-3-1029/index.md) O-01。

|              | 可能 A：名單寫錯                                                                                                      | 可能 B：名單是對的，但後端還在用舊的                              |
| ------------ | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 怎麼回事     | `CORS_ORIGINS` 寫的不是 `http://<主機>:18080`。例如照抄了範例的 `hd-server`、寫成 `localhost`、名稱和 IP 混用、埠寫錯 | 改過 `.env`，但改完沒有 `up -d`，執行中的後端拿的還是改之前的名單 |
| 指向它的線索 | 17:47 問過「`hd-server` 要照寫嗎」                                                                                    | `<主機>` 是現場邊問邊決定的，中途改過值並不意外                   |
| 怎麼修       | 改對 `.env`，然後 `up -d`                                                                                             | 直接 `up -d`                                                      |

**兩種的修法最後都是「改對 → `up -d` → 再打一次第三條，直到它印出 `Access-Control-Allow-Origin`」**，所以下一次就算還是分不出來，也修得好。但分得出來，才知道手冊哪裡要再改，所以下一次動手之前先抄下三樣東西（E-06）。

💡 **一個當時 V-17 還沒收進去的查法**（E-15；1029 收進第三次進院 J-07 第 2 條）：後端每次啟動，日誌裡都會印一行「**允許的前端來源：…**」，那就是**執行中的後端手上那份名單**（程式在 `apps/api/src/main.ts`）。拿它和 `.env` 的 `CORS_ORIGINS` 比一下：

```
Select-String -Path $cfg -Pattern '^CORS_ORIGINS='
[Console]::OutputEncoding = [Text.Encoding]::UTF8; docker compose --env-file $cfg logs api | Select-String '允許的前端來源'
```

| 兩行比起來                               | 是哪一種                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------- |
| 兩邊一樣，但都不是 `http://<主機>:18080` | 可能 A：名單寫錯                                                          |
| `.env` 是對的，日誌裡最後一行還是別的值  | 可能 B：改完沒 `up -d`                                                    |
| 兩邊一樣，而且都是 `http://<主機>:18080` | 名單沒問題，問題在網址列或網頁裡的後端位址（3.3 節）——**1029 就是這一列** |

日誌裡若有好幾行，看**最後一行**（最近一次啟動）。逗號分開的多個來源，日誌裡會用頓號「、」隔開。

## 6. 一張紙帶進去

當時給進院的人準備的；只能帶一張紙的話，帶這張：

1. **`<主機>` 只有一種寫法**，名稱或 IP 擇一，資訊室確認過的那一個。
1. **瀏覽器一律開 `http://<主機>:18080`**，不用 `localhost`。
1. **改了 `CORS_ORIGINS` → `up -d`；改了 `HD_PUBLIC_API_URL` → `build` 再 `up -d`。** 只存檔等於沒改。
1. **`Failed to fetch` ＝ 帳號密碼還沒被看過**，先查名單和位址，不要先懷疑密碼。
1. **放行檢查要印出 `Access-Control-Allow-Origin`**，空的就是不收。
1. **改之前先抄**，抄原文、抄到最後一行。
1. **登入通了才往下。**
1. **院方 API 只用探測工具看**（E-16），不用瀏覽器或 `curl` 直接打——會把病人資料印在螢幕上。
