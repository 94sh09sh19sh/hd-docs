    摘要¶

    • 現況：1029 起院內主機用資訊室固定下來的 IP（<IP>），舊第十八冊 J-07～J-14 照子文件的 T-xx 換成，護理站 1029 15:34 登得進去；1116 換到 v0.5.0 後仍登得進去

    • 登入時網頁連的是建置時寫進去的 HD_PUBLIC_API_URL；後端只收 CORS_ORIGINS 列的來源，http://＋主機＋埠要和網址列一字不差
    • CORS_ORIGINS 改了要 up -d；HD_PUBLIC_API_URL 改了要先 build 再 up -d，只存檔等於沒改
    • 登不進去：看訊息 → 抄網址列 → 主機上五條指令，結果全部抄下來（第 2 節）；試了一小時不通就停手
    • 換位址＝.env 三個位址一起改 → build → up -d → shell-builder 重簽伺服器憑證 → keys-backup → restart patient-web，一步都不能少；改之前先從護理站與平板連一次新位址
    • 平板已經佈建了（1029 起 TB-00），換位址每一台都要重新佈建：不要換來換去（子文件第 4 節）

    1. 先懂三件事¶

    1.1 按下「登入」的那一刻發生了什麼¶

    護理端的網頁和後端是兩個不同的服務，各自用一個埠：

      護理站的瀏覽器
      │
      │ ① 開 http://<主機>:18080          → 護理端（nurse-web）把登入頁送過來
      │
      │ ② 按下登入，網頁去呼叫
      │    http://<主機>:13000/api/…       → 後端（api）檢查帳號密碼
      │
      │    瀏覽器先問後端：「我手上這頁是 http://<主機>:18080 來的，你收不收？」
      │      ├─ 後端回答「收」  → 送出帳號密碼 → 登入成功或「工作ID 或密碼錯誤」
      │      └─ 後端沒回答「收」→ 瀏覽器自己擋下來 → Failed to fetch

    重點在第 ② 步那個「先問」。這是瀏覽器的安全規定，不是我們的程式自己加的：一個網頁要去呼叫另一個埠上的服務，對方必須明白說「我收你」，瀏覽器才肯把結果交給網頁。 這套規定叫 CORS；後端願意收的網頁位址，寫在 .env 的 CORS_ORIGINS，這一份叫它「放行名單」。

    可以把後端想成大樓的管理員、CORS_ORIGINS 是他桌上的訪客名單：名單上沒有你，你連大門都進不去，根本輪不到檢查你的證件（帳號密碼）。所以 Failed to fetch 出現時，帳號密碼對不對還完全沒被看過。

    病人端與後端同一個來源（迭代 12 起病人端經自己的埠轉送呼叫後端），不必列進放行名單。

    1.2 「來源」要一字不差¶

    放行名單上寫的、瀏覽器拿去問的，都是網址列最前面那一段：http:// ＋ 主機 ＋ 埠，叫做「來源」。比對時是一個字一個字比，不會去想「這兩個其實是同一台機器」。

    假設 CORS_ORIGINS=http://<主機>:18080，<主機> 是一個名稱：

    瀏覽器網址列上的來源 是不是同一台機器 後端收不收
    http://<主機>:18080 是 收
    http://localhost:18080 是（在主機上開的話） 不收：localhost ≠ <主機>
    http://<主機的 IP>:18080 是 不收：IP ≠ 名稱
    http://<主機>.<DNS 尾碼>:18080 是 不收：多了尾碼就是另一串字
    http://<主機>:13000 是 不收：埠不同
    https://<主機>:18080 是 不收：https ≠ http

    所以 <主機> 只能有一種寫法：選定了名稱就全部用名稱，選定了 IP 就全部用 IP，包括你在瀏覽器裡打的網址。真的需要在主機上用 localhost 開的話，CORS_ORIGINS 可以用逗號列兩個來源：http://<主機>:18080,http://localhost:18080，改完 up -d 即可，不必再 build（院內 1029 起只留 <IP> 一個，子文件 T-06）。

    1.3 .env 改了不會自己生效¶

    .env 是一份文字檔，改了存檔，執行中的服務不會知道。兩項跟登入有關的設定，生效的時機還不一樣：

    .env 的哪一項 什麼時候被讀進去 改了之後要做什麼 比喻
    CORS_ORIGINS（放行名單） 後端的容器建立時讀一次 docker compose --env-file $cfg up -d（compose 會發現設定變了，重建後端） 管理員上班時領一份名單，換名單要請他重新報到
    HD_PUBLIC_API_URL（網頁要去連的後端位址） 建置（build）時寫死進護理端的網頁檔案 先 build、再 up -d。只 up -d 沒有用 印在傳單上的電話號碼，要改只能重印

    只存檔、不做右邊那一欄，等於沒改。 1001 的兩種可能原因裡，有一種就是這個（《第二次進院紀錄（1001）之一》）。退回舊版時也一樣：舊映像檔裡的網頁寫的是建置舊映像檔當時的位址（《本系統換版與退回》W-20）。

    2. 護理端頁面開得起來卻登不進去¶

    先認清：用哪個網址開¶

    開的網址 登得進去嗎
    http://<IP>:18080 可以。在主機上開也一樣，網頁連後端時會連回主機自己
    http://localhost:18080 登不進去：網址列是 localhost，名單上是 <IP>
    http://<名稱>:18080，或 <IP> 的另一種寫法 1029 換成 IP 之後登不進去：名單上只剩 <IP>

    🧪 開發機演練時「故意用 localhost 開」的練習，就是在看這張表的第二列。

    第 1 步：看登入鈕下面的訊息¶

    訊息 意思 接著
    工作ID 或密碼錯誤 有連到後端（名單沒問題），帳號或密碼不對 換帳號或請護理長重設。換版不會改密碼。第一個最高權限帳號（.env 的 SUPER_ADMIN_WORK_ID、SUPER_ADMIN_INITIAL_PASSWORD）只在資料庫還沒有任何使用者時建立，事後改 .env 不會改到已建立的帳號；都不對就停手，由開發端出重設的辦法，不在現場改資料庫
    Failed to fetch 瀏覽器沒拿到後端的回應：後端位址錯，或被放行名單擋掉 第 2 步
    頁面一直轉圈 — 按 F12 → Network，再按一次登入，抄下請求送去的網址與錯誤原文

    第 2 步：網址列¶

    把網址列上的網址原文抄下來。 不是 http://<IP>:18080（一字不差）就改用這個網址開，Ctrl＋F5（舊網頁可能還留在瀏覽器裡），再登入一次。1001 卡住時，這一項沒有查。

    第 3 步：在主機上查¶

    照順序打，結果全部抄進演練紀錄，包括正常的那幾條（1001 帶回了第三、四條，但第一條 CORS_ORIGINS 的內容沒帶回來，所以分不出是寫錯了還是改完沒 up -d）：

    Select-String -Path $cfg -Pattern '^(HD_PUBLIC_API_URL|CORS_ORIGINS)='
docker compose --env-file $cfg exec nurse-web grep -rhoE 'https?://[A-Za-z0-9.-]+:[0-9]+' apps/nurse-pwa/dist/assets
curl.exe -s http://<IP>:13000/api/health
curl.exe -s -i -H "Origin: http://<IP>:18080" http://<IP>:13000/api/health | Select-String Access-Control-Allow-Origin
[Console]::OutputEncoding = [Text.Encoding]::UTF8; docker compose --env-file $cfg logs api | Select-String '允許的前端來源' | Select-Object -Last 1
    結果 意思 處置
    第二條的位址與第一條的 HD_PUBLIC_API_URL 不一樣 網頁是在改 .env 之前建的 docker compose --env-file $cfg build、docker compose --env-file $cfg up -d，Ctrl＋F5 再登入
    第一條的 CORS_ORIGINS 不是第 2 步網址列上的來源 名單寫錯 改 .env，docker compose --env-file $cfg up -d
    第三條沒有 {"status":"ok",…} <IP>:13000 連不到後端 docker compose --env-file $cfg logs api --tail 30 看原因；用名稱時查不到，先 Resolve-DnsName <主機>
    第四條印出 Access-Control-Allow-Origin: http://<IP>:18080 後端有放行這個來源 問題不在名單：回第 2 步，或按 F12 → Network 再按一次登入，抄下請求送去的網址與錯誤原文
    第四條什麼都沒印，第五條不是 http://<IP>:18080 名單寫錯，或改完 .env 還沒 up -d：.env 只在容器建立時讀一次，執行中的後端還在用舊值 改 .env 的 CORS_ORIGINS，docker compose --env-file $cfg up -d，再打第四條
    第五條什麼都沒印 那一行開頭的 [Console]::OutputEncoding = [Text.Encoding]::UTF8; 漏打了：PowerShell 預設用 big5 讀 Docker 的輸出，中文對不上；或日誌被清過（容器重建過） 補上整行再打；日誌被清過就寫「沒有」
    • 輸出被截斷也算有印出來。 視窗太窄時，第四條那一行可能只看得到後半段（例如 …rol-Allow-Origin）。看得到 Allow-Origin 這幾個字就是有放行；要看完整的一行，把視窗拉寬，或在指令最後加 | Out-String -Width 300。反過來，真的什麼都沒印才是沒放行。1001 就是空的
    • 先確認 <IP> 換成了真的位址：照抄 <IP> 一定什麼都不印
    • 另一種看法：瀏覽器按 F12 → Network，再按一次登入，看請求送去哪個網址

    試了一小時仍然不通¶

    停手，不再改任何東西，把每一步的結果與錯誤原文抄回來。再看是哪一種情形：

    情形 做什麼
    剛換上新版才登不進去 照《本系統換版與退回》W-20 退回舊版（1029 之後的 v0.4.0、v0.5.0 都用 <IP> 登得進去），紀錄帶回
    剛換過位址（子文件 T-xx 做到一半），資訊室說舊名稱在院內 DNS 查得到、.env.before-ip 還在 照子文件第 3 節換回名稱（CORS_ORIGINS 改成 http://<名稱>:18080；1001 填錯的就是這一行）
    其他 保留現況；照《備份、還原與關服務》停用服務，紀錄帶回

    3. 要換主機位址¶

    名稱與 IP 互換、院內主機的 IP 要換、換一台主機，照《護理站登不進去與主機位址之一：換主機位址》（T-01～T-14）。1029 已照它從名稱換成 IP。換之前先讀它第 1 節：主機位址寫在十個地方，少換一處就有一個地方還在用舊位址；1029 起平板已佈建，換位址每一台都要重新佈建。
