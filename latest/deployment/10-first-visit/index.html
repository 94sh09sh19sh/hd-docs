    第十冊 · 第一次進院紀錄（0922，失敗）¶

    版本：v0.1　文件狀態：紀錄（0922 進院當天的現場資料整理而成）　編號：F-xx

    前九冊寫的是應該怎麼做，這一冊記的是0922 第一次進院實際發生了什麼。 結果是總覽第 2 節的 C 級：失敗——服務沒有在院內主機上跑起來。

    依第五冊的前提，C 級不是白跑一趟，前提是紀錄做滿。這一冊把當天帶回來的零散資訊 （現場筆記、第五冊情報蒐集表的回答、四張螢幕照片）整理成下一次進院能直接用的形狀： 做錯了什麼、主機長什麼樣、哪些題目還空著、現場留下了什麼要收拾、手冊要改哪裡。

    編號 F-xx 是這一冊的發現與待辦，寫進訊息或下一次的準備清單時用它指稱。

    公開範圍：文件站是公開的。主機名稱、帳號名稱、完整的連接埠清單與原始照片一律不寫進這一冊， 留在開發端本機的現場資料夾（不進 repo）。這一冊只寫判斷所需的結論。

    0. 先講結論¶

    0.1 一句話¶

    院方要求以容器部署，這正是第九冊的情境；但當天沒有照第九冊的方式做， 而是先手動開了一個通用的 Python 容器、在容器裡 git clone，再在容器「裡面」照第九冊從頭執行。 第九冊的每一條指令都是寫給主機上的 PowerShell 下的，在容器裡一條都不成立，之後就全部亂掉了。

    0.2 失敗原因，由重到輕¶

    # 原因 屬於 詳見
    F-01 在自己開的容器裡面照第九冊做，第九冊本身卻就是在教怎麼建出容器 現場操作 第 2 節
    F-02 -v /c:/app 把整顆 C 槽掛進了容器 現場操作，有資料與資安風險 第 2 節
    F-03 -p 3000:8000：主機的 3000 已經有人在用，容器裡的 8000 也沒有任何東西在聽 現場操作 第 2 節
    F-04 第九冊與 0921 的三處容器修正都不在 master 上，院方照預設 clone 到的是修正前的版本 進院前的準備（D-01） 第 2 節
    F-05 進院前的 D-02～D-04 沒有做到位：Docker 問題清單沒有事先寄出、沒有在乾淨機器上演練 進院前的準備 第 2 節
    F-06 院方的要求本身有兩種讀法（見 0.3），當場沒有釐清就動手 溝通 第 2 節

    即使 F-01～F-03 都沒有發生，照第九冊做也會在 D-14 或 D-18 倒下：F-04 讓院方拿到的是修正前的 Dockerfile（沒有 OpenSSL、/data 屬於 root、compose 只接受繫結掛載），第九冊 0.3 節那三個問題會原樣重演。 所以這一次的失敗有兩層，現場那一層很顯眼，準備那一層更根本。

    0.3 院方到底要求什麼（還沒釐清）¶

    現場筆記的原話是：「院方要求部署在 container 內，但似乎又允許鏡像到 docker 外。」這句話有兩種讀法，結果差很多：

    讀法 意思 對應
    甲 服務要跑在容器裡；連接埠、備份目錄這些對應到容器外是允許的 就是第九冊：程式在映像檔裡、資料在具名資料卷、備份掛主機目錄
    乙 資料（資料庫檔案）也可以直接放在 Windows 目錄，用繫結掛載給容器讀寫 違反 DEP-23。《部署規範》3.1 當初改掉容器，理由正是這種放法的 SQLite 檔案鎖不可靠

    下一次進院前要拿到書面答案（F-20）。若院方的意思是乙，那不是手冊能開的例外， 要回到《部署規範》3.3 談。

    兩條路線的逐項比較、以及不用容器也能與同機其他專案隔離的理由，整理在《部署路線比較》，詢問院方時帶著它去。

    1. 當天實際做了什麼¶

    1.1 經過¶

    1. 查主機資訊：主機名稱、作業系統、時區、磁碟、連接埠、node -v、docker version（第 3 節）。
    2. 直接下了這一行，建出一個容器：
    docker run -dit --name dialysis_system_v0 -v /c:/app -p 3000:8000 python
    1. 進到這個容器裡 git clone 本專案。
    2. 在容器裡按第九冊從頭（D-01 起）往下做，之後步驟一步步對不上，現場判斷為失敗。

    1.2 沒有留下來的紀錄¶

    以下是第五冊 3.6 節要求、這次沒有記到的東西。它們已經拿不回來了，列在這裡是為了下一次不要再漏：

    第五冊 應該記的 這次
    C-38 每一步的錯誤原文 沒有。只知道「後面亂成一團」，不知道是哪一條指令、哪一行錯誤
    C-39 每一步的實際耗時 沒有
    C-40 卡住的每一件事 只有整體印象，本冊第 2 節是事後推斷
    C-41 有沒有人提議「開一下網路」 沒有記。但主機當天是連得到院外的（見 F-07）
    C-42 現場任何人說的「這樣不行」「我們這裡都是…」 只有 0.3 那一句

    這一條本身就是教訓：錯誤原文沒抄，下一次連「上次卡在哪」都說不清楚。 總覽第 7 節第 3 條「錯誤訊息抄原文」在人慌的時候最容易被放掉。

    2. 為什麼會失敗¶

    F-01 在容器裡面照第九冊做¶

    發生了什麼：先 docker run 出一個 python 容器，再進去照第九冊做。

    為什麼不成立：第九冊的形狀是「主機上有 Docker → 在主機上 git clone → 在主機上 docker build 把原始碼建成映像檔 → docker compose up 由映像檔開出三個容器」。 容器是這一整串的產物，不是起點。在容器裡面做，每一步都少了它要的東西：

    第九冊的步驟 在 python 容器裡會怎樣
    D-07 docker version、docker compose version 容器裡沒有 docker 指令，也碰不到主機的 Docker
    D-09 Get-LocalGroupMember 容器裡沒有 PowerShell，那是 Linux
    D-11 New-Item、C:\hd 同上；路徑也不存在
    D-14 docker build 沒有 docker，建不出映像檔
    D-16 產生 JWT_SECRET、D-18 套用遷移 都要先有映像檔；python 映像檔裡也沒有本專案要的 Node.js 20
    D-19 docker compose up -d 同 D-14

    下一次怎麼做：不要自己先開任何容器。 在主機的 PowerShell 視窗裡，從 D-05 開始照第九冊做； 容器會在 D-19 由 docker compose up -d 自己出現，名字是 api、nurse-web、patient-web。

    F-02 整顆 C 槽被掛進容器¶

    發生了什麼：-v /c:/app 在 Docker Desktop 上的意思是「把主機的 C:\ 掛到容器的 /app」。 （這一點要在主機上用 F-10 的指令確認，見下。）

    為什麼嚴重：

    • 容器裡預設是 root。容器裡的任何指令，都能讀寫主機整顆 C 槽——包含同一台主機上另一個專案的檔案、 Windows 使用者資料夾、Docker 自己的虛擬磁碟所在的 AppData。這是 DEP-37 共用主機隔離的反面
    • 在容器裡對 /app 做的任何刪除，刪的是主機上的真檔案。 在容器裡下一句 rm -rf /app/*，就是清空 C 槽
    • 在 /app 底下 git clone，原始碼就落在主機 C 槽的根目錄底下，而且是在一個沒人預期的位置
    • 若之後把資料庫也放在 /app 底下，就是 0.3 讀法乙，違反 DEP-23

    下一次怎麼做：第九冊這條路線上，只有一個主機目錄會被掛進容器：備份目錄（HD_BACKUP_DIR，掛到 /backups）。 其餘一律不掛。這件事由 docker-compose.yml 決定，不要自己下 -v。

    F-03 連接埠對應兩頭都不對¶

    發生了什麼：-p 3000:8000 是「主機的 3000 → 容器的 8000」。

    為什麼不成立：

    端 問題
    主機的 3000 現場的連接埠清單裡，3000 已經有行程在聽，而且與 9000 是同兩個行程——很可能是同機另一個專案的 Docker 轉送，也可能是這個容器自己開的（要用 F-09 確認）。無論是哪一種，本系統都不能再用 3000
    容器的 8000 本系統的後端在容器裡聽的是 3000、護理端 8080、病人端 8081，沒有任何東西聽 8000

    下一次怎麼做：D-13 那三個埠要避開 3000 與 9000。 現場清單上 8080、8081 是空的；後端埠要另外挑一個空的、向資訊室登記，寫進 .env 的 HD_API_PORT， 也寫進 D-14 的 VITE_API_BASE_URL（兩處要一致，否則要重建映像檔）。

    F-04 要被 clone 的那一版根本不在 master 上¶

    發生了什麼（事後在開發端查到的）：

    分支 最新 commit 有沒有第九冊 有沒有 0921 三處容器修正
    origin/master（GitHub 預設分支） c4109fa（第八冊） 沒有 沒有
    origin/docker-route 70b5de5 有 有

    git clone 不指定分支時拿到的是 master。院方當天 clone 到的若是 master，拿到的就是 第九冊 0.3 節說「不修會在院內直接倒下」的那一版：沒有 OpenSSL、/data 屬於 root、compose 只接受繫結掛載。

    為什麼會這樣：第九冊 D-01 就是在防這件事—— 「本機與 origin/master 的 commit 一模一樣」。這一步在進院前沒有做到：修正推上了 docker-route 分支，沒有合回 master。

    當天實際 clone 到哪一版不知道：只記到 git remote -v（有 origin），沒有記 git log -1 --oneline。 這一版在容器裡、也在主機 C 槽上（F-02），F-10 可以查到。

    下一次怎麼做：進院前把 docker-route 合回 master 並推上去，然後才做 D-01 的比對； 交付單上寫 commit，現場 D-12 用 git log -1 逐字核對。

    F-05 進院前的 D-02～D-04 沒有到位¶

    第九冊 應該在進院前 這次
    D-02 在一台乾淨的 Windows 機器上把 D-11～D-23 完整走一次 沒有。開發機上的演練（0.3 節）與這台主機差很多：主機 3000 埠被佔、有 RAM 磁碟、Docker Desktop 從 Microsoft Store 更新
    D-03 兩週前把 9 題 Docker 問題清單寄給資訊室 沒有。第 2、3 題（Docker Desktop 授權、重新開機後有沒有人登入）到現在仍無答案
    D-04 準備一把唯讀、會過期的權杖 沒有。當天是臨時建了一把 classic 權杖，已於 0922 刪除，見 F-11

    第九冊寫的是「院方要求容器的話翻這一冊」，但院方的要求是當天才知道的，準備工作排不進去。 這條教訓要寫回總覽：院方有可能臨時改要求，進院前就要把第九冊的準備做完，不管用不用得到。

    F-06 院方的要求沒有當場釐清¶

    0.3 那一句話有兩種讀法，現場沒有問清楚就動手。第九冊 D-05、 D-06 本來就是要在動手前把這件事講清楚、簽下來的一步；這次跳過了。

    F-07 主機當天連得到院外¶

    這不是失敗原因，但是這一趟最重要的發現之一：當天 docker run ... python 能把 python 映像檔從 Docker Hub 拉下來、 容器裡 git clone 能從 GitHub 拿到私有 repo，表示這台主機當時有對外連線。

    • 這與部署規範「零院外連線」的前提不一致，要問清楚：是一直都開著，還是當天為了部署臨時開的？誰開的、誰會關？ （第九冊 D-03 第 7 題、D-24）
    • 第四冊 H-08 預期路線 A「每一步都失敗」，這台主機上不成立
    • 在這個問題有書面答案之前，不得輸入任何真實病人資料（與第九冊 D-24 同一條）

    3. 主機實況（現場帶回來的）¶

    對照第四冊 H-06、H-07 與第九冊 D-07～D-09。

    3.1 系統¶

    看什麼 現場看到的 判斷
    作業系統 Windows 11，組建 26200，x64 ✓
    時區 (UTC+08:00) 台北，不實施日光節約時間 ✓ DEP-15
    全域 Node.js 沒有（node -v 無法辨識） ✓ 兩條路線都不需要它
    記憶體 沒有記到 下次補（systeminfo）
    同機其他專案 有另一個專案在用 Docker 第九冊 D-03 第 5 題、D-08 第 4 項「不要動」、D-09 都因此成立

    5. 帶回來之後才看清楚的幾件事¶

    F-08 電源不穩，而且無人看管¶

    這是比這次部署失敗更大的問題，它決定這台主機能不能跑照護系統，不論走哪一條路線：

    • 主機稍微被碰到就會斷電，要有人手動開機；主機放在護理站（C-27），被碰到的機會不低
    • 無人看管，重新開機之後誰去確認服務有起來，答案是沒有人（C-35）
    • Docker Desktop 要有人登入 Windows 才會啟動（3.3）。斷電 → 有人按開機 → 還要有人登入 → Docker 才起來 → 容器才回來。這條鏈上任何一環沒人做，服務就停著，而且沒人知道
    • SQLite 已經以 WAL 加 synchronous FULL 設定，對突然斷電的承受度是它能做到的上限；但反覆硬斷電仍然是資料庫最不想遇到的事，備份又只在同一台主機上（C-14）

    第九冊 D-26 寫過： 「沒人登入就不會起來，而院方也不會安排人登入——這條路線就不適合 24 小時運作的照護系統。」 這台主機現在就是這個情形。要由院方決定，手冊不替院方決定：

    可以問院方的方向 解決哪一段
    加一台不斷電系統（UPS），主機移到不會被碰到的位置 斷電本身
    主機的 BIOS 設成「恢復供電後自動開機」 斷電後沒人按開機
    改用 WSL2 裡的 Docker Engine 由開機排程工作啟動，或回到安裝包路線（排程工作不需要有人登入） 開機後沒人登入
    指定一個人負責「每班確認一次服務有在跑」 C-35

    F-09 3000 埠是誰的¶

    要在主機上查清楚：

    Get-NetTCPConnection -State Listen -LocalPort 3000, 9000 | Select-Object LocalPort, OwningProcess
Get-Process -Id <上一行的 OwningProcess> | Select-Object Id, ProcessName, Path
docker ps --format "{{.Names}}  {{.Ports}}"
    • 若行程是 com.docker.backend 或 wslrelay，那是 Docker 在轉送某個容器的埠；第三行會告訴你是哪個容器
    • 若那個容器是 dialysis_system_v0，就是 F-03 自己佔的，F-10 收掉之後就會空出來——但本系統仍不要用 3000，同機另一個專案的 9000 旁邊還是容易撞
    • 若是另一個專案的容器，登記下來，那就是 DEP-37 第 2 項要的登記

    F-10 那個容器與它掛進去的東西¶

    dialysis_system_v0 很可能還在主機上（-d 讓它在背景跑；主機斷電後它不會自己回來，但容器本身仍在）。 它掛著整顆 C 槽，裡面有一份 clone 下來的原始碼，也可能留著當天那把權杖的字串（已作廢，F-11）。下一次進院第一件事就是收掉它，而且順序不能錯：

    ① 先看，不要動

    docker ps -a --filter name=dialysis_system_v0
docker inspect dialysis_system_v0 --format "{{json .Mounts}}"
docker inspect dialysis_system_v0 --format "{{.HostConfig.RestartPolicy.Name}}"

    第二行會印出掛載的來源（Source）與目的地（/app）——這是 F-02「整顆 C 槽」的證據，抄下來。

    ② 查 clone 下來的那一份在哪、是哪一版

    docker start dialysis_system_v0
docker exec dialysis_system_v0 sh -c "ls /app; find /app -maxdepth 3 -name .git -type d 2>/dev/null"
docker exec dialysis_system_v0 sh -c "cd <上一行找到的目錄的上一層> && git log -1 --oneline && git remote -v && git config --list --show-origin | grep -i credential"

    git log -1 就是 F-04 那個「當天實際 clone 到哪一版」的答案。git remote -v 的網址或 Git 設定裡若看得到權杖，那是 0922 那把已刪除的權杖，照 F-11 把殘留清掉即可。

    ⚠️ 在這個容器裡絕對不要對 /app 下任何刪除、移動、改權限的指令。 /app 就是主機的 C 槽，rm -rf 下去刪的是主機上的真檔案，包含另一個專案的東西。

    ③ 收掉容器

    docker stop dialysis_system_v0
docker rm dialysis_system_v0
docker ps -a --filter name=dialysis_system_v0

    最後一行什麼都沒印才算完成。docker rm 只刪容器，不會刪到主機 C 槽上的檔案——這是對的。

    ④ 收掉主機 C 槽上那一份 clone

    ②找到的目錄，在主機上是 C:\ 底下同名的資料夾。確認路徑無誤、確認資訊室同意之後，用檔案總管刪除 （不要在容器裡刪）。這條路線要的原始碼目錄是 C:\hd\hd-tablet-care\，那是下一次在主機上重新 clone 的（D-11）。

    ⑤ python 映像檔

    docker image ls python

    它是當天為了 F-01 拉下來的，本系統用不到。要不要刪問過資訊室：同機另一個專案有可能也在用同一個映像檔。

    F-11 clone 用的憑證¶

    本專案的 repo 是私有的，容器裡的 git clone 用的是部署當天臨時建立的一把 GitHub 權杖（classic）， 不是 D-04 要求事先準備的那種唯讀、只限這個 repo、會過期的權杖。

    看什麼 現況
    權杖類型 classic。classic 權杖無法限定單一 repo，權限範圍依建立時勾選的 scope，通常比 D-04 要求的寬
    處理 已於 2026-09-22 在 GitHub 上刪除，這把權杖從此不能再用
    主機上的殘留 字串可能還留在容器裡的 Git 設定、git remote -v 的網址或 shell 歷史中。已經失效，不再是外洩風險，但下一次進院照 F-10 ②～④ 收掉容器與 clone 時一併清除

    下一次不要再臨時開 classic 權杖。 照 D-04 事先建 fine-grained 權杖：只勾這個 repo、Contents 唯讀、進院隔天過期； 院方若要自己 clone，請院方用他們自己的帳號取得存取權。

    F-12 帳號與權限¶

    • docker-users 群組裡只有一個本機帳號，而那也是平常登入這台主機的帳號
    • 那個帳號就是最高權限（C-10、C-11）
    • 帳號的其他現況不寫在公開文件，留在院外筆記，下一次當面交給資訊室

    合起來的意思是：能坐到這台主機前面的人，就能讀到資料卷裡的全部照護資料，不需要知道任何本系統的密碼。 這正是第九冊 D-09 說「最容易被忽略的一條」。這一條不在我們能決定的範圍，要當面告訴資訊室這代表什麼、 請院方決定，並寫進交接文件。在院方給出答案之前，這台主機不得輸入真實病人資料。
