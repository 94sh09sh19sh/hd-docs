    《第一次進院（0922）· 部署本系統》與它的兩份子文件寫的是應該怎麼做，這一冊記的是0922 第一次進院實際發生了什麼。結果是《進院通則》三種結果裡的 C 級：失敗——服務沒有在院內主機上跑起來。

    依《進院通則》的前提，C 級不是白跑一趟，前提是紀錄做滿。這一冊把當天帶回來的零散資訊（現場筆記、情報蒐集表的回答、四張螢幕照片）整理成下一次進院能直接用的形狀：做錯了什麼、主機長什麼樣、哪些題目還空著、現場留下了什麼要收拾、手冊要改哪裡。

    公開範圍：文件站是公開的。主機名稱、帳號名稱、完整的連接埠清單與原始照片一律不寫進這一冊，留在開發端本機的現場資料夾（不進 repo）。這一冊只寫判斷所需的結論。（0922 早於 1108 定的敏感資料雙軌，私人 repo 的 deploy/records/ 沒有 0922 的資料夾。）

    摘要¶

    • C 級失敗：院方當天要求以容器部署，現場卻先手動開了一個 python 容器、在容器裡 git clone，再在容器裡照《git clone＋Docker 路線詳細版》做，指令一條都不成立（F-01）
    • 那個容器掛了整顆 C 槽（F-02）、連接埠對應兩頭都不對（F-03）
    • 更根本的一層：容器修正不在 master 上（F-04）、進院前的 D-02～D-04 沒做（F-05）、院方的要求沒有當場釐清（F-06）
    • 最重要的發現：主機當天連得到院外（F-07）；電源極不穩、無人看管，Docker Desktop 要有人登入才會啟動（F-08）
    • 現場留下 dialysis_system_v0 容器與 C 槽上一份 clone（F-10），classic 權杖已於 0922 刪除（F-11）
    • 情報蒐集表 A 級 25 題：答到 6、部分 5、空白或未確認 14
    • 手冊待改 F-13～F-19 已於 0926 全部改完；下一次進院前要先有書面答案的 14 題在 F-20
    • 1117 後續：F-10 的容器 1029 已確認不在（《第三次進院紀錄（1029）》）；院內主機的現況以《院內主機現況與未完成事項》為準

    0. 先講結論¶

    0.1 一句話¶

    院方要求以容器部署，這正是《git clone＋Docker 路線詳細版》的情境；但當天沒有照那一冊的方式做，而是先手動開了一個通用的 Python 容器、在容器裡 git clone，再在容器「裡面」照那一冊從頭執行。 那一冊的每一條指令都是寫給主機上的 PowerShell 下的，在容器裡一條都不成立，之後就全部亂掉了。

    0.2 失敗原因，由重到輕¶

    # 原因 屬於 詳見
    F-01 在自己開的容器裡面照《git clone＋Docker 路線詳細版》做，那一冊本身卻就是在教怎麼建出容器 現場操作 第 2 節 F-01
    F-02 -v /c:/app 把整顆 C 槽掛進了容器 現場操作，有資料與資安風險 第 2 節 F-02
    F-03 -p 3000:8000：主機的 3000 已經有人在用，容器裡的 8000 也沒有任何東西在聽 現場操作 第 2 節 F-03
    F-04 《git clone＋Docker 路線詳細版》與 0921 的三處容器修正都不在 master 上，院方照預設 clone 到的是修正前的版本 進院前的準備（D-01） 第 2 節 F-04
    F-05 進院前的 D-02～D-04 沒有做到位：Docker 問題清單沒有事先寄出、沒有在乾淨機器上演練 進院前的準備 第 2 節 F-05
    F-06 院方的要求本身有兩種讀法（見 0.3），當場沒有釐清就動手 溝通 第 2 節 F-06

    即使 F-01～F-03 都沒有發生，照《git clone＋Docker 路線詳細版》做也會在 D-14 或 D-18 倒下：F-04 讓院方拿到的是修正前的 Dockerfile（沒有 OpenSSL、/data 屬於 root、compose 只接受繫結掛載），那一冊 0.3 節那三個問題會原樣重演。所以這一次的失敗有兩層，現場那一層很顯眼，準備那一層更根本。

    0.3 院方到底要求什麼（還沒釐清）¶

    現場筆記的原話是：「院方要求部署在 container 內，但似乎又允許鏡像到 docker 外。」這句話有兩種讀法，結果差很多：

    讀法 意思 對應
    甲 服務要跑在容器裡；連接埠、備份目錄這些對應到容器外是允許的 就是《git clone＋Docker 路線詳細版》：程式在映像檔裡、資料在具名資料卷、備份掛主機目錄
    乙 資料（資料庫檔案）也可以直接放在 Windows 目錄，用繫結掛載給容器讀寫 違反 DEP-23。《部署規範》3.1 當初改掉容器，理由正是這種放法的 SQLite 檔案鎖不可靠

    下一次進院前要拿到書面答案（F-20）。若院方的意思是乙，那不是手冊能開的例外，要回到《部署規範》3.3 談。

    兩條路線的逐項比較、以及不用容器也能與同機其他專案隔離的理由，整理在《部署路線比較》，詢問院方時帶著它去。

    1. 當天實際做了什麼¶

    1.1 經過¶

    1. 查主機資訊：主機名稱、作業系統、時區、磁碟、連接埠、node -v、docker version（第 3 節）。
    2. 直接下了下面這一行，建出一個容器。
    3. 進到這個容器裡 git clone 本專案。
    4. 在容器裡按《git clone＋Docker 路線詳細版》從頭（D-01 起）往下做，之後步驟一步步對不上，現場判斷為失敗。

    第 2 步下的那一行：

    docker run -dit --name dialysis_system_v0 -v /c:/app -p 3000:8000 python

    1.2 沒有留下來的紀錄¶

    以下是情報蒐集表 3.6 節（《進院通則》）要求、這次沒有記到的東西。它們已經拿不回來了，列在這裡是為了下一次不要再漏：

    情報蒐集表 應該記的 這次
    C-38 每一步的錯誤原文 沒有。只知道「後面亂成一團」，不知道是哪一條指令、哪一行錯誤
    C-39 每一步的實際耗時 沒有
    C-40 卡住的每一件事 只有整體印象，本冊第 2 節是事後推斷
    C-41 有沒有人提議「開一下網路」 沒有記。但主機當天是連得到院外的（見 F-07）
    C-42 現場任何人說的「這樣不行」「我們這裡都是…」 只有 0.3 那一句

    這一條本身就是教訓：錯誤原文沒抄，下一次連「上次卡在哪」都說不清楚。《進院通則》現場的基本原則第 3 條「錯誤訊息抄原文」在人慌的時候最容易被放掉。

    2. 為什麼會失敗¶

    F-01 在容器裡面照 git clone＋Docker 路線做¶

    發生了什麼：先 docker run 出一個 python 容器，再進去照那一冊做。

    為什麼不成立：那一冊的形狀是「主機上有 Docker → 在主機上 git clone → 在主機上 docker build 把原始碼建成映像檔 → docker compose up 由映像檔開出三個容器」。容器是這一整串的產物，不是起點。在容器裡面做，每一步都少了它要的東西：

    那一冊的步驟 在 python 容器裡會怎樣
    D-07 docker version、docker compose version 容器裡沒有 docker 指令，也碰不到主機的 Docker
    D-09 Get-LocalGroupMember 容器裡沒有 PowerShell，那是 Linux
    D-11 New-Item、C:\hd 同上；路徑也不存在
    D-14 docker build 沒有 docker，建不出映像檔
    D-16 產生 JWT_SECRET、D-18 套用遷移 都要先有映像檔；python 映像檔裡也沒有本專案要的 Node.js 20
    D-19 docker compose up -d 同 D-14

    下一次怎麼做：不要自己先開任何容器。 在主機的 PowerShell 視窗裡，從 D-05 開始照那一冊做；容器會在 D-19 由 docker compose up -d 自己出現，名字是 api、nurse-web、patient-web。

    F-02 整顆 C 槽被掛進容器¶

    發生了什麼：-v /c:/app 在 Docker Desktop 上的意思是「把主機的 C:\ 掛到容器的 /app」。（這一點要在主機上用 F-10 的指令確認，見下。）

    為什麼嚴重：

    • 容器裡預設是 root。容器裡的任何指令，都能讀寫主機整顆 C 槽——包含同一台主機上另一個專案的檔案、 Windows 使用者資料夾、Docker 自己的虛擬磁碟所在的 AppData。這是 DEP-37 共用主機隔離的反面
    • 在容器裡對 /app 做的任何刪除，刪的是主機上的真檔案。 在容器裡下一句 rm -rf /app/*，就是清空 C 槽
    • 在 /app 底下 git clone，原始碼就落在主機 C 槽的根目錄底下，而且是在一個沒人預期的位置
    • 若之後把資料庫也放在 /app 底下，就是 0.3 讀法乙，違反 DEP-23

    下一次怎麼做：這條路線上，只有一個主機目錄會被掛進容器：備份目錄（HD_BACKUP_DIR，掛到 /backups）。其餘一律不掛。這件事由 docker-compose.yml 決定，不要自己下 -v。

    F-03 連接埠對應兩頭都不對¶

    發生了什麼：-p 3000:8000 是「主機的 3000 → 容器的 8000」。

    為什麼不成立：

    端 問題
    主機的 3000 現場的連接埠清單裡，3000 已經有行程在聽，而且與 9000 是同兩個行程——很可能是同機另一個專案的 Docker 轉送，也可能是這個容器自己開的（要用 F-09 確認）。無論是哪一種，本系統都不能再用 3000
    容器的 8000 本系統的後端在容器裡聽的是 3000、護理端 8080、病人端 8081，沒有任何東西聽 8000

    下一次怎麼做：D-13 那三個埠要避開 3000 與 9000。現場清單上 8080、8081 是空的；後端埠要另外挑一個空的、向資訊室登記，寫進 .env 的 HD_API_PORT， 也寫進 D-14 的 VITE_API_BASE_URL（兩處要一致，否則要重建映像檔）。

    F-04 要被 clone 的那一版根本不在 master 上¶

    發生了什麼（事後在開發端查到的）：

    分支 最新 commit 有沒有《git clone＋Docker 路線詳細版》 有沒有 0921 三處容器修正
    origin/master（GitHub 預設分支） c4109fa（《備份、還原與關服務》前身那一冊） 沒有 沒有
    origin/docker-route 70b5de5 有 有

    git clone 不指定分支時拿到的是 master。院方當天 clone 到的若是 master，拿到的就是 《git clone＋Docker 路線詳細版》0.3 節說「不修會在院內直接倒下」的那一版：沒有 OpenSSL、/data 屬於 root、compose 只接受繫結掛載。

    為什麼會這樣：那一冊的 D-01 就是在防這件事——「本機與 origin/master 的 commit 一模一樣」。這一步在進院前沒有做到：修正推上了 docker-route 分支，沒有合回 master。

    當天實際 clone 到哪一版不知道：只記到 git remote -v（有 origin），沒有記 git log -1 --oneline。這一版在容器裡、也在主機 C 槽上（F-02），F-10 可以查到。

    下一次怎麼做：進院前把 docker-route 合回 master 並推上去，然後才做 D-01 的比對；交付單上寫 commit，現場 D-12 用 git log -1 逐字核對。

    F-05 進院前的 D-02～D-04 沒有到位¶

    步驟 應該在進院前 這次
    D-02 在一台乾淨的 Windows 機器上把 D-11～D-23 完整走一次 沒有。開發機上的演練（《git clone＋Docker 路線詳細版》0.3 節）與這台主機差很多：主機 3000 埠被佔、有 RAM 磁碟、Docker Desktop 從 Microsoft Store 更新
    D-03 兩週前把 9 題 Docker 問題清單寄給資訊室 沒有。第 2、3 題（Docker Desktop 授權、重新開機後有沒有人登入）到現在仍無答案
    D-04 準備一把唯讀、會過期的權杖 沒有。當天是臨時建了一把 classic 權杖，已於 0922 刪除，見 F-11

    那一冊寫的是「院方要求容器的話翻這一冊」，但院方的要求是當天才知道的，準備工作排不進去。這條教訓要寫回總覽：院方有可能臨時改要求，進院前就要把那一冊的準備做完，不管用不用得到。

    F-06 院方的要求沒有當場釐清¶

    0.3 那一句話有兩種讀法，現場沒有問清楚就動手。D-05、D-06 本來就是要在動手前把這件事講清楚、簽下來的一步；這次跳過了。

    F-07 主機當天連得到院外¶

    這不是失敗原因，但是這一趟最重要的發現之一：當天 docker run ... python 能把 python 映像檔從 Docker Hub 拉下來、容器裡 git clone 能從 GitHub 拿到私有 repo，表示這台主機當時有對外連線。

    • 這與部署規範「零院外連線」的前提不一致，要問清楚：是一直都開著，還是當天為了部署臨時開的？誰開的、誰會關？ （D-03 第 7 題、D-24）
    • 《進院當天詳細版》H-08 預期路線 A「每一步都失敗」，這台主機上不成立
    • 在這個問題有書面答案之前，不得輸入任何真實病人資料（與 D-24 同一條）

    3. 主機實況（現場帶回來的）¶

    3.2 磁碟¶

    磁碟 類型 大小 可用 判斷
    C（系統） NTFS，固定 1.09 TB 798.65 GB 空間充足。Docker 的虛擬磁碟在這一顆上（3.3）
    D（媒體） NTFS，固定 840.6 GB 38.46 GB 只剩約 4.6%。不適合放備份，除非資訊室說明這顆的用途與誰在寫入
    E RAM 磁碟，FAT32 3.99 GB 3.38 GB ✗ 任何東西都不能放這裡：斷電或重新開機就全部消失。這台主機又常斷電（F-08）
    F 卸除式，exFAT 57.3 GB 57.06 GB 當時插著的隨身碟或外接碟，不是主機的磁碟
    另有三個小分割區 NTFS／FAT32 各 1.3 GB 或 299.4 MB — 系統保留，不理它

    這台與《部署規範》記載的規格對不太上：規範寫的是「2TB SSD ×2」，現場是一顆約 1.1 TB 的 C 與一顆約 840 GB 的 D。可能是同一組硬碟分割的方式不同，也可能不是同一台。H-06 說過：「裝錯機器是最難救的錯誤」，下一次先問清楚（F-20）。

    3.4 連接埠（DEP-37 第 2 項）¶

    埠 現況 對本系統的意義

    其餘 Windows 系統服務與動態埠 完整清單見原始照片（不上站）
