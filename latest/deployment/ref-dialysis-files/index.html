    讀檔：啟用、檢查、停用¶

    狀態：現行（常備參考）。院內主機 1116 起讀檔是開著的，現況見《院內主機現況與未完成事項》。

    1117 由舊第二十三冊附錄二（停用讀檔）、第二十四冊附錄二（停用之後已寫進主機的資料）、第二十冊附錄三（停用讀檔）、第二十三、二十四冊 SY-09～SY-11 裡之後還會用到的檢查，與第十五冊 V-30a 的讀檔檢查改寫；以 apps/api 的讀檔程式、docker-compose.dialysis-files.yml、deploy/hospital.env.example（master）核對。

    編號 DF-xx 是這一份新給的；舊冊的 SY-09～SY-11 照舊是第五次進院那一趟的步驟，在《第五次進院（1116）任務二 · 本系統換版上線》。

    公開範圍：指定資料夾以外的院內路徑、病人的值不寫；讀檔檢查只印結構與統計，整段可以抄進紀錄。現場值記在私人 repo 的 deploy/records//。

    摘要¶

    • 讀檔＝本系統唯讀讀抓取腳本 hd-hospital-fetch 存下的檔，不打院方 API；院內 1116 起開著，讀 C:\API_Fetch\IDH_interface
    • 開關只有 .env 五行（HD_DIALYSIS_LIST_DIR、HD_LAB_DIR、COMPOSE_FILE、HOSPITAL_API_BASE_URL、HD_SIMULATION_DEPLOYMENT）加一次 docker compose --env-file $cfg up -d（DF-02、DF-09）
    • 啟用是分界線：一開，當天清單上所有病人的主檔、床位、療程每 3 分鐘寫進主機；啟用前四條全過才開（DF-01）
    • 每次改完都跑讀檔檢查 hospital-api-probe，看「在、讀得到」「唯讀：是」「模擬標記檔：沒有」「狀態檔：讀得到」「結果：成功」（DF-03）
    • 日常看「系統管理 → 院方資料同步」卡；對數字、稽核、時間往前跳的看法在 DF-04～DF-07
    • 停用不會刪掉已寫進去的資料；要清掉只有退回更新前備份或撤除整套，都要開發端判斷（DF-09、DF-10）
    • 🧪 開發機改讀模擬院方資料；與院內不同的每一處標在步驟裡
    • 檢驗資料（HD_LAB_DIR）1111 起不讀：學長答 hb 不由這邊處理

    0. 讀檔怎麼運作¶

    哪一段 怎麼做
    誰寫檔 院內主機上的抓取腳本 hd-hospital-fetch（工作排程器，每 3 分鐘、07:00～23:00），寫進指定資料夾的 YYYY-MM.txt，每一輪覆寫同一個資料夾裡的 fetch-status.json；腳本的維運在《院方 API 抓取腳本的維運》
    怎麼掛進來 設定目錄 .env 的 HD_DIALYSIS_LIST_DIR 寫主機上的資料夾路徑；COMPOSE_FILE 帶上 docker-compose.dialysis-files.yml，它把那個資料夾以唯讀繫結掛到 api 容器的 /hospital/dialysis-list，docker-compose.yml 再把容器內的 HOSPITAL_DIALYSIS_LIST_DIR 設成這個路徑。沒填就不掛（DEP-37 第 3 條的例外只到這裡）
    多久讀一次 營運參數「院方資料讀檔頻率」，預設 3 分鐘（1～30），在護理端「系統管理 → 營運參數與選項清單」調
    讀什麼 當月檔從檔尾往回讀出今天的段落，合起來（同一個鍵以後面的為準）；每列要 51 欄，依（病歷號、透析開始時間）分成一次一次的透析

    DF-05 對數字¶

    不抄任何病人的值。

    • 透析次數：卡片表格「透析次數」跟讀檔檢查的透析次數差不多
    • 病人數：即時總覽（專業版首頁「即時總覽（日期）」的「當日排班」）要對的是讀檔檢查「姓名欄含『〇』：N 列（M 位病人）」的 M，不是透析次數 K：同一位病人預排與實際開始時間不同會算成兩次，K 比 M 多幾次正常；隔一輪多 1、2 位也正常（剛來的病人）。1116：讀檔檢查 89 位病人、95 次；即時總覽 89，下一輪 90
    • 病人數差很多：讀檔檢查算的是整個月份檔的當天段落，卡片同步的是今天；差幾位正常，差一半以上就抄下兩個數字，可以停用
    • 療程進行中：即時總覽這一格算的是有平板綁定的療程，不是讀檔的「透析中」；沒綁平板時是 0，正常
    • 🏥 有空時問護理師「現在在透析的有幾床、今天排了幾床」，跟即時總覽對；護理師很忙可以不問，紀錄寫「未問，以讀檔檢查與即時總覽一致代替」
    • 床號：系統管理 →「床位清單」卡，院方資料出現的床號自動加在最後面。院內會看到 A1～E9（沒有 4 號床）、I1、I2，以及原樣出現的 1A～3D、99——1A～3D 共 12 床，跟 A1 那些是不同的床、不是倒過來寫，成大現有系統的床位圖也沒有它們；99 不是一張床，一天約 10 次透析、同一時間好幾位病人，斗六分院的程式叫它「暫存床」。不要改設定。當天沒人透析的床（例如 1A～1D）不會出現。簡易版只顯示平板編號與病人姓名，看不到床號（1116 模擬實測）。🧪 模擬資料只有字母開頭的床號
    • 🏥 院內清單最前面的 01～15 是 1005 以前的版本在全新資料庫自動建的 15 床預設床位（院內資料庫是 1001 建的），不是院方的床；由護理長在「床位清單」拿掉。拿掉只是停用、不刪紀錄，有病人或平板在那一床時拿不掉

    DF-06 稽核軌跡¶

    系統管理 → 稽核軌跡：

    • 「院方資料格式不符，該次透析未寫入」（卡片表格的「格式不符」欄也是這個數）：🏥 應該沒有；有的話抄原因（不含病歷號），多半是床號或療程欄位對不上，回來看。🧪 每一輪都會有 1 筆，是模擬資料故意放的壞資料（模擬辛，每列少兩欄），正常
    • 「院方 API：整批未寫入，共 1 處問題。第 1 列 value：目標脫水量超出可接受的範圍 0～8000 mL」（1116 院內看到很多筆）：不擋、不停用。被擋的只有那位病人那一次的四個數值（理想體重、目標脫水量、結束體重、實際脫水量），療程、床位、生命徵象照常寫；每 3 分鐘重讀一次就再記一筆，所以很多筆。含迭代 32.2 的版本換上之後（1124 做完，下一個 tag）：超出範圍的照院方的值寫，這一句不再出現；只剩「目標脫水量是負數」或「目標脫水量的值讀不懂」這類，被擋的只有那一個值，另外三個照寫。查是負的還是太大（只印次數與最小最大，不印病人）：
    docker compose --env-file $cfg exec -T api node -e "const f=require('./apps/api/dist/modules/hospital-sync/hospital-files.js'),p=require('./apps/api/dist/modules/hospital-sync/hospital-api.format.js');(async()=>{const d=await f.readDialysisDay(process.env.HOSPITAL_DIALYSIS_LIST_DIR,p.hospitalLocalDate(new Date()));const v=p.validateRows(f.mergeDialysisSegments(d.segments)).dialyses.map(x=>x.ufTargetMl).filter(x=>x!==null);console.log('dialyses',v.length,'negative',v.filter(x=>x<0).length,'over8000',v.filter(x=>x>8000).length,'min',Math.min(...v),'max',Math.max(...v))})()"

    dialyses 是今天有目標脫水量的透析次數，negative、over8000 是超出範圍的次數，min、max 單位 mL。整行抄進紀錄，回開發端看要不要改範圍；首波那一位若被擋，「本次透析」面板先不開（或指派前先確認他不在被擋的那幾次裡）。1116 院內結果：dialyses 96 negative 0 over8000 3 min 500 max 74600——74.6 公升不可能是脫水量，像是院方那幾筆把體重（74.6 公斤）填進目標脫水量欄；範圍檢查擋得對，不必改程式。1118 醫師說明是護理師填錯，建議不要擋（顯示錯的值有助於病人提醒更正），1120 使用者定放行、排成迭代 32.2，1124 程式做完（院方 API《之二之一》E-5、《院內主機現況》ST-34）；含 32.2 的版本換上之前照舊擋；稽核要不要改成「同一次透析同一個原因只記一次」是開發端的候選改動，先問使用者

    DF-08 什麼時候停用¶

    • DF-03 讀檔檢查不對（唯讀：否、🏥 模擬標記檔有）

    • 🏥 卡片出現「目前接的是模擬院方 API」
    • 院方要求先停
    • 🧪 第五次進院演練的 SY-M1（驗院內設定擋得住模擬之後停用）

    要連版本一起退回（退到上一個 tag）時，不是只停用，照《本系統換版與退回》；退回步驟裡已經包含清空 HD_DIALYSIS_LIST_DIR、註解 COMPOSE_FILE。

    DF-09 停用讀檔¶

    做什麼：notepad $cfg，HD_DIALYSIS_LIST_DIR 清空（等號後面什麼都不留）、COMPOSE_FILE 那一行改回註解（開頭加 #），然後：

    docker compose --env-file $cfg up -d

    成功：「院方資料同步」卡寫「還沒有設定院方資料的來源，系統不讀院方資料：病人、床位與療程照護理師的人工操作。」；日誌沒有「院方資料同步已啟用」。之後病人、床位、療程回到護理師的人工操作。抓取腳本不受影響、照跑（要停腳本是另一件事，在《院方 API 抓取腳本的維運》）。

    已經寫進主機的資料不會被刪，現場不要自己刪（DF-10）。

    DF-10 停用之後，已經寫進主機的資料¶

    停用不會刪掉。病人主檔、床位、療程留在資料庫裡，床位只新增、不會自己消失。要整個清掉只有兩條路，都要開發端判斷後再做：

    1. 退回啟用讀檔之前的更新前備份：做《本系統換版與退回》退回的「停後端、把現在的資料庫移到旁邊、還原、啟動」那一步，但版本留在現在的 tag（只清空 HD_DIALYSIS_LIST_DIR、註解 COMPOSE_FILE，不改 HD_IMAGE_TAG、不 git checkout）。那份備份之後的改密碼、建帳號、平板註冊也會一起消失。院內能用的是 1116 SY-04 的更新前備份（檔名與雜湊在私人紀錄 deploy/records/1116-fifth-visit/），時間在 1116 啟用讀檔之前
    2. 撤除整套：要院方書面同意，會刪掉整個透析中心在本系統的紀錄；照《備份、還原與關服務》的撤除

    現場不要自己刪。
