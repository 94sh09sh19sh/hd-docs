# 讀檔：啟用、檢查、停用

> 狀態：現行（常備參考）。院內主機 1116 起讀檔是開著的，現況見《[院內主機現況與未完成事項](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-status/index.md)》。
>
> 1117 由舊第二十三冊附錄二（停用讀檔）、第二十四冊附錄二（停用之後已寫進主機的資料）、第二十冊附錄三（停用讀檔）、第二十三、二十四冊 SY-09～SY-11 裡之後還會用到的檢查，與第十五冊 V-30a 的讀檔檢查改寫；以 `apps/api` 的讀檔程式、`docker-compose.dialysis-files.yml`、`deploy/hospital.env.example`（master）核對。
>
> 編號 `DF-xx` 是這一份新給的；舊冊的 `SY-09`～`SY-11` 照舊是第五次進院那一趟的步驟，在《[第五次進院（1116）任務二 · 本系統換版上線](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/visit-5-system-2/index.md)》。
>
> **公開範圍**：指定資料夾以外的院內路徑、病人的值不寫；讀檔檢查只印結構與統計，整段可以抄進紀錄。現場值記在私人 repo 的 deploy/records//。

## 摘要

- 讀檔＝本系統唯讀讀抓取腳本 `hd-hospital-fetch` 存下的檔，**不打院方 API**；院內 1116 起開著，讀 `C:\API_Fetch\IDH_interface`
- 開關只有 `.env` 五行（`HD_DIALYSIS_LIST_DIR`、`HD_LAB_DIR`、`COMPOSE_FILE`、`HOSPITAL_API_BASE_URL`、`HD_SIMULATION_DEPLOYMENT`）加一次 `docker compose --env-file $cfg up -d`（DF-02、DF-09）
- **啟用是分界線**：一開，當天清單上所有病人的主檔、床位、療程每 3 分鐘寫進主機；啟用前四條全過才開（DF-01）
- 每次改完都跑讀檔檢查 `hospital-api-probe`，看「在、讀得到」「唯讀：是」「模擬標記檔：沒有」「狀態檔：讀得到」「結果：成功」（DF-03）
- 日常看「系統管理 → 院方資料同步」卡；對數字、稽核、時間往前跳的看法在 DF-04～DF-07
- 停用不會刪掉已寫進去的資料；要清掉只有退回更新前備份或撤除整套，都要開發端判斷（DF-09、DF-10）
- 🧪 開發機改讀模擬院方資料；與院內不同的每一處標在步驟裡
- 檢驗資料（`HD_LAB_DIR`）1111 起不讀：學長答 `hb` 不由這邊處理

## 1. 啟用

### DF-01 啟用前四條

四條**全部**成立才往下；有一條不成立就不啟用。

| #   | 條件                                                                                                                                                                                          | 現況（1116）                  | 🧪                       |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------ |
| 1   | 防毒排除有結論：已加，或沒加、出現現象再加（1116 定，現象見《[交接紙](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-status-handover/index.md)》「防毒」那一列）                | 沒加，照決定出現現象再加      | 寫「院內要問」，照樣往下 |
| 2   | 病人告知有答案（涵蓋，或已補公告；《資料庫使用規範》19.1）                                                                                                                                    | 1116 使用者回報既有告知已涵蓋 | 同上                     |
| 3   | 抓取腳本最近幾輪都成功（`LastTaskResult` `0`、狀態檔 `result` `ok`，看法在《[院方 API 抓取腳本的維運](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-fetch-script/index.md)》） | 1116 AF-11 三輪成功           | 模擬做過就算             |
| 4   | 「院方床位轉床號的方式」是 `0`；時段對（下面）                                                                                                                                                | `0`                           | 只看前半                 |

- **時段**：首波還沒開始用時，透析時段也可以啟用（DEP-32 1116 例外）——沒有人靠這套系統，斷線一分鐘、療程一口氣同步進來都不影響照護，在透析時段做反而能對正在透析的床；挑護理師不忙的時候。**首波開始用之後**，再改設定或更新就照舊排非透析時段
- **為什麼是分界線**：讀檔一開，每 3 分鐘就把當天清單上**所有病人**的主檔、床位、療程寫進資料庫，護理端會看到整個透析室，不是只有首波那一位；床位只新增、不會自己消失。停用不會刪掉已寫進去的（DF-10）。先讓首波護理師知道
- **床號轉換維持 `0`**（原樣顯示）：設成 `1` 會把 `1A` 轉成 `A1`，兩床的病人併成一床。1118 醫師說明 `1A`～`3D` 是 8 樓住院、`99` 是急診、`A`～`D` 開頭是透析門診（院方 API《[之二之一](https://94sh09sh19sh.github.io/hd-docs/latest/notes/hospital-api-fetch-methods-questions-answered/index.md)》D-1），床號原樣就對，不改

### DF-02 改 `.env` 五行

`notepad $cfg`，五行改成下面方框的樣子，其他行不動。路徑有空白與中文照寫、**不加引號**；用檔案總管網址列複製貼上最不會錯。`COMPOSE_FILE` 開頭沒有 `#`，第一個一定是 `docker-compose.yml`，後面**沒有** `;docker-compose.lab-files.yml`，也**不能留成空白的一行**。

🏥 院內：

```
HD_DIALYSIS_LIST_DIR=C:\API_Fetch\IDH_interface
HD_LAB_DIR=
COMPOSE_FILE=docker-compose.yml;docker-compose.dialysis-files.yml
HOSPITAL_API_BASE_URL=
HD_SIMULATION_DEPLOYMENT=
```

- 院內 `.env` 是較早的範本建的，沒有 `HOSPITAL_API_BASE_URL`、`HD_SIMULATION_DEPLOYMENT` 這兩行（1116 SR-05）：不用補，沒寫等於空白，正是院內要的
- `HD_LAB_DIR` 留空：檢驗資料不讀（1111 學長答 `hb` 不由這邊處理）；`HOSPITAL_LAB_FIELD_MAP` 也留空
- 範本在 `deploy\hospital.env.example` 的「院方資料：讀抓取腳本存下的檔」那一段；`v0.5.0` 的範本那一段有一行斷掉的註解（「aw_txt 與 hb-status.json）」），整段複製會讓 compose 讀不到 `.env`，只照上面方框改（master 已修好，下一個 tag 起沒有這一行）

🧪 開發機讀模擬院方資料：

```
HD_DIALYSIS_LIST_DIR=
HD_LAB_DIR=
COMPOSE_FILE=docker-compose.yml;docker-compose.hospital-files-sim.yml
HOSPITAL_API_BASE_URL=
HD_SIMULATION_DEPLOYMENT=yes
```

🧪 這一組要用 `docker compose --env-file $cfg --profile simulation up -d` 起，等 3 分鐘再做 DF-03。練院內那種掛法（路徑帶空白與中文、複製一份模擬的檔出來）的步驟是第五次進院演練的 SY-10 B2，在《[第五次進院（1116）任務二 · 本系統換版上線](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/visit-5-system-2/index.md)》。

### DF-03 套用、讀檔檢查

**做什麼**：

```
docker compose --env-file $cfg up -d
docker compose --env-file $cfg exec -T api node apps/api/dist/hospital-api-probe.js
```

任何時候想知道讀檔的狀態，都可以只打第二行（只讀、不寫任何檔、不碰資料庫）。

**成功**：

- 標題「院方資料讀檔檢查（只讀、只印結構，不印任何一個值，也不印路徑）」
- 「透析清單資料夾」：「在、讀得到」「唯讀：是」「模擬標記檔：沒有」（🧪 「有」才對）；月份檔數與範圍
- 狀態檔「讀得到」、結果「成功」、最後一次嘗試與成功是幾分鐘前
- 當月檔大小與修改時間；當天段落「N 段可讀、0 段略過」與合起來的列數；每列 51 欄
- 透析次數（依病歷號＋開始時間分組）與其中格式不符幾次；各欄型態分布；床位樣式（數字→`9`、字母→`A`）；姓名欄含「〇」的列數與病人數；透析進行中幾次；數值大小分布；同一分鐘兩筆幾筆
- 「檢驗資料資料夾：沒有設定（HOSPITAL_LAB_DIR）」是正常的
- 最後一行「以上可以整段抄進演練紀錄。」——**整段抄進紀錄**（工具不印路徑、姓名、病歷號）
- 日誌有「院方資料同步已啟用（讀透析清單資料夾），啟動後先讀一次，之後依營運參數的頻率」

1116 院內第一次的結果（17 段、514 列、95 次透析、格式不符 0、89 位病人）在《[第五次進院紀錄](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/record-5-1116/index.md)》第 2 節，之後可以拿來對照規模。

### DF-05 對數字

不抄任何病人的值。

- **透析次數**：卡片表格「透析次數」跟讀檔檢查的透析次數差不多
- **病人數**：即時總覽（專業版首頁「即時總覽（日期）」的「當日排班」）要對的是讀檔檢查「姓名欄含『〇』：N 列（M 位病人）」的 M，不是透析次數 K：同一位病人預排與實際開始時間不同會算成兩次，K 比 M 多幾次正常；隔一輪多 1、2 位也正常（剛來的病人）。1116：讀檔檢查 89 位病人、95 次；即時總覽 89，下一輪 90
- **病人數差很多**：讀檔檢查算的是整個月份檔的當天段落，卡片同步的是今天；差幾位正常，差一半以上就抄下兩個數字，可以停用
- **療程進行中**：即時總覽這一格算的是**有平板綁定**的療程，不是讀檔的「透析中」；沒綁平板時是 0，正常
- 🏥 有空時問護理師「現在在透析的有幾床、今天排了幾床」，跟即時總覽對；護理師很忙可以不問，紀錄寫「未問，以讀檔檢查與即時總覽一致代替」
- **床號**：系統管理 →「床位清單」卡，院方資料出現的床號自動加在最後面。院內會看到 `A1`～`E9`（沒有 4 號床）、`I1`、`I2`，以及原樣出現的 `1A`～`3D`、`99`——`1A`～`3D` 共 12 床，跟 `A1` 那些是**不同的床**、不是倒過來寫，成大現有系統的床位圖也沒有它們；`99` **不是一張床**，一天約 10 次透析、同一時間好幾位病人，斗六分院的程式叫它「暫存床」。不要改設定。當天沒人透析的床（例如 `1A`～`1D`）不會出現。簡易版只顯示平板編號與病人姓名，看不到床號（1116 模擬實測）。🧪 模擬資料只有字母開頭的床號
- 🏥 院內清單最前面的 `01`～`15` 是 1005 以前的版本在全新資料庫自動建的 15 床預設床位（院內資料庫是 1001 建的），不是院方的床；由護理長在「床位清單」拿掉。拿掉只是停用、不刪紀錄，有病人或平板在那一床時拿不掉

### DF-06 稽核軌跡

系統管理 → 稽核軌跡：

- **「院方資料格式不符，該次透析未寫入」**（卡片表格的「格式不符」欄也是這個數）：🏥 應該沒有；有的話抄原因（不含病歷號），多半是床號或療程欄位對不上，回來看。🧪 每一輪都會有 1 筆，是模擬資料故意放的壞資料（模擬辛，每列少兩欄），正常
- **「院方 API：整批未寫入，共 1 處問題。第 1 列 value：目標脫水量超出可接受的範圍 0～8000 mL」**（1116 院內看到很多筆）：**不擋、不停用**。被擋的只有那位病人那一次的四個數值（理想體重、目標脫水量、結束體重、實際脫水量），療程、床位、生命徵象照常寫；每 3 分鐘重讀一次就再記一筆，所以很多筆。查是負的還是太大（只印次數與最小最大，不印病人）：

```
docker compose --env-file $cfg exec -T api node -e "const f=require('./apps/api/dist/modules/hospital-sync/hospital-files.js'),p=require('./apps/api/dist/modules/hospital-sync/hospital-api.format.js');(async()=>{const d=await f.readDialysisDay(process.env.HOSPITAL_DIALYSIS_LIST_DIR,p.hospitalLocalDate(new Date()));const v=p.validateRows(f.mergeDialysisSegments(d.segments)).dialyses.map(x=>x.ufTargetMl).filter(x=>x!==null);console.log('dialyses',v.length,'negative',v.filter(x=>x<0).length,'over8000',v.filter(x=>x>8000).length,'min',Math.min(...v),'max',Math.max(...v))})()"
```

`dialyses` 是今天有目標脫水量的透析次數，`negative`、`over8000` 是超出範圍的次數，`min`、`max` 單位 mL。整行抄進紀錄，回開發端看要不要改範圍；首波那一位若被擋，「本次透析」面板先不開（或指派前先確認他不在被擋的那幾次裡）。1116 院內結果：`dialyses 96 negative 0 over8000 3 min 500 max 74600`——74.6 公升不可能是脫水量，像是院方那幾筆把體重（74.6 公斤）填進目標脫水量欄；範圍檢查擋得對，不必改程式。**1118 醫師說明是護理師填錯**，建議不要擋（顯示錯的值有助於病人提醒更正），要不要放行由開發端判斷（院方 API《[之二之一](https://94sh09sh19sh.github.io/hd-docs/latest/notes/hospital-api-fetch-methods-questions-answered/index.md)》E-5、《院內主機現況》ST-34），定之前照舊擋；稽核要不要改成「同一次透析同一個原因只記一次」是開發端的候選改動，先問使用者

### DF-07 時間有沒有往前跳

等 3 分鐘，卡片表格最上面一列的時間往前跳就是在讀。

- 沒往前跳：看抓取腳本的排程是不是還在跑（`Get-ScheduledTaskInfo -TaskName hd-hospital-fetch`，看法在《[院方 API 抓取腳本的維運](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-fetch-script/index.md)》）
- 23:00 後抓取腳本不抓，狀態檔停在 23:00 前最後一輪，正常
- 🧪 從模擬複製出來的資料夾不會再變，卡片一定是「內容沒變」，之後出現「未更新」提示也正常

## 3. 停用

### DF-08 什麼時候停用

- DF-03 讀檔檢查不對（`唯讀：否`、🏥 模擬標記檔有）
- DF-05 床號或療程對不上（B 級，記下實況）
- 🏥 卡片出現「目前接的是模擬院方 API」
- 院方要求先停
- 🧪 第五次進院演練的 SY-M1（驗院內設定擋得住模擬之後停用）

要連版本一起退回（退到上一個 tag）時，不是只停用，照《[本系統換版與退回](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-upgrade/index.md)》；退回步驟裡已經包含清空 `HD_DIALYSIS_LIST_DIR`、註解 `COMPOSE_FILE`。

### DF-09 停用讀檔

**做什麼**：`notepad $cfg`，`HD_DIALYSIS_LIST_DIR` 清空（等號後面什麼都不留）、`COMPOSE_FILE` 那一行改回註解（開頭加 `#`），然後：

```
docker compose --env-file $cfg up -d
```

**成功**：「院方資料同步」卡寫「還沒有設定院方資料的來源，系統不讀院方資料：病人、床位與療程照護理師的人工操作。」；日誌沒有「院方資料同步已啟用」。之後病人、床位、療程回到護理師的人工操作。抓取腳本不受影響、照跑（要停腳本是另一件事，在《[院方 API 抓取腳本的維運](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-fetch-script/index.md)》）。

已經寫進主機的資料不會被刪，**現場不要自己刪**（DF-10）。

### DF-10 停用之後，已經寫進主機的資料

停用不會刪掉。病人主檔、床位、療程留在資料庫裡，床位只新增、不會自己消失。要整個清掉只有兩條路，**都要開發端判斷後再做**：

1. 退回啟用讀檔之前的更新前備份：做《[本系統換版與退回](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-upgrade/index.md)》退回的「停後端、把現在的資料庫移到旁邊、還原、啟動」那一步，但版本留在現在的 tag（只清空 `HD_DIALYSIS_LIST_DIR`、註解 `COMPOSE_FILE`，不改 `HD_IMAGE_TAG`、不 `git checkout`）。那份備份之後的改密碼、建帳號、平板註冊也會一起消失。院內能用的是 1116 SY-04 的更新前備份（檔名與雜湊在私人紀錄 deploy/records/1116-fifth-visit/），時間在 1116 啟用讀檔之前
1. 撤除整套：要院方書面同意，會刪掉整個透析中心在本系統的紀錄；照《[備份、還原與關服務](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-backup-shutdown/index.md)》的撤除

現場不要自己刪。
