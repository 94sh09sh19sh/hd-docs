    第十五冊之三 · 1001 為什麼登不進去、下一次怎麼做（新手版）¶

    版本：v0.1　文件狀態：草案（1005 新增）　編號：E-xx　與第十五冊一起印出來帶進去

    這一冊給誰：沒去過 1001、沒碰過 CORS，下一次卻要進院接手的人。

    1001 第二次進院的完整紀錄在第十四冊之四，但那一冊是寫給已經知道來龍去脈的人看的： 編號多、術語多，一句話裡常常塞了三件事。這一冊把它翻成白話，只回答三個問題：

    1. 那天到底卡在哪裡（第 0、2 節）
    2. 為什麼會卡在那裡、為什麼當場解不開（第 1、3、4 節）
    3. 下一次要做什麼，才不會再卡一次（第 5 節）

    這一冊只解釋、不另立步驟。 要打的指令仍以第十五冊 V-17 與它的附錄為準； 這裡抄過去的幾條是為了讓你看懂，兩邊不一致時以第十五冊為準。

    編號 E-xx 是第 5 節「下一次要做的事」，寫進訊息或準備清單時用它指稱。 文中的 M-xx 是第十四冊之四的發現、V-xx 是第十五冊的步驟、N-xx 是第十四冊的步驟。

    公開範圍：文件站是公開的。主機名稱、IP、帳號、.env 裡的值一律不寫進這一冊，下面都用 <主機> 代替。這一條與第十冊、第十四冊之四相同。

    下一次第一件事 服務還在的話，先把放行名單改對、讓後端重新讀一次、確認放行，再用正確的網址登入。登入通了才往下做備份、重新開機與平板（第 5 節）

    1. 先懂三件事¶

    沒有這三件事的概念，第 3 節的原因會看不懂。每一件都不難。

    1.1 按下「登入」的那一刻發生了什麼¶

    護理端的網頁和後端是兩個不同的服務，各自用一個埠：

      護理站的瀏覽器
      │
      │ ① 開 http://<主機>:18080          → 護理端（nurse-web）把登入頁送過來
      │
      │ ② 按下登入，網頁去呼叫
      │    http://<主機>:13000/api/…       → 後端（api）檢查帳號密碼
      │
      │    瀏覽器先問後端：「我手上這頁是 http://<主機>:18080 來的，你收不收？」
      │      ├─ 後端回答「收」  → 送出帳號密碼 → 登入成功或「工作ID 或密碼錯誤」
      │      └─ 後端沒回答「收」→ 瀏覽器自己擋下來 → Failed to fetch

    重點在第 ② 步那個「先問」。這是瀏覽器的安全規定，不是我們的程式自己加的： 一個網頁要去呼叫另一個埠上的服務，對方必須明白說「我收你」，瀏覽器才肯把結果交給網頁。 這套規定叫 CORS；後端願意收的網頁位址，寫在 .env 的 CORS_ORIGINS，這一冊叫它「放行名單」。

    可以把後端想成大樓的管理員、CORS_ORIGINS 是他桌上的訪客名單：名單上沒有你，你連大門都進不去，根本輪不到檢查你的證件（帳號密碼）。 所以 Failed to fetch 出現時，帳號密碼對不對還完全沒被看過。

    1.2 「來源」要一字不差¶

    放行名單上寫的、瀏覽器拿去問的，都是網址列最前面那一段：http:// ＋ 主機 ＋ 埠，叫做「來源」。 比對時是一個字一個字比，不會去想「這兩個其實是同一台機器」。

    假設 CORS_ORIGINS=http://<主機>:18080，<主機> 是一個名稱：

    瀏覽器網址列上的來源 是不是同一台機器 後端收不收
    http://<主機>:18080 是 收
    http://localhost:18080 是（在主機上開的話） 不收：localhost ≠ <主機>
    http://<主機的 IP>:18080 是 不收：IP ≠ 名稱
    http://<主機>.<DNS 尾碼>:18080 是 不收：多了尾碼就是另一串字
    http://<主機>:13000 是 不收：埠不同
    https://<主機>:18080 是 不收：https ≠ http

    這就是為什麼第十五冊一再說「<主機> 只能有一種寫法」：選定了名稱就全部用名稱，選定了 IP 就全部用 IP，包括你在瀏覽器裡打的網址。

    1.3 .env 改了不會自己生效¶

    .env 是一份文字檔，改了存檔，執行中的服務不會知道。兩項跟登入有關的設定，生效的時機還不一樣：

    .env 的哪一項 什麼時候被讀進去 改了之後要做什麼 比喻
    CORS_ORIGINS（放行名單） 後端的容器建立時讀一次 docker compose --env-file $cfg up -d（compose 會發現設定變了，重建後端） 管理員上班時領一份名單，換名單要請他重新報到
    HD_PUBLIC_API_URL（網頁要去連的後端位址） 建置（build）時寫死進護理端的網頁檔案 先 build、再 up -d。只 up -d 沒有用 印在傳單上的電話號碼，要改只能重印

    只存檔、不做右邊那一欄，等於沒改。 1001 的兩種可能原因裡，有一種就是這個（第 3 節）。

    時間 發生什麼 事後回頭看

    17:00 前後 填了 HD_PUBLIC_API_URL、CORS_ORIGINS 等三項位址 填了什麼沒有記下來（照規定值不寫進文件，但「用名稱還是 IP」應該記）。1005 補記：用的是名稱
    之後 建置（build）、建資料庫、啟動，health 正常 這時網頁裡已經寫死了一個後端位址
    17:45 問：「能不能用 localhost 開護理端？」 實際部署用 localhost 開，一定登不進去（1.2 節表格第二列）
    17:47 問：「hd-server 要照寫，還是寫我的主機名稱？」 hd-server 是手冊範例，不是要填的值。這一問表示範例可能被照抄過
    17:5x 按下登入，出現 Failed to fetch —

    離院 未解。三個服務留在主機上繼續跑 登入不通，所以目前沒有人能用它

    3. 直接原因：放行名單裡沒有護理端¶

    3.1 現場那三條指令說了什麼¶

    指令在問什麼 結果 白話
    第一條：.env 裡的 CORS_ORIGINS、HD_PUBLIC_API_URL 寫了什麼 沒有帶回來 不知道
    第二條：用 <主機>:13000 連後端的 health {"status":"ok",…} 後端活著，用這個位址找得到它 ✓
    第三條：假裝自己是 http://<主機>:18080 來的網頁，問後端收不收 什麼都沒印出來 後端不收 ✗

    第三條如果後端收，會印出一行 Access-Control-Allow-Origin: http://<主機>:18080（意思是「我收這個來源」）。沒印出來就是不收。 光這一條就足以讓登入出現 Failed to fetch。

    3.2 為什麼不收：兩種可能¶

    可能 A：名單寫錯 可能 B：名單是對的，但後端還在用舊的
    怎麼回事 CORS_ORIGINS 寫的不是 http://<主機>:18080。例如照抄了範例的 hd-server、寫成 localhost、名稱和 IP 混用、埠寫錯 改過 .env，但改完沒有 up -d（1.3 節），執行中的後端拿的還是改之前的名單
    指向它的線索 17:47 問過「hd-server 要照寫嗎」 <主機> 是現場邊問邊決定的，中途改過值並不意外
    怎麼修 改對 .env，然後 up -d 直接 up -d

    兩種的修法最後都是「改對 → up -d → 再打一次第三條，直到它印出 Access-Control-Allow-Origin」，所以下一次就算還是分不出來，也修得好。 但分得出來，才知道手冊哪裡要再改，所以下一次動手之前先抄下三樣東西（E-06）。

    💡 一個第十五冊還沒收進去的查法：後端每次啟動，日誌裡都會印一行「允許的前端來源：…」，那就是執行中的後端手上那份名單 （程式在 apps/api/src/main.ts）。拿它和 .env 的 CORS_ORIGINS 比一下：

    Select-String -Path $cfg -Pattern '^CORS_ORIGINS='
docker compose --env-file $cfg logs api | Select-String '允許的前端來源'
    兩行比起來 是哪一種
    兩邊一樣，但都不是 http://<主機>:18080 可能 A：名單寫錯
    .env 是對的，日誌裡最後一行還是別的值 可能 B：改完沒 up -d
    兩邊一樣，而且都是 http://<主機>:18080 名單沒問題，問題在網址列或網頁裡的後端位址（3.3 節）

    日誌裡若有好幾行，看最後一行（最近一次啟動）。逗號分開的多個來源，日誌裡會用頓號「、」隔開。

    3.3 名單修好之後，還有兩個坑¶

    現場只查到名單就離院了，下面兩件事還沒驗過。名單修好之後照樣可能 Failed to fetch：

    坑 為什麼會登不進去 怎麼確認
    瀏覽器網址列上的網址不對 17:45 問過能不能用 localhost 開。網址列是 localhost，名單上是 <主機>，對不上（1.2 節） 一律開 http://<主機>:18080，在主機上開也一樣
    網頁裡寫死的後端位址是舊的 若是先 build、之後才改了 .env 的 HD_PUBLIC_API_URL，網頁還在連舊位址（1.3 節） 第十五冊 V-17 第二段的前兩條：.env 裡的位址與網頁裡實際的位址要一模一樣

    4. 根本原因：為什麼會走到這一步、為什麼當場解不開¶

    「名單寫錯了」只是表面。真正要改的是讓名單一開始就不會寫錯、寫錯了在開發機就會發現、在現場發現了也解得開。 1001 這幾道防線都破了：

    # 破口 白話 依據 已經補上的 還沒做的
    R1 主機位址沒在進院前定下來 「護理站與平板用哪個名稱或 IP 連主機」這一題，進院前寄給資訊室的問題清單裡根本沒有，現場只好自己決定 M-04 第十一冊 W-03 補一列、Q-27 補第 12 題；第十五冊新增 V-08「決定主機位址」，排在填 .env 之前 資訊室還沒有答覆（E-01）
    R2 範例長得像真的名字 第十四冊之一的範例一律寫 hd-server，第一次做的人分不出那是範例還是要照抄的值 M-04 第十五冊之一的範例改寫成 <主機>，填完多一條「有沒有照抄範例」的檢查 deploy/hospital.env.example 與 docker-compose.yml 的註解裡還寫著 hd-server 當例子（M-12 第 14 項，待決定）
    R3 開發機上的模擬部署練不到這種錯 第十四冊之二的模擬部署三個位址都用 localhost，網址列與名單永遠一致，所以這種錯在開發機上永遠不會出現，第一次見到它就是在醫院 M-12 第 13 項 第十五冊之二改用開發機的區網 IP，並要求故意用 localhost 開一次、親眼看過 Failed to fetch 還沒照第十五冊之二做過一次（E-02）
    R4 查法是當場才寫的 Failed to fetch 怎麼查，1001 以前手冊裡沒有；是在現場出事之後，開發端才邊問邊寫進附錄 M-01 查法併進第十五冊 V-17 的四段步驟與附錄 印出來帶進去（E-03）
    R5 少抄了一條結果 三條指令只帶回第二、三條，第一條（名單寫了什麼）沒帶回來，回來之後分不出是可能 A 還是 B M-10 第十五冊附錄寫明「三條全部抄進演練紀錄，包括正常的」 下一次動手前先抄（E-06）

    另外一條流程上的破口，這次沒有造成登入失敗，但同樣要守住：

    # 破口 白話 依據 下一次
    R6 帶進院的版本沒先模擬部署過 v0.3.0 是出發前才打的 tag，沒有先在開發機照手冊走一次。這次的問題剛好都不是程式的問題，那是運氣 第十四冊之四 1.1 節、M-15 E-02

    為什麼說「當場解不開」不全是現場的錯：R1～R4 都是出發前就該補好的。現場的人照當時的手冊做，手冊沒寫的題目（主機位址）、 沒寫的查法（Failed to fetch），本來就只能在現場臨時處理。這一冊的第 5 節大部分是出發前要做的事，就是這個原因。

    4.1 同一天的其他問題（沒有造成登入失敗，但下一次要處理）¶

    問題 白話 現況 詳見
    主機原本沒有 Git 現場自己裝了。手冊規定實際部署要請資訊室裝，誰裝的、資訊室同不同意沒有記 要補問 M-02、V-04
    防毒排除清單是空的 資料庫所在的位置正被 Windows Defender 即時掃描，會造成不定時、很難重現的錯誤 未處理，要交資訊室。加上之前不得輸入真實病人資料 M-05、V-05
    Docker 三次查不到 Docker Hub 的網域 下載映像檔時出現 no such host，時好時壞；同一條指令再打一次就過了 第十五冊 V-06 改成建置前先 docker pull 測一次 M-06、V-06
    根目錄放在 C 槽 實際放 C:\hd\hd-tablet-care，手冊原本寫 D 槽 院方同不同意待確認 M-03、V-09

    5. 下一次要做什麼¶

    照順序做。標「出發前」的沒做完不要出發。

    5.1 出發前¶

    # 做什麼 為什麼 怎麼知道做完了
    E-01 拿到資訊室對「護理站與平板用哪個名稱或 IP 連主機」的書面答覆（Q-27 第 12 題）；用 IP 的話，問能不能固定。1007 已答：用 IP，IP 是固定的；護理站與平板的網段連不連得到，照第十五冊之四 T-01 第 2、3 題確認 R1。這個值就是放行名單、網頁裡的後端位址、平板憑證要用的那一個，之後不能再換 演練紀錄寫下「<主機> 用的是名稱／IP，由＿＿確認」
    E-02 要帶進院的 tag，先照第十五冊在開發機模擬部署一次，三個位址用開發機的區網 IP（第十五冊之二）；V-17 登入成功之後，故意用 http://localhost:18080 開一次、按登入，親眼看一次 Failed to fetch R3、R6。在醫院第一次看到這個錯是最貴的 演練紀錄有這一輪的紀錄，包括那次故意的 Failed to fetch
    E-03 印出第十五冊、第十五冊之一、這一冊帶進去，V-17 與附錄那幾頁一定要有 R4 紙本在包包裡
    E-04 確認下一次帶的是不是 v0.3.0。1005 已經有新的程式改動（含資料庫結構），若帶新的 tag，那是一次更新，照第十一冊 W-19 換版，不是重新 clone 第十五冊 0.5 節 決定好帶哪個 tag，而且它做過 E-02

    5.2 進院當天，前三十分鐘¶

    # 做什麼 為什麼 怎麼知道做完了
    E-05 照第十五冊 0.5 節，先確認服務還是 1001 離開時的樣子（tag、三個容器、兩個資料卷、金鑰備份、health） 中間可能有人動過、可能斷過電。不一樣就停手先問 0.5 節的表格每一列都對得上
    E-06 動手改任何東西之前，先抄下三樣：① .env 的 CORS_ORIGINS 與 HD_PUBLIC_API_URL、② 日誌最後一行「允許的前端來源」（3.2 節方框）、③ 網頁裡寫死的後端位址（V-17 第二段第二條） R5。這三樣能分出 1001 是可能 A 還是 B，改完就再也看不到了 三樣都抄進演練紀錄（值本身只寫演練紀錄，不寫進任何會上站的文件）
    E-07 照第十五冊 V-17 第二段修：網頁裡的位址與 .env 不一樣就 build ＋ up -d；名單不對就改 .env 再 up -d。改完打放行檢查那一條 第 3 節。E-01 的答覆是改用 IP 的話，這一項與 E-08 改照第十五冊之四 T-05～T-12 做（它包含重建、up -d、重簽伺服器憑證）。1005 使用者決定改用 IP：資訊室確認 IP 已固定，就走第十五冊之四；沒固定就照本列原本的修法，不換 放行檢查印出 Access-Control-Allow-Origin: http://<主機>:18080
    E-08 用 http://<主機>:18080 登入：先在主機上（第三段），再到護理站的電腦上（第四段）。不要用 localhost 3.3 節。主機連自己不經過防火牆，主機上登得進去不代表護理站登得進去 護理站的電腦登入成功，被要求改密碼
    E-09 登入通了才往下：V-18 備份與還原、V-19 重新開機、V-25～V-28 平板、V-29～V-30 AI 閘道、第 10.1 節冒煙測試與交接（第十五冊 0.5 節的表） 1001 卡在登入，後面全部沒做 —
    E-16 （1005 新增）探測院方透析清單 API：在 api 容器裡跑探測工具，只印結構、不印值；把輸出整段抄回來 1005 起院方 API 要取代護理師的手動輸入（《實作規格書》4.19），下機怎麼判定、床號長什麼樣都要親眼看一次。工具 1005 已在迭代 15 做好，指令在第十五冊 V-30a（位址當場輸入、不寫進 .env）；帶去的 tag 沒有這個工具就跳過，不要用瀏覽器或 curl 直接打（會把病人資料印在螢幕上） 演練紀錄有一段探測輸出；或寫下「沒帶工具，跳過」

    還是登不進去的話：

    情形 怎麼辦
    放行檢查印出來了、網頁裡的位址也對，主機上用正確網址仍 Failed to fetch 瀏覽器按 Ctrl＋F5 強制重新整理（舊網頁可能還留在瀏覽器裡），再試一次；仍不行就按 F12 → Network，再按一次登入，把請求送去的網址與錯誤原文抄下來
    主機上登得進去，護理站的電腦開不到頁面 防火牆或網段的問題，找資訊室，不要自己關防火牆
    護理站的電腦說找不到主機 <主機> 是名稱而護理站查不到，回 V-08，改用資訊室固定的 IP，照第十五冊之四換
    試了一小時仍然不通 停手。服務留著（登不進去，沒有人能用它），把 E-06 那三樣和上面每一步的結果、錯誤原文全部抄回來。不要改程式、不要自己開容器

    5.3 離院前¶

    # 做什麼 為什麼
    E-10 補齊 1001 空著的紀錄：~~<主機> 是名稱還是 IP~~（1005 補記：名稱）、V-05 的 Docker Desktop 四項設定、V-22 的三個 SHA-256（下載頁最下面抄得到）、0922 的容器有沒有收掉（第十四冊之三 L-01、L-07）、Git 是誰裝的 第十四冊之四 M-10
    E-11 防毒排除：請資訊室把 Docker 的資料夾加入 Defender 排除清單；加不了就寫下「誰、什麼時候加」 4.1 節。加上之前不得輸入真實病人資料
    E-12 每一步開始與結束各記一次時間，錯誤訊息抄原文、抄到最後一行 1001 只有一步有計時；JWT_SECRET 那次只回報了第一行，後面其實是下載失敗（M-07）

    5.4 回來之後¶

    # 做什麼
    E-13 照 E-06 抄回來的三樣，判斷 1001 是可能 A 還是 B，寫回這一冊第 3.2 節與第十四冊之四 M-01
    E-14 決定 deploy/hospital.env.example 與 docker-compose.yml 註解裡的 hd-server 範例要不要改成 <主機>（R2，docs/ 以外的檔案）
    E-15 3.2 節方框那條「允許的前端來源」的查法若在現場有用，收進第十五冊 V-17 第二段與附錄

    6. 一張紙帶進去¶

    只能帶一張紙的話，帶這張：

    1. <主機> 只有一種寫法，名稱或 IP 擇一，資訊室確認過的那一個。
    2. 瀏覽器一律開 http://<主機>:18080，不用 localhost。
    3. 改了 CORS_ORIGINS → up -d；改了 HD_PUBLIC_API_URL → build 再 up -d。 只存檔等於沒改。
    4. Failed to fetch ＝ 帳號密碼還沒被看過，先查名單和位址，不要先懷疑密碼。
    5. 放行檢查要印出 Access-Control-Allow-Origin，空的就是不收。
    6. 改之前先抄，抄原文、抄到最後一行。
    7. 登入通了才往下。
    8. 院方 API 只用探測工具看（E-16），不用瀏覽器或 curl 直接打——會把病人資料印在螢幕上。
