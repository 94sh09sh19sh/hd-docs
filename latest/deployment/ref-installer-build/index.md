## 摘要

- 第一部（`P-xx`，原建議時點 D-3）：終點是桌上有一份**可以交付的安裝包**，以及一張寫著版本與雜湊值的交付單；全在開發機上做、全程需要網路，凡是現場才會下載的都收進包裡（例如 Prisma 引擎）
- 第一部的節：確認要交付什麼（P1）→ 建置（P2）→ 驗收五項、看它失敗一次（P3）→ 交付單、開發端掃毒、隨身碟（P4）→ 練更新與回退、小抄、列印（P5）→ 完成條件（P6）；「可以交付」的定義在 P-11
- 第二部（`R-xx`，原建議時點 D-2）是彩排：在一台乾淨、斷網的機器上，把院內那一整套從頭到尾走一次，進院那天就不是第一次
- 第二部為什麼不能省：迭代 10 的安裝包在開發機上全綠，真的跑起來當場出現兩個缺陷（R0）
- 第二部的節：找乾淨機器（R1）→ 送包與驗收（R2）→ 模擬院內主機的設定（R3）→ 安裝與啟動（R4）→ 功能冒煙測試（R5）→ 更新與回退各一次（R6）→ 收尾（R7）→ 完成條件（R8）
- 最重要的一條：PWA 呼叫後端的位址是**建置時**寫進產物的，院內主機的位址要在建置前就知道（R-08 的警告框）；容器路線同樣如此（`HD_PUBLIC_API_URL` 改了要重建，見[《護理站登不進去與主機位址》](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-login/index.md)）

## 第一部 · 開發機準備與安裝包建置（`P-xx`）

> 這一部的終點是：桌上有一份**可以交付的安裝包**，以及一張寫著版本與雜湊值的交付單。「可以交付」有明確定義，見 P-11。

## P0. 開始之前

**這一部全部在開發機上做，全程需要網路。**

這是整條流程裡**唯一**允許連外的階段——安裝包之後的每一步（帶進院內、解壓、套用遷移、啟動）都必須在完全沒有網路的機器上做得完。所以凡是「現場才會去下載」的東西，都要在這裡收進包裡（最典型的是 Prisma 引擎，DEP-30）。

預計耗時：**60～90 分鐘**，其中建置與驗收約各 10 分鐘，其餘是檢查與抄寫。

## P1. 確認你要交付的是什麼

### P-01 確認 commit 與工作區乾淨

**做什麼**

```
git status --short
git log -1 --oneline
```

**怎麼知道成功了**

`git status --short` **沒有任何輸出**（工作區完全乾淨），`git log -1` 顯示的是你要交付的那一版。

**可能怎麼壞、怎麼處理**

| 症狀                        | 原因             | 處置                                                                                                                                                                                                |
| --------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `git status` 有一堆檔案     | 有未提交的改動   | **先 commit 或 stash**。工作區不乾淨時建出來的包，`VERSION.json` 的 `commitClean` 會是 `false`，而**正式交付的包不接受這個值**（P-08）。理由：那份包對應的程式碼在 git 上找不到，日後出問題無從對照 |
| 只有 `dist-package/` 有變動 | 上一次建置的產物 | 它已在 `.gitignore`，若出現在 `git status` 表示 gitignore 有問題，先查                                                                                                                              |
| 不確定現在在哪一版          | —                | `git log -5 --oneline` 看最近五筆。交付的應該是最新一筆迭代的 commit                                                                                                                                |

### P-02 確認執行期版本

**做什麼**

```
node -v
npm -v
```

**怎麼知道成功了**

`node -v` ≥ v20.11（開發機目前用 v24）。

**可能怎麼壞、怎麼處理**

| 症狀                         | 處置                                                                                          |
| ---------------------------- | --------------------------------------------------------------------------------------------- |
| 版本低於 20.11               | 升級 Node。`npm run check:offline` 會擋下（它檢查 `engines` 宣告）                            |
| 有多個 Node 版本（nvm 之類） | **建置用哪一版，包裡就帶哪一版的執行期**。確認你現在這個終端機裡的 `node -v` 就是你要的那一版 |

> **這件事會跟著進醫院**：安裝包裡的 `runtime/node.exe` 是從你這台機器複製過去的。你在這裡用的版本，就是院內主機上會跑的版本。

### P-03 確認相依套件是完整的

**做什麼**

```
npm install
npm run check:offline
```

**怎麼知道成功了**

`check:offline` 六項全部通過，結束狀態 0，**沒有任何「阻擋項」**。

**可能怎麼壞、怎麼處理**

| 症狀                             | 原因                                                                         | 處置                                                                                                        |
| -------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `Prisma 引擎目錄不存在`          | `node_modules` 是用 `--ignore-scripts` 裝的，或從別處複製而排除了二進位檔    | 刪掉 `node_modules`，重新 `npm install`（**不要加 `--ignore-scripts`**）。引擎約 40MB，由安裝後腳本另外下載 |
| `Prisma 版本沒有鎖死`            | `package.json` 寫成浮動的版本範圍                                            | 改成確定版本。引擎與 CLI 版本必須一致，浮動範圍會在某次重新安裝時悄悄換掉其中一邊（DEP-30 第 3 點）         |
| `npm install` 出現 EPERM／EACCES | Windows 三大原因：還有 node 行程開著、專案在雲端同步資料夾底下、防毒即時掃描 | 依序排除。詳見手動測試手冊 §01 的同名提示                                                                   |
| 建置產物不存在                   | 還沒跑 `npm run build`                                                       | 下一步就會做                                                                                                |

### P-05 五支盤點全部跑過

**做什麼**

```
npm run check:all
```

**怎麼知道成功了**

最後那張總表五支全綠：零院外連線、介面技術識別、介面設計基準、離線可部署性、遷移安全。

**可能怎麼壞、怎麼處理**

| 症狀                 | 原因                               | 處置                                                                                     |
| -------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- |
| 零院外連線有發現     | 程式或設定裡出現指向院外的網址     | **一定要清掉**。這是 FR-S07，也是這套系統能進院的前提                                    |
| 介面技術識別有發現   | 畫面上露出需求編號或列舉常數       | 不擋部署，但記下來                                                                       |
| 遷移安全有發現       | 新增的 schema 變更可能弄掉既有資料 | **擋部署**。到院內套用遷移時受害的是真實病人資料                                         |
| 五支裡有一支跑不起來 | 腳本本身壞了                       | 單獨跑那一支看錯誤。`check:all` 刻意讓每一支都跑完再一起算帳，不會因為其中一支失敗就停住 |

> **不要用「先跳過，之後再處理」的心態對待這裡的紅字。** 這五支擋下來的東西，到院內都會變成「起不來的服務」或「壞掉的資料」，而現場沒有人有能力當場修。

## P3. 驗收

### P-09 驗收五項

**做什麼**

```
npm run package:verify -- --dir dist-package/<安裝包目錄>
```

**怎麼知道成功了**

五項全綠：

1. 雜湊值逐檔核對（兩萬多個檔案）
1. 包內沒有設定檔、資料庫或備份（DEP-13）
1. 以**包內引擎**套用既有遷移到一個全新的資料庫（DEP-31）
1. 以**包內執行期**啟動三個行程並通過存活檢查
1. **全程沒有往院外的連線**（連線哨兵，有一筆就不得交付）

**可能怎麼壞、怎麼處理**

| 症狀                                       | 原因                            | 處置                                                                                         |
| ------------------------------------------ | ------------------------------- | -------------------------------------------------------------------------------------------- |
| 第 3 項倒在 `ENOTFOUND binaries.prisma.sh` | 引擎沒指好                      | 這正是 DEP-30 要擋的。確認 `engines/` 裡兩個檔案都在，且 `PRISMA_ENGINES_DIR` 有被啟動器帶上 |
| 第 4 項起不來，說「找不到專案根目錄」      | 迭代 10 修掉的缺陷 1 復發       | 確認你建的是修正後的版本（迭代 10 之後）                                                     |
| 第 4 項說連接埠被佔用                      | 開發機上還有 `npm run dev` 在跑 | **先把它停掉**再驗收                                                                         |
| **第 5 項有連線紀錄**                      | 有東西在偷連外                  | **不得交付。** 看哨兵記下的主機名稱是誰，回去 `npm run check:egress` 對照                    |

### P-10 讓驗收腳本失敗一次

**做什麼**

在包裡隨便一個檔案尾端加一個字（例如 `安裝說明.md`），再跑一次 P-09。

**怎麼知道成功了**

**為什麼要做這一步**

**每一個檢查都要有人看過它失敗的樣子。** 沒看過失敗，你不知道它是真的在檢查，還是永遠回傳綠色。到了院內，這支腳本是你唯一能判斷「帶進來的包有沒有在路上壞掉」的工具。

## P4. 交付單與掃毒

### P-11 寫交付單

**做什麼**

拿一張紙（或一個檔案，但**最後要印出來**）寫下：

| 欄位                       | 值                                   |
| -------------------------- | ------------------------------------ |
| 安裝包檔名                 | `hd-tablet-care-<版本>-<commit>.zip` |
| 版本 / commit              |                                      |
| 建置時間                   |                                      |
| `commitClean`              | **必須是 true**                      |
| 壓縮檔 SHA-256             |                                      |
| `CHECKSUMS.txt` 的 SHA-256 |                                      |
| 包內執行期版本             |                                      |
| 檔案數 / 大小              |                                      |
| 建置者 / 建置機器          |                                      |

**「可以交付」的定義**：P-01 到 P-10 全部通過，且 `commitClean` 為 `true`。少一項都不算，不要用「應該沒問題」補上去。

> 雜湊值為什麼要寫在紙上：院內那台機器沒有網路，你不能傳訊息給自己。而且**核對雜湊的目的就是懷疑手上的檔案**——把它存在同一支隨身碟裡，等於沒有核對。

### P-12 開發端掃毒（DEP-26 第一次）

**做什麼**

用開發機上的防毒軟體，對**壓縮檔**與**解壓後的整個目錄**各掃一次。

**怎麼知道成功了**

**可能怎麼壞、怎麼處理**

| 症狀                                          | 原因                         | 處置                                                                                                 |
| --------------------------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| 報出可疑檔案，多半在 `runtime/` 或 `engines/` | 未簽章的執行檔常被啟發式判定 | **不要直接排除了事**。記下是哪一個檔案、判定名稱是什麼——院內掃描站十之八九也會報同一個，先準備好解釋 |
| 掃描要很久                                    | 包有 2 萬多個檔案            | 預留時間。順便記下耗時，院內要用它估掃描站要站多久（Q-29 第 4 題）                                   |
| 防毒把檔案直接刪掉了                          | 即時防護                     | **整包重做，並把 `dist-package/` 加進排除清單**。被刪過的包雜湊一定對不上                            |

### P-13 準備隨身碟

**做什麼**

1. 找一支**專門為這件事準備的**隨身碟，先完整格式化
1. 只放兩樣東西：**安裝包壓縮檔**、`scripts/verify-package.mjs`
1. 不要放任何其他東西——不是舊版本、不是筆記、不是別的專案的檔案

**怎麼知道成功了**

隨身碟裡只有兩個檔案，掃一次毒是乾淨的。

**可能怎麼壞、怎麼處理**

| 症狀                            | 處置                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------- |
| 院方規定要用院方發放的加密碟    | 這是 Q-29 第 1 題，**D-14 就要問**。問不到就兩種都準備                          |
| 隨身碟容量不夠（壓縮檔數百 MB） | 用 8GB 以上的                                                                   |
| 想順便放點別的東西「以防萬一」  | **不要。** 隨身碟是單向的（DEP-28），碟上每多一個檔案，離院時就多一件要解釋的事 |

## 第二部 · 開發端的測試部署（`R-xx`）

> 這一部做的是**彩排**：在一台什麼都沒有的機器上，把院內那一整套從頭到尾走一次。終點是——你已經做過一次，所以進院那天不是第一次。
>
> 0926 起現行的開發機演練不再照這一部：容器路線的演練照各進院冊的 🧪 標記與[《從零部署本系統之一：容器路線的原冊》](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-fresh-install-detail/index.md)第 7 節。

## R0. 為什麼這一步不能省

迭代 10 在開發機上建好安裝包、所有靜態檢查全綠之後，**把它真的跑起來，當場出現兩個缺陷**：

| #   | 症狀                               | 真正的原因                                                                    |
| --- | ---------------------------------- | ----------------------------------------------------------------------------- |
| 1   | 後端起不來，說「找不到專案根目錄」 | 資料庫路徑檢查往上找帶 workspaces 的 `package.json`，**安裝包裡沒有那個東西** |
| 2   | 套用遷移時找不到 Prisma CLI        | 指令外套只認得開發機的兩種版面，**安裝包的版面少一層**                        |

**兩個都不是設定寫錯，是「開發機的版面與安裝包的版面不一樣」**——而所有靜態檢查都只看得到前者。

這就是 DEP-22 的意思：**在開發機上解壓來測，測到的是開發機，不是安裝包。**

預計耗時：**半天**。第一次做會更久，而那正是它的價值——這些時間你遲早要花，在自己家裡花比在醫院裡花便宜得多。

## R1. 先找一台「乾淨」的機器

「乾淨」的定義：**沒有開發環境、沒有全域安裝的 Node.js、沒有這個專案的任何殘留。**

沒有第二台實體機也有替代品，但**可信度差很多**，要知道自己在用哪一種：

| 方案                                             | 可信度 | 說明                                                                            |
| ------------------------------------------------ | ------ | ------------------------------------------------------------------------------- |
| **另一台實體 Windows 機器**                      | ★★★    | 最接近院內主機。借一台、或用家裡那台不寫程式的                                  |
| **全新安裝的 Windows VM**（Hyper-V／VirtualBox） | ★★★    | 幾乎等價，而且可以照快照重來。**強烈建議用這個**                                |
| 同一台機器上新增一個本機使用者帳號               | ★      | **驗不到 DEP-22**：Node.js 裝在系統層，新帳號一樣看得到它。只能拿來驗權限那幾項 |
| 開發機上直接解壓來測                             | ✗      | **不算數**。這正是 DEP-22 明文要擋的                                            |

> **建議做法**：開一台 Windows VM，裝完系統之後**先拍一個快照**。每練一次就還原快照，你可以練很多次，而每一次都是真正的「第一次安裝」。

### R-04 解壓並核對雜湊（DEP-27）

**做什麼**

```
Expand-Archive -Path C:\hd\hd-tablet-care-<版本>-<commit>.zip -DestinationPath C:\hd\hd-tablet-care-<版本>-<commit>
cd C:\hd\hd-tablet-care-<版本>-<commit>
Get-FileHash -Algorithm SHA256 .\CHECKSUMS.txt
```

壓縮檔裡**沒有最上層資料夾**，所以 `-DestinationPath` 一定要寫到有版本號的那一層，不能只寫 `C:\hd\`。

拿輸出的雜湊值與[交付單](#p-11-%E5%AF%AB%E4%BA%A4%E4%BB%98%E5%96%AE)上那一個逐字對照。

**怎麼知道成功了**

兩串完全相同。**逐字比對，不要只看頭尾四碼。**

**可能怎麼壞、怎麼處理**

| 症狀                                                                           | 原因                                              | 處置                                                                                                                                     |
| ------------------------------------------------------------------------------ | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **雜湊不一樣**                                                                 | 檔案在路上壞了，或被防毒動過手腳，或你拿錯版本    | **停下來。** 重新複製一次再比。還是不一樣就回開發機整包重做。不要「應該只是小問題」硬著頭皮往下                                          |
| `cd` 說找不到路徑，`C:\hd\` 底下直接出現 `runtime`、`CHECKSUMS.txt` 等一堆檔案 | 解壓目的地只寫了 `C:\hd\`，壓縮檔沒有最上層資料夾 | 把 `C:\hd\` 底下除了壓縮檔與 `verify-package.mjs` 以外的東西刪掉，照上面的指令重解一次。**不要用搬的**，搬漏一個檔案就要到 R-05 才會發現 |
| 解壓很慢或失敗                                                                 | 2 萬多個檔案                                      | 正常會花幾分鐘。失敗就看磁碟空間                                                                                                         |
| `Expand-Archive` 說路徑太長                                                    | Windows 的路徑長度上限                            | **把解壓目的地換成很短的路徑**（例如 `C:\hd\`），不要放在桌面底下好幾層。這一條在院內一樣會遇到                                          |

### R-06 決定三個目錄

**做什麼**

| 用途           | 這次演練用                                                  | 院內要填什麼                               |
| -------------- | ----------------------------------------------------------- | ------------------------------------------ |

| 想法                                     | 為什麼不行                                                                                                                                   |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 「資料庫放在安裝包裡比較好找」           | 某一次「把舊資料夾整個刪掉再解壓新版」就會把資料庫一起刪掉。**這種事不會發生在第一次更新，會發生在第五次、由另一個人執行的那一次**（DEP-08） |

| 「用網路磁碟機的代號，反正看起來像本機」 | 看起來像本機，行為是網路檔案系統。**後端會拒絕啟動**，這是《資料庫使用規範》7.2 明文要擋的                                                   |

| 不知道院內主機位址          | **Q-27 沒問到**            | 見下方的警告框                                                                      |

> ### ⚠ 位址必須在建置安裝包之前就知道
>
> **兩個 PWA 呼叫後端的位址是在建置時寫進產物裡的**（`VITE_API_BASE_URL`），不是啟動時才讀的。預設值是 `http://localhost:3000`——在護理站那台電腦上開啟護理端時，`localhost` 指的是**那台電腦自己**，不是主機。
>
> 也就是說：**院內主機的位址必須在 [P-04](#p-04-%E5%BB%BA%E7%BD%AE%E4%B8%89%E5%80%8B%E7%94%A2%E7%89%A9) 建置之前就決定**，建置前把 `VITE_API_BASE_URL=http://<院內主機>:<API_PORT>` 填進開發機的 `.env` 再 `npm run build`。
>
> 這件事與憑證的主體別名是同一個位址（K-01，在[《安裝包路線（歷史）》](https://94sh09sh19sh.github.io/hd-docs/latest/deployment/ref-installer/index.md)），**兩邊必須一致**。
>
> **R-13 就是專門用來抓這個問題的**：一定要從另一台機器連進來測，不要只在主機本機上開。位址到現場才知道的話，唯一的補救是帶著開發機進院重新產生安裝包——那要先確認院方允許外來筆記型電腦接上院內網路（Q-29）。
