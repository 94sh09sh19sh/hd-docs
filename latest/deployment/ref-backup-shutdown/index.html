    備份、還原與關服務¶

    • 狀態：現行（常備參考）。備份、還原驗證、把服務關乾淨（暫停、停用、撤除）都照這一份；要印出來帶進去
    • 1117 由舊的第八冊（把服務關乾淨，全部）與舊第十一冊第 8 節（容器版的關服務指令）改寫；第 1 節收舊第十一冊 W-17、舊第十五冊 V-18、舊第十八冊 J-22、舊第二十三冊 SY-06 共通的「備份一次、證明還原得回來」
    • 編號：S-xx（沿用第八冊）。0926 起現行路線是容器（docker compose）；第八冊原文的排程工作 HD-TabletCare、service-*.ps1 是安裝包路線（歷史），保留在各步的「安裝包（歷史）」
    • 分成兩份（1118 拆，每份 300 行內）：本份是第 0～2 節（關乾淨的判準與三種深度、備份與還原、S-01～S-02 關之前）；《備份、還原與關服務（第 2 份，第 3～6 節，S-03～S-09）》是三種深度的做法（暫停 S-03～S-04、停用 S-05、撤除 S-06～S-09）與關完要寫下來

    摘要¶

    • 「關乾淨」有四條判準，四條都成立才算數，指令印出「已停止」不算（第 0 節）
    • 三種深度：暫停 docker compose stop、停用 docker compose down、撤除（再刪資料卷、映像檔、目錄）；三種都不刪資料庫與備份，資料去向是院方的決定；拿不定主意選停用
    • 備份：每天 03:00 自動一份、護理端可「立即備份」，都在 $root\backups，旁邊同名 .sha256 是完整雜湊；「有備份」和「備份能用」是兩件事，照第 1.2 節還原到測試檔驗證
    • 關之前先告訴病房（S-01）：停機期間求助按鈕通知不到護理站，這是唯一會直接傷到病人的情形；再確認要關的是哪一個（S-02）
    • 三種深度的做法（S-03～S-09）與關完要寫下來（第 6 節）在第 2 份

    0. 先講結論¶

    《進院通則》的當場停手、《現場疑難排解》X-36 的撤退、《第一次進院（0922）· 部署本系統之三：進院當天詳細版》第 10 節的「隨時可以停手」都說「把服務停掉」，怎麼停、停到什麼程度、怎麼證明真的停了，寫在這一份。會用到它的情形不只撤退：備份與還原、資料修補、換版（安裝包時代是《安裝包路線之五：建置與開發端彩排》R-20 第 1 步）、主機維護與重新開機、試用結束要撤除，都要先關服務（容器路線的換版與退回只停 api，見《本系統換版與退回》）。

    開工三行（＝《從零部署本系統》V-09）：

    $root = "C:\hd\hd-tablet-care"
$cfg  = "$root\config\.env"
cd $root\repo

    🧪 第一行改成 $root = "C:\hd-sim"。

    0.1 「關乾淨」的四條判準¶

    # 容器路線（現行） 安裝包（歷史） 為什麼要看這一條
    1 docker compose ps 沒有任何 hd-tablet-care 的容器在跑 排程工作 HD-TabletCare 不是 Running 還在跑的東西會把服務重新帶起來
    2 沒有一次性容器（換版、還原、資料取出的 run --rm）還在跑 本安裝包底下的 node.exe 行程是 0 個 排程工作停的只是啟動器，三個子行程要另外確認（原為 DEP-12 的落實方式，DEP-12 已於 0926 作廢）
    3 三個連接埠（13000、18080、18081）沒有任何行程在聽 三個連接埠（API_PORT、NURSE_PORT、PATIENT_PORT）沒有行程在聽 名稱對不上時的第二道確認
    4 沒有任何容器掛著資料卷 hd-tablet-care-data 資料庫檔案可以被獨占開啟 這一條才是備份與還原真正在乎的：還有人開著它，備份就是在一個還在被寫入的檔案上做的（DEP-10）

    容器路線這四條的指令（S-04）是 1117 依 docker-compose.yml 改寫的，院內與開發機都還沒照這四條跑過；第一次用時把輸出抄回來。

    0.2 三種深度，先想清楚要哪一種¶

    深度 容器路線 安裝包（歷史） 重新開機後 什麼時候用
    一、暫停 docker compose --env-file $cfg stop；資料不動 停掉行程 容器路線：不會自己起來（restart: unless-stopped 把手動停的容器當成不要再啟動）；安裝包：會自己起來（排程工作的觸發條件是開機時） 備份、還原、資料修補、換版
    二、停用 docker compose --env-file $cfg down；資料不動，資料卷是 external，down -v 也刪不掉 暫停＋停用排程工作 不會起來，要手動恢復 主機維護、系統更新要重新開機；《進院通則》的當場停手撤退；問題查清楚前不准再有人用
    三、撤除 停用＋刪資料卷、映像檔、主機上的目錄（S-08）；刪了就沒有了 停用＋移除排程工作與主機上的設定 不會起來，也沒有東西可以恢復 試用結束、院方書面要求移除
    • 三種深度都不刪資料庫與備份。 病人資料的去向是院方的決定，不是部署的人在現場的決定。撤除也一樣：資料交給院方，由院方決定留存或銷毀（S-09）
    • 拿不定主意時選「停用」。 停用多做的只有一行指令，恢復也只要一行；安裝包時代的暫停會在下一次重新開機時，讓一個你以為關掉的系統悄悄回來，而護理師會開始用它
    • 容器路線的暫停與停用，重新開機後目前都不會回來；差別是 down 連容器與網路一起刪掉，誰都不會誤按「啟動」把它帶起來。下一個 tag 預定改 compose 的 restart（舊第二十四冊 SY-M4 例外）：改成 always 的話，stop 之後 Docker 一重新啟動容器就會回來，那時要它不回來一定用 down
    • docker compose down 只關得到 hd-tablet-care 這個專案（專案名稱寫死在 compose 檔裡，DEP-37 第 1 項）。不要用 docker stop $(docker ps -q) 這種會關到同機別人容器的寫法

    1. 備份與還原¶

    1.1 備份在哪裡、怎麼來的¶

    備份 怎麼來的 檔名
    每日排程 後端每天 BACKUP_DAILY_AT（預設 03:00）自動做一份 hd-backup-<時間>.db
    立即備份 護理端 系統管理 →「立即備份」 同上
    更新前備份 換版時 db-update 自動做（《本系統換版與退回》W-19 ④） hd-before-update-<時間>.db
    金鑰備份 shell-builder keys-backup（《平板與外殼 App》） keys\hd-keys-<時間>.tar.gz
    • 都在 $root\backups（.env 的 HD_BACKUP_DIR，容器裡是 /backups）。資料庫本身在具名資料卷 hd-tablet-care-data，檔案總管看不到它是正常的；備份資料夾是資料卷裡的資料庫唯一看得見的出口
    • 每一份 .db 旁邊有同名的 .sha256（<檔名>.db.sha256），前半段那 64 個字就是完整雜湊；畫面上的備份歷程只顯示前 12 碼。護理端 稽核軌跡（動作選「資料庫線上備份」）的說明欄也有完整的一份
    • 檔名裡的時間是 UTC（結尾的 Z），比台灣時間少 8 小時：下午 3 點的備份檔名是 …T07…
    • 備份是線上做的（VACUUM INTO），服務在跑時就能備份，不必先停
    • 備份只放在同一台主機，主機壞了就一起沒了：院方的備份軟體從這個資料夾（連同 keys\）送往院內另一台機器（DEP-06），.sha256 要跟著一起送。由誰送、多久送是資訊室的事，答不出來就寫進交接的「已知限制」（1116 時還沒問到，見《院內主機現況與未完成事項》）
    • 看排程備份有沒有在跑：Get-ChildItem $root\backups -Filter *.db | Measure-Object。0 份 → 排程備份沒在跑，記下來（主機每天晚上可能都關機）

    1.2 備份一次，並證明還原得回來¶

    從零部署（V-18、W-17）、每一次換版之後、撤除前（S-06）都做這一段。「有備份」和「備份能用」是兩件事（規範 8.1）。

    做什麼

    1. 護理端 → 系統管理 →「立即備份」。列出最新的檔名直接複製（下面的 <檔名> 都是含 .db 的整個檔名），再讀完整的雜湊：
    Get-ChildItem $root\backups\hd-backup-* | Sort-Object LastWriteTime | Select-Object -Last 2 Name
Get-Content "$root\backups\<檔名>.sha256"
    1. 還原到資料卷裡的一個測試檔、跑完整性檢查，再刪掉測試檔（第一條是一整行，一律用 PowerShell）：
    docker compose --env-file $cfg run --rm --no-deps api node_modules/.bin/ts-node --project apps/api/tsconfig.json apps/api/scripts/restore-backup.ts --from /backups/<檔名> --to /data/restore-check.db --sha256 <雜湊>
docker compose --env-file $cfg run --rm --no-deps --entrypoint rm api /data/restore-check.db
    1. 🏥 問資訊室：備份資料夾（連同 keys\）由誰、多久送往院內另一台機器。🧪 跳過，做到還原成功即可

    成功：第 2 步印出 [1] 備份檔：…、[2] SHA-256：…、✓ 與備份歷程上的紀錄相符、[3] 已複製為 restore-check.db、[4] 完整性檢查：ok 與各資料表筆數（護理端帳號、病人、稽核紀錄、功能開關、備份歷程）；$root\backups\ 裡看得到那個檔和同名的 .sha256。

    最後一行 [5] 下一步：把 .env 的 DATABASE_URL 改為 file:<剛才 --to 的路徑>，再啟動後端（npm run dev:api）。 是寫給開發機的，主機上不理它：容器裡的 DATABASE_URL 固定是 file:/data/hd.db，這一步只是驗證。

    服務起不來、打不開備份歷程時：備份歷程與稽核軌跡都存在資料庫裡，打不開網頁就看不到。直接看資料夾，Get-ChildItem "$root\backups\*.db" | Sort-Object LastWriteTime 最後一個是最新的備份，雜湊在它旁邊的 .sha256。

    症狀 處置
    還原中止：找不到備份檔 … 檔名打錯（要含 .db），或用了 Git Bash：Git Bash 會把 /backups/… 改寫成 Windows 路徑。非用不可時先 export MSYS_NO_PATHCONV=1，--env-file 寫成 C:/…
    還原中止：SHA-256 與備份歷程上的紀錄不符，備份檔可能已損毀或被更動 雜湊抄錯；用 Get-Content 那一條重新複製。還是不符就打電話給開發端
    還原中止：目的檔 restore-check.db 已存在；還原不覆蓋任何既有檔案，請換一個路徑 上一次的測試檔沒刪，先打第 2 步的第二條再重來
    刪測試檔那一條印「No such file」 前一條沒寫出測試檔，看前一條的錯誤原文
    還原中止：完整性檢查未通過：… 那份備份壞了。換前一天的再驗一次，兩份都壞就打電話給開發端

    1.3 從備份把正本換回來¶

    • 換版之後要退回：照《本系統換版與退回》W-20
    • 同一版、正本壞掉或不見了（《現場疑難排解》X-15）：照 W-20 第 2 步的四條指令（停 api、把 hd.db 三個檔移到 /data/before-rollback/、還原、up -d），不 git checkout、不改 HD_IMAGE_TAG。那份備份之後寫進去的資料會消失；先打電話給開發端再做
    • hd.db 與它的 -wal、-shm 是一組，要搬、要備份，三個一起（DEP-09）

    1.4 金鑰備份¶

    院內 CA、伺服器憑證、APK 簽章金鑰在資料卷 hd-tablet-care-keys，遺失即無法補救（DEP-35）。備份與驗證照《平板與外殼 App》Y-06，遺失時的還原在同一份第 7 節；1116 時 backups\keys 有兩份（1001、1029）。金鑰備份裡有私鑰，不得出院、不得寄給開發端。

    2. 關之前¶

    S-01 先告訴病房¶

    做什麼：找護理長或當班的負責護理師，講清楚四件事：

    1. 什麼時候開始停、預計停多久
    2. 停機期間照原本的紙本流程做，恢復之後要不要補登由護理長決定
    3. 病人平板上的「求助」按鈕停機期間通知不到護理站——平板會告訴病人「目前無法即時通知護理站」，但護理師要知道這件事，改用床邊的原有叫人方式
    4. 症狀回報會先存在平板上，恢復連線後自動補傳，不必重填（撤除的情形例外，見 S-07）

    成功：對方複述得出「幾點到幾點、這段時間用紙本、求助按鈕沒用」。

    症狀 處置
    正在透析班次中，找不到空檔 能等就等到班次之間。 不能等（例如資料有問題必須立刻停）就停，但一定要先講完第 3 點
    「停一下而已，不用講吧」 要講。求助按鈕沒有反應、而護理師不知道，是這一份裡唯一會直接傷到病人的情形
    找不到任何護理人員可以告知 寫在紙上貼在護理站，並記進紀錄。不要默默停

    首波開始使用之前（1116 時平板還沒指派病人），沒有病人在用平板，第 3、4 點講一句就好，第 1、2 點照講。

    S-02 確認要關的是哪一個，先看一眼¶

    做什麼（容器路線）：

    docker compose --env-file $cfg ps -a
docker ps --format "{{.Names}}  {{.Image}}  {{.Status}}"

    成功：第一條只列 hd-tablet-care- 開頭的容器（api、nurse-web、patient-web，有做 AI 閘道的話還有 ai-gateway），抄下來，這是停之前的樣子；第二條另外列出的容器是同機別的專案的，抄下名字，不要動。

    症狀 處置
    failed to connect to the docker API at npipe:… Docker Desktop 沒開，服務本來就不在跑。照 S-04 確認就好
    有 hd-tablet-care-api-run-… 這種名字的容器 有一次性容器（換版、還原、資料取出）還在跑。等它跑完，或問是誰開的；不要直接關

    安裝包（歷史）：以系統管理員身分開 PowerShell（安裝包的每一步都需要；開不了就請資訊室的人來，或由他操作、你在旁邊唸）：

    cd C:\hd\hd-tablet-care-<版本>-<commit>
.\scripts\service-status.ps1
Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" | Select-Object ProcessId, CommandLine | Format-List

    service-status.ps1 列出排程工作、執行身分、行程數，抄下來；清單裡的每一個 node.exe 都說得出是誰的，本系統的三個命令列裡都有這一包的路徑。清單裡有別的專案的 node.exe、命令列裡剛好有 dist\main.js、static-server.js 或 run-all.mjs：不要跑 service-stop.ps1（它靠命令列裡的這幾個字串找行程，會把別人的一起收掉），改走 S-03 的「共用主機」做法。主機上有兩包本系統（新舊版並存）：只有一包該有行程在跑，service-status.ps1 在正在跑的那一包底下執行。
