    第一冊 · 開發機準備與安裝包建置¶

    版本：v0.1　文件狀態：草案　編號：P-xx　建議時點：D-3

    這一冊的終點是：桌上有一份可以交付的安裝包，以及一張寫著版本與雜湊值的交付單。 「可以交付」有明確定義，見 P-11。

    0. 開始之前¶

    這一冊全部在開發機上做，全程需要網路。

    這是整條流程裡唯一允許連外的階段——安裝包之後的每一步（帶進院內、解壓、套用遷移、啟動） 都必須在完全沒有網路的機器上做得完。所以凡是「現場才會去下載」的東西，都要在這裡收進包裡 （最典型的是 Prisma 引擎，DEP-30）。

    預計耗時：60～90 分鐘，其中建置與驗收約各 10 分鐘，其餘是檢查與抄寫。

    1. 確認你要交付的是什麼¶

    P-01 確認 commit 與工作區乾淨¶

    做什麼

    git status --short
git log -1 --oneline

    怎麼知道成功了

    git status --short 沒有任何輸出（工作區完全乾淨），git log -1 顯示的是你要交付的那一版。

    可能怎麼壞、怎麼處理

    症狀 原因 處置
    git status 有一堆檔案 有未提交的改動 先 commit 或 stash。工作區不乾淨時建出來的包，VERSION.json 的 commitClean 會是 false，而正式交付的包不接受這個值（P-08）。理由：那份包對應的程式碼在 git 上找不到，日後出問題無從對照
    只有 dist-package/ 有變動 上一次建置的產物 它已在 .gitignore，若出現在 git status 表示 gitignore 有問題，先查
    不確定現在在哪一版 — git log -5 --oneline 看最近五筆。交付的應該是最新一筆迭代的 commit

    P-02 確認執行期版本¶

    做什麼

    node -v
npm -v

    怎麼知道成功了

    node -v ≥ v20.11（開發機目前用 v24）。

    可能怎麼壞、怎麼處理

    症狀 處置
    版本低於 20.11 升級 Node。npm run check:offline 會擋下（它檢查 engines 宣告）
    有多個 Node 版本（nvm 之類） 建置用哪一版，包裡就帶哪一版的執行期。確認你現在這個終端機裡的 node -v 就是你要的那一版

    這件事會跟著進醫院：安裝包裡的 runtime/node.exe 是從你這台機器複製過去的。 你在這裡用的版本，就是院內主機上會跑的版本。

    P-03 確認相依套件是完整的¶

    做什麼

    npm install
npm run check:offline

    怎麼知道成功了

    check:offline 六項全部通過，結束狀態 0，沒有任何「阻擋項」。

    可能怎麼壞、怎麼處理

    症狀 原因 處置
    Prisma 引擎目錄不存在 node_modules 是用 --ignore-scripts 裝的，或從別處複製而排除了二進位檔 刪掉 node_modules，重新 npm install（不要加 --ignore-scripts）。引擎約 40MB，由安裝後腳本另外下載
    Prisma 版本沒有鎖死 package.json 寫成浮動的版本範圍 改成確定版本。引擎與 CLI 版本必須一致，浮動範圍會在某次重新安裝時悄悄換掉其中一邊（DEP-30 第 3 點）
    npm install 出現 EPERM／EACCES Windows 三大原因：還有 node 行程開著、專案在雲端同步資料夾底下、防毒即時掃描 依序排除。詳見手動測試手冊 §01 的同名提示
    建置產物不存在 還沒跑 npm run build 下一步就會做

    2. 建置¶

    P-04 建置三個產物¶

    做什麼

    npm run build

    怎麼知道成功了

    沒有紅字，且這幾個目錄都有新的檔案：

    產物 位置
    共用型別 packages/shared/dist/
    後端 apps/api/dist/（含 main.js、static-server.js）
    護理端 apps/nurse-pwa/dist/
    病人端 apps/patient-pwa/dist/（含 sw.js，離線快取靠它）

    可能怎麼壞、怎麼處理

    症狀 原因 處置
    找不到 @hd/shared 模組 build:shared 沒跑或失敗 單獨跑 npm run build:shared 看真正的錯誤
    TypeScript 型別錯誤 程式有問題 修好再往下。建置失敗的東西不要打包
    病人端產物裡沒有 sw.js Service Worker 外掛沒跑到 看 apps/patient-pwa/vite.config.ts。沒有它，平板斷網就是一片空白，而離線能力正是選 PWA 的唯一理由

    P-05 五支盤點全部跑過¶

    做什麼

    npm run check:all

    怎麼知道成功了

    最後那張總表五支全綠：零院外連線、介面技術識別、介面設計基準、離線可部署性、遷移安全。

    可能怎麼壞、怎麼處理

    症狀 原因 處置
    零院外連線有發現 程式或設定裡出現指向院外的網址 一定要清掉。這是 FR-S07，也是這套系統能進院的前提
    介面技術識別有發現 畫面上露出需求編號或列舉常數 不擋部署，但記下來
    遷移安全有發現 新增的 schema 變更可能弄掉既有資料 擋部署。到院內套用遷移時受害的是真實病人資料
    五支裡有一支跑不起來 腳本本身壞了 單獨跑那一支看錯誤。check:all 刻意讓每一支都跑完再一起算帳，不會因為其中一支失敗就停住

    不要用「先跳過，之後再處理」的心態對待這裡的紅字。 這五支擋下來的東西， 到院內都會變成「起不來的服務」或「壞掉的資料」，而現場沒有人有能力當場修。

    P-06 建置安裝包¶

    做什麼

    npm run package:build -- --zip

    怎麼知道成功了

    最後印出五件事，逐項抄下來：

    1. 安裝包目錄：dist-package/hd-tablet-care-<版本>-<commit>/
    2. 檔案數與總大小（上一次是 23,588 個檔案、681.4 MB 未壓縮）
    3. CHECKSUMS.txt 的 SHA-256
    4. 壓縮檔路徑
    5. 壓縮檔的 SHA-256

    可能怎麼壞、怎麼處理

    症狀 原因 處置
    建置到一半說找不到 dist P-04 沒做完 回去跑 npm run build
    包的大小差很多（例如 200MB 或 2GB） 相依裁剪出了問題 用 --full 再建一份對照（不裁剪，整份 node_modules 照收），比較差在哪
    磁碟空間不足 包加上壓縮檔要 1.5GB 以上 清掉舊的 dist-package/ 子目錄
    想換輸出位置 — npm run package:build -- --zip --out <目錄>

    P-07 看一眼包的最上層¶

    做什麼

    ls -a dist-package/<安裝包目錄>

    怎麼知道成功了

    八樣東西，一樣不多一樣不少：

    runtime/      app/         engines/      scripts/
VERSION.json  CHECKSUMS.txt  .env.範本   安裝說明.md

    可能怎麼壞、怎麼處理

    症狀 為什麼嚴重 處置
    出現 .env DEP-13：設定絕不隨包走 建置腳本有問題，查清楚再重做。把開發機的 .env 帶進院內，等於把開發機的資料庫路徑與金鑰一起帶進去
    出現 .db、.db-wal、.db-shm 包裡有資料庫 同上，而且可能帶著測試資料
    少了 engines/ Prisma 引擎沒收進去 現場套用遷移會倒在 getaddrinfo ENOTFOUND binaries.prisma.sh（DEP-30）
    少了 runtime/ 執行期沒收進去 現場沒有 Node.js，什麼都跑不起來（DEP-04）

    P-08 檢查 VERSION.json¶

    做什麼

    cat dist-package/<安裝包目錄>/VERSION.json

    怎麼知道成功了

    {
  "commit": "<你在 P-01 看到的那一個>",
  "commitClean": true,
  "node": "<你在 P-02 看到的那一版>",
  "prismaEngines": ["query_engine-windows.dll.node", "schema-engine-windows.exe"],
  "platform": "win32-x64"
}

    可能怎麼壞、怎麼處理

    症狀 意思 處置
    commitClean 是 false 建置時工作區有未提交的改動 這份包不得正式交付。 回到 P-01 把工作區弄乾淨，整包重做一次。（目前 dist-package/ 底下那一份就是 false，它是迭代 9.1 時的測試產物，不是能帶進院的包）
    platform 不是 win32-x64 你在 macOS 或 Linux 上建的 重做。院內主機是 x86-64 的 Windows，包內的執行期與引擎都必須是 Windows 版
    commit 與 P-01 對不上 建置中途切過分支 重做

    3. 驗收¶

    P-09 驗收五項¶

    做什麼

    npm run package:verify -- --dir dist-package/<安裝包目錄>

    怎麼知道成功了

    五項全綠：

    1. 雜湊值逐檔核對（兩萬多個檔案）
    2. 包內沒有設定檔、資料庫或備份（DEP-13）
    3. 以包內引擎套用既有遷移到一個全新的資料庫（DEP-31）
    4. 以包內執行期啟動三個行程並通過存活檢查
    5. 全程沒有往院外的連線（連線哨兵，有一筆就不得交付）

    可能怎麼壞、怎麼處理

    症狀 原因 處置
    第 3 項倒在 ENOTFOUND binaries.prisma.sh 引擎沒指好 這正是 DEP-30 要擋的。確認 engines/ 裡兩個檔案都在，且 PRISMA_ENGINES_DIR 有被啟動器帶上
    第 4 項起不來，說「找不到專案根目錄」 迭代 10 修掉的缺陷 1 復發 確認你建的是修正後的版本（迭代 10 之後）
    第 4 項說連接埠被佔用 開發機上還有 npm run dev 在跑 先把它停掉再驗收
    第 5 項有連線紀錄 有東西在偷連外 不得交付。 看哨兵記下的主機名稱是誰，回去 npm run check:egress 對照

    P-10 讓驗收腳本失敗一次¶

    做什麼

    在包裡隨便一個檔案尾端加一個字（例如 安裝說明.md），再跑一次 P-09。

    怎麼知道成功了

    雜湊值那一項變紅，而且指出是哪一個檔案。改回去再跑一次，恢復綠色。

    為什麼要做這一步

    每一個檢查都要有人看過它失敗的樣子。 沒看過失敗，你不知道它是真的在檢查， 還是永遠回傳綠色。到了院內，這支腳本是你唯一能判斷「帶進來的包有沒有在路上壞掉」的工具。

    4. 交付單與掃毒¶

    P-11 寫交付單¶

    做什麼

    拿一張紙（或一個檔案，但最後要印出來）寫下：

    欄位 值
    安裝包檔名 hd-tablet-care-<版本>-<commit>.zip
    版本 / commit
    建置時間
    commitClean 必須是 true
    壓縮檔 SHA-256
    CHECKSUMS.txt 的 SHA-256
    包內執行期版本
    檔案數 / 大小
    建置者 / 建置機器

    「可以交付」的定義：P-01 到 P-10 全部通過，且 commitClean 為 true。 少一項都不算，不要用「應該沒問題」補上去。

    雜湊值為什麼要寫在紙上：院內那台機器沒有網路，你不能傳訊息給自己。 而且核對雜湊的目的就是懷疑手上的檔案——把它存在同一支隨身碟裡，等於沒有核對。

    P-12 開發端掃毒（DEP-26 第一次）¶

    做什麼

    用開發機上的防毒軟體，對壓縮檔與解壓後的整個目錄各掃一次。

    怎麼知道成功了

    結果是乾淨的，並且記下工具名稱、版本、掃描時間——這三項要填進演練紀錄 §2.3。

    可能怎麼壞、怎麼處理

    症狀 原因 處置
    報出可疑檔案，多半在 runtime/ 或 engines/ 未簽章的執行檔常被啟發式判定 不要直接排除了事。記下是哪一個檔案、判定名稱是什麼——院內掃描站十之八九也會報同一個，先準備好解釋
    掃描要很久 包有 2 萬多個檔案 預留時間。順便記下耗時，院內要用它估掃描站要站多久（Q-29 第 4 題）
    防毒把檔案直接刪掉了 即時防護 整包重做，並把 dist-package/ 加進排除清單。被刪過的包雜湊一定對不上

    P-13 準備隨身碟¶

    做什麼

    1. 找一支專門為這件事準備的隨身碟，先完整格式化
    2. 只放兩樣東西：安裝包壓縮檔、scripts/verify-package.mjs
    3. 不要放任何其他東西——不是舊版本、不是筆記、不是別的專案的檔案

    怎麼知道成功了

    隨身碟裡只有兩個檔案，掃一次毒是乾淨的。

    可能怎麼壞、怎麼處理

    症狀 處置
    院方規定要用院方發放的加密碟 這是 Q-29 第 1 題，D-14 就要問。問不到就兩種都準備
    隨身碟容量不夠（壓縮檔數百 MB） 用 8GB 以上的
    想順便放點別的東西「以防萬一」 不要。 隨身碟是單向的（DEP-28），碟上每多一個檔案，離院時就多一件要解釋的事

    隨身碟是單向的：只能把安裝包帶進院內，不得帶任何東西出院—— 不是備份、不是紀錄檔、不是截圖。用完當場清除（第五冊 C-20）。

    5. 練手：讓現場的指令變成肌肉記憶¶

    P-14 在開發機上練一次更新與回退¶

    做什麼

    先把 DATABASE_URL 指到一份複本，再跑：

    npm run db:update -- --note "進院前演練"
npm run db:restore -- --from <備份檔> --to <另一個路徑> --sha256 <備份歷程上的雜湊>

    怎麼知道成功了

    db:update 六步依序完成：確認服務已停 → 開啟更新紀錄 → 備份 → 驗證備份還原得起來 → 套用既有遷移 → 寫紀錄。db:restore 雜湊相符、完整性檢查 ok、列出主要資料表筆數。

    為什麼要在 D-3 做

    現場真的要用到它的時候，通常是出事的時候——那不是第一次看這支腳本輸出的好時機。 詳細項次見迭代 10 分冊 t33–t39。

    可能怎麼壞、怎麼處理

    症狀 原因 處置
    被擋下，說服務還在跑 後端還開著 正確行為。停掉後端再跑
    停在備份那一步 BACKUP_DIR 寫不進去，或磁碟可用空間低於 DB_DISK_MIN_FREE_MB 正確行為。備份沒做成就不往下走，這是整支腳本的重點
    倒在「database is locked」 迭代 10 修掉的缺陷 2 復發 確認你用的是修正後的版本

    P-15 把要用的指令抄成一張小抄¶

    現場會用到的指令不多，但每一條都不能打錯。抄成一張 A4，貼在螢幕旁邊：

    # 核對雜湊
Get-FileHash -Algorithm SHA256 .\CHECKSUMS.txt

# 套用既有遷移（絕不能用開發用的那一支）
.\runtime\node.exe .\app\api\scripts\prisma-cli.mjs migrate deploy --schema .\app\api\prisma\schema.prisma

# 註冊服務
.\scripts\service-install.ps1 -Account "<帳號>" -DataDir "<資料目錄>" -BackupDir "<備份目錄>" -LockDownDataDir

# 啟停與狀態
.\scripts\service-start.ps1
.\scripts\service-status.ps1
.\scripts\service-stop.ps1

# 乾淨機器上的驗收
.\runtime\node.exe verify-package.mjs --dir .

    migrate deploy 與開發用的遷移指令，差別是會不會把資料庫整個重建（DEP-31）。 現場只准用上面這一支。小抄上把這一行畫起來。

    P-16 列印紙本¶

    院內沒有網路，這份文件在現場開不起來。至少印這七份：

    印什麼 為什麼
    第四冊 · 進院當天 當天照著走
    第五冊 · 帶進去與帶出來 離院前逐條打勾
    第六冊 · 現場疑難排解 出事的時候翻
    第七冊 · 院方要求直接 git clone H-08 的 clone 萬一成功時照著走
    第八冊 · 把服務關乾淨 停手、備份、換版前要關服務時照著走
    第九冊 · 院方要求以 git clone ＋ Docker 部署 院方指定容器部署時，取代第四冊 H-08～H-13
    《部署規範》第 9 章的 26 條清單 逐條打勾，打完那張紙就是部署紀錄

    再加上 P-11 的交付單、P-15 的小抄，以及一本空白筆記本（第五冊會用掉半本）。
