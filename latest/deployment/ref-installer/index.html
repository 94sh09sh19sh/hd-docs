    安裝包路線（歷史）¶

    狀態：歷史（路線 0926 撤除）。院方要求以容器部署、不准用隨身碟（《部署規範》v3.0），離線安裝包撤除；現行的部署是容器＋git clone，照《從零部署本系統》；外殼 APK 與平板照《平板與外殼 App》。這一份與兩份子文件只當紀錄，不再照做：npm run package:build、package:verify、cert:hospital-ca、scripts/service-*.ps1、run-all.mjs 與 apps/kiosk-shell/ 1117 時已不在 repo 裡，指令照抄跑不起來。

    1117 從五份舊冊改寫：《進院當天》的 H-08～H-13（路線 A 與路線 B 的安裝包步驟）；《帶進去與帶出來》的隨身碟部分（C-01 第 1、2、5、6、8、11、12 列、C-02、C-05 的隨身碟與掃毒列）；《現場疑難排解》的 A 類（X-01～X-04）；《平板與外殼 App》0927 起被外殼路線取代的部分（盤點裡安裝包那幾列、HTTPS 缺口、K-01～K-07、K-09、K-12，以及 K-13 原文的憑證警告原因）；以及總覽裡安裝包路線的說明。

    編號：H-xx、C-xx、X-xx、K-xx，都沿用原編號；同一套編號的其餘步驟在別份（見第 0.3 節）。

    摘要¶

    • 安裝包路線：開發機上建一份離線安裝包（內含 Node 執行期與 Prisma 引擎）→ 乾淨機器上彩排 → 隨身碟帶進院 → 掃毒、解壓、核對雜湊 → 建 .env、套用遷移 → 低權限服務帳號、註冊成排程工作啟動（第 0 節）
    • 0926 院方要求容器部署、不准用隨身碟，整條路線撤除；0922 第一次進院走的是這條路線的準備，結果見《第一次進院紀錄》
    • 子文件：建置與開發端彩排（P-xx、R-xx）在《安裝包路線之一》；git clone 意外成功時的岔路（G-xx）在《安裝包路線之二》
    • 外殼 App 原本在開發機上自產院內 CA、自建 keystore、自編 APK、側載（K-01～K-07、K-09、K-12，第 1 節）；0927 起改由院內主機上的 shell-builder 建置與簽章、平板從下載頁安裝
    • 原本的 HTTPS 缺口（安裝包只有 HTTP，Service Worker 註冊不了）0927 由病人端自己終止 TLS 解決（第 1.1 節）
    • 隨身碟、交付單、轉接頭、筆記型電腦要帶，隨身碟裡只放兩個檔案，離院前清除（C-01、C-02、C-05 的安裝包列，第 2 節）
    • 進院當天：路線 A 讓 git clone／npm install 失敗並記下（H-08），路線 B 解壓核對雜湊、建 .env、遷移、服務帳號、註冊啟動（H-09～H-13，第 3 節）
    • 安裝包與雜湊的出錯處置（X-01～X-04，第 4 節）

    0. 總說明¶

    0.1 這條路線是什麼¶

    階段 原本的時點 做什麼 在哪裡
    決定位址、產生憑證 D-10 院內主機位址、院內 CA 與伺服器憑證 第 1 節 K-01～K-03
    外殼 App D-7 編譯環境、把 CA 放進外殼、keystore、release APK、模擬器 第 1 節 K-04～K-07
    建置安裝包 D-3 建置、五支盤點、package:build、驗收五項、交付單、掃毒、隨身碟 《安裝包路線之一》 P-01～P-16
    開發端彩排 D-2 乾淨斷網機器上解壓、驗收、.env、遷移、註冊服務、從另一台連進來、重新開機、更新與回退 《安裝包路線之一》 R-01～R-24
    打包 D-1 實體物品、紙本、隨身碟 第 2 節 C-01～C-04
    進院當天 D 日 路線 A 取證據、路線 B 正式安裝 第 3 節 H-08～H-13；其餘步驟在《第一次進院之一：進院當天詳細版》
    git clone 竟然成功 D 日 查來源與憑證、三條出路 《安裝包路線之二》

    整趟的時程表與當時的已知空白在《第一次進院（0922）· 部署本系統》。

    安裝包的形狀：最上層八樣 runtime/、app/、engines/、scripts/、VERSION.json、CHECKSUMS.txt、.env.範本、安裝說明.md；兩萬多個檔案、約 681 MB 未壓縮；.env 放在安裝包目錄的上一層，資料庫與備份目錄在安裝包之外（DEP-08）；服務以專用低權限帳號、排程工作的形式跑三個行程（後端、護理端、病人端）。

    1.1 當時的盤點與 HTTPS 缺口¶

    項次 0923 的現況 誰擋住誰
    外殼 App 原始碼 在（apps/kiosk-shell/：MainActivity.kt、ProvisioningActivity.kt、BootReceiver.kt、network_security_config.xml）；0927 搬到另一個私人 repo hd-kiosk-shell —

    APK 簽名金鑰（keystore） 未建立 擋住 K-06
    平板實體 見《平板與外殼 App》第 10 節 —
    主機的 HTTPS 安裝包目前只提供 HTTP，見下方警告 擋住離線能力

    ⚠ 一個必須先解決的缺口：病人端要離線，就必須是 HTTPS¶

    Service Worker（病人端離線能力的全部依靠）只在安全來源底下才會註冊。 http://localhost 算安全來源，http://<院內主機 IP>:<埠> 不算——平板連的正是後者，於是 navigator.serviceWorker 根本不存在，註冊會靜悄悄地跳過，不出錯、不提示，直到有一天網路斷了才發現畫面是空白的。

    而目前安裝包裡沒有任何東西在做 TLS：後端與兩個靜態站都是純 HTTP。自簽 CA 產生的 server.crt／server.key 現在沒有地方可以掛。

    三條路，建議第一條：

    方案 代價 評估
    ① 讓安裝包自己終止 TLS（後端與兩個靜態站讀 server.crt／server.key） 改動不大，全在自己的程式碼裡 建議。不新增任何要過資安審查的第三方執行檔
    ② 加一個反向代理（nginx／IIS） 多一個要送進院內、另外過一次資安審查的元件 與當初捨棄服務包裝器的理由相同，能免則免
    ③ 首波先跑 HTTP，不要離線能力 「選 PWA 而非純網頁的唯一理由」當場消失 不建議，但若只為了驗主機這一段，可以當成過渡

    這一條在 D-7 之前要有結論，否則平板佈建做不完整。現況已記在這裡，不要到現場才發現。

    結論（0927）：走的是第一條的方向——病人端的靜態服務自己以院內 CA 簽的伺服器憑證提供 HTTPS，HTTP 只留外殼下載頁（《平板與外殼 App》 Y-07）。

    K-01 決定院內主機的位址（所有事情的上游）¶

    做什麼

    向資訊室要一個固定的位址，二擇一：

    • 院內 DNS 名稱，例如 hd.<院內網域>
    • 固定 IP，例如 192.0.2.10

    為什麼這是上游

    同一個位址同時決定四件事，改了任何一次都要重做一輪：

    誰用到它 改了會怎樣
    伺服器憑證的主體別名 要重簽憑證
    PWA 建置時寫死的 API 位址（VITE_API_BASE_URL） 要重新產生安裝包（見《安裝包路線之一》 R-08 的警告）
    .env 的 CORS_ORIGINS、MDM_KIOSK_BASE_URL 改設定重新啟動
    外殼 App 的 network_security_config.xml 15 台平板全部要重發 APK

    可能怎麼壞、怎麼處理

    症狀 處置
    資訊室說「IP 可能之後會變」 要一個不會變的。會變的 IP 等於每次變動都要重發 15 台的 APK
    只給得出 IP，給不出 DNS 名稱 可以，但寫進紀錄：這個 IP 從此不能換
    到 D-7 還沒有答覆 那這次進院的目標降為 B 級（三種結果見《進院通則》），平板整段延後

    之後的演變：容器路線把位址的決定放在《從零部署本系統》 V-08；1007 Q-27 答覆院內主機的 IP 是固定的，1029 由名稱換成 IP。現在位址要換，影響的是 HD_PUBLIC_API_URL（要重建網頁）、CORS_ORIGINS、MDM_KIOSK_BASE_URL 與伺服器憑證（shell-builder 自動重簽，CA 不變），步驟在《護理站登不進去與主機位址》。

    隨身碟 ×2 已當場清除，並在紀錄寫明時間與執行者（DEP-28；H-23）
    掃毒結果的紙本或單號 DEP-26 要求留存

    C-05 其餘的列（筆記本、26 條檢查清單、交接文件的副本）在《進院通則》。

    隨身碟相關的情報題（C-16 隨身碟政策、C-17 掃毒站、C-21 外來筆記型電腦）與離院前十問的第 8 題（隨身碟清乾淨了嗎）在《進院通則》；清除隨身碟的步驟 H-23 在《第一次進院之一：進院當天詳細版》。

    3. 進院當天的安裝包步驟（H-08～H-13）¶

    原本排在進院當天的第 60～75 分（路線 A）與第 75～150 分（路線 B）；之前的 H-01～H-07（出門前、報到、掃毒、認識這台機器）與之後的 H-14～H-24（Windows 五件事、防火牆、驗證、交接、離院）在《第一次進院之一：進院當天詳細版》。0926 起 H-08～H-13 由容器路線取代（第 0.2 節）。

    3.1 路線 A（預期失敗，目的是取證據）¶

    H-08 讓它失敗，並把失敗記下來（DEP-25）¶

    做什麼（每一步都計時）

    git clone https://github.com/<repo>.git
npm install

    怎麼知道「成功」了

    每一步都失敗，而且你抄下了錯誤原文與耗時。

    要填的欄位（演練紀錄 §1.3）：

    欄位 值
    日期／時間
    執行者
    主機
    git clone 的錯誤原文
    耗時
    npm install 的錯誤原文
    耗時
    有沒有人提議「開一下網路就好」、怎麼回應的

    可能怎麼壞、怎麼處理

    症狀 處置
    git clone 成功了 先不要往下跑。 翻《安裝包路線之二》，從 G-01 做起
    院方指定要 clone 之後用 Docker 部署 H-08～H-13 改照《第一次進院之二：git clone＋Docker 路線詳細版》走，從 D-05 做起；H-14 起再回到《第一次進院之一：進院當天詳細版》
    有人說「我開一下網路給你」 婉拒，並把這件事記下來。 零院外連線是這套系統能放病人資料的前提，第一天就自己破壞它，之後沒有人會再認真看待這條
    機器上連 git 都沒有 更好——那本身就是證據。記下來
    錯誤訊息很長 抄開頭那幾行就夠，重點是錯誤碼與主機名稱。另外一定要記耗時：開發端量到的是 71 秒，而它連第一個套件的中繼資料都還沒拿到
    覺得這一步沒必要、想跳過 這份紀錄有兩個用途：向資訊室解釋「為什麼不能用一般方式部署」時它比任何說明都有效；日後有人提議「直接在主機上更新就好」時，它是現成的答案

    📍 0926 之後：院方要求的正是容器＋git clone，對外連線也是常態（0930 Q-32 答覆）；0922 實際的經過見《第一次進院紀錄》。

    3.2 路線 B（正式安裝）¶

    H-09 解壓並核對雜湊（DEP-27）¶

    做什麼

    Expand-Archive -Path <隨身碟>:\hd-tablet-care-<版本>-<commit>.zip -DestinationPath C:\hd\hd-tablet-care-<版本>-<commit>
cd C:\hd\hd-tablet-care-<版本>-<commit>
Get-FileHash -Algorithm SHA256 .\CHECKSUMS.txt

    壓縮檔裡沒有最上層資料夾，-DestinationPath 要寫到有版本號的那一層。

    與交付單上那一串逐字比對。

    可能怎麼壞、怎麼處理

    症狀 處置
    雜湊不一樣 停下來。 重新複製再比一次。還是不同就是路上壞了或被掃描站動過——今天不要裝（X-01）
    cd 找不到路徑，檔案全散在 C:\hd\ 底下 解壓目的地少寫了版本號那一層。清掉散出來的檔案，照上面的指令重解，不要用搬的
    路徑太長導致解壓失敗 解到很短的路徑（C:\hd\），不要放在桌面或使用者資料夾深處（X-02）
    解壓很慢 2 萬多個檔案，幾分鐘是正常的
    不知道要解到哪 問資訊室指定的安裝路徑。要記得它必須與資料庫、備份目錄分開（DEP-08）

    H-10 建立 .env¶

    做什麼

    Copy-Item .\.env.範本 ..\.env
notepad ..\.env

    照 R-08 那張表填（《安裝包路線之一》）。把你在演練時填的那份拿出來照抄，只換四種值：主機位址、連接埠、路徑、密碼。

    可能怎麼壞、怎麼處理

    症狀 處置
    忘了 DEPLOYMENT_ENV=production 時區檢查不會擋、開發用遷移指令不會擋。一定要填
    CORS_ORIGINS 還是 localhost 護理站電腦一連就被擋，而且錯誤只在瀏覽器主控台看得到
    API_PORT 沒填 正式環境會直接拒絕啟動。這是刻意的：逼出「埠要先登記」這件事
    密碼裡有特殊字元 整串加引號，或改用不含引號與 # 的密碼

    H-11 套用既有遷移（DEP-31）¶

    做什麼

    .\runtime\node.exe .\app\api\scripts\prisma-cli.mjs migrate deploy --schema .\app\api\prisma\schema.prisma

    怎麼知道成功了

    列出套用了哪幾個遷移，資料庫檔案出現在你指定的目錄。

    可能怎麼壞、怎麼處理

    症狀 處置
    ENOTFOUND binaries.prisma.sh PRISMA_ENGINES_DIR 沒指好。注意：這不是網路問題，不要因此去要網路
    Error code 14: Unable to open the database file 目錄不存在或沒有寫入權限。先建目錄
    拒絕啟動，說路徑在共用位置 換一個專屬路徑（DEP-37 第 3 項）
    有人建議用開發用那支遷移指令「比較快」 絕對不可以：它可能直接重建整個資料庫

    H-12 建立服務帳號（需要資訊室）¶

    做什麼

    請資訊室建立一個專用的低權限帳號，並告訴你帳號名稱（密碼由他們輸入，你不要知道）。

    可能怎麼壞、怎麼處理

    症狀 處置
    「用我的帳號跑就好」 不行。那個人改密碼或離職的那天服務就停了
    「用 SYSTEM 跑」 不行。權限過大，且違反 DEP-12
    網域帳號有密碼到期政策 當場問清楚多久到期、到期時誰來改。這是日後服務突然停掉的頭號原因，寫進交接文件

    H-13 註冊服務並啟動¶

    做什麼

    .\scripts\service-install.ps1 -Account "<網域或機器名>\<服務帳號>" -DataDir "<資料目錄>" -BackupDir "<備份目錄>" -LockDownDataDir
.\scripts\service-start.ps1
.\scripts\service-status.ps1

    怎麼知道成功了

    排程工作 Running、執行身分是服務帳號、3 個行程、存活檢查 HTTP 200。

    可能怎麼壞、怎麼處理

    症狀 處置
    執行原則擋下 .ps1 Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass。先問過資訊室
    資訊室堅持要 services.msc 看得到的服務 目前是排程工作（Q-27 第 6 題）。今天先用排程工作把系統跑起來，把需求記下來，回去換那一支腳本
    行程數 0 用前景跑一次看錯誤：.\runtime\node.exe .\scripts\run-all.mjs
    資料目錄被擋（在安裝包目錄之內） 正確行為（DEP-08）。換一個路徑

    服務起不來的其他情形（X-05～X-11）在《現場疑難排解》。

    4. 安裝包與雜湊的出錯處置（X-01～X-04）¶

    舊《現場疑難排解》的 A 類；其餘各類在《現場疑難排解》。

    X-01 雜湊值對不上¶
    你會看到 Get-FileHash 出來的字串與交付單上不同
    可能原因 複製時中斷；防毒「清理」過檔案；拿錯版本；解壓不完整
    先查 是不是拿錯壓縮檔（檔名裡的 commit）；隨身碟上那一份的雜湊對不對
    處置 重新複製、重新解壓、再比一次。還是不同就今天不要裝
    不要做 「差一點應該沒關係」——雜湊沒有「差一點」

    X-02 解壓失敗，說路徑太長¶
    可能原因 Windows 的路徑長度上限，加上 node_modules 本來就很深
    處置 解到極短的路徑，例如 C:\hd\。不要放在桌面或使用者資料夾深處

    X-03 驗收腳本第 5 項抓到對外連線¶
    你會看到 連線哨兵列出一個院外主機名稱
    處置 不得交付。記下那個主機名稱帶回去，用 npm run check:egress 對照
    不要做 當成誤判跳過。這一條是整套系統能放病人資料的前提

    X-04 掃描站把檔案刪掉或隔離了¶
    你會看到 雜湊對不上，或解壓後少了某個檔案
    處置 請對方加例外並重新複製一份；同時記下判定名稱與檔案路徑
    不要做 用被動過的包硬裝。那份包已經不是你驗收過的那一份
