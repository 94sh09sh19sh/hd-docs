    血液透析中心平板照護輔助系統 — 軟體需求規格書（SRS）¶

    版本：v2.0　文件狀態：草案　適用讀者：FDE 工程團隊、醫院資訊室、護理部、法務／法規合規承辦人

    0. 本版異動摘要（0910）¶

    0909 版的功能邊界與部署假設在本週被大幅改寫。以下六項是與 v1.0 的實質差異，第 5 章之後的所有內容都以本表為準：

    # 項次 v1.0（0909） v2.0（0910）
    1 三項高 SaMD 風險功能（FR-P03、FR-P05、FR-N06） 標註高風險，實作規格書整條排除 納入實作範圍，但受第 5.6 節 FR-R 控制措施約束，並設書面確認閘門
    2 推播通知 系統元件之一，架構圖有推播中繼那一跳 整條移除。所有資料不得離開醫院網路
    3 AI 模型 經 AI Proxy 呼叫外部 LLM 服務商 地端推論（院內 128GB 伺服器）；過渡期用實驗室 API，僅得送合成資料
    4 資料庫 測試用 Supabase，正式為醫院 MSSQL 測試與正式皆為 SQLite
    5 使用者角色 病人、護理師、護理站管理者、FDE 新增護理長／單位主管、醫院管理層（唯讀）、稽核角色
    6 功能範圍 病人端 8 項、護理端 9 項、系統 4 項 新增管理與營運（FR-M）、對外揭露（FR-X）、高風險控制（FR-R）三組

    1. 文件目的與範圍¶

    本文件定義「血液透析中心平板照護輔助系統」之軟體需求，涵蓋病人端 15 台 Android 平板、護理端多裝置應用、後端服務、地端 AI 輔助功能、單位管理與營運分析，以及資料治理規範。

    系統目標為在不取代任何臨床判斷與侵入性操作的前提下，將可數位化與可數位優化的護理工作流程予以實作（工作區塊盤點見《FDE 數位化／數位優化評估報告》）。

    本文件不涵蓋：透析機台參數整合、藥局／HIS 系統雙向寫入、透析機台硬體通訊協定（列為未來擴充項）。

    與其他文件的關係：本文件是功能需求的來源（FR 編號出處）。資料治理的強制規則以《資料庫使用規範》為準；實作範圍與技術棧決策以《實作規格書》為準；部署形態、環境界線與交付方式以《部署規範》為準（DEP 編號）。

    3. 系統總覽¶

    3.1 使用者角色¶

    3.2 系統邊界¶

    系統由病人端 PWA、護理端 PWA、管理端介面（與護理端共用應用，以權限區分）、後端 API Gateway、裝置綁定服務、地端 AI 推論服務、規則引擎、臨床資料匯入服務、對外報表服務，以及 SQLite 資料檔所組成。

    0910 的邊界變動：

    • 推播通知服務移除。 即時通知改由院內 SSE 長連線提供，配合常駐總覽螢幕與音效提示。
    • 外部 LLM 服務移除。 AI 推論在院內伺服器完成。過渡期的實驗室 API 為院外服務，因此過渡期僅得送合成資料。
    • 新增規則引擎。 三項高風險功能不經語言模型，改以可攤開的規則計算（FR-R01）。
    • 資料層改為單一 SQLite 檔案，即時狀態改由後端記憶體與資料庫共同承擔，不另設快取服務。

    4. 權限模型與裝置綁定¶

    4.1 病人端不提供登入介面（維持 v1.0 設計）¶

    病人端平板不提供任何登入介面（無帳號、密碼、生物辨識、或病人自選身分清單）。病人於平板上能存取的所有資料與功能，其存取權限之啟用，一律由護理師透過「裝置指派」動作觸發。理由：

    1. 病人在透析情境下（可能虛弱、視力不佳、認知負荷高）不適合承擔身分驗證責任
    2. 平板為機構共用裝置，若允許病人自行選擇／切換身分，會產生資料誤植給錯病人的風險
    3. 從法規遵循角度，臨床資料的存取授權應可追溯到「哪一位護理師、何時、為哪一位病人核准」，而非病人自證身分

    4.3 裝置與病人綁定流程¶

    前置條件：護理站已建立當日排班表（病人—療程時段對應）。

    1. 病人到達透析中心，護理師於護理站主控台（或當班護理端裝置）選取當日排班中的病人
    2. 護理師選擇欲指派之平板序號（清單選取、掃描病人手環條碼、掃描平板背面 QR 碼三者擇一）
    3. 護理師確認指派後，請求送至後端裝置綁定服務
    4. 裝置綁定服務核發一組限時 Session Token，綁定「病人 ID＋平板序號＋當次療程時段」三項，並透過安全通道送至該平板
    5. 平板在收到有效 Session 前，僅顯示中性等待畫面（「請由護理人員為您開始使用」），不顯示任何病人可識別資訊、不提供輸入欄位
    6. Session 啟用後，平板僅能存取「本次已綁定病人」之資料與功能，無法切換查看其他病人
    7. Session 失效條件（三者擇一觸發）：正常下機流程、護理師手動提前解除、超過療程時間上限（預設 6 小時）自動失效
    8. Session 失效後，平板本地暫存資料需清除，並回復至「等待指派」狀態
    9. 每一次綁定與解除動作，須記錄操作護理師帳號、時間戳、病人 ID、平板序號，寫入稽核軌跡

    4.4 例外情況¶

    • 平板離線期間無法完成新綁定；若原本已有效 Session 而平板離線，症狀回報可暫存本地（IndexedDB），恢復連線後同步，但求助功能於離線期間需明確提示「目前無法即時通知護理站」
    • 若同一病人短時間內被誤指派至兩台平板，系統應偵測並阻擋第二次綁定，提示「該病人已有進行中之綁定」
    • 0910 新增：Session 失效後，閒置輪播中已快取的第三層臨床數值須一併清除，不得殘留給下一位使用者

    5. 功能性需求¶

    編號規則：FR-P 病人端、FR-N 護理端、FR-M 管理與營運、FR-X 對外揭露、FR-S 系統與整合、FR-R 高風險功能控制。 優先權：P0 必要／P1 次要／P2 可延後。 「SaMD 風險」欄僅標示該功能是否涉及臨床判斷輸出；標為高者，必須同時滿足第 5.6 節全部 FR-R 條款。

    5.1 病人端¶

    編號 需求描述 優先權 SaMD 風險 0910

    FR-P08 情緒／滿意度回饋問卷，長期趨勢偏離時建議轉介社工 P2 中 不變
    FR-P09 閒置輪播：平板無操作達設定門檻（預設 60 秒）後，自動輪播本次透析的重要資訊 P1 無 新增
    FR-P10 輪播卡片可點選展開細節頁；細節頁停留超過設定時間或無操作後自動退回 P1 無 新增

    FR-P12 求助被護理師結案後，平板顯示「已處理」狀態與簡短結果，讓病人知道事情有被處理 P2 無 新增
    FR-P13 輪播不得影響主線功能：求助按鈕全程可見且位置固定；任何觸控立即中止輪播；症狀問卷到期時優先於輪播；輪播全程靜音 P0 無 新增

    FR-P09～P13 補充說明：

    • 輪播第一層（療程進度、今日已回報內容、衛教完成度）不依賴任何外部資料來源，應優先實作。
    • 輪播第三層（乾體重、超過濾目標、抽血結果、Kt/V）依賴院方提供，來源尚未確定為 API 或 Excel，一律經 FR-S05 的介面層取得。
    • 輪播畫面中的病人可識別資訊只到床號層級，姓名與病歷號不得出現在輪播畫面（治療區內鄰床可見）。
    • 晚班時段輪播應自動調暗或改為靜態顯示。

    FR-N03 緊急通報接收，含病人症狀趨勢背景摘要，依嚴重度分級路由 P0 中 分級依據限定為病人自選急迫度＋靜態分派表，不得摻入模型推論
    FR-N04 事件當下快速點選式記錄範本，事後由 AI 草擬敘述初稿供審閱 P1 無（AI 僅草擬，護理師簽核） 改由地端模型生成
    FR-N05 護理記錄自動預填草稿（依病人自報資料），護理師審閱簽核取代重新輸入 P1 無 改由地端模型生成
    FR-N06 每月／每週抽血與 Hb／EPO 趨勢儀表板，標註軌跡偏離之病人並提供劑量調整參考建議 P1 高 由排除改為納入，受 FR-R01～R08 約束
    FR-N07 透析適足性（Kt/V、URR）自動計算與趨勢預測 P1 中（計算無風險，預測部分適用 FR-R） 不變
    FR-N08 心理社會風險趨勢彙總與轉介建議 P2 中 不變
    FR-N09 SOP／藥品劑量查詢介面，僅限醫院既有文件範圍內回答，須標出原文出處段落 P1 中 補上出處標示要求
    FR-N10 求助處理結果登記：護理師結案時須以結構化欄位登記處理方式與結果，不得只留自由文字 P0 無 新增
    FR-N11 同一病人同一類別求助於設定期間內再次發生時，於通報畫面標示「近期再發」與前次處理方式 P2 無 新增
    FR-N12 常駐總覽螢幕模式：一種不進入休眠、字級放大、有聲音提示的全螢幕總覽模式，供護理站固定螢幕使用 P0 無 新增（推播移除後的必要補償）
    FR-N13 高風險功能（FR-P03／P05／N06）之輸出，護理師須逐則標記「已檢視」及「是否採納」，未採納可選填原因 P0 無 新增

    FR-N10 的結構化欄位（實際選項須由護理部確認）：

    欄位 內容
    處理方式 分類清單（現場處置、通知醫師、調整機台設定、提供物品、協助如廁、心理安撫、轉介、其他）
    處理結果 分類清單（已解決、部分緩解、持續觀察、升級處理、病人自行取消、無法處理）
    是否需後續追蹤 是／否，若是則帶出追蹤事項
    到達床邊時間 由護理師在床邊登記產生，與「確認通報」的時間分開記錄
    自由文字補充 選填，不取代上述結構化欄位

    為什麼「確認時間」與「到達床邊時間」要分開：兩者的差距是資料品質的檢查點。若只記錄確認時間，一旦這個數字被用於績效，最省力的做法會變成「先按確認再慢慢走過去」，指標就失去意義。分開記錄讓這種情況看得見。

    5.3 管理與營運（0910 新增，對應新增任務一之 1～3）¶

    本節全部為新增。設計原則見《FDE 評估報告》第五章，資料分級與存取限制見《資料庫使用規範》第 11 條。

    編號 需求描述 優先權 資料級別
    FR-M01 護理師班表建立、檢視與匯入（支援手動建立與檔案匯入兩種方式） P0 L2
    FR-M02 當班床位分配：指定每位當班護理師負責的床位 P0 L2
    FR-M03 臨時調動：有人請假時，依技能標記、連續工時、近期負荷產生候補人選排序供護理長選擇 P1 L3
    FR-M04 勞動條件硬性檢查：連續工時、班距、單日時數上限違反時擋下儲存並說明違反哪一條，非僅提示 P0 L2
    FR-M05 工作量實測儀表板：依既有稽核軌跡呈現各班次的求助件數、回應時間分布、尖峰時段 P1 L2
    FR-M06 成效儀表板（L1）：單位聚合指標，供醫院管理層唯讀存取 P1 L1
    FR-M07 成效基準建檔：提供介面讓護理長輸入系統啟用前的人工量測結果，作為 FR-M06 的對照基準 P0 L1
    FR-M08 獎勵指標定義：計分規則可於管理介面設定，設定內容對全體護理師公開可查 P1 L2
    FR-M09 觀察期模式：獎勵指標可設為「只計算不計分」，用於上線初期驗證資料無系統性偏差 P1 L2
    FR-M10 個人自我檢視：每位護理師可查閱自己的計分明細與原始事件，並提出更正申請 P1 L3（限本人）
    FR-M11 L3 總開關：個人層級績效資料預設關閉，開啟與關閉均寫入稽核軌跡，且需記錄核准依據 P0 —
    FR-M12 簡報模式：一頁式成效摘要（含基準對照與未達成事項），供會議與訪視使用 P2 L1

    FR-M04 是本節唯一的 P0 硬性擋下項：其餘功能給的是建議，護理長可以不採納；但系統不得產出違反勞動法規或醫院規定的班表。

    FR-M07 的時效性警告：成效基準只能在系統正式啟用前取得。一旦紙本流程消失，就再也無從量測。這一項的實作優先權因此高於它的複雜度所暗示的順序。

    禁止事項（實作時的硬性界線）：

    • 不得建立「護理師×病人臨床結果」的關聯評分
    • 不得產生公開的個人排名
    • 不得將績效彙整結果回寫至臨床資料表
    • 不得以回應速度作為自動派工的依據

    5.4 對外揭露（0910 新增，對應新增任務一之 4）¶

    編號 需求描述 優先權
    FR-X01 對外報表產生功能：獨立模組，具備自己的權限控制，是資料離開院內的唯一合法管道 P1
    FR-X02 對外報表僅輸出聚合值；樣本數少於門檻（預設 5）的分組不呈現；禁止欄位（姓名、病歷號、床號、工作 ID、精確時間戳）於產生時即排除 P0（只要 FR-X01 做，這條就必須同時做）
    FR-X03 對外報表須經指定核准角色確認後方可取出 P0
    FR-X04 每一次對外報表的產生與核准均寫入稽核軌跡：誰產生、給誰、包含哪些指標、核准者 P0
    FR-X05 對外展示環境：獨立機器、獨立資料庫檔案、資料全為合成，與正式環境無任何連線 P2

    設計說明：對外揭露真正有說服力的素材是工程證據（架構、治理規範、測試手冊）與可操作的展示環境，這兩者本來就不含病人資料。成效數字（FR-X01～X04）是補充，不是主體。

    5.5 系統與整合¶

    編號 需求描述 優先權 0910
    FR-S01 MDM 整合，支援裝置 Kiosk 鎖定、遠端註冊與解除註冊 P0 不變（本階段仍為介面層＋模擬實作）
    FR-S02 所有裝置綁定／解除、資料存取、AI 輸出使用情形、L3／L4 查詢、對外報表產生均需寫入稽核軌跡 P0 擴充範圍
    FR-S03 AI 呼叫一律經後端服務轉發，前端不持有任何 API 金鑰 P0 不變
    FR-S04 病人可識別資訊不得傳送至任何院外服務；去識別化須在寫入資料庫前完成 P0 強化：從「不送外部 LLM」擴大為「不出院內網路」
    FR-S05 臨床資料來源介面層（ClinicalDataSourcePort）：檔案匯入、院方 API、人工輸入三種實作共用同一介面與同一組內部資料表 P0 新增
    FR-S06 模型供應者介面層（LlmProviderPort）：模擬、實驗室 API、地端推論三種實作可透過設定切換，不需改程式碼 P0 新增
    FR-S07 即時通知一律以院內連線（SSE）提供；系統不得包含任何院外推播中繼的呼叫 P0 新增（取代原推播需求）
    FR-S08 功能開關中心：高風險三項、L3 績效、輪播各層、AI 功能，皆可獨立開關，切換寫入稽核軌跡 P0 新增
    FR-S09 備份與還原作業介面：可觸發線上備份、檢視備份歷程，備份動作寫入稽核軌跡 P1 新增（SQLite 單檔風險的對應）

    FR-S06 的過渡期限制：實驗室 API 為院外服務，因此在切換至地端推論之前，系統不得將任何真實病人資料送入 AI 流程，僅得使用合成資料。此限制以程式強制（設定為 LabApiProvider 時，帶有真實病人資料的請求應被擋下），不依賴人的自律。

    5.6 高風險功能控制（0910 新增）¶

    本節適用於 FR-P03、FR-P05、FR-N06 三項。八條全部滿足才得實作與啟用，缺一不可。

    編號 控制要求 對應
    FR-R01 三項功能的計算一律由規則引擎執行，不得使用語言模型產生判斷結果 FDE 報告 R-1
    FR-R02 規則門檻值由臨床端書面提供並版本化儲存；未取得書面依據前，該規則只得對合成資料執行 R-2
    FR-R03 每一則輸出可展開完整依據：所引用的歷史資料、套用的規則條目、門檻值、規則版本 R-3
    FR-R04 輸出一律標示「僅供參考，非診斷結果」；措辭須為事實陳述（「符合 X 規則：近三次療程第 2 小時後曾回報頭暈」），不得為結論陳述（「病人有低血壓風險」） R-4
    FR-R05 輸出不自動生效、不自動觸發任何動作：不得自動調整醫囑、不得自動改變處理優先順序、不得自動通知醫師 R-5
    FR-R06 記錄「誰檢視、是否採納、未採納原因」，寫入稽核軌跡 R-6，對應 FR-N13
    FR-R07 三項功能各有獨立開關，護理站管理者可即時關閉；關閉後介面完全不出現相關內容 R-7，對應 FR-S08
    FR-R08 書面確認閘門：未取得醫院法務／資訊室對 TFDA 分類的書面確認前，三項功能不得對真實病人啟用。系統應以設定強制此限制，而非僅寫在文件裡 R-8

    法規立場說明：以上設計取向是讓這三項功能盡可能停留在「提供資訊、由專業人員自行判斷」的範圍，而非「軟體自行做出臨床結論」。這樣的設計能否使其免於醫療器材管理，判定權在主管機關與醫院法務，開發端不做此判斷。判定完成前，功能可開發、可用合成資料驗證，但不對真實病人啟用。

    6. 非功能性需求¶

    類別 需求 0910
    效能 症狀回報送出至護理端接收延遲需 < 5 秒（正常院內網路） 不變
    效能（AI） 即時性質的 AI 功能（SOP 查詢）回應需 < 10 秒；非即時性質（衛教生成、記錄草擬）可走背景佇列，但須有明確進度提示 新增。0912 更新：正式主機為 DGX Spark，載入量充裕但記憶體頻寬有限且與其他專案共用，實際可達成值仍待實測（Q-07）
    效能（資料庫） 統計與報表查詢不得阻擋臨床寫入；長查詢一律走唯讀連線 新增（SQLite 單一寫入者的限制）
    可用性 病人端療程期間介面需穩定運作 4 小時以上不中斷；護理端多裝置存取一致 不變
    可用性（通報） 因不做推播，護理站須有常駐總覽螢幕（FR-N12）。此為部署必要條件，非選配 新增
    安全性 Session Token 限時效、限裝置；所有 API 呼叫需 TLS 加密；資料庫檔案與備份依《資料庫使用規範》第 9 條保護 調整
    網路邊界 系統不得包含任何主動連向院外的連線（過渡期的實驗室 API 為唯一例外，且僅得送合成資料） 新增
    離線韌性 衛教與輪播靜態內容可離線瀏覽；症狀回報可離線暫存並於恢復連線後同步；求助功能離線時需明確告知限制 擴充至輪播
    多語言 衛教與輪播內容、介面至少支援繁體中文；可擴充其他語言 擴充至輪播
    可用性（病人端） 病人多為長者。字級、對比、觸控目標尺寸須符合高齡友善原則；輪播文字尺寸須可從床上距離辨讀 新增
    可擴充性 前後端架構需可延伸支援管理端儀表板，共用同一套 API 層 擴充
    可稽核性 任何影響臨床或人事的輸出，皆須可回溯到「依據什麼、誰看過、是否採納」 新增
    感染管制 平板共用需搭配醫院訂定之消毒 SOP。閒置輪播使平板成為長時間顯示的公共資訊面板，觸碰頻率不會下降，消毒需求不因此減輕 強化
    可移植性 系統不得對正式主機的全域環境有任何要求，也不得假設執行架構為 x86-64。正式環境為 ARM64 且與其他專案共用 0912 新增（DEP-04、DEP-05）
    正確性（時間） 所有以時間為基礎的計算（班表、連續工時與班距檢查、排程備份、稽核時間顯示）一律依伺服器當地時區。正式環境未設定時區時系統拒絕啟動 0912 新增（DEP-15）

    7. 系統架構需求¶

    • 前端採 PWA 架構，病人端搭配 MDM／Kiosk 鎖定；護理端與管理端為響應式設計，涵蓋工作站／平板／手機，另含常駐總覽螢幕模式
    • 後端採 API Gateway／BFF 作為唯一對外入口，內部區分裝置綁定服務、AI 推論代理、規則引擎、臨床資料匯入服務、對外報表服務
    • 資料層為單一 SQLite 檔案，置於院內伺服器本機磁碟；即時狀態由後端行程內部維護，不另設快取服務
    • 無任何主動連向院外的元件。原架構圖中的推播中繼與外部 LLM 兩條跨院外連線，於本版全部移除
    • 地端 AI 推論服務部署於院內伺服器；過渡期改指向實驗室 API，切換方式為設定變更（FR-S06）
    • 0912 新增：正式環境以容器部署於院內 NVIDIA DGX Spark（ARM64、128GB 統一記憶體、與其他專案共用）。資料庫與備份以主機本機磁碟的繫結掛載提供，不放在映像檔內
    • 0912 新增：地端推論服務不由本系統部署或啟動。對本系統而言它只是一個可設定的 HTTP 端點，本系統不需要 GPU 存取權限（DEP-16）

    架構圖現況：《架構圖》已於 2026-09-11 依本章重繪，推播中繼、外部 LLM 與 PostgreSQL 三處已拿掉。圖與本章文字若有出入，仍以本章文字為準。

    8. 資料治理與法規遵循需求¶

    • FR-P03、FR-P05、FR-N06 三項於上線前須與醫院法務／資訊室確認 TFDA 醫療器材軟體認證範疇，並取得書面確認（FR-R08）
    • AI 與規則引擎的輸出於介面上須明確標示「僅供決策輔助，非診斷結果」（FR-R04）
    • 所有 AI 呼叫、規則執行、資料存取、裝置綁定／解除、L3／L4 查詢、對外報表產生，須留存可稽核之操作紀錄，留存期限依《資料庫使用規範》第 8.2 條
    • 病人可識別資訊不得以任何形式離開醫院網路；去識別化須於寫入資料庫前完成
    • 護理師績效資料屬目的外利用，適用《資料庫使用規範》第 11 條的分級與啟用限制，個人層級預設關閉
    • 任何要離開院內的統計數字，須經對外報表模組產生並取得核准（FR-X01～X04）

    9. 裝置管理需求¶

    • 15 台平板須以 MDM（Android Enterprise／Samsung Knox 等）納管，鎖定為單一 PWA 網址之 Kiosk 模式
    • 支援遠端裝置註冊、解除註冊、應用更新推送
    • 裝置遺失或運作不正常時，護理站管理者可遠端鎖定或清除本地暫存資料
    • 0910 新增：閒置輪播會使螢幕長時間亮著，須確認 MDM 的螢幕逾時設定與輪播行為不衝突，並評估對電池與螢幕壽命的影響（15 台裝置的汰換成本）
    • 0910 新增：常駐總覽螢幕若使用其中一台平板或另配硬體，須一併納入 MDM 管理

    6 AI 推論於院內 NVIDIA DGX Spark 執行（0912 確認：ARM64、128GB 統一記憶體、GB10 Grace Blackwell）。載入量充裕，但記憶體頻寬約 273 GB/s 且與其他專案共用，可用額度與實際回應速度尚未定案（Q-07） 0912 改寫
    7 實驗室 API 尚未取得；在取得並切換至地端推論前，AI 功能僅得對合成資料執行 新增
    8 輪播第三層的臨床數值來源（API 或 Excel）尚未確定，第一、二層不受此影響 新增
    9 三項高風險功能的規則門檻值尚未由臨床端提供，在此之前只能對合成資料執行 新增

    11 正式環境以容器部署，交付物為離線映像檔；院內主機不需要對外連線即可安裝。開發環境維持本機直跑，不容器化 0912 新增
    12 正式主機為桌上型機器，無備援電源、無磁碟陣列、記憶體不具 ECC。備份目的地因此必須是院內另一台機器，不接受同機備份 0912 新增
