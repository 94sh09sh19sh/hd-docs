    血液透析中心平板照護輔助系統 — 部署規範¶

    版本：v2.0　文件狀態：草案　適用讀者：FDE 工程團隊、醫院資訊室

    0. 本文件與其他文件的關係¶

    本文件把「這套系統最後要跑在哪裡、用什麼形態跑、怎麼交到院方手上」收斂成可執行的決策。

    • 《軟體需求規格書》：功能需求來源
    • 《資料庫使用規範》：資料治理強制規則。資料庫檔案、備份、加密與版本更新的規定以該文件為準，本文件只補「在這台主機上怎麼落實」
    • 《實作規格書》：範圍界定與技術棧。功能範圍與技術選型衝突時仍以該文件為準
    • 《FDE 數位化評估報告》：選型理由與背景脈絡
    • 《平板管控：免 MDM 的全院內方案》：病人端平板的管控路線，本文件第 8 章的佈建步驟以它為準
    • 《尚待確認事項清冊》：本文件的待確認事項一律指回 Q 編號，不在此另立清單

    本文件擁有最終決定權的範圍只有三件事：部署形態（安裝包或容器）、環境界線（哪個環境可以放什麼資料）、交付方式（安裝包怎麼進院內）。這三件事以外的爭議一律回到上列文件。

    本文件的強制規則以 DEP-xx 編號，其他文件引用時寫編號，不複製內容。

    0.1 v1.0 → v2.0 異動摘要（0919）¶

    正式主機換了，因此 v1.0 的核心決策必須重做。 v1.0（0916 定版）建立在「正式環境是院內一台與其他專案共用的 ARM64 DGX Spark」這個前提上；0919 起前提改為：

    v1.0（0916） v2.0（0919）
    應用主機 NVIDIA DGX Spark，ARM64，與其他專案共用 院內另一台 Windows 工作站，x86-64；仍與其他專案共用，院方確保本系統資源足夠
    規格 128GB 統一記憶體、4TB NVMe Intel i7-14700、64GB 記憶體、2TB SSD ×2
    部署形態 linux/arm64 容器 離線安裝包（容器降為備案）
    交付物 docker save 的映像檔封存檔 壓縮的安裝包，經防毒掃描後以隨身碟帶入
    地端推論 同一台機器上的另一個服務 另一台機器（DGX Spark）上的一個 API 端點
    平板管控 MDM（Android Enterprise） 免 MDM：自包 WebView 外殼＋螢幕固定
    臨床數值來源 未定（API 或 Excel） 院方 API

    換機器沒有換掉「共用」這件事。 新主機同樣是一台與其他專案共用的機器，差別在於院方確保本系統可用的處理器、記憶體與磁碟額度足夠。因此 v1.0 為共用主機寫的隔離要求整條保留，只是落實方式由容器層級改為安裝包層級（DEP-37）。逼出安裝包的是「容器在 Windows 上會撞到資料庫規範」，不是「主機變專用了」（見 3.1）。

    受影響的 DEP 條款：DEP-02（理由改變、結論不變）、DEP-04（保留並加嚴）、DEP-05（作廢）、DEP-06（保留）、DEP-07（改寫）、DEP-08～DEP-14（改寫為安裝包版本）、DEP-15（保留，落實方式改）、DEP-16（保留並強化）、DEP-18～DEP-19（改寫）。新增 DEP-21～DEP-37。

    1. 三個環境¶

    開發環境 過渡環境 正式環境
    機器 FDE 的 Windows 筆電 實驗室主機（院外） 院內一台共用 Windows 工作站
    架構 x86-64 x86-64 x86-64（0919 起與開發環境相同）
    作業系統 Windows Linux（容器內） Windows
    執行形態 npm run dev，不容器化 容器（實驗室規定） 離線安裝包，以 Windows 服務常駐
    資料庫 本機 SQLite 檔案 不放資料庫 本機 SSD 上的 SQLite 檔案
    可用資料 合成資料 僅合成資料 真實病人資料
    AI 供應者 MockLlmProvider LabApiProvider OnPremiseProvider（指向 DGX Spark 的端點）
    對外連線 僅開發工具（npm、Prisma 引擎下載） 有 零（FR-S07）

    DEP-01｜三個環境的資料界線不得跨越。 過渡環境在院外，任何真實病人資料不得進入；此限制由 LabApiProvider 的合成資料檢查以程式強制（FR-S06），不靠人的自律。

    DEP-02｜開發環境不容器化。 v1.0 的理由是「Windows 的 Docker Desktop 會把 SQLite 檔案掛進 WSL2 的檔案系統，而《資料庫使用規範》7.2 明文禁止把資料庫放在檔案鎖行為不可靠的位置」。0919 之後這個理由不只適用於開發環境，也適用於正式環境——兩邊都是 Windows。結論不變，適用範圍變大，見 DEP-07。

    0919 的附帶好處：開發環境與正式環境現在是同一種作業系統、同一個架構、同一種執行形態。v1.0 那句「刻意讓開發與正式的執行形態不同，代價是兩種環境要各驗一次」不再適用——這一次省下的不是工，是「在開發機上測過了」這句話的可信度。

    1.1 過渡環境的實際形態¶

    實驗室資源的已知條件（見 Q-08）：

    項次 內容
    硬體 單張 NVIDIA RTX 3090，24GB 顯示記憶體
    存取 SSH 連線，以 VS Code 遠端開發
    規定 必須在個人容器內工作，套件一律裝在容器裡
    推論服務 Ollama，提供相容於 chat completions 的端點
    權限 只能呼叫模型，不能管理模型；要新模型須另外申請

    這件事對本專案有一個直接的好處：實驗室給的是相容端點，院內推論服務（不論 Ollama 或其他）大多也是同一組相容介面。因此 LabApiProvider 與 OnPremiseProvider 共用同一份 HTTP 實作，差別只有端點位址與模型識別字，切換供應者真的只是設定變更（實作規格書 3.4 硬性規則第 1 條）。

    DEP-03｜不得為實驗室 API 寫專屬邏輯。 過渡期若發現端點格式與相容規格有出入，改的是 HttpLlmProvider 的組裝與解析，不是在業務邏輯裡分支判斷現在接的是誰。

    2. 正式環境：院內一台共用 Windows 工作站¶

    2.1 已確認的硬體事實¶

    項次 規格
    處理器 Intel Core i7-14700
    架構 x86-64
    記憶體 64GB
    儲存 2TB SSD ×2
    作業系統 Windows
    GPU 不需要。本系統不做任何本機推論（DEP-16）
    共用狀況 與其他專案共用，院方確保本系統的處理器、記憶體與磁碟額度足夠。實際額度、同機還有哪些專案、誰有這台機器的登入權限，仍待資訊室答覆（Q-27）

    這台機器的規格對本系統來說仍然寬裕，而那是好事。 本系統的負載是 15 床、三班、尖峰同時請求個位數、資料庫是一個以 MB 計的 SQLite 檔案。即使與其他專案分享這台機器，只要院方承諾的額度到位，效能不會是上線初期的問題來源，注意力可以全部放在資料安全與流程正確上。

    但「資源足夠」是一句承諾，不是一個設定。 它要落到數字上才擋得住事：本系統拿得到多少記憶體、資料庫那顆磁碟保留多少可用空間、可以佔用哪幾個連接埠，都要有人寫下來（Q-27）。共用主機上最常見的失敗不是效能不夠，而是某一天別的專案把磁碟寫滿、或先佔走了本系統要用的連接埠——這兩種情形都不會在測試階段出現。

    2.2 四個後果¶

    後果一：主機仍然是共用的。 v1.0 花了大篇幅處理「共用主機」帶來的隔離需求，這一整條完整保留；換了機器只是換了它的落實方式——由容器層級改為安裝包層級（DEP-37）。

    DEP-04｜本系統不得對正式主機的全域環境有任何要求。（保留並加嚴）不得要求院方預先安裝 Node.js、npm 或任何執行期相依，也不得要求院方為本系統調整任何全域設定。理由有兩條：主機上還有別的專案，全域裝了什麼、升級到哪一版，不由本系統決定；以及更根本的一條——院方主機上裝了什麼、什麼時候被更新、被誰更新，都不在開發端的掌握裡。執行期一律隨安裝包帶進去。

    DEP-37｜共用主機上的隔離一律在安裝包層級做到，不要求作業系統層級的隔離。 四件事一起做，缺一件就不算隔離：

    # 要做到 不做會怎樣
    1 執行期隨包攜帶，不使用主機上任何全域安裝的 Node.js 別的專案升級或移除全域 Node.js，本系統跟著壞，而且看起來像是本系統自己壞的
    2 連接埠向資訊室登記後固定下來，值寫在主機的 .env，不寫死在程式碼 與其他專案搶同一個埠，服務起不來；而且多半在某次重新開機、兩個服務的啟動順序對調時才發作
    3 安裝目錄、資料庫目錄、備份目錄三者都在本系統自己的路徑底下，不放共用的暫存或文件目錄 別的專案的清理腳本掃得到本系統的檔案
    4 資料庫與備份目錄的權限只給服務帳號與系統管理員（DEP-12），其他登入者連讀都不行 共用主機上別的專案的維運人員也登得進這台機器，預設權限等於把病人資料攤開

    另外要有一條磁碟空間下限。 本系統不是這台機器上唯一在寫磁碟的人，而 SQLite 在磁碟寫滿時的行為是寫入失敗，不是逐步降級。資料庫所在磁碟的保留空間與監看方式列入 Q-27 一併問清楚。

    這四項裡有三項程式擋得住，一項只能靠人（0919 於迭代 7 落實，見《實作規格書》4.5）：

    DEP-37 程式怎麼擋
    第 1 項 執行期隨包攜帶 PRISMA_ENGINES_DIR 指向包內引擎，版本鎖成確定版本；npm run check:offline 把「這份 node_modules 帶不帶得進院內」列成盤點項
    第 2 項 連接埠固定 正式環境設定下 API_PORT 沒填就拒絕啟動；實際埠號與它是主機設定還是程式預設值，顯示在護理端的「執行環境」上
    第 3 項 目錄是自己的 資料庫與備份目錄指到暫存、公用、桌面、文件、下載等共用位置時拒絕啟動，後端與 db:update 共用同一條判定
    第 4 項 目錄權限 擋不住，這是部署當天的人工確認（檢查清單 9.1 第 9 條）。程式看得到自己以哪個帳號在跑，但看不到別人讀不讀得到那個資料夾

    磁碟下限同樣落成設定（DB_DISK_MIN_FREE_MB，預設 1GB）：可用空間顯示在護理端的資料庫狀態上，低於下限時版本更新會在備份之前就停下——備份做到一半才寫滿，等於在最需要備份的時候沒有備份。

    後果二：架構與開發機相同。

    DEP-05｜（0919 作廢） v1.0 的「正式環境的映像檔一律為 linux/arm64」不再適用。取代它的是 DEP-22。

    DEP-22｜安裝包必須在一台乾淨的 Windows 機器上實際啟動過，只確認建置成功不算。 「乾淨」的意思是那台機器上沒有開發環境、沒有全域安裝的 Node.js、沒有這個專案的任何殘留。在開發機上解壓來測，測到的是開發機，不是安裝包。

    後果三：仍然是一台桌上型機器。 沒有備援電源、沒有磁碟陣列、記憶體不具 ECC。兩顆 SSD 不等於磁碟陣列，除非院方另外做了設定；預設情況下它們只是兩顆各自獨立的磁碟。 而且這兩顆磁碟是和其他專案一起用的——第二顆 SSD 要當備份的第一落點，得先確認它不是別的專案的資料碟。

    DEP-06｜備份目的地必須是院內另一台機器。（保留）第二顆 SSD 可以作為備份的第一落點——快、方便、一天可以做很多次——但不得是唯一落點。整機故障、遭勒索軟體加密、或有人誤刪整個資料夾時，同一台機器上的兩顆磁碟一起沒。

    後果四：它是 Windows。 這是 v1.0 完全沒處理過的一類問題。

    DEP-21｜Windows 特有的三件事，部署前必須逐項確認：

    # 要做的事 不做會怎樣
    1 資料庫目錄加入防毒軟體排除清單 即時掃描會在 SQLite 寫入時開啟同一個檔案，造成間歇性、不固定重現的鎖定失敗。這是最難查的一類錯誤
    2 確認資料庫目錄不在任何雲端同步資料夾底下 醫院電腦常把「文件」重新導向到 OneDrive，而路徑上看不出來。同步資料夾等同把資料庫送出院外，同時毀掉檔案鎖
    3 確認資料庫路徑不是對應網路磁碟機的代號 看起來像本機磁碟，行為是網路檔案系統——正是《資料庫使用規範》7.2 要擋的情形

    另外兩件也要做，但後果沒有上面三件嚴重：關閉該機的自動休眠，以及確認系統更新的重新啟動時段不落在透析班次中。

    主機是共用的，這五件事更容易被推翻。 防毒排除清單、休眠設定、更新時段，別的專案的維運人員一樣改得動，而改掉之後本系統不會收到任何通知。部署紀錄上要寫明這幾項是誰設的、由誰保管，以及改動前要知會誰。

    3. 部署形態：離線安裝包¶

    DEP-07｜（0919 改寫）正式環境以離線安裝包部署，以 Windows 服務常駐。容器降為備案。

    3.1 為什麼改掉容器¶

    v1.0 選容器有三個理由。0919 之後，三個裡只有一個消失，剩下兩個都還在——但那兩個都不必靠容器達成：

    v1.0 的理由 0919
    共用主機需要隔離 仍在。 但它逼出的不是容器：安裝包自帶執行期、裝在自己的目錄、以專用低權限帳號與登記過的連接埠執行，隔離在安裝包層級就做到了（DEP-37）
    跨架構（開發 x86、正式 ARM64）需要一個確定的產物 消失。 兩邊都是 x86-64 Windows
    離線安裝：不能在現場 npm install 仍在，但這一條用安裝包也做得到，而且在 Windows 上做得更乾淨

    而且容器在這台主機上會直接撞到資料庫規範。 Windows 的容器執行環境走 WSL2，於是資料庫檔案只有兩個落點，兩個都有問題：

    落點 問題
    Windows 目錄的繫結掛載 跨檔案系統的轉譯層，SQLite 的檔案鎖不可靠。《資料庫使用規範》7.2 明文禁止
    WSL2 的 Linux 檔案系統（具名資料卷） 檔案鎖沒問題，但資料庫躲進一個虛擬磁碟裡：院方看不到、備份軟體掃不到、資訊室要取用得先學會怎麼進去

    這不是設定調一調的問題，是形態選錯了。 一個裝著整個透析中心照護紀錄的檔案，第一要務是「放在看得到、備份得到、還原得回來的地方」。

    還有兩件次要但真實的事：容器執行環境要先在院方機器上安裝並取得核准（多一道變更流程、可能牽涉授權條款），以及一個 docker save 出來的封存檔對防毒軟體而言是一個不透明的大檔，掃描結果往往是「無法檢查內容」——而完成掃毒正是進院的必經流程（DEP-26）。

    3.2 安裝包裡放什麼、不放什麼¶

    安裝包內（每次更新整包換掉）        主機上（安裝包不碰）
├── Node.js 執行期（隨包攜帶）      ├── SQLite 資料庫檔案（含 -wal、-shm）
├── 後端已建置產物                  ├── 備份輸出目錄
├── 兩個 PWA 的靜態產物             ├── .env（環境設定）
├── Prisma 引擎（見 DEP-30）        └── 服務紀錄檔
├── migration 檔
├── 服務註冊與啟停腳本
└── 版本標記（含對應的 git commit）

    DEP-08｜（0919 改寫）資料庫檔案與備份目錄一律放在主機本機 SSD 的固定目錄，且必須在安裝包目錄之外。 兩者放在一起，某一次「把舊資料夾整個刪掉再解壓新版」就會把資料庫一起刪掉。這種事不會發生在第一次更新，會發生在第五次、由另一個人執行的那一次。

    DEP-09｜-wal 與 -shm 必須與主檔在同一個目錄。 它們與主檔是一組，分開處理會毀損資料庫。

    DEP-10｜後端仍然是唯一開啟資料庫檔案做寫入的行程。 不得同時啟動兩個服務執行個體指向同一個資料庫檔案；備份與資料修補在服務停止後執行，或使用後端自己提供的線上備份端點。

    DEP-11｜不得在正式主機上執行 npm install 或任何建置步驟。（保留）建置全部在開發端完成。理由：正式主機沒有對外連線，而且現場不該有任何「這一步失敗了怎麼辦」的空間。

    DEP-12｜（0919 改寫）服務以專用的低權限帳號執行，資料庫與備份目錄的存取權限只給該帳號與系統管理員，一般登入者不得讀寫。主機是共用的，這一條因此不是形式：同一台機器上別的專案的維運人員也有登入權限，而他們不該讀得到病人資料（DEP-37 第 4 項）。

    DEP-13｜安裝包不得包含 .env、資料庫檔案、備份檔或任何真實資料。（保留）設定一律於安裝時以主機上的 .env 提供。與《資料庫使用規範》第 9 條「不得把資料庫路徑或密碼寫入程式碼」是同一件事的延伸。

    DEP-14｜安裝包啟動時不得連往院外。（保留）零院外連線盤點（npm run check:egress）的掃描範圍涵蓋安裝包的設定檔與啟動腳本。

    3.3 容器備案的啟用條件¶

    容器設定（Dockerfile、docker-compose.yml）保留在 repo 中，不刪除。只在下列任一情形發生時才改走容器路線：

    • 院方資訊室明確要求以容器形式交付
    • DEP-37 的安裝包層級隔離經實際運行後證明不夠，院方要求作業系統層級的隔離
    • 正式主機改為 Linux

    DEP-23｜改走容器路線時，資料庫檔案不得落在 Windows 目錄的繫結掛載上，必須放在 Linux 檔案系統的具名資料卷裡，並另外安排一條把備份送到主機可見目錄的路徑。這一條是 3.1 那張表的結論，換路線時不得重新討論。

    4. 時區¶

    DEP-15｜（0919 落實方式改變）正式主機的時區必須是 Asia/Taipei，後端於啟動時檢查，不符即拒絕啟動。

    v1.0 檢查的是容器的 TZ 環境變數；改成 Windows 主機之後，檢查的是主機時區設定經 Node.js 解析後的結果。規則本身不變，而且必要性不變：

    • 護理師班表與當班床位分配（FR-M01／M02）
    • 勞動條件硬性檢查——連續工時與班距（FR-M04）
    • 每日自動備份的執行時間
    • 稽核軌跡與求助處理的時間顯示

    時區錯八小時，班表會整張錯開一格，而且錯得很像「排班排錯了」，不像系統設定錯誤——這種錯誤不會有人回報成程式問題。

    Windows 上多一個要注意的地方：主機時區正確，不代表服務執行帳號取得的時區正確。檢查要在服務實際執行的身分底下做，不是在管理員的互動式工作階段裡做。

    5. 地端推論服務在另一台機器上¶

    DEP-16｜（0919 強化）本專案不包含、不啟動、也不與任何推論服務同機。

    對本系統而言，地端推論只是一個 HTTP 端點（LLM_ENDPOINT）。0919 之後這件事比以前更單純：那台機器（DGX Spark）與本系統的應用主機是兩台不同的機器，之間只有一條院內網路上的 HTTP 呼叫。

    項次 狀況
    誰維運推論端點 資訊室（待確認，Q-07）
    本系統需要 GPU 嗎 不需要
    端點不通時會怎樣 AI 功能顯示為暫時無法使用；主線功能（症狀回報、求助、總覽、綁定）完全不受影響
    端點位址怎麼來 設定，不寫死

    DEP-24｜AI 端點必須可以整個關掉，而且關掉之後系統要能完整運作。 第一次部署時 AI 功能預設為關（DEP-29），這一條因此在上線第一天就會被實際驗到。

    DEP-17｜模型識別字與端點一律由設定提供。（保留）與實作規格書 3.4 硬性規則第 2 條相同。

    6. 交付：第一次部署的兩條路線¶

    DEP-18｜（0919 改寫）交付物是一份壓縮的離線安裝包加一份啟動設定範本，不是一份安裝手冊。

    第一次正式部署要實際走兩條路線，順序固定，目的不同。

    6.1 路線 A：在正式主機上 git clone 並安裝（預期失敗，仍然要做）¶

    目的不是成功，是取得證據。 這條路線幾乎確定會失敗，而失敗的地方正好就是要寫進交付文件的地方。

    步驟 預期結果
    git clone 失敗。 主機沒有對外連線，連不到 GitHub
    （假設程式碼以其他方式進去了）npm install 失敗。 需要從 npm 套件來源下載數百個套件
    （假設套件裝好了）套用資料庫遷移 失敗。 Prisma 引擎不在套件包裡，要另外下載（見 6.3）

    DEP-25｜路線 A 的每一次失敗都要記錄下來：在哪一步、錯誤訊息的原文、花了多久。 這份紀錄有兩個用途：向資訊室說明「為什麼不能用一般的方式部署」時，它比任何說明都有效；以及日後有人提議「直接在主機上更新就好」時，它是現成的答案。

    路線 A 不得為了讓它成功而在正式主機上開對外連線。 若真的開了，零院外連線這個前提就在第一天被自己破壞。

    6.2 路線 B：隨身碟帶入離線安裝包（正式路線）¶

    開發端                                    院內
建置安裝包 → 壓縮 → 產生雜湊值 → 防毒掃描 → 隨身碟 → 掃描 → 解壓 → 核對雜湊 → 安裝

    DEP-26｜安裝包在進院前與進院後各掃描一次。 開發端掃過一次不代表隨身碟上那份沒事——中間經過一個實體媒介。院內那次由資訊室的防毒工具執行，掃描結果要留存。

    DEP-27｜安裝包必須附雜湊值，解壓後核對。 防毒只回答「有沒有惡意內容」，不回答「是不是我給的那一份、有沒有在路上壞掉」。

    DEP-28｜隨身碟是單向的。（呼應《資料庫使用規範》8.1）只能把安裝包帶進院內，不得帶任何資料出院——不是備份、不是紀錄檔、不是截圖。用完當場清除，並在部署紀錄上寫明「已清除」與執行者。

    待確認：院方對外來儲存媒體的規定、是否須事先報備、是否有指定的掃描站（Q-29）。

    6.3 離線環境的 Prisma 引擎（一個已知會卡住的地方）¶

    症狀：全程離線的建置測試中，套用資料庫遷移的步驟失敗，錯誤是

    request to https://binaries.prisma.sh/... failed, reason: getaddrinfo ENOTFOUND binaries.prisma.sh

    原因：Prisma 的執行引擎（schema engine 與 query engine）不在 npm 套件裡。套件安裝時由 @prisma/engines 的安裝後腳本另外下載，約 40MB。因此只要 node_modules 是在沒有成功下載引擎的情況下產生的——離線安裝、跳過安裝後腳本、或從別處複製過來而排除了二進位檔——第一次用到 Prisma 指令時就會現場去下載，而那時已經沒有網路。

    這不是設定錯誤，是一個「套件裝好了不代表可以用」的相依。

    DEP-30｜安裝包必須自帶 Prisma 引擎，並以設定指向它們，不得依賴安裝後腳本。 三件事一起做：

    # 做什麼
    1 建置安裝包時，把引擎檔一併收進包裡（來源是開發端已下載好的那份）
    2 啟動與遷移時以環境變數指向包內的引擎路徑，不讓 Prisma 自己去找
    3 把 Prisma 的版本鎖成確定版本，不用可浮動的版本範圍。引擎與 CLI 的版本必須一致，浮動的版本範圍會在某次重新安裝時悄悄換掉其中一邊

    DEP-31｜正式環境一律使用「套用既有遷移」的指令，不得使用開發用的遷移指令。 開發用的那支在偵測到資料庫與遷移歷史對不上時，會提議或直接重建整個資料庫（《資料庫使用規範》18.1 第 3 關）。這一條與離線引擎是兩件事，但會在同一個指令上相遇，所以寫在一起。

    驗收方式：把離線建置測試的步驟改成「連網只發生在建置安裝包的那台機器上」，院內端全程離線，從解壓到服務起來不得出現任何一次對外請求。

    6.4 更新¶

    DEP-19｜（0919 改寫）每次更新都要能回到上一版，而且更新不得破壞既有資料。

    完整規則在《資料庫使用規範》第 18 條，此處只列部署端的動作：

    順序 動作 不做會怎樣
    1 停止服務 資料庫還有寫入時做的備份不可靠
    2 執行備份並驗證它還原得起來 「有備份」和「備份能用」是兩件事
    3 保留舊版安裝包目錄（改名，不刪除） 沒有可以退回去的東西
    4 解壓新版安裝包到新目錄
    5 套用遷移（用 DEP-31 那支指令）
    6 啟動服務，確認主線功能
    7 把這次更新寫進紀錄（規範 18.4） 半年後沒有人答得出資料是哪一次更新弄壞的

    DEP-32｜更新排在非透析時段，且更新後的第一個班次要有人在。 這不是謹慎，是算術：問題在累積新資料之前被發現，還原備份的代價是零；之後才發現，代價是那段期間的所有紀錄。

    DEP-20｜前端更新不需要逐台處理平板。（保留）PWA 由伺服器提供，平板下次開啟即為新版。0919 補充：改走自包 WebView 外殼之後這一點仍然成立——外殼只是載入器，網頁改了不必重發 APK；只有改動外殼本身（權限、設定、憑證）才需要逐台側載 15 次（平板管控方案 6.2）。

    7. 第一次部署的範圍與時程¶

    7.1 首波只開放少數護理師與病人¶

    DEP-33｜第一次部署為首波試用，不是全單位上線。 這件事要寫在部署紀錄與交接文件上，因為它改變了好幾個判斷的基準：

    項次 首波的狀況
    使用者 少數護理師（護理站的一兩台電腦）、少數病人
    併發量 遠低於設計值。不要拿首波的效能數字當成全單位上線的依據
    成效基準量測（Q-01） 順延至下週執行。首波期間紙本流程仍在跑，量測的時機還沒過
    三項高風險功能 尚未實作，不提供服務
    管理儀表板、獎勵、對外揭露 尚未實作，不提供服務

    DEP-34｜尚未實作的功能一律不提供服務，而不是提供一個停用的入口。 介面上不出現、後端端點一併擋下，不以「敬請期待」、灰色按鈕或停用樣式呈現。理由有兩個：停用的入口會被當成故障回報，以及一個點得到但沒反應的按鈕，會讓使用者對整套系統的其他部分也失去信任。

    7.2 首波要關閉的功能¶

    DEP-29｜下列功能於第一次部署時關閉，之後可在護理端系統設定開啟（FR-S11），不需要重新部署。

    關閉的東西 為什麼 什麼時候開
    三項高風險功能（FR-P03／P05／N06） 尚未實作；且需要法務書面確認與臨床端門檻值 實作完成且兩項外部答覆到齊
    所有需手持裝置的功能（例如「我到床邊了」） 護理師手上沒有平板或手機，護理端只在護理站的電腦上開。硬留著只會得到事後補按的假資料 護理師配發行動裝置後
    班表、成效基準 首波不排班、基準下週才量 下週
    離院衛教 首波不做下機衛教流程 護理部確認流程後
    L3 個人層級績效 需護理部書面同意（FR-M11） 同意到位後
    AI 生成功能 推論端點尚未確認（Q-07）；且首波應先確認主線穩定 端點就位且健康檢查通過
    輪播第二層 護理部尚未提供衛教與公告內容 內容上架後自動可開

    階段 時點 做什麼
    一 本週 部署前修正四個迭代完成 → 建置安裝包 → 走路線 A 取得失敗證據 → 走路線 B 正式部署 → 首波試用
    二 下週 成效基準量測（Q-01）；規則引擎與三項高風險功能；管理儀表板與對外揭露

    8. 病人端平板的佈建¶

    完整方案見《平板管控：免 MDM 的全院內方案》，本節只列部署時要做的動作與它們的順序。

    8.1 伺服器端（做一次）¶

    1. 產生院內自簽 CA 與伺服器憑證，CA 根憑證交給外殼 App 打包
    2. 安裝並啟動本系統（第 3、6 章）
    3. 建立 15 台裝置清單，產生各台的序號與金鑰

    DEP-35｜CA 的簽名金鑰與 APK 的簽名金鑰遺失即無法補救。 兩者建立後立即異地備份（院內，不出院），並寫進交接文件。APK 簽名金鑰遺失的後果是「再也發不出更新版，只能換套件名重新側載 15 台」。

    8.2 平板端（每台各做一次，15 次）¶

    1. 設定裝置 PIN，關閉新增使用者
    2. 開啟允許安裝不明來源應用程式
    3. 側載 APK
    4. 首次啟動，輸入或掃描該台的序號與金鑰
    5. 設定 → 安全性 → 開啟螢幕固定，勾選「解除固定前要求 PIN」
    6. 開啟 App 並釘住
    7. 記錄序號與床號的對應，核對護理端裝置清單

    DEP-36｜首波試用只佈建實際會用到的台數，其餘維持原狀。 15 台全部佈建完再開放，等於把佈建的錯誤一次放大 15 倍；先佈建兩三台、跑過一個完整班次、確認流程沒問題，再佈建其餘。

    每日要做的一件事（納入交班檢查表）：前一天有重新開機的平板要重新釘選。 App 會自動啟動，但螢幕固定不會自動恢復。護理端總覽看得到哪一台跳出了 Kiosk，不必逐台目視。
