    血液透析中心平板照護輔助系統 — 部署規範¶

    版本：v1.0　文件狀態：草案　適用讀者：FDE 工程團隊、醫院資訊室

    0. 本文件與其他文件的關係¶

    本文件把「這套系統最後要跑在哪裡、用什麼形態跑、怎麼交到院方手上」收斂成可執行的決策。

    • 《軟體需求規格書》：功能需求來源
    • 《資料庫使用規範》：資料治理強制規則。資料庫檔案、備份與加密的規定以該文件為準，本文件只補「在容器裡怎麼落實」
    • 《實作規格書》：範圍界定與技術棧。功能範圍與技術選型衝突時仍以該文件為準
    • 《FDE 數位化評估報告》：選型理由與背景脈絡
    • 《尚待確認事項清冊》：本文件的待確認事項一律指回 Q 編號，不在此另立清單

    本文件擁有最終決定權的範圍只有三件事：部署形態（容器或直接安裝）、環境界線（哪個環境可以放什麼資料）、交付方式（映像檔怎麼進院內）。這三件事以外的爭議一律回到上列文件。

    本文件的強制規則以 DEP-xx 編號，其他文件引用時寫編號，不複製內容。

    1. 三個環境¶

    開發環境 過渡環境 正式環境
    機器 FDE 的 Windows 筆電 實驗室主機（院外） 院內 NVIDIA DGX Spark
    架構 x86-64 x86-64 ARM64（aarch64）
    執行形態 npm run dev，不容器化 容器（實驗室規定） 容器
    資料庫 本機 SQLite 檔案 不放資料庫 本機磁碟 SQLite 檔案
    可用資料 合成資料 僅合成資料 真實病人資料
    AI 供應者 MockLlmProvider LabApiProvider OnPremiseProvider
    對外連線 僅開發工具（npm、Prisma 引擎下載） 有 零（FR-S07）

    DEP-01｜三個環境的資料界線不得跨越。 過渡環境在院外，任何真實病人資料不得進入；此限制由 LabApiProvider 的合成資料檢查以程式強制（FR-S06），不靠人的自律。

    DEP-02｜開發環境不容器化。 理由不是偷懶：Windows 的 Docker Desktop 會把 SQLite 檔案掛進 WSL2 的檔案系統，而《資料庫使用規範》7.2 明文禁止把資料庫放在檔案鎖行為不可靠的位置。開發期強行容器化，第一個壞掉的就是資料庫。開發環境維持 npm run dev，容器只在建置與正式部署時出現。

    1.1 過渡環境的實際形態¶

    實驗室資源的已知條件（見 Q-08）：

    項次 內容
    硬體 單張 NVIDIA RTX 3090，24GB 顯示記憶體
    存取 SSH 連線，以 VS Code 遠端開發
    規定 必須在個人容器內工作，套件一律裝在容器裡
    推論服務 Ollama，提供相容於 chat completions 的端點
    權限 只能呼叫模型，不能管理模型；要新模型須另外申請

    這件事對本專案有一個直接的好處：實驗室給的是相容端點，院內推論服務（不論 Ollama 或其他）大多也是同一組相容介面。因此 LabApiProvider 與 OnPremiseProvider 共用同一份 HTTP 實作，差別只有端點位址與模型識別字，切換供應者真的只是設定變更（實作規格書 3.4 硬性規則第 1 條）。

    DEP-03｜不得為實驗室 API 寫專屬邏輯。 過渡期若發現端點格式與相容規格有出入，改的是 HttpLlmProvider 的組裝與解析，不是在業務邏輯裡分支判斷現在接的是誰。

    2. 正式環境：NVIDIA DGX Spark¶

    2.1 已確認的硬體事實¶

    Q-07 原本問的兩件事（128GB 是哪一種記憶體、有沒有 GPU）已有答案：

    項次 規格
    處理器 GB10 Grace Blackwell，20 核心 Arm（10× Cortex-X925＋10× Cortex-A725）
    架構 ARM64（aarch64）
    GPU Blackwell 架構，與處理器共用同一塊記憶體
    記憶體 128GB LPDDR5x 統一記憶體，頻寬約 273 GB/s
    儲存 4TB NVMe，硬體自我加密
    作業系統 NVIDIA DGX OS（以 Ubuntu 為基礎）

    「統一記憶體」的意思：128GB 由處理器與 GPU 共用，不是「系統記憶體 128GB，另外還有顯示記憶體」。這比原評估的情境 A（純 CPU）好得多，模型載入量接近情境 C；但記憶體頻寬約 273 GB/s，遠低於資料中心級顯示卡，吐字速度不會快。

    結論：載得下大模型，但跑不快。 這正好符合本系統的負載特性——尖峰同時請求數不超過個位數，瓶頸在單次延遲而非吞吐量。

    2.2 三個後果¶

    後果一：主機是共用的。 DGX Spark 上不只本專案。這代表：

    • 系統套件、Node.js 版本、連接埠都可能與別的專案衝突
    • 記憶體是共用的。別的專案載入一個大模型，本系統可用的就少了
    • 不能假設任何全域安裝的東西會一直在

    DEP-04｜本系統不得對正式主機的全域環境有任何要求。 除了容器執行環境本身，不得要求院方在主機上安裝 Node.js、npm 或任何執行期相依。

    後果二：架構是 ARM64。 開發筆電是 x86-64。

    DEP-05｜正式環境的映像檔一律為 linux/arm64。 在 x86 機器上以預設設定建置出來的映像檔在 DGX Spark 上不會執行。建置方式二選一：以 docker buildx --platform linux/arm64 跨架構建置，或直接在目標機器上建置。交付前必須在 ARM64 上實際啟動過一次，只確認建置成功不算。

    後果三：DGX Spark 是開發與原型用的桌上型機器，不是機房等級伺服器。 沒有備援電源、沒有磁碟陣列、記憶體不具 ECC。

    DEP-06｜備份目的地必須是另一台機器。《資料庫使用規範》8.1 允許「同機或院內另一台」，但在這個硬體上只接受院內另一台。單檔 SQLite 配上無備援的單機，同機備份等於沒有備份。

    3. 部署形態：容器¶

    DEP-07｜正式環境以容器部署。

    3.1 四個理由¶

    理由 說明
    共用主機的隔離 Node.js 版本、系統套件、連接埠全部鎖進映像檔，不與其他專案互相影響（後果一）
    交付可重現 交付的是一份確定的映像檔，不是一份「請照著裝」的說明。院方不必逐步執行安裝步驟，也就沒有步驟被漏掉的可能
    離線安裝 映像檔在開發端建好、打包帶進院內。院內主機不需要任何對外連線即可安裝與啟動（FR-S07）
    回復容易 版本有問題時換回上一個映像檔標籤即可，不必反向拆解安裝過程

    3.2 容器裡放什麼、不放什麼¶

    映像檔內（不可變）              主機上（掛載進容器）
├── 後端已建置產物              ├── SQLite 資料庫檔案（含 -wal、-shm）
├── 兩個 PWA 的靜態產物         ├── 備份輸出目錄
├── Prisma migration            └── .env（環境設定）
└── Node.js 執行期

    DEP-08｜資料庫檔案與備份目錄一律以主機本機磁碟的繫結掛載提供，不得放在映像檔內，也不得使用走網路的儲存驅動。 容器一重建，寫在映像檔層裡的資料就沒了；而網路儲存上的 SQLite 檔案鎖不可靠（《資料庫使用規範》7.2）。掛載來源必須是 DGX Spark 的 NVMe 本機路徑。

    DEP-09｜-wal 與 -shm 必須與主檔在同一個掛載點。 它們與主檔是一組，分開掛載會毀損資料庫。

    DEP-10｜後端仍然是唯一開啟資料庫檔案做寫入的行程。 容器化不改變這一條：不得同時啟動兩個後端容器指向同一個資料庫檔案。備份與資料修補以 docker exec 進入既有容器執行，不另起第二個容器。

    3.3 映像檔規則¶

    DEP-11｜不得在正式主機上執行 npm install 或任何建置步驟。 建置全部在開發端完成。理由有二：正式主機沒有對外連線；共用主機上的建置會佔用別的專案的資源。

    DEP-12｜映像檔以非 root 使用者執行，並且掛載目錄的擁有者要與該使用者一致。共用主機上的權限問題比單機嚴重。

    DEP-13｜映像檔不得包含 .env、資料庫檔案、備份檔或任何真實資料。 設定一律於啟動時以環境變數或掛載提供。這一條與《資料庫使用規範》第 9 條「不得把資料庫路徑或密碼寫入程式碼」是同一件事的延伸。

    DEP-14｜基底映像不得在啟動時連往院外。 零院外連線盤點（npm run check:egress）的掃描範圍涵蓋容器設定檔。

    4. 時區¶

    DEP-15｜容器必須明確設定 TZ=Asia/Taipei。

    這一條單獨列出來，因為它最容易漏而且後果最嚴重。Linux 容器的基底映像預設時區是 UTC，而本系統有大量以伺服器當地時間為準的邏輯：

    • 護理師班表與當班床位分配（FR-M01／M02）
    • 勞動條件硬性檢查——連續工時與班距（FR-M04）
    • 每日自動備份的執行時間（BACKUP_DAILY_AT）
    • 稽核軌跡與求助處理的時間顯示

    時區錯八小時，班表會整張錯開一格，而且錯得很像「排班排錯了」，不像系統設定錯誤——這種錯誤不會有人回報成程式問題。後端於正式環境啟動時會檢查 TZ 是否設定，未設定直接拒絕啟動。

    5. 地端推論服務不由本專案部署¶

    DEP-16｜本專案的容器不包含、也不啟動任何推論服務，不需要 GPU 存取權限。

    對本系統而言，地端推論只是一個 HTTP 端點（LLM_ENDPOINT）。理由：

    • DGX Spark 是共用主機。由本專案自行載入模型，等於跟其他專案搶同一塊 128GB 統一記憶體
    • 推論服務由誰維運、載哪些模型，是資訊室的決定，不是本專案的實作細節
    • 本專案的容器因此不需要 NVIDIA 容器工具鏈，部署難度下降一個層級

    待資訊室確認：推論服務由誰提供與維運、端點位址、可用模型清單、以及在共用狀況下本專案的記憶體額度。見 Q-07。

    DEP-17｜模型識別字與端點一律由設定提供。 與實作規格書 3.4 硬性規則第 2 條相同，此處不重複，僅強調容器化後它落在啟動時的環境變數，不是映像檔內的檔案。

    6. 交付與更新¶

    DEP-18｜交付物是一份離線映像檔封存檔加一份啟動設定，不是一份安裝手冊。

    交付物 內容
    映像檔封存檔 docker save 產出，在院內以 docker load 載入
    啟動設定 compose 檔，含掛載路徑、連接埠、環境變數欄位
    環境變數範本 .env.example，一律空值
    版本標記 映像檔標籤與對應的 git commit

    DEP-19｜每次更新都要能回到上一版。 舊映像檔在新版穩定前不得刪除。資料庫 migration 若不可逆，更新前必須先完成一次備份並確認可還原——《資料庫使用規範》8.1「沒有還原過的備份不算備份」。

    DEP-20｜前端更新不需要逐台處理平板。 PWA 由伺服器提供，平板下次開啟即為新版；這是選 PWA 的理由之一（FDE 報告 7.1），容器化不改變這一點。

    7. 什麼時候搬進容器¶

    容器化改的是部署封裝，不改業務邏輯。太早做只是多維護一份東西，太晚做會在最忙的時候同時撞上架構、掛載與時區三件事。

    階段 時點 做什麼
    一 迭代 6 期間（現在） 建立容器設定，作為產出正式映像檔之用；在 ARM64 上建置並啟動過一次。日常開發不走容器
    二 迭代 7 完成後、臨床試用前 於 DGX Spark 實機部署，跑完整驗收腳本全綠，並實際演練一次還原

    判準一句話：容器化要排在「第一次把系統交到資訊室手上」的前一個迭代，不是更早。

    8. 部署前置檢查清單¶

    上線前逐條確認，缺一條就不算可以部署。

    # 要確認什麼 對應
    1 映像檔為 linux/arm64，且已在 DGX Spark 上實際啟動過 DEP-05
    2 TZ=Asia/Taipei 已設定，班表與備份時間顯示正確 DEP-15
    3 資料庫檔案與備份目錄掛載至 NVMe 本機路徑，非網路儲存 DEP-08
    4 四項 PRAGMA 實測生效，正式環境 synchronous=FULL 規範第 7 條
    5 備份目的地為院內另一台機器，並已實際還原成功一次 DEP-06、DEP-19
    6 NVMe 自我加密已啟用 規範第 9 條
    7 npm run check:egress 全綠，含容器設定檔 FR-S07、DEP-14
    8 LLM_PROVIDER=onprem，端點可連線且健康檢查通過 FR-S06
    9 功能開關確認：高風險三項與 L3 績效皆為關閉 FR-S08
    10 常駐總覽螢幕就位且不進入休眠 FR-N12
    11 透析區 Wi-Fi 覆蓋實測通過 Q-12
    12 容器以非 root 執行，掛載目錄權限正確 DEP-12
