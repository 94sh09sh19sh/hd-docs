# 尚待確認事項清冊 Q-35 院方透析清單 API 的使用報備與連線

上層文件：《[尚待確認事項清冊](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/open-questions/index.md)》第 4 章

|            |                                                                                                                                   |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **問誰**   | 負責 IDH 系統的學長（1108 起；原本是資訊室）                                                                                      |
| **急迫度** | **C**                                                                                                                             |
| **卡住**   | 迭代 15 的院方 API 對真實資料啟用。**介接程式 1005 已寫好**：設定目錄的 `.env` 填上位址就開始抓，等的就是這一題與第三次進院的探測 |
| **狀態**   | 待提出（1005 新增）                                                                                                               |

**背景**

1005 使用者決定本系統直接使用同院 IDH 預警系統正在用的那支透析清單 API，並且**全面取代手動輸入**（SRS FR-S15）。那支 API 參考程式呼叫時不帶任何認證，技術上呼叫得到；但本系統要每 3 分鐘抓一次**全中心**的病人資料，而且病人主檔、床位、療程都靠它。參考調查第 9.2 節第 1 項原本建議「寫介接程式前用一封信報備」，1005 起介接程式排進迭代 15，這一題因此獨立出來。

**不確認的後果**

- 沒有報備：日後院方查起來，本系統在抓全中心的資料卻沒有任何紀錄，也對不上 Q-06 的資料使用範圍
- 主機連不到：本系統跑在另一台主機上，與 IDH 系統不一定在同一個網段；連不到的話，迭代 15 做好也用不了
- API 改版或停機沒人通知：病人、床位、療程全部停在最後一次成功的樣子，護理師不一定馬上發現（系統會在護理端標示「院方資料已 N 分鐘未更新」）

**具體要問的**

| #   | 問句                                                                        |
| --- | --------------------------------------------------------------------------- |
| 1   | 本系統也要呼叫這支 API（每 3 分鐘、查當天全中心），要不要報備或申請？向誰？ |
| 2   | 本系統所在的主機，連得到那台 PHP 伺服器嗎？要不要開防火牆？                 |
| 3   | 那支 API 會不會改版或停機維護？改的時候能不能通知本專案？                   |
| 4   | 有沒有呼叫頻率的限制？                                                      |
| 5   | 它是不是本院區那台？成大、斗六各有一台，本系統要用的是哪一個位址？          |

**現況／暫代做法**

開發與驗收全部用**模擬院方 API**（合成資料、同格式），不碰真的那一支。第三次進院以探測工具從主機的容器打一次（實作規格書 4.19）：**第 2 題當場就有答案**，其餘照問。API 的院內位址只寫在院內的 `.env`，不寫進任何文件。

**1108 補充：呼叫者換了，問法要跟著換。** 負責 IDH 系統的學長 1107 要求院方 API 只由主機上一支獨立腳本呼叫、存成檔，本系統與另一組讀檔；使用者 1108 決定照做（實作規格書 3.5 的 1108 段落）。第 1 題改問：「主機上的腳本每 N 分鐘呼叫一次、存成檔，本系統與另一組讀這些檔，要不要報備？存檔的位置與留存期限要不要院方核可？」第 4 題的頻率是腳本的設定；第 2、3、5 題照舊。學長 1107 沒有回答「這樣算不算有醫師授權」，本題仍待提出（《[院方 API 介接之一](https://94sh09sh19sh.github.io/hd-docs/latest/notes/hospital-api-fetch-methods-status/index.md)》第 3、7.3 節）。

**1108 補充二：問誰改成學長。** 使用者 1108 轉述：上週開會醫師明確表示 API 相關事宜授權學長決定。授權不必再問醫師；第 1、3 題（要不要報備、改版會不會通知）改問學長，要不要再知會資訊室也由學長決定。第 2 題的主機就是學長說的那台（現場三台最右邊那台，腳本與本系統同一台）。1108 交給學長的問法在《[之二：1108 給學長的問題清單](https://94sh09sh19sh.github.io/hd-docs/latest/notes/hospital-api-fetch-methods-questions/index.md)》H-1、H-2（第一版的第 7 題）。

**1108 補充三：第 4 題也改問學長。** 呼叫頻率與速率限制併進之二 F-3，連同「護理站還能不能調頻率」「重新整理能不能讓腳本馬上抓」一起問；腳本由學長管，頻率不再是本系統的營運參數能單獨決定的。

**1111 迭代 32 做完**：本系統只讀兩個資料夾（唯讀掛載），一次都不打院方 API；呼叫院方的只剩兩支抓取腳本（透析清單每 3 分鐘、檢驗資料 `hb` 每 6 小時），報備時 `hb` 一起報（之一 7.3 的問法）。**1111 稍晚**：學長答 `hb` 不用這邊處理（院方 API 之二 A-5），這邊只裝透析清單那支、院內先不讀檢驗資料，報備也只報透析清單。

**1114 補充：五題都有結論了。** 第 1 題 1111 學長答不用另外知會（之二 H-1，醫師授權學長、學長說了算）；第 2 題 1029 探測從主機連得到；第 3 題 1114 學長答「不知道會不會通知」（之二 H-2）——當成不會通知，靠護理站「院方資料同步」卡的腳本狀態與「未更新」提示發現，格式一改不合格的那一次透析整次不寫、不會寫錯；第 4 題頻率先每 3 分鐘、1114 起只在 07:00～23:00 抓（之二 F-3、F-6）；第 5 題用本院區那台（私人 repo 的 `values.md`）。《第五次進院任務二之三》A-02 不再擋上線。
