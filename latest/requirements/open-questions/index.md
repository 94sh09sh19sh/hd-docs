**這份文件是專案唯一的待確認事項總表。** 其餘五份需求文件不再各自維護清單，它們對「待確認」的引用一律指回這裡。要知道現在卡在誰身上、卡了什麼、不解決會怎樣，看這一份就夠。

## 0. 怎麼用這份文件

### 0.1 急迫度分級

| 級別  | 定義                                                     | 處理原則                     |
| ----- | -------------------------------------------------------- | ---------------------------- |
| **A** | **過期就作廢。** 錯過某個時點，答案永遠拿不到            | 立刻提出，不排隊             |
| **B** | 阻塞「對真實病人或真實資料啟用」。功能做得出來，但不能開 | 開發照做，同時併行催         |
| **C** | 阻塞實作決策或硬體選型。不確認就只能猜，猜錯要重工       | 提出後暫用可替換的介面層頂著 |
| **D** | 可先用暫代值。答案來了替換掉即可，不影響架構             | 一併問，但不擋進度           |

**分級的意思不是重要性，是時間性。** D 級的事項可能對臨床很重要（例如症狀問卷題目要不要改），但它晚兩週回覆不會造成任何重工；A 級只有一項，晚兩週就永久損失。

### 0.2 狀態

| 狀態       | 意思                                                   |
| ---------- | ------------------------------------------------------ |
| **待提出** | 開發端尚未正式問出去                                   |
| **已提出** | 已問，等回覆。記錄提出日期與受詢問單位                 |
| **已回覆** | 有答案了，但還沒反映到文件或程式                       |
| **已結案** | 答案已反映到對應文件與實作，移到第 7 章                |
| **作廢**   | 需求變更或時點已過，不再需要答案。**要寫明為什麼作廢** |

### 0.3 維護方式

- 每週三定版日檢視一次，更新狀態欄
- 新問題隨時加，編號只增不重複使用；已結案的移到第 7 章但**保留原編號**
- 其他文件要引用某個待確認事項時，寫 `Q-0X` 編號，不要複製內容過來（複製就會有兩份不同步的清單）
- 答案回來後，**先改對應的需求文件，再把這裡的狀態改成已結案**，順序不要顛倒

## 2. A 級：過期就作廢

### Q-01 成效基準的量測人力與時程

|            |                                                                                                       |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **問誰**   | 護理長（量測執行）、護理部（背書）                                                                    |
| **急迫度** | **A —— 唯一過期作廢的一項**                                                                           |
| **卡住**   | 新增任務一之(1)「向長官與政府展現重要性」的全部說服力                                                 |
| **狀態**   | **已排定下週執行（0919）**。FR-M07 的建檔介面早在 0911 完成，系統這一側不再是瓶頸，**只差現場的數字** |

**背景**

成效基準是「系統啟用前，同一件事要花多久」。例如病人按鈴到護理師走到床邊，現在平均幾分鐘。系統上線後這個數字會自動被記錄，但**上線前的數字不存在於任何地方**——它只存在於現在正在發生的紙本與口頭流程裡。

要取得它，需要有人在治療區實測：碼表、紀錄表、三個班次、每項約 20 筆。這佔用護理師工時，是**一次性成本**。

**0919：為什麼「這週部署、下週量測」不算把它放掉。** 第一次部署是**首波試用，只開放少數護理師與少數病人**（DEP-33）。紙本流程對其餘的班次與病人**仍然照舊在跑**，因此「以前要花多久」還量得到。真正關上這扇門的不是第一次部署，是**全單位改用系統的那一天**。

但這不代表可以再拖：首波試用的存在本身就在改變現場的習慣，而且一旦護理長覺得「系統都上了，還量什麼」，這件事就會自然消失。**下週要做，而且要在會議上被指定給一個人。**

**不確認的後果**

系統一上線，紙本流程就消失，再也無從量測「以前要花多久」。屆時所有「省下 X 分鐘」的說法都只能靠估算，經不起長官追問。這會直接掉掉新增任務一的第一個目的——沒有基準，只能說「系統很方便」；有基準，才能說「按鈴到到場從 4.2 分鐘降到 1.6 分鐘」，後者才寫得進評鑑資料。

**先問這一題，可能省掉一半工作**

> 護理部現在有沒有已經在統計的品質指標？例如透析中低血壓事件數、跌倒件數、護理紀錄完成時間、病人滿意度調查。

現成的數字比重新測便宜太多，而且是護理部自己的資料，拿去給長官看時公信力更高。**先撈現成的，撈不到的才實測。**

**具體要問的七題**

| #   | 問句                                                             | 為什麼要問                                               |
| --- | ---------------------------------------------------------------- | -------------------------------------------------------- |
| 1   | 預計哪一週開始對真實病人試用？                                   | 從這天往回推，量測必須在這之前做完                       |
| 2   | 現行的紙本記錄單、交班表、呼叫鈴流程能不能給一份？               | 測的東西要對得上現行流程，否則數字沒有可比性             |
| 3   | 能不能指定一位種子護理師協助，而不是全員配合？                   | 一個人記三個班次就夠，全員配合會變成大家的負擔           |
| 4   | 下面五項要測的事，哪幾項不值得測、或該換成別的？                 | 清單是開發端擬的，護理長才知道現場真正的痛點             |
| 5   | 每項 20 筆、分三班取樣，可行嗎？                                 | 樣本數要當面談，太多做不完、太少沒說服力                 |
| 6   | 之後這些數字要給院長室看，誰來背書說「這是本單位認可的基準」？   | 現在講好，比事後被質疑「這數字哪來的」好                 |
| 7   | 願不願意同時做一次護理師自陳問卷（紙本記錄有多少是事後補寫的）？ | 這題不用碼表，但很能打動長官——它量的是「以前有多不精確」 |

**建議量測的五項**（第 4 題請護理長刪減）

| #   | 要測的事                               | 怎麼測             | 建議樣本       |
| --- | -------------------------------------- | ------------------ | -------------- |
| 1   | 病人按鈴到護理師到床邊                 | 現場碼表抽測       | 分三班各 20 次 |
| 2   | 一次事件記錄從動筆到完成               | 護理師自記起訖時間 | 20 筆          |
| 3   | 每班口頭重複衛教的次數與時長           | 觀察記錄           | 3 個班次       |
| 4   | 交班時查找病人資訊的耗時               | 觀察記錄           | 3 個班次       |
| 5   | 紙本記錄「當下寫」與「事後補寫」的比例 | 護理師自陳問卷     | 全單位         |

**0911 實作現況**

建檔介面已完成（護理端「成效基準」頁）。五條指標的定義、建議量測方式、建議樣本數都已建好，畫面逐條列出「尚未建檔」與「只有估算值」兩種缺口——上線前只有這個畫面看得出來還差什麼。

建檔時**必須填背書者**（本頁第 6 題的那個人），空著存不進去：沒有出處的數字，被院長室問到「這數字哪來的」就答不出來。同一條指標可以重測重建，舊版保留並標記為已被取代，不會被蓋掉。

**如果來不及測（退路，但要標明）**

可以用回溯式自陳問卷（請護理師估「以前大概要多久」），或從現有紙本紀錄推估。但這種數字在文件與簡報上**必須標明是估算**，不能當實測講。被長官問到來源時遮掩一次，後面所有數字的可信度都跟著沒了。

這條退路已寫進系統：建檔時來源可選「估算（非實測）」，選了之後該筆資料在所有畫面上都會帶著「引用時必須標明是估算，不得當成實測數字陳述」的提示，建檔進度表也會把「只有估算值」的指標另外列出來。**把退路做進系統，是為了讓它留下痕跡，不是為了讓它變得方便。**

**這一項與前提四的輕微衝突**

《[FDE 評估報告](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/fde-assessment/index.md)》前提四要求「不得影響主要使用功能」，而基準量測會佔用護理師時間。這是刻意接受的例外：一次性成本，且不做就沒有第一個目的。降低衝擊的做法就是第 3 題——指定一位種子護理師，不要全員配合。

這五項的共同特徵是：**功能可以 100% 做完並用合成資料驗收，但不能對真實的人或真實的資料開。** 因此它們不擋開發進度，只擋上線。

### Q-02 三項高風險功能的 TFDA 分類書面確認

|            |                                              |
| ---------- | -------------------------------------------- |
| **問誰**   | 醫院法務、資訊室（必要時由醫院向食藥署函詢） |
| **急迫度** | B                                            |
| **卡住**   | 迭代 7 的啟用（FR-R08）。實作不受阻          |
| **狀態**   | 待提出（0909 已列為待決，尚未取得書面回覆）  |

**背景**

三項功能——FR-P03 風險分層、FR-P05 療程中預警、FR-N06 劑量調整參考——一旦其輸出被拿來做臨床判斷依據，在台灣可能落入《醫療器材管理法》的軟體醫療器材（SaMD）範疇。

開發端的設計取向是盡量讓它們停在「提供資訊、由專業人員自行判斷」的一側：用可攤開的規則而非語言模型、輸出可回溯到依據、不自動生效、措辭為事實陳述而非結論。但**分類判定權不在開發端**，本專案自行判斷不具法律效力。

**不確認的後果**

功能做得出來但不能對真實病人開。更糟的情況是先開了、之後才發現需要走查驗登記，屆時已經產生了臨床使用紀錄，處理起來比事前確認麻煩得多。

**具體要問的**

1. 這三項功能，依院方目前的理解，是否落入醫療器材軟體管理範疇？
1. 如果不確定，醫院是否有既有管道向食藥署函詢或申請分類分級諮詢？要多久？
1. 院內是否有其他已上線的臨床決策支援系統走過同樣的判定？走的是哪一條路？
1. 若判定為需要查驗登記，院方的立場是「調整功能設計以避開」還是「走完認證」？
1. 開發端的八條控制措施（規則可攤開、依據可複核、不自動生效、事實陳述式措辭、檢視與採納留痕、可全域關閉）是否足以佐證「非醫療器材」的主張？還缺什麼？
1. 在書面確認到位之前，用合成資料開發與內部驗收是否有任何限制？

**現況／暫代做法**

以功能開關實作硬閘門（`RISK_STRATIFICATION`／`INTRA_DIALYSIS_ALERT`／`DOSE_REFERENCE`），三者預設關閉，開啟需留核准紀錄。閘門未開時，三項功能只對已標記為合成資料的病人執行。

**要帶去談的材料**

《[FDE 評估報告](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/fde-assessment/index.md)》第八章的 R-1～R-8 控制措施表，以及《[軟體需求規格書](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/srs/index.md)》5.6 節。這兩份就是「我們做了哪些事讓它不像醫療器材」的完整說明。

**具體要問的**

1. 依《醫療法》的病歷留存規定，本系統的病人自報症狀與求助紀錄算不算病歷的一部分？要留幾年？
1. 稽核軌跡要留多久？醫院既有系統的慣例是多少？
1. AI 呼叫紀錄（提示與輸出）開發端建議留 12 個月，之後只留統計列。可以嗎？
1. 護理師績效彙整結果依人資規定要留多久？
1. 到期後是刪除、還是轉為離線封存？封存放在哪裡（必須仍在院內）？
1. 病人如果要求刪除自己的資料，醫院的處理方式是什麼？本系統要提供什麼介面配合？

**現況／暫代做法**

《資料庫使用規範》8.2 已列建議期限，但明確標示為建議值。**期限未定案前，系統一律只做「標記」不做實際刪除。**

### Q-06 去識別化資料可用於院內 AI 推論的同意範圍

|            |                            |
| ---------- | -------------------------- |
| **問誰**   | 法務、資訊室               |
| **急迫度** | B                          |
| **卡住**   | 所有 AI 功能對真實資料啟用 |
| **狀態**   | 待提出                     |

**背景**

0909 版的假設是「醫院已同意去識別化資料可用於 AI 模型訓練與推論」。0910 的前提變更後，本專案**只做推論、不做訓練**，且模型跑在院內伺服器。範圍縮小了，但原本的同意究竟涵蓋什麼，需要確認。

**不確認的後果**

AI 功能只能對合成資料執行。所有生成類功能（衛教內容、記錄草擬、SOP 查詢）都無法對真實病人啟用。

**具體要問的**

1. 現有的同意（如果有）是書面的嗎？涵蓋範圍是訓練、推論，還是兩者？
1. 病人的知情同意書裡有沒有提到資料會用於資訊系統或 AI 輔助？需不需要補簽或補公告？
1. 「去識別化」的判定標準由誰認定？開發端的做法是送進模型前移除姓名、病歷號等直接識別欄位，這樣夠嗎？
1. 過渡期會用院外的實驗室 API。開發端已決定過渡期**一律只送合成資料**，這個限制是否足夠？或者院方連合成資料都不希望送出去？
1. AI 生成的衛教內容要給病人看。這些內容需不需要臨床審閱後才能顯示，還是可以直接呈現？
1. 病人可否拒絕 AI 輔助？若可以，拒絕後哪些功能要退回人工版本？

**現況／暫代做法**

`AI_FEATURES` 與 `REAL_PATIENT_DATA_TO_AI` 兩個開關預設關閉。後者只在 provider 為地端推論時才允許開啟。`LabApiProvider` 帶程式強制的合成資料檢查，帶真實病人資料標記的請求會被擋下。

第 5 題的暫代做法（迭代 4）：AI 產生的衛教內容一律「先審後給」——護理師核可前病人端看不到；AI 總開關關閉時，已核可的 AI 內容也一併從病人端消失。答案回來後再調整。

**1004 線索（斗六院區另一套系統的程式，不是院方答覆）**：那套系統在寫檔前，把病歷號與姓名用固定金鑰做**可還原的固定式加密**（同一個值每次結果相同，才能串接），而不是像本系統一樣直接移除。問第 3 題時可以把兩種做法一起帶去，請法務判定哪一種才算去識別化。見《[同院 IDH 系統參考調查](https://94sh09sh19sh.github.io/hd-docs/latest/notes/idh-reference-survey/#64-%E6%96%97%E5%85%AD%E7%89%88%E7%9A%84%E5%85%A9%E5%80%8B%E5%81%9A%E6%B3%95%E5%B0%8D-q-06q-07)》6.4 節。

**背景**

0912 確認正式部署環境為**院內一台 NVIDIA DGX Spark**，原本問的前兩件事因此有了答案：

| 原問題                             | 答案                                                     |
| ---------------------------------- | -------------------------------------------------------- |
| 128GB 是系統記憶體還是顯示記憶體？ | **都是。** 128GB LPDDR5x 為處理器與 GPU 共用的統一記憶體 |
| 有沒有 GPU？                       | 有。GB10 Grace Blackwell 內含 Blackwell GPU              |

完整硬體規格與據此訂出的部署決策，見《[部署規範](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/deployment-spec/index.md)》第 2 章。

**這個答案改變了什麼**：載入量接近原評估的情境 C（70B 級可載入），但記憶體頻寬約 273 GB/s，遠低於資料中心級顯示卡——**載得下大模型，但吐字速度不會快**。加上這台機器同時跑其他專案，可用記憶體還要再打折。

**0919 範圍縮小**：本系統的應用主機改為院內另一台 Windows 工作站（**那一台同樣是共用的**），**DGX Spark 與本系統的關係只剩一條 HTTP 呼叫**。原本混在這一題裡的「共用主機上本專案佔多少記憶體、跟誰搶連接埠」並沒有消失，只是要問的機器換了一台，移到 Q-27（那是 Windows 主機的問題）。**這一題現在只問端點本身**：位址、認證、可用模型、額度、誰維運。

這個變化也讓這一題不再擋任何東西：AI 功能在第一次部署時預設關閉（DEP-29），端點沒到齊，主線功能完全不受影響（DEP-24）。

**剩下不確認的後果**

不知道共用狀況下實際拿得到多少記憶體，就無法決定 SOP 查詢這類功能能不能做成即時互動。也不知道推論服務該由誰啟動與維運——這件事若沒有歸屬，上線時會卡在「大家都以為對方會處理」。

**具體要問的**

1. 這台機器上還有哪些專案？共用狀況下本系統可用的記憶體額度是多少？有沒有排擠時的優先順序？
1. **地端推論服務由誰提供與維運？** 是資訊室統一起一個共用端點，還是各專案自理？本專案的設計是**不自行載入模型、只呼叫端點**（DEP-16）。
1. 端點位址、認證方式、可用模型清單為何？繁體中文能力實測過嗎？
1. 這台機器什麼時候可以給開發端測試？可以先給一個小規模的試用時段嗎？
1. 若評估後發現額度不夠，有沒有追加機器的可行性與時程？

**開發端可以先提供的資訊**（有助於資訊室評估）

15 床、三班、每位病人每次療程估 5～10 次 AI 呼叫，**尖峰同時請求數不會超過個位數**，換算下來每秒請求數遠低於 1。因此本系統的瓶頸是單次回應延遲，不是吞吐量，**不需要昂貴的高併發推論架構**，也不需要獨佔整台機器。

**現況／暫代做法**

所有模型呼叫走 `LlmProviderPort`，預設 `MockLlmProvider`。額度確認後只需改設定指向端點，不動業務邏輯。

**1004 線索（斗六院區另一套系統的程式）**：那套系統直接呼叫院內一台自架的 Ollama 服務。那是斗六的網段、與本系統所在的院區無關，但代表「院內已有團隊自己架推論服務」有先例；問第 2 題時可以順帶問本院區有沒有類似的共用端點。

**1005 使用者告知**：本院區（成大）的院內推論端點**尚未架設**。第 2、3 題照舊要問；在那之前 AI 功能維持預設關閉，走模擬模型或實驗室端點。

| **卡住**   | 第一次部署能不能把安裝包送進那台主機 |
| **狀態**   | **作廢（0926）**                     |

**背景**

正式主機沒有對外連線，交付路線是「隨身碟帶入離線安裝包」（DEP-18、6.2 節）。這條路線上有三個關卡不在開發端手上：院方允不允許外接儲存媒體、掃毒要在哪裡做、誰核准這次變更。

**不確認的後果**

安裝包做好了，人也到現場了，卻在門口被擋下來。**這是唯一一種「全部做對了還是進不去」的失敗**，而且它不會在測試階段暴露出來。

**具體要問的**

1. 院方允許使用外接隨身碟嗎？要不要事先報備？有沒有指定的媒體（例如院方發放的加密碟）？
1. 有沒有指定的掃毒站？掃描結果要不要留存、留在哪裡？
1. 把軟體安裝到一台院內主機上，要不要走變更申請？流程多久、誰核准？
1. 安裝包約數百 MB，掃描一次大概多久？當天能不能完成？
1. **日後每次更新都要重走一次這個流程嗎**，還是第一次核准後可沿用？
1. 可以接受的部署與更新時段是什麼時候？（要避開透析班次，見 DEP-32）

**現況／暫代做法**

安裝包附雜湊值（DEP-27），進院前先在開發端掃描一次（DEP-26），隨身碟用完即清除且不帶任何資料出院（DEP-28）。**這些是開發端能自己做到的部分，做了不代表流程就會通過。**

### Q-30 護理師的行動裝置

|            |                                      |
| ---------- | ------------------------------------ |
| **問誰**   | 護理長（需求）、資訊室（採購與納管） |
| **急迫度** | D                                    |
| **卡住**   | 需手持裝置的功能什麼時候能開         |
| **狀態**   | 待提出（0919 新增）                  |

**背景**

目前護理端只會在護理站的一兩台電腦上開啟，護理師手上沒有平板或手機。這讓一整類功能在物理上無法成立——最具體的是「我到床邊了」這顆按鈕（FR-N10）：它要在床邊按才有意義，而護理師走到床邊時手上沒有東西可以按。

**0919 的處理方式**：這類功能**先關閉**，可在系統設定開啟（DEP-29、FR-S11）。關閉期間「到達床邊時間」留空，不以確認時間頂替，並在成效指標上明確標示「本期間無到達時間資料」。

**不確認的後果**

**具體要問的**

1. 護理師在班上有沒有可能配發行動裝置？共用幾台就夠（一班一台？一人一台？）
1. 如果短期內沒有，有沒有替代做法——例如床邊固定一台小螢幕、或用病人端平板上的一個護理師專用畫面？
1. 感染管制上，護理師隨身帶著裝置在治療區移動，消毒規範怎麼訂？（與 Q-22 同一場談）
1. 若之後配發，是否納入與病人端平板相同的管控方式？

**現況／暫代做法**

功能已實作、資料欄位已存在，只是關著。配發之後在系統設定開啟即可，**不必改程式、不必重新部署、資料結構不必改**。

### Q-31 介面改版的現場試用人選

|            |                     |
| ---------- | ------------------- |
| **問誰**   | 護理長              |
| **急迫度** | D                   |
| **卡住**   | 介面設計改動的驗收  |
| **狀態**   | 待提出（0919 新增） |

**背景**

0919 起兩端介面全面重新設計，依據是《[介面設計基準](https://94sh09sh19sh.github.io/hd-docs/latest/notes/uiux-design-baseline/index.md)》裡的族群分析。**但族群分析是開發端寫的，它需要被現場的人打臉過至少一次才算數。**

**不確認的後果**

介面在開發機上看起來好看，到了現場才發現護理師的操作順序跟設計假設不同、或病人根本看不清楚某個字級。這種問題改起來不貴，但**發現得晚會讓首波試用的使用者留下壞印象**，而第一印象很難修。

**具體要問的**

1. 能不能指定一到兩位護理師，在首波試用前先看過新介面並試著操作？
1. 能不能找一位真實病人（或家屬）在平板上試按一次求助與問卷？**這一題比上一題重要**——護理師會替病人猜，猜不準
1. 護理師一天之中真正會用到的功能有哪些？現在放在導覽列上的那幾個對不對？
1. 治療區的光線、病人的姿勢（多半是躺著、單手）有沒有開發端沒想到的限制？
1. 護理站電腦的螢幕尺寸與解析度為何？從護理師站的位置看得清楚嗎？
1. （1005 新增）能不能請三位左右的病人，在病床上看一次跑馬燈，回答「看得清嗎、跟得上嗎、看了累不累或煩不煩」？**跑馬燈開啟前一定要做**（SRS FR-P10）：速度是開發端訂的預設值，只有長者本人說得準
1. （1010 新增）緊急回報的圖示改成畫出症狀本身（迭代 17.8）：能不能請病人**把字遮起來**看一次，說出每個圖示是什麼症狀？說不出來的那幾個再改
1. （1010 新增）遊戲（透析小花園、麻將連連看、記憶相簿）開給病人前，能不能請幾位長者在病床上實際玩一次，回答「看得清嗎、點得到嗎、玩了累不累或煩不煩、會不會覺得是給小孩玩的」？任一題有人說不行就改了再試（遊戲化分析 12.2）

**現況／暫代做法**

導覽列的版位可在系統設定調整（FR-S11），因此第 3 題答錯的代價很低——改的是設定，不是程式。**第 2、4、6 題沒有暫代做法**，只能實際看。第 6 題在院內還沒機會之前，開發端先找同齡的人試看一輪，但那只能當起點，不能取代病人。

**1005 迭代 16 已做完跑馬燈**，「跑馬燈」功能開關因此**預設關閉**、等第 6 題的結果才開。試看的步驟與記錄表在《[迭代 16 分冊](https://94sh09sh19sh.github.io/hd-docs/latest/testing/iteration-16/index.md)》§16.10： 速度、開頭靜止、兩則間隔都是營運參數，有人說不行就當場調慢重看；最後採用的速度連同試看結果寫在那個參數的修改理由裡（只記代號與年齡層，不記姓名）。

### Q-32 院內主機對外連線的範圍與穩定性

|            |                                                           |
| ---------- | --------------------------------------------------------- |
| **問誰**   | 資訊室                                                    |
| **急迫度** | **C**                                                     |
| **卡住**   | 部署與每次更新：git clone、建置映像檔、建置外殼 APK       |
| **狀態**   | **已結案（0930）**：對外連線是常態、沒有限制（0926 新增） |

**0930 答覆**：主機對外連線**是常態**，**沒有限制**——第 1、2 題的答案是常態開放、沒有代理也沒有白名單；第 3 題照「沒有限制」理解為 SSH 連得出去，院內主機上尚未實測。 第 4 題（稽核要求）沒有談到。答覆已反映到《部署規範》2.1、DEP-14 與部署手冊第十一、十四冊，同日結案（第 7 章）。

**背景**

0926 確認「院內網路可以連出去，外面連不進來」，交付因此改走 git clone ＋ 就地建置（DEP-07）。但 0922 現場的筆記是「主機當天連得到院外」，**沒有講清楚那是常態還是臨時開的**。整條部署路線都建立在「連得出去」上。

**不確認的後果**

第一次部署順利，下一次更新時對外連線已經被關掉或被代理伺服器擋住，git fetch 與映像檔建置在現場失敗——而且沒有隨身碟可以當退路。

**具體要問的**

1. 對外連線是**常態開放**，還是需要時申請？若要申請，流程與時間？
1. 有沒有代理伺服器或網域白名單？若有，本系統需要的是：GitHub（兩個私人 repo 的 SSH 連線）、容器映像檔來源、npm 套件來源、Prisma 引擎發布站、Python 套件來源、Android 建置相依（Gradle 與 Google 的套件庫）
1. **SSH 連往 GitHub 的連接埠有沒有開？** 沒開的話要改用 HTTPS 搭配唯讀權杖，部署金鑰那一套（DEP-43）就要換
1. 院方對「院內主機連出去」有沒有稽核要求？需要留紀錄的話，本系統的建置階段會連哪些網域可以事先列給資訊室

**現況／暫代做法**

建置所需的外部來源已在《部署規範》3.2、3.4 與第 7 章列出。**執行期本來就不連外**（DEP-14），所以即使對外連線日後被關掉，已經跑起來的服務不受影響，受影響的只有更新。

**0927 迭代 12 實測後補上外殼 APK 建置實際連到的網域**：`dl.google.com`（Android 命令列工具與 SDK）、`services.gradle.org`（Gradle 本體，會轉到 GitHub 的發布檔，再轉到 GitHub 的檔案主機）、`maven.google.com`、`repo.maven.apache.org`、`plugins.gradle.org`（Gradle 外掛與相依）。總量約 1.5 GB，只在建置 `shell-builder` 的映像檔時連；執行 `shell-builder` 時完全沒有網路。開發機上 Gradle 那一個檔案約 130 MB 就下載了 6.6 分鐘，院內主機若更慢要預留時間（《部署演練紀錄》9.1）。

**0927 迭代 13 補上 AI 閘道映像檔建置會連到的網域**：Docker Hub（Python 基底映像檔）、`deb.debian.org`（映像檔裡的 `curl`）、`pypi.org` 與 `files.pythonhosted.org`（LangChain 等 45 個 Python 套件，全部鎖版本）。映像檔約 330 MB，**只在建置時連**；執行時閘道只連 `config.yaml` 指定的院內推論端點，不連任何院外位址。AI 首波關閉時閘道可以不建（DEP-24）。

1. 系統的顯示大小（字型大小、顯示比例）有沒有被院方統一設定過？

### Q-24 情緒／滿意度回饋的題目與「趨勢偏離」判定

|            |                                         |
| ---------- | --------------------------------------- |
| **問誰**   | 護理部、社工                            |
| **急迫度** | D                                       |
| **卡住**   | 迭代 4 的 FR-P08／N08（已用暫定值實作） |
| **狀態**   | 待提出                                  |

**背景**

SRS FR-P08 要求「長期趨勢偏離時建議轉介社工」。「偏離」要有一個說得清楚的定義，否則等於開發端在替臨床下判斷。開發端先訂了暫定規則 `PSY-DEV-v1`：近 3 次情緒相關題目（心情、睡眠、有人可以幫忙或聊天）的平均，比先前最多 6 次的平均低 1.0 分以上即列出；不足 6 份不套用。

**具體要問的**

1. 多久填一次？目前是每次療程最多一份、病人自願填。
1. 「低 1.0 分以上」「近 3 次比先前 6 次」這組門檻合適嗎？
1. 列出來之後，轉介社工的流程是什麼？要不要在系統裡記錄「已評估、是否轉介」？
1. 病人寫的文字意見要不要有人定期看？誰看？

**現況／暫代做法**

規則放在共用常數並標版本；比對結果只以事實陳述呈現給護理師（例如「近 3 次平均 2.1 分，先前平均 4.0 分，低了 1.9 分」），不對心理狀態下結論，也不自動觸發任何轉介。病人端看不到比對結果。

| 欄位               | 選項                                                                                                                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 有無症狀（單選）   | 有症狀、無症狀                                                                                                                                                                      |

### Q-34 透析室的床位數、床號與療程時段

**現況／暫代做法**

**1004 線索（同院 IDH 系統程式，不是院方答覆）**

- **第 1 題**：同院另一套系統把床位寫死成六區共 41 床——A、B、C、D 各 8 床，E 7 床，I 2 床；床號是「區碼＋數字」（如 `A1`、`E8`），**每一區都沒有 4 號床**。本系統床位上限是 40 床（`BED_MAX_COUNT`），首波只開一區不受影響，涵蓋全中心時差一床
- **第 2 題**（旁證）：那套系統用早 10～11 點、午 15～16 點、晚 20～21 點判斷「這一班的病人」，沒有結束時間的透析補成開始後 4 小時。這只是查詢用的時間窗，不是班別定義

問法因此可以改成：「首波 15 床是 41 床裡的哪幾床？三班各從幾點到幾點？」見《[同院 IDH 系統參考調查](https://94sh09sh19sh.github.io/hd-docs/latest/notes/idh-reference-survey/#61-%E5%BA%8A%E4%BD%8D%E9%85%8D%E7%BD%AE%E5%B0%8D-q-34)》6.1、6.5 節。

**1005 使用者決定**

- **床號照醫院編號**，由護理長在「系統管理 → 營運參數 → 床位清單」照實際編號填，系統不寫死任何一組床號
- **床位數不設上限**（原本的 40 床上限 `BED_MAX_COUNT` 已拿掉）
- **平板跟著病人**：平板是給原本要用它的那位病人；病人每次透析的床不固定，換床時在床位圖上把平板移到新的床即可

全新環境第一次啟動時長出的預設 15 床（01～15）要不要拿掉，列在調查文件第 9 節待使用者決定。第 2 題（三班起訖）照舊待問。

**1005 新版需求**：院方 API 全面取代手動輸入（SRS FR-S15）。對這一題的影響：**床位改由 API 的床位欄帶入**，全新環境不再預設 15 床；病人在哪一床也跟著 API。第 2 題（三班起訖）**變得比較要緊**：迭代 15 起，API 判定透析開始時系統自動建立療程，算哪一班就靠它；答覆回來之前沿用 12 點、17 點的暫代值。

**1007 補記**：使用者告知本透析中心的透析時間**一律四小時**，~~院方資料沒有預計結束時間時以開始後 4 小時計~~ 不管院方資料有沒有預計結束時間都是開始後 4 小時結束——這是院方的硬性規定，不是建議。三班起訖仍要問，但每一班的長度可以用這一條核對。

| 種類                                         | 病人在哪裡看、什麼時候看                                         | 內容從哪裡來                                                | 現況                                                             |
| -------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------- |
| **院內衛教**（「公告與院內衛教」頁）         | 透析中，病人平板面板底部的跑馬燈，「標題：內容」整則跑過、不能點 | AI 依附錄 C.6 的主題生成，護理師核准（SRS FR-P10、FR-N17）  | 迭代 17 完成；跑馬燈開關預設關閉，等長者試看速度（Q-31 第 6 題） |
| **結束衛教與測驗**（「結束與離院衛教」頁）   | 透析快結束時，病人平板全螢幕出現，一題一頁                       | 個人化衛教內容與附錄 C.6 題庫（SRS FR-P04、FR-P07、FR-P15） | 已開放                                                           |
| **離院衛教**（「結束與離院衛教」頁裡的一段） | 下機之後，打算讓病人用自己的手機帶回家給家人或自己看             | AI 生成的離院衛教重點（SRS FR-P07）                         | **帶回家的方式未定，預設關閉**（迭代 17.1）                      |

1006 迭代 17.1 已經把結束衛教與離院衛教併成一頁，理由是「兩者類似，不要讓護理師用兩次」。三種是不是都需要，沒有問過院方。

**不確認的後果**

不大：三種都已做好或預設關閉，不擋任何一次進院。但離院衛教要開放就得先設計帶回家的方式，那是一筆新的開發； 若護理部認為某一種用不到，先問清楚就省掉這筆工，也少一頁讓護理師維護。

**具體要問的**

1. 三種衛教都需要嗎？若有可以捨棄的，是哪一種？
1. 若三種都要留：院內衛教（透析中一直跑）與結束衛教（快結束時看、有測驗）的主題要不要分開，還是同一份主題清單（附錄 C.6）就好？
1. 離院衛教若要留，病人或家屬帶回家的方式有沒有偏好（紙本、手機掃碼、院方既有的管道）？

**現況／暫代做法**

三種照現況：院內衛教與結束衛教可用，離院衛教預設關閉。答覆是捨棄某一種的話，先關掉它的開關或版位（跑馬燈是功能開關，另兩種是導覽版位），不必改程式；之後再決定要不要把程式拿掉。

### Q-37 護理紀錄的現行形式與如何接上現有作業

|            |                                                                      |
| ---------- | -------------------------------------------------------------------- |
| **問誰**   | 護理長；若現行紀錄是院內的電子系統，加問資訊室                       |
| **急迫度** | D                                                                    |
| **卡住**   | 護理記錄簽核之後的去處：只當草稿、列印附在紙本，還是匯出交給院內系統 |
| **狀態**   | **已回覆（1010）**，迭代 17.8 實作後結案（1007 新增）                |

**1010 答覆**（使用者轉述院方）：不支援直接寫進醫院資料庫，現階段由本系統協助護理師完成護理紀錄、**以複製貼上的方式交給院內的正式紀錄**；系統管理可切換 **DART 或 SOAP**，預設 DART；AI 沒串或沒開也要能用；**事件時間與相關病人數值寫在格式原有的段落裡**，不另立欄位，貼過去就一起帶過去——這些是本系統上線前護理紀錄缺的部分。反映到 SRS FR-N04、FR-N05、FR-N18 與實作規格書 4.15.8。

**背景**

系統的護理記錄（SRS FR-N04、FR-N05，迭代 4）是：事件當下用點選式範本勾選（Q-25），或依病人自報建立預填草稿，可再請 AI 草擬初稿，護理師修改後簽核；**簽核後不能再改，也只存在本系統**——沒有匯出、列印或寫入院方任何系統的功能。

開發時假設的現行作業是「紙本記錄單」（《FDE 評估報告》任務七），但**透析室實際怎麼記，沒有問過院方**。Q-25 第 3 題只問到範本的欄位要不要對得上院內既有的紀錄，沒有問紀錄本身是什麼形式、本系統的記錄要怎麼交出去。

**不確認的後果**

護理師可能同一件事要記兩次：本系統簽核一次，正式的護理紀錄再寫一次。這與 FR-N05「審閱簽核取代重新輸入」的用意相反，等於多一份工；首波試用時護理師最容易因此不想用。

**具體要問的**

1. 透析室現在的護理紀錄是什麼形式？紙本記錄單、院內醫療資訊系統的電子護理紀錄，還是同院 IDH 系統裡？能不能給一份空白表單或畫面截圖（可與 Q-01 第 2 題要的紙本記錄單一起給）？
1. 透析中要記哪些：每小時的生命徵象與機器數值、事件與處置、交班重點？各記在哪裡、誰在什麼時候寫（當下寫還是下機後補寫）？
1. 本系統簽核的記錄，院方希望怎麼接上：
1. 只當草稿，護理師照著抄或複製貼上到正式紀錄
1. 列印出來附在紙本
1. 匯出成檔案，交資訊室匯入院內系統
1. 本系統的記錄就是正式紀錄（牽涉病歷的法定效力與 Q-05 的留存期限，要另外確認）
1. 若正式紀錄在電子系統：有沒有可以寫入的介面，或至少有固定的欄位格式？（本階段不做雙向寫入，與 Q-25 第 3 題相同）
1. 有哪些內容院方的系統已經記了（例如院方 API 已帶入的血壓與脫水量），本系統不該再要護理師記一次？

**現況／暫代做法**

照現況：簽核後只存在本系統，不匯出、不列印、不寫入院方系統。答覆前不改程式；答覆是「只當草稿」的話，最可能要補的是一鍵複製簽核內容，其餘三種要另外評估開發量。

**建議談法（0926 重排優先順序）**：**先談 Q-27 與 Q-32，它們擋的是第二次進院**——Q-29（隨身碟）已作廢。這兩項要一起談，因為它們是同一件事的兩半：程式怎麼進去（對外連線）、進去之後斷電了能不能自己回來（Docker 與開機登入）。0919 版問的服務帳號與目錄權限不必再問，院方已決定能登入者一律可信任。

**0930 起**：Q-32 已回覆，對外連線這一半成立。剩下 Q-27 未答的題目，**先問第 9、10 題**——兩項都是整台主機的設定，這台 Docker 同時在跑別的專案，要資訊室同意才能改。

**1007 起**：第 4、9、10、12 題已答。剩下的 Q-27 **先問第 6 題（防毒排除）**——排除之前不得輸入真實病人資料；第 11 題（Git）、第 13 題（DNS）可以同一封信帶過。

其餘 C 級（Q-09 技術面、Q-07、Q-10、Q-11、Q-12）可以在同一場的後半段一次帶完，它們都不擋第一次部署。B 級三項要法務一起，另外約。

談之前先把兩件事講清楚，可以省掉一半的來回：**本系統不在 DGX Spark 上跑**（它只是一個 API 端點，本專案不需要 GPU、不需要那台機器的登入權限），以及**尖峰請求數遠低於每秒 1**（不需要準備高規格設備）。0912 那次談的時候這兩點還沒定，容易讓資訊室以為要整台機器被獨佔。

## 7. 已結案

**0919 有四項一次結案，但結案方式與一般情形不同**，欄位上要看得出來：它們是**院方授權採用**，不是**逐條審閱同意**。授權的意思是「先用，有問題再改」；審閱的意思是「看過了，就是這樣」。把前者當成後者，日後被問到「這些題目誰審的」就答不出來。
