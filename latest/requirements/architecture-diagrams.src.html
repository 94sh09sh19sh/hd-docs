圖版 01

全端架構與裝置綁定

病人不登入、前端碰不到資料庫；即時通知走院內 SSE，所有 AI 呼叫先過閘道；護理師自己的資料與臨床資料分表。

圖版 02

實體架構與網路分區

服務執行時院內一條對外連線都沒有；主機只在建置與更新時連出，實驗室通道只在開發環境。

三句必背

  1. 資料流方向恆定：前端 → 後端 API → SQLite 檔案。前端不碰資料庫檔案，後端是唯一的寫入者，統計與報表走唯讀連線。
  2. 身分不靠登入靠綁定：Session Token ＝ 病人＋平板＋療程時段，限時限裝置，由自建服務核發與失效。
  3. 服務執行時，院內裝置與資料庫一條對外連線都沒有；主機只在建置與更新時連出。過渡期的實驗室只在開發環境經 SSH 通道使用，AI 閘道在程式裡強制只送合成資料，正式環境設定拒絕選用它。
  4. 病人的資料與護理師的資料分表存放：營運與排班模組寫的是班表與成效基準，兩邊永遠不互相回寫。

與 0909 版的差異

  • 推播中繼整條拿掉。護理端與總覽畫面改由院內 SSE 長連線推送，護理站加一台常駐總覽螢幕。
  • 外部 LLM 改為院內 AI 伺服器。過渡期的實驗室 API 只送合成資料；AI Proxy 改為 AI 閘道，並加上背景佇列。
  • PostgreSQL 與即時狀態快取改為一個 SQLite 檔案。檔案放在應用伺服器本機磁碟，即時狀態放在後端行程記憶體。
  • 新增元件。臨床資料匯入、照護業務模組、備份目的地；規則引擎與對外報表服務以虛線標為規劃中。
  • 1005 迭代 16：照護業務模組的「閒置輪播・三層內容」改成「本次透析面板・跑馬燈」；規則引擎與對外報表服務的迭代編號改成 18、19（1005 重排）。沒有新增任何元件或連線。
  • 1005 迭代 15：「臨床資料匯入」改稱院方資料同步，院方透析清單 API 成為病人、床位與療程的日常來源；圖版一的 Session Token 標籤補上平板的 SSE 通知，圖版二的 HIS／EMR 與它的連線改標「透析清單」「每 3 分鐘唯讀抓取」、平板的連線補上 SSE。只改標籤，分區與連線一條未動；開發與模擬部署用的模擬院方 API 不在圖上（正式環境不得啟動）。迭代 17 的跑馬燈草稿走既有的 AI 閘道，圖上不必改。
  • 迭代 6 補上閒置輪播與正式主機。輪播併在照護業務模組裡（卡片由後端組好再送到平板）；兩張圖的「院內 AI 伺服器」標上 DGX Spark，應用伺服器標上容器部署。沒有新增任何機器或網路連線，圖版 02 的分區與線一條未改。
  • 迭代 5 再加一個營運與排班模組。它是本系統第一個蒐集「護理師自己的資料」的地方——班表、床位分配、成效基準。與其他模組寫同一個檔案，但自成資料表，不回寫臨床資料表（資料庫使用規範 §11.2）。
  • 0919 第一次動到圖版 02 的分區與線。應用伺服器由 DGX Spark 改為院內另一台 Windows 工作站（仍與其他專案共用），以離線安裝包部署；AI 推論端點退成另一台機器，兩者之間只有一條院內 HTTP 呼叫；MDM 整格拿掉，平板改以自包 WebView 外殼加螢幕固定，那條「註冊／遠端鎖定」的線一併消失；臨床數值來源由「待確認」改為院方唯讀 API。前面幾次都只換標籤，這一次真的少了一台機器、少了一條線。
  • 0926 第二次動到圖版 02 的線。部署改為 Docker 容器＋git clone（安裝包撤除），應用伺服器多一條建置期才有的連出，與執行期零連外分開畫；後端與 AI 推論端點之間多一格本系統的 AI 閘道（容器，不含模型）；院內主機連到實驗室的那條線拿掉，改為只在開發環境由開發機經 SSH 通道連到實驗室個人容器裡的 AI 閘道。
