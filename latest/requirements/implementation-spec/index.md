## 0. 本文件與其他文件的關係

本文件**不取代**另外四份文件，而是把「設計層級」的需求收斂成「可執行」的實作決策：

- 《[軟體需求規格書](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/srs/index.md)》：功能需求來源（FR 編號皆引用自此）
- 《[資料庫使用規範](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/database-policy/index.md)》：資料庫使用的強制規則，**Agent 必須全程遵守，優先權等同本文件**
- 《[部署規範](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/deployment-spec/index.md)》：部署形態、環境界線與交付方式的強制規則（`DEP` 編號），**優先權等同本文件**
- 《[FDE 數位化／數位優化評估報告](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/fde-assessment/index.md)》：背景脈絡與技術選型理由
- [兩張架構圖](https://94sh09sh19sh.github.io/hd-docs/latest/requirements/architecture-diagrams/index.md)：系統實體與邏輯架構的視覺依據

若本文件與上述文件有衝突，以本文件的**範圍界定與技術棧決策**為準；資料治理與存取控制規則仍以《資料庫使用規範》為準，部署形態與環境界線以《部署規範》為準。

**架構圖現況**：兩張架構圖已於 **2026-09-19 重繪**——應用伺服器由 DGX Spark 改為院內另一台 Windows 工作站（仍與其他專案共用），AI 推論端點獨立成另一台機器，MDM 那一格拿掉改為自包外殼與螢幕固定，臨床數值來源改標為院方 API。**這一次圖二的分區與線有動**（多了一台機器、少了一條 MDM 線），與 0912 那次「只換標籤」不同。圖與文字若有出入，架構相關疑義仍以 SRS 第 7 章與本文件第 3 章為準。

### 2.1 Prisma 改用 SQLite 的注意事項

- **`provider` 改為 `sqlite`，移除 `directUrl`。** migration 檔與 PostgreSQL 不相容，`migrations/` 整組重建（既有資料為合成資料，直接捨棄，見《資料庫使用規範》第 15 條）。
- **連線行為必須實測確認。** SQLite 只允許一個寫入者，Prisma 的連線設定（如連線字串上的 `connection_limit`）要驗證實際行為，不要照抄 PostgreSQL 的設定。
- **`PRAGMA` 設定要在連線建立時套用**：`journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout>=5000`、正式環境 `synchronous=FULL`。這四項是《資料庫使用規範》第 7 條的必開項，缺一個都會在多人同時操作時出問題。
- **不得用 `Float` 承載任何臨床數值**（劑量、體重、脫水量）。改用整數最小單位或 `String`，見《資料庫使用規範》6.2。
- **部分批次操作在 SQLite provider 上的支援與 PostgreSQL 不同**，使用前先確認當前 Prisma 版本的實際支援，不要假設兩邊一樣。
- 既有的六條 schema 約束（不用 enum、不用 JSON 承載關聯資料、不用資料庫專屬預設值、snake_case、稽核欄位不省略、級聯路徑只留一條）**全部保留**。

#### 0919 新增：離線環境下的 Prisma 引擎與遷移指令

**這兩件事在第一次部署時會同時撞上，而且都會毀掉當天的進度。**

**（一）引擎不在 npm 套件裡。** Prisma 的 schema engine 與 query engine 約 40MB，由 `@prisma/engines` 的安裝後腳本另外下載。全程離線的建置測試因此失敗：

```
request to https://binaries.prisma.sh/... failed, reason: getaddrinfo ENOTFOUND binaries.prisma.sh
```

只要 `node_modules` 是在沒有成功下載引擎的情況下產生的（離線安裝、跳過安裝後腳本、或從別處複製而排除了二進位檔），第一次用到 Prisma 指令時就會現場去下載。

**Agent 要做到的三件事**：

1. **建置安裝包時把引擎檔收進包裡**，來源是開發端 `node_modules` 裡已下載好的那份
1. **啟動與遷移時以環境變數指向包內的引擎路徑**，不讓 Prisma 自己去找
1. **把 `prisma` 與 `@prisma/client` 鎖成確定版本**（拿掉版本範圍前綴）。引擎版本與 CLI 版本必須一致，浮動的版本範圍會在某次重新安裝時悄悄換掉其中一邊，而症狀會是一個看起來毫不相干的錯誤

**（二）正式環境不得用開發用的遷移指令。** 目前 `npm run prisma:migrate` 對應的是開發用的那支，它在偵測到「資料庫與遷移歷史對不上」時會提議或直接**重建整個資料庫**。在開發機上那是方便，在正式主機上那是把整個透析中心的紀錄刪掉。

**正式環境一律用「套用既有遷移」的那支**（`prisma:deploy`，已存在）。這一條與《資料庫使用規範》第 18 條、DEP-31 是同一件事，此處不重複。

**驗收方式**：離線建置測試改成「連網只發生在建置安裝包的那台機器上」，院內端從解壓到服務起來不得出現任何一次對外請求。

### 3.4 模型供應者介面層 `LlmProviderPort`（改寫）

**取代 v1.0 的「AI Proxy Service 直接呼叫外部服務商」設計。**

```

├── MockLlmProvider      ← 預設。回傳固定範例，讓所有 AI 功能可先開發與測試
```

介面至少涵蓋：`generate(prompt, options)`、健康檢查、可用模型清單。

**硬性規則**：

1. **任何呼叫語言模型之處，一律透過 `LlmProviderPort`。** 不得在業務邏輯中出現任何一家廠商的 SDK、端點或模型名稱。切換 provider 只能是設定變更。
1. **模型識別字串、端點、金鑰全部由設定提供**，`.env.example` 保留空值。院內推論服務的端點與可用模型未確認（Q-07）、實驗室的可用模型會變動（Q-08），因此**不在程式或文件中寫死任何模型名稱**。0926 起模型名稱只寫在 AI 閘道的 `config.yaml`（實驗室那一份不進 repo，repo 只放範本）。
1. **`LabApiProvider` 必須帶「合成資料檢查」**：當目前 provider 為 `LabApiProvider` 時，帶有真實病人資料標記的請求要被擋下並記錄（FR-S06）。這是程式強制，不是靠人的自律。
1. **去識別化在寫入資料庫之前完成**，不是查詢時才遮蔽（《資料庫使用規範》第 14 條）。
1. **AI 呼叫一律寫入 `ai_invocations`**：provider、模型、參數、耗時、是否觸發去識別化、成功或失敗。提示與輸出留存 12 個月，原始（未去識別化）提示不存。
1. **非即時功能走背景佇列。** 衛教生成、記錄草擬這類「可以等」的工作不得阻擋 HTTP 請求，也不得在資料庫交易中呼叫模型（會佔住 SQLite 唯一的寫入位置）。

**0926：介面之下多一層 AI 閘道**（FR-S13、部署規範第 5 章）。`LlmProviderPort` 不動，`LabApiProvider` 與 `OnPremiseProvider` 的 `LLM_ENDPOINT` 都指向**閘道**，不指向推論端點：

```
  ├── MockLlmProvider                      │ config.yaml：provider／base_url／model／參數

  └── OnPremiseProvider ┘ 同一份 HTTP 實作 └─▶ 院內正式 GPU API（正式）
```

硬性規則再加四條：

1. **後端不得直接連推論端點**（DEP-41）。Ollama 的位址、模型名稱、LangChain 只准出現在閘道裡

1. **正式環境設定下 `LLM_PROVIDER=lab` 拒絕啟動**（DEP-40），與第 3 條的合成資料檢查並存

### 3.6 規則引擎（新增）

對應 FR-R01。三項高風險功能的計算**由規則引擎執行，不經語言模型**。

**為什麼自建而不用第三方規則引擎套件**：需求是「能逐條印出來給醫師看、能版本化、能指出這次套用了哪一條的哪一個門檻」。第三方套件的表達能力遠超需求，卻讓可解釋性變差。本專案的規則形態很窄——都是「某個數值或次數超過門檻」，自建一個小型評估器即可。

**資料模型**：

| 資料表                    | 用途                                                                           |
| ------------------------- | ------------------------------------------------------------------------------ |
| `rule_definitions`        | 規則的身分：識別字串、名稱、適用需求（FR-P03／P05／N06）、狀態                 |
| `rule_versions`           | 每一版的門檻值與條件、生效期間、**臨床端書面依據的出處**、建立者               |
| `rule_evaluations`        | 每一次執行：對哪位病人、哪次療程、套用哪個規則版本、輸入了哪幾筆歷史資料、結果 |
| `rule_evaluation_reviews` | 誰檢視、是否採納、未採納原因（FR-R06、對應 FR-N13）                            |

**硬性規則**：

1. 規則版本一經使用即不可修改，要改就新增版本。`rule_evaluations` 永遠指向當時的版本。
1. **未附書面依據出處的規則版本不得標為生效**（FR-R02）。無依據時規則只能在「合成資料模式」下執行。
1. 每一則輸出必須可展開完整依據：引用的歷史資料、規則條目、門檻值、版本編號（FR-R03）。

護理紀錄的格式（DART／SOAP，FR-N18）**不是開關**，是營運參數（迭代 17.8）：兩種都是「開」，只是選哪一種。

連動（小花園帶著送花）是新的行為：連動造成的那一次切換一樣寫稽核軌跡，理由記成「隨透析小花園開啟（或關閉）」。 **九個遊戲化開關全關時，病人端、護理端、總覽螢幕都要與迭代 17.7 一模一樣**——這一條是迭代 20～23 每一個的驗收標準。 **1010 迭代 20 實作**：開關中心只建這次做的三個（新的分組「病人平板的遊戲化」），其餘六個隨迭代 21～23 的功能一起加——功能還沒做，連開關都不出現（DEP-34）。 **1010 迭代 21 實作**：同一個分組多三個（透析小花園、送花、病人之間的互動），共六個；麻將連連看、狀態評估彙整、記憶相簿隨迭代 22、23 加。 **1011 迭代 22 實作**：同一個分組多兩個（麻將連連看、狀態評估彙整），共八個；記憶相簿隨迭代 23 加。 **1011 迭代 23.3 實作**：同一個分組多第九個（老台灣記憶相簿），**九個到齊**。病人詳細資訊的 `anyFeatureFlags` 多記憶相簿（只開相簿時這一頁也存在，裡面只有「最近幾次有沒有玩」與「可以聊的話題」）；系統管理「內容與選項」的「記憶相簿的圖卡」分頁跟著這個開關，關著時不出現、端點 404。護理端的「病人詳細資訊」一頁要透析小花園、麻將連連看、狀態評估彙整**至少一個**開著才存在（導覽定義的 `anyFeatureFlags`）：都關著時連結、路由、系統管理的版位清單都沒有，端點回 404——九個全關時護理端與迭代 17.7 一樣。

**0919 新增的一條硬性規則**：開關關閉時，**尚未實作的功能連「停用的入口」都不得出現**（DEP-34）。已實作但關閉的功能同樣不出現入口，但它的後端端點回傳的是「功能未啟用」而不是 404——兩者在稽核軌跡上要分得出來。

**開關的顯示名稱**：功能開關清單在護理端是給人看的，**不得印出上表左欄那些識別字**（FR-S10）。識別字留在後端與稽核紀錄裡。

**硬性規則**：開關為關閉時，相關介面元素**完全不出現**，而不是顯示為停用。後端端點也要一併擋下，不能只靠前端隱藏。 （目前唯一的例外是 1007 的「護理師自己新增病人」，理由寫在上表那一列；要再開例外，比照它寫在表裡。）

`.env` 由使用者填入，Agent 產生 `.env.example` 時保留空值，**不得寫入任何真實金鑰或路徑**：

**必須做到的事**（《資料庫使用規範》第 7、8 條）：

- 連線建立時套用四項 `PRAGMA`（見 2.1）
- 資料庫檔案放在**專案目錄外**，並確認已被 `.gitignore` 涵蓋

- 備份用 SQLite 線上備份機制（`VACUUM INTO`），不用檔案複製；WAL 模式的 `-wal`／`-shm` 與主檔是一組

### 3.10 績效資料分級的實作方式（新增）

對應《資料庫使用規範》第 11 條的 L1～L4。**這不是前端顯示問題，是後端授權問題。**

| 實作要求                 | 說明                                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| 分級標在端點上           | 每個統計端點宣告自己回傳的最高級別，由 middleware 依角色與開關判定，不在 service 內部零散判斷 |
| L3／L4 查詢逐次留痕      | 誰查了誰、查詢區間、宣告用途，寫入稽核軌跡                                                    |
| 不設「總分」「排名」欄位 | 排名一律查詢時即時計算，不寫入資料表                                                          |
| 績效與臨床資料表分離     | 不得把績效彙整結果回寫到臨床資料表                                                            |
| 禁止交叉評分             | 不得建立「護理師×病人臨床結果」的關聯資料表                                                   |

**1010 迭代 19 實作結果**（4.17）：

| 實作要求                 | 怎麼做的                                                                                                                                                                                                                                                                                                                                        |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 分級標在端點上           | 端點掛 `@DataLevel(L1／L2／L3／L3_SELF／L4)`；全域的資料分級守衛（排在導覽版位之後、功能開關之前）依角色比對該級的權限，L3 另看 `PERF_INDIVIDUAL_L3` 與宣告用途。唯讀角色進不進得來看權限，不看標記：醫院管理層只有 L1 的權限                                                                                                                   |
| L3／L4 查詢逐次留痕      | L3 由服務寫 `PERFORMANCE_L3_QUERIED`（誰、查了哪幾位或哪一班、區間、用途）；總開關關著被擋的寫 `PERFORMANCE_L3_QUERY_BLOCKED`；本人看自己的也寫，用途記「本人自我檢視」。L4（稽核軌跡原始列）每次查詢寫 `AUDIT_LOG_QUERIED`，查完才記；用途選填（既有的驗收腳本都在打它），沒宣告記成「未宣告用途」，稽核原始列的用途清單裡沒有「獎勵計分審閱」 |

**1017 修正**（4.26）：上表「歸給做那件事的人」實作成**當時登入的帳號**（`resolved_by_id`、`signed_by_id`、`reviewed_by_id`、`closed_by_id`）。護理站一人登入大家用，那是「誰的帳號開著」，不是「誰做的」。迭代 26.3 起計分**一律讀處理者指名**（`handler_declarations`），四個帳號欄位照記、只供稽核；沒有指名的事件不計分。處理者指名屬 L3（可對應到特定護理師），只在獎勵制度與個人層級的端點讀，不進任何 L1、L2 的數字；「未指名的比例」是全單位一個比例，屬 L2。

### 3.13 導覽版位與功能可設定（FR-S11，0919 新增）

**每個功能在導覽上只會是三種版位之一**：主列、選單、關閉。版位存在資料裡，不寫死在前端。

**硬性規則**：

1. **關閉不只是隱藏連結，後端端點要一併擋下。** 只藏前端等於沒關——知道網址的人直接打得進去
1. **尚未實作的功能與已實作但關閉的功能要分得出來**：前者連路由都不存在，後者回傳「功能未啟用」。兩者在稽核軌跡上是不同的事件
1. **版位改動寫入稽核軌跡**，記錄誰改的、從哪個版位改到哪個版位
1. **預設值寫在共用常數裡，不是寫在資料庫的 seed 裡**。全新環境第一次啟動時要能長出正確的預設版位
1. **「需手持裝置的功能」是一個群組，不是一個一個的開關。** 護理師拿到行動裝置那天要能一次開啟，不是去找七個地方各開一次

**0919 迭代 9 實作結果**：版位存在 `nav_placement_settings`，17 項功能各一列； 守衛 `NavItemGuard` 掛在全域，控制器標上 `@RequireNavItem()` 即納管。 第 2 條實作出來是這樣：**關閉的功能回 404 並寫一筆稽核，未實作的功能連路由都沒有** ——前者在軌跡上查得到，後者查不到，因為它從來沒有被呼叫過。 另外補了一條規格沒寫、但寫程式時才看得出來的限制：**主列滿 7 項時，第 8 項移不進去**， 會被擋下並說「請先把其中一項改到更多選單」。上限若只寫在文件裡，半年後主列就會有 9 項。

### 3.14 選項與題庫改為資料（0919 新增）

對應 SRS 附錄 C。**院方授權先採用 AI 產生的預設內容，並要求可在護理端調整**，因此這些內容必須從程式常數搬進資料表。

| 內容               | 現況                                  | 要變成                                              |
| ------------------ | ------------------------------------- | --------------------------------------------------- |
| 求助處理方式與結果 | **已經是資料**（迭代 5 就做成可設定） | 只需依附錄 C.3／C.4 更新預設內容                    |
| 求助類別           | 共用常數                              | **資料表**，依附錄 C.2 重新設計，含分派表預設急迫度 |
| 透析前問卷題目     | 共用常數                              | **資料表＋版本號**，依附錄 C.5                      |
| 衛教題庫           | 共用常數                              | **資料表＋版本號＋知識點標記**，依附錄 C.6          |
| 回饋題目           | 共用常數                              | **資料表＋版本號**，依附錄 C.7                      |

**硬性規則**：

1. **識別碼不可改，顯示文字可改。** 識別碼欄位建立後在介面上不可編輯
1. **停用是唯一的移除方式**，沒有刪除按鈕；既有紀錄仍查得到停用選項的文字
1. **問卷與題庫改動即產生新版本號**，每一份作答記錄它當時的版本。**沒有版本號，改過題目之後的趨勢圖就是把兩種不同的問題畫在同一條線上**
1. **「其他」不可停用、不可刪除**，且選了必須填自由文字
1. **共用常數改為「首次啟動時寫入資料表的預設值」**，之後一律以資料表為準。**不得留下「程式讀常數、介面讀資料表」的雙軌**
1. 每一次增刪改寫入稽核軌跡

**為什麼要連問卷題目都資料化**：附錄 C.1 的兩個目的（對個別病人客製化、用大量資料訓練）都要求選項固定且可比較。**寫在程式裡的題目，每改一次就要重新部署一次；而重新部署的門檻高到最後大家就不改了**——不改的結果不是穩定，是護理部放棄使用這個系統的這一部分。

**0919 迭代 9 實作結果**：

| 硬性規則 | 實作在哪裡                                                                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1、2     | 識別碼是 upsert 的 where 條件，改了就是新增一個；服務層沒有任何 delete                                                                                                              |
| 3        | 三組帶版本號的內容各有一張版本表。**改一題＝整份複製成新版本再套上改動，在同一個交易裡完成**——半成品的版本比沒有版本更難查                                                          |
| 4        | `is_other` 欄位。後端擋（回 409）、前端不出現那顆按鈕                                                                                                                               |
| 5        | 舊常數只剩一個用途：把迭代 9 之前那一版補寫成第 1 版，讓既有作答還原得出當時的題目。**全新環境不會寫入那一份**，版本號直接從 2 起算——同一個版本字串在任何一套環境裡都要指同一份題目 |
| 6        | 每一次增刪改都要填理由，理由連同新舊值進稽核軌跡                                                                                                                                    |

**三件規格沒寫、實作時才浮出來的事**：

1. **平板拿著舊版題目送出時要擋下。** 默默拿新版的題目去解讀舊版的答案，比拒收更危險—— 同一個識別碼在兩版之間可能換過選項，對不起來的是資料本身
1. **求助類別的顯示文字要留一份快照在紀錄上。** 識別碼不變、文字可改是對的， 但事後回頭看那一筆求助時，要知道病人按的是哪一個按鈕上的**哪幾個字**
1. **回饋的冪等要排在題目檢查之前。** 第一次送出之後每月加問的兩題就不再到期， 拿當下該問的題目去檢查重送的那一份，會把自己的成功回應判成錯誤

### 3.15 已知缺陷：解除綁定在某些條件下找不到入口（0919，**當日修正**）

> **2026-09-19 已於迭代 7 修正。** 三件修法全數完成，次要原因 1 的冪等解除也一併做了； 驗收方式那一條已寫進 `verify:iteration7`，不是只寫在手動測試手冊裡。 次要原因 2 依原判斷不改程式，改在測試手冊寫明要用不同的瀏覽器設定檔。 以下保留缺陷的定位過程——**同一個入口設計再出現時，要認得出它**。
>
> **1007 迭代 17.6**：使用者指示修法 1 的「目前有效綁定」清單與排班與指派重複，拿掉（裝置管理也改名「新增裝置」，見 4.15.6）。 跨日的綁定仍由修法 2 的提示列出，按一下跳到那一天就解得掉；**畫面上「不改日期就解除」這一條因此不再成立**，`verify:iteration7` 驗的是後端（不依日期的清單端點與解除），照樣通過。

**回報症狀**：在本機測試時，護理端有時無法解除某個綁定。懷疑的情境有很多種——未解除就關閉病人端或護理端、斷網、伺服器重新啟動、在本機綁定多台病人端裝置。

**定位結果：主因只有一個，而且與上面列的情境都無關。**

**解除綁定的唯一入口，掛在「當日排班」清單的每一列上，而那份清單是依排班日期篩選的（預設今天）。** 因此只要一筆有效綁定所屬的排班日期不是畫面上選的那一天，**那一列根本不會出現，自然沒有按鈕可按**。會踏進這個狀況的情境至少三種：

| 情境                     | 為什麼綁定還在，但按鈕不在                                                                                                               |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **跨日**                 | 大夜班 23:00 起，過了午夜之後，那筆綁定的排班日期是「昨天」，而畫面預設顯示今天                                                          |
| **前幾天測試留下的綁定** | 綁定的有效期上限預設 6 小時，但**逾時掃描沒跑到之前它仍是有效狀態**；而就算過了 6 小時，那幾個小時內只能手動解除，按鈕卻在另一個日期底下 |
| **看得到卻解不掉**       | 裝置管理頁面**看得到**某台平板正綁著誰，但那一頁只有遠端鎖定與解除註冊，**沒有解除綁定**                                                 |

**連帶的第二個症狀**：那台平板因為還綁著，在指派清單裡被濾掉，於是變成「這台平板不見了」，而畫面上不會說明為什麼。

**次要原因兩個，一併修掉**：

| #   | 問題                                                                                                                   | 修法                                                                                                                                                                                       |
| --- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | 解除時若該綁定剛好已被逾時掃描結束掉，後端回傳錯誤，畫面顯示成失敗                                                     | **改為冪等**：目標狀態已經達成就回報成功，並說明「這筆綁定已於某時因逾時結束」                                                                                                             |
| 2   | 本機測試時多個病人端分頁共用同一份瀏覽器儲存空間，後佈建的裝置會覆蓋先佈建的，造成「某台平板的綁定沒有任何分頁在輪詢」 | 這是**本機測試環境特有的**，不是正式環境的問題（正式環境一台平板一支 App、各自獨立）。修法是在測試手冊寫明要用不同的瀏覽器設定檔，並在病人端佈建時顯示目前這台的序號，讓人一眼看出被換掉了 |

**修法（三件事，缺一不可）**：

1. **新增一個不依日期的「目前有效綁定」清單**，放在裝置管理頁，每一列都有解除按鈕。後端的清單端點已經存在（`GET /bindings`），目前沒有任何畫面用它
1. **排班清單加上「顯示其他日期的有效綁定」提示**：當有效綁定的排班日期不等於目前選的日期時，在畫面上明白說出來並提供跳過去的連結
1. **裝置指派下拉選單濾掉某台平板時要說明原因**，不是默默不顯示。「這台正綁給某位病人」與「這台已停用」是兩件不同的事

**驗收方式**：建立一筆昨天日期的排班並綁定 → 護理端預設畫面（今天）→ **要能在不改日期的情況下解除它**。這一條寫進迭代驗收腳本，不是只寫在手動測試手冊裡。

### 4.0 為什麼是這個順序

排序不是照需求編號，也不是照「哪個看起來最重要」，而是照四條原則。順序若違反其中任一條，代價都是重工或永久性的損失：

| #   | 原則                             | 具體後果                                                                                                           |
| --- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 1   | **會動到所有既有程式的事情先做** | SQLite 遷移碰到每一個資料存取點。先做新功能再遷移，等於把新功能也重工一遍                                          |
| 2   | **有時效性的先做**               | 成效基準（FR-M07）只能在系統正式啟用前量測。紙本流程一消失，「以前要花多久」永遠補不回來                           |
| 3   | **不需要等別人回答的先做**       | AI 生成功能用 `MockLlmProvider` 今天就能做完；規則引擎要等臨床端給門檻值。把等待中的項次排前面，只會讓進度停在原地 |
| 4   | **產生資料的先做，吃資料的後做** | 管理儀表板與獎勵制度（新增任務一）需要求助處理紀錄、班表、成效基準累積過一段時間才有東西可看                       |

**原則 4 需要特別說明，因為它看起來像是把新增任務一的優先權往後放。** 實際相反：新增任務一的目的是「向長官與外部展現成效」，而**空的儀表板比沒有儀表板更傷**。先把產生資料的三件事（求助處理結果、班表、成效基準）做完並實際跑一段時間，儀表板上線時才有真實數字。因此新增任務一被拆成兩半——產生資料的部分排在迭代 5（很前面），呈現與計分的部分排在最後（0919 重排後為迭代 12）。

**另一個刻意的決定**：三項高風險功能（原本週任務二）排在後面，而非最前面。理由是它同時卡在兩個外部答覆上（法務的分類確認、臨床端的門檻值），而且規則引擎本身不長。把它排在前面，最可能的結果是引擎寫好了、門檻值還沒到，然後空等。排在後面，前面幾個迭代的時間正好是等答覆的時間。**若門檻值與書面確認提早到齊，這個迭代可以隨時往前插隊**——它與其他迭代沒有相依。

**0919 補上第五條原則，而且它的優先權高於前四條**：

## 5. 每次迭代開始前，Agent 應自我檢查

在動工前確認：

- 本次要新增的資料表／欄位是否已對照 SRS 需求與稽核軌跡欄位需求
- 是否有任何前端程式碼企圖直接碰資料庫檔案（禁止，《資料庫使用規範》第 2 條）
- 存取控制是否寫在後端應用層（禁止依賴檔案權限或前端隱藏，第 4 條）
- 是否在業務邏輯中直接寫 SQL 或 SQLite 方言（改走 Repository／ORM 層，第 5 條）
- 新增的臨床數值欄位是否誤用浮點數（一律整數最小單位或字串，6.2）
- 是否新增了第二個會寫入資料庫的常駐行程（不允許，第 7 條）
- 是否有任何相依指向院外網域（FR-S07，跑檢查腳本）
- 呼叫語言模型是否一律透過 `LlmProviderPort`（3.4）
- 呼叫 MDM 是否一律透過 `MdmProviderPort`（3.3）
- 取用院方臨床數值是否一律透過 `ClinicalDataSourcePort`（3.5）
- 本次功能是否觸及 1.4 的有條件納入項；若是，開關是否預設關閉
- 本次功能是否會產生 L3 個人層級績效資料；若是，是否已擋在 `PERF_INDIVIDUAL_L3` 之後
- 本次的輸出是否可能離開院內；若是，是否走對外報表模組（FR-X01）
- 測試資料是否為虛構合成資料（禁止任何接近真實病人的資訊）
- 若本次功能疑似要「依資料做出會影響臨床判斷的建議或分級」而未列於 SRS 5.6，**先停下來問使用者**

### 8.1 三支盤點腳本的共同設計

| 決定                             | 為什麼                                                                     |
| -------------------------------- | -------------------------------------------------------------------------- |
| **一律可重複執行，不改任何檔案** | 它們是量尺，不是修理工具。會自動改東西的工具，出錯時沒有人看得出它改了什麼 |
| **都支援 `--json`**              | 要接進驗收腳本或 CI 時不必解析人看的輸出                                   |
| **有發現就回傳非零狀態**         | 才擋得住「跑了但沒人看輸出」                                               |
| **每一筆都附「要改成什麼」**     | 只說哪裡錯不夠——這幾類問題的正確做法都不只一種寫法，要講清楚選哪一種       |

### 8.2 `check:ui` 的一個關鍵界線

**程式碼註解不算違規。** FR-S10 管的是「使用者看得到的字」，不是原始碼—— 需求編號留在註解與文件裡是對的，那是可追溯性的來源。 因此這支腳本**先把註解剝掉再比對**，而且是用一個認得字串與樣板字串的狀態機剝， 不是 `replace(/\/\/.*$/)`——後者會把網址裡的 `//` 當成註解開頭， 把整行後半段吃掉，於是真正的違規反而掃不到。

**0919 首次執行的結果：22 筆，分成 5 類。** 這 22 筆就是迭代 9 那一項工作的清單。

**0919 迭代 9 完成後：0 筆。** 基準線同步降到 0（`verify:iteration8` 裡那條棘輪也改了）， 之後只能往下，不能往上。

**唯一的例外寫在腳本裡，而且逐行列出。** 「系統管理 → 內容與選項」那一頁看得到識別碼， 這是刻意的：依附錄 C.0 第 1 條「識別碼不可改，顯示文字可改」， **護理長看不到識別碼，就不知道自己改的是文字（安全）還是新增了一個選項（會讓歷史資料斷開）**。 例外一律逐行列出並寫明理由——不開放整個檔案，也不接受「加個註解就跳過」那種寫法。

### 8.3 `check:offline` 首次執行就抓到一個真的問題

`prisma` 與 `@prisma/client` 宣告的是 `^6.5.0`，**實際安裝到的是 6.19.3**。 浮動的版本範圍讓引擎與 CLI 有機會在某次重新安裝後對不起來，而症狀會是一個看起來毫不相干的錯誤。

**0919 已於迭代 7 鎖成 `6.19.3`**（DEP-30 第 3 點），同一支腳本另外多了兩項檢查： 開發用的遷移指令有沒有加上防呆、更新流程有沒有可執行的入口。目前 0 項阻擋。

### 8.4 還沒有工具、要靠人的四件事

**寫出來是為了不要假裝腳本涵蓋了全部。**

| 要驗什麼                         | 為什麼腳本驗不到                            | 怎麼辦                                                                                          |
| -------------------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 對比度                           | 要實際算色值，而顏色來自 CSS 自訂屬性與繼承 | 在瀏覽器的開發者工具裡量                                                                        |
| 觸控目標尺寸                     | 要實際繪製才知道最終尺寸                    | 同上，或用瀏覽器自動化量測                                                                      |
