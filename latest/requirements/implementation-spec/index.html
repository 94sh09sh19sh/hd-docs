    血液透析中心平板照護輔助系統 — 實作規格書（給 AI Coding Agent）¶

    版本：v2.0　文件性質：實作導向補充規格，與《軟體需求規格書 SRS》《資料庫使用規範》《部署規範》《FDE 評估報告》共同構成完整需求脈絡 適用讀者：Claude Code／任何協助本專案開發的 AI coding agent

    0. 本文件與其他文件的關係¶

    本文件不取代另外四份文件，而是把「設計層級」的需求收斂成「可執行」的實作決策：

    • 《軟體需求規格書》：功能需求來源（FR 編號皆引用自此）
    • 《資料庫使用規範》：資料庫使用的強制規則，Agent 必須全程遵守，優先權等同本文件
    • 《部署規範》：部署形態、環境界線與交付方式的強制規則（DEP 編號），優先權等同本文件
    • 《FDE 數位化／數位優化評估報告》：背景脈絡與技術選型理由
    • 兩張架構圖：系統實體與邏輯架構的視覺依據

    若本文件與上述文件有衝突，以本文件的範圍界定與技術棧決策為準；資料治理與存取控制規則仍以《資料庫使用規範》為準，部署形態與環境界線以《部署規範》為準。

    架構圖現況：兩張架構圖已於 2026-09-19 重繪——應用伺服器由 DGX Spark 改為院內另一台 Windows 工作站（仍與其他專案共用），AI 推論端點獨立成另一台機器，MDM 那一格拿掉改為自包外殼與螢幕固定，臨床數值來源改標為院方 API。這一次圖二的分區與線有動（多了一台機器、少了一條 MDM 線），與 0912 那次「只換標籤」不同。圖與文字若有出入，架構相關疑義仍以 SRS 第 7 章與本文件第 3 章為準。

    2.1 Prisma 改用 SQLite 的注意事項¶

    • provider 改為 sqlite，移除 directUrl。 migration 檔與 PostgreSQL 不相容，migrations/ 整組重建（既有資料為合成資料，直接捨棄，見《資料庫使用規範》第 15 條）。
    • 連線行為必須實測確認。 SQLite 只允許一個寫入者，Prisma 的連線設定（如連線字串上的 connection_limit）要驗證實際行為，不要照抄 PostgreSQL 的設定。
    • PRAGMA 設定要在連線建立時套用：journal_mode=WAL、foreign_keys=ON、busy_timeout>=5000、正式環境 synchronous=FULL。這四項是《資料庫使用規範》第 7 條的必開項，缺一個都會在多人同時操作時出問題。
    • 不得用 Float 承載任何臨床數值（劑量、體重、超過濾量）。改用整數最小單位或 String，見《資料庫使用規範》6.2。
    • 部分批次操作在 SQLite provider 上的支援與 PostgreSQL 不同，使用前先確認當前 Prisma 版本的實際支援，不要假設兩邊一樣。
    • 既有的六條 schema 約束（不用 enum、不用 JSON 承載關聯資料、不用資料庫專屬預設值、snake_case、稽核欄位不省略、級聯路徑只留一條）全部保留。

    0919 新增：離線環境下的 Prisma 引擎與遷移指令¶

    這兩件事在第一次部署時會同時撞上，而且都會毀掉當天的進度。

    （一）引擎不在 npm 套件裡。 Prisma 的 schema engine 與 query engine 約 40MB，由 @prisma/engines 的安裝後腳本另外下載。全程離線的建置測試因此失敗：

    request to https://binaries.prisma.sh/... failed, reason: getaddrinfo ENOTFOUND binaries.prisma.sh

    只要 node_modules 是在沒有成功下載引擎的情況下產生的（離線安裝、跳過安裝後腳本、或從別處複製而排除了二進位檔），第一次用到 Prisma 指令時就會現場去下載。

    Agent 要做到的三件事：

    1. 建置安裝包時把引擎檔收進包裡，來源是開發端 node_modules 裡已下載好的那份
    2. 啟動與遷移時以環境變數指向包內的引擎路徑，不讓 Prisma 自己去找
    3. 把 prisma 與 @prisma/client 鎖成確定版本（拿掉版本範圍前綴）。引擎版本與 CLI 版本必須一致，浮動的版本範圍會在某次重新安裝時悄悄換掉其中一邊，而症狀會是一個看起來毫不相干的錯誤

    （二）正式環境不得用開發用的遷移指令。 目前 npm run prisma:migrate 對應的是開發用的那支，它在偵測到「資料庫與遷移歷史對不上」時會提議或直接重建整個資料庫。在開發機上那是方便，在正式主機上那是把整個透析中心的紀錄刪掉。

    正式環境一律用「套用既有遷移」的那支（prisma:deploy，已存在）。這一條與《資料庫使用規範》第 18 條、DEP-31 是同一件事，此處不重複。

    驗收方式：離線建置測試改成「連網只發生在建置安裝包的那台機器上」，院內端從解壓到服務起來不得出現任何一次對外請求。

    3.6 規則引擎（新增）¶

    對應 FR-R01。三項高風險功能的計算由規則引擎執行，不經語言模型。

    為什麼自建而不用第三方規則引擎套件：需求是「能逐條印出來給醫師看、能版本化、能指出這次套用了哪一條的哪一個門檻」。第三方套件的表達能力遠超需求，卻讓可解釋性變差。本專案的規則形態很窄——都是「某個數值或次數超過門檻」，自建一個小型評估器即可。

    資料模型：

    資料表 用途
    rule_definitions 規則的身分：識別字串、名稱、適用需求（FR-P03／P05／N06）、狀態
    rule_versions 每一版的門檻值與條件、生效期間、臨床端書面依據的出處、建立者
    rule_evaluations 每一次執行：對哪位病人、哪次療程、套用哪個規則版本、輸入了哪幾筆歷史資料、結果
    rule_evaluation_reviews 誰檢視、是否採納、未採納原因（FR-R06、對應 FR-N13）

    硬性規則：

    1. 規則版本一經使用即不可修改，要改就新增版本。rule_evaluations 永遠指向當時的版本。
    2. 未附書面依據出處的規則版本不得標為生效（FR-R02）。無依據時規則只能在「合成資料模式」下執行。
    3. 每一則輸出必須可展開完整依據：引用的歷史資料、規則條目、門檻值、版本編號（FR-R03）。
    4. 輸出措辭為事實陳述，不是結論陳述。 寫「符合 HYPO-01 規則：近三次療程第 2 小時後曾回報頭暈」，不寫「病人有低血壓風險」（FR-R04）。文案不得由模型生成，一律由規則版本內的範本組出。
    5. 不自動觸發任何動作（FR-R05）：不改醫囑、不改處理優先順序、不自動通知醫師。

    3.13 導覽版位與功能可設定（FR-S11，0919 新增）¶

    每個功能在導覽上只會是三種版位之一：主列、選單、關閉。版位存在資料裡，不寫死在前端。

    硬性規則：

    1. 關閉不只是隱藏連結，後端端點要一併擋下。 只藏前端等於沒關——知道網址的人直接打得進去
    2. 尚未實作的功能與已實作但關閉的功能要分得出來：前者連路由都不存在，後者回傳「功能未啟用」。兩者在稽核軌跡上是不同的事件
    3. 版位改動寫入稽核軌跡，記錄誰改的、從哪個版位改到哪個版位
    4. 預設值寫在共用常數裡，不是寫在資料庫的 seed 裡。全新環境第一次啟動時要能長出正確的預設版位
    5. 「需手持裝置的功能」是一個群組，不是一個一個的開關。 護理師拿到行動裝置那天要能一次開啟，不是去找七個地方各開一次

    0919 迭代 9 實作結果：版位存在 nav_placement_settings，17 項功能各一列； 守衛 NavItemGuard 掛在全域，控制器標上 @RequireNavItem() 即納管。 第 2 條實作出來是這樣：關閉的功能回 404 並寫一筆稽核，未實作的功能連路由都沒有 ——前者在軌跡上查得到，後者查不到，因為它從來沒有被呼叫過。 另外補了一條規格沒寫、但寫程式時才看得出來的限制：主列滿 7 項時，第 8 項移不進去， 會被擋下並說「請先把其中一項改到更多選單」。上限若只寫在文件裡，半年後主列就會有 9 項。

    3.15 已知缺陷：解除綁定在某些條件下找不到入口（0919，當日修正）¶

    2026-09-19 已於迭代 7 修正。 三件修法全數完成，次要原因 1 的冪等解除也一併做了； 驗收方式那一條已寫進 verify:iteration7，不是只寫在手動測試手冊裡。 次要原因 2 依原判斷不改程式，改在測試手冊寫明要用不同的瀏覽器設定檔。 以下保留缺陷的定位過程——同一個入口設計再出現時，要認得出它。

    回報症狀：在本機測試時，護理端有時無法解除某個綁定。懷疑的情境有很多種——未解除就關閉病人端或護理端、斷網、伺服器重新啟動、在本機綁定多台病人端裝置。

    定位結果：主因只有一個，而且與上面列的情境都無關。

    解除綁定的唯一入口，掛在「當日排班」清單的每一列上，而那份清單是依排班日期篩選的（預設今天）。 因此只要一筆有效綁定所屬的排班日期不是畫面上選的那一天，那一列根本不會出現，自然沒有按鈕可按。會踏進這個狀況的情境至少三種：

    情境 為什麼綁定還在，但按鈕不在
    跨日 大夜班 23:00 起，過了午夜之後，那筆綁定的排班日期是「昨天」，而畫面預設顯示今天
    前幾天測試留下的綁定 綁定的有效期上限預設 6 小時，但逾時掃描沒跑到之前它仍是有效狀態；而就算過了 6 小時，那幾個小時內只能手動解除，按鈕卻在另一個日期底下
    看得到卻解不掉 裝置管理頁面看得到某台平板正綁著誰，但那一頁只有遠端鎖定與解除註冊，沒有解除綁定

    連帶的第二個症狀：那台平板因為還綁著，在指派清單裡被濾掉，於是變成「這台平板不見了」，而畫面上不會說明為什麼。

    次要原因兩個，一併修掉：

    # 問題 修法
    1 解除時若該綁定剛好已被逾時掃描結束掉，後端回傳錯誤，畫面顯示成失敗 改為冪等：目標狀態已經達成就回報成功，並說明「這筆綁定已於某時因逾時結束」
    2 本機測試時多個病人端分頁共用同一份瀏覽器儲存空間，後佈建的裝置會覆蓋先佈建的，造成「某台平板的綁定沒有任何分頁在輪詢」 這是本機測試環境特有的，不是正式環境的問題（正式環境一台平板一支 App、各自獨立）。修法是在測試手冊寫明要用不同的瀏覽器設定檔，並在病人端佈建時顯示目前這台的序號，讓人一眼看出被換掉了

    修法（三件事，缺一不可）：

    1. 新增一個不依日期的「目前有效綁定」清單，放在裝置管理頁，每一列都有解除按鈕。後端的清單端點已經存在（GET /bindings），目前沒有任何畫面用它
    2. 排班清單加上「顯示其他日期的有效綁定」提示：當有效綁定的排班日期不等於目前選的日期時，在畫面上明白說出來並提供跳過去的連結
    3. 裝置指派下拉選單濾掉某台平板時要說明原因，不是默默不顯示。「這台正綁給某位病人」與「這台已停用」是兩件不同的事

    驗收方式：建立一筆昨天日期的排班並綁定 → 護理端預設畫面（今天）→ 要能在不改日期的情況下解除它。這一條寫進迭代驗收腳本，不是只寫在手動測試手冊裡。

    4.0 為什麼是這個順序¶

    排序不是照需求編號，也不是照「哪個看起來最重要」，而是照四條原則。順序若違反其中任一條，代價都是重工或永久性的損失：

    # 原則 具體後果
    1 會動到所有既有程式的事情先做 SQLite 遷移碰到每一個資料存取點。先做新功能再遷移，等於把新功能也重工一遍
    2 有時效性的先做 成效基準（FR-M07）只能在系統正式啟用前量測。紙本流程一消失，「以前要花多久」永遠補不回來
    3 不需要等別人回答的先做 AI 生成功能用 MockLlmProvider 今天就能做完；規則引擎要等臨床端給門檻值。把等待中的項次排前面，只會讓進度停在原地
    4 產生資料的先做，吃資料的後做 管理儀表板與獎勵制度（新增任務一）需要求助處理紀錄、班表、成效基準累積過一段時間才有東西可看

    原則 4 需要特別說明，因為它看起來像是把新增任務一的優先權往後放。 實際相反：新增任務一的目的是「向長官與外部展現成效」，而空的儀表板比沒有儀表板更傷。先把產生資料的三件事（求助處理結果、班表、成效基準）做完並實際跑一段時間，儀表板上線時才有真實數字。因此新增任務一被拆成兩半——產生資料的部分排在迭代 5（很前面），呈現與計分的部分排在最後（0919 重排後為迭代 12）。

    另一個刻意的決定：三項高風險功能（原本週任務二）排在後面，而非最前面。理由是它同時卡在兩個外部答覆上（法務的分類確認、臨床端的門檻值），而且規則引擎本身不長。把它排在前面，最可能的結果是引擎寫好了、門檻值還沒到，然後空等。排在後面，前面幾個迭代的時間正好是等答覆的時間。若門檻值與書面確認提早到齊，這個迭代可以隨時往前插隊——它與其他迭代沒有相依。

    0919 補上第五條原則，而且它的優先權高於前四條：

    # 原則 具體後果
    5 要交到使用者手上的事，排在所有新功能之前 第一次部署擋在四件事上：解除綁定找不到入口、離線建置失敗、更新會弄壞資料庫、介面不堪用。這四件每一件都不是新功能，但每一件都能讓部署當天停擺。做完第五個新功能而系統交不出去，等於零

    8.2 check:ui 的一個關鍵界線¶

    程式碼註解不算違規。 FR-S10 管的是「使用者看得到的字」，不是原始碼—— 需求編號留在註解與文件裡是對的，那是可追溯性的來源。 因此這支腳本先把註解剝掉再比對，而且是用一個認得字串與樣板字串的狀態機剝， 不是 replace(/\/\/.*$/)——後者會把網址裡的 // 當成註解開頭， 把整行後半段吃掉，於是真正的違規反而掃不到。

    0919 首次執行的結果：22 筆，分成 5 類。 這 22 筆就是迭代 9 那一項工作的清單。

    0919 迭代 9 完成後：0 筆。 基準線同步降到 0（verify:iteration8 裡那條棘輪也改了）， 之後只能往下，不能往上。

    唯一的例外寫在腳本裡，而且逐行列出。 「系統管理 → 內容與選項」那一頁看得到識別碼， 這是刻意的：依附錄 C.0 第 1 條「識別碼不可改，顯示文字可改」， 護理長看不到識別碼，就不知道自己改的是文字（安全）還是新增了一個選項（會讓歷史資料斷開）。 例外一律逐行列出並寫明理由——不開放整個檔案，也不接受「加個註解就跳過」那種寫法。

    8.3 check:offline 首次執行就抓到一個真的問題¶

    prisma 與 @prisma/client 宣告的是 ^6.5.0，實際安裝到的是 6.19.3。 浮動的版本範圍讓引擎與 CLI 有機會在某次重新安裝後對不起來，而症狀會是一個看起來毫不相干的錯誤。

    0919 已於迭代 7 鎖成 6.19.3（DEP-30 第 3 點），同一支腳本另外多了兩項檢查： 開發用的遷移指令有沒有加上防呆、更新流程有沒有可執行的入口。目前 0 項阻擋。

    8.4 還沒有工具、要靠人的四件事¶

    寫出來是為了不要假裝腳本涵蓋了全部。

    要驗什麼 為什麼腳本驗不到 怎麼辦
    對比度 要實際算色值，而顏色來自 CSS 自訂屬性與繼承 在瀏覽器的開發者工具裡量
    觸控目標尺寸 要實際繪製才知道最終尺寸 同上，或用瀏覽器自動化量測
    求助區在輪播中有沒有被蓋住 要真的畫出來才看得到 輪播中與非輪播各截一張圖比對（基準 2.3）
    安裝包在乾淨機器上跑不跑得起來 這台機器上有開發環境 只能在一台乾淨的 Windows 機器上實際跑（DEP-22）
