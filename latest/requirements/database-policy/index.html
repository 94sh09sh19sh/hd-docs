    血液透析平板照護輔助系統 — 資料庫使用規範（SQLite）¶

    版本：v2.0　適用範圍：本專案所有開發者與 AI coding agents 目的：測試階段與正式部署皆採 SQLite，確保資料全程留在應該在的機器上，且未來若情勢改變仍能低成本轉移

    正式環境以容器部署，本規範的每一條在容器裡怎麼落實，見《部署規範》；兩者衝突時，資料治理以本規範為準。

    0. 背景與核心原則¶

    0.1 0910 的重大變更¶

    項次 0909 版 0910 版
    測試階段資料庫 Supabase（PostgreSQL，東京） SQLite（開發者本機檔案）
    正式環境資料庫 醫院既有 MSSQL SQLite（院內伺服器檔案）
    主要防範的風險 平台鎖定、資料流向院外服務商 單檔資料庫的實體風險、內部誤用、留存期限失控
    Supabase 上的既有資料 — 不保留，不遷移。 全為合成測試資料，直接捨棄

    正式部署也是 SQLite，不接醫院資料庫。 這是本版最重要的前提變更：過去所有為了「未來要遷到 MSSQL」而設的限制，現在的理由變成「萬一哪天要遷，不要被卡死」——優先權下降，但規則保留（見第 6 條）。

    0.2 核心原則（三條，順序即優先權）¶

    1. 資料不離開它該在的機器。 開發階段是開發者本機，正式階段是院內伺服器。備份、匯出、除錯用的複製檔一律適用這條。
    2. SQLite 只是一個檔案格式，不是系統邏輯的一部分。 所有驗證、存取控制、業務邏輯留在自建後端程式碼中。這一條從 0909 版原封不動繼承——當時防的是 Supabase 平台功能，現在防的是「反正是本機檔案，直接開來改一下」這種捷徑。
    3. 稽核軌跡是不可否認的紀錄。 它同時被拿去算護理師績效（見第 11 條），因此更不能開放修改或刪除。

    任何 AI agent 在協助開發時都必須遵守以下規則，即使 SQLite 官方文件、Prisma 文件或範例建議了更方便的做法。

    1. 為什麼是 SQLite¶

    1.1 為什麼它在這個場景是對的選擇¶

    條件 為什麼 SQLite 合適
    單一透析中心，15 台平板加數台護理端裝置 併發寫入量極低。尖峰時段的寫入是「幾位病人同時送出問卷」，不是每秒數千筆
    所有資料不得離開醫院網路 沒有資料庫伺服器就沒有資料庫連接埠，暴露面比架一台 PostgreSQL 小得多
    醫院資訊室不見得有餘力維運一台資料庫伺服器 SQLite 沒有伺服器行程、沒有帳號設定、沒有版本升級停機
    備份要簡單到不會有人偷懶 備份就是複製一個檔案
    讀多寫少 儀表板、總覽、輪播全是讀取，SQLite 的單機讀取效能非常好

    1.2 它換來的四個問題（本規範第 7～9 條就是在處理這些）¶

    問題 後果 對策條號
    同時只允許一個寫入者 寫入尖峰會出現 SQLITE_BUSY，處理不當就是使用者看到操作失敗 第 7 條
    整個資料庫是一個檔案 有讀取權限的人可以整份複製帶走；檔案毀損就是全毀 第 8、9 條
    不適合放在網路磁碟 放在 SMB／NFS 上的 SQLite 檔案，其檔案鎖行為不可靠，會造成資料毀損 第 7 條
    沒有內建的使用者權限機制 誰能讀寫完全由作業系統檔案權限決定，粒度太粗 第 4、9 條

    1.3 Agent 行為規則¶

    • 不得為了方便額外引進 Firebase／Firestore、MongoDB 或任何 NoSQL 服務作為主要資料儲存。
    • 不得為了解決併發寫入問題而自行改用其他資料庫，遇到問題先看第 7 條的設定是否做齊。
    • 不得在專案中同時存在兩個資料儲存來源（例如一部分資料寫檔案、一部分寫資料庫）。

    2. 資料庫存取必須收斂在後端一層¶

    與 0909 版相同，且因為改用 SQLite 而更加不可妥協。

    • 禁止前端（病人端 PWA、護理端 PWA）以任何方式接觸資料庫檔案。
    • 所有資料流向必須是：前端 → 自建後端 API（API Gateway／BFF）→ SQLite 檔案。
    • 後端程式是唯一開啟資料庫檔案的常駐行程。不得有第二個常駐行程同時開啟同一個檔案做寫入（腳本與備份工具的例外見第 7、8 條）。

    Agent 行為規則：

    • 生成前端程式碼時，不得引入 sql.js、wa-sqlite、better-sqlite3 或任何在瀏覽器端操作 SQL 的套件。
    • 病人端的離線暫存仍使用 IndexedDB。那是送出佇列不是資料庫副本，只放「尚未送出的自報內容」，不得把伺服器端的資料鏡像下來。
    • 所有資料庫查詢／寫入邏輯只能出現在後端服務程式碼中。

    3. 身分驗證與 Session 一律自建¶

    • 本系統的身分機制是「病人不登入，由護理師在護理站主控台觸發裝置綁定，核發限時 Session Token」；護理端則是工作 ID 加密碼、經審核後啟用。
    • SQLite 沒有內建使用者系統，這反而讓規則變簡單：沒有任何現成機制可以依賴，全部自己實作，也就沒有平台鎖定的問題。
    • Session Token 的產生、驗證、失效邏輯由後端裝置綁定服務自行實作與管理；Token 明文不寫入資料庫，只留雜湊或 jti。

    Agent 行為規則：

    • 密碼一律雜湊儲存（bcrypt／argon2），不得明碼儲存。
    • 不得把「使用者是否有權限」的判斷放在資料庫層或檔案權限上（見第 4 條）。
    • 不得引進任何第三方託管的身分驗證服務——它們一律在院外，違反核心原則第 1 條。

    4. 存取控制邏輯必須寫在後端應用層¶

    SQLite 沒有 Row Level Security，也沒有資料庫層級的使用者。這代表存取控制只有一個地方可以放：後端應用層。

    不得用來當存取控制的東西 為什麼
    作業系統檔案權限 粒度只到「能不能開這個檔案」，無法表達「這位護理師能看哪幾位病人」
    SQLite 的 ATTACH 分庫 把資料切到不同檔案不等於做了授權，只是讓查詢變複雜
    前端的畫面隱藏 沒有顯示不等於沒有回傳。授權要發生在 API 回應之前
    SQL 檢視表（View） 可作為輔助，但不得是唯一的授權機制

    本系統要求「存取授權可追溯到哪一位護理師、何時、為哪一位病人核准」（SRS 4.1），這個邏輯必須在自己可完全掌控、可稽核的後端程式碼中。

    Agent 行為規則：

    • 實作存取控制時，一律寫在後端應用邏輯（API 層的 authorization middleware／service 層）。
    • 每一個回傳病人資料的 API，都必須在查詢前檢查「當前呼叫者是否有權取得這一位病人的資料」，不得只靠「前端不會呼叫到」當作保護。
    • 新增任務一的管理與績效資料，授權規則比臨床資料更嚴（見第 11 條），不得沿用「登入即可看」的判斷。

    5. 統一資料存取層（Repository 層 / ORM）¶

    • 使用 Prisma（本專案既有選擇）或自建 Repository 層包裝所有資料庫操作。
    • 業務邏輯程式碼中不得散落原生 SQL 字串，更不得出現 SQLite 方言。

    Agent 行為規則：

    • 新增資料庫操作時，一律透過既有 Repository/DAO 層的介面，不得在 controller、service、路由處理函式中直接嵌入查詢語法。
    • 確實需要原生 SQL 時（例如統計查詢），一律集中在 Repository 層的具名方法中，並在註解寫明「為什麼 ORM 表達不了」。
    • SQLite 專屬函式（json_extract、SQLite 版本的 strftime、rowid 等）不得出現在業務邏輯。統計查詢若不得不用，須在該方法上方註解標記 SQLITE-SPECIFIC，方便日後盤點。

    6. Schema 設計原則¶

    6.1 沿用 0909 版的六條約束¶

    改用 SQLite 之後，這六條的理由從「將來要遷到 MSSQL」變成「不要被任何一種資料庫綁死」，優先權下降但一條都不放寬：

    1. 不使用 Prisma enum — 所有列舉值都是 TEXT，合法值由 @hd/shared 常數與 class-validator 在應用層把關。
    2. 不使用 JSON 欄位承載結構化關聯資料 — 一律正規化成資料表與外鍵。SQLite 雖然有 json_extract，但用了就等於把查詢邏輯埋進方言裡。
    3. 不使用任何資料庫專屬預設值 — UUID 由 Prisma client 在應用層產生。
    4. 命名：欄位 snake_case，資料表名複數 snake_case。
    5. 稽核欄位不因階段而省略 — 誰、何時、對誰、做了什麼，設計時就納入。
    6. 級聯路徑只留一條 — 這一條原本是為 SQL Server 而設，SQLite 沒有這個限制。仍然保留，因為多條級聯刪除路徑本身就難以推理，跟哪一種資料庫無關。

    6.2 SQLite 特有的型別注意事項¶

    SQLite 只有五種儲存類別（NULL、INTEGER、REAL、TEXT、BLOB），與 PostgreSQL 的差異必須知道：

    情況 SQLite 的行為 本專案的做法
    沒有原生 BOOLEAN 存成 0／1 的 INTEGER 交給 Prisma 處理，程式端一律當 Boolean 用，不得直接比對 0／1
    沒有原生 DATETIME Prisma 存成毫秒整數 一律以 UTC 寫入，顯示時才轉當地時間。已經踩過一次的坑：scheduled_date 用「當日 00:00 UTC」，這個慣例不要改
    沒有原生 DECIMAL 用 REAL（浮點數）會失去精度 任何劑量、體重、超過濾量一律不得用浮點數。改用整數存最小單位（例如公克、毫升），或存 TEXT 再於應用層轉換
    字串比對預設區分大小寫 LIKE 對 ASCII 不分大小寫，其餘分 工作 ID、病歷號的唯一性檢查，一律在應用層先正規化（統一轉大寫或小寫）再寫入，不依賴資料庫的比對規則
    外鍵預設不強制 不開 foreign_keys 就形同沒有外鍵 見第 7 條，這是必開項
    沒有嚴格型別（除非用 STRICT 表） 欄位可以塞進任何型別的值 應用層驗證是唯一防線，class-validator 不可省略

    6.3 Agent 行為規則¶

    • 設計或修改資料表時，需同時確認是否已涵蓋稽核軌跡所需欄位（誰、何時、對誰、做了什麼）。
    • 新增任何帶小數的臨床數值欄位前，先讀 6.2 的 DECIMAL 那一列，不得便宜行事用 Float。
    • Prisma 的部分批次操作在 SQLite provider 上的支援與 PostgreSQL 不同，使用前先確認當前 Prisma 版本的支援情況，不要假設兩邊一樣。

    7. SQLite 運作設定（必開項，不是建議）¶

    以下設定若沒做齊，系統在多人同時操作時一定會出問題。後端在開啟資料庫連線時必須全部套用：

    設定 值 為什麼非做不可
    journal_mode WAL 預設模式下，一個寫入會擋住所有讀取。護理站總覽是持續讀取的畫面，不開 WAL 就會在有人送出問卷時整頁卡住
    foreign_keys ON SQLite 預設不強制外鍵。不開這個，schema 上的所有關聯形同虛設
    busy_timeout 至少 5000（毫秒） 遇到寫入衝突時等待而不是立刻失敗。沒設這個，尖峰時段會出現莫名其妙的操作失敗
    synchronous FULL（正式環境） 這是臨床紀錄，不接受「斷電後掉最後幾筆」。開發環境可放寬為 NORMAL 換取速度

    7.1 單一寫入者的實作要求¶

    • 後端必須是唯一的寫入來源。不得同時執行第二個會寫入的行程，包含 prisma studio、手動開啟的 SQLite 命令列工具、資料修補腳本。
    • 需要跑資料修補腳本時，先停掉後端服務，跑完再啟動。這一條在正式環境是硬性規定。
    • 寫入交易要短。不得在一個交易裡面呼叫語言模型或等待外部回應——那會把唯一的寫入位置佔住好幾秒。
    • 長時間的統計查詢（管理儀表板、對外報表）應在唯讀連線上執行，避免拿到寫入鎖。

    7.2 檔案位置¶

    • 正式環境：資料庫檔案放在院內伺服器的本機磁碟，不得放在任何網路磁碟（SMB／NFS／雲端同步資料夾）。SQLite 的檔案鎖在網路檔案系統上不可靠，這是資料毀損最常見的原因。
    • 開發環境：放在專案目錄外的固定路徑，並且必須加進 .gitignore。資料庫檔案永遠不進版控。
    • WAL 模式會另外產生 -wal 與 -shm 兩個檔案。它們與主檔是一組，複製、搬移、備份時不得只拿主檔。

    0919 改寫：正式主機改為 Windows 之後這一條怎麼落實。 0912 寫的是容器化版本，正式主機當時是 DGX Spark；0919 主機改為院內另一台 Windows 工作站（仍與其他專案共用），交付形態改為離線安裝包（《部署規範》DEP-07）。本條規則一字未改，落實方式如下：

    規則 Windows 主機上的具體做法
    放在本機磁碟 放在該機內接 SSD 的固定目錄（例如 D:\hd-care\data\），不得放在對應的網路磁碟機、不得放在 OneDrive／SharePoint 等同步資料夾、不得放在任何 UNC 路徑
    -wal／-shm 與主檔是一組 三個檔案在同一個目錄，備份與搬移一起處理
    後端是唯一寫入行程 後端以 Windows 服務形式常駐，同一個資料庫檔案只能有一個服務執行個體。資料修補先停服務
    檔案權限只給後端執行帳號 該目錄的 ACL 只給服務執行帳號與系統管理員，一般登入者不得讀寫

    Windows 上另外三件必須做的事（前兩件在開發機上已經踩過，見手動測試手冊的疑難排解）：

    1. 把資料庫目錄加入防毒軟體的排除清單。 即時掃描會在 SQLite 正在寫入時開啟同一個檔案，造成間歇性的鎖定失敗；這種錯誤不固定重現，最難查。部署前置檢查要逐項確認這件事已經做了。
    2. 確認該目錄不在任何雲端同步資料夾底下。 醫院電腦常預設把「文件」重新導向到 OneDrive，而路徑上看不出來。
    3. 不得使用對應網路磁碟機的代號指向遠端目錄。 看起來像本機磁碟，行為是網路檔案系統，正是本條要擋的情形。

    容器路線若日後啟用，0912 那張表仍然適用，但要多一條：資料庫檔案不得落在 Windows 目錄的繫結掛載上（在 WSL2 底下它是跨檔案系統的轉譯層，檔案鎖不可靠），必須放在 Linux 檔案系統的具名資料卷裡。這也是 0919 不選容器的理由之一。

    0926：容器路線成為正式路線（《部署規範》v3.0，安裝包撤除）。本條規則仍一字未改，上面那張 Windows 表改為下表：

    規則 0926 的具體做法
    放在本機磁碟 放在 Docker 具名資料卷（WSL2 的 Linux 檔案系統，實體在主機本機 SSD）。不得以繫結掛載把 Windows 目錄給後端當資料庫用（DEP-23）
    -wal／-shm 與主檔是一組 掛的是資料卷的目錄，三個檔案在同一個掛載點
    後端是唯一寫入行程 compose 裡 api 只有一個執行個體；資料修補與遷移在 api 停止時以一次性容器執行
    ~~檔案權限只給後端執行帳號~~ 0926 作廢：院方決定能登入主機者一律可信任，不另設作業系統層級的帳號與權限（DEP-38）。容器內仍以非 root 執行
    院方看得到、備份得到 資料卷在檔案總管裡看不到，因此備份一律寫到主機的備份目錄（繫結掛載，備份檔寫完即不再被開啟，不受檔案鎖問題影響），再送往院內另一台機器
    防毒排除 要排除的改為 Docker 的資料目錄（WSL2 虛擬磁碟），不是某個資料庫資料夾

    資料卷標為 external，docker compose down -v 也刪不掉它。

    8. 備份、還原與留存期限¶

    8.1 備份¶

    要求 說明
    不得用檔案總管直接複製 服務執行中直接複製 .db 檔可能拿到不一致的狀態。一律用 SQLite 的線上備份機制（VACUUM INTO 或 .backup 指令）
    備份也不能離開院內 備份檔與正本適用同一條規則。不得備到雲端硬碟、不得寄信、不得拷到個人隨身碟。~~0919 補充：部署用的隨身碟是單向的~~（0926：院方不准用隨身碟，這條補充隨之作廢；院內網路現在連得出去，備份不出院改靠程式與流程擋：備份只寫到主機的備份目錄與院內另一台機器，任何腳本不得把備份送往院外）
    至少每日一次，保留數個世代 單檔資料庫的風險是「壞了就全壞」，只留最新一份等於沒有備份
    備份目的地必須是院內另一台機器 0912 收緊，0919 維持。正式主機仍是一台沒有備援電源、沒有磁碟陣列、記憶體不具 ECC 的桌上型機器，同機備份擋不住整機故障（DEP-06）。兩顆 SSD 屬於同一台機器：第二顆可以當備份的第一落點（快、方便、每日多次），但不得是唯一落點——整機故障、遭勒索軟體加密、或有人誤刪整個資料夾時，兩顆一起沒
    更新前必須有一份剛做好且驗證過的備份 0919 新增（FR-S12）。 見第 18 條
    定期演練還原 沒有還原過的備份不算備份。建議每個里程碑至少實際還原一次到測試環境
    備份動作寫入稽核軌跡 誰在什麼時候備份、備到哪裡

    8.2 留存期限（0910 新增，0909 版沒有規範）¶

    無限期堆積本身就是風險。以下期限為建議值，實際期限須由醫院依《醫療法》病歷保留規定與個資法確認後定案：

    資料類別 建議留存 到期後
    稽核軌跡 依醫院規定，至少與病歷同期 不刪除，轉為離線封存
    病人自報症狀與求助紀錄 同病歷 同上
    AI 呼叫紀錄（提示與輸出） 12 個月 刪除內容，保留「發生過、用哪個模型」的統計列
    護理師績效彙整結果 依人資規定 刪除個人層級，保留單位層級聚合
    對外報表產出紀錄 永久 不刪除，這是釋出責任的證據
    開發／測試環境的合成資料 無限制 可隨時整份刪除

    Agent 行為規則：實作任何刪除或封存機制前，先確認醫院是否已定案期限；未定案前一律只做「標記」不做「實際刪除」。

    9. 加密與實體安全¶

    單檔資料庫最大的風險是「整個系統的資料就是這一個檔案」。

    層次 要求
    磁碟層 院內伺服器啟用全磁碟加密。~~0912：正式主機的 4TB NVMe 具硬體自我加密~~ → 0919 改寫：正式主機為 Windows 工作站，改以 BitLocker 對兩顆 SSD 皆啟用，並確認還原金鑰的保管方式已由資訊室指定。金鑰若只存在那台機器上，加密等於沒做；金鑰若存在網域帳號以外的地方，要有人負責保管
    檔案層 資料庫檔案的存取權限只給後端服務的執行帳號，不給一般登入者
    資料庫層 若醫院要求資料庫檔案本身加密，可評估 SQLCipher 等方案。這會改變 Prisma 的連線方式，須先確認相容性再決定，不要在沒確認前寫進架構
    備份檔 與正本同等保護。備份檔常常是最弱的一環
    實體 伺服器機箱與機房門禁由醫院既有規範處理，本專案不另訂

    Agent 行為規則：

    • 不得把資料庫檔案路徑、加密金鑰或任何密碼寫入程式碼、文件、commit 訊息或終端機輸出。一律走環境變數。
    • 不得為了除錯方便，把正式環境的資料庫檔案複製到開發機。要重現問題請用合成資料重建情境。

    10. 測試資料規範¶

    • 絕對禁止在任何開發或測試環境中使用真實病人的可識別資訊（真實姓名、真實病歷號、真實生命徵象數值組合）。
    • 測試資料一律使用完全虛構的合成資料：假名、隨機生成的病歷號格式（HD-TEST-xxxx）、隨機生成的數值。
    • 理由的變化：0909 版的理由是「Supabase 主機在院外」。改用 SQLite 後這個理由消失，但規則不變，新理由有兩個：
    • 開發者本機不是院內環境，把真實資料放上去等於資料離開了它該在的機器（核心原則第 1 條）
    • 過渡期的 AI 走實驗室 API，那是院外服務。只要開發環境有真實資料，就有送出去的風險

    Agent 行為規則：

    • 產生測試資料／seed 腳本時，一律使用假資料產生器（faker 等）產生合成資料。
    • 若使用者提供看起來像真實病人資料的內容作為測試輸入，應提醒改用合成資料。
    • 對外展示環境（見第 12 條）一律使用合成資料，且必須與正式環境是不同的資料庫檔案、不同的機器。

    11. 營運與績效資料的蒐集限制（0910 新增）¶

    新增任務一要蒐集護理師的工作表現資料，用於排班、獎勵與對外展現成效。同一批資料，用途不同，風險等級完全不同，因此需要一組獨立於臨床資料的規則。

    11.1 資料分級¶

    級別 內容 誰能看
    L1 單位聚合 全單位／全班次的統計量（回應時間中位數、當班求助總數） 已登入的護理端使用者皆可
    L2 班次層級 單一班次的統計量 護理長以上
    L3 個人層級 可對應到特定護理師的統計量 護理長以上，且須經第 11.3 條的啟用流程
    L4 原始事件 稽核軌跡原始列，含操作者、時間戳 護理站管理者與稽核角色，逐次查詢須留紀錄

    11.2 目的外利用的禁止¶

    稽核軌跡的原始蒐集目的是法規遵循與事故追溯。拿它算績效屬於目的外利用，因此：

    • L3 與 L4 的查詢，每一次都要寫入稽核軌跡（誰查了誰的資料、查詢區間、查詢當下宣告的用途）
    • 不得把績效彙整結果回寫到臨床資料表中，兩者永遠分開儲存
    • 不得建立「護理師×病人」的交叉評分資料表——那會把病人的臨床結果與特定護理師綁定，是明確的禁區（見《FDE 評估報告》5.4）
    • 對外報表一律不得包含 L3 與 L4

    11.3 個人層級資料的啟用流程¶

    L3 預設關閉。要開啟必須同時滿足：

    1. 護理部書面同意，且已向全體護理師公告計分規則
    2. 系統設定中有一個明確的開關，開啟與關閉都寫入稽核軌跡
    3. 已完成至少一個完整週期的「只看不算」觀察期
    4. 每一位護理師都能查閱自己的原始計分事件並提出更正申請

    Agent 行為規則：

    • 實作任何會產生 L3 資料的查詢或報表前，必須先確認上述開關存在且已開啟，不得以「先做起來放著」為由跳過。
    • 不得在資料表設計中預留「總分」「排名」這類欄位。排名若有需要，一律於查詢時即時計算，不寫入資料表。

    12. 資料釋出（要離開院內的內容）¶

    對應新增任務一之(4)「讓外部公司或機構判斷團隊實力」。任何要離開醫院網路的資料，都必須經過這一節。

    12.1 唯一合法的釋出管道¶

    • 一律經由系統內建的對外報表功能產生，不得以資料庫檔案複製、SQL 查詢結果貼上、螢幕截圖等方式取出。
    • 對外報表功能是一個獨立的模組，有自己的權限與稽核，不共用一般查詢的權限。

    12.2 對外報表的硬性規則¶

    規則 說明
    只輸出聚合值 不得輸出任何單筆紀錄
    最小分母門檻 任何分組的樣本數少於 5 筆，該分組一律不呈現（避免反推到個人）
    禁止欄位 姓名、病歷號、床號、工作 ID、可定位到單一療程的精確時間戳，一律不得出現
    時間粒度限制 最細到「日」，不得輸出到分秒
    核准後才能取出 由指定核准角色（建議護理部主管加資訊室）確認
    全程留痕 誰產生、什麼時候、給誰、包含哪些指標、核准者是誰

    12.3 對外展示環境¶

    若要提供可實際操作的展示環境給外部單位：

    • 必須是獨立的資料庫檔案、獨立的機器，與正式環境無任何連線
    • 資料全部由 faker 產生，不得由正式資料脫敏而來——脫敏後的資料仍可能保留可辨識的模式
    • 展示環境的建立與銷毀寫入稽核軌跡

    13. 外部資料匯入（輪播第三層與臨床數值）¶

    對應新增任務二。院方可能提供 API，也可能提供 Excel，格式尚未確定。

    規則 說明
    統一入口 不論來源是 API 或檔案，一律經由 ClinicalDataSourcePort 進入，收斂成同一組內部資料表
    全有或全無 一批匯入中只要有任何一筆解析失敗或驗證不過，整批不寫入。臨床數值只對一半比完全沒有更危險
    來源可追溯 每一筆匯入資料都要記錄來源（檔名或 API 端點）、匯入時間、匯入者、批次編號
    重複偵測 同一份檔案重複上傳必須被擋下，或明確標記為覆蓋並保留前一版
    欄位對應可設定 Excel 欄位名稱會被人改動。欄位對應要能在管理介面調整，不得寫死在程式碼裡
    不得直接餵給輪播 匯入的資料先進資料表、通過驗證，輪播才讀得到
    時效標示 每一筆臨床數值都要有「這是什麼時候的資料」，輪播顯示時必須一併呈現，避免病人看到三週前的體重以為是今天的

    Agent 行為規則：不得為了先看到畫面而把 Excel 直接解析後塞進前端。介面層與資料表要先建立，即使一開始只有 ManualEntryAdapter 可用。

    14. AI 相關資料的儲存¶

    資料 存不存 規則
    送給模型的提示內容 存 已去識別化的版本才存。留存 12 個月（見 8.2）
    模型回傳的內容 存 同上。供事後查核「當時系統對護理師說了什麼」
    使用的模型名稱、參數、耗時 存 永久保留，這是成效與成本分析的基礎
    是否觸發去識別化過濾 存 永久保留，這是治理證據
    護理師是否採納 AI 輸出 存 對應 FDE 報告 R-6，永久保留
    原始（未去識別化）提示 不存 沒有任何理由需要保留它
    模型權重、快取檔 不進資料庫 放檔案系統，不佔資料庫檔案空間

    Agent 行為規則：

    • 去識別化必須發生在寫入資料庫之前，不是查詢時才遮蔽。
    • 三項高風險功能（風險分層、療程中預警、劑量調整參考）的計算不經語言模型（FDE 報告 R-1），因此它們的紀錄存的是「套用了哪一條規則、哪一個門檻、規則版本」，不是模型輸出。

    15. 從 Supabase 撤出（一次性作業）¶

    步驟 動作
    1 確認 Supabase 專案中確實只有合成測試資料（依 0909 版第 7 條，本應如此）
    2 不做資料遷移。 既有測試資料直接捨棄，用 seed 腳本在 SQLite 上重建
    3 Prisma datasource provider 改為 sqlite，移除 directUrl
    4 重新產生 migration。SQLite 與 PostgreSQL 的 migration 檔不相容，舊的 migration 目錄整組重建
    5 移除所有 Supabase 相關環境變數與套件相依
    6 停用並刪除 Supabase 專案，確認雲端不再留有任何本專案資料
    7 更新《資料字典》的環境標示與型別對照表

    驗收：全新環境 clone 之後，只設定一個 DATABASE_URL 指向本機檔案，跑完 migration 與 seed 就能啟動，全程不需要任何網路連線。

    16. 快速檢查清單（給 Agent 的執行前自我檢查）¶

    在協助撰寫任何與資料庫相關的程式碼前，Agent 應自我確認：

    • 這段程式碼是否讓前端直接碰資料庫檔案？→ 若是，改為透過後端 API
    • 存取控制邏輯是否寫在後端應用層？→ 不得依賴檔案權限或前端隱藏
    • 是否在業務邏輯中直接寫 SQL 或 SQLite 方言？→ 改走 Repository／ORM 層
    • 新欄位若帶小數，是否誤用了浮點數？→ 臨床數值一律改整數最小單位或 TEXT
    • 是否新增了第二個會寫入資料庫的行程？→ 不允許
    • 測試資料是否為虛構合成資料？→ 若不是，一律替換
    • Schema 是否包含稽核軌跡所需欄位？→ 若無，補齊後再實作
    • 這次的功能是否會產生 L3 個人層級績效資料？→ 若是，先確認第 11.3 條的開關
    • 這次的輸出是否可能離開院內？→ 若是，走第 12 條的對外報表模組
    • 匯入外部資料時，是否做到全有或全無？→ 部分寫入不允許
    • 送進 AI 的內容是否已去識別化？→ 去識別化要在寫入前發生
    • 資料庫或備份的路徑是否寫死在程式裡？→ 一律由設定提供；正式環境是主機上的一個目錄，不是固定字串
    • 這次的 schema 變更是否可能讓既有資料讀不出來或被清空？→ 見第 18 條，先過那四關
    • 這次改的是已經套用過的遷移檔嗎？→ 不允許，改成新增一個

    17. 總結¶

    SQLite 在本專案中的角色是「一個檔案，裝著整個透析中心的照護紀錄」。這句話同時說明了它的優點與它的風險：簡單到不需要維運，也脆弱到一次疏忽就全毀、一次複製就全外流。

    因此本規範的重點從 0909 版的「不要被平台綁死」，轉為三件事：讓資料留在該在的地方（第 1、7.2、9、12 條）、讓它不會壞掉也不會丟掉（第 7、8 條）、讓它不被拿去做原本不該做的事（第 11 條）。

    所有驗證、授權、業務邏輯、Session 管理仍然全部留在自建後端。這一點從 0909 版到現在沒有變過，未來也不會因為換了哪一種資料庫而改變。

    18. 版本更新時的資料庫保護（0919 新增）¶

    對應 SRS 的 FR-S12。第一次正式部署之後，每一次更新面對的都是真實病人資料，而這份資料只有一個檔案。 本條規範的是「更新這件事本身」，與第 8 條的日常備份是兩回事。

    18.1 四道關卡，缺一不可¶

    # 關卡 不做會怎樣
    1 更新前完成一次備份，並實際驗證它還原得起來 「有備份」和「備份能用」是兩件事。沒有還原過的備份不算備份（第 8.1 條），而發現它不能用的時機通常是你最需要它的那一刻
    2 遷移只能前滾 已經套用過的遷移檔不得修改。改了之後，開發機重建出來的資料庫與正式環境那顆會長得不一樣，而且不會有任何錯誤訊息
    3 正式環境不得執行任何會重建資料庫的指令 開發用的遷移指令在偵測到「資料庫與遷移歷史對不上」時，會提議或直接重建整個資料庫。在開發機上那是方便，在正式主機上那是把整個透析中心的紀錄刪掉
    4 舊版本在新版穩定前不得刪除 沒有可以退回去的東西時，出問題的當下只剩「硬著頭皮往前修」一條路

    18.2 遷移怎麼寫才不會毀掉既有資料¶

    原則：一次更新只做加法，減法留到下一次。

    要做的事 安全的做法 危險的做法
    新增欄位 允許為空，或給預設值 直接加上「不得為空且無預設值」的欄位——既有的列填不出來
    改欄位型別 新增一個新欄位 → 搬資料 → 兩邊並存一段時間 → 下一版才移除舊的 直接改型別，讓資料庫自己轉換
    改欄位名 同上，新增再搬 直接改名
    移除欄位或資料表 至少隔一個版本，確認新版穩定、沒有程式再讀它之後才移除 與新增同一版一起做
    補既有資料 寫成獨立的資料轉換步驟，可重複執行且結果相同 寫在應用程式啟動流程裡

    為什麼「改欄位名」要繞這麼大一圈：SQLite 的部分結構變更會以「建新表、搬資料、刪舊表、改名」的方式完成。這個過程中任何一步失敗，留下的可能是一個半成品。加法不會走到這條路徑上。

    18.3 回到上一版的正確做法¶

    程式可以退版，資料庫不行退版。

    情形 怎麼做
    新版有問題，但這一版沒有動 schema 直接換回舊版（0926 起：checkout 舊 tag、改用舊版映像檔標籤），資料庫不動
    新版有問題，且這一版動過 schema 還原更新前那份備份，再換回舊版。不要試圖把遷移倒回去
    已經在新版上累積了新的資料，才發現問題 停下來評估：還原備份會失去這段期間的資料。此時的決定不是技術決定，要有人負責

    第三種情形是最貴的一種，而它只有一個預防方法：更新之後的頭一個班次要有人盯著。 更新排在非透析時段、上線後第一個班次確認主線功能正常，就是為了讓「發現問題」發生在「累積新資料」之前。

    18.4 每一次更新都要留下的紀錄¶

    • 更新前備份的檔名、大小、驗證還原的時間與結果
    • 這次套用了哪幾個遷移
    • 更新前後的版本標記
    • 誰執行的、什麼時候、在哪一個時段

    這些寫入稽核軌跡，與備份動作同一類事件。沒有這份紀錄，半年後發現資料對不上時，沒有人答得出「那是哪一次更新帶進來的」。
