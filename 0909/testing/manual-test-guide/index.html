    血液透析平板照護輔助系統 — 完整手動測試手冊¶

    從 git clone 一路走到每一個細節功能。每一項都寫明「怎麼做」與「應該看到什麼」。 對應版本：Iteration 2 · 43 條 API 路由 · 32 種稽核動作。

    本頁的核取方塊在 GitHub 與 HackMD 上都可直接勾選，用來記錄你走到哪裡。

    00 · 開始之前¶

    這份手冊假設你手上有一台 Windows 或 macOS 開發機、一個 Supabase 專案，以及 Chrome。全程只在本機執行，不需要任何雲端部署。

    服務 網址 說明
    護理站主控台 http://localhost:5173 護理端 PWA，需登入
    病人端平板 http://localhost:5174 Kiosk 介面，沒有登入，靠裝置金鑰佈建
    後端 API http://localhost:3000/api 所有資料存取的唯一入口

    注意｜測試資料規範

    《資料庫使用規範》第 7 條：絕對禁止輸入任何接近真實病人的資訊。手冊中所有姓名、病歷號皆為虛構，請照抄或自行編造。

    說明｜關於速度

    資料庫已於 2026-09-07 由孟買（ap-south-1）搬到東京（ap-northeast-1）。單次資料庫查詢往返約 237 ms，一次已驗證的 API 請求約 700 ms，端到端（平板送出 → 護理端收到）約 1.9 秒。 畫面上仍會有短暫等待，但已不再是搬遷前那種數秒級的停頓。若你看到單一動作卡超過 5 秒，那多半是別的問題，可以往 §10 疑難排解找。

    01 · 從 clone 到跑起來¶

    • a1 ［終端機］ Clone 專案並進入目錄。 → 取得 apps/、packages/、demand_v1/ 三個資料夾。
    git clone https://github.com/94sh09sh19sh/hd-tablet-care.git
cd hd-tablet-care
    • a2 ［終端機］ 確認 Node 版本 ≥ 20.11。 → node -v 顯示 v20.11 以上（開發環境用 v24）。版本太舊會在後續步驟出現語法錯誤。
    • a3 ［終端機］ 安裝相依套件。 → npm workspaces 會一次裝好 api、兩個 PWA 與 shared 套件，過程無紅字錯誤。
    node -v
npm install

    注意｜npm install 出現權限錯誤（EPERM／EACCES／operation not permitted）

    Windows 上最常見的三個原因，依序排查：① 有 node 行程正抓著 node_modules — 關掉還在跑的 dev server 與編輯器再重試。② 專案放在 OneDrive／雲端同步資料夾底下，同步程式會鎖檔 — 把專案移到不同步的路徑。③ 防毒即時掃描擋住寫入 — 把專案資料夾加入排除清單。 都試過還是不行，再以系統管理員身分開啟 PowerShell 重跑；若已經裝壞了，先刪掉 node_modules 資料夾，執行 npm cache clean --force 後重來。

    建立 .env¶

    • a4 ［終端機］ 複製環境變數範本。 → 專案根目錄出現 .env（已列入 .gitignore，不會被提交）。
    cp .env.example .env
# PowerShell：Copy-Item .env.example .env

    以下五個變數必填，其餘留空即用預設值：

    變數 怎麼取得
    DATABASE_URL Supabase → Project Settings → Database → Connection string → 選 Transaction pooler（port 6543），結尾加上 ?pgbouncer=true&connection_limit=5
    DIRECT_URL 同一個 pooler 主機但 port 5432（Session pooler），不加 pgbouncer 參數。供 prisma migrate 使用
    JWT_SECRET 自行產生，見下方指令
    SUPER_ADMIN_WORK_ID 初始最高權限帳號的工作ID，例如 ADMIN001（英數字、底線、連字號，3–32 字元）
    SUPER_ADMIN_INITIAL_PASSWORD 至少 8 字元。首次登入後會被強制變更

    在終端機執行 — 這是指令，不是要貼進 .env 的值

    node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

    注意｜這一行是指令，不是設定值

    把整行貼到終端機執行（PowerShell、cmd、Git Bash 都可以），它會印出一串長長的亂碼。那串印出來的東西才是要填進 .env 的值： JWT_SECRET=印出來的那一串 不要把 node -e ... 這行本身貼進 .env — 那樣後端啟動時會把整行當成金鑰，雖然不會壞掉，但等於用了一把人人都猜得到的鑰匙。

    地雷｜常見地雷

    DIRECT_URL 不要用 Supabase 的 Direct connection（db.<ref>.supabase.co）。那個主機只有 IPv6 記錄，在 IPv4-only 的網路會出現 P1001 Can't reach database server。一定要用 Session pooler 字串。

    • a5 ［終端機］ 填完 .env 後，確認五個必填變數都有值。 → DATABASE_URL 與 DIRECT_URL 是兩個不同 port（6543 / 5432）的字串。

    建立資料庫與測試資料¶

    • a6 ［終端機］ 先編譯共用型別套件（後端與前端都依賴它）。 → packages/shared/dist/ 產生 cjs 與 esm 兩份輸出。
    • a7 ［終端機］ 建立資料庫 schema。 → 套用兩個 migration（init、iteration2_symptom_reports_help_requests），最後顯示資料庫已同步。
    • a8 ［終端機］ 產生合成測試資料。 → 建立 8 位病人（HD-TEST-0001～0008）與 15 台平板（TB-01～TB-15），裝置金鑰寫入 apps/api/.device-keys.json。這 15 台平板預設尚未納入 MDM，稍後要手動註冊。
    npm run build:shared
npm run prisma:migrate
npm run db:seed

    這三行各做一件事，缺一不可：

    指令 在做什麼 為什麼需要
    npm run build:shared 把 packages/shared 的 TypeScript 編譯成 JS。裡面是前後端共用的型別與常數：問卷題庫、求助分派規則、26 種稽核動作代碼、權限碼。 後端與兩個 PWA 都會 import 它。沒編譯過，後端一啟動就找不到模組。之後每次改動 shared 都要重跑（npm run dev 會自動先跑一次）。
    npm run prisma:migrate 讀 apps/api/prisma/schema.prisma，把資料表建到 .env 的 DIRECT_URL 指向的資料庫，並產生 Prisma Client。本專案目前有兩個 migration。 你的資料庫一開始是空的。這步建出 nurses、patients、devices、device_bindings、symptom_reports、help_requests、audit_logs 等資料表。沒跑過，後續任何操作都會失敗。
    npm run db:seed 灌入虛構測試資料：8 位病人（HD-TEST-0001～0008）與 15 台平板（TB-01～TB-15），並把平板金鑰寫到 apps/api/.device-keys.json。 沒有病人就不能建排班，沒有平板就不能指派。它不建立任何護理師帳號 — 那是後端啟動時依 .env 自動建立的。可重複執行，已有資料時會自動略過。

    啟動¶

    • a9 ［終端機］ 一次啟動後端與兩個 PWA。 → 三色標示的 log 同時輸出。後端出現「後端服務已啟動：http://localhost:3000/api」。
    • a10 ［終端機］ 在後端 log 中找「已建立初始最高權限帳號」。 → 全新資料庫會看到這行，代表 .env 的帳密已建立成 SUPER_ADMIN。若資料庫已有使用者則不會出現（正常）。
    npm run dev

    補充｜只想跑其中一個

    npm run dev:api / npm run dev:nurse / npm run dev:patient 可分別啟動。改動 packages/shared 後要重跑 npm run build:shared 才會生效。

    02 · 冒煙測試¶

    花兩分鐘確認三個服務都活著，再往下走。

    • b1 ［護理端］ 開啟 http://localhost:5173。 → 看到「護理站主控台」登入卡片，有「登入 / 註冊申請」兩個分頁。
    • b2 ［病人端］ 開啟 http://localhost:5174（不帶任何參數）。 → 看到「裝置尚未佈建」畫面。這是給院方人員設定平板用的，不是病人登入 — 正式環境由 MDM 直接把序號與金鑰寫進 Kiosk 網址，病人永遠看不到這頁。
    • b3 ［終端機］ 確認 API 有回應。 → 回傳 401。沒帶權杖被拒是正確的 — 代表路由有掛上、驗證有生效。

    Git Bash / cmd.exe

    curl -i http://localhost:3000/api/overview

    PowerShell — 注意是 curl.exe

    curl.exe -i http://localhost:3000/api/overview

    注意｜PowerShell 要打 curl.exe

    PowerShell 把 curl 設成 Invoke-WebRequest 的別名，它不認得 -i、-s、-H 這些參數，會噴「找不到符合參數名稱 i 的參數」。加上 .exe 才會呼叫到真正的 curl。本手冊後面所有 curl 指令，在 PowerShell 都要改成 curl.exe；Git Bash 與 cmd.exe 直接用 curl 即可。

    03 · 主線 A — 裝置綁定完整流程¶

    這是 Iteration 1 的驗收主線：登入 → 核准護理師 → 建排班 → 指派平板 → 病人端顯示 → 解除綁定 → 稽核可查。走完這一段，系統的骨架就確認可用了。

    身份驗證與審核¶

    • c1 ［護理端］ 以 .env 的 SUPER_ADMIN_WORK_ID 與初始密碼登入。 → 登入失敗跳「工作ID 或密碼錯誤」請看下方的排查框。全新資料庫：直接被導到「變更密碼」畫面，藍色提示說明此帳號正在使用 .env 的初始密碼，未變更前不能使用其他功能。
    • c2 ［護理端］ 設定新密碼（至少 8 字元，兩次輸入需一致）。 → 顯示「密碼已變更 / 所有既有登入階段已撤銷」，必須用新密碼重新登入。請記下新密碼 — .env 裡的舊密碼從此失效。
    • c3 ［護理端］ 重新登入，確認進入主控台。 → 頂端導覽列出現：即時總覽、緊急通報、排班與指派、帳號審核、病人、裝置管理、稽核軌跡。右上顯示你的工作ID 與 SUPER_ADMIN。
    • c4 ［護理端］ 登出 → 切到「註冊申請」分頁 → 申請一個新帳號，工作ID 用 N001、姓名自訂、密碼至少 8 字元。 → 顯示申請已送出、等待審核。
    • c5 ［護理端］ 立刻用 N001 嘗試登入。 → 被拒，訊息「註冊申請尚待審核，核准後才能登入」（HTTP 403）。這是 3.1 節第 2 點的要求。
    • c6 ［護理端］ 以管理者登入 → 「帳號審核」→ 在「待審核註冊申請」找到 N001 → 按「核准」。 → 綠色提示「已核准 N001，該帳號現在可以登入」，下方「帳號與權限」表中該列狀態變成 ACTIVE。
    • c7 ［護理端］ 登出，改用 N001 登入。 → 登入成功。導覽列只有即時總覽、緊急通報、排班與指派、病人、裝置管理 — 沒有「帳號審核」與「稽核軌跡」（一般護理師無此權限）。

    地雷｜登入一直顯示「工作ID 或密碼錯誤」

    這個訊息只代表兩件事之一：工作ID 不存在，或密碼不對（刻意不區分，避免洩漏帳號是否存在）。依序排查： ① 別用打的，用複製貼上。最常見的兇手是中文輸入法：密碼結尾若有 !，中文模式下會打成全形的 ！，長度一樣但完全不同的字元。切到英數模式，或直接從 .env 複製貼上。 ② 檢查瀏覽器自動填入有沒有蓋掉你輸入的值（欄位變黃底就是）。 ③ 你是不是已經改過密碼了？手冊的 c2 步驟會強制變更密碼，改完之後 .env 裡的初始密碼就永久失效。 ④ 用下面的指令直接驗（完全不經過鍵盤與瀏覽器）。

    在專案根目錄執行，用 .env 的原值直接打 API

    node -r dotenv/config -e "fetch('http://localhost:3000/api/auth/login',{method:'POST',headers:{'Content-Type':'application/json'},body:JSON.stringify({workId:process.env.SUPER_ADMIN_WORK_ID,password:process.env.SUPER_ADMIN_INITIAL_PASSWORD})}).then(r=>Promise.all([r.status,r.text()])).then(([s,t])=>console.log(s,t.slice(0,80)))" dotenv_config_path=.env

    補充｜怎麼判讀上面的結果

    印出 200 加一串 accessToken → 帳號與密碼都是對的，問題百分之百出在瀏覽器的輸入（回頭看 ① 和 ②）。 印出 401 → 資料庫裡的密碼確實跟 .env 不一樣了，多半是已經改過密碼。用你當初設定的新密碼登入；真的想不起來，就照 §10 重置資料庫。 印出 403 → 帳號存在但狀態不是 ACTIVE。 連不上（ECONNREFUSED）→ 後端沒啟動。

    05 · 離線韌性¶

    SRS 4.4 對離線行為有兩條方向相反的要求：症狀回報必須能暫存並自動補傳；求助則必須明確告知無法通知護理站。這一節同時驗證兩者。

    注意｜為什麼求助不做離線暫存

    讓病人誤以為護理站已收到，比誠實說明送不出去更危險。因此離線時求助按鈕直接停用並引導改用床邊呼叫鈴。這是刻意的設計取捨，不是缺漏。

    • e1 ［病人端］ 在病人端按 F12 開 DevTools → Network 分頁 → 把 Throttling 下拉選成「Offline」。 → 只影響這個分頁，護理端不受影響。
    • e2 ［病人端］ 等 3–5 秒觀察主畫面。 → 出現黃字「目前沒有網路連線。症狀問卷仍可填寫並暫存於本平板；求助請改用床邊呼叫鈴。」求助按鈕副標變成「目前無法即時通知護理站」。
    • e3 ［病人端］ 點進「我需要協助」。 → 頂端橘色警示框：「目前無法即時通知護理站。請改用床邊呼叫鈴，或直接出聲呼叫附近的護理人員。」底部按鈕顯示「離線中，無法通知」且停用。
    • e4 ［病人端］ 回上一頁 → 點進「填寫透析前症狀問卷」。 → 頂端黃字：「目前沒有網路連線。您仍可以填寫，送出後會暫存在這台平板，恢復連線時自動傳送給護理站。」問卷本身完全可用（題庫打包在前端，不需連線）。
    • e5 ［病人端］ 把「呼吸會喘」點成嚴重，按「送出給護理站」。 → 回主畫面顯示綠字「已暫存在這台平板。恢復連線後會自動送給護理站，資料不會遺失。」以及「尚有 1 筆症狀回報等待傳送」。
    • e6 ［病人端］ 把 Throttling 改回「No throttling」，等約 10 秒。 → 離線提示消失，出現綠字「已將 1 筆離線暫存的症狀回報送出給護理站」，等待傳送的計數歸零。
    • e7 ［護理端］ 看即時總覽該病人列。 → 病人自述症狀更新為「呼吸會喘・嚴重」（顯示的是最新一份回報）。
    • e8 ［護理端］ 「稽核軌跡」→ 篩選「病人送出症狀問卷」→ 看最新一列的說明欄。 → 包含「送出方式 離線暫存後補傳」。系統把即時送出與離線補傳分開記錄，且保留病人當初填寫的時間，不會被補傳時間覆寫。

    說明｜資料為什麼不會掉

    病人按下送出時，資料是先寫進 IndexedDB 佇列、再嘗試上傳，成功才移除。就算平板在上傳途中斷電或被 Kiosk 重新載入，資料仍在。後端再用平板產生的識別碼去重，所以重複補傳也不會變成兩筆。

    非常緊急，請馬上過來 緊急處置團隊 緊急處置團隊
    不太舒服，請盡快過來 護理師 護理師
    不急，方便時再過來 護理師 護佐／行政支援

    • f49 ［病人端］ 送出「需要上廁所」＋「非常緊急，請馬上過來」。 → 「分派：緊急處置團隊」。急迫度優先於類型。
    • f50 ［病人端］ 送出「機器在叫」＋「不急，方便時再過來」。 → 「分派：護理師」。臨床類型即使不急也不會下放給護佐。

    08 · 收工 — 正確關閉與重新啟動¶

    測試告一段落時，把服務關乾淨比想像中重要：Windows 上 Ctrl+C 有機會沒把子行程一起帶走，下次啟動就會撞 EADDRINUSE，而且你會以為是程式壞了。

    正常關閉¶

    • j1 ［終端機］ 回到執行 npm run dev 的那個終端機視窗，按一次 Ctrl+C。 → concurrently 會一併停掉後端與兩個 Vite，三色 log 停止輸出，提示字元回到你手上。後端有註冊 shutdown hook，會正常中斷資料庫連線後才結束，不是硬砍。
    • j2 ［終端機］ 如果你另外開了視窗跑 Prisma Studio（§06.7），那個視窗要各按一次 Ctrl+C。 → port 5555 釋出。它是獨立行程，不會被 npm run dev 的 Ctrl+C 帶走。
    • j3 ［病人端］ 關掉病人端與護理端的瀏覽器分頁。 → 病人端每 3 秒輪詢一次、護理端持有一條 SSE 長連線。不關不會壞（後端一起來它們會自動接回），但排查問題時這些背景請求會干擾你判讀 log。

    確認真的關乾淨¶

    這一步別跳過。四個 port 分別是：後端 3000、護理端 5173、病人端 5174、Prisma Studio 5555。

    PowerShell

    Get-NetTCPConnection -LocalPort 3000,5173,5174,5555 -State Listen -ErrorAction SilentlyContinue |
  Select-Object LocalPort, OwningProcess

    Git Bash / cmd.exe

    netstat -ano | findstr /R /C:":3000 " /C:":5173 " /C:":5174 " /C:":5555 "
    • j4 ［終端機］ 執行上面任一版本。 → 沒有任何輸出＝已經關乾淨。若列出 port 與 PID，代表有行程沒被帶走（Windows 上這其實蠻常見的）。
    • j5 ［終端機］ 有殘留的話，用上一步查到的 PID 精準結束它。 → 再查一次應該就沒有輸出了。

    用 PID 結束（把 33244 換成你查到的數字）

    # PowerShell
Stop-Process -Id 33244 -Force

# cmd.exe
taskkill /PID 33244 /F

# Git Bash 要用雙斜線
taskkill //PID 33244 //F

    地雷｜不要一次砍光所有 node

    Get-Process node | Stop-Process -Force 這種寫法非常危險。一般開發機上通常同時有十幾個 node 行程 — 編輯器、語言伺服器、其他專案、甚至 Claude Code 本身都可能是 node。一定要先查出 port 對應的 PID，再針對那個 PID 結束。

    關掉之後，哪些東西還在¶

    項目 關閉服務後會怎樣
    所有資料（帳號、病人、排班、綁定、問卷、求助、稽核） 都在 Supabase，完全不受影響。本機只是應用程式。
    進行中的綁定 不會因為關掉服務而失效，資料庫裡仍是 ACTIVE。下次啟動照常運作；若一直沒人管，超過 BINDING_MAX_HOURS（預設 6 小時）後，背景掃描會自動讓它逾時失效。
    病人端未送出的離線回報 存在瀏覽器的 IndexedDB，關掉分頁不會遺失。下次用同一台平板開啟、且該筆綁定仍有效時會自動補傳。但綁定若已被解除，補傳會被拒絕，資料會在清除流程中一併移除。
    .device-keys.json 留在 apps/api/，下次還能用。除非你重跑 db:seed 或重置資料庫。
    登入權杖 存在瀏覽器 localStorage，下次開啟仍是登入狀態（除非超過 JWT_EXPIRES_IN，預設 8 小時）。

    收工前建議做的兩件事¶

    • j6 ［護理端］ 看即時總覽，把還在「療程進行中」的綁定按「下機結束」。 → 不是必要步驟，但下次進來時資料狀態乾淨，也比較貼近真實流程（病人下機才離開）。
    • j7 ［病人端］ 看病人端有沒有「尚有 N 筆症狀回報等待傳送」。 → 若有，先確認網路正常、等它顯示「已將 N 筆離線暫存的症狀回報送出給護理站」再關 — 否則那筆資料可能會隨著綁定解除被清掉。

    下次重新啟動¶

    • j8 ［終端機］ 在專案根目錄執行 npm run dev 就好。 → 不需要重跑 prisma:migrate 或 db:seed — 資料都還在。build:shared 也不用手動跑，npm run dev 會自動先跑一次。
    • j9 ［終端機］ 若啟動時出現 EADDRINUSE :::3000。 → 就是上次沒關乾淨。回到本節「確認真的關乾淨」，查 PID 然後結束它，再啟動一次。

    補充｜只重新啟動後端

    改了後端程式碼時，npm run dev 用的是 nest start --watch，會自動重新編譯並重新啟動，不必手動關。此時護理端的即時總覽會短暫顯示「串流中斷，改為定時更新」，後端起來後自動變回「即時連線中」。

    10 · 疑難排解¶

    症狀 原因與處理
    PowerShell 執行 curl 噴「找不到符合參數名稱 i 的參數」 PowerShell 的 curl 是 Invoke-WebRequest 的別名。改打 curl.exe，或改用 Git Bash。
    npm install 出現 EPERM／權限不足 ① 關掉還在跑的 node 行程與編輯器；② 專案不要放在 OneDrive 等同步資料夾；③ 把資料夾加入防毒排除清單。仍失敗再以系統管理員身分開 PowerShell 重跑。
    用 .env 的帳密登入卻說「工作ID 或密碼錯誤」 最常見是中文輸入法把 ! 打成全形 ！ — 改用複製貼上。其次是你已經走過強制變更密碼那步（.env 的初始密碼從此失效）。用 §03 的 node 指令可直接判斷是哪一種。
    P1001 Can't reach database server DIRECT_URL 用了 Direct connection（只有 IPv6）。改用 Session pooler 字串（同 pooler 主機、port 5432）。
    每個動作都要等好幾秒 先確認 .env 指向的是東京的 pooler 主機（aws-0-ap-northeast-1...）。若仍指向 ap-south-1（孟買），單次往返會是 1.7–2.2 秒而不是 237 ms — 照 §12 搬遷。正式環境資料庫在院內時不存在此成本。
    EADDRINUSE :::3000（或 5173／5174） 上次沒關乾淨，有殘留行程佔著 port。照 §08 查出 PID 再精準結束；不要一次砍光所有 node 行程。
    前端出現 CORS 錯誤 CORS_ORIGINS 沒包含前端網址。預設是 http://localhost:5173,http://localhost:5174。
    操作到一半一直跳 401 權杖過期（JWT_EXPIRES_IN 預設 8h），或你剛變更密碼／被降權 — 兩者都會主動撤銷既有登入階段。重新登入即可。
    病人端一直停在「裝置尚未佈建」 序號或金鑰不對，或該平板還沒在後端註冊。用 .device-keys.json 的值，或在護理端重新註冊一台取得新網址。
    指派平板的下拉選單是空的 平板需同時符合：已 MDM 納管、未被鎖定、未被其他病人佔用。seed 出來的 15 台預設未納管。
    改了 packages/shared 沒生效 要重跑 npm run build:shared。npm run dev 啟動時會自動跑一次。
    稽核軌跡少了某筆記錄 稽核寫入失敗不會中斷主流程，只在後端 log 留下 error。去終端機找 稽核軌跡寫入失敗。

    12 · 附錄 — 更換資料庫區域¶

    說明｜本專案已於 2026-09-07 完成搬遷

    孟買（ap-south-1）→ 東京（ap-northeast-1）。實測改善： 單次資料庫查詢往返 1,741–2,249 ms → 237 ms；驗收腳本量測的 API 往返 1,741–2,249 ms → 702 ms；端到端（平板送出 → 護理端收到）4,710–5,899 ms → 1,856–1,893 ms。兩支驗收腳本皆全數通過，且「環境相關觀察」警告已消失。 以下步驟保留供日後再次搬遷（或建立新環境）時參考。

    Supabase 不支援原地換區，做法是開一個新專案再把 schema 建過去。

    補充｜決定連到哪個資料庫的只有兩條字串

    DATABASE_URL（應用程式走 Transaction pooler）與 DIRECT_URL（migration 走 Session pooler）。.env.example 裡的 SUPABASE_PROJECT_URL 與 SUPABASE_SERVICE_ROLE_KEY 沒有任何程式碼引用，改不改都不影響執行。其餘變數（JWT_SECRET、SUPER_ADMIN_*、BINDING_MAX_HOURS…）一律不用動。

    步驟¶

    • k1 ［終端機］ 先照 §08 把服務關乾淨。 → 3000／5173／5174／5555 都沒有行程監聽。
    • k2 ［資料庫］ 在 Supabase 開新專案，區域選 Tokyo（ap-northeast-1），設一組新的 database password 並記下來。 → 從台灣連，延遲大致是 Tokyo ≈ Seoul < Singapore ≪ Mumbai。等 provisioning 跑完再繼續。
    • k3 ［資料庫］ Project Settings → Database → Connection string，取兩條字串。 → Transaction pooler（port 6543）→ 給 DATABASE_URL，結尾加 ?pgbouncer=true&connection_limit=5；Session pooler（port 5432，同一個 pooler 主機）→ 給 DIRECT_URL，不加參數。主機名會變成 aws-0-ap-northeast-1.pooler.supabase.com 之類。
    • k4 ［終端機］ 把兩條字串填進 .env，並把字串中的 [YOUR-PASSWORD] 換成實際密碼。 → 密碼若含特殊字元要 URL-encode：@→%40、#→%23、/→%2F。
    • k5 ［終端機］ 對新資料庫建表。 → 套用既有的兩個 migration。用 migrate deploy 而非 migrate dev：對全新空庫它不會反問問題。
    • k6 ［終端機］ 灌測試資料。 → 8 位病人、15 台平板，並產生全新的 apps/api/.device-keys.json。
    • k7 ［終端機］ 啟動並看後端 log。 → 應出現「已建立初始最高權限帳號」— 新資料庫沒有任何使用者，bootstrap 會重跑。第一次登入會再次強制變更密碼。
    • k8 ［終端機］ 跑兩支驗收腳本。 → 全部通過。
    • k9 ［終端機］ 看 verify:iteration2 第 2 步印出的「單次資料庫查詢往返約 X ms」。 → 拿它對照搬遷前的數字。若改善夠多，結尾的「環境相關觀察」警告會直接消失（端到端延遲降到 5 秒以內）。

    步驟 k5–k8

    npm run prisma:deploy -w @hd/api
npm run db:seed
npm run dev

# 另開一個終端機
npm run verify:acceptance
npm run verify:iteration2

    三個會咬人的地方¶

    現象 原因與處理
    病人端一直停在「裝置尚未佈建」 .device-keys.json 換過了。舊金鑰對新資料庫無效，之前記下的佈建網址全部作廢，要用新 seed 產生的值。
    所有帳號、病人、排班、稽核都不見了 預期行為。舊資料留在舊專案，不會跟過來。以測試環境來說這是好事 — 等於順便做了一次乾淨重置。
    登入又被要求變更密碼 預期行為。新資料庫的 SUPER_ADMIN 是重新建立的，passwordChangeRequired 回到 true。
    P1001 Can't reach database server 又踩到 Direct connection（db.<ref>.supabase.co，只有 IPv6）。這個坑跟區域無關，換到東京還是要用 Session pooler 字串。

    如果真的想保留舊資料¶

    不建議 — 測試庫累積的多半是驗收腳本殘渣。真的需要的話用 pg_dump / pg_restore，並跳過 k5、k6（dump 裡已含資料表與 _prisma_migrations，再跑 migrate 會衝突）。本機需有 PostgreSQL client 工具，且 pg_dump 版本不可低於 Supabase 的 server 版本。

    pg_dump "舊的 DIRECT_URL" --no-owner --no-privileges -Fc -f backup.dump
pg_restore -d "新的 DIRECT_URL" --no-owner --no-privileges backup.dump
