    血液透析中心平板專案：FDE數位化/數位優化評估報告¶

    專案背景：醫院採購15台Android平板，供病人透析時使用；FDE工程師可呼叫語言模型API、醫院資料庫（匿名化）、自訓模型，目標為最大程度數位化與數位優化護理人員工作。

    一、名詞定義¶

    詞彙 定義
    數位化 Digitization 把原本紙本/口頭/人工執行的流程，原封不動搬上數位介面，流程邏輯不變，只換載體
    數位優化 Digital Optimization 利用AI、資料、自動化能力，重新設計流程本身，使原本必須人力執行的判斷、蒐集、重複勞動被實質減輕或取代

    二、十大工作區塊分類總表（納入AI API + 醫院資料條件後）¶

    區塊 分類 說明
    一、班前準備 完全無法 機台/水質/消毒物理操作，AI與資料無用武之地
    二、病人到達與評估 部分協助 生命徵象人工測量無法取代；症狀評估可用AI+歷史資料做風險分層
    三、上針 完全無法 無菌侵入性技術
    四、透析中監測 部分協助 機台參數無法取得（需另做整合）；病人自覺症狀+歷史趨勢可做預警
    五、下機後照護 部分協助 拔針止血無法；離院衛教可個人化生成
    六、班後機台清潔 完全無法 純物理清潔工作
    七、護理記錄與行政 部分協助 記錄簽核責任在護理師；AI可預先草擬部分欄位
    八、週期性/例行工作 部分協助 抽血/Hb/EPO趨勢可由AI主動標註異常，減少人工覆盤
    九、突發狀況處理 部分協助（預警為主） 處置100%人力；AI可提前示警、輔助記錄與查詢
    十、感染管制 完全無法（且新增負擔） 15台平板共用是新的感染風險點，需另訂消毒SOP

    法規提醒：任務二、四、九一旦AI輸出被拿來做臨床判斷依據（風險分層、預警、劑量建議），在台灣可能觸及食藥署（TFDA）醫療器材軟體（SaMD）認證範疇，需與醫院法務/資訊室及早確認邊界。

    三、六項「部分協助」任務深度拆解¶

    以下針對任務二、四、五（面對病人，依透析前/中/後分期）與任務九、七、八（面對護理師，依工作中/後/例行分類）逐一拆解子任務，並標註「數位化」與「數位優化」各能提供什麼。

    （一）面對病人¶

    任務二：透析前¶

    子任務 數位化 數位優化
    透析間期症狀評估（水腫、喘、發燒、出血） 紙本問卷→平板結構化問卷 結合病人歷史體重增幅/血壓趨勢，AI自動標註「今日低血壓/水分超標風險偏高」，護理師帶著判斷接觸病人
    血管通路自覺症狀 平板文字/勾選回報 進階可加拍照上傳，AI視覺初篩紅腫/滲液跡象（僅作提示，非診斷），異常自動排優先接觸順序
    衛教與心理支持 制式衛教影片/文字上架平板，取代口頭重複講解 AI依病人透析史、衛教完成紀錄、慣用語言，動態生成個人化衛教內容與可互動問答
    治療計畫說明 顯示醫囑設定的乾體重、超過濾目標值 AI將專業數值轉換為病人易懂的白話說明，依健康識能程度調整用詞複雜度
    如廁/需求確認 平板勾選提醒清單 （此項本身邏輯簡單，優化空間有限）

    任務四：透析中¶

    子任務 數位化 數位優化
    病人自覺症狀回報（頭暈、噁心、抽筋、搔癢） 定時彈出式症狀問卷 AI結合病人過去多次透析中同一時段症狀發生模式，做「趨勢預測性預警」（例如：此病人過去3次都在第2小時後抽筋，建議提前介入），而非等症狀發生才回報
    情緒/焦慮陪伴 娛樂內容（影音、閱讀）打發4小時療程 AI陪伴式對話緩解焦慮，並可從互動語氣做情緒側寫，異常時通知護理師關注
    過程中衛教強化 顯示飲食/水分注意事項 依當次抽血/超過濾資料即時客製化提醒內容
    求助/緊急按鈕 取代傳統呼叫鈴，明確分類求助類型 按下時自動附帶病人近期自報症狀趨勢摘要，護理師到場前已掌握狀況背景，縮短反應與判斷時間
    非臨床需求（如廁、環境調整、口渴） 需求分類與派工，非臨床需求可導向護佐而非護理師 AI依需求急迫度與現場人力排序處理順序，降低對護理師的無效打斷

    任務五：透析後¶

    子任務 數位化 數位優化
    離院衛教（飲食水分限制、返診時機、傷口照護） 制式衛教文件顯示於平板 AI依當次超過濾量、抽血資料、飲食紀錄趨勢，生成個人化衛教重點，並支援多語言
    衛教理解確認 平板小測驗取代口頭確認 AI自適應測驗，找出病人真正不懂的知識點，並標記「此病人需要護理師加強口頭衛教」，讓護理師把時間留給真正需要的人，而非每人都重複衛教
    情緒/滿意度回饋 滿意度問卷數位化 情緒趨勢分析長期追蹤，及早捕捉透析疲勞/憂鬱徵兆（透析族群常見），異常自動建議轉介社工

    （二）面對護理師¶

    任務九：工作中（突發狀況處理）¶

    子任務 數位化 數位優化
    症狀初步判斷輔助 （單純數位化意義不大，此項本質是優化項） 依病人自報症狀模式+歷史資料，AI提供「可能情境參考」（如低血壓 vs 抽筋）供護理師參考，僅為決策輔助，非診斷（SaMD風險最高的一項）
    異常通報流程 取代喊叫/跑動通報，改為平板/系統即時警報 依嚴重度自動分級並路由給對應人力（護理師/醫師/急救團隊）
    事件當下記錄 危機當下先用快速點選式範本記錄關鍵時間點，取代事後憑記憶補寫 AI依系統時間戳與病人自報資料，事後自動草擬事件敘述初稿，護理師僅需審閱修改，大幅縮短補記錄時間
    藥品/劑量/SOP查詢 電子化SOP文件取代翻紙本 AI查詢介面（僅限於醫院既有SOP文件範圍內回答），危機當下快速定位處置步驟，節省翻找時間
    家屬溝通 完全無法協助 完全無法協助

    任務七：工作後（護理記錄與行政）¶

    子任務 數位化 數位優化
    護理記錄撰寫 紙本記錄單→電子表單 AI依病人平板自報資料（症狀、衛教完成度）自動預填草稿，護理師「審閱簽核」取代「從頭輸入」；抽血/醫囑相關內容仍須護理師專業確認，AI不能取代簽核責任
    EPO/用藥用量登記 紙本登記簿→電子登記 若串接藥局/給藥系統，可自動帶入用量資料，減少手動輸入誤差
    衛教完成紀錄 平板自動記錄病人觀看/測驗結果作為衛教完成證明 自動標記需要加強衛教的病人清單，供下次排班參考
    病人需求評估紀錄 平板自報資料自動匯入記錄系統 AI生成摘要段落供護理師確認而非重寫

    任務八：例行工作¶

    子任務 數位化 數位優化
    每月抽血追蹤（BUN、Cr、Albumin） 紙本圖表→數位儀表板 AI跨時間趨勢分析，主動標註異常軌跡病人，生成「優先追蹤清單」取代逐一人工覆盤全部病人
    每週Hb/EPO紀錄 數位化登記取代手寫 AI依既定protocol提供劑量調整參考建議（需臨床確認，屬決策輔助，SaMD風險項）
    透析適足性評估（Kt/V、URR） 自動計算取代人工公式計算 趨勢追蹤並預測適足性風險，提前介入而非事後發現
    心理社會轉介評估 定期情緒/滿意度調查數位化彙整 AI匯總趨勢，主動標記心理社會風險上升病人，建議轉介社工
    員工健康管理（疫苗、X光） 與病人平板無關，此系統範疇外 此系統範疇外

    四、開發模式選擇分析：App／網頁／網頁式App（PWA）／其他¶

    專案限制條件（決定選型的關鍵前提）¶

    • 15台固定機構用途的Android平板，病人使用，非個人裝置 → 需要能「鎖定」防止亂點亂滑出應用範圍
    • 單一透析療程4小時，介面互動頻率低但需長時間穩定運作
    • 需串接醫院資料庫（PHI匿名化）與AI API → AI呼叫與資料存取必須經後端閘道，不可讓平板直接持有API金鑰或直接傳送病人可識別資訊給外部LLM服務
    • FDE多半是精簡團隊甚至單人作戰，需求會隨臨床回饋快速迭代
    • 未來可能擴展到護理站端的Dashboard，前後端架構最好能共用

    比較表¶

    模式 優點 缺點
    原生 App（Kotlin/Java） 完整硬體存取（相機、感測器）；搭配Android Enterprise可做最強力的Kiosk鎖定；效能與離線快取最佳；長期機構部署穩定性高 開發成本高、週期長；需要Android專業技能；每次更新需重新打包測試15台裝置；對單人FDE快速迭代不友善
    純網頁（Web） 開發速度最快；後端更新即生效，不需重新安裝；未來護理站Dashboard可共用同一套程式碼 鎖定裝置較弱（需額外用Kiosk瀏覽器App如Fully Kiosk Browser輔助）；持續依賴網路連線；離線能力弱
    網頁式App（PWA） 開發速度接近純網頁，但可安裝到主畫面、具備Service Worker離線快取（衛教影片/文字可離線）、支援推播通知；搭配MDM/Kiosk模式仍可鎖定；後端與未來Web Dashboard高度共用 部分Android WebView限制；背景同步/通知穩定性不如原生；AI查詢與即時症狀同步仍需網路，離線能力僅止於靜態內容
    混合式（原生殼包WebView / Flutter跨平台） 兼具原生打包／上架與鎖定優勢，內部邏輯仍用Web技術開發維護；比純原生開發快 仍需一定原生開發基礎；除錯層次比純Web多一層（WebView橋接問題）

    建議¶

    以FDE的角色（需要快速迭代驗證需求、資源有限、且未來很可能要延伸出護理站端系統）來看，建議以「PWA」為主要開發模式，搭配MDM（如Android Enterprise/Samsung Knox）將裝置鎖定為單一應用的Kiosk模式：

    1. 開發與迭代速度最符合FDE需要快速根據臨床回饋調整的工作型態
    2. 前後端架構可與未來護理站Dashboard共用同一套API層與程式碼基礎
    3. 更新只需部署伺服器端，不需逐台重新安裝15台裝置
    4. 裝置鎖定問題不一定要靠原生App解決，MDM本身就能把平板鎖定在單一PWA網址，防止病人亂點跳出應用
    5. 主要代價是離線能力有限——衛教靜態內容可預先快取，但AI風險預警、症狀同步分析等核心優化功能仍仰賴即時網路連線，這點需要向醫院資訊室確認病房/透析區網路穩定性是否足夠

    若醫院網路環境不穩定或未來要做更深度的機台資料整合（涉及硬體/藍牙/序列埠通訊等），屆時可考慮升級為Flutter等跨平台框架包裝的混合式App，兩者可視為分階段演進路徑，而非互斥選擇。

    資料治理提醒¶

    即使醫院已同意匿名化資料可用於訓練模型，實務上仍建議： - AI API呼叫一律經由醫院自建後端閘道轉發，避免病人可識別資訊直接流向外部LLM服務商 - 若涉及風險分層、預警、劑量建議等會影響臨床判斷的輸出，及早與醫院法務/資訊室確認是否落入SaMD認證範疇，避免功能上線後才發現需要重新走驗證流程
