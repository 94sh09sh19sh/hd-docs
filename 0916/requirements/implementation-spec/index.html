    2.1 Prisma 改用 SQLite 的注意事項¶

    • provider 改為 sqlite，移除 directUrl。 migration 檔與 PostgreSQL 不相容，migrations/ 整組重建（既有資料為合成資料，直接捨棄，見《資料庫使用規範》第 15 條）。
    • 連線行為必須實測確認。 SQLite 只允許一個寫入者，Prisma 的連線設定（如連線字串上的 connection_limit）要驗證實際行為，不要照抄 PostgreSQL 的設定。
    • PRAGMA 設定要在連線建立時套用：journal_mode=WAL、foreign_keys=ON、busy_timeout>=5000、正式環境 synchronous=FULL。這四項是《資料庫使用規範》第 7 條的必開項，缺一個都會在多人同時操作時出問題。
    • 不得用 Float 承載任何臨床數值（劑量、體重、超過濾量）。改用整數最小單位或 String，見《資料庫使用規範》6.2。
    • 部分批次操作在 SQLite provider 上的支援與 PostgreSQL 不同，使用前先確認當前 Prisma 版本的實際支援，不要假設兩邊一樣。
    • 既有的六條 schema 約束（不用 enum、不用 JSON 承載關聯資料、不用資料庫專屬預設值、snake_case、稽核欄位不省略、級聯路徑只留一條）全部保留。

    3. 關鍵機制設計¶

    3.1 護理端身分驗證（沿用，補上新角色）¶

    機制與 v1.0 相同：.env 提供初始最高權限帳密建立第一個 SUPER_ADMIN；護理師以工作 ID 註冊、狀態 PENDING；具權限者核准後轉 ACTIVE；登入後由後端核發可設定期限並可主動作廢的 token。

    0910 新增三個角色，對應 SRS 3.1：

    角色識別字串 對應 SRS 權限重點
    NURSE_LEAD 護理長／單位主管 護理師排班與調動、L2／L3 績效、獎勵指標設定
    HOSPITAL_VIEWER 醫院管理層 只能讀 L1 聚合儀表板，不得存取任何病人層級資料
    AUDITOR 稽核／法規角色 只能讀稽核軌跡、AI 呼叫紀錄、規則執行紀錄；無臨床操作權

    Agent 行為規則：

    • 角色仍以字串欄位承載，合法值定義在 @hd/shared，不使用 Prisma enum。
    • HOSPITAL_VIEWER 與 AUDITOR 是唯讀角色，所有寫入端點都必須明確擋掉它們，不得只靠前端不顯示按鈕。
    • 每一次角色指派與權限變更都要寫入稽核軌跡。

├── MockLlmProvider      ← 預設。回傳固定範例，讓所有 AI 功能可先開發與測試
├── LabApiProvider       ← 過渡期。實驗室 API（院外），僅得送合成資料
└── OnPremiseProvider    ← 正式。院內 DGX Spark 上的推論端點（不由本專案部署，見 DEP-16）

    介面至少涵蓋：generate(prompt, options)、健康檢查、可用模型清單。

    硬性規則：

    1. 任何呼叫語言模型之處，一律透過 LlmProviderPort。 不得在業務邏輯中出現任何一家廠商的 SDK、端點或模型名稱。切換 provider 只能是設定變更。
    2. 模型識別字串、端點、金鑰全部由設定提供，.env.example 保留空值。院內推論服務的端點與可用模型未確認（Q-07）、實驗室 API 未取得（Q-08），因此本階段不在程式或文件中寫死任何模型名稱。
    3. LabApiProvider 必須帶「合成資料檢查」：當目前 provider 為 LabApiProvider 時，帶有真實病人資料標記的請求要被擋下並記錄（FR-S06）。這是程式強制，不是靠人的自律。
    4. 去識別化在寫入資料庫之前完成，不是查詢時才遮蔽（《資料庫使用規範》第 14 條）。
    5. AI 呼叫一律寫入 ai_invocations：provider、模型、參數、耗時、是否觸發去識別化、成功或失敗。提示與輸出留存 12 個月，原始（未去識別化）提示不存。
    6. 非即時功能走背景佇列。 衛教生成、記錄草擬這類「可以等」的工作不得阻擋 HTTP 請求，也不得在資料庫交易中呼叫模型（會佔住 SQLite 唯一的寫入位置）。

    對應 FR-S05。院方尚未確定給 API 還是 Excel，因此先定介面。

    ClinicalDataSourcePort（抽象介面）
├── ManualEntryAdapter   ← 先做這個。護理師在管理介面手動輸入少數欄位
├── FileImportAdapter    ← 迭代 6 完成。Excel／CSV 上傳解析，欄位名稱走可設定的對應表
└── HospitalApiAdapter   ← 院方給 API 後補上，介面不變

    三種來源一律收斂成同一組內部資料表，輪播與儀表板只讀內部資料表，不認來源。

    硬性規則：

    • 全有或全無。 一批匯入中任何一筆解析失敗或驗證不過，整批不寫入。臨床數值只對一半比完全沒有更危險。
    • 來源可追溯：每筆資料記錄批次編號、來源（檔名或端點）、匯入時間、匯入者。
    • 欄位對應可設定，不寫死在程式裡（Excel 欄位名稱會被人改動）。
    • 每筆數值都要有「資料時間」，呈現時必須一併顯示，避免病人看到三週前的體重以為是今天的。
    • 重複匯入要被偵測並擋下，或明確標記覆蓋並保留前一版。

    3.6 規則引擎（新增）¶

    對應 FR-R01。三項高風險功能的計算由規則引擎執行，不經語言模型。

    為什麼自建而不用第三方規則引擎套件：需求是「能逐條印出來給醫師看、能版本化、能指出這次套用了哪一條的哪一個門檻」。第三方套件的表達能力遠超需求，卻讓可解釋性變差。本專案的規則形態很窄——都是「某個數值或次數超過門檻」，自建一個小型評估器即可。

    資料模型：

    資料表 用途
    rule_definitions 規則的身分：識別字串、名稱、適用需求（FR-P03／P05／N06）、狀態
    rule_versions 每一版的門檻值與條件、生效期間、臨床端書面依據的出處、建立者
    rule_evaluations 每一次執行：對哪位病人、哪次療程、套用哪個規則版本、輸入了哪幾筆歷史資料、結果
    rule_evaluation_reviews 誰檢視、是否採納、未採納原因（FR-R06、對應 FR-N13）

    硬性規則：

    1. 規則版本一經使用即不可修改，要改就新增版本。rule_evaluations 永遠指向當時的版本。
    2. 未附書面依據出處的規則版本不得標為生效（FR-R02）。無依據時規則只能在「合成資料模式」下執行。
    3. 每一則輸出必須可展開完整依據：引用的歷史資料、規則條目、門檻值、版本編號（FR-R03）。
    4. 輸出措辭為事實陳述，不是結論陳述。 寫「符合 HYPO-01 規則：近三次療程第 2 小時後曾回報頭暈」，不寫「病人有低血壓風險」（FR-R04）。文案不得由模型生成，一律由規則版本內的範本組出。
    5. 不自動觸發任何動作（FR-R05）：不改醫囑、不改處理優先順序、不自動通知醫師。
    6. 三項功能各有獨立開關（FR-R07），走 3.7 的功能開關中心。

    4. 迭代規劃（迭代 3～8）¶

    4.0 為什麼是這個順序¶

    排序不是照需求編號，也不是照「哪個看起來最重要」，而是照四條原則。順序若違反其中任一條，代價都是重工或永久性的損失：

    # 原則 具體後果
    1 會動到所有既有程式的事情先做 SQLite 遷移碰到每一個資料存取點。先做新功能再遷移，等於把新功能也重工一遍
    2 有時效性的先做 成效基準（FR-M07）只能在系統正式啟用前量測。紙本流程一消失，「以前要花多久」永遠補不回來
    3 不需要等別人回答的先做 AI 生成功能用 MockLlmProvider 今天就能做完；規則引擎要等臨床端給門檻值。把等待中的項次排前面，只會讓進度停在原地
    4 產生資料的先做，吃資料的後做 管理儀表板與獎勵制度（新增任務一）需要求助處理紀錄、班表、成效基準累積過一段時間才有東西可看

    原則 4 需要特別說明，因為它看起來像是把新增任務一的優先權往後放。 實際相反：新增任務一的目的是「向長官與外部展現成效」，而空的儀表板比沒有儀表板更傷。先把產生資料的三件事（求助處理結果、班表、成效基準）做完並實際跑一段時間，儀表板上線時才有真實數字。因此新增任務一被拆成兩半——產生資料的部分排在迭代 5（很前面），呈現與計分的部分排在迭代 8。

    另一個刻意的決定：三項高風險功能（本週任務二）排在迭代 7，而非最前面。理由是它同時卡在兩個外部答覆上（法務的分類確認、臨床端的門檻值），而且規則引擎本身不長。把它排在前面，最可能的結果是引擎寫好了、門檻值還沒到，然後空等。排在迭代 7，前面幾個迭代的時間正好是等答覆的時間。若門檻值與書面確認提早到齊，這個迭代可以隨時往前插隊——它與迭代 4～6 沒有相依。

    迭代 6 完成後，唯一仍在倒數的是 Q-01。 其餘所有外部依賴都只是「答覆回來換個設定」，它是唯一「答覆不來就永遠拿不到」的一項——一旦紙本流程消失，「以前要花多久」就再也量不到了。

    5. 每次迭代開始前，Agent 應自我檢查¶

    在動工前確認：

    • 本次要新增的資料表／欄位是否已對照 SRS 需求與稽核軌跡欄位需求
    • 是否有任何前端程式碼企圖直接碰資料庫檔案（禁止，《資料庫使用規範》第 2 條）
    • 存取控制是否寫在後端應用層（禁止依賴檔案權限或前端隱藏，第 4 條）
    • 是否在業務邏輯中直接寫 SQL 或 SQLite 方言（改走 Repository／ORM 層，第 5 條）
    • 新增的臨床數值欄位是否誤用浮點數（一律整數最小單位或字串，6.2）
    • 是否新增了第二個會寫入資料庫的常駐行程（不允許，第 7 條）
    • 是否有任何相依指向院外網域（FR-S07，跑檢查腳本）
    • 呼叫語言模型是否一律透過 LlmProviderPort（3.4）
    • 呼叫 MDM 是否一律透過 MdmProviderPort（3.3）
    • 取用院方臨床數值是否一律透過 ClinicalDataSourcePort（3.5）
    • 本次功能是否觸及 1.4 的有條件納入項；若是，開關是否預設關閉
    • 本次功能是否會產生 L3 個人層級績效資料；若是，是否已擋在 PERF_INDIVIDUAL_L3 之後
    • 本次的輸出是否可能離開院內；若是，是否走對外報表模組（FR-X01）
    • 測試資料是否為虛構合成資料（禁止任何接近真實病人的資訊）
    • 若本次功能疑似要「依資料做出會影響臨床判斷的建議或分級」而未列於 SRS 5.6，先停下來問使用者

    6. 尚待確認的開放問題¶

    已移出本文件。 全部待確認事項集中在《尚待確認事項清冊》。那份文件有急迫度分級（A 過期作廢／B 阻塞啟用／C 阻塞實作／D 可暫代）、不確認的後果、具體要問的問句、暫代做法，以及按要問的人分組的提問清單。

    各迭代的外部依賴已寫在第 4 章各節的「外部依賴」段落，並在 4.7 節有一覽表。要知道現在卡在誰身上，看 4.7；要知道該怎麼問，看清冊。

    開工前只要記住一件事：清冊裡只有 Q-01（成效基準的量測人力與時程）有時效性，系統一上線就永遠拿不到，其餘 26 項晚回覆都不會造成永久損失。

    7. 已知風險¶

    實作過程中最可能出事的五件事，以及對應的做法：

    風險 為什麼會發生 對應
    遷移改壞既有行為 SQLite 遷移碰到每一個資料存取點，型別對照與外鍵行為都與 PostgreSQL 不同 迭代 3 驗收第 2 條：既有兩支驗收腳本必須全綠，不得修改腳本來配合
    新增功能排擠主線 輪播與績效蒐集都是「額外」的，容易在不知不覺中拖慢求助反應或增加護理師的操作步驟 FR-P13 列 P0；迭代 6 驗收第 2 條明確要求求助反應時間無差異。0912 實測：輪播輪詢與求助同時發生時，求助往返時間與非輪播狀態無實質差異（驗收腳本步驟 11 每次執行都會重測）
    高風險功能悄悄對真實病人開啟 開發時為了看畫面而繞過閘門，之後忘了關回去 閘門一律以功能開關實作、預設關閉、切換寫稽核；不接受「寫在文件裡提醒自己」
    績效資料變成考核工具 資料一旦存在，用途就會擴散 L3 預設關閉、查詢逐次留痕、禁止排名欄位與交叉評分（3.10）
    交付當天才發現映像檔跑不起來 開發筆電是 x86-64，正式主機是 ARM64；主機還是共用的，權限、連接埠、掛載路徑都不在開發端手上 容器設定提前到迭代 6 建立並在 ARM64 上實際啟動過（DEP-05）；權限與傳入管道另立 Q-27 先問清楚
