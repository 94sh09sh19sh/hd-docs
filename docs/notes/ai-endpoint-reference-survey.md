# 同主機 RAG 系統參考調查：AI 推論端點怎麼接

版本：v0.1　文件狀態：草案（2026-11-23 開立）　適用讀者：FDE 工程團隊、使用者本人

---

## 摘要

- 1123 讀了院內同一台主機上另一套系統（腎臟科臨床指引問答，RAG）的程式，只看它怎麼接 AI 推論端點；只讀不改
- 它直接連 **Ollama**：位址一個環境變數（`OLLAMA_BASE_URL`），沒有金鑰；主回答 `gpt-oss:120b`、輕量工作 `gpt-oss:20b`、看圖 `qwen3-vl:30b`，都經 LangChain 呼叫（第 3 節）
- 它踩過的坑跟本系統會遇到的一樣：**同一個 Ollama 一次只讓一件大工作跑**、看圖冷啟動要 60 秒以上所以逾時給 180 秒、串流每 5 秒送心跳（第 3.3、3.4 節）
- 用在本專案：**程式一行都不用改**，AI 閘道本來就照這種接法設計；要做的只有院內那一份 `config.yaml` 填上同一個端點與模型（第 5 節）
- 但現在只有那套系統的公開程式碼，**院內實際連到哪裡、能不能共用、裝了哪些模型都還不知道**，要先問（第 6 節）；問到之前 Q-07 照舊不結案
- 語音：它在主機 CPU 上跑 `whisper-small` 轉文字，證明這台主機 CPU 跑得動小型辨識模型，但不懂台語，取代不了本系統選的 Breeze（第 5.5 節）
- 參考程式的網址、作者與院內實際位址不寫進本文件，在私人 repo 的 `deploy/records/1123-ai-ref-system/`

## 0. 本文件的定位

本文件不是需求文件，是一份**調查紀錄**。2026-11-23 使用者指示：院內同一台主機上部署了另一套系統，讀它怎麼接 AI 推論端點，寫成文件。

閱讀時請記住三件事：

- **第 2～4 節是從別人的公開程式「讀出來的」，不是院方或對方團隊的答覆。** 公開 repo 只有兩個 commit，最後一個是「去敏感化」，院內跑的版本與 `.env` 可能不一樣
- 本系統的 AI 規則以《[部署規範](../requirements/deployment-spec.md)》第 5 章（DEP-16、DEP-17、DEP-40、DEP-41）為準；本文件只寫「照那套規則，要怎麼接上同一個端點」
- 與需求文件衝突時，以需求文件為準

## 2. 那套系統的架構

```
瀏覽器 ── Next.js（:3000）── /api/* 轉給 ──▶ FastAPI（:8000）
                                              │
              ┌───────────────────────────────┼──────────────────────────┐
              ▼                               ▼                          ▼
      Ollama（OLLAMA_BASE_URL）        向量模型 e5-large-v2         Whisper 轉文字／Piper 朗讀
      gpt-oss:120b、20b、qwen3-vl:30b  （本機 CPU）                 （本機 CPU）
```

- 推論只有 Ollama 一個端點；向量模型、語音轉文字、朗讀都在後端自己的行程裡跑
- 後端沒有登入，作者在 `SECURITY.md` 寫「Ollama 與模型端點只放私有網路、不對外」「真實病人資料要放在認證或 VPN 後面」

## 3. 它怎麼呼叫推論端點

### 3.1 設定

| 環境變數 | 預設值 | 用途 |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://127.0.0.1:11434` | Ollama 的位址；README 寫「Ollama 在別台機器就改這個」 |
| `LLM_MODEL` | `gpt-oss:120b` | 主回答 |
| `LLM_MODEL_FLASH` | `gpt-oss:20b` | 追問、摘要等輕量工作 |
| `VLM_MODEL` | `qwen3-vl:30b` | 判斷指引裡的圖跟回答有沒有關 |
| `EMBEDDING_MODEL` | `intfloat/e5-large-v2` | 向量模型，HuggingFace 下載、本機 CPU 跑 |

- 沒有金鑰、沒有認證欄位：Ollama 本身不驗
- `HF_HUB_OFFLINE=1` 寫死在程式開頭：模型先下載好，執行時不連外

### 3.2 四種呼叫

| 用途 | 模型 | LangChain 物件 | 走的介面 | 參數 |
|---|---|---|---|---|
| 中文問題先翻成英文 | 主模型 | `langchain_classic.llms.Ollama` | Ollama 原生（文字補完） | `temperature=0` |
| 主回答（串流） | 主模型 | 同上，`.stream()` | 同上 | `temperature=0` |
| 追問、口語摘要 | 輕量模型 | 同上 | 同上 | `temperature=0` |
| 圖跟回答有沒有關 | 看圖模型 | `ChatOllama`，圖片轉 base64 放進訊息 | Ollama 原生（對話） | `temperature=0`，要求只回 JSON |

- 每次都是同步呼叫，後端用 `run_in_executor` 丟到執行緒裡跑，不擋住非同步迴圈
- 沒有設定逾時、沒有重試；看圖那一段解析 JSON 失敗就當「不相關」
- 看圖那一段用改環境變數 `OLLAMA_HOST` 的方式指定位址，不是傳 `base_url`——改的是整個行程的環境，不好的寫法

### 3.3 併發與逾時：它踩過的坑

程式註解寫的是實際遇過的問題：

| 問題 | 它的做法 |
|---|---|
| LLM 與看圖模型同時跑會「撞車」（GPU 記憶體不夠，兩個模型輪流換入） | 摘要跑完才開始看圖；看圖加一把全域鎖，同一時間只有一張圖在推論 |
| 看圖模型冷啟動要 60 秒以上 | 每張圖逾時 180 秒，逾時就跳過那張，不讓整個回答失敗 |
| 看圖的函式內部自己開了 3 條執行緒並行 | 外面再包一個只有 1 條執行緒的執行器，強迫一張一張來 |
| 一次回答要看很多張圖 | 最多只看前 3 張 |

結論：**它的 Ollama 一次扛不住兩個大模型同時推論**。本系統若共用同一個端點，就是第三個搶的人（第 5.3 節）。

### 3.4 串流給前端

- `/api/query/stream` 回 SSE：先送翻譯、再一段一段送回答文字，最後送摘要、朗讀音檔、相關的圖與一包完整結果
- 每 5 秒沒有資料就送一行註解當心跳，回應標頭加 `X-Accel-Buffering: no`，避免中間的代理伺服器把連線切掉或攢著不送
- 背景工作出錯只寫紀錄、改送「無法生成摘要」之類的替代內容，不讓串流斷掉

### 3.5 語音

| 方向 | 做法 |
|---|---|
| 轉文字 | 前端 `MediaRecorder` 錄完整段（瀏覽器預設格式），整包上傳；後端 `faster-whisper` 的 `whisper-small`，CPU、int8、`language="zh"`、beam 5。**每次請求都重新載入模型** |
| 朗讀 | 摘要交給 Piper（`zh_CN-huayan-medium`，中國大陸口音的模型）產生 WAV，base64 放進串流 |

### 3.6 它沒有的東西

- 健康檢查、模型在不在的檢查：端點不通要等到使用者提問才知道
- 認證、存取控管、對外連線的限制
- 推論的紀錄：只記問答內容與耗時，沒記用了哪個模型、哪些參數

## 4. 與本專案 AI 閘道的對照

| 比較 | 那套系統 | 本專案（《部署規範》第 5 章、`services/ai-gateway/`） |
|---|---|---|
| 誰連推論端點 | 後端自己連 | 只有 AI 閘道連（DEP-41），後端連閘道 |
| 位址與模型放哪 | `.env` | 閘道的 `config.yaml`，改檔即生效 |
| 呼叫方式 | LangChain，Ollama 原生 | LangChain，`provider: ollama`（`ChatOllama`）或 `openai`（OpenAI 相容介面）擇一 |
| 逾時 | 只有看圖 180 秒 | 閘道 `timeout_seconds`（範本 120）＋後端 `LLM_TIMEOUT_SECONDS`（範本 150），健康檢查另外 3 與 5 秒 |
| 重試 | 沒有 | 閘道不重試，由後端背景佇列決定 |
| 端點不通 | 使用者提問才發現 | `/health` 與 `/v1/models` 不通過，AI 總開關開不起來；主線功能不受影響（DEP-24） |
| 併發 | 一把鎖、一條執行緒 | 本系統的 AI 功能一律走背景佇列，沒有使用者在畫面前等串流 |
| 紀錄 | 問答內容寫進資料庫 | 閘道紀錄檔只寫模型、耗時、成敗，不寫提示與輸出；後端 `ai_invocations` 記實際模型與參數 |
| 往院外送 | 沒有防線 | 正式設定下 `LLM_PROVIDER=lab` 拒絕啟動（DEP-40）；`check:egress` 只准院內位址（`.internal` 結尾的主機名稱也算院內） |

兩邊用的是同一套 LangChain 與 Ollama，差別在本專案多了閘道這一層，所以換端點只改設定、不改程式。

## 5. 用在本專案

### 5.1 結論

1. **不改程式**。那套系統用的 Ollama 原生介面就是本專案 `provider: ollama` 那一種，閘道已經支援
2. 院內那一份 `config.yaml`（主機設定目錄底下 `ai-gateway/config.yaml`）填三個值：`provider: ollama`、`base_url`、`model`。範本 `services/ai-gateway/config.hospital.example.yaml` 現在預設 `provider: openai` 且位址、模型留空，**等第 6 節問到答案後再改範本**
3. 後端 `.env` 改 `LLM_PROVIDER=onprem`，`compose` 加 `--profile ai` 啟動閘道
4. 首波部署 AI 預設關閉（DEP-29）照舊；接上端點只是讓總開關開得起來，開不開另外決定

### 5.2 `base_url` 要怎麼填：要看 Ollama 在哪

| 情況 | 閘道的 `base_url` | 要注意 |
|---|---|---|
| Ollama 在**同一台** Windows 主機上 | `http://host.docker.internal:11434` | 閘道在容器裡，`127.0.0.1` 指的是容器自己，不是主機；Ollama 只聽主機本機介面時，Docker Desktop 轉得過去與否**要實測** |
| Ollama 在**院內另一台**（例如 DGX Spark） | `http://<那台的院內位址>:11434` | 那台的 Ollama 要聽院內網路（不是只聽本機）；院內位址只寫進主機設定目錄與私人紀錄 |
| 院內實際設定跟公開程式不一樣 | 照實際的 | 第 6 節第 1 題 |

`check:egress` 只掃 repo 裡的範本；填好的那一份在主機設定目錄，不進 repo（DEP-13）。

### 5.3 共用同一個端點的風險與對策

| 風險 | 對策 |
|---|---|
| 搶 GPU：它的 Ollama 本來就一次只扛一件大工作（第 3.3 節），本系統再呼叫就是第三個 | 本系統的 AI 呼叫本來就只在背景佇列、量很少（衛教草稿、SOP 回答）；先問對方能不能共用、有沒有時段限制（第 6 節第 2 題） |
| 換模型的冷啟動：本系統若指定不同的模型，Ollama 會把對方的模型換出去，雙方都要等載入 | **優先用對方已經常駐的模型**（例如 `gpt-oss:20b`），不另外要模型；要換再跟對方協調 |
| 冷啟動超過逾時 | 它的經驗是看圖模型 60 秒以上、主模型 120B 可能更久。第一次接上先照範本（閘道 120、後端 150）實測，不夠再兩個一起加大（後端要比閘道大） |
| gpt-oss 是思考型模型 | 閘道已會拿掉 `<think>` 區塊；`reasoning` 設定對 gpt-oss 有沒有作用**要實測**。繁體中文用語由迭代 17.3 的檢查擋 |
| 對方改設定、換模型、停機 | 本系統的健康檢查會不通過、AI 總開關自動開不起來，主線功能不受影響；但要有人通知，第 6 節第 3 題 |
| 病人資料經過別人的服務 | Ollama 不留存請求內容，但端點的主機與紀錄設定由對方管；送出前的去識別化照舊（FR-S06），並確認那台在院內（DEP-40 的目的） |

### 5.4 可以借的作法、不借的作法

| 借 | 不借 |
|---|---|
| 同一時間只讓一件推論跑（本系統背景佇列已是一次一件，接上共用端點後**不要調高併發**） | 每次請求重新載入語音模型 |
| 冷啟動的逾時給足、逾時就跳過那一件，不拖垮整體 | 改 `OLLAMA_HOST` 環境變數指定位址 |
| SSE 每 5 秒心跳、`X-Accel-Buffering: no`（本系統的 SSE 已有心跳，日後若加串流回答照用） | 後端直接連端點、位址放 `.env`（違反 DEP-41） |
| 模型先下載好、執行時離線（`HF_HUB_OFFLINE`），語音閘道日後照做 | 沒有健康檢查、沒有推論紀錄 |

### 5.5 對語音功能的意義

- **Ollama 不提供語音辨識**。本系統的語音說明（《[緊急求助的語音說明](emergency-voice-help.md)》第 5 節）要的辨識端點不能靠這個 Ollama，仍是另一個服務
- 那套系統在主機 CPU 上跑 `whisper-small` 是**可行性的旁證**：同一台主機的 CPU 跑得動小型辨識模型。但它只認華語，本系統要台語與台華混用，選的是 Breeze-ASR（《[之一：開源專案與模型的選型](emergency-voice-help-models.md)》第 2、6 節），模型大得多，速度仍要實測
- 同一台主機的 CPU 已有那套系統的向量模型與辨識在跑，本系統若也在 CPU 上跑語音閘道，三方會搶 CPU——主機共用的問題（Q-27）多一個實例
- 錄音的作法它是 `MediaRecorder` 錄完整段上傳；本系統要錄音期間分段送、斷線不遺失，已選 AudioWorklet 轉 PCM，不照它的
