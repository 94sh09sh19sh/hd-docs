# 護理師回饋：怎麼提高意願、怎麼拿到手

版本：v0.2　文件狀態：草案（2026-11-23 開立，1125 照醫師答覆改）　適用讀者：FDE 工程團隊、使用者本人、醫師與護理長（第 3、5、8 節）

---

## 摘要

- 1123 使用者指示：要收到護理師對本系統的任何評價與修正建議；先想怎麼讓護理師願意說、再想怎麼拿到手（第 0 節）
- 護理師不說的主因不是不滿意，是**沒時間、覺得說了沒用、怕得罪人、想到的時候不在電腦前**（第 2 節）
- 最有效的一招是**讓他們看到說了有改**：每次換版在護理站貼一張「你們說、我們改」，週報也寫；其次是把成本壓到 30 秒、可以不留名、有一位固定聯絡人（第 3 節）
- **1125 醫師答第 8 節四題**：護理師上班不能用手機，QR code 不用；醫師建議**系統裡放表單連結**，排成迭代 36（第 6.1 節），1125 做完、等院內換版；聯絡人先由醫師當；要用在論文；進院跟班看當天情況
- 管道組合（1125 起）：**主管道是護理端導覽列的「意見」連到外部短表單**（在護理站電腦上填，回應直接進使用者的試算表）；**紙卡箱併行**到連結上線滿一個月（第 4.4 節）；試用第 2、4 週各一次短問卷；進院時能跟就跟；系統本身的使用紀錄看「做了什麼」（第 4、5 節）
- 系統內的完整意見表單（三個大按鈕、資料留在院內主機）照舊是候選，**使用者開口才排**（第 6.2 節）
- 要用在論文：問卷、訪談、跟班紀錄要先送倫理審查，核准前收到的只用來改系統（第 8.1 節）
- 拿到之後：一張追蹤表、每一則都要回覆「改／不改＋原因」；原話進私人紀錄、公開文件只寫分類後的結論（第 7 節）
- 第 8 節四題 1125 答完；剩三題（第 8.2 節）：護理站電腦開不開得了外部表單、送審要不要與錄音同意書併成同一次修正、紙卡誰收

## 0. 本文件的定位

- 不是需求文件，是做法規劃；與需求文件衝突以需求文件為準
- 只寫文件，不改程式；第 6 節的系統內功能要做時另排迭代
- **1123 寫進需求**：系統內意見入口成為 SRS FR-N23（候選、預設關、不給迭代編號）；第 8 節四題進清冊 Q-42
- 時間點：1125 週報的首要目標仍是「首波試用真的開始」（[1125 週報](../weekly/2026-11-25.md)），護理師還沒在臨床用過本系統；**回饋管道要在試用第一天就在**，第一週的意見最多、也最容易流失

## 1. 前提與限制

| 事實 | 對回饋的意思 |
|---|---|
| 護理師忙，而且是被打斷的忙（《[介面設計基準](uiux-design-baseline.md)》第 3.1 節） | 每多一步都是從照顧病人的時間扣；回饋要 30 秒內做完 |
| **護理師上班不能用手機**（1125 醫師） | 不能靠 QR code 讓他們用自己的手機填；要在護理站電腦上就能填 |
| 首波只有護理站一兩台電腦、首波一床（`A`～`D` 開頭） | 用的人少、用的時間短，每一則意見都珍貴；也代表樣本少，不能只看統計 |
| 開發端不常駐院內，平常靠每週三與醫師開會 | 轉述會失真、會延遲；要有一條護理師**直接到開發端**的路 |
| 指定一位護理師當聯絡人會加重那一位的工作、降低參與意願（1125 醫師） | 聯絡人先由醫師當；要頻繁聯絡時才請護理長指定一位護理師 |
| 院內主機只在院內；資料離開主機要院方核准（《[資料庫使用規範](../requirements/database-policy.md)》第 12 章） | 系統內收的回饋開發端拿不到即時的；院外的管道不能收病人資料 |
| 文件站是公開的 | 回饋原話可能有病人名、床號、同事名，不能直接貼進 `docs/` |

## 2. 護理師為什麼不回饋

| 阻力 | 對策（第 3 節） |
|---|---|
| 沒時間；想到時正在處理病人 | 成本壓到 30 秒；隨時可以事後補 |
| 覺得說了也沒用 | 讓每一則都看得到結果 |
| 怕被當成抱怨、怕主管或醫師看到是誰說的 | 可以不留名；不經過直屬主管轉交 |
| 不知道要說什麼；面對空白欄位寫不出來 | 給選項，不問「有什麼建議」 |
| 覺得自己說不清楚、不懂系統 | 只說「哪一頁、卡在哪」就夠，不必說怎麼改 |
| 新鮮期過了就不說 | 固定時點主動問；有一位聯絡人記得問 |
| 以為是在評量自己 | 明講：評的是系統，不是人；沒有對錯 |

## 3. 提高意願的做法（照效果排）

1. **看得到結果**：每次換版，在護理站電腦旁貼一張 A4「你們說、我們改」，一則一行：「〇〇頁按鈕太小 → 已放大（11/30 起）」；不改的也寫一句原因。週報同步寫一節。這是最有效的一招，護理師看到第一張之後才會說第二次
2. **成本壓到 30 秒**：表單第一題三選一（卡住了／有錯／希望有），第二題「哪一頁」點選，第三題一句話可空白；不必登入、不必截圖
3. **可以不留名**：表單的名字欄選填；紙卡不寫名字
4. **一位固定聯絡人**：~~請護理長指定一位種子護理師，每週二問一次大家~~ **1125 醫師答：聯絡人先由醫師當**，不另外加重某一位護理師的工作；之後真的要頻繁聯絡，再請護理長指定一位護理師
5. **問在空檔**：定期問卷挑交班後或班末，不在上機、下機時段；系統裡不跳任何回饋視窗（違反設計基準 N-1、N-5）
6. **給題目**：試用第一週把「我們最想知道的 3 件事」印在卡上（例如「求助通報有沒有漏看」「床邊前速覽夠不夠」「哪一頁從來沒點過」），比空白好答
7. **小小的謝意**：試用滿一個月請大家一次飲料或點心，醫師同意就做；不和回饋件數掛鉤，避免為了湊數而寫

### 4.1 表單 A 的題目（草案）

| # | 題目 | 形式 |
|---|---|---|
| 1 | 這是哪一種？ | 單選：卡住了／有錯／希望有／想稱讚 |
| 2 | 哪一頁？ | 單選：即時總覽、緊急通報、床邊前速覽、排班與指派、新增裝置、護理紀錄、管理儀表板、病人平板、其他 |
| 3 | 發生什麼事？（一句話就好） | 簡答，選填 |
| 4 | 多困擾？ | 單選：不影響／有點煩／會耽誤工作 |
| 5 | 想讓我們知道是誰嗎？ | 簡答，選填 |

- 表單開頭一行：「請不要寫病人姓名、病歷號或床號」
- 不收床號、不收照片；選項照護理端實際的頁名，換版改了頁名就跟著改
- 表單在護理站電腦上填（1125 起），版面照電腦螢幕排；共用電腦上第 5 題留空就不留名

### 4.2 問卷 E（試用第 2、4 週）

- 系統易用性量表（System Usability Scale，SUS）中文版 10 題，五點量表，約 2 分鐘；第 2 週與第 4 週分數可以比
- 另加 3 題：「最常用哪一頁」「最想拿掉或改的一件事」「會不會推薦給別床的同事用，為什麼」
- 1125 醫師答要用在論文：量表用正式的中文版，**送審核准之後才發**（第 8.1 節）；核准晚於第 2 週就順延，改成核准後第 2、4 週

### 4.3 進院 F 怎麼做

- 跟班觀察 30 分鐘：只看、不教、不解釋；記下「停下來找的地方」「繞過系統改用紙或口頭的地方」
- 訪談 2～3 位、每人 10 分鐘：先問最近一次用的情境，再問卡在哪；不問「好不好用」
- 不錄音（現場有病人）；只記不含病人的內容
- 1125 醫師答「看當天情況」：每次進院帶著觀察表與訪談題目，現場不忙才做；忙就只留表單與紙卡，不另外約時間
- 要用在論文的跟班紀錄與訪談，送審核准前不做研究用的記錄（第 8.1 節）；核准前看到的卡點只當改系統的線索

### 4.4 紙卡要不要併行（1125 開發端判斷：併行）

醫師 1125 建議表單改成系統裡的連結，使用者要開發端判斷紙卡路線要不要一起留。**判斷：併行，到連結上線滿一個月再決定留不留。**

| 理由 | 說明 |
|---|---|
| 連結要等換版 | 迭代 36 已做完（1125），還要院內換版才有；首波試用可能先開始，這段時間紙卡是護理師直接到開發端的唯一一條路 |
| 護理站電腦未必開得了外部表單 | 院內主機對外連線沒限制（Q-32），護理站電腦沒測過（第 8.2 節第 1 題）；開不了的話紙卡就是主管道 |
| 共用電腦不夠匿名 | 護理站電腦是大家輪流用、旁邊有人，怕被看到的人寧可寫紙卡；第 2 節「怕得罪人」那一條靠紙卡補 |
| 成本幾乎是零 | 印卡、一個意見箱，不必開發；護理師不寫就沒有任何負擔 |

- 代價是有人要收：聯絡人是醫師，不再加重護理師；誰收、多久收一次是第 8.2 節第 3 題
- 卡片上印「請不要寫病人姓名、病歷號或床號」；照片傳來前醫師不必整理，開發端照第 7 節整理
- 連結上線滿一個月：紙卡一個月少於 2 張就收掉意見箱，只留表單；2 張以上照留

## 6. 系統裡的入口

### 6.1 表單連結（1125 醫師建議，迭代 36，1125 做完）

- 護理端導覽列最右側固定區（專業版在「系統管理」與「變更密碼」之間）多一項「意見」，簡易版放在登出旁；不放主列（設計基準 N-2）、不主動跳出
- 點了在新分頁開外部表單 A；網址由系統管理者在營運參數填，**沒填就不出現**；不帶任何參數（不附病人、床號、帳號）
- 網址只存在營運參數，程式與設定檔裡沒有它；系統本身從不連它，是護理站電腦的瀏覽器去開（SRS FR-S07 零院外連線不受影響）
- 網址填在系統管理「營運參數與選項清單」最上面那張「意見表單網址」卡：只收 `https://` 開頭、500 字以內，要填理由；清空就不出現
- 需求：SRS FR-N23 第一段；實作：實作規格書 4.36（1125 做完）。要院內換到含迭代 36 的 tag 才有；填網址前先在護理站電腦點一次（8.2 第 1 題）

### 6.2 系統內的完整意見表單（候選，未排）

護理師最省事的做法，但資料只在院內主機。6.1 上線一個月後看表單收得如何，收不到使用者再開口；排之前要先改的需求文件列在最後。

- **入口**：護理端使用者選單裡一項「意見」，不放主列（設計基準 N-2）、不主動跳出
- **畫面**：三個大按鈕（卡住了／有錯／希望有）＋一句話選填＋「不留名」勾選；自動附上當時的畫面名稱、系統版本、時間，**不附病人、不附床號**
- **看結果**：管理頁列出，系統管理者可以標「已改／不改＋原因」；換版後護理端第一次登入時出現一次「這版依你們的意見改了什麼」，看完就不再出現
- **取得**：新的一張表歸進取出指令的一類（《蒐集資料的完整取出》第 5.5 節，每張表都要歸類）；開發端要等進院或院方核准取出才看得到
- **要先改**：SRS 新增一條護理端需求、資料字典新表、實作規格書新迭代、資料取出的分類登記；介面要照設計基準

## 7. 拿到之後怎麼整理

- **一張追蹤表**（放私人 repo，見下）：編號、收到日期、管道（A～H）、原話、分類（錯誤／卡住／希望有／稱讚／轉述病人的意見）、哪一頁、決定（改／不改／先問醫師）、對應迭代、回覆聯絡人了沒、貼上「你們說、我們改」了沒
- **每一則都要回覆**，不改的也寫原因；沒回覆就等於第 3 節第 1 條沒做
- **要改的**：看完實機才提的小修正，照往例歸成某個迭代底下的小迭代（如迭代 27.1）；牽涉臨床規則的先問醫師
- **雙軌**：原話、紙卡照片、表單回應的原始檔放私人 repo 的 `deploy/records/<MMDD>-nurse-feedback/`；公開文件只寫分類後的結論，不寫人名、床號。原話裡如有病人姓名或病歷號，**存檔前先刪**，私人紀錄也不留
- **和使用紀錄對照**：有人說「沒用到」的頁，看 G 是不是真的沒人點；說「通報漏看」的，看那段時間的處置時間

### 8.1 要用在論文：送審的範圍
