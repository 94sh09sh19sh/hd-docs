# 緊急求助的語音說明之三：鏡頭能做到哪些事

版本：v0.2　文件狀態：規劃中（2026-10-26 開立；同日依使用者三點再修：數人改由錄音推估、床邊拍照不做、平板怎麼放待問）　適用讀者：護理部、資訊室、FDE 工程團隊

上層文件：《[緊急求助的語音說明：根本判斷與設計](emergency-voice-help.md)》第 3.5 節；整條流程在《[之四：從按下求助到完成護理紀錄的完整流程](emergency-voice-help-flow.md)》

---

## 摘要

- 1026 院方除了麥克風，也強烈建議求助時配合使用鏡頭；使用者要求先查公信力與安全性等同 GitHub 千星的專案，確認鏡頭能做到什麼，再重新規畫整條流程（第 0 節）
- 1026 以 GitHub API 查了 48 個 repo：鏡頭能做的九件事裡，有 MIT、千星專案的是影像傳輸、人物偵測、人臉偵測與辨識；姿勢、遠端量心跳、表情疼痛的主流專案都是 Apache、GPL 或限制用途的授權（第 2 節）
- 判斷沿用之二的前提：鏡頭跟語音一樣**不放在派遣路徑上**，護理站不看即時影像、也不看送出當下的照片；連按都按不了的人，鏡頭要整場透析開著才幫得上，等於全程監看，不做（第 3.1、3.2 節）
- **1026 再修：第一版鏡頭不開。** v0.1 唯一採用的「平板數人」只推估護理師到床邊與離開，使用者指出錄音就做得到；比過之後，鏡頭只多了「護理師到了先不開口」那幾秒的準度，卻要多一格同意、平板跑模型、外殼開鏡頭權限，改由逐字稿推估，數人留作備援（第 3.4、4.1 節）
- **床邊拍照不做**（上層第 9.2 節第 11 題，使用者委由開發端定；院方說拍照、錄影都行）：當下護理師戴著手套、手可能沾血，碰共用平板是感染管制問題；照片進不了院方的正式紀錄（第 4.2 節）
- 鏡頭拍得到什麼取決於平板怎麼放，**下週問醫師有沒有架子**（上層新增第 13 題）；醫師「看就知道會喘會抖」那句的分析在第 3.6 節，只作參考：它說得通的是「護理師要盡快去看」，推不出「透過鏡頭看」
- 鏡頭唯一護理師親眼看不到的，是按下到到床邊那一兩分鐘與已經過去的發作；醫師若要的是這個，候選做法是那一段錄影只存、醫師事後看，依下週答覆再評估（第 3.6 節）
- **不做**：即時影像、遠端量心跳呼吸、表情與疼痛判讀、姿勢與跌倒偵測、人臉辨識、手勢求助、視訊通話、床邊拍照；第一版也不數人（第 5 節）

## 0. 為什麼有這一份

1026 院方：求助時除了強烈建議配合使用麥克風，也強烈建議配合使用鏡頭。使用者要求：

1. 先到網路上查公信力與安全性等同 GitHub 千星以上的專案，確認鏡頭能做到哪些事
2. 再重新規畫病人按下求助到護理師完成護理紀錄的完整流程（寫在之四）
3. 只寫文件，不改程式

判斷的前提跟語音相同（之二第 0、1 節），這裡只列跟鏡頭有關的：

- 護理師手上沒有裝置（Q-30），看到通報幾秒內就出發，出發後什麼都看不到；在護理站多看一步就是延誤與工作量
- 分級只看病人自選急迫度與分派表（FR-N03），不得摻入模型推論；判讀病情的功能屬 FR-P05 那一類高風險
- **平板怎麼放還沒確認**（上層第 9.2 節第 13 題）：院方 1014 只說固定橫放（Q-33），沒說有沒有支架、放在哪。架在病人面前時，前鏡頭拍到的是臉與上半身，打針那隻手臂多半不在畫面裡；平放或隨手放時可能只拍到天花板（第 3.5 節）。透析室很暗（0930 醫師）
- 平板是暫用的 Galaxy Tab S6 Lite（4 GB 記憶體、WebView 155，《[暫用平板](interim-tablet.md)》）；正式的 15 台型號未定（Q-33）
- 外殼現在只在佈建畫面掃 QR code 時用相機，病人端網頁拿不到相機（《[外殼契約](../reference/kiosk-shell-contract.md)》第 2 節）

1026 使用者再提三點（v0.2）：

1. 鏡頭目前的功用只有確認護理師動向，這不是錄音就能做到嗎（第 3.4 節）
2. 平板有沒有架子、還是病人隨便放，決定鏡頭拍到什麼，下週開會問醫師（第 3.5 節）
3. 第 11 題（床邊拍照）由開發端決定，院方說拍照與錄影都行（第 4.2 節）；第 12 題醫師說「護理師確認病人狀況最直接的方式就是用看的，病人會喘會抖」，使用者認為不精確、兩者看得到的範圍也不同，只作參考（第 3.6 節）

## 1. 篩選條件

照之一第 1 節，不另訂：

- 直接選用的 GitHub 專案：MIT、超過 1000 顆星
- 非 GitHub 的專案與權重：之一第 1.2 節「等同千星」五條判準（發布者、社群檢驗、安全格式、授權、硬體）
- 執行期零院外連線（DEP-14）；平板或院內 Windows 主機的 CPU 跑得動
- 近半年有推送（之一條件 7，開發端訂的）

授權、星數、最後推送都是 2026-10-26 以 `gh api repos/<名稱>` 查的；判讀不出授權的另外開 LICENSE 或 README 看。

## 2. 鏡頭能做到的事

### 2.1 九件事與對應的專案

| # | 能力 | 在透析室能做什麼 | 千星專案（授權／星數／最後推送） | 符合條件嗎 |
|---|---|---|---|---|
| 1 | 即時影像、錄影 | 護理站看即時畫面或回放 | [go2rtc](https://github.com/AlexxIT/go2rtc)（MIT／14,486／1025）、[MediaMTX](https://github.com/bluenviron/mediamtx)（MIT／20,512／1025）、[Pion WebRTC](https://github.com/pion/webrtc)（MIT／16,853／1024） | 符合 |
| 2 | 人物偵測與計數 | 畫面裡有幾個人、有沒有第二個人走近 | [MultimediaTechLab/YOLO](https://github.com/MultimediaTechLab/YOLO)（YOLOv9 作者的官方 MIT 版，MIT／1,757／0316）、[ONNX Runtime](https://github.com/microsoft/onnxruntime)（含網頁版，MIT／22,169／1025） | 符合（YOLO 超過半年沒推送，見 4.1） |
| 3 | 姿勢估計（骨架關鍵點） | 頭垂下、身體滑落、離開座位 | [MediaPipe](https://github.com/google-ai-edge/mediapipe)（Apache-2.0／37,399）、[MMPose](https://github.com/open-mmlab/mmpose)（Apache-2.0／7,989）、[OpenPose](https://github.com/CMU-Perceptual-Computing-Lab/openpose)（非商用授權／34,520） | **沒有 MIT 的千星專案** |
| 4 | 跌倒、離床的整套系統 | 偵測加告警加錄影 | [Frigate](https://github.com/blakeblackshear/frigate)（MIT／36,924） | 程式符合；是給固定式網路攝影機的監視系統，不是平板 |
| 5 | 遠端光體積描記（rPPG：從臉部膚色的細微變化量心跳、呼吸） | 不接觸量心跳呼吸 | [rPPG-Toolbox](https://github.com/ubicomplab/rPPG-Toolbox)（負責任 AI 原始碼授權，限制用途／1,236）、[pyVHR](https://github.com/phuselab/pyVHR)（GPL-3.0／598） | **不符合** |
| 6 | 表情、情緒、疼痛 | 看起來痛不痛、害不害怕 | [DeepFace](https://github.com/serengil/deepface)（MIT／23,599）、[OpenFace](https://github.com/TadasBaltrusaitis/OpenFace)（學術授權／7,783）、[Py-Feat](https://github.com/cosanlab/py-feat)（389） | DeepFace 程式符合，但它 README 自己寫：包進來的模型授權照原模型，要另查 |
| 7 | 人臉偵測與模糊化 | 要存的影像先把臉遮掉 | [CenterFace](https://github.com/Star-Clouds/CenterFace)（MIT／1,347／2021）、[deface](https://github.com/ORB-HD/deface)（MIT／1,617／2024-10）、[OpenCV Zoo 的 YuNet](https://github.com/opencv/opencv_zoo)（Apache-2.0／1,101） | MIT 的兩個多年沒維護 |
| 8 | 人臉辨識 | 認出是誰 | [face_recognition](https://github.com/ageitgey/face_recognition)（MIT／56,855，模型 CC0）、[InsightFace](https://github.com/deepinsight/insightface)（判讀不出／30,048） | 符合，但是生物特徵 |
| 9 | 拍照 | 床邊拍傷口、血管通路 | 不需要專案：瀏覽器的 `getUserMedia` 就做得到 | — |

人物偵測另外查過、因授權排除的：[Ultralytics](https://github.com/ultralytics/ultralytics)（AGPL-3.0／62,829）、[YOLOv10](https://github.com/THU-MIG/yolov10)（AGPL-3.0）、[YOLOv9 舊版](https://github.com/WongKinYiu/yolov9)（GPL-3.0）、[YOLOX](https://github.com/Megvii-BaseDetection/YOLOX)、[RT-DETR](https://github.com/lyuwenyu/RT-DETR)、[RF-DETR](https://github.com/roboflow/rf-detr)、[D-FINE](https://github.com/Peterande/D-FINE)、[NanoDet](https://github.com/RangiLyu/nanodet)（都是 Apache-2.0）；[ncnn](https://github.com/Tencent/ncnn)、[DEIM](https://github.com/Intellindust-AI-Lab/DEIM)、[LibreYOLO](https://github.com/LibreYOLO/libreyolo) 判讀不出授權。日後若把 GitHub 專案放寬成「授權可用」，鏡頭這邊第一個回頭看的是 MediaPipe（姿勢、臉部、物件偵測都有網頁版）。

### 2.2 文獻怎麼說

- **透析室的遠端量心跳**：唯一在透析室做的研究是牛津 Churchill 醫院（《Scientific Reports》2020）：40 位病人、84 次透析、約 304 小時影片；用的是研究級攝影機、距離 1 公尺、未壓縮影像。病人穩定時心跳平均誤差 2.8 次/分、呼吸 2.1 次/分；但因動作排除後只剩 72% 的影片可用，心跳又只在其中 65% 的時間算得出來。**病人醒著說話、用手機、跟醫護互動時，動作就讓訊號失效**；日光燈閃爍、醫護的影子也會干擾
- **非接觸量測的臨床整體**：系統性回顧收 12 篇、654 人，作者結論仍是需要更多臨床研究
- **表情判讀疼痛**：2015～2025 的系統性回顧收 25 篇，準確度約 70%～90% 以上，但**幾乎沒有外部驗證**；OpenFace 在長者與失智者身上的某些臉部動作單位，精確度只有 54%；疼痛資料集裡的長者很少，皺紋與中風後的面癱會改變表情
- **醫院的鏡頭跌倒偵測**：查到的是研究原型（Fraunhofer，影像先模糊化、或告警後才看得到畫面）與廠商自述的成效，沒有找到有對照組的護理人員評估；另一條路是不用鏡頭的毫米波雷達（富士通與和歌山醫大試驗中）

## 3. 根本判斷

### 3.1 派遣路徑：不放

| # | 鏡頭能給護理站什麼 | 為什麼不用 |
|---|---|---|
| 1 | 即時影像 | 護理師看到通報就出發，不會坐下來看；護理站沒人時沒有人看；手上沒有裝置，出發後看不到（Q-30） |
| 2 | 送出當下的一張照片（放在床邊前速覽裡） | 看一眼只要一秒，是鏡頭比語音強的地方，所以單獨評估：前鏡頭拍不到打針的手臂；透析室暗，臉色看不出來；一張「看起來還好」的照片會讓人慢下來，而分級只認病人自選（FR-N03）；類別本身已經告訴護理師要帶什麼；護理站螢幕旁人看得到。唯一說得通的是「還沒選」那一則，但它本來就是緊急、本來就馬上去，照片改變不了「立刻出發」 |
| 3 | 模型判讀（姿勢、表情、心跳） | 沒有驗證；FR-N03 不得摻入模型推論；FR-P05 高風險 |

**開發端決定：第一版護理站看不到任何鏡頭的影像。** 照片的事若要重提，條件是試用中出現「護理師到床邊才發現要回頭拿東西或多叫一個人」的情形，而且是照片看得出來的——由護理部提出再議。院方 1026 說拍照與錄影都行，拿掉的只是院方那一關，上面這些理由不受影響。

### 3.2 連按都按不了的人：不做

鏡頭要在按下之前就開著才看得到，等於整場透析（約四小時）都被看著；姿勢與跌倒偵測沒有 MIT 的千星專案；自動告警屬高風險規則（FR-R）。正解仍是之二第 3 節的 H（生理量測警示）、G（床邊呼叫鈴）、I（透析機警報與巡視）。

### 3.3 護理紀錄與資訊化

- **護理師不會回看影片**，跟不聽原音同理；錄影看得到身體與鄰床，隱私代價遠大過錄音
- 紀錄裡真正缺的是**時間**：到床邊時間一直是空的（FR-N10「我到床邊了」跟著手持裝置開關關著，Q-30），儀表板「按下到到床邊」也一直空白。v0.1 以為這件事要靠鏡頭，1026 比過錄音之後改了（第 3.4 節）
- 傷口與血管通路的樣子，照片比文字清楚；但在求助當下拍不划算（第 4.2 節）

### 3.4 數人：錄音就推估得到（1026 再修）

使用者 1026 指出：鏡頭在 v0.1 的唯一用途是確認護理師到床邊與離開，錄音就做得到。逐項比過：

| 要知道的 | 錄音怎麼推估 | 鏡頭多做到什麼 |
|---|---|---|
| 到床邊 | 逐字稿裡**第一句護理師對病人說的話**的時間。挑句子時本來就要分出哪一句是護理師說的衛教（上層第 3.1 節 T 段），同一次呼叫多標一欄就好；看的是內容，不是聲音特徵 | 護理師到了先看機器、不開口的那幾秒到幾十秒 |
| 離開 | 最後一句護理師說的話的時間 | 停錄可以早兩分鐘（推估離開後 60 秒，比「3 分鐘沒人說話」早）。錄音這邊改成**錄得到、留不下**：整段處理時，護理師最後一句之後超過 60 秒的音訊與逐字稿直接刪，留存的旁人對話一樣少 |
| 誤判 | 鄰床的護理師對鄰床病人說話，可能被當成「到了」；AI 沒開時不推估 | 鄰床與走道的人入鏡會被算進去；太暗偵測不到；平板怎麼放決定拍不拍得到（第 3.5 節） |

鏡頭多出來的代價：同意書多一格、平板上載入模型（DEP-16 的例外）、外殼開鏡頭權限、平板耗電發燙要驗、另一套光線與角度的驗證語料。用途是一個第一版只存不顯示、分鐘級的數字，**幾秒的準度不值這些代價**。

**開發端決定：第一版鏡頭不開**；到床邊與離開改由逐字稿推估（上層第 3.1、3.3 節），一樣只存不顯示、驗證過才讓護理師點「寫入」。數人留作備援，條件寫在第 4.1 節。

### 3.5 平板怎麼放決定鏡頭拍得到什麼（第 13 題，下週問醫師）

其他文件一直假設「平板多半架在床邊支架上、視距 40～70 公分」（《[介面設計基準](uiux-design-baseline.md)》、遊戲化），院方 1014 只確認了固定橫放；支架採購還掛在 Q-22。

| 放法 | 前鏡頭拍到什麼 | 對鏡頭用途的影響 |
|---|---|---|
| 支架在病人正前方（床尾桌、懸臂） | 臉與上半身；護理師站床側時只入鏡一部分或不入鏡 | 數人可能漏掉站床側的護理師；錄影看得到上半身的動作 |
| 支架在床側 | 病人側臉、走道、鄰床 | 鄰床與走道的人入鏡多，誤報與隱私都差 |
| 放在病人腿上、床上，或隨手放 | 天花板、下巴、被子，每次不一樣 | 任何鏡頭用途都不可靠 |
| 病人自己拿著 | 晃動、角度不定 | 同上 |

要問的：有沒有支架、裝在哪裡、會不會每床不同、病人會不會拿下來。沒有支架的話，**介面設計基準的視距與觸控假設也要回頭改**，不只鏡頭。

### 3.6 醫師說「用看的」：親眼看與鏡頭看得到的範圍不同（第 12 題，只作參考）

醫師 1026：「護理師確認病人的狀況最直接的方式就是用看的，病人會喘會抖等等。」使用者認為這句不精確、兩者看得到的範圍也不同，只作參考。對照：

| 比什麼 | 護理師到床邊親眼看 | 平板鏡頭 |
|---|---|---|
| 部位 | 全身、穿刺處與血管通路、透析機螢幕與管路、床單（有沒有出血） | 鏡頭朝哪就看哪；架在面前時是臉與上半身，平放時是天花板（第 3.5 節） |
| 角度 | 走近、換位置、掀開被子 | 固定一個角度 |
| 光線 | 可以開床頭燈 | 透析室暗，臉色、嘴唇發紺看不出來 |
| 喘 | 看胸廓起伏、聽呼吸聲、量血氧 | 肩頸用力的明顯喘看得出；輕的看不出；遠端量呼吸在說話、動作時就不準（第 2.2 節） |
| 抖 | 摸得出冷熱，分得出寒顫、抽筋或抽搐 | 大動作看得出，分不出原因 |
| 其他 | 摸（冷汗、脈搏）、問、聽 | 沒有 |
| 什麼時候有 | 到了之後 | 只有「沒有人在場」的時段才有親眼看替代不了的價值 |

讀法：

- 這句話說得通的是「**護理師要盡快到床邊去看**」——派遣路徑不加任何一步，正是為了這個（上層第 2.2 節）；推不出「透過鏡頭看」，鏡頭看得到的都比親眼看少
- 鏡頭唯一護理師看不到的，是**按下到到床邊那一兩分鐘**，以及到了之前就過去的發作（例如寒顫、抽搐只持續一下）
- 醫師若要的是這個，候選做法是「送出到護理師到床邊」那一段**錄影只存不顯示、醫師事後在紀錄頁看**；院方已說錄影可以，剩下的是病人同意、誰看、留多久，以及第 3.5 節的放法拍不拍得到。開發端不先做，依下週答覆再評估
- 醫師若要的是「護理師出發前先看一眼」，照第 3.1 節說明不做的理由

## 4. v0.1 採用的兩件（1026 再修：第一版都不做）

### 4.1 數人：推估到床邊與離開（改為備援）

第 3.4 節定案前的設計，保留在這裡，備援時照用。**拿出來的條件**（都要成立）：

1. 逐字稿推估到床邊的驗證沒過門檻（上層第 6 節：時間差第 90 百分位 15 秒內、誤報 5% 以下）
2. 第 13 題答覆的放法拍得到床邊（第 3.5 節表第一列）
3. 外殼另加一次版號（第一版只開麥克風）

**什麼時候開**：跟錄音同一段——臨床組與「還沒選」的求助，送出那一刻開始，停止條件照上層第 3.1 節，再加「推估離開後 60 秒」。倒數期間不開；非臨床組不開；病人沒同意鏡頭的不開。

**在哪裡跑：平板本機，影像不離開平板。**

1. 病人端以 `getUserMedia` 取前鏡頭，每秒取一張、縮成 320×320
2. 以 ONNX Runtime Web（WebAssembly）跑 YOLOv9 最小的 t 版，只取「人」這一類
3. 取完結果，影像立刻丟掉；不存檔、不上傳
4. 送到後端的只有每秒一筆「時間、近處人數、最大的人框占畫面的比例」，沿用錄音的裝置 Token 與重送規則

選平板而不選後端：影像不出平板，隱私最好；後端也不必收每床每秒一張圖。代價是平板耗電與發燙，第 6 節要量；扛不住就退回每 2 秒一張，再不行才考慮改送後端（那時要另外評估影像傳輸與留存）。

**近處才算**：人框的高度超過畫面一半（約 1 公尺內）才算一個人，鄰床與走道上的人不算。門檻是起始值，用第 6 節的語料調。

| 推估 | 條件 | 起始值 |
|---|---|---|
| 到床邊 | 送出後，近處人數從 1（或 0）變成 2 以上，持續一段時間 | 3 秒 |
| 離開 | 到床邊之後，近處人數回到 1 以下，持續一段時間 | 60 秒 |

**拿來做什麼**：跟逐字稿推估同一個用途——只存不顯示，驗證過才在草稿 A 段時間線旁出現「推估 14:06 到床邊」、護理師點一下才寫進去；不認人，不得用於個人考核。

**權重與相依**：

- MultimediaTechLab/YOLO 在 GitHub 發布的 `v9-t.pt` 是 PyTorch pickle，照之一第 1.2 節在隔離的開發機以 `weights_only=True` 載入、轉成 ONNX、記雜湊，平板只放轉好的檔案
- 這個 repo 最後推送是 2026-03-16，超過之一條件 7 的半年；備援時照用：它只在開發機上轉一次權重，執行期只有 ONNX Runtime（MIT、持續維護）
- ONNX Runtime Web 與 YOLO 權重在平板上載入，屆時要另問 DEP-16 的例外

**平板上的畫面**：「正在記錄對話與到床邊時間（鏡頭只數人數，不拍照、不錄影）」；按「不要記錄」錄音與數人一起停、已收的一起刪。Android 鏡頭使用中的綠點會亮。

### 4.2 床邊拍照：不做（1026 開發端定）

v0.1 的設計：錄音期間平板多一顆「拍照給紀錄」，護理師拍出血、腫脹的部位，回護理站在草稿旁點「附上」。使用者把第 11 題交給開發端決定，院方說拍照、錄影都行。**決定不做**：

1. **感染管制**：要拍的時候正是出血、滲漏的時候，護理師戴著手套、手可能沾血；拿共用的病人平板去拍，平板要另外消毒（Q-22 的消毒 SOP 還沒定）。脫手套再拍，就是緊急處置中多一步
2. **第二份紀錄**：複製到院方系統的是文字，照片只能留在本系統，正式紀錄與照片分在兩處，以後查的人不知道要看哪裡
3. **不好拍**：前鏡頭朝著病人；有支架要先取下（第 3.5 節）；10 吋平板單手不好拍；正式平板有沒有後鏡頭還不知道（Q-33）
4. 院方同意拍照，拿掉的只是院方那一關，上面三條不受影響

真正有用的是**血管通路跨次追蹤**（這次的瘀青比上次大嗎），那不是求助的事，也不該綁在求助流程；護理部若提出，另案設計，用院方原本拍傷口的設備與流程。影像判讀仍照 FDE 評估不做（實作規格書第 1.3 節）。

## 5. 不做的事

| 不做 | 理由 |
|---|---|
| 第一版開鏡頭數人 | 錄音推估得到；幾秒的準度不值多一格同意與平板跑模型（第 3.4 節）；備援條件見第 4.1 節 |
| 床邊拍照 | 感染管制、第二份紀錄（第 4.2 節） |
| 護理站看即時影像或送出當下的照片 | 第 3.1 節 |
| 錄影（不論存不存） | 護理師不回看；看得到身體與鄰床，隱私代價最大。唯一保留的可能是第 3.6 節「到床邊前那一段給醫師事後看」，依下週答覆再評估 |
| 遠端量心跳、呼吸 | 沒有符合授權的千星專案；透析機與院方本來就量；病人說話、跟護理師互動時量不準——求助時正好是這種時候（第 2.2 節） |
| 表情、疼痛、情緒判讀 | 沒有長者的驗證、權重授權不明；會被當成病情輕重（FR-P05）。語氣的「只存不顯示」不延伸到臉：存臉的判讀結果要先存臉的影像，代價不同 |
| 姿勢、跌倒、離床偵測 | 要整場開著；沒有 MIT 的千星專案；告警屬高風險（第 3.2 節） |
| 人臉辨識 | 生物特徵；理由同上層「不做聲紋」 |
| 舉手、揮手等手勢求助 | 要整場開著；理由同之二第 3 節 F（常開麥克風） |
| 病人與護理站視訊通話 | 護理師會坐下來講，而不是過去 |
| 影像模糊化後存檔 | 不存影像就不需要；MIT 的兩個專案也多年沒維護 |

## 6. 驗證（備援拿出來時才做）

- **語料**：開發團隊與志工在模擬床位錄，只在開發機上用、不帶進院內：亮與暗兩種光線（含實際透析室的亮度）；照第 13 題答覆的放法擺平板；護理師站在病人左、右、床尾；鄰床有人、走道有人走過；**不用病人**
- **指標**：推估到床邊與人工標註的時間差（中位數、第 90 百分位）；漏報與誤報；推估離開的時間差；暫用平板 10 分鐘連續跑的耗電、溫度、每張的推論時間
- **顯示門檻**：跟逐字稿推估相同（上層第 6 節）
- 逐字稿推估的驗證寫在上層第 6 節

## 7. 隱私與同意

- **第一版不開鏡頭**：同意書只有錄音一格，外殼不開鏡頭權限，平板送出去的資料裡沒有任何影像，也沒有處理過影像
- 備援或第 3.6 節的錄影若日後採用：同意書另加一格、錄音與鏡頭可以只同意一種；數人雖然影像算完就丟，仍是處理了病人與護理師的影像，要寫明；到床邊時間只做單位層級、不得用於個人考核
