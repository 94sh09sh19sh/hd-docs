版本：v0.1　文件狀態：**進行中（部署當天要回來填）**　適用讀者：FDE 工程團隊、醫院資訊室

## 0. 這份文件是什麼

《[部署規範](../requirements/deployment-spec.md)》DEP-25 要求：**路線 A 的每一次失敗都要記錄下來——
在哪一步、錯誤訊息的原文、花了多久。紀錄本身就是交付物。**

它有兩個用途：向資訊室說明「為什麼不能用一般的方式部署」時，它比任何說明都有效；
以及日後有人提議「直接在主機上更新就好」時，它是現成的答案。

本文件同時收 DEP-26～28（路線 B）、DEP-19／DEP-32（更新與回退）與 DEP-22（乾淨機器）的演練結果。

**要知道每一格怎麼填出來，看《[部署手冊](../deployment/index.md)》**（0921 新增）：
這一份收的是**結果**，那一份寫的是**動作的順序與每一步會怎麼壞**。
現場的對應關係是——[第二冊](../deployment/02-dry-run.md) 填 §3.2、
[第四冊](../deployment/04-onsite.md) 填 §1.3 與 §2.3、
[第三冊](../deployment/03-tablet-shell.md) 填 §6.1。

**每一節分成兩塊**：

| 塊 | 意思 |
|---|---|
| **已完成（開發端）** | 迭代 10 在開發機上實際跑過，輸出照抄 |
| **部署當天要填** | 只有在院內那台主機上才做得出來的，先把欄位列好 |

**不要把開發端那一塊當成驗收通過。** 開發機有網路、有 Node.js、有一份完整的套件目錄，
院內那台三樣都沒有——而那正是整件事的重點。

## 1. 路線 A：在正式主機上 `git clone` 並安裝（預期失敗）

**目的不是成功，是取得證據。**

### 1.1 已完成（開發端）：把每一步的失敗重現一次

正式主機還沒拿到，因此在開發機上把「沒有對外連線」這個條件做出來再跑一次，
取得每一步的錯誤原文。**這不能取代現場那一次**（錯誤訊息會因為院內的代理伺服器設定而不同），
但它先回答了「會失敗在哪裡」。

| 步驟 | 重現方式 | 結果 |
|---|---|---|
| `git clone` | — | 未在開發端重現：開發機連得到程式碼來源，重現不出院內那台的情形。**現場照做並記錄** |
| `npm install` | 把套件來源指向一個不存在的位址（`--registry=http://127.0.0.1:9`），並使用空的快取目錄 | **失敗，耗時 71 秒** |
| 套用資料庫遷移 | 見 1.2 | 引擎不在套件裡，會現場下載 |

`npm install` 的錯誤原文（節錄自 npm 的除錯紀錄）：

```
25 error code ECONNREFUSED
26 error syscall connect
27 error errno ECONNREFUSED
28 error FetchError: request to http://127.0.0.1:9/@nestjs%2fcore failed,
   reason: connect ECONNREFUSED 127.0.0.1:9
```

**要看的不是那串錯誤碼，是那 71 秒**：它連「第一個套件的中繼資料」都還沒拿到。
這個專案的相依有數百個，現場不會有人在那裡等它一個一個逾時。

### 1.2 套用遷移：一個裝好了也還是不能用的相依

Prisma 的執行引擎**不在 npm 套件裡**，是安裝套件時由安裝後腳本另外下載的（約 40MB）。
因此即使前兩步奇蹟般成功，這一步仍然會倒在

```
request to https://binaries.prisma.sh/... failed, reason: getaddrinfo ENOTFOUND binaries.prisma.sh
```

這一條在迭代 7 就撞過一次，處置寫在 DEP-30。**安裝包自帶引擎**，路線 B 不會遇到它。

|---|---|
| 日期／時間 |  |
| 執行者 |  |
| 主機 |  |
| `git clone` 的錯誤原文 |  |
| 耗時 |  |
| `npm install` 的錯誤原文 |  |
| 耗時 |  |

| **若 `git clone` 成功**：來源（直連／代理／院內鏡像）、用了誰的憑證、連線是否常態、選了哪一條出路（[第七冊](../deployment/07-git-clone.md) G-02～G-06） |  |

## 2. 路線 B：隨身碟帶入離線安裝包（正式路線）

```
開發端                                    院內
建置安裝包 → 壓縮 → 產生雜湊值 → 防毒掃描 → 隨身碟 → 掃描 → 解壓 → 核對雜湊 → 安裝
```

### 2.1 已完成（開發端）：建置與驗收

```
npm run build
npm run check:offline
npm run package:build -- --zip
npm run package:verify -- --dir dist-package/<安裝包目錄>
```

2026-09-20 的建置結果：

| 項次 | 值 |
|---|---|
| 安裝包 | `hd-tablet-care-0.1.0-<commit>` |
| 檔案數／大小 | 23,588 個檔案，681.4 MB（未壓縮） |
| 自帶執行期 | Node.js v24.16.0（win32-x64） |
| 自帶 Prisma 引擎 | `query_engine-windows.dll.node`、`schema-engine-windows.exe` |
| 雜湊值 | `CHECKSUMS.txt` 逐檔 SHA-256；清單本身再取一次 SHA-256 附在交付單上 |

`npm run package:verify` 的五項：

| 項次 | 結果 |
|---|---|
| 雜湊值核對（23,588 個檔案） | 通過 |
| 包內沒有設定檔、資料庫或備份（DEP-13） | 通過 |
| 以包內引擎套用既有遷移到全新資料庫（DEP-31） | 通過 |
| 以包內執行期啟動三個行程並通過存活檢查 | 通過 |
| 全程沒有往院外的連線（連線哨兵） | 通過 |

**這一次驗收在開發機上做的，只證明安裝包內部是完整的。**
它證明不了 DEP-22——那要一台沒有 Node.js、沒有套件目錄、沒有網路的機器。

### 2.2 建置期間抓到的兩個缺陷

演練的價值在這裡：**兩個缺陷都只有在真的把安裝包跑起來時才會現形**。

| # | 症狀 | 原因 | 處置 |
|---|---|---|---|
| 1 | 後端在安裝包裡起不來，錯誤是「找不到專案根目錄」 | 資料庫路徑檢查會往上找帶 workspaces 的 `package.json`（避免資料庫被收進版控）。**安裝包裡沒有那個東西**，於是一路找到磁碟根目錄然後丟例外 | 改成兩段：先找專案根目錄，找不到就找安裝包根目錄（以 `VERSION.json` 與 `runtime/` 辨識）。兩者要擋的是同一件事——資料庫不得放在「每次更新會整個換掉的那個目錄」裡（DEP-08） |
| 2 | `prisma migrate deploy` 在包內找不到 CLI | 指令外套只認 `apps/api/node_modules` 與 monorepo 根目錄兩個落點，安裝包的版面是 `app/node_modules`（少了一層） | 補上第三個落點 |

兩個都不是設定寫錯，是**開發機的版面與安裝包的版面不一樣**，而所有靜態檢查都只看得到前者。

## 4. 更新演練（DEP-19、規範第 18 條）

### 4.1 已完成（開發端）：完整跑過一次，而且跑出一個缺陷

2026-09-20，以正式流程對一份含真實筆數的開發資料庫副本執行 `npm run db:update`：

| 步驟 | 結果 |
|---|---|
| 1 確認服務已停止 | 沒有服務在回應，可以繼續 |
| 2 開啟更新紀錄 | 前一次成功更新的版本：0.1.0 |
| 3 更新前備份 | `hd-before-update-20260920T170519.db`（4,247,552 bytes），SHA-256 `4dd0a9e6…52860a` |
| 4 驗證備份還原得起來 | 完整性檢查 ok；護理端帳號 129、病人 131、綁定 112、求助 120、稽核紀錄 3,080 |
| 5 套用既有遷移 | 套用了 1 個遷移：`20260921030000_iteration10_kiosk_foreground` |
| 6 寫入更新紀錄 | 更新紀錄與稽核軌跡都已寫入 |

**第一次跑的時候第 5 步倒了**：

```
Error: SQLite database error
database is locked
   0: sql_schema_connector::sql_migration_persistence::initialize
```

原因是更新腳本為了寫更新紀錄，一直開著一條連往正本的連線，而遷移引擎要的是獨占存取——
**更新腳本自己擋住自己**。它倒的位置是「備份做完、驗證通過、正要動 schema」的那一刻，
看起來像資料庫壞了。

這個缺陷只有在**這次更新真的帶著待套用的遷移**時才會現形；沒有 schema 變更的更新一路綠燈。
換句話說，**它會在第一次真正需要它的時候失敗**。處置：在套用遷移之前先把腳本自己的連線放掉。

## 5. 回退演練（DEP-19、規範 18.3）

**程式可以退版，資料庫不行退版。** 動過 schema 的版本要回退，是**還原備份**再換回舊版程式，
不是把遷移倒回去。

### 5.1 已完成（開發端）

接續 4.1，把該次更新前的備份還原到另一個檔案：

```
npm run db:restore -- --from <備份檔> --to <還原後的路徑> --sha256 <備份歷程上的雜湊>
```

| 項次 | 結果 |
|---|---|
| 雜湊值 | 與備份歷程上的紀錄相符 |
| 完整性檢查 | ok |
| 筆數 | 護理端帳號 129、病人 131、稽核紀錄 3,080、功能開關 11、備份歷程 49 |

還原後與更新後兩份資料庫的對照：

| | 更新後 | 還原後 |
|---|---|---|
| `devices` 的逸出偵測欄位 | 三欄都在 | 沒有（回到遷移前的樣子） |
| 已套用的遷移數 | 9 | 8 |
| 稽核紀錄 | 3,083 | 3,080 |

差的那三筆是更新流程自己寫的（更新開始、備份已驗證、更新完成）——**資料完整，沒有遺失**。
