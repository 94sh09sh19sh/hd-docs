版本：v0.1　文件狀態：草案　適用讀者：FDE 工程團隊、護理部、任何要動到介面的人

## 0. 本文件的定位

本文件不是需求文件，是一份**設計基準**：它規定「這套系統的介面長什麼樣、為什麼長這樣、下一次改的時候要遵守什麼」。

- 功能需求來源是《[軟體需求規格書](../requirements/srs.md)》，介面相關的硬性要求在第 6 章非功能性需求與 FR-P13、FR-S10、FR-S11
- 與需求文件衝突時，**以需求文件為準**
- 待確認事項指回《[尚待確認事項清冊](../requirements/open-questions.md)》，本文件不另立清單

**這份文件不是一次性的改版說明。** 使用者於 2026-09-19 指示：介面重新設計之後，**日後所有介面工作都要依這份基準做**。因此它寫的是可重複套用的規則，不是這一次改了哪幾個畫面。

> **給 AI agent**：對應的可執行版本在專案的 `.claude/skills/hd-uiux/`。動任何介面程式碼前先讀那一份；本文件是它的理由書與人類可讀版。兩者若有出入，**以本文件為準並回報 skill 已過時**。

## 1. 為什麼要先分析族群

上一版介面的問題不是「不好看」，是**沒有預設的使用者**。兩端共用同一套版面假設：一樣的字級邏輯、一樣的卡片密度、一樣的資訊層級。但這兩群人的使用情境幾乎沒有一處相同：

| | 病人端 | 護理端 |
|---|---|---|
| 姿勢 | **躺著**，視線斜向上 | 站著或半坐，視線平視 |
| 手 | **常常只有一隻手能動**（另一隻在打針） | 兩隻手，但常拿著東西 |
| 時間 | 四小時，非常多 | **被切碎**，每次幾十秒 |
| 注意力 | 低，可能想睡、不舒服 | 高但被分散，同時盯多床 |
| 動機 | 打發時間、身體不舒服時求救 | 完成手上的事，不漏掉任何一床 |
| 熟悉度 | 每週三次，**但多半不熟數位介面** | 每天用，會變得很熟 |
| 犯錯的代價 | 按錯 → 護理師白跑一趟 | 看漏 → **病人沒有被處理** |

**同一套版面同時服務這兩群人，只會兩邊都做不好。** 下面兩節分別描述它們。

## 2. 族群一：透析病人（病人端平板）

### 2.1 這群人的事實

台灣血液透析族群的組成有幾項結構性事實，它們直接決定介面怎麼做：

| 事實 | 對介面的意思 |
|---|---|
| **年齡偏高**，多數為中老年 | 老花是常態。**字級不是偏好問題，是能不能看到的問題** |
| **糖尿病腎病變是最大宗病因** | 糖尿病視網膜病變常見，對比度與色彩辨識能力可能下降。**不得用顏色作為唯一的資訊載體** |
| 每週固定三次、每次四小時 | 這個介面他們會看**幾百次**。一個小小的煩人之處會被放大幾百倍 |
| 治療中一隻手固定不能動 | **所有操作必須單手可完成**，而且是在畫面的下半部 |
| 躺著，平板多半架在床邊支架上 | 視距約 40～70 公分，角度傾斜。**畫面上半部反光最嚴重** |
| 可能虛弱、想睡、注意力低 | 任何需要「讀完一段話才知道怎麼做」的設計都會失敗 |
| 不舒服的時候才最需要它 | **求助這條路徑必須在最糟的狀態下也走得通** |

### 2.2 六條設計原則

| # | 原則 | 具體規則 |
|---|---|---|
| P-1 | **求助永遠在同一個地方，而且永遠在下半部** | 固定版位，任何畫面、任何狀態、輪播中或非輪播中，位置與尺寸一律相同 |
| P-2 | **一個畫面一件事** | 首頁四個動作，加上求助區共五個目標（0920 起，見下方註）。不要因為「還有空間」就多放東西 |
| P-3 | **字要大到躺著看得清楚** | 內文最小 20px，數值與按鈕文字更大；行高寬鬆 |
| P-4 | **顏色不是唯一線索** | 每一個用顏色區分的狀態都要同時有文字或圖形 |
| P-5 | **不要有需要精準的操作** | 觸控目標最小 64×64px，彼此間距至少 12px；沒有長按、沒有滑動手勢、沒有雙擊 |
| P-6 | **不確定的時候，說人話** | 不寫「已提交」寫「護理師收到了」；不寫「同步中」寫「正在送出」 |

> **0920 調整（迭代 9.1）**：首頁的動作由三個增為四個，加上求助區共五個目標。
> 新增的是「看今天的資訊」——輪播原本只有「靜置到門檻」一個入口，病人想主動看就沒有辦法，
> 而病人端不得有長按、滑動、雙擊（P-5），能做的入口只剩一顆看得見的按鈕。
> 同一次調整把首頁的求助狀態由最多六列收成一列，首頁在平板上因此不必捲動就看得完。
> 理由與完整清單見《[迭代 9.1 修正清單](iteration-9-1-fixes.md)》第 2.4、2.5 節。

### 2.3 這一次修掉的具體問題：緊急按鈕蓋住輪播的字

**症狀**：閒置輪播開始後，求助按鈕蓋住輪播卡片的文字。

**原因不是「按鈕太大」。** 原本的做法是：輪播是一個覆蓋整個畫面的圖層，而求助按鈕在底下那個首頁版面的正常文件流裡，輪播開始時把它的**堆疊層級抬高**，讓它浮到輪播之上。

這個做法有兩個問題：

1. **按鈕的位置由首頁版面決定，不是由畫面決定。** 它是首頁四個按鈕中的第二個，實際落在哪裡取決於上面有多少內容、螢幕多高。輪播那一層只能「猜」它在下半部，然後把卡片往上推——猜錯就蓋住。
2. **「位置固定」被實作成「層級固定」。** FR-P13 要的是版位固定，兩者不是同一件事。

**修法：把求助按鈕從版面裡拿出來，做成整個應用程式共用的固定底部區域。**

```
┌─────────────────────────┐
│                         │
│   內容區                 │  ← 首頁、問卷、衛教、輪播都畫在這裡
│   （輪播卡片也在這裡）     │     這一區的高度 = 畫面高度 − 求助區高度
│                         │
├─────────────────────────┤
│   ★ 我需要協助           │  ← 固定區。永遠在這裡，永遠一樣大
└─────────────────────────┘     內容區永遠畫不到這裡
```

三個要點：

- **求助區是版面的一部分，不是浮在上面的東西。** 內容區的可用高度先扣掉它，因此「蓋住」在結構上不可能發生
- **輪播卡片的高度以內容區為基準計算**，不是以整個畫面為基準
- **非輪播時求助區也在**，位置與尺寸完全相同——這才是 FR-P13 所說的「位置固定」

**驗收方式**：在輪播進行中截圖，量求助區的位置與尺寸；退出輪播再截一次。**兩張圖上那塊區域必須一模一樣，而且輪播卡片的任何一個字都不得落在那塊區域裡。**

## 3. 族群二：透析室護理師（護理端）

### 3.1 這群人的事實

| 事實 | 對介面的意思 |
|---|---|
| **忙，而且是被打斷的那種忙** | 每次看畫面只有幾十秒。**要能一眼看出「現在有沒有事」** |
| 同時負責多床 | 總覽的密度要高，但**重要的東西要跳出來** |
| 站著或走動中操作 | 目標不能太小；但不像病人端那麼極端 |
| 每天用同一套介面 | 會變熟。**熟了之後最在意的是「要點幾下」** |
| 首波只有護理站的一兩台電腦 | 螢幕不小，但**不是隨身的**。需要走回護理站才能操作 |
| 漏看一則通報的代價很高 | 通知不能只靠一個數字角標 |

**最重要的一條**：護理師不是「使用者」，是**在工作中順便用這個工具的人**。介面每多一個步驟、每多一個要讀的字，都是從照顧病人的時間裡扣掉的。

### 3.2 六條設計原則

| # | 原則 | 具體規則 |
|---|---|---|
| N-1 | **一眼看出有沒有事** | 進畫面 2 秒內要能回答「現在需要我嗎」。待處理通報要用顏色＋數字＋位置三重強調 |
| N-2 | **每天用到的才放在主列** | 導覽列只放每日必用；其餘收進選單或關閉（FR-S11） |
| N-3 | **順序照工作流程，不照功能分類** | 交班 → 指派 → 盯著 → 處理 → 收工。不是「病人相關／裝置相關／設定相關」 |
| N-4 | **不要讓護理師讀系統的內部用語** | 狀態一律中文，開關一律中文名稱（FR-S10） |
| N-5 | **破壞性動作要有阻力，日常動作不要有** | 解除綁定要確認；標記已讀不要確認 |
| N-6 | **關掉的功能就是不存在** | 不放灰色按鈕、不放「敬請期待」（DEP-34） |

### 3.3 導覽列重新編排

**原本 17 條連結一字排開**，沒有層級、沒有順序邏輯，每天用的跟半年用一次的並列在一起。

**新編排分三層（版位可在系統設定調整，FR-S11）**：

**主列——每日必用，順序照一天的工作流程：**

| 順位 | 項次 | 為什麼在這裡 |
|---|---|---|
| 1 | 即時總覽 | 預設畫面，一天中看最多次 |
| 2 | 緊急通報 | 有事的時候第一個要去的地方，帶未處理數 |
| 3 | 排班與指派 | 每個班次開始時做一次 |
| 4 | 裝置管理 | 平板有狀況時；也是看 Kiosk 逸出狀態的地方 |
| 5 | 病人 | 新病人或資料要改的時候 |
| 6 | 輪播內容 | 內容維護。**這一項是主列裡最邊緣的，若護理長覺得用不到，改設定收進選單** |
| 7 | 總覽螢幕模式 | 開護理站那台大螢幕用，一天按一次 |

**選單（「更多」下拉）——用得到，但不是每天：**

帳號審核、護理紀錄、衛教、SOP 查詢、臨床數值、病人趨勢、稽核軌跡

**關閉——首波不提供：**

班表、成效基準、離院衛教，以及所有需手持裝置才能用的功能（DEP-29）

**最右側固定**：系統管理（只有具權限者看得到）、使用者名稱與登出。

**三條規則**：

1. **主列最多 7 項。** 超過就不是「每日必用」了，是把選單攤開
2. **順序是工作流程，不得改成字母或功能分類**
3. **版位改動寫入稽核軌跡**——半年後有人問「這個功能什麼時候不見的」要答得出來

### 3.4 移除介面上的內部技術識別（FR-S10）

**現況盤點**（實際出現在護理師看得到的畫面上）：

| 問題 | 出現在哪一類地方 |
|---|---|
| 卡片標題帶需求編號，例如「功能開關中心（FR-S08）」 | 系統管理、SOP 查詢、趨勢、衛教、護理紀錄的區塊標題 |
| 提示文字帶待確認編號，例如「待資訊室確認（Q-09）」 | 臨床數值匯入、成效基準 |
| 直接印出列舉常數，例如排班狀態、帳號狀態 | 排班與指派的狀態欄、帳號審核的狀態欄 |
| 開關清單印出開關識別字與需求編號 | 功能開關 |
| 說明文字帶介面層類別名 | 臨床數值 |
| 說明文字提到迭代編號，例如「將於迭代 8 提供」 | 唯讀帳號的空狀態 |

**處理原則**：

- **每一個列舉值都要有中文顯示名稱**，由共用常數提供，不在畫面上臨時拼
- **需求編號、待確認編號、迭代編號一律移除**；要說明「這個還沒好」就直接說人話，或依 DEP-34 整個不顯示
- **程式碼註解不動。** 這條規範管的是使用者看得到的字，不是原始碼——需求編號留在註解與文件裡，那是可追溯性的來源
- 新增一支檢查腳本掃描前端原始碼中會被繪製出來的字串，**把它納入驗收**，不靠人工複查

## 4. 共用的設計系統

兩端各有各的版面，但底層的語彙要一致——同一個顏色在兩邊代表同一件事，否則維護的人會混亂。

### 4.1 顏色

**只有四種語意色，而且每一種都必須搭配文字或圖形**（P-4）：

| 語意 | 用在哪 | 搭配 |
|---|---|---|
| 一般 | 預設狀態、可點擊的東西 | — |
| 注意 | 待處理、進行中 | 文字標籤 |
| 警示 | 緊急通報、勞動條件違反、斷線 | 文字標籤＋圖形 |
| 完成 | 已處理、成功 | 文字標籤 |

**求助按鈕用警示色，而且只有它用。** 病人端畫面上不得有第二個紅色的東西，否則它就不再是「那顆紅色的」。

**兩端都必須通過對比度檢查**：內文對背景至少 4.5:1，大字與圖形至少 3:1。病人端因為糖尿病視網膜病變常見，**目標值提高到內文 7:1**。

### 4.2 字級

| | 病人端 | 護理端 |
|---|---|---|
| 內文最小 | **20px** | 15px |
| 主要按鈕文字 | **28px** | 16px |
| 數值（體重、時間） | **36px 以上** | 20px |
| 輪播卡片主文 | **40px 以上**（要從床上看得清楚） | — |

字級一律以相對單位定義並隨畫面寬度縮放，但**下限就是上表的數字，不得被縮到更小**。

### 4.3 觸控與點擊目標

| | 病人端 | 護理端 |
|---|---|---|
| 最小尺寸 | **64×64px** | 40×40px |
| 目標間距 | 至少 12px | 至少 8px |
| 手勢 | **只有「點一下」。** 無長按、無滑動、無雙擊 | 可有鍵盤快速鍵，但不得是唯一路徑 |

### 4.4 動態

- **病人端不做任何會自己動的裝飾。** 閒置輪播的換卡是功能，不是裝飾；除此之外不要有呼吸燈、不要有位移動畫
- 護理端的新通報可以有一次性的進場強調，**但不得持續閃爍到令人疲勞**——會被忽略的警示等於沒有警示
- 兩端都要尊重作業系統的「減少動態效果」設定

### 4.5 暗色與夜間

- 病人端已有夜間模式（晚班調暗），**調暗不得改變版面與字級**，只改亮度
- 護理端常駐總覽螢幕整夜開著，**要能調暗但仍看得清楚**；不得用降低字級的方式節省空間

## 5. 這份基準怎麼被持續使用

**這是最重要的一節，因為一次性的改版三個月後就會被稀釋回去。**

| 時機 | 要做什麼 |
|---|---|
| 動任何介面程式碼**之前** | 讀 `.claude/skills/hd-uiux/`（本文件的可執行版） |
| 新增一個畫面或元件 | 對照第 4 章的設計系統；找不到對應的語彙就**先在這裡補一條**，不要就地發明 |
| 改動導覽列 | 對照 3.3 的三條規則；主列超過 7 項要說明理由 |
| 提交前 | 跑介面檢查腳本（技術識別字串、對比度、觸控目標尺寸） |
| 每次迭代結束 | 用瀏覽器自動化在兩種畫面尺寸下截圖，人工看一遍 |

**允許使用外部設計知識庫與前端視覺工具**（使用者 2026-09-19 授權），但有兩條界線：

1. **不得引入任何指向院外網域的執行期相依**——字型、圖示、樣式表、分析工具一律自帶（FR-S07、零院外連線盤點會擋）
2. 外部設計系統只當**參考**，實際採用的語彙一律落在第 4 章，不直接把整套元件庫搬進來

## 6. 驗收清單

介面改動要能逐條回答，不能只說「看起來比較好了」。

### 6.1 病人端

- [ ] 求助區在所有畫面、所有狀態下的位置與尺寸完全相同
- [ ] 輪播進行中，**沒有任何一個字落在求助區裡**
- [ ] 內文字級 ≥ 20px，輪播主文 ≥ 40px
- [ ] 所有可點擊目標 ≥ 64×64px，間距 ≥ 12px
- [ ] 沒有長按、滑動、雙擊
- [ ] 每一個用顏色表示的狀態都有文字
- [ ] 內文對比度 ≥ 7:1
- [ ] 單手在畫面下半部可完成所有主線操作
- [ ] 夜間模式只改亮度，不改版面與字級

### 6.2 護理端

- [ ] 主列項次 ≤ 7，順序與 3.3 一致
- [ ] 待處理通報在進畫面 2 秒內看得出來
- [ ] **畫面上找不到任何需求編號、待確認編號、迭代編號、資料表或欄位名、列舉常數、開關識別字**
- [ ] 所有狀態都是中文
- [ ] 關閉的功能完全不出現入口，後端端點也擋下
- [ ] 破壞性動作有確認，日常動作沒有
- [ ] 內文對比度 ≥ 4.5:1

### 6.3 兩端共通

- [ ] 沒有任何指向院外網域的資源（字型、圖示、樣式表）
- [ ] 尊重作業系統的減少動態效果設定

## 6.4 這份基準落在程式碼的哪裡（0919 迭代 8 實作後補）

前面五章講的是規則，這一節講**規則現在住在哪一個檔案裡**。
下一個要改介面的人從這張表開始看，比從任何一章開始都快。

| 規則 | 落在哪 | 怎麼被擋住 |
|---|---|---|
| 4.1 顏色、4.2 字級、4.3 觸控 | `apps/patient-pwa/src/design-tokens.css`、`apps/nurse-pwa/src/design-tokens.css` | **色碼與字級只能出現在這兩個檔裡。** 樣式表裡出現任何裸色碼（含 `rgba()`）`npm run check:ui:design` 就會紅 |
| 4.1 對比度門檻 | 同上＋`scripts/check-ui-design.mjs` 的搭配清單 | 腳本直接從色碼算 WCAG 對比度。**半透明的顏色算不出來，所以一律不准用** |
| 2.2 求助區的版面契約 | `apps/patient-pwa/src/PatientShell.tsx` | `npm run verify:iteration8` 驗結構：兩列的 grid、輪播是 `absolute` 不是 `fixed`、求助按鈕規則裡沒有 `z-index`、求助按鈕只有一個出處 |
| N-5 破壞性動作的阻力 | `apps/nurse-pwa/src/components.tsx` 的 `ConfirmButton` | 驗收腳本檢查它有被用到，而且沒有人改用瀏覽器的 `confirm` |
| 4.5 常駐總覽螢幕的字級 | `--wall-scale`（護理端語彙） | 整面牆的字級相對這一個倍率。觀看距離確定後（Q-10）改一個數字 |

**新增一組顏色或一個字級時，順序是**：先在本文第 4 章補一條語彙 → 再加到 `design-tokens.css` →
若它是「某個字疊在某個底色上」，**回到 `scripts/check-ui-design.mjs` 的搭配清單補一列**。
漏掉第三步，那組顏色就沒有被任何人檢查過——腳本推不出來誰疊在誰上面，那份清單是人維護的契約。

**兩個刻意的決定，寫下來免得日後被當成疏漏：**

1. **常駐總覽螢幕斷線時的紅框仍然持續閃爍**，雖然 4.4 說「不得持續閃爍到令人疲勞」。
   那一條講的是**新通報的進場強調**——那種東西閃久了會被學會忽略。斷線不是通報，
   是一個持續存在的故障狀態：它一直在，示警就應該一直在。畫面上另有一條「連線中斷」的橫幅，
   顏色不是唯一線索；開了「減少動態效果」時閃爍會停，紅框仍然留著。
2. **病人端未指派時沒有求助區。** 平板還沒指派給任何人，求助送出去護理站不知道是誰按的。
   那個畫面改成直接寫「需要護理人員時，請按床邊的呼叫鈴」——
   **一顆按了會失敗的按鈕，比沒有按鈕更糟。**
