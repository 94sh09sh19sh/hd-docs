## 0. 本文件的定位

《透析中的遊戲化》（以下稱**上層文件**）是分析。這一份是它的子文件，記錄 1010 使用者對上層文件第 11 節的決定，以及之後幾段接續的分析與決定：

- 存檔、跟護理師互動、跟其他病人互動的**技術代價**（第 3 節），包括「存檔不能用 JSON」這條規定合不合理、開放要付出什麼（第 3.5 節）
- 送花送給誰、最低人數門檻（第 3.2、3.3 節）
- 花園種滿與清空：自己的花園開花之後、「一班」怎麼定義、共同花園的格數、每月歸檔與背景（第 3.6 節，1010 第三輪）
- 護理站會有幾個**功能開關**、各管什麼，以及全部關掉之後還剩下什麼（第 4 節）
- 實作順序、圖由誰畫、能不能挪用網路上的程式與素材（第 5 節）

**這一份仍然不是需求文件。** 1010 使用者指示「完成遊戲化」之後，第 6 節列的需求條文**已一次改齊**（SRS FR-P16～P19、FR-N19～N20、FR-S17 等，實作規格書迭代 20～23，《資料庫使用規範》第 19 條）；資料字典與介面設計基準跟著各迭代的程式改。與需求文件衝突時，以需求文件為準。

上層文件的章節編號在本文件寫成「上層 7.1」這種形式。

## 3. 技術代價

以目前的程式為基準（迭代 17.7）。範圍已經照第 1、2 節縮小：沒有暗棋，所以沒有對弈。

### 3.1 存檔

| 可以直接沿用的 | 要新做的 | 會卡的地方 |
|---|---|---|
| 病人端 `offline-queue.ts` 的做法：資料一律先寫進平板本機（IndexedDB）再送出，以 clientId 讓後端不重複寫入。目前只用在症狀回報 | 每款遊戲的存檔資料表，加上每一步的操作紀錄（狀態評估要用） | **平板上那份存檔只在這次療程內有用。** 綁定解除時平板要清掉本機資料（SRS 4.3 步驟 8，`device_bindings.device_cleared_at`），所以換平板接著玩完全靠伺服器 |
| | 每一步帶序號，斷線補送時伺服器照序號排，不會新舊顛倒 | **《資料庫使用規範》6.1 不以 JSON 承載。** 見第 3.5 節 |

**代價：中。** 大部分是存檔資料表的設計與序號處理；JSON 能不能用，會讓這一塊差上好幾張資料表。

### 3.2 跟護理師互動

| 功能 | 可以直接沿用的 | 要新做的 |
|---|---|---|
| 送花 | 護理站常駐總覽螢幕（FR-N12）與它的即時推送 | 總覽螢幕上「今天的花瓶」一小塊；送給誰見下方 |
| 護理師回貼圖或預設回覆 | 下一次療程才顯示，存起來、開療程時讀出來即可，**不需要即時推送** | 貼圖與預設回覆的清單；回覆以病人為準存，不以平板 |
| 病友小撇步 | 跑馬燈的核准流程（FR-N17）、長度上限 | 病人端「我也是這樣做的」與預設小撇步的選單；護理端核准清單多一種來源；署名只到「本中心病友」 |
| 共通 | 稽核軌跡 | 護理師送給病人的內容要不要記進稽核軌跡，比照現有的護理師操作 |

另外有一件不花程式、但要刻意做的事：**上層 H-13 規定不能變成工作**，所以護理端不能有未讀紅點、待辦清單、催促。

**代價：低～中。**

#### 送花送給誰（1010 決定）

**實際情況**：護理站除了一面常駐總覽螢幕，只有一兩台電腦是登入狀態，而且不會是每位護理師各自登入；醫院目前沒有規畫讓護理師隨身帶平板或手機。

| | A. 送給負責這一床的護理師 | **B. 送給護理站（照顧我的護理師們）** |
|---|---|---|
| 第 1 角：從被照顧的人變成給予的人 | 有 | 有 |
| 第 5 角：跟人有關 | 理論上較強，因為收花的是一個人 | 收花的是一群每次都在的人；病人多半不記得今天是哪一位負責 |
| 第 3 角：送出去有沒有回音 | **弱**：沒有個人裝置，那位護理師未必看得到。送給一個人卻沒被看見，比送給大家更傷 | **強**：花一定出現在總覽螢幕上；經過的護理師看到床號，可以走過去當面說謝謝，這是最好的回音 |
| 上層 H-13：不增加工作 | 容易變成「你看到某床送你的花了沒」的壓力 | 沒有指定給誰，沒有人欠誰一個回應 |
| 《資料庫使用規範》11.2 | **踩線**：「哪位護理師收到幾朵花」就是病人對特定護理師的評分，屬於明文禁止的「護理師×病人」交叉評分，也是要走 11.3 啟用流程的 L3 個人層級資料 | 只有護理站層級的數字，屬於 L1 單位聚合 |

**決定：B，送給護理站。** 規格：

- 病人端選好一朵花，按「送給照顧我的護理師們」，一下就好；送出後顯示「花已經放進護理站的花瓶了」
- 護理站總覽螢幕的角落有一塊「今天的花瓶」：花的圖加床號，新的一朵直接出現，不閃、不出聲；**有求助橫幅時讓位，求助永遠優先**；跨日清空
- 登入的電腦：病人詳細資訊那一格寫「今天送了一朵油桐花」。護理師可以（不是必須）回一句預設的「謝謝你的花」，走開關 2（護理師回貼圖）的同一條管道，病人下次療程看到
- 資料只記病人、療程、哪一種花、時間；**不記哪位護理師收到，也不做任何以護理師為單位的統計**。護理站層級的「這個月收到幾朵」可以有

### 3.3 跟其他病人互動（只有匿名的彙總）

| 可以直接沿用的 | 要新做的 | 會卡的地方 |
|---|---|---|
| `treatment_sessions` 有排班日期與班別，「今天這一班」算得出來 | 共同花園、今日牌局完成人數、共同記憶三種彙總的計算 | ~~**固定班別群組在資料模型裡沒有。** 共同花園要跨很多次療程累積，要的是「一三五早班」這種固定群組，現在只有「某天某班」~~ **1010 第三輪解掉**：病人的透析星期不一定是一三五或二四六，固定群組歸不了組；改成一班就是療程的班別（早／午／晚），不分星期，班別現成就有（第 3.6 節） |
| | 最低人數門檻（下方） | **人數少時匿名會破功。**「今天這一班有 1 個人家裡也有大同電鍋」，鄰床猜得出是誰 |

**代價：中。** 若將來做暗棋的非同步對弈，代價會跳到**高**：邀請與同意、輪流下棋的狀態、對方沒來或換床、離線補送，以及第一次把別人的資料畫到自己的平板上（隱私模型要擴大）。這些這次都不做。

#### 最低人數門檻（1010 決定）

前提：平板只有 15 台，一班有平板的人最多 15 位，某一款當天有玩的往往只有幾位。

| 規則 | 說明 |
|---|---|
| **人數句要「做到的 ≥ 3 人」，而且「沒做到的是 0 人或 ≥ 3 人」才顯示** | 2 人時，兩人都知道另一位做了什麼；3 是讓任何一個人都沒辦法被另一個人單獨認出來的最小數字。後半條是防反面：「9 個人玩、8 個人完成今日牌局」，那一位沒完成的就被凸顯了 |
| 分母是這一班今天開過這款遊戲的人 | 沒玩的人不算進「沒做到」 |
| 當天湊不到，改用這星期的累計，句子改成「這星期」；還是湊不到就不顯示 | 看不到這一句，遊戲照樣完整（上層 H-8） |
| 「想起某個人」永遠不做彙總 | 牽動情緒的回應，人數再多也不拿來說 |
| 共同花園不顯示人數，花也不標是誰種的 | 只看得到花。共同花園不另設門檻，人少的班照常顯示（第 3.6 節） |
| 兩個 3 都做成營運參數 | 試辦後可以調，但不得低於 3 |

### 3.4 狀態評估資料的調閱（第 2 節第 6 題衍生）

| 要新做的 | 說明 |
|---|---|
| 社工、醫師的角色 | 系統現有角色沒有這兩種。最小的做法是新增兩個角色，只能看病人詳細資訊與狀態評估彙整，不能操作臨床功能 |
| 調閱的稽核 | 比照現有病人資料的調閱 |
| 留存與同意 | 比照平板其他資料，寫進資料字典與資料庫使用規範，不另立一套 |

**代價：中。** 角色與權限是整個護理端都會碰到的地方，要連帶檢查每一頁的權限。

### 3.5 「不能用 JSON 存」這條規定

#### 出處與原文

《資料庫使用規範》6.1 第 2 條：

> **不使用 JSON 欄位承載結構化關聯資料** — 一律正規化成資料表與外鍵。SQLite 雖然有 `json_extract`，但用了就等於把查詢邏輯埋進方言裡。

這條是 0909 版為了「將來要遷到醫院的 MSSQL」而定的。0910 確定正式環境也用 SQLite 之後，6.1 開頭寫明理由改成「不要被任何一種資料庫綁死」，**優先權下降，但一條都不放寬**。同一份規範第 5 條另外規定 `json_extract` 這類 SQLite 專屬函式不得出現在業務邏輯。目前的 schema 全部遵守，好幾張表的註解都寫著「不以 JSON 承載」。

#### 它防的是什麼

| 理由 | 說明 | 合理嗎 |
|---|---|---|
| 不被資料庫綁死 | 要查 JSON 裡面，就得用各家資料庫自己的函式 | 合理 |
| 資料完整 | JSON 裡寫的病人編號、護理師編號沒有外鍵：病人被刪掉不會連帶處理，寫錯的編號也不會被擋下來 | 合理 |
| 查得到、對得起來 | 統計、對外報表（第 12 條）、稽核都要能逐欄查 | 合理 |
| 寫得進資料字典 | 資料字典逐欄寫「蒐集的意義」；一大包 JSON 寫不清楚裡面有什麼 | 合理 |

**對臨床、稽核、績效這類資料，這條規定完全合理，不該動。**

#### 套到遊戲存檔

遊戲存檔其實分兩種東西：

| | 盤面快照 | 每一步的紀錄與成果 |
|---|---|---|
| 是什麼 | 牌怎麼排、哪幾張消掉了、花園哪一格種什麼長到哪裡 | 點了哪裡、花了多久、完成了沒、開了什麼花、送了什麼花 |
| 用途 | **只用來「接著玩」**：整份讀出、整份寫回 | 狀態評估、彙總、統計 |
| 指向其他資料表嗎 | 不會（裡面只有牌碼、格子座標、成長階段） | 會（病人、療程） |
| 資料庫要查它裡面嗎 | 不用 | 要 |

條文管的是「結構化**關聯**資料」。盤面快照有結構、但不關聯，也從來不在資料庫裡查，是條文沒有寫清楚的灰色地帶。把它拆成欄位，拿到的保護（外鍵、可查）用不上，卻要付出代價：

- 麻將一桌最多 48 張牌就是 48 列，每次自動洗牌重寫全部；花園 12 格是 12 列；三款加起來多出五到八張表
- **遊戲規則每微調一次，就是一次資料庫遷移**，要過第 18 條的四道關卡（先備份並驗證還原、只能前滾、只做加法……）。像「花園從 3×4 改成 3×5」「連連看多一個難度旋鈕」這種小事，都變成正式環境的結構變更

每一步的紀錄與成果則**一定要正規化**，跟現在所有資料表一樣，這部分不受影響。

#### 開放的成本

建議的做法是**開一個窄例外**，不是放寬整條規定：

| 成本 | 內容 | 大小 |
|---|---|---|
| 文件 | 《資料庫使用規範》6.1 第 2 條補一段例外與界線（下方）；資料字典寫每款遊戲快照的格式與版本 | 低 |
| 程式：版本與驗證 | 快照多一個「格式版本」欄位；寫入前、讀出後都在應用層驗證格式；舊版快照的升級寫在程式裡，等於把一部分「遷移」的責任從資料庫搬到程式，**要有測試** | 中 |
| 程式：雙寫 | 狀態評估與彙總要用的東西，**一律另外寫成正規欄位**，不從快照裡挖。這條不守，例外遲早長成 JSON 查詢 | 低（本來就要寫） |
| 風險：被擴大解讀 | 下一次有人拿「遊戲可以，我這個也可以」開更多例外。靠界線條款擋 | 要靠審查守住 |

界線條款（寫進規範）：

1. 只限**遊戲盤面快照**，每位病人每款遊戲一列
2. 內容不得有病人識別資料、臨床數值，也不得有任何其他資料表的編號
3. 不得被任何資料表參照；資料庫裡不得以 `json_extract` 或任何方式查詢它的內容
4. 要有格式版本欄位，大小設上限（例如 16 KB）
5. 統計、評估、彙總要用的資料一律另存正規欄位

**比較**：不開例外，三款遊戲多五到八張表，每次規則微調都要遷移；開了例外，多一段規範條文與一套快照版本與驗證的程式。

**1010 使用者決定開窄例外**，已寫進《[資料庫使用規範](../requirements/database-policy.md)》6.1「第 2 條的唯一例外」一段（上面五條界線，再加一條「例外只此一處，不得自行類推」），第 16 條檢查清單與資料字典的共通約束也跟著補上。

### 3.6 花園種滿與清空（1010 第三輪決定）

小花園有兩種花園：每位病人**自己的花園**（3×4＝12 格，上層 7.5），以及同一班病人一起種的**共同花園**。自己的花園裡開好的花，可以送給護理站（第 3.2 節），也可以**種進共同花園**。本節說的「種花」指的都是後者，跟送花是兩件事。

原本的文件只寫了花瓶跨日清空、植物不枯不倒退、共同花園種滿時不出現院方要兌現什麼的字句；**種滿之後怎麼辦、花什麼時候離開花園，都沒有寫**。這一節補上。

#### 自己的花園

| 情況 | 做法 | 理由 |
|---|---|---|
| 花開了以後 | 一直留在那一格，**系統永遠不自動移走** | 上層第 8 角：不會失去 |
| 送給護理站，或種進共同花園 | 那一格變回空地，可以再種；圖鑑的紀錄留著 | 花園才有事可做；送出去的花在圖鑑裡也找得到 |
| 12 格都有植物，其中有開好的花 | 不提醒、不催；種子區旁邊安靜寫一句「花園滿了，可以把開好的花送出去或種到大家的花園，再種新的」 | 上層 H-13 不催促，同時不讓花園卡住 |

#### 「一班」怎麼定義

原本寫的是「固定班別群組」，例如一三五早班。但病人的透析星期不一定是一三五或二四六：有人一三六、有人一週兩次，也有人臨時改班，固定群組歸不了組。

| 做法 | 結果 |
|---|---|
| A. 替病人分組（看最近幾週多半在哪一組） | 一三六的人被硬塞進一組，週六種的花跑到週一的花園；換組時以前的花算哪裡要另訂規則 |
| B. 看種花那一次療程：星期單雙＋班別，共 6 片 | 不必分組，看到的是當天在場的人種的；週日的療程要另外歸類 |
| **C. 只看班別：早班、午班、晚班，共 3 片** | 不必分組、不必另訂；班別在 `treatment_sessions.shift` 現成就有 |

**決定：C。** 一班就是療程的班別，不分星期。每一朵花歸到**種下去那一次療程**的班別；病人改班，之後種的花就進新那一班的花園，以前種的不搬。今日牌局完成人數與共同記憶（FR-S17）的「這一班」照同一個定義：當天的同一班別，「這星期的累計」就是這星期同一班別的累計。

代價：週一早班的病人看得到週二早班病人種的花，「每次見面的那幾張臉」的感覺比 B 弱一點。換來的是規則只有一條，資料模型不必加群組。

#### 透析時段跨班的病人（實作要特別注意）

同一位病人這個月不一定都在同一班：例如一天早班、一天午班，或臨時改班。這種病人最容易寫出 bug，實作一律照下表：

| 情況 | 做法 | 不可以這樣做 |
|---|---|---|
| 判斷種進哪一班 | 用**當下這一次療程**的 `treatment_sessions.shift`，由伺服器依病人目前的療程查出 | 不可以用病人「平常的班別」、最近幾次最多的班別、平板或床位綁的班別，也不可以讓前端把班別傳上來 |
| 例：週一早班、週三午班 | 週一種的花進早班花園，週三種的花進午班花園 | 不可以把週三那朵也種進早班花園，或把週一那朵搬到午班 |
| 種下之後 | 花永遠留在種下去的那一座，改班不搬、不複製 | 不可以依病人現在的班別重新歸類以前種的花 |
| 當月開放中的花園 | 只顯示**當下這一次療程那一班**的花園，可以看、可以種；其他班當月的花園不顯示 | 不可以在午班療程裡顯示或種進早班當月的花園 |
| 種滿的提示 | 「這個月○班的花園種滿了」的○班是當下這一次療程的班別 | 不可以寫成病人平常的班別 |
| 圖鑑「我們的花園」 | 列出這位病人那個月**所有透析過的班別**的歸檔，例如早班、午班兩座都列 | 不可以只列一班，也不可以只看那個月最後一次療程的班別 |

驗收要有一位一個月內跨早班與午班的測試病人，上面每一列都要測到。

#### 共同花園的格數

每一班每個月一片花園。**這個月種滿了就不能再種**，下個月依這個月的情形調整格數：

| 這個月歸檔時 | 下個月的總格數 |
|---|---|
| 全部種滿 | 這個月格數的 1.5 倍 |
| 種下的不到一半 | 這個月種下的格數的 1.5 倍，但不少於起始格數 |
| 其他 | 不變 |

- 起始 12 格，跟自己的花園一樣大
- 格數一律**向上取到 6 的倍數**，才排得成整齊的格子
- **一座花園最多 24 格**：橫放 4 列 × 6 格、直放 6 列 × 4 格；每格至少 96×96px、間距 12px，比觸控下限 64px（介面設計基準 4.3）大，是為了讓植物插畫看得清楚；在 1280×800 與 800×1280 都不捲動。總格數超過 24 就**分成幾座**，每座平均分（同樣取到 6 的倍數，所以總數可能比算出來的略多），避免格子太密太小
- 有好幾座時，花園畫面用「上一座／下一座」翻，一次只看一座（上層 H-2：選項一次不超過 3～4 個）
- 這個月種滿時，病人按「種到大家的花園」會看到「這個月早班的花園種滿了，下個月會多一些位置」，花留在自己的花園。這句話**系統自己兌現得了**（下個月一定變大），不涉及院方承諾（第 2 節第 3 題）
- 起始格數（12）、一座上限（24）、縮減門檻（一半）是營運參數。一座上限不得超過介面設計基準算得出來的上限；24 是暫定，迭代 21 在目標平板截圖驗收時確認。**1010 迭代 21 確認**：1280×800 一座 24 格每格約 106px、800×1280 約 140px；橫放第 5 列會讓每格掉到 96px 以下，所以上限就是 24（營運參數的最大值也設成 24）

例：早班第一個月 12 格種滿 → 第二個月 18 格，又種滿 → 第三個月算出 27，超過 24，分兩座、各 18 格（共 36）→ 第三個月只種了 14 格，不到一半 → 第四個月算出 21，取到 24，一座。

#### 每月歸檔與背景

| 事情 | 做法 |
|---|---|
| 什麼時候清 | 每個月 1 日起（伺服器所在地時間），上個月的花園**歸檔**，開一片新的。不是刪掉：花跟著歸檔留下，圖鑑裡看得到 |
| 看得到哪些歸檔 | 圖鑑多一頁「我們的花園」，列出這位病人**那個月透析過的班別**的歸檔，新的在前；只能看、不能種。有好幾座的月份一樣用「上一座／下一座」翻 |
| 那個月沒人種 | 不歸檔，不留空白的花園 |
| 背景 | 每個月一張，**兩年一輪，共 24 張**：同一個月份的兩張季節相同、畫面不同。歸檔的花園保留它那個月的背景 |
| 背景誰畫 | 跟植物插畫一樣由 AI 畫，列進植物分析子文件（第 5.2 節）：寫實雅致、不用紅色、不畫人，顏色要退在植物後面 |

#### 匿名：不另外處理

| 規則 | 說明 |
|---|---|
| 種下去**馬上出現** | 自己當下就看得到；別人下一次點開花園就看得到，不必即時推送。**不延到下一次療程** |
| 不顯示人數、不標誰種的 | 只看得到花（第 3.3 節原本就有） |
| 不另設門檻 | 人少的班（例如晚班）照常顯示。第 3.3 節的最低人數門檻不變，它管的是「幾個人做了什麼」這種句子，共同花園沒有這種句子 |
| 斷線時 | 共同花園只能看、不能種，花留在自己的花園，連上之後再種。格數有限，種下去要由伺服器確認那一格還空著 |
| 兩個人同時點同一格 | 後到的那一位看到「這一格剛剛有人種了，換一格吧」，花還在自己手上 |

#### 資料

共同花園**不用盤面快照**（第 3.5 節的例外只限每位病人每款遊戲一列），照一般規矩正規化：

- `shared_gardens`：班別、年月、第幾座、格數、背景代號、狀態（開放中／已歸檔）、歸檔時間
- `shared_garden_plots`：哪一座、第幾格、花的代號、種下時間。**沒有病人欄位**；誰種的只記在每一步的操作紀錄（`game_events`），跟其他遊戲操作一樣，畫面上不出現
- 歸檔不刪，留存比照平板其他資料（《資料庫使用規範》第 19 條）

共同花園歸開關 5（病人之間的互動），但花從自己的花園來，所以**開關 3 也開著才出現**。

## 4. 功能開關

### 4.1 九個開關

照 FR-S08 的做法；切換要有 `FEATURE_FLAG_MANAGE` 權限，開和關都要登記理由，每次切換寫進稽核軌跡。**除了開關 9，全部預設關閉。**

| # | 開關 | 管什麼 | 預設 | 實作階段 |
|---|---|---|---|---|
| 1 | 病友小撇步 | 病人端看完衛教後的「我也是這樣做的」與分享選單；護理端核准清單裡的小撇步來源。關掉時已核准上架的照樣播完 | 關 | 1 |
| 2 | 護理師回貼圖 | 護理端對心情問卷「想讓我們知道的事」回貼圖或預設回覆，以及對送花回「謝謝你的花」；病人端下一次療程開始時顯示 | 關 | 1 |
| 3 | 透析小花園 | 花園本身；問卷、衛教、遊戲做完給養分；**連動開關 4** | 關 | 2 |
| 4 | 送花 | 病人送花給護理站；總覽螢幕的「今天的花瓶」；病人詳細資訊那一行 | 關 | 2 |
| 5 | 病人之間的互動 | 三種匿名彙總：共同花園（開關 3 也開著才出現，第 3.6 節）、今日牌局完成人數、共同記憶 | 關 | 2 |
| 6 | 麻將連連看 | 一般牌局與今日牌局 | 關 | 3 |
| 7 | 狀態評估彙整（護理端顯示） | 護理端看不看得到由遊戲資料整理出的趨勢陳述（上層 9.2）。**關掉時資料照樣記錄**，只是不顯示 | 關 | 3 |
| 8 | 老台灣記憶相簿 | 相簿本身，加上護理端病人詳細資訊那格「回應主題」聊天話題 | 關 | 4 |
| 9 | **現有功能的小幅遊戲化** | 問卷送出後的那一句話、任務完成記號、我的衛教小本子、跑馬燈的「你知道嗎」（第 4.3 節） | **開** | 1 |

不建立的開關：換位拼圖、暗棋（不做）、里程碑卡（第 7 題不做）。

**開關 9 預設開啟**是 FR-S08「預設全關」的第二個例外。第一個例外是「本次透析」面板，理由一樣：只呈現、不碰臨床判讀、不碰隱私、不增加護理師的工作。

### 4.2 送花與小花園的連動

| 動作 | 結果 |
|---|---|
| 開小花園 | 送花**跟著開** |
| 關小花園 | 送花**跟著關** |
| 小花園開著，關送花 | 只關送花，花園照常 |
| 小花園關著，開送花 | **不允許**：送花的前提是有花園。開關中心顯示「要先開透析小花園」 |

一個後果要知道：小花園關了再開，送花會跟著重新開啟。若院方只想要花園、不要送花，每次開小花園之後要再關一次送花。

實作上，現有的開關中心已經有「開啟前提」的檢查（`feature-flags.service.ts` 的 `judge`），「要先開小花園」可以直接用它；**「跟著開、跟著關」的連動是新的行為**。連動造成的那一次切換也寫進稽核軌跡，理由記成「隨透析小花園開啟（或關閉）」。

### 4.3 開關 9 管的四樣

原本（1010 第一輪）判斷這四樣不必設開關；第二輪改成由開關 9 一起管，讓九個全關時可以關乾淨。

| 功能 | 上層出處 | 關掉時 |
|---|---|---|
| 問卷送出後的那一句話 | 4.3 | 回到現在的送出畫面 |
| 任務完成記號 | 4.4 | 回到現在的完成畫面。給小花園養分的事歸開關 3，不受影響：開關 9 關、開關 3 開時，養分照給，只是在花園裡才看得到 |
| 我的衛教小本子 | 4.4、4.6 | 入口與小本子都不出現；已經亮起的主題照樣記著，再開時還在。**入口放在結束衛教做完的畫面**（「翻我的小本子」），遊戲圖示出現時遊戲選單裡也放一份；**首頁不放**（FR-P14） |
| 跑馬燈的「你知道嗎」 | 4.9 | 護理端不能再新增這一類，已上架的停播 |

### 4.4 九個全關之後還剩什麼

## 5. 實作順序

### 5.1 四個階段

| 階段 | 做什麼 | 開關 | 先決條件 |
|---|---|---|---|
| **1 平板現有功能的遊戲化** | 問卷送出後的一句話、任務完成記號、我的衛教小本子、跑馬燈的「你知道嗎」、病友小撇步、護理師回貼圖 | 9、1、2 | 改 FR-P08、FR-N17、FR-S08 等條文（第 6 節） |
| **2 透析小花園** | 遊戲圖示與遊戲框（沿用 `TaskFrame`）；存檔機制（第 3.1 節）；花園、圖鑑、養分接上階段 1 的完成事件；送花與總覽螢幕的花瓶；最低人數門檻；共同花園（一班就是班別、每月歸檔、格數調整，第 3.6 節） | 3、4、5 | 植物分析子文件與插畫（第 5.2 節）；存檔照 JSON 例外的界線設計（第 3.5 節） |
| **3 麻將連連看** | 牌局、連線規則、自動洗牌、今日牌局與完成人數；每一步的操作紀錄；護理端的狀態評估彙整；社工與醫師的角色 | 6、7 | 牌面（第 5.3 節） |
| **4 老台灣記憶相簿** | 相簿、共同記憶、護理端聊天話題 | 8 | 主題篩選子文件、圖（第 5.2 節） |

換位拼圖、暗棋先不做。

**1010：四個階段對到迭代 20～23**（實作規格書 4.0.5、4.20～4.23），排在迭代 18、19 之後。

**為什麼這個順序**：上層 4.11 指出，第 1、3、5 角大多落在現有功能，**不必等遊戲就能先開始心理支援**；小花園是把其他功能串起來的骨幹，要在另外兩款之前，養分才有地方去；連連看程式量低、資料最乾淨，順便把狀態評估的資料管線做起來；相簿內容量最大，要等主題篩選與繪圖兩件前置工作。

### 5.2 圖由誰畫：兩份分析子文件與繪圖子任務

相簿的圖與小花園的植物插畫，都由 AI（Claude）在實作時畫，**畫之前各先寫一份分析子文件**，掛在上層文件底下。

| | 老台灣記憶相簿（第 8、9 題） | 透析小花園（1010 第二輪） |
|---|---|---|
| 子文件要判斷的 | 主題分類（上層 7.1 的飲食、交通、家庭、遊戲、節慶、工作，可增減）與每類要畫哪些物件；要避開的題材（創傷、政治、戰爭、重大歷史事件、選舉）與「可能讓人難過」的判斷準則；「這是什麼？」的選項與說明文字寫法 | 要種哪些花（台灣原生與常見花卉、節令花）與分類；**要避開的花**：有喪葬聯想的（例如白菊）、花語不吉利的、會讓人聯想到病或毒的——花會被送進護理站，不能送出會被誤會的花；每種花畫幾個成長階段（種子、芽、苗、花苞、開花）；三種種子怎麼配；**共同花園的 24 張月份背景**（兩年一輪，第 3.6 節） |

### 5.4 挪用網路上的程式：規則與安全

三款遊戲若 GitHub 上有可以無條件挪用的程式，可以直接拿來改。

**什麼算「無條件」**：

| 授權 | 算不算 |
|---|---|
| CC0、Unlicense、0BSD、明示放棄著作權（public domain） | **算**，可以直接用 |
| MIT、BSD、Apache 2.0 | **不算**：要保留授權聲明，是有條件的。遇到時另外問使用者 |
| GPL、LGPL 等 | 不算：會要求整個專案跟著開放原始碼 |
| 沒有寫授權 | 不算：沒寫就是保留所有權利 |

**1011 迭代 22**：牌面照上表放進病人端（`assets/mahjong-tiles/`，釘 commit `26e127b`，來源、授權全文、改了什麼寫在同目錄的 `SOURCE.md`）；紅色（含筒子、條子上的紅點）一律改深棕，白板的原檔是空白牌、改畫藍框。**程式沒有挪用**：連線判定、保證有解的發牌、重排都自己寫（`@hd/shared` 的 `mahjong.ts`），理由同下段「整套挪過來改，常常比自己寫還費工」。

**1010 初步搜尋的結果**：以 Unlicense、CC0、0BSD 搜「shisen-sho」「mahjong connect」「onet」（連連看的幾種英文叫法）都沒有結果；有一套 Unlicense 的麻將遊戲 tcottrill/myMahjong，但它是多層疊放的麻將接龍，正是上層 6.4 不選的那一種。小花園與相簿的搜尋碰到 GitHub 的查詢次數上限，**沒有查完**，實作開始時要再查一次。（**1010 迭代 21、1011 迭代 23.1**：小花園與相簿的圖都自己畫，沒有挪用任何素材，這次搜尋因此不必再做。）

**實際上能挪用的多半只是片段**：這三款的程式核心很小（連連看是「最多轉兩個彎」的路徑判定、保證有解的發牌、無解時重排；小花園是依療程次數成長的狀態），而上層的硬性限制（只能點、不計時、無聲、不用紅色、只鋪一層、每一步存到伺服器）跟一般遊戲差很多。**整套挪過來改，常常比自己寫還費工**；比較划算的是挪路徑判定、發牌這類程式片段，以及素材。

**安全規則**（挪用任何程式或素材都適用）：

1. **整份讀過才放進來**，釘在特定 commit；把網址、commit、授權全文跟程式放在一起，資料字典或實作規格書記一筆來源
2. **複製進專案，不用套件管理器在執行期裝進來**；不帶進任何安裝時會執行的指令碼；若帶進相依套件，照常跑弱點檢查
3. **拿掉所有對外連線**：分析、廣告、外部字型、更新檢查、回報。病人端本來就不得連向院外（SRS 第 6 章），照現有的內容安全政策
4. 拿掉 `eval`、`new Function`、把外來字串塞進 `innerHTML`、動態載入腳本這類寫法
5. 拿掉音效檔與震動（上層 H-3）、計時器、排行榜、內購
6. **SVG 圖檔也要清**：SVG 裡可以藏腳本、事件屬性與外部參照，放進來前全部清掉
7. 改完照常做程式審查、跑既有測試
8. 素材若事後發現授權有問題，直接換掉；存檔只存牌碼不存圖，換圖不影響任何人的存檔
