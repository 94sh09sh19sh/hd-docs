## 1. 問題：SSE 繞過了推播，但繞不過 MDM

SRS 第 10 章定下「所有資料不得離開醫院網路」，因此推播整條移除，即時通知改用院內 SSE 長連線（FR-S07）。這一步是成立的——護理端與病人端都在院內網段，長連線從頭到尾不出院。

但 MDM 是另一條**完全獨立**的控制通道，SSE 蓋不到它。原規劃的 Android Enterprise 在三個地方必須連外：

| 情境 | 為什麼連外 |
|---|---|
| 平板首次佈建 | 需連 Google 下載 Android Device Policy 並註冊 Managed Google Play |
| 後端設定裝置政策 | 伺服器要呼叫 `googleapis.com`，直接違反 SRS 10.2「無任何主動連向院外的元件」 |
| 遠端鎖定即時生效 | 命令靠 FCM 送達裝置——**就是被移除的那個推播** |

也就是說，只要採用 Android Enterprise，「全程院內」這個前提就不成立。

## 2. MDM 在本系統實際做了哪五件事

盤點目前 `MockMdmProvider` 提供的能力，逐項檢查是否真的需要作業系統層權限：

| MDM 做的事 | 需要作業系統權限嗎 | 說明 |
|---|---|---|
| 納管狀態作為「可指派」的前提 | 否 | 純粹是資料庫的一個布林值，已經是應用層邏輯 |
| 設定 Kiosk 網址 | 否 | 佈建時用一次 |
| 遠端鎖定 | 否 | FR-P01 中性等待畫面加上解除綁定清除本地暫存，效果等價 |
| 螢幕保持亮著（FR-N12 常駐總覽螢幕） | 否 | 網頁的 Wake Lock API 或 Android 的 `FLAG_KEEP_SCREEN_ON` 都能做到 |
| **防止病人跳出這個應用程式** | **是** | 唯一一項 |

**五件事裡只有最後一件需要作業系統權限。** 前四件早已在應用層完成或可在應用層完成，跟 MDM 沒有關係。

## 3. 選型：這其實是兩層決策

最容易混淆的地方，是把「網頁用什麼技術做」跟「這個網頁裝在什麼容器裡跑」當成同一題。它們是兩層，各自獨立：

| 層 | 在問什麼 | 選項 |
|---|---|---|
| 第一層 | 病人端的內容用什麼技術做 | 原生 App／純網頁／**PWA** |
| 第二層 | 這個 PWA 由誰負責載入與顯示 | Chrome／**自包 WebView App**／Device Owner App |

**選了 PWA，不代表就得用 Chrome 開。** 下面兩節分別交代。

### 3.1 第一層：為什麼是 PWA，不是原生 App 也不是純網頁

沿用《FDE 數位化評估報告》7.1 的結論，此處補上與另外兩個選項的直接對照。

| | 原生 App | 純網頁 | **PWA（採用）** |
|---|---|---|---|
| 網路斷線時 | 可運作 | **整個畫面掛掉，求助按鈕按不了** | 可運作（離線快取＋本地暫存） |
| 內容更新 | 逐台重裝 15 次 | 改伺服器 | 改伺服器 |
| 與護理端共用 API 層 | 不行，等於兩套程式碼 | 可以 | 可以 |
| 迭代速度 | 慢，不合 FDE 工作型態 | 快 | 快 |

**排除純網頁的關鍵是離線。** 透析區 Wi-Fi 覆蓋尚未確認（Q-12），若網路一斷病人連求助按鈕都按不了，這在臨床場域不可接受。純網頁沒有離線能力，PWA 有——這正是 PWA 相對於純網頁**唯一但決定性**的差別。

**排除原生 App 的關鍵是更新成本與共用 API 層。** 護理端已經是網頁，病人端若走原生就變成兩套程式碼、兩套發版流程。升級為原生（或 Flutter 混合式）的觸發條件不變，仍是「要做透析機台資料直接整合」——那需要藍牙或串列埠，網頁碰不到。目前不做這件事。

附帶一提，0909 版曾把「具備推播通知能力」列為選 PWA 的理由之一，該項已因不做推播而失效，不再計入。

### 3.2 第二層：為什麼是自包 WebView App，不是 Chrome 也不是 Device Owner

三個容器的差別只在一句話：**誰能決定信任哪張憑證、誰能決定 App 的行為邊界。**

| | A：Chrome 開 PWA | **B：自包 WebView App（採用）** | C：Device Owner App |
|---|---|---|---|
| 要寫什麼 | 什麼都不用 | 一個 WebView 外殼 | 外殼＋裝置管理邏輯 |
| 開發成本 | 0 | **1～2 天** | 2～3 週 |
| Kiosk 靠什麼 | 螢幕固定 | **螢幕固定（與 A 相同）** | 作業系統強制鎖定 |
| 憑證 | 只能走公開網域加 DNS-01 | **自簽 CA 打包進 APK** | 自簽 CA 或 `installCaCert()` |
| 佈建誰做 | 護理師 | 護理師 | 需還原原廠，由資訊室走 QR 流程 |

**為什麼不選 A（Chrome）**——四個理由，第一個最重：

1. **憑證。** Chrome 環境下唯一乾淨的做法是取得公開網域加 DNS-01 驗證，等於為了一套純院內系統去養一個對外網域，外加每 90 天更新一次的例行負擔。這與「全程院內」的精神相斥，也多了一項要院方核准的外部相依。改用自簽則 Chrome 會顯示連線不安全，且**憑證有誤的來源會被完全停用 Service Worker**，離線能力（3.1 選 PWA 的唯一理由）當場消失
2. **安裝性。** A 要靠 Chrome 的「安裝到主畫面」，那有一串條件要滿足；B 的 APK 本身就是 App，這個問題整個不存在
3. **可控性。** 長按選字、右鍵選單、下載、分頁這些在 Chrome 裡關不乾淨，在自己的 WebView 裡一次關掉
4. **版本漂移。** Chrome 會自行更新且 15 台未必同步，介面與行為可能在你不知情時改變；B 的行為由你的 App 設定決定

**為什麼不選 C（Device Owner）**：

C 比 B 多出來的只有兩件事——作業系統層強制鎖定，以及重新開機後不必重釘。為此要付兩三週開發、15 台實機測試，而且 Device Owner **只能在尚無任何帳號的裝置上設定**，測試失誤就得還原原廠重來。B 的開機自動啟動（4.2）已經吃掉重開機那件事的一半痛苦：App 會自己起來，護理師只需要重釘螢幕固定。

**C 的重新評估觸發條件**：平板數量成長到數十台以上、或出現螢幕固定被規避的實際事件而交班檢查無法解決時。

## 4. 採用方案的內容

### 4.1 Kiosk 鎖定用 Android 內建的螢幕固定

Android 5.0 起內建：設定 → 安全性 → 螢幕固定，開啟並勾選「解除固定前要求 PIN」。之後把 App 釘住，病人退不出去，解除需要輸入只有護理師知道的 PIN。

不需要 MDM、不需要 Google 帳號、不需要任何對外連線。

### 4.2 WebView 外殼要做的事

| 要做的 | 怎麼做 |
|---|---|
| 全螢幕沉浸模式 | `WindowInsetsController` 隱藏狀態列與導覽列 |
| 螢幕恆亮（FR-N12） | `FLAG_KEEP_SCREEN_ON`，比網頁的 Wake Lock API 可靠 |
| 開機自動啟動 | 監聽 `BOOT_COMPLETED`，減輕重新開機後的復原工作 |
| 允許本地儲存 | `setDomStorageEnabled(true)`，IndexedDB 的離線暫存靠它 |
| 關掉長按選字 | `setOnLongClickListener` 回傳 `true` |
| 關掉縮放 | `setSupportZoom(false)` |
| 擋掉外部連結 | `shouldOverrideUrlLoading` 只放行自家網域 |
| 信任院內憑證 | `network_security_config.xml` 釘住自簽 CA，見 4.3 |
| 裝置身分 | 序號與金鑰存在 App 私有儲存，取代現行的一次性佈建網址 |

### 4.3 憑證：自簽 CA 打包進 APK

自建一個 CA，把根憑證放進 APK 的資源檔，宣告成這個網域的信任錨點：

```xml
<domain-config>
  <domain includeSubdomains="true">hd.院內網域</domain>
  <trust-anchors>
    <certificates src="@raw/hosp_ca" />
  </trust-anchors>
</domain-config>
```

TLS 正常驗證、沒有警告、Service Worker 正常運作。**不必購買網域、不必每 90 天更新、不必碰任何一台平板的信任設定。**

這裡要區分兩種把 CA 弄上裝置的方式，它們的寫法不同：

| 方式 | 憑證放哪 | 設定寫法 | 本方案 |
|---|---|---|---|
| 打包進 APK | App 自己的資源檔，裝置不知情 | `src="@raw/hosp_ca"` | **採用** |
| 手動安裝到裝置 | Android 的使用者信任存放區 | `src="user"` | 不採用，要逐台手動裝且到期要重來 |

（Android 7 起，使用者手動安裝的 CA 預設不被應用程式信任，這是第二種方式需要明寫 `src="user"` 的原因。第一種方式不受此限。）

### 4.4 逸出偵測：讓它看得見，而不是防得住

螢幕固定唯一守不住的是「有人解開了而護理師不知道」。這一點不必靠作業系統強制：

平板端每 30 秒回報一次「我還在前景」，並監聽 `visibilitychange`，一離開前景就立刻回報。護理端的裝置清單直接顯示哪一台跳出了 Kiosk。

**把「用作業系統權限預防」換成「用既有連線偵測並讓護理師看見」**，與求助、症狀回報是同一個模式，不新增任何架構。

**0920 實作時的一處修正**：本節原本寫「走既有的 SSE」。實際做法是平板以既有的裝置驗證
`POST /api/device/foreground`，護理端那一頁每 15 秒重新取得一次清單——**不經 SSE**。
原因是 SSE 那條長連線是給護理端訂閱用的，平板端從來沒有訂閱它；為了逸出偵測讓平板也接一條
長連線，等於為一件每 30 秒一筆的小事多養一條連線。兩者相加，跳出到護理端看得見最長 30 秒，
與原定的要求一致。

## 5. 前置條件

以下五項在第一次部署前必須完成，缺任何一項這條路線都走不完整。
**0920（迭代 10）更新現況欄：前兩項已完成，後三項要在部署當天做。**

| 前置條件 | 現況 | 為什麼是前置條件 |
|---|---|---|
| **Service Worker** | **0920 完成** | 3.1 選 PWA 而非純網頁的唯一理由就是離線能力，而離線快取靠它。`offline-queue.ts` 的 IndexedDB 暫存是另一回事，只存得住待送出的資料，存不住畫面本身。<br>做法：建置時由 `apps/patient-pwa/vite.config.ts` 的外掛把產物清單填進 `sw-template.js`，不引入任何外部相依。畫面走網路優先、逾時退回快取（平板靠「下次開啟就是新版」更新，快取優先會讓新版晚一個療程）；**`/api/` 一律不快取**——快取裡出現病人資料，等於把資料留在平板上 |
| **圖示資產** | **0920 完成** | 走本路線後，圖示不再是「能不能安裝到主畫面」的條件（APK 本身就是 App），但仍需要一張圖當 APK 的啟動圖示。<br>做法：`npm run assets:icons` 由腳本產生（192／512／512 maskable／1024），顏色取自病人端的設計語彙。**做成腳本而不是把圖檔丟進 repo**，是為了讓「它是怎麼來的、顏色跟誰對齊」留得住 |
| **自簽 CA 與伺服器憑證** | **0927 改由 `shell-builder` 在主機上產生**（迭代 12；原 `npm run cert:hospital-ca` 已移除），病人端以它提供 HTTPS | 4.3 的基礎。根憑證有效期設 10 年，免得日後頻繁重發 APK。`npm run cert:hospital-ca -- --host <院內主機> --ip <院內 IP>` 產生 CA 與伺服器憑證；**主體別名要涵蓋平板實際連的位址**，且腳本不會覆蓋既有的 CA |
| **APK 簽名金鑰（keystore）** | **0927 改由 `shell-builder` 在主機上產生**，開發機與院內各一把，`keys-backup` 備份、`keys-verify` 核對 | **遺失就再也發不出更新版**，只能換套件名重新側載 15 台。建立後立即異地備份，並記錄在交接文件 |
| **平板允許側載** | 未確認 | 需開啟「允許安裝不明來源應用程式」。屬院方設備政策，見 Q-11 |

另外，`manifest.webmanifest` 目前的 `display` 是 `fullscreen`，這一項已經是對的，不需要改。

## 6. 選這條路線之後，實際要做哪些工作

### 6.1 第一次部署

伺服器端（做一次）：

1. 產生自簽 CA 與伺服器憑證，CA 根憑證交給 App 打包
2. 安裝並啟動系統（依《[部署規範](../requirements/deployment-spec.md)》，**0919 起是 Windows 主機上的離線安裝包，不是容器**），掛上憑證
3. 匯入 15 台裝置清單，產生各台的序號與金鑰

> **0919 補充：憑證裡的名稱要對得上。** 自簽憑證的主體別名必須涵蓋平板實際連的那個位址。主機換成 Windows 工作站之後，這個位址多半是院內網段的一個固定 IP 或院內 DNS 名稱——**兩者擇一之後就不要再換**，換了要重簽伺服器憑證；若連 CA 都換，15 台都要重發 APK。

平板端（**每台各做一次**，15 次；**0919：首波試用只先佈建實際會用到的兩三台**，跑完一個班次沒問題再做其餘，見 DEP-36）：

1. 設定裝置 PIN，關閉「新增使用者」
2. 開啟「允許安裝不明來源應用程式」
3. 側載 APK
4. 首次啟動，輸入或掃描該台的序號與金鑰
5. 設定 → 安全性 → 開啟螢幕固定，勾選「解除固定前要求 PIN」
6. 開啟 App 並釘住
7. 記錄序號與床號的對應，核對護理端裝置清單

### 6.2 版本迭代

**關鍵在於分辨改的是網頁還是外殼**，兩者成本差 15 倍：

| 改了什麼 | 要做什麼 | 頻率 |
|---|---|---|
| **只改網頁**（絕大多數情況） | 部署伺服器，15 台下次載入就是新版。**完全不必碰平板** | 高 |
| 改 WebView 外殼（設定、權限、套件版本） | 重新編譯簽名 APK，逐台側載 15 次 | 低，應盡量批次累積後一次處理 |
| 換伺服器憑證 | 只換伺服器端。CA 沒變，**平板不受影響** | 1～2 年一次 |
| 換 CA 根憑證 | 重發 APK，逐台側載 15 次 | 10 年一次 |

外殼改版與 CA 更換都要排在非透析時段，並事先與護理長確認班次。

### 6.3 例行性工作

| 週期 | 工作 |
|---|---|
| 每月 | 檢視逸出偵測紀錄，找出經常跳出 Kiosk 的平板與原因 |
| 每季 | 清點 15 台實體、檢查電池健康度與螢幕狀況 |
| 每年 | 確認伺服器憑證到期日；驗證 keystore 備份仍可用（**只備份不驗證等於沒備份**） |
| CA 到期前一年 | 啟動重簽與 APK 重發的規劃 |

### 6.4 每日工作

由護理師執行，應納入交班檢查表：

1. **前一天有重新開機的平板要重新釘選。** App 會因開機自動啟動而自己起來，但螢幕固定不會自動恢復，需人工再釘一次
2. 交班時確認 15 台都在 Kiosk 狀態——**不必逐台目視，護理端總覽看得到**（4.4）
3. 治療結束照既有流程解除綁定，系統自動清除該台本地暫存

## 7. 守不住什麼

| 破口 | 影響與處置 |
|---|---|
| 重新開機後螢幕固定會解除 | App 自動啟動，但需人工重釘。已列入 6.4 每日工作 |
| 病人解開固定而護理師不知情 | 由 4.4 的逸出偵測補上，改為可見而非可防 |
| 還原原廠設定、更改 Wi-Fi 設定 | 擋不住。屬物理接觸風險，透析治療區全程有護理師在場 |
| keystore 遺失 | **無法補救**，只能換套件名重新側載 15 台。靠第 5 章的備份與 6.3 的年度驗證防範 |
| 平板的 WebView 版本凍結 | 離線環境無法更新 WebView。屬已知取捨，伴隨零連外一起接受 |

## 8. 對現有程式碼與文件的影響

### 8.1 程式碼

`MdmProviderPort` 介面**不需要任何改動**。`MockMdmProvider` 保留，但語意改變：

- 改動前：模擬真實 MDM 的控制行為，等待換成 `AndroidEnterpriseProvider`
- 改動後：**裝置佈建狀態的紀錄與稽核**，本來就不需要控制實體硬體

因此稽核說明欄的 `[mock]` 前綴應移除——它已經不是模擬品，而是這項功能的正式實作。

需要新增的：第 5 章的 Service Worker 與圖示、4.4 的前景回報端點與護理端總覽欄位，以及一個新的 Android 外殼專案。

**0920（迭代 10）全部完成**：

| 要做的 | 落在哪裡 |
|---|---|
| Service Worker 與圖示 | `apps/patient-pwa/sw-template.js`、`scripts/generate-icons.mjs` |
| 前景回報端點 | `POST /api/device/foreground`（走既有的裝置驗證）。每 30 秒一次，離開前景立刻一次 |
| 護理端的欄位 | 裝置清單多一欄「固定狀態」，四種狀態：固定中／已跳出／失去回報／尚未回報 |
| 外殼 App | `apps/kiosk-shell/`（獨立的 Android 專案，不進本 repo 的建置流程；README 寫的是兩邊的契約） |
| 稽核 | **只記轉折點**。15 台每 30 秒一筆，一天四萬多筆會把稽核軌跡淹掉；要回答的問題是「哪一台什麼時候跳出去的」，答案只在轉折點上 |

**「已跳出」與「失去回報」刻意分成兩種狀態**：前者是平板說的，後者是它不說話。
護理師要做的事不同——前者去把螢幕固定重新釘回來，後者去看看那台平板還在不在。
「尚未回報」則是外殼 App 還沒裝，不是故障。
