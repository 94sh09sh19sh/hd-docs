# 平板管控：免 MDM 的全院內方案

版本：v0.1　文件狀態：草案　適用讀者：FDE 工程團隊、醫院資訊室

## 0. 本文件的定位

本文件不是需求文件，是一份**技術方案評估**，記錄「15 台病人端平板要怎麼管」這一題在 2026-09-19 的結論與理由。

- 功能需求來源是《[軟體需求規格書](../requirements/srs.md)》FR-S01、FR-S07、FR-N12
- 介面層設計的出處是《[實作規格書](../requirements/implementation-spec.md)》3.3 節
- 待確認事項一律指回《[尚待確認事項清冊](../requirements/open-questions.md)》的 Q 編號，本文件不另立清單

結論若被採納，會回頭修改上述文件；在那之前，以上述文件為準。

## 1. 問題：SSE 繞過了推播，但繞不過 MDM

SRS 第 10 章定下「所有資料不得離開醫院網路」，因此推播整條移除，即時通知改用院內 SSE 長連線（FR-S07）。這一步是成立的——護理端與病人端都在院內網段，長連線從頭到尾不出院。

但 MDM 是另一條**完全獨立**的控制通道，SSE 蓋不到它。原規劃的 Android Enterprise 在三個地方必須連外：

| 情境 | 為什麼連外 |
|---|---|
| 平板首次佈建 | 需連 Google 下載 Android Device Policy 並註冊 Managed Google Play |
| 後端設定裝置政策 | 伺服器要呼叫 `googleapis.com`，直接違反 SRS 10.2「無任何主動連向院外的元件」 |
| 遠端鎖定即時生效 | 命令靠 FCM 送達裝置——**就是被移除的那個推播** |

也就是說，只要採用 Android Enterprise，「全程院內」這個前提就不成立。

## 2. 先問：MDM 在本系統實際做了哪五件事

盤點目前 `MockMdmProvider` 提供的能力，逐項檢查是否真的需要作業系統層權限：

| MDM 做的事 | 需要作業系統權限嗎 | 說明 |
|---|---|---|
| 納管狀態作為「可指派」的前提 | 否 | 純粹是資料庫的一個布林值，已經是應用層邏輯 |
| 設定 Kiosk 網址 | 否 | 佈建時用一次，現行的一次性佈建網址已經做到 |
| 遠端鎖定 | 否 | FR-P01 中性等待畫面加上解除綁定清除本地暫存，效果等價 |
| 螢幕保持亮著（FR-N12 常駐總覽螢幕） | 否 | 網頁的 Wake Lock API 就能做到 |
| **防止病人跳出這個應用程式** | **是** | 唯一一項 |

**五件事裡只有最後一件需要作業系統權限。** 前四件早已在應用層完成或可在應用層完成，跟 MDM 沒有關係。

## 3. 採用方案

### 3.1 Kiosk 鎖定改用 Android 內建的螢幕固定

Android 5.0 起內建「螢幕固定」功能：設定 → 安全性 → 螢幕固定，開啟並勾選「解除固定前要求 PIN」。之後在最近工作畫面把 PWA 釘住，病人就退不出去，解除需要輸入只有護理師知道的 PIN。

**不需要 MDM、不需要 Google 帳號、不需要任何對外連線、不需要寫任何程式碼。** 15 台由護理師一次設定完成。

### 3.2 搭配的前端設定

| 設定 | 做法 | 對應需求 |
|---|---|---|
| 隱藏網址列 | PWA 安裝到主畫面，manifest 設 `"display": "standalone"` | — |
| 螢幕不休眠 | Wake Lock API | FR-N12 |
| 防止加開使用者 | 平板設定裝置 PIN，關閉「新增使用者」 | — |

### 3.3 逸出偵測改用既有的 SSE 回報

螢幕固定唯一守不住的是「有人解開了而護理師不知道」。這一點不必靠作業系統強制，用既有的連線偵測即可：

平板端的 PWA 每 30 秒回報一次「我還在前景」，並監聽 `visibilitychange`，一離開前景就立刻回報。護理端總覽直接顯示哪一台跳出了 Kiosk。

**這是把「用作業系統權限預防」換成「用既有連線偵測並讓護理師看見」**，與系統其他功能（求助、症狀回報）是同一個模式，不新增任何架構。

### 3.4 憑證信任

PWA 的 Service Worker 強制要求 HTTPS，而院內主機名稱不是公開網域，公開 CA 依 CA/B Forum 規則不得簽發給內部名稱與私有位址。三條路：

| 做法 | 結果 |
|---|---|
| 自簽憑證 | **不可行**。瀏覽器顯示連線不安全，且憑證有誤的來源會被完全停用 Service Worker，離線快取無法運作 |
| 院方內部 CA 簽發 | 技術上可行，但根憑證需裝進 15 台平板的信任存放區。**安裝憑證原本就是 MDM 的工作**，不用 MDM 就得每台手動安裝，憑證到期再來一次 |
| **公開網域加 DNS-01 驗證** | **採用**。取得一個真實網域，DNS A 紀錄指向院內位址。DNS-01 只需修改 TXT 紀錄，主機完全不必對外開放；憑證在有對外連線的開發機上簽發，檔案帶進院內部署。公開 CA 已在信任清單內，平板端零設定 |

補充一項與此相關的限制：Android 7 起，使用者手動安裝的 CA 預設不被應用程式信任，只有系統內建的算數。Chrome 不受此限，因此以 Chrome 開啟 PWA 可行；但若日後改為自行封裝 WebView 應用程式，必須在 `network_security_config.xml` 明確宣告 `<certificates src="user" />`。

採用第三條路即可完全避開平板端的憑證設定。

## 4. 守不住什麼

| 破口 | 影響與處置 |
|---|---|
| 重新開機後螢幕固定會解除 | 護理師開機時重新釘選一次。15 台、每日一次，可接受。列入交班檢查清單 |
| 病人解開固定而護理師不知情 | 由 3.3 的逸出偵測補上，改為可見而非可防 |
| 還原原廠設定、更改 Wi-Fi 設定 | 擋不住。屬物理接觸風險，透析治療區全程有護理師在場 |
| 無法遠端派送應用程式更新 | PWA 走伺服器端部署，本來就不需要逐台更新；平板上的瀏覽器版本則會凍結 |

## 5. 對現有程式碼與文件的影響

### 5.1 程式碼

`MdmProviderPort` 介面**不需要任何改動**。`MockMdmProvider` 保留，但語意改變：

- 改動前：模擬真實 MDM 的控制行為，等待換成 `AndroidEnterpriseProvider`
- 改動後：**裝置佈建狀態的紀錄與稽核**，本來就不需要控制實體硬體

因此稽核說明欄的 `[mock]` 前綴應移除——它已經不是模擬品，而是這項功能的正式實作。

需要新增的只有 3.3 的前景回報端點與護理端總覽的對應欄位。

### 5.2 需求文件

| 文件 | 需要的修改 |
|---|---|
| SRS | FR-S01 由「MDM 整合」改為「裝置佈建狀態紀錄」，真 MDM 串接自 P0 降級為「院方若已有既有方案再接」 |
| 實作規格書 3.3 | 補上本方案為現行做法 |
| 部署規範 | 補上憑證取得方式（3.4）與平板的螢幕固定設定步驟 |
| 尚待確認事項清冊 | Q-11 縮小範圍，見下節 |

### 5.3 Q-11 縮小後的範圍

原本要問的是「串接 Management API 需要什麼權限與帳號、申請流程多久」，採用本方案後不再需要。剩下兩題：

1. 15 台平板的型號與 Android 版本為何？（確認支援螢幕固定，Android 5.0 以上皆有）
2. 院內憑證由誰簽發？是否同意採用 3.4 的公開網域加 DNS-01 方式？

## 6. 被否決的方案：自建 Device Owner 應用程式

為留下判斷依據，記錄另一條技術上可行但未採用的路。

做法是自行開發 DPC（Device Policy Controller），佈建時以 QR 碼指向院內網址下載 APK，命令通道走既有的 SSE，完全不觸及 Google 服務。可用的 API 皆為本地呼叫：`setLockTaskPackages()`、`startLockTask()`、`addUserRestriction()`、`lockNow()`、`installCaCert()` 等。

**否決理由**：為了「防止病人跳出應用程式」這一件事，代價是一個完整的 Android 專案（估 2 至 3 週）、15 台實機測試，且 Device Owner 只能在尚無任何帳號的裝置上設定，測試失誤就要還原原廠重來。而內建的螢幕固定以零成本達成同一效果，差別僅在「重新開機後需要重新釘選」。

**重新評估的觸發條件**：平板數量成長到數十台以上、或出現螢幕固定被規避的實際事件而交班檢查無法解決時，再回頭考慮這條路。
