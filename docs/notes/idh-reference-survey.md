# 同院 IDH 系統參考調查：臨床資料 API 與可借用的資訊

版本：v0.1　文件狀態：草案（2026-10-04 開立）　適用讀者：FDE 工程團隊、使用者本人

---

## 0. 本文件的定位

本文件不是需求文件，是一份**調查紀錄**。院內同一個地方已經部署了另一套系統：另一個團隊做的「透析中低血壓（IDH）預警系統」，它每隔幾分鐘就向院方抓一次透析紀錄。2026-10-04 使用者指示：

1. 讀那套系統的程式，釐清它取得病人臨床資料的 API 怎麼用
2. 找出那套系統裡可以補足本系統的資訊

調查的程式有兩份：**成大版**（使用者提供的那一個分支）與**斗六版**（使用者先前取得、放在本機的一份）。兩份都**只讀不改**：成大版 clone 到專案 repo 以外的參考資料夾，推送位址已改成無效值；本系統的程式一行都沒動。

閱讀時請記住三件事：

- **這裡的每一條都是從別人的程式「讀出來的」，不是院方的答覆。** 程式寫的不一定等於 API 的實際行為，也不代表院方同意本系統使用同一支 API。因此本文件**不讓任何一個待確認事項結案**，只在清冊裡記下線索、把要問的題目縮小（見第 7 節）
- **公開文件的界線照舊**（AGENT.md「其他硬性規則」）：API 的院內位址、參考程式的 repo 網址、任何一筆真實資料，**一律不寫進本文件**。要找位址，看參考程式的 `scripts/fetch_API.py`
- 與需求文件衝突時，以需求文件為準

## 1. 調查範圍與做法

| 範圍 | 做了什麼 | 結果 |
|---|---|---|
| 成大版程式 | 讀 Django 專案的抓取、拆檔、匯入、資料模型、畫面邏輯與兩個預測模型 | 本文件第 2～6 節的主要來源 |
| 成大版其他分支 | 比對各分支與提供者分支的差異 | 發現真實病人資料留在版本歷史中，見第 8 節 |
| 斗六版程式 | 讀抓取程式與單一病人歷史查詢 | 多一種查詢方式；血壓欄位的位置與成大版互相矛盾，見第 5 節 |
| 實際呼叫 API | 從院外試連端點的連接埠 | **連不上**（API 只在院內網路，預期中），沒有取得任何回應 |
| 把成大版跑起來 | 沒有做 | 提供者分支缺 Django 的設定檔，原樣無法啟動 |
| 回應格式的實證 | 從版本歷史中一份 2024 年的原始回應，只看遮罩後的結構（數字、中文全部換成佔位字元） | 確認了回應外形與各欄型態；做到一半被權限機制擋下，**已停手，抽出的暫存檔已刪除** |

## 2. 臨床資料 API 怎麼用

| 面向 | 內容 |
|---|---|
| 形態 | 院內一台 PHP 伺服器上的 `dialysislist.php`，HTTP `GET` |
| 查詢一：某一天全中心 | `?date=YYYY-MM-DD`。成大版、斗六版都用這一種 |
| 查詢二：某位病人一段期間 | `?case_number=<病歷號>&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD`。**只有斗六版用過**（抓 45 天歷史算統計值）；成大那一台是否也支援，未驗證 |
| 位址 | 成大、斗六各一台，都是院內 IP（不寫進公開文件） |
| 認證 | 參考程式呼叫時**沒有帶任何認證資訊**，純 HTTP。本系統若要使用，正式的認證方式仍要資訊室給 |
| 回應外形 | 開頭一段 `<meta charset="UTF-8" />`，後面接 JSON：`{"data_list": [[…51 個值…], [...], ...]}` |
| 一列是什麼 | **一次透析中的一筆生命徵象紀錄**。透析層級的欄位（體重、脫水量、設定值）在同一次透析的每一列重複出現 |
| 欄位怎麼認 | **陣列沒有欄位名稱，只能靠位置**。順序見第 3 節 |
| 回傳範圍 | 每次都回傳**當天到目前為止的全部紀錄**，不是增量。呼叫端要自己去重 |
| 速率限制 | 程式裡看不出來。成大版沒有逾時與重試；斗六版加了 30 秒逾時、最多重試 3 次 |

### 2.1 值的格式（取自 2024 年那份回應的遮罩結構）

| 種類 | 格式 |
|---|---|
| 病歷號 | 8 碼數字字串 |
| 生日 | `YYYY-MM-DD` |
| 透析開始、結束、紀錄時間 | `YYYY-MM-DD HH:MM`，**沒有秒、沒有時區**（當地時間） |
| 數值 | JSON 數字（浮點數），例如體重、血壓、流速 |
| 缺值 | 空字串 `""`。參考程式寫進資料庫前另把缺值補成 `-1` |
| 文字欄 | 透析模式（如 `HD`）、透析器型號、血管通路是一整串自由文字、Heparin 是「Free / 數字 u / 數字 u」這類組合字串 |

那份回應涵蓋 2024-11-06～12-12，共 1394 次抓取、約 11 萬列，每一列都是 51 個值。

### 2.2 參考系統怎麼抓、怎麼存

```
有人開著儀表板，且分鐘數是 3 的倍數
   └─ fetchData()      GET ?date=今天 → 原始回應整段附加到 YYYY-MM.txt（備份）
   └─ convertCSV()     51 欄放進表格，丟掉兩種列（見下）→ temp.csv
   └─ splitCSV()       拆成病人、透析、紀錄三份 CSV
   └─ saveData()       寫進 SQLite；病人以病歷號、透析以（病歷號＋透析次數）、
                       紀錄以（透析＋紀錄時間）判斷是否已存在
```

- **沒有真正的排程**：抓取是「頁面被開啟」時順便觸發的，沒人看畫面就不抓
- 丟掉的兩種列：病歷號不是純數字的（註解寫「同一病人有兩個 ID」）、床位以數字開頭的
- 原始回應每月一個 `YYYY-MM.txt` 留底，另有一支 `refetch_from_txt.py` 可從留底重建資料庫

## 3. 51 個欄位與本系統的對應

順序取自成大版 `convertCSV` 的欄位名稱清單。**第 22～25 與 36～37 欄的身分有爭議**，見第 5 節第 1 點。

|---|---|---|
| 0 | ID（病歷號） | `patients.medical_record_no` |
| 1 | 姓名 | `patients.display_name` |
| 2 | 性別 | `patients.gender`（API 是一個中文字，本系統 seed 用 `M`／`F`） |
| 3 | 出生年月日 | `patients.birth_date` |
| 4 | 年齡 | — |
| 5 | 透析次數（本院） | 與病歷號一起當作「同一次透析」的識別 |
| 6～8 | 透析開始時間、透析結束時間、紀錄時間 | 開始、結束可算出 `SESSION_MINUTES` |
| 9 | 透析機編號 | — |
| 10 | 床位 | 對 `beds`，見第 6.1 節 |
| 11～12 | 體溫、開始體溫 | — |
| 13 | 透析前體重（kg） | — |
| 14 | 理想體重（kg） | `DRY_WEIGHT`（**推測**，要護理部確認「理想體重」就是乾體重） |
| 15 | 目標脫水量（L） | `UF_TARGET`（**推測**；API 是公升，本系統是 mL，要乘 1000） |
| 16～19 | 輸液量、食物重量、預估脫水量、設定脫水量（L／kg） | — |
| 20 | 結束體重（kg） | `WEIGHT_POST` |
| 21 | 實際脫水量（L） | `UF_VOLUME`（乘 1000 換成 mL） |
| 22～25 | Start_SBP、Start_DBP、End_SBP、End_DBP | — |
| 26～31 | 透析模式、透析器、開始透析液流速、開始血液流速、透析液 Ca、傳導度 | — |
| 32～35 | 血管通路、Heparin、ESA、透析器凝血情況 | — |
| 36～37 | 血壓（收縮）、血壓（舒張） | — |
| 38～50 | 脈搏、呼吸、血流速、透析液流速、靜脈壓、透析液壓、膜上壓、脫水速率、累積量、透析液溫度、肝素注射量、沖水量、確認血管通路 | — |

**這支 API 沒有任何抽血數值。** 本系統的十種臨床數值裡：

| 本系統的數值 | 這支 API 有沒有 |
|---|---|
| `DRY_WEIGHT`、`UF_TARGET` | 有（各需一項確認，見上表） |
| `WEIGHT_POST`、`UF_VOLUME`、`SESSION_MINUTES` | 有 |
| `HEMOGLOBIN`、`ALBUMIN`、`BUN_PRE`、`BUN_POST` | **沒有** |
| `KT_V` | **沒有**，也算不出來（缺 BUN） |

## 4. 本系統 `HospitalApiAdapter` 會長什麼樣

`ClinicalDataSourcePort` 的第三個實作原本寫的是「院方給 API 後補上」。依上面的格式，它要做的事已經清楚，**只差第 9 節的幾項決定**：

1. `GET ?date=今天`，從第一個 `{` 開始解析 JSON（不要學參考程式用 `strip`，見第 5 節第 3 點）
2. 依位置取欄位；同一次透析只取一次透析層級的值（取最後一列）
3. 單位換算（公升 → mL）、時間補上院內時區
4. 輸出 `NormalizedClinicalValue`，`measuredAt` 用透析開始時間（透析前的數值）或結束時間（透析後的數值）
5. 其餘照現行規則：病人不存在、重複、全有或全無，都交給 `ClinicalDataImportService`

**要留意的一個上限**：單一批次最多 200 筆（`CLINICAL_BATCH_MAX_ROWS`）。全中心 41 床、每人抓五種數值就會超過，介接時要分批，或對 API 來源另訂上限。

## 5. 寫介接程式前要避開的坑

1. **血壓欄位的位置，兩份參考程式互相矛盾。** 成大版把第 22～25 欄當透析開始／結束血壓、第 36～37 欄當每一筆紀錄的血壓；斗六版的歷史查詢剛好把這兩組對調。兩者必有一錯。本系統目前不讀血壓，但日後做風險分層（FR-P03）一定會用到，要以資訊室的欄位定義或一次真實回應為準
2. **不要照抄成大版的匯入對應。** `load_data.py` 把「預估脫水量」寫進 `expect_dehydration`、「設定脫水量」寫進 `estimate_dehydration`，「目標脫水量」完全沒用到。本系統若參考它的欄位，以第 3 節的位置表為準
3. **去掉開頭那段 `<meta>` 要自己來。** 參考程式用 Python 的 `strip('<meta charset="UTF-8" />')`，那是「逐字元刪除頭尾出現在這組字元裡的字」，碰巧可用。本系統應該從第一個 `{` 開始解析
4. **床位格式可能改過。** 2024 年那份回應的床位是「數字＋英文字母」的形式，而現行程式會丟掉數字開頭的列，另外還留著一行被註解掉的「床號反轉」。現在的格式要在院內看一次才知道
5. **時間沒有秒，也沒有時區。** 以（病歷號、透析開始時間、紀錄時間）去重時，同一分鐘內的兩筆會被當成同一筆
6. **成大版沒有逾時。** 院方伺服器一慢，抓取就卡住整個頁面；斗六版補了逾時與重試，本系統照斗六版的做法即可

## 6. 其他可借用的資訊

### 6.1 床位配置（對 Q-34）

成大版畫面把床位寫死成六區（`views.py` 第 31～36 行）：

| 區 | 床號 |
|---|---|
| A | A1、A2、A3、A5、A6、A7、A8、A9 |
| B | B1、B2、B3、B5、B6、B7、B8、B9 |
| C | C1、C2、C3、C5、C6、C7、C8、C9 |
| D | D1、D2、D3、D5、D6、D7、D8、D9 |
| E | E1、E2、E3、E5、E6、E7、E8 |
| I | I1、I2 |

共 **41 床**。值得注意的兩點：

- **每一區都沒有 4 號床**；床號是「區碼＋數字」，不是本系統暫代的 `01`～`15`
- 本系統床位上限是 40 床（`BED_MAX_COUNT`）。首波若只開一區不受影響；**要涵蓋全中心就差一床**

### 6.2 低血壓的判定與門檻（對 Q-03）

| 用途 | 規則 |
|---|---|
| 交班回饋表標出「疑似低血壓」 | 任一筆 SBP ≤ 90，或比前一筆掉超過 20 mmHg |
| EBM 模型判定「過去某次透析有低血壓」 | 開始 SBP < 160 用 90、≥ 160 用 100 當門檻（註解稱 Nadir90／100），任一筆有效 SBP 低於門檻即算 |
| EBM 模型跳出警示 | 預測機率 ≥ 0.85 |
| 排除不合理讀數 | SBP < 50 不採計；序列模型另有一組合理範圍（SBP 60～250、脈搏 30～150 等） |

EBM 模型的 16 個輸入：性別、年齡、過去 7 天與 28 天的低血壓次數、開始 SBP／DBP、脈搏、呼吸、開始體溫、透析前體重、理想體重、目標脫水量、脫水量占體重比、開始血液流速、開始透析液流速、透析液溫度。

**這些是另一個團隊的選擇，不是院方書面 protocol**，Q-03 要的「書面依據出處」它補不上；但拿去問醫師時，可以當作「同院已有系統這樣用」的起點。

### 6.3 低血壓處置的選項（對 Q-25）

成大版警示回饋表可勾選的內容：

| 類別 | 選項 |
|---|---|
| 口服藥物 | Midodrine、其他 |
| 針劑藥物 | IV Glucose、其他 |
| 調整透析設定 | 降低血流速、降低脫水量（UF）、降低透析液流速、其他 |
| 護理處置 | 頭低腳高、降低透析液溫度、沖水（flush）、其他 |
| 其他處理 | 持續觀察、其他 |
| 另記 | 有無症狀、處置時間、當下 SBP／DBP、員工號 |

本系統「病人不適處置」範本目前的處置選擇是調整姿勢、測量生命徵象、通知醫師、依醫囑處置、心理安撫、持續觀察，**沒有任何針對低血壓的選擇**。上表可以直接當草稿帶去給護理部看。

### 6.4 斗六版的兩個做法（對 Q-06、Q-07）

- **去識別化**：斗六版在寫入 CSV 前，把病歷號與姓名用固定金鑰做可還原的固定式加密（同一個值每次加密結果相同，才能用來串接）。本系統送進 AI 前是直接移除識別欄位，兩種做法可以一起帶去問法務
- **院內推論端點**：斗六版的程式呼叫院內一台 Ollama 服務。那是斗六的網段，與本系統所在的院區無關，但代表「院內已有團隊自己架推論服務」這件事有先例，問 Q-07 時可以提

### 6.5 時段（對 Q-34，旁證）

成大版交班回饋表用三個時間窗判斷「這一班的病人」：早 10～11 點、午 15～16 點、晚 20～21 點（另一個版本是 10～12、14～16、19～21）；沒有結束時間的透析一律補成開始後 4 小時。這只是查詢用的時間窗，**不是班別定義**，但可以推測三班大約的起點。

## 8. 參考程式的資料保護問題

調查時發現：參考程式的 repo **不需登入就能 clone**，而其中一個分支的版本歷史裡，**留著真實病人的原始回應與資料庫檔**（含姓名、病歷號、生日）。提供者分支與主分支已經清掉，那個分支沒有。斗六版的本機資料夾裡也有一份病人資料 CSV 與一把金鑰檔，本次都沒有開啟。

這件事不在本系統的範圍內，也不是本系統能處理的，但不處理的話資料會一直公開。**是哪個分支、哪些檔案，刻意不寫在公開文件裡**，已在對話中告知使用者。要怎麼處理見第 9 節第 1 項。
