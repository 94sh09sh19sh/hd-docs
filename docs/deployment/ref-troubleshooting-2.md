# 現場疑難排解（第 2 份，D～G 類）

上層文件：《[現場疑難排解](ref-troubleshooting.md)》

> - 狀態：**現行**（常備參考），照「症狀 → 先查什麼 → 怎麼處置」找；**要印出來帶進去**；1117 由舊的第六冊 D～G 類改寫，每一條加了一列「容器路線」；編號 `X-xx`（沿用第六冊）
> - 第 0 節（容器路線先查哪一份）、第 1 節（四個除錯原則、五秒鐘的分層檢查）與 B、C 類在第 1 份

## 摘要

- D 類（X-18～X-23、X-37）：護理站連不到、登入沒反應、CORS、埠被佔、總覽斷線、有人要開對外網路、`git clone` 竟然成功
- E 類（X-24～X-28）：憑證警告、平板斷網後畫面一片空白、「尚未回報」、重新開機後螢幕固定不見、APK 裝不上
- F 類（X-29～X-32）：更新被擋、停在備份、要退回、不確定現在跑哪一版
- G 類（X-33～X-36）：資訊室的人中途離開、被要求先上線、手冊沒寫到的問題、今天做不完
- 仍然通用的：X-18 分層查連不到、X-23 婉拒開網路、X-33～X-36 人與流程
- 現場出現手冊沒寫到的問題：分層、抄原文，十分鐘沒頭緒就先跳過做別的（X-35）；做不完就乾淨地撤退（X-36）

## D. 網路、連接埠、連不進來

### X-18 護理站電腦連不到

| | |
|---|---|
| **分層查** | ① 主機上 `curl.exe http://localhost:<API_PORT>/api/health` 通不通 → ② 護理站 `ping <主機>` 通不通 → ③ 護理站瀏覽器開靜態站的埠 |
| **① 不通** | 服務沒起來，看 B 組 |
| **② 不通** | 網段或路由問題，找資訊室 |
| **③ 不通而 ② 通** | **防火牆**。要開三個埠的輸入規則 |
| **容器路線** | ✓ 適用，埠是 13000（後端）、18080（護理端）、18081（病人端）：① 主機上 `curl.exe -s http://localhost:13000/api/health` → ② 護理站瀏覽器開 `http://<IP>:13000/api/health` → ③ 護理站開 `http://<IP>:18080`；平板的 Wi-Fi 另外開 `http://<IP>:18081/shell/`。開不到找資訊室，**不要自己關防火牆**（《[護理站登不進去與主機位址之一：換主機位址](ref-login-switch-ip.md)》T-04） |

### X-19 畫面出得來，但登入沒反應

| | |
|---|---|
| **最可能的原因** | **PWA 裡的 API 位址是 `localhost`**——護理端正在向護理站那台電腦自己要資料 |
| **怎麼確認** | 瀏覽器開發者工具 → 網路，看請求打到哪個主機 |
| **處置** | 沒有當場的設定可以改：那個位址是**建置時**寫死的。唯一的補救是用院內主機位址重新產生安裝包（要帶開發機） |
| **預防** | 《[安裝包路線之五：建置與開發端彩排](ref-installer-build-5.md)》R-13 就是為了在家裡先抓到它 |
| **容器路線** | 原因相同（`HD_PUBLIC_API_URL` 建置時寫進護理端網頁），補救變簡單：在主機上改 `.env`、`docker compose --env-file $cfg build`、`up -d`，不必帶開發機。完整查法在《[護理站登不進去與主機位址](ref-login.md)》第 2 節 |

### X-20 瀏覽器主控台出現 CORS 錯誤

| | |
|---|---|
| **原因** | `.env` 的 `CORS_ORIGINS` 沒有列出護理端／病人端實際的來源 |
| **處置** | 補上 `http://<主機>:<NURSE_PORT>` 與 `http://<主機>:<PATIENT_PORT>`，重新啟動服務 |
| **容器路線** | 迭代 12 起病人端與後端同一個來源，`CORS_ORIGINS` 只列護理端：`http://<IP>:18080`。改完要 `docker compose --env-file $cfg up -d`（容器建立時才讀；`restart` 不會換成新值）。登入時的 `Failed to fetch` 多半就是這一條，見《[護理站登不進去與主機位址](ref-login.md)》 |

### X-21 連接埠被佔用

| | |
|---|---|
| **先查** | `Get-NetTCPConnection -State Listen \| Where-Object LocalPort -eq <埠>` |
| **處置** | 換一個埠，改 `.env`（`API_PORT`／`NURSE_PORT`／`PATIENT_PORT` 與 `CORS_ORIGINS`），重新啟動。**同時請資訊室登記** |
| **注意** | 這件事多半在某次重新開機、兩個服務啟動順序對調時才發作 |
| **容器路線** | 訊息是 `address already in use`，同機別的專案佔用。`.env` 的變數是 `HD_API_PORT`、`HD_NURSE_PORT`、`HD_PATIENT_PORT`；位址裡帶埠的 `HD_PUBLIC_API_URL`（要 `build`）、`CORS_ORIGINS`、`MDM_KIOSK_BASE_URL` 也要跟著改，平板已佈建的要重新佈建。換埠前先登記（《[從零部署本系統之一：容器路線的原冊](ref-fresh-install-detail.md)》W-07） |

### X-22 總覽一直顯示斷線

| | |
|---|---|
| **原因** | SSE 長連線被中斷（代理、閒置逾時、網路不穩） |
| **處置** | 超過約兩倍心跳沒收到訊息就會自動重連。持續斷線要查網路設備有沒有對長連線設逾時 |
| **容器路線** | ✓ 適用。心跳是 `.env` 的 `REALTIME_HEARTBEAT_SECONDS`（預設 20 秒）。換版、`up -d` 時護理端出現斷線紅框，服務回來後自己消失，是正常的 |

### X-23 有人說「我開一下對外網路就好了」

| | |
|---|---|
| **處置** | **婉拒，並記下這件事**（《[進院通則](ref-visit-rules.md)》情報蒐集表 `C-41`） |
| **怎麼說** | 「這套系統能放病人資料的前提就是它不連外。今天開了，之後每一次稽核都要重新解釋。真正缺的東西我們帶進來了。」 |
| **容器路線** | ✓ 適用，形式變了：院內主機 0926 起連得出去，但**連得出去不等於資料可以出去**（DEP-14）；部署與更新要連 GitHub、Docker Hub、npm，執行期零院外連線由程式擋。現場聽到的會是「手動開個容器把整顆磁碟掛進去」「把 `LLM_PROVIDER` 改成 `lab` 接實驗室」——一樣婉拒（`lab` 後端會拒絕啟動，DEP-40） |

### X-37 `git clone` 竟然成功了

| | |
|---|---|
| **意義** | 主機連得到程式碼來源，而且**某個帳號的憑證被用上了**（repo 是私有的） |
| **處置** | **先不要跑 `npm install`**，翻《[安裝包路線之六：院方要求直接 git clone](ref-installer-git-clone.md)》從 G-01 做起 |
| **容器路線** | ✗ 不適用：0926 起 `git clone` 就是部署方式，用的是 repo 的唯讀部署金鑰（DEP-43）。`git fetch` 說 `Permission denied (publickey)` 是部署金鑰被拿掉了，見《[本系統換版與退回](ref-upgrade.md)》W-19 ① |

## E. 憑證與平板

### X-24 平板上出現憑證警告

| | |
|---|---|
| **可能原因** | CA 沒打包進 APK；`network_security_config.xml` 的網域與實際位址不符；**主機根本沒開 TLS** |
| **處置** | 前兩項要回開發機重編 APK；第三項見《[平板與外殼 App](ref-tablet.md)》的 HTTPS 缺口 |
| **容器路線** | 0927 起 APK 在院內主機上由 `shell-builder` 建置、內建院內 CA，病人端走 HTTPS（`https://<IP>:18081`）。對應的原因：伺服器憑證上的位址與平板填的不一樣（換過位址沒重跑 `shell-builder`），或 `patient-web` 還在用 HTTP（日誌**最後一次**啟動是「找不到伺服器憑證…暫以 HTTP 提供」）。處置：重跑 `shell-builder`、`restart patient-web`（《[護理站登不進去與主機位址之二：換主機位址](ref-login-switch-ip-2.md)》T-08、T-10）；其餘見《[平板與外殼 App](ref-tablet.md)》 |

### X-25 平板斷網後畫面一片空白

| | |
|---|---|
| **原因** | Service Worker 沒註冊。**最常見的是因為連的是 HTTP**（非安全來源，`navigator.serviceWorker` 根本不存在） |
| **處置** | 同 X-24 第三項 |
| **為什麼嚴重** | 離線能力是選 PWA 而非純網頁的**唯一**理由。它不成立，這個選型就是假的 |
| **容器路線** | ✓ 適用：平板一律連 `https://`（`MDM_KIOSK_BASE_URL` 必須是 `https://`）；`patient-web` 掉回 HTTP 時照 X-24 容器路線那一列 |

### X-26 護理端顯示「尚未回報」而不是「固定中」

| | |
|---|---|
| **意思** | **外殼 App 還沒裝**，不是故障、也不是跳出 Kiosk |
| **三種狀態要分開** | 尚未回報＝沒裝 App；已跳出＝平板說它離開前景了；失去回報＝它不說話了（關機或斷網） |
| **容器路線** | ✓ 適用。1116 `TB-00` 是「固定中」 |

### X-27 重新開機後螢幕固定不見了

| | |
|---|---|
| **這是已知取捨** | App 會自動啟動，螢幕固定不會自動恢復 |
| **處置** | 人工重釘，列入每日交班檢查。護理端看得到哪一台跳出了，不必逐台目視 |
| **容器路線** | ✓ 適用（外殼行為，與主機路線無關）；最新做法見《[平板與外殼 App](ref-tablet.md)》 |

### X-28 APK 裝不上去

| | |
|---|---|
| **可能原因** | 之前裝過 debug 簽名版；未開啟「允許安裝不明來源」；機型內建的安全掃描擋下 |
| **處置** | 先解除安裝舊的；逐項開權限；必要時用 `adb install` |
| **容器路線** | ✓ 適用。0927 起 APK 從院內下載頁（`http://<IP>:18081/shell/`）安裝；開發機的 `dev` 簽章版與院內的 `hospital` 簽章版不能互相覆蓋安裝，裝過另一種要先解除安裝（《[平板與外殼 App](ref-tablet.md)》） |

## F. 更新與回退

### X-29 更新腳本被擋下，說服務還在跑

| | |
|---|---|
| **這是正確行為** | 更新期間的寫入會落在備份與遷移之間的空窗裡 |
| **處置** | `.\scripts\service-stop.ps1`，確認行程數 0 再重跑 |
| **容器路線** | ✓ 適用。訊息是 `更新中止：後端服務還在執行`：先 `docker compose --env-file $cfg stop api` 再重跑；**不要加 `--allow-running`**，那是演練用的（《[本系統換版與退回](ref-upgrade.md)》W-19 ④） |

### X-30 更新停在備份那一步

| | |
|---|---|
| **這是正確行為** | **備份沒做成就不往下走**，這是整支腳本的重點 |
| **常見原因** | 備份目錄寫不進去；磁碟可用空間低於門檻 |
| **容器路線** | ✓ 適用。訊息是 `更新中止：備份沒有成功完成，更新到此為止：…` 或空間不足（X-16）；資料庫沒有被改動 |

### X-31 更新後發現不對，要退回去

| | |
|---|---|
| **順序** | ① 停服務 → ② 還原更新前的備份 → ③ 把改名保留的舊版目錄換回來 → ④ 啟動 → ⑤ 記錄 |
| **關鍵觀念** | **程式可以退版，資料庫不行退版。** 回退是還原備份再換回舊版程式，不是把遷移倒回去 |
| **前提** | 更新時第 3 步「舊版目錄改名，不要刪」有做到。**沒做的話就沒有東西可以退** |
| **容器路線** | 觀念相同，做法在《[本系統換版與退回](ref-upgrade-2.md)》W-20：`git checkout <舊 tag>`、`HD_IMAGE_TAG` 改回、停 `api`、把新版資料庫移到旁邊、還原 `hd-before-update-…` 那一份、`up -d`。前提換成「**舊映像檔沒有刪**」與「`db-update` 第 3 段的備份檔名與雜湊有抄」 |

### X-32 不確定現在跑的是哪一版

| | |
|---|---|
| **查哪裡** | 安裝包目錄的 `VERSION.json`；護理端「維運狀態」的版本標記；更新紀錄 |
| **容器路線** | `git describe --tags`（程式碼）、`docker ps --format "{{.Names}} {{.Image}} {{.Status}}"` 的映像檔標籤（實際在跑的）、`.env` 的 `HD_IMAGE_TAG`，三者要一樣；護理端稽核軌跡「版本更新完成」那一筆的說明寫著新舊 tag。「版本更新紀錄」的版本欄是 `package.json` 的號碼（`0.1.0 → 0.1.0`），不是 tag。1116 起院內是 `v0.5.0`（`ai-gateway` 仍是 `v0.4.0`） |

## G. 人與流程

### X-33 資訊室的人中途離開，剩下的步驟需要他

| | |
|---|---|
| **處置** | 把需要權限的步驟集中排在他在的時候。他不在時做不需要權限的（冒煙測試、文件、問答） |
| **預防** | 一開始就問「您會全程在旁邊嗎」（《[第一次進院（0922）· 部署本系統之一：進院當天詳細版](visit-1-system-onsite.md)》H-03） |
| **容器路線** | ✓ 適用。容器路線要資訊室的是：防毒排除、防火牆、Docker Desktop 的設定、重新開機、備份送往另一台機器。1116 資訊室沒來，這幾項都留到院外補（《[院內主機現況與未完成事項](ref-status.md)》） |

### X-34 有人要求「先讓護理師開始用，其他的之後再說」

| | |
|---|---|
| **判斷** | 防毒排除、備份、權限這三項只要有一項沒完成，**就不要讓真實資料進去**。**1116 起防毒排除不在此列**（容器路線，見《[第五次進院（1116）任務二 · 本系統換版上線之一：詳細版](visit-5-system-detail.md)》SY-03）；權限 0926 起由 DEP-38 取代 |
| **怎麼說** | 「可以先讓大家看畫面、練操作，但真實病人資料要等備份與防毒設定完成。沒有備份的系統不該收病人資料。」 |
| **容器路線** | 剩下的硬條件是**備份做過、還原驗證過**（《[備份、還原與關服務](ref-backup-shutdown.md)》第 1.2 節）。功能開關照 DEP-29 先關，等對真實資料驗過、相關的人看過才開。說法的後半句改成「真實病人資料要等備份驗證完成」 |

### X-35 現場出現一個手冊沒寫到的問題

| | |
|---|---|
| **處置** | ① 照第 1 節分層 ② 抄下錯誤原文 ③ 若十分鐘內沒有頭緒，**先跳過、做別的，不要卡在同一個地方** ④ 記進《[進院通則](ref-visit-rules.md)》情報蒐集表 `C-40` |
| **原則** | 現場不是除錯的地方。**能帶回去查的就帶回去查** |
| **容器路線** | ✓ 適用。照片可以拍，只進私人 repo；`.env` 的內容、密碼、病人資料的畫面不拍 |

### X-36 今天做不完，要怎麼乾淨地撤退

**三件事，順序不能換**：

1. **把服務停掉**（若已啟動，照《[備份、還原與關服務](ref-backup-shutdown-2.md)》做到「停用」，容器路線是 `docker compose --env-file $cfg down`）。不要留一個半成品在跑——護理師會開始用它，然後把問題當成正常行為。已經在用的版本（例如換版失敗、已退回舊版）就讓它維持在一個說得清楚的狀態（哪一版、讀檔開或關），不必停
2. **把現況寫下來**：做到哪一步、卡在哪、已經在主機上留下了什麼（安裝包時代：目錄、帳號、排程工作、資料庫檔案；容器路線：容器、映像檔、資料卷、`$root` 底下的目錄、改過的 `.env` 行）
3. **當場講清楚下一次需要什麼**，並**約好下一次的時間**（《[進院通則](ref-visit-rules.md)》情報蒐集表 `C-37`）

還要做的：**把 A 級情報補完**（《[進院通則](ref-visit-rules.md)》）。安裝包時代另有**清除隨身碟**（H-23）；0926 起不准用隨身碟，容器路線 ✗ 不適用，改成離院前手機裡含院內資料的照片移進私人 repo 後刪掉。

**撤退不是失敗。** 帶著完整情報撤退，下一次就會成功；硬幹到一半留下半成品，下一次要先花時間清理現場。
