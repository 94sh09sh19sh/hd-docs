# 第七冊 · 院方要求直接 `git clone`，而且成功了

版本：v0.1　文件狀態：草案　編號：`G-xx`　**這一冊要印出來帶進去**

> 手冊其餘六冊都假設 [H-08](04-onsite.md#h-08-讓它失敗並把失敗記下來dep-25) 的 `git clone` 會失敗。
> 這一冊處理相反的情形：**院方叫你直接 clone，而它真的成功了。**
> 那不是好事也不是壞事——**是一筆預料之外的情報**，而你接下來的每一步都取決於它為什麼會成功。

---

## 0. 先講結論

**clone 成功不會改變規則，只會改變你知道的事。**

| 不變的 | 為什麼 |
|---|---|
| DEP-11：不得在正式主機上執行 `npm install` 或任何建置步驟 | clone 成功只證明「連得到程式碼來源」，不證明連得到套件來源與 Prisma 引擎來源，更不證明院方允許 |
| DEP-14：安裝包啟動時不得連往院外 | 這台機器連得出去，正是這一條更要守住的理由 |
| 最後裝進去的一律是**安裝包** | 不管程式碼怎麼進來，`H-10` 之後的步驟、腳本、目錄界線全部一樣。**不要從 clone 下來的目錄直接跑服務** |

因此這一冊只有三條出路，在 [G-06](#g-06-決定走哪一條) 選一條：

| 出路 | 什麼情況 | 終點 |
|---|---|---|
| **一、記下來，照走路線 B**（**預設，建議**） | 院方只是想試試看，或沒有堅持 | 清掉 clone 與憑證，回到 [H-09](04-onsite.md#h-09-解壓並核對雜湊dep-27) |
| **二、在主機上建置安裝包** | 院方**堅持**以 clone 的方式部署，且願意**書面**同意例外 | 在主機上產出一份安裝包，驗收通過後從 [H-10](04-onsite.md#h-10-建立-env) 接回 |
| **三、停手** | 查不出連線從哪來、或憑證是別人的、或沒有人能為例外負責 | [總覽第 6 節](index.md#6-什麼情況下當場停手)的撤退三件事 |

> **出路二是把開發機的工作搬進院內做，不是把開發環境搬進院內跑。**
> 建置完、驗收完、連線關掉之後，主機上跑的仍然是一份離線安裝包，和隨身碟帶進來的那一份沒有兩樣。

## 1. 先弄清楚它為什麼會成功

### G-01 停下來，把成功記下來

**做什麼**

**先不要接著跑 `npm install`。** 把 clone 的輸出與耗時照 [H-08](04-onsite.md#h-08-讓它失敗並把失敗記下來dep-25) 的格式寫進筆記本，
只是「錯誤原文」那一欄改寫成「成功的輸出」。

**怎麼知道成功了**

筆記本上有：執行的完整指令（含網址）、輸出的最後幾行、耗時、當時誰在旁邊、**是誰叫你 clone 的**。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 有人說「成功了就直接裝下去吧」 | 「好，我先花十分鐘確認它是怎麼連出去的，這會寫進交接文件。」然後做 G-02～G-05 |
| 想順手把 `npm install` 也跑下去看看 | **不要。** 那一步會在主機上寫入數百 MB 的套件、執行安裝後腳本，而你還不知道它連去哪裡、誰允許的 |

---

### G-02 查出程式碼是從哪裡來的

**做什麼**

```powershell
cd <clone 下來的目錄>
git remote -v
Test-NetConnection github.com -Port 443
netsh winhttp show proxy
git config --show-origin --get-regexp "http.*proxy"
Get-ChildItem Env: | Where-Object Name -Match "proxy"
```

**怎麼知道成功了**

你能回答下面這張表的其中一列：

| 情形 | 怎麼認 | 意義 |
|---|---|---|
| **直連 GitHub** | 遠端是 `github.com`，`Test-NetConnection` 的 `TcpTestSucceeded` 是 `True`，沒有代理 | 這台主機**可以直接上網**。零院外連線的前提在這台機器上不成立 |
| **經院內代理伺服器** | 有 proxy 設定，`TcpTestSucceeded` 可能是 `False` 但 clone 成功 | 院方有一條受管制的對外路徑。**要問白名單是什麼**，套件來源與 Prisma 引擎來源多半不在上面 |
| **院內程式碼鏡像** | 遠端是院內主機名稱（GitLab、Gitea 之類），不是 `github.com` | 有人事先把程式碼搬進院內了。**問清楚是誰、從哪一版搬的**（G-04 會核對） |

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 三種都對不上 | **停手**（出路三）。連線從哪來都說不清，就沒有人能為接下來的事負責 |
| 資訊室說「這台本來就能上網」 | 記下原話與說話的人。這是 [C-42](05-carry-in-out.md#36-這一趟的過程紀錄b-級但只有現在寫得出來) 那一類情報，也直接牴觸 Q-27 的前提 |

---

### G-03 查出是誰的憑證

**這一步最容易被忽略，而後果最嚴重。** 這個專案的 repo 是**私有的**，沒有憑證 clone 不會成功——
所以一定有某個帳號的憑證被用上了。

**做什麼**

```powershell
git config --show-origin --get-regexp "credential"
cmdkey /list | Select-String -Pattern "git"
```

回想一下剛才 clone 的時候：**有沒有跳出登入視窗？是誰輸入的？**

**怎麼知道成功了**

你知道用的是哪個帳號，以及它有沒有被**存在這台機器上**。

| 情形 | 處置 |
|---|---|
| **是你自己的 GitHub 帳號** | 你的憑證現在存在一台共用主機上，任何登入這台機器的人都能用它讀寫整個 repo。**離院前一定要清掉**（G-08），而且回去之後**把那一組權杖作廢** |
| 是院方的部署帳號或唯讀部署金鑰 | 最好的情形。記下帳號名稱、權限範圍、誰保管 |
| 是院內鏡像的帳號 | 同上 |
| 不知道是誰的 | **停手**（出路三） |

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 網址裡直接寫著權杖（`https://<權杖>@github.com/...`） | 權杖已經寫進 `.git\config` 與命令歷程。**這一組權杖視同外洩**，離院前刪掉 clone 目錄，回去立刻作廢 |
| 有人提議「把你的權杖留在上面，以後更新方便」 | **不要。** 那等於把 repo 的存取權交給這台主機上的每一個人，而且你離職或換權杖的那天，院內的更新就斷了 |

### G-04 確認 clone 到的是哪一版

**做什麼**

```powershell
git log -1 --oneline
git status --short
```

**怎麼知道成功了**

`git log -1` 的 commit 與[交付單](01-dev-machine.md#p-11-寫交付單)上的**一模一樣**，`git status --short` 沒有輸出。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| commit 比交付單新 | clone 拿的是分支最新一筆，而那一筆沒有經過[第一冊](01-dev-machine.md)與[第二冊](02-dry-run.md)的驗收。出路二要先 `git checkout <交付單上的 commit>` |
| commit 比交付單舊 | 多半是院內鏡像沒同步。**不要用它**，問清楚鏡像多久同步一次 |
| 找不到交付單上的 commit | 鏡像只同步了部分分支，或根本是別的 repo。停下來查 |

---

### G-05 問清楚這條連線的來歷

**做什麼**

這一段要問資訊室，答案寫進筆記本：

| # | 問題 | 為什麼要問 |
|---|---|---|
| 1 | 這台主機的對外連線是**常態**開著，還是今天臨時開的？ | 常態開著的話，Q-27 的前提要整個重談 |
| 2 | 誰開的、有沒有申請紀錄？ | 沒有紀錄的連線，稽核時沒有人說得清 |
| 3 | 白名單上有哪些網域？（`github.com`、`registry.npmjs.org`、`binaries.prisma.sh`？） | 決定出路二做不做得完 |
| 4 | **今天結束之後會關掉嗎？誰關？怎麼證明關了？** | 出路二的最後一步（G-17）要靠這一題 |
| 5 | 連線有沒有被記錄或監看？ | 日後有人問「那天主機連去哪裡」時要答得出來 |
| 6 | 院方想用 clone 的方式部署，理由是什麼？ | 常見的理由是「不想處理隨身碟」或「以後更新方便」。**知道理由才能談替代方案** |

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 答不出第 4 題 | 出路二就不能走。**開了關不掉的連線，比沒開更糟** |
| 第 6 題的理由是「以後更新方便」 | 說明更新的路線（[第 5 節](#5-之後的更新)）：就算用 clone，每次更新也都要開、建、驗、關一輪，省不了多少事 |

## 2. 決定

### G-06 決定走哪一條

**做什麼**

依 G-02～G-05 的答案，對照下表，**和資訊室一起**選一條，選完寫進筆記本並請對方確認。

| 條件 | 出路 |
|---|---|
| 院方沒有堅持 | **一** |
| 院方堅持，但答不出 G-05 第 4 題（誰關、怎麼證明關了） | **一**，並把「院方想用 clone」列為下一次要談的事 |

## 3. 出路一：記下來，照走路線 B

### G-07 把這次 clone 寫進紀錄

**做什麼**

演練紀錄 §1.3 照填，「`git clone` 的錯誤原文」那一欄寫「**成功**」，並附上 G-02～G-05 的答案。
**`npm install` 不必跑**——它不會改變結論，只會在主機上多留一堆東西。

---

### G-08 清掉 clone 與憑證

**做什麼**

```powershell
cd C:\
Remove-Item -Recurse -Force <clone 下來的目錄>
cmdkey /list | Select-String -Pattern "git"
cmdkey /delete:<上一行列出的目標名稱>
```

**怎麼知道成功了**

clone 目錄不在了，`cmdkey /list` 再也找不到任何 `git` 開頭的憑證。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 院方要求保留 clone 目錄 | 可以，但**憑證一定要清**，並在交接文件寫明：那個目錄**不是**安裝目錄，改了它不會影響服務 |
| 刪除時說檔案被佔用 | 多半是檔案總管或防毒還開著它。關掉檔案總管視窗再試 |
| 憑證是用 Git Credential Manager 存的，`cmdkey` 看不到 | `git credential-manager github list` 看帳號，再 `git credential-manager github logout <帳號>` |

然後回到[第四冊 H-09](04-onsite.md#h-09-解壓並核對雜湊dep-27)，照原本的路線 B 做完。

## 4. 出路二：在主機上建置安裝包

**這一整節只有在 G-06 選了二時才做。** 它等於把[第一冊](01-dev-machine.md) P-02～P-09 搬到院內主機上重做一次。
**預留 60～120 分鐘**，大部分花在 G-11 下載套件。

### G-09 取得書面例外

**做什麼**

請資訊室（或有權限核准的人）在紙上寫明並簽名：

| 事項 | 內容 |
|---|---|
| 例外的條款 | DEP-11（在正式主機上建置）；以及今天這段對外連線 |
| 期間 | 今天幾點到幾點 |
| 允許連線的來源 | G-05 第 3 題的白名單 |
| 關閉連線的人與確認方式 | G-05 第 4 題 |
| 以後的更新是否沿用 | 是／否（[第 5 節](#5-之後的更新)） |

**怎麼知道成功了**

你手上有一張簽了名的紙。**口頭同意不算。**

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 「不用那麼麻煩，我說可以就可以」 | 回出路一。這張紙保護的是對方：半年後有人問「為什麼這台主機上有 `npm install` 的痕跡」，答案就在這張紙上 |

> 回去之後，這次例外要寫進《[部署規範](../requirements/deployment-spec.md)》。
> **手冊不能替規範開例外**，它只記錄現場發生了什麼。

### G-10 確認主機上的 Node.js，並分好三個目錄

**做什麼**

```powershell
node -v
npm -v
```

然後決定三個目錄，**三個必須彼此分開**：

| 目錄 | 放什麼 | 建議 |
|---|---|---|
| **建置目錄** | clone 下來的原始碼、`node_modules` | 就是剛才 clone 的那個，路徑越短越好 |
| **安裝目錄的上一層** | 建出來的安裝包、`.env` | 與 [H-09](04-onsite.md#h-09-解壓並核對雜湊dep-27) 相同，例如 `C:\hd\` |
| **資料與備份目錄** | 資料庫、備份 | 與 [H-13](04-onsite.md#h-13-註冊服務並啟動) 相同，資訊室指定 |

**怎麼知道成功了**

`node -v` ≥ v20.11，三個目錄寫在筆記本上。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| **沒有 Node.js** | 裝 Node.js 是另一件要走變更申請的事，而且要從 `nodejs.org` 下載（又一個要開的來源）。**多半今天做不完——回出路一** |
| 有 Node.js，但低於 v20.11 | 同上。**不要升級它**：那是別的專案裝的，升級可能弄壞人家 |
| 有 Node.js 且版本夠 | 可以用，但要知道：**安裝包裡的 `runtime\node.exe` 就是從這一支複製的**。記下版本，它會寫進 `VERSION.json` |
| 建置目錄在「文件」或桌面底下 | 搬到短路徑。兩萬多個檔案加上深層目錄，會撞到 Windows 的路徑長度限制 |

---

### G-11 安裝相依套件

**做什麼**（計時）

```powershell
cd <建置目錄>
npm ci
```

**用 `npm ci` 不用 `npm install`**：前者只照 `package-lock.json` 裝，不會自行升級任何套件，
裝出來的東西和開發機上驗收過的是同一份。

**怎麼知道成功了**

沒有 `ERR!`，最後一行是 `added <數字> packages`，而且 `node_modules\@prisma\engines\` 底下有引擎檔：

```powershell
Get-ChildItem node_modules\@prisma\engines\ | Where-Object Name -Match "engine"
```

**可能怎麼壞、怎麼處理**

| 症狀 | 原因 | 處置 |
|---|---|---|
| `ECONNREFUSED`／`ETIMEDOUT`，網址是 `registry.npmjs.org` | 白名單沒有套件來源 | 抄下錯誤原文。請資訊室加，加不了就回出路一 |
| `407 Proxy Authentication Required` | 代理要帳密 | **不要把任何人的帳密寫進 npm 設定。** 回出路一 |
| 裝完了，但 `engines` 底下沒有引擎檔 | `binaries.prisma.sh` 不在白名單，安裝後腳本靜靜地失敗了 | G-12 一定會擋下來。請資訊室加白名單，然後 `Remove-Item -Recurse node_modules` 重跑 `npm ci` |
| `EPERM`／`EACCES` | 防毒即時掃描、或還有 node 行程開著 | 請資訊室暫時把**建置目錄**加進排除清單；不行就等掃描過去再重跑 |
| 跑了 20 分鐘還沒完 | 代理限速 | 記下耗時。這是院方評估「以後更新方便」時該知道的數字 |

### G-13 填建置用的 `.env`，只填一行

**做什麼**

```powershell
Set-Content -Encoding utf8 -Path .\.env -Value "VITE_API_BASE_URL=http://<院內主機>:<API_PORT>"
```

**這個 `.env` 放在建置目錄**，只用來告訴建置兩個 PWA 該連哪個位址。
它**不是**服務要讀的那一份——服務讀的在安裝目錄的上一層，接回第四冊 H-10 時才建。

**怎麼知道成功了**

`Get-Content .\.env` 只有那一行，位址與[第三冊](03-tablet-shell.md) K-01 決定的一致。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 想把 `JWT_SECRET`、管理員密碼也寫進來 | **不要。** 建置不需要它們，而建置目錄是你離院時要刪掉或留給院方的東西 |
| 位址還沒決定 | 回出路一。**這一行填錯，護理站就登不進去**（[X-19](06-troubleshooting.md#x-19-畫面出得來但登入沒反應)） |

> **這是出路二唯一比路線 B 好的地方**：位址是在現場、看著真正的主機填的，
> 不會發生「開發機上建包時填錯位址，到院內才發現」的事。

### G-14 建置並確認位址寫對了

**做什麼**

```powershell
npm run build
Select-String -Path apps\nurse-pwa\dist\assets\*.js -Pattern "<院內主機>" -List | Select-Object Filename
Select-String -Path apps\nurse-pwa\dist\assets\*.js -Pattern "localhost:3000" -List | Select-Object Filename
```

**怎麼知道成功了**

第一個 `Select-String` **找得到**，第二個**找不到**。`apps\patient-pwa\dist\` 底下有 `sw.js`。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 仍然找得到 `localhost:3000` | `.env` 不在建置目錄的最上層，或變數名稱打錯。改好再 `npm run build` |
| TypeScript 錯誤 | 在開發機上建得起來、在這裡建不起來，多半是 Node 版本差太多。**不要現場改程式**，回出路一 |
| 其餘 | 見 [P-04](01-dev-machine.md#p-04-建置三個產物) 的表 |

---

### G-15 五支盤點

**做什麼**

```powershell
npm run check:all
```

**怎麼知道成功了**

與 [P-05](01-dev-machine.md#p-05-五支盤點全部跑過) 相同，五支全綠。

**可能怎麼壞、怎麼處理**

**在開發機上全綠、在這裡有紅字**，代表兩邊的程式碼或相依不一樣。先回頭看 G-04 的 commit，
再看 `git status --short`——`npm ci` 不應該改動任何被追蹤的檔案。**查不出原因就回出路一。**

---

### G-16 建置安裝包並驗收

**做什麼**

```powershell
npm run package:build -- --out C:\hd
Get-Content C:\hd\<安裝包目錄>\VERSION.json
npm run package:verify -- --dir C:\hd\<安裝包目錄>
```

不需要 `--zip`：包不必搬動，就在它要安裝的地方。

**怎麼知道成功了**

| 看什麼 | 應該是 |
|---|---|
| `VERSION.json` 的 `commit` | 與 G-04、交付單一致 |
| `commitClean` | `true`（建置目錄的 `.env` 被 gitignore 排除，不會讓它變成 `false`） |
| `node` | G-10 記下的版本 |
| 驗收五項 | 全綠 |

**把 `CHECKSUMS.txt` 的 SHA-256 抄下來**（`Get-FileHash -Algorithm SHA256 C:\hd\<安裝包目錄>\CHECKSUMS.txt`）。
它對不上交付單上的值是**正常的**——執行期與建置時間不同，雜湊一定不同。
**從現在起，這一串才是這台主機上那份安裝包的身分**，寫進交接文件。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| **第 5 項有連線紀錄** | 在這台**真的連得出去**的機器上，這一項抓到的是真的對外連線。**不得安裝**，抄下哨兵記的主機名稱，回出路一 |
| `commitClean` 是 `false` | 建置過程改動了被追蹤的檔案。`git status --short` 看是哪些，**不得安裝** |
| 其餘 | 見 [P-09](01-dev-machine.md#p-09-驗收五項) 的表 |

---

### G-17 關閉對外連線，並當場確認

**做什麼**

請資訊室依 G-09 那張紙上寫的方式關閉連線，然後**你自己**確認：

```powershell
Test-NetConnection github.com -Port 443
Test-NetConnection registry.npmjs.org -Port 443
```

**怎麼知道成功了**

兩個 `TcpTestSucceeded` 都是 `False`。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 還是 `True` | **服務可以裝，但不得開始輸入真實病人資料**，直到連線關閉。與 [H-14](04-onsite.md#h-14-windows-五件事需要資訊室) 防毒排除清單加不了時的處置相同 |
| 「這台本來就要上網，關不了」 | 記下原話與說話的人。**這已經不是部署的問題，是能不能在這台機器上放病人資料的問題**，回去要重新決策 |

---

### G-18 請院方掃一次，然後接回第四冊

**做什麼**

1. 請資訊室用院方防毒掃**安裝包目錄**（DEP-26 的精神：隨身碟那一份掃過兩次，這一份一次都還沒掃過）
2. 清掉憑證（同 [G-08](#g-08-清掉-clone-與憑證) 的 `cmdkey` 那兩行）
3. 處理建置目錄：G-09 寫了「以後的更新沿用」就留著，並把建置用的 `.env` 刪掉；沒有就整個刪掉

然後從[第四冊 H-10](04-onsite.md#h-10-建立-env) 接著做。
**H-09 可以跳過**：G-16 的驗收第 1 項就是逐檔核對雜湊。

**怎麼知道成功了**

掃描結果乾淨並留存；`cmdkey /list` 沒有 `git` 開頭的憑證；你人在安裝包目錄，正要複製 `.env.範本`。

**可能怎麼壞、怎麼處理**

| 症狀 | 處置 |
|---|---|
| 想直接在建置目錄跑 `npm run dev` 或 `node apps\api\dist\main.js` | **不要。** 那是開發環境，不是安裝包：沒有低權限帳號、沒有目錄界線、沒有哨兵。後續的腳本也全都假設你在安裝包目錄 |
| 掃描報出 `runtime\node.exe` | 那是主機自己的 Node.js 複製過來的。請對方掃原本那一支對照，結果應該相同 |

## 5. 之後的更新

**只有 G-09 寫了「以後的更新沿用」時才適用。** 否則之後的更新一律照路線 B，由隨身碟帶新版安裝包進來。

每一次更新都是**開、建、驗、關、換**一整輪，一步都不能省：

| 順序 | 做什麼 | 對應 |
|---|---|---|
| 1 | 依 G-09 寫定的方式請資訊室開連線 | G-09 |
| 2 | `git fetch`，再 `git checkout <這次要交付的 commit>`。**不要 `git pull`**——它拿的是分支最新一筆，而那一筆沒人驗收過 | G-04 |
| 3 | `npm ci` → `check:offline` → `build` → `check:all` | G-11～G-15 |
| 4 | `package:build -- --out C:\hd` 產出**新的目錄**，驗收五項 | G-16 |
| 5 | 關閉連線並確認 | G-17 |
| 6 | 照更新七步換版：停服務、備份並驗證、**舊版目錄改名不要刪**、切到新目錄、套用遷移、啟動、寫紀錄 | [第二冊 R-20](02-dry-run.md#r-20-更新演練) |

> **這張表就是 G-05 第 6 題的答案**：用 clone 更新並沒有比較省事，
> 它只是把「在開發機上建包、用隨身碟帶進來」換成「在院內開一次網路、在正式主機上建包」。
> 每一次更新都多一次對外連線、多一次在正式主機上跑建置。**讓院方看完這張表再決定要不要沿用。**
