## 摘要

- 「上線」在這一冊指**首波試用**（DEP-33）：1 台暫用平板、1 床、少數護理師，不是全單位上線
- 現況：院內主機是 `v0.4.0`，`HOSPITAL_API_BASE_URL` 空白，系統還沒接真實資料
- 三個最大的缺口：防毒排除沒加（A-01）、Q-35 沒問（A-02）、**沒有「啟用院方 API」的手冊**（A-13）
- 還有一件事沒人確認過：病人告知與同意涵不涵蓋這套系統（A-03）
- `v0.4.0` 之後只有文件異動，不必換版；補測若要改程式，新 tag 要整輪重做第十七冊（O-02）
- 開發端要先補 I-13～I-15（A-12）：`v0.4.0` 沒做過，而院方 API 同步正是這次要開的東西
- 探測結果對照程式：`<meta>`、下機判定、單位都對得上；**床號未解決**，三種樣式混用（第 3 節）
- 位址一填，當天清單上**所有病人**的主檔與療程都會進主機，不是只有首波那一位；床號設定要排在填位址之前（第 5 節）
- Q-35、病人告知或防毒排除任何一項沒有答案，就停在位址之前，這次算 B 級（第 6 節）

## 0. 先講結論

### 0.1 上線的定義

| 範圍 | 首波 |
|---|---|
| 平板 | 1 台暫用平板 `TB-00`，同一時間只服務一床、沒有備品（《[暫用平板](../notes/interim-tablet.md)》第 5 節） |
| 護理師 | 護理長指定的少數幾位 |
| 資料來源 | 院方透析清單 API，每 3 分鐘抓一次、只讀不寫 |
| 功能 | 第 7 節的功能全部維持關閉（DEP-29） |

《部署規範》第 11 章第 22 條寫「先兩三台跑完一個班次」，現在只有一台，這一條只驗得到一台。

### 0.2 為什麼位址是分界線

1029 為止，主機上沒有真實病人資料。`HOSPITAL_API_BASE_URL` 一填，每一次抓取都會依序做病人主檔、床位清單、每一次透析的療程與下機（`hospital-sync.service.ts`）。三件事要先知道：

- **病人主檔不分有沒有平板**：回應裡的病人都會建立；1029 當天是 88 位。只有生命徵象紀錄限有配平板的病人
- **療程也不分有沒有平板**：護理端會看到整個透析室，不是只有首波那一床；要先讓首波護理師知道
- **床位只新增、不會自己消失**：床號格式設錯，錯的床號會留在清單裡

所以 A-01、A-02、A-03 都要排在填位址之前，床號設定（A-07）也是。

## 3. 探測結果對照程式（O-10）

讀 `v0.4.0` 的程式與 1029 的探測輸出對照的結果，**沒有接真實 API 跑過同步**。

| 對照點 | 探測看到 | 程式 | 結論 |
|---|---|---|---|
| JSON 前的 `<meta>` | 第一個 `{` 前有 25 個字元 | `parseHospitalApiBody` 從第一個 `{` 解析 | 不必改 |
| 下機 | 結束體重有空字串，血壓等欄有 `0` | 結束體重大於 0 才判定下機，結束時間不參與 | 不必改 |
| 已有結束時間、沒有結束體重 | 2 次 | 同上，視為進行中 | 不必改 |
| 累積量、脫水量、輸液量 | 數值都在 0～10 | 當公升讀 | 對得上 |
| 格式 | 601 列、51 欄、格式不符 0 次 | 不合格的那一次透析整次不寫 | 對得上 |
| 理想體重 | 306 列是 `0` | 讀到 0 不顯示（Q-09 的 1005 決定） | 不必改；開始用之後看面板缺不缺 |
| **床位** | `A9` 429 列、`9A` 90 列、`99` 82 列 | 預設 `0` 原樣 | **未解決** |

**床號要做的決定**：「院方床位轉床號的方式」是營運參數，不必改程式。

| 情形 | 做法 |
|---|---|
| `9A` 就是 `A9` 倒過來寫 | 設成 `1`（字母在前），同一床才不會變成兩床 |
| `9A` 與 `A9` 是不同的床 | 維持 `0` |
| `99` | 探測只印樣式、不印值，看不出是哪種床；三種設定都不會改動它，要問到才知道對不對 |
