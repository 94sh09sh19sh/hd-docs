## 3. 遇到的問題

### M-01 護理端登入出現 `Failed to fetch`

**發生了什麼**：N-16 用瀏覽器開護理端，登入頁出得來，按下登入，登入鈕下面出現 `Failed to fetch`。

`Failed to fetch` 的意思是**瀏覽器根本沒拿到後端的回應**——帳號密碼還沒被檢查到。原因只有兩類：網頁連的後端位址不對，或後端的 CORS 不放行這個來源。

**現場查到哪裡**：照[《第二次進院（1001）· 從零部署本系統之六：詳細版（附錄：查防毒排除清單、登不進去）》](visit-2-system-detail-6.md)的附錄「護理端頁面開得起來卻登不進去」第 2 步打了三條指令：

| 指令 | 結果 | 意思 |
|---|---|---|
| 第一條：`.env` 裡的 `CORS_ORIGINS`、`HD_PUBLIC_API_URL` | **沒有帶回來** | — |
| 第二條：`curl.exe -s http://<主機>:<後端埠>/api/health` | `{"status":"ok",…}` | 用 `.env` 裡那個 `<主機>` 連得到後端 ✓ |
| 第三條：帶 `Origin: http://<主機>:<護理端埠>` 看 `Access-Control-Allow-Origin` | **什麼都沒印出來** | **後端沒有放行這個來源** ✗ |

> 17:58 在現場曾回報第三條「印出 `…rol-Allow-Origin`」；回來後確認，**第三條的結果是空的**，以紀錄檔為準。

> **1029 補記**：第三次進院抄回第一條（`.env` 的 `CORS_ORIGINS` 與 `HD_PUBLIC_API_URL`）與執行中後端的名單，兩者都是 `http://<主機>:<護理端埠>`、網頁裡的位址也一致，**名單沒有寫錯，也不是改完沒 `up -d`**。第三條為什麼是空的已無法重現；1029 改成 IP 後護理站登得進去。見[《第三次進院紀錄（1029，部分成功）》](record-3-1029.md) O-01。

**這三條合起來的意思**：後端活著、`<主機>:<後端埠>` 連得到（第二條），但後端的 CORS 名單裡**沒有** `http://<主機>:<護理端埠>` 這個來源（第三條）。光這一點就足以讓登入出現 `Failed to fetch`。照附錄，原因只有兩種：

1. **`.env` 的 `CORS_ORIGINS` 寫的不是 `http://<主機>:<護理端埠>`**——例如仍是範例的 `hd-server`、寫成 `localhost`、名稱與 IP 的寫法和第三條用的不同、埠不對。17:47 問過「`hd-server` 要照寫還是寫主機名稱」，照抄過範例的可能性不低。
2. **`.env` 是對的，但改完之後沒有 `up -d`**：`.env` 只在容器建立時讀一次，執行中的後端還在用改之前的 `CORS_ORIGINS`。

第一條沒帶回來，所以分不出是哪一種。**兩種的處置都是改好 `.env` 之後 `docker compose --env-file $cfg up -d`，再打一次第三條，要印出 `Access-Control-Allow-Origin: http://<主機>:<護理端埠>`。**

**CORS 修好之後還要確認的兩件事**（現場沒查到這裡）：

1. **瀏覽器網址列上的網址**。17:45 問過「能不能用 `localhost` 開護理端」——實際部署用 `localhost` 開，網址列的來源與 `CORS_ORIGINS` 對不上，CORS 修好了照樣是 `Failed to fetch`。
2. **網頁裡寫死的後端位址**。`HD_PUBLIC_API_URL` 在 `build` 時寫進網頁檔案；若建置之後才把 `.env` 的位址改成真正的名稱，只 `up -d` 不會更新網頁裡的位址。

**下一次怎麼做**：見[第 7 節](record-2-1001-2.md#7-下一次進院) M-14 第 2 項，《從零部署本系統》V-17 把這些都排進了步驟本身。白話的分析在[《第二次進院紀錄（1001）之一：為什麼登不進去》](record-2-1001-login.md)。

### M-03 根目錄改放 C 槽

**發生了什麼**：本系統放在 `C:\hd\hd-tablet-care`，N-08 寫的是 `D:\hd-tablet-care`。

**為什麼會這樣**：紀錄沒有寫理由。0922 帶回來的資料裡，D 槽只剩約 4.6%（0922 紀錄 3.2 節），C 槽空間充足、Docker 的虛擬磁碟也在 C 槽，放 C 槽是合理的選擇。

**影響**：`.env` 的 `HD_BACKUP_DIR`、`HD_CONFIG_DIR`、`HD_SHELL_SRC_DIR` 都在 `C:\hd\hd-tablet-care` 底下；開工三行的 `$root` 也要用這個路徑。這是**資訊室要知道的位置**（備份目錄由院方送往另一台機器），Q-27 第 5 題「備份目錄與設定目錄放哪一顆磁碟」還沒有書面答覆，下一次要確認院方同意這個位置。

**手冊怎麼改**：《從零部署本系統》與[《`.env` 怎麼填》](ref-env.md)的根目錄改成 `C:\hd\hd-tablet-care`。

### M-04 主機位址要填什麼

**發生了什麼**：填 `.env` 的 `HD_PUBLIC_API_URL`、`CORS_ORIGINS`、`MDM_KIOSK_BASE_URL` 時，現場問了兩次：「`<主機>` 要怎麼查？」「`hd-server` 要照寫，還是寫我的主機名稱？」

**為什麼會這樣**：

- 當時[《之七：`.env` 怎麼填》](visit-2-system-env.md)的範例一律寫 `hd-server`，0.3 節雖然寫了「這些只是範例」，但範例本身長得像一個真的名字。
- 同一節說這一題「在 N-02 的問題清單裡」，**實際上不在**：W-03 那張表沒有「護理站、平板用哪個名稱或 IP 連主機」這一題，所以進院前沒問到，只能在現場自己決定。

**最後填了什麼**：紀錄沒有寫（照規定 `.env` 的值本來就不寫進文件，但「用的是主機名稱還是 IP」這一句應該記下來）。這一題與 M-01 直接相關。

**1005 補記**：用的是**主機名稱**（`hostname` 印出的那一個；有沒有帶 DNS 尾碼未記）。日後要改用 IP，照[《護理站登不進去與主機位址》](ref-login.md)；1029 已經換成 IP。

**手冊怎麼改**：W-03 補一列；《從零部署本系統》新增 V-08「決定主機位址」，放在填 `.env` 之前；《`.env` 怎麼填》的範例改寫成 `<主機>`，不再用一個像真名的範例。

### M-05 防毒排除清單是空的

**發生了什麼**：照詳細版的附錄「查防毒軟體與排除清單」（這一段就是當天在現場寫進去的）查到：

| 查什麼 | 結果 |
|---|---|
| 主機上的防毒 | Windows Defender，`hex` 是 `061100`——中間兩碼 `11`，**正在運作** |
| Defender 的排除清單 | **空的** |

**意思**：Docker Desktop 的虛擬磁碟（資料庫就在裡面）正被 Defender 即時掃描。這正是《進院通則》的停手條件「防毒排除當天加不了，有人說先跑跑看」那一條：SQLite 被即時掃描鎖住的錯誤是**間歇性、不固定重現**的。

**這一次沒有停手**：服務已經起來了。這不違反「停手」那一條的字面（沒有人提議「先跑跑看」），但效果相同。**在排除加上之前，這台主機不得輸入真實病人資料**——反正登入還沒通（M-01），目前也不會有人輸入。

**下一次怎麼做**：請資訊室把 N-05 第 4 項的 Disk image location 加入 Defender 的排除清單，加完用同一條 `Get-MpPreference` 看得到它。

> 紀錄寫的是「空」。`Get-MpPreference` 不是用系統管理員身分執行時，會印出一行 `N/A: Must be an administrator to view exclusions`，而不是什麼都不印。所以「空」可以視為真的沒有排除路徑；下一次用系統管理員身分再看一次確認。

**之後**：1029 用系統管理員身分再看仍是空的，這次沒有跟資訊室提（record-3-1029 O-04）；1116 使用者決定「不加也能跑，出現現象再請資訊室加」（[《第五次進院紀錄（1116，讀檔上線、平板與交接待補）》](record-5-1116.md) SR-11）。

### M-06 Docker 查不到 Docker Hub 的網域

**發生了什麼**：Docker 從 Docker Hub 下載映像檔時，**三次**查不到 Docker Hub 的網域（DNS）：

| # | 步驟 | 錯誤（節錄） | 怎麼過的 |
|---|---|---|---|
| 1 | N-11 第一次 `docker run node:20-bookworm-slim …` | `failed to copy: … Get "https://production.cloudfront.docker.com/…": … lookup production.cloudfront.docker.com: no such host` | 沒有過，見第 2 次 |
| 2 | N-11 同一條再打一次 | `failed to resolve reference "docker.io/library/node:20-bookworm-slim": failed to authorize: failed to fetch anonymous token: Get "https://auth.docker.io/token?…": … lookup auth.docker.io: no such host` | 沒有過，改用 PowerShell 產生 `JWT_SECRET`（M-07） |
| 3 | N-20 `docker compose … --profile shell build shell-builder` | `failed to resolve source metadata for docker.io/library/eclipse-temurin…`、`lookup production.cloudfront.docker.com: no such host` | **同一條指令再打一次就過了** |

三次的錯誤裡都有一句 `connecting to … via direct connection because Docker Desktop has no HTTPS proxy`，那只是說明「沒有設代理、直接連」，不是錯誤本身。

**怎麼讀這三次**：

- 第 1、2 次查不到的是**不同的網域**（下載站、認證站），第 3 次又回到下載站，而第 3 次重跑就過——**時好時壞，不是被擋掉**。
- 中間 N-13 的建置也要從 Docker Hub 下載 `node:20-bookworm-slim`，那一次成功了。
- N-06 的連線實測這次沒有記到結果；而且 `Test-NetConnection` 是 Windows 去查名稱，`docker pull` 是 Docker Desktop 自己去查，**兩條路不一定同時通**。原本的 N-06 只測前者，也沒有列 `production.cloudfront.docker.com` 這個下載站。
- 原因在院內 DNS 還是 Docker Desktop，這次沒有查到（沒有在出錯當下打 `Resolve-DnsName`）。

N-20 這一步含出錯與重來，總共花了 27～33 分鐘。

**手冊怎麼改**：

- 已改（1001 現場，`9d9975c`）：N-06／W-06 多測 `production.cloudfront.docker.com`；N-20／Y-04 的出錯表補上這一列與依序的處置（第一步就是「再打一次」，這次正是這樣過的）。
- 已改（《從零部署本系統》V-06）：連線實測之後，**先用 `docker pull` 把兩個基底映像下載下來**，讓 Docker 自己的那條路在建置之前就被測到；`no such host` 的處置集中寫在這裡，V-14、V-21、V-30 都指回來。
- Q-27 補一題問院內 DNS 對這些網域穩不穩（[M-12](record-2-1001-2.md#m-12-手冊要改的地方)）。

### M-07 產生 `JWT_SECRET` 的 `docker run` 下載失敗

**發生了什麼**：當時《之七》1.6 節的 `docker run --rm node:20-bookworm-slim node -e …` 先印出 `Unable to find image 'node:20-bookworm-slim' locally`（這一行本身不是錯誤，Docker 接著會自己下載），然後**下載失敗**；再打一次，換成另一個網域查不到（M-06 第 1、2 次）。

當時在現場只回報了第一行，開發端的回答是「這一行不是錯誤，等它下載」；**帶回來的照片才看出後面其實是下載失敗**。這也是 0922 紀錄就寫過的教訓：錯誤要抄原文，而且要抄到最後一行。

**手冊怎麼改**：已改（1001 現場，`05ebb61`）。改用 Windows 內建的 PowerShell 產生，輸出格式相同（64 個字元、只有英數字與 `-`、`_`），不必下載任何映像檔，也就不受 M-06 影響。
