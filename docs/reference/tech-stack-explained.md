# 這套系統是用什麼蓋的 — 給非技術背景的人

> 這頁不談程式，只用「蓋房子」把技術名詞講清楚，讓沒有工程背景的人也能聽懂會議上冒出來的那幾個詞。
> 需要精確定義與版本決策，請看[實作規格書](../requirements/implementation-spec.md)。

---

## 先講結論

| 專案裡的名詞 | 蓋房子裡的角色 | 一句話 |
|---|---|---|
| TypeScript | 建材 | 整套系統從頭到尾只用這一種建材 |
| React 19 | 蓋「前棟」的工法 | 病人與護理師看得到、摸得到的那兩棟 |
| NestJS 11 | 蓋「後棟機房」的工法 | 沒有人會走進去，但全部管線與門禁都在裡面 |
| Prisma 6 | 管線轉接頭 | 房子接到資料庫的標準接頭，換資料庫不必重拉全屋管路 |
| Vite 6 | 施工機具 | 蓋的時候用，交屋後不留在房子裡 |
| PWA | 組合屋式的門面 | 用網頁技術蓋的應用程式，不必送 App Store 審核 |

## 一、基地上有三棟樓

```
      ┌──────────────┐        ┌──────────────┐
      │  病人端 PWA  │        │  護理端 PWA  │   ← 前棟：有門面，人在裡面操作
      │  床邊平板    │        │  護理站主控台│
      └───────┬──────┘        └──────┬───────┘
              └───────────┬──────────┘
                  ┌───────┴────────┐
                  │   後端 API     │             ← 後棟機房：沒有門面
                  │  （伺服器）    │
                  └───────┬────────┘
                  ┌───────┴────────┐
                  │    資料庫      │             ← 地下的市政管線
                  └────────────────┘
```

- **前棟兩棟**：病人端是床邊平板的畫面（不必登入，像大樓的公共大廳）；護理端是護理站的主控台（要驗證身分，像有門禁的辦公樓層）。
- **後棟一棟**：所有規則、驗證、稽核紀錄都在這裡執行。病人與護理師永遠不會直接碰到資料庫，一律要透過後棟轉手。
- **資料庫**：不屬於這棟建築本身，比較像市政的地下管線，房子只是接上去。

---

## 二、建材：TypeScript

整個專案，三棟樓都用同一種建材，所以工程師換棟工作不必重學一種語言。

它跟一般建材（JavaScript）的差別在於：**每一根都事先裁切好、貼上尺寸標籤**。

蓋的時候，工人拿一根梁要往柱子上裝，標籤對不起來就當場被擋下來，根本裝不上去 —— 這叫「編譯時檢查」。
房子蓋完交屋時，標籤會被撕掉，真正立在那裡的還是原本的建材。

實務上的意義：**很多錯誤在還沒交給臨床端使用之前，就已經被擋掉了**，而不是等病人按下去才發現。

---

## 三、工法：React 19 與 NestJS 11

這兩個是同一層級的東西，都叫「框架」。框架不只是規範，它還附贈一整批預鑄件——牆板、樓梯、電箱都幫你做好，你只要組。

| | React 19 | NestJS 11 |
|---|---|---|
| 負責 | 前棟（病人端、護理端） | 後棟機房 |
| 幫你準備好的預鑄件 | 畫面怎麼組、按下去畫面怎麼跟著變 | 門禁、路由、排程、稽核掛勾 |
| 使用者感受得到嗎 | 感受得到，就是操作的手感 | 感受不到，但它壞了全樓停擺 |

### 一個常見的誤會

很多人會把它們理解成「React 管外觀、NestJS 管內部」。**這個說法會誤導。**

護理端要排班、要即時更新病人狀態、要處理呼叫，這些邏輯又多又複雜，全部發生在前棟裡，一點都不「外觀」。
比較準的講法是**前棟與後棟**：差別在「人走不走得進去」，不在「複不複雜」。

## 四、其他會聽到的名詞

- **PWA（漸進式網頁應用程式）**
  用網頁技術做的應用程式。可以像一般 app 一樣釘在平板首頁、全螢幕開啟，但**不必上架 App Store、不必逐台更新**——伺服器改好，平板下次開就是新版。對院內幾十台平板來說，這省掉的是每次改版逐台更新的人力。

- **Prisma 6（管線轉接頭）**
  目前資料庫暫時放在雲端的 PostgreSQL，未來要搬進院內的 MSSQL。有這個轉接頭，搬遷時換的是接頭，不是把全屋管路重拉一次。

- **Vite 6（施工機具）**
  開發時用來即時預覽、打包的工具。像工地的升降機與鷹架，交屋後不會留在房子裡。

- **共用零件廠（`packages/shared`）**
  兩棟前棟不是各做各的。共用的按鈕、共用的資料格式定義，統一在一個地方做好，兩邊都拿去用，樣式與規則才不會走鐘。

## 五、「四個服務」其實在同一棟樓裡

文件上會看到四個名字：**API Gateway、裝置綁定服務、推播通知服務、AI Proxy Service**。

聽起來像四棟樓，實際上是**同一棟機房裡的四個房間**。

```
        ┌──────────── 後端機房（一個 NestJS 程式）────────────┐
        │                                                      │
        │  ┌──────────┐  ┌──────────┐  ┌────────┐  ┌────────┐  │
        │  │ Gateway  │  │ 裝置綁定 │  │ 推播   │  │AI Proxy│  │
        │  │ 總櫃檯   │  │ 平板配對 │  │ 通知   │  │對外關口│  │
        │  └──────────┘  └──────────┘  └────────┘  └────────┘  │
        └──────────────────────────────────────────────────────┘
```

這樣做的理由很單純：**現階段規模還小，先用隔間把職責分清楚就夠了**。等哪天量體大到某個房間需要獨立的水電與樓地板，再把它拆出去蓋成獨棟（工程上叫「拆成微服務」）。因為隔間一開始就切乾淨了，將來要拆才不會牽一髮動全身。

各房間現況：

| 房間 | 它在做什麼 | 目前狀態 |
|---|---|---|
| API Gateway | 總櫃檯。所有請求都先到這裡，驗身分、分派、留紀錄 | 已完成 |
| 裝置綁定服務 | 把某一台平板配到某一位病人身上，時間到自動解除 | 已完成 |
| 推播通知服務 | 病人按了呼叫，讓護理站馬上知道 | 院內即時通知已完成；要讓護理師手機在院外也收得到的那一段還沒做 |
| AI Proxy Service | 對外的唯一關口。要問 AI 之前，先把病人可識別資訊拿掉再送出去 | 尚未動工，排在後續階段 |

**AI Proxy 為什麼一定要獨立成一個房間**：外部 AI 服務在院外。全院只留這一個對外出口，所有送出去的內容都得先經過它去識別化，才有辦法保證「沒有任何一筆病人可識別資訊流出院外」。出口只有一個，才守得住。

## 六、這個比喻到哪裡為止

任何比喻都有極限，這幾點要記得：

1. **房子蓋完就不動了，軟體會一直改。** 這裡的每次改版，比較像整棟樓在正常營業的狀態下抽換管線，所以才需要那麼多測試與稽核紀錄。
2. **兩棟前棟不是各蓋各的。** 它們用同一種建材、同一批共用零件，比較像同一份設計圖蓋出來的雙胞胎，只是用途不同。
3. **建材不會用完。** 軟體的「材料」可以無限複製，成本幾乎都在設計與施工的時間上，不在材料本身。

## 七、名詞速查

| 看到這個字 | 就想成 |
|---|---|
| 前端 / 前棟 | 人看得到、會操作的畫面 |
| 後端 / 後棟 | 沒有畫面的伺服器，規則與資料都在這裡把關 |
| 框架（React／NestJS） | 工法規範＋一整批預鑄件 |
| 編譯 | 施工前的尺寸總檢查，對不起來就不准開工 |
| 部署 | 交屋，把蓋好的東西放上伺服器讓人使用 |
| 微服務 | 把機房裡的某個房間拆出去，蓋成獨棟 |
| 稽核軌跡 | 監視器紀錄，誰在什麼時候動了什麼，事後查得到 |
