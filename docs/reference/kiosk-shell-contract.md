# 病人端外殼 App 契約

**契約第 1 版**（2026-09-27，迭代 12）｜對應 FR-S14、《[部署規範](../requirements/deployment-spec.md)》DEP-45、《[實作規格書](../requirements/implementation-spec.md)》3.3

> 外殼 App 是另一個私人 repo（`hd-kiosk-shell`），與本系統之間**只靠這一份契約對齊，不複製程式碼**。
> 真本在本系統：這份文件加上 `packages/shared/src/kiosk-shell.ts` 的型別與常數。
> 外殼 repo 不另寫一份，只在它的 `gradle.properties` 宣告自己實作哪一版。

---

## 1. 兩邊各管什麼

| | 本系統 | 外殼 App |
|---|---|---|
| 畫面與業務邏輯 | **全部**。病人端網頁改了，平板下次載入就是新版 | 沒有。它只是一個框 |
| 載入哪裡 | 提供病人端網址、`/api/` 轉送、`/shell/` 下載頁 | 載入佈建時輸入的那個網址，只放行同一個來源 |
| 身分 | 核發序號與金鑰，驗證每一個請求 | 儲存序號與金鑰，載入時交給網頁一次 |
| 逸出偵測 | 網頁定時回報、後端算狀態、護理端顯示 | 提供「現在是否釘選」給網頁問 |
| 版本 | 宣告目前的契約版本與最低可用外殼版本 | 宣告自己的版本與實作的契約版本 |
| 憑證 | `shell-builder` 產生院內 CA 與伺服器憑證 | 只信任建置時嵌入的院內 CA |

**判斷一件事該放哪一邊**：改外殼要逐台重裝 APK，改網頁不必碰平板。能放網頁的一律放網頁。

## 2. 載入網址與裝置身分

佈建時由護理師在外殼的設定畫面輸入三項，存在 App 的私有儲存：

| 欄位 | 格式 | 從哪裡來 |
|---|---|---|
| 主機位址 | `https://<院內主機>:<病人端埠>`，**必須是 https** | 設定目錄 `.env` 的 `MDM_KIOSK_BASE_URL` |
| 序號 | 英數字與連字號，3–32 字元（例 `TB-01`） | 護理端「裝置管理」註冊時填的 |
| 金鑰 | 後端產生的隨機字串 | 註冊成功時**只顯示一次** |

每次啟動時外殼載入：

```
https://<主機>:<埠>/?serial=<序號>&key=<金鑰>
```

兩個參數以 URL 編碼。網頁收到後存進自己的本機儲存，並**立刻把它們從網址列移除**
（`apps/patient-pwa/src/device.ts` 的 `readCredentials`），病人不會在畫面上看到金鑰。
金鑰遺失就在護理端解除佈建後重新註冊，不必重發 APK。

**外殼只放行同一個來源**（協定、主機、埠三者相同）。任何外部連結一律不開。

## 3. JavaScript 介面：`window.HdKioskShell`

外殼以 `addJavascriptInterface` 注入。**只有讀取，沒有任何會改變平板狀態的方法**。

| 方法 | 回傳 | 用途 |
|---|---|---|
| `shellVersion()` | 字串，三段數字，例 `"0.2.0"` | 前景回報附上，護理端比對最低可用版本 |
| `contractVersion()` | 整數，例 `1` | 前景回報附上，護理端比對契約版本 |
| `isPinned()` | 布林 | 這台平板現在是否釘選在外殼上（Android 螢幕固定） |

一般瀏覽器裡這個物件不存在，網頁照舊運作、不帶版本。呼叫丟出例外時網頁當作沒有外殼處理——**前景回報本身不能因此停掉**。

## 4. 版本握手：`GET /api/device/shell-contract`

**不需要裝置驗證**。外殼在載入網頁之前、每次回到前景時各問一次。

```json
{ "contractVersion": 1, "minShellVersion": "0.2.0" }
```

| 欄位 | 意思 | 由誰決定 |
|---|---|---|
| `contractVersion` | 本系統實作的契約版本 | `KIOSK_SHELL_CONTRACT_VERSION`（程式常數） |
| `minShellVersion` | 低於這一版的外殼要換 | 設定目錄 `.env` 的 `KIOSK_SHELL_MIN_VERSION`，空白用程式內建預設值 |

> **這一支端點的路徑與回應格式是契約裡唯一任何版本都不得變更的部分。** 版本不合時雙方就是靠它發現的；
> 改了它，舊外殼連「不相容」都說不出來。

## 5. 前景回報

網頁自己做（`apps/patient-pwa/src/offline-shell.ts`），外殼不送任何請求：

```
POST /api/device/foreground        （裝置驗證：序號＋金鑰標頭，與其他 /api/device/* 相同）
{ "foreground": true, "shellVersion": "0.2.0", "contractVersion": 1 }
```

| 時機 | 內容 |
|---|---|
| 每 30 秒 | 目前狀態 |
| `visibilitychange` | 立即 |
| `pagehide` | 立即送「不在前景」，以 keepalive 送出 |
| 釘選狀態改變（每 5 秒問一次外殼） | 立即 |

**`foreground` 在外殼裡是「畫面可見而且仍釘選」**。解開螢幕固定之後 App 常常還停在前景，只看畫面可不可見會把它報成「固定中」。

`shellVersion` 與 `contractVersion` **同進退**：只帶其中一個，後端回 400。一般瀏覽器兩個都不帶，後端留著上一次外殼回報的版本。

外殼要做的只有兩件事：不要擋住網頁的網路請求；讓 `visibilitychange` 如實反映真實狀態（不要用把 WebView 藏起來的方式切換畫面）。

## 6. 憑證與連線

| 項次 | 規則 |
|---|---|
| 協定 | **只准 HTTPS**。外殼的 `network_security_config.xml` 以 `base-config` 禁止明文連線 |
| 信任誰 | **只信任院內 CA**，不信任系統內建的任何 CA。院外的 HTTPS 在交握時就失敗 |
| CA 從哪裡來 | `shell-builder` 首次執行時在院內主機產生，建置 APK 時放進 `res/raw/hospital_ca.pem`。**不進任何 repo** |
| 伺服器憑證 | 同一把 CA 簽，主體別名是 `MDM_KIOSK_BASE_URL` 的主機名稱或 IP；病人端靜態服務以它提供 HTTPS |
| 憑證錯誤 | 一律拒絕，不給「仍要繼續」 |
| 後端在哪 | 與病人端同一個來源：病人端靜態服務把 `/api/` 轉給後端。外殼只需要信任一張伺服器憑證 |

換伺服器憑證不影響平板（CA 沒變）；**換 CA 要逐台重裝 APK**。

## 7. 版本與釘住

| 東西 | 在哪裡 | 規則 |
|---|---|---|
| 外殼版本 | 外殼 repo `gradle.properties` 的 `hdShellVersion` | 三段數字。發版時打同名 tag：`0.2.0` → `v0.2.0` |
| 外殼實作的契約版本 | 外殼 repo `gradle.properties` 的 `hdShellContractVersion` | 等於本文件的版本 |
| 本系統釘住哪一版外殼 | 本系統 `services/shell-builder/shell.pin` 的 `SHELL_TAG` | `shell-builder` **只建這一個 tag**，不建分支的最新狀態（DEP-44） |
| 本系統要的契約版本 | `shell.pin` 的 `SHELL_CONTRACT_VERSION`、`KIOSK_SHELL_CONTRACT_VERSION` | 兩者必須相同，`npm run verify:iteration12` 會核對 |

`shell-builder` 建置前核對三件事，任何一件對不上就不建：tag 存在、tag 裡的版本等於 tag 名稱、tag 裡宣告的契約版本等於 `shell.pin`。

## 8. 版本不合時兩邊看到什麼

| 情況 | 平板上 | 護理端裝置管理「外殼版本」欄 |
|---|---|---|
| 契約相符、版本不低於最低可用版本 | 正常 | 版本正常 |
| 契約相符、版本低於最低可用版本 | 正常（還能用） | **外殼過舊**（注意色） |
| 契約版本不同 | 畫面上方出現提示列：「這台平板的程式與系統版本不相容……請通知護理師更新平板程式」，**不蓋住網頁，求助區照常** | **版本不相容**（警示色） |
| 從未回報版本 | — | 未回報版本（迭代 12 之前的外殼、或在一般瀏覽器裡開的） |

最低可用版本一調高，護理端下一次重新取得清單（15 秒內）就會標出來，不必等平板再回報。
外殼版本或契約版本改變時寫一筆稽核「平板程式版本變更」。

## 9. 改契約的流程

改到第 2～6 節任何一項外殼看得到的東西，照這個順序：

1. 改本文件與 `packages/shared/src/kiosk-shell.ts`，**契約版本號加一**，在第 10 節記一筆
2. 外殼 repo 實作新版，`hdShellContractVersion` 跟著改，發版打 tag
3. 本系統 `shell.pin` 改成新 tag 與新契約版本
4. **兩個 repo 的 commit 訊息互相寫對方的 tag 或 commit**（實作規格書 3.3）
5. 部署新版本系統之後，所有舊外殼都會顯示「版本不相容」，直到逐台換上新 APK——**所以契約能不改就不改**，能放網頁的一律放網頁

只改外殼內部（例如換套件版本）不動契約：外殼版本加一、打 tag、改 `shell.pin` 的 `SHELL_TAG` 即可。
