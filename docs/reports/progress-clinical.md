## 一、一句話總結

系統已完成「**護理師指派平板給病人 → 病人在平板上回報症狀與求助 → 護理站即時看到並處理**」這條完整流程，並在這之上再完成兩層：

- **迭代 3（封閉網路化）**：所有資料不再離開醫院網路。測試資料庫改回開發者本機，推播通知整條移除，改由護理站一台常駐總覽螢幕保證通報被看見
- **迭代 4（AI 輔助內容）**：護理記錄草擬、個人化衛教與小測驗、SOP 查詢、心情與滿意度回饋、透析適足性計算都已可操作。**AI 產出一律由護理師審閱後才生效，AI 不取代任何簽核責任**
- **迭代 5（求助紀錄、班表、成效基準）**：求助結案改為選項登記，「確認通報」與「到達床邊」分開記錄；護理師班表可建立與匯入，違反勞動條件的班表**直接擋下儲存**；成效基準的建檔介面已就緒
- **迭代 6（閒置輪播）**：平板閒置達設定時間後，自動輪播本次療程的重要資訊。**求助按鈕全程在原位，碰一下螢幕任何地方就立刻回到主畫面，全程沒有聲音**；臨床數值每一則都標著「這是什麼時候量的」。院方臨床數值現在也可以用 Excel 或 CSV 整批匯入（**1005 迭代 16 起輪播拿掉**，改成下面的「本次透析」）
- **迭代 7～10（第一次進院前）**：更新系統前一定先備份並證明還原得起來；兩端介面重做；選項與題庫改成護理長自己改；平板跳出畫面時護理端看得到是哪一台
- **迭代 11～14.5（第一次進院之後）**：安裝方式改成院方要的容器；平板用掃 QR code 設定；**病人端首頁只剩三塊、問卷到時自己出現；護理端多了「簡易版」，一個畫面拖一下就完成一件事**；斷線時每一個畫面都看得出來，很多床同時按求助也不會把畫面蓋住；**病人平板改成白底，10 吋平板橫放直放字一樣大**（第〇之一節）
- **迭代 15～17（第二次進院之後，1005）**：**接上院方的透析紀錄 API**——病人、床位、透析開始與下機都從院方紀錄來，護理師只剩「第一次把平板配給病人」；病人平板中間改成**血壓與脫水量的折線圖**，院方一有新紀錄就自己更新；衛教與公告改成一條**跑馬燈，內容由 AI 寫、護理師只核准**（第〇節）。**院內真正的 API 還沒接過**，第三次進院先確認它的長相
- **迭代 17.8～18.1（1010）**：護理紀錄**簽核後一鍵複製、貼進院內的正式紀錄**，格式 DART（預設）或 SOAP、事件時間與院方量測寫在段落裡；緊急回報的圖示改成看圖就知道是什麼症狀；**三項高風險功能加上 Kt/V 趨勢推估做好了**——一律由固定規則計算、不經 AI，每一則都點得開依據、旁邊寫「僅供參考，非診斷結果」，**只在護理站專業版，病人平板上沒有**；書面確認改由系統管理者在系統裡登記（第六節）
- **迭代 19（1010）**：**成效儀表板**（全單位的數字對照上線前的成效基準，沒有基準就照實寫沒有）、**各班工作量**、開會用的**一頁式簡報**（好的數字與還沒做到的放在同一頁），醫院管理層登入只看得到這一頁；**獎勵制度**只算流程上的事（紀錄完不完整、衛教、通報處理完不完整），不看病人的臨床結果、不看誰回應得快，**沒有排名**，每位護理師看得到自己的每一筆、可以提出更正；個人層級的數字要護理部書面同意、規則公告、觀察期跑完才開得起來；**對外報表**只有合計、樣本少於 5 不出、要另一個人核准才拿得出去；另有一個資料全是虛構的**對外展示環境**
- **迭代 20（1010）**：**遊戲化之一**，不必等任何遊戲，先讓現有的問卷、衛教、跑馬燈做心理支援。做完問卷或衛教，平板出現一個安靜的「**完成了**」與一句「謝謝，護理師會照這個照顧你」——**與答案無關**，答什麼都一樣；衛教小測驗**不再給病人看錯幾題**，改成每一題一起看答案，答對的主題收進「**我的衛教小本子**」；病人可以從預設的**病友小撇步**裡點一則「我也是這樣做的」，**不能自己打字**，護理師核准才在跑馬燈播，署名只到「本中心病友」；跑馬燈多一類「**你知道嗎**」（老台灣的小常識、節令典故）；護理師可以（不是必須）對心情問卷「想讓我們知道的事」**回一張貼圖**，病人下一次透析時看到，**護理端沒有未讀數、沒有待辦**。三個開關，「現有功能的小幅遊戲化」預設開，另兩個預設關；**三個都關時跟以前一模一樣**

⏰ **成效基準的數字還沒有（0919 已排定量測）。** 建檔的地方做好了，但數字只能在紙本流程還在跑的時候量。**首波試用不會關上這扇門**——首波只開放少數護理師與少數病人，其餘班次照舊；真正關上它的是全單位改用系統的那一天（見第九節 Q-01）。

## 〇、1005 更新：第二次進院部分成功，院方 API 取代手動輸入

### 1001 第二次進院：系統裝起來了，護理站還登不進去

這一次照新手版手冊一步一步做，**三個服務在院內主機上起來了**，病人平板要裝的那支小程式也建好、金鑰備份核對過。
卡在最後一步：護理站按下登入時出現「Failed to fetch」，離院前沒有查出原因。
回來確認是後端的**放行名單裡沒有護理站那個網址**——瀏覽器每次登入都先問後端「收不收這個來源」，名單上沒有就不送出。
這是設定上的問題，不是系統壞掉；但登入不過，**備份還原、重新開機測試與平板都還沒做**，系統留在主機上跑著，還不能交給護理師用。

完整經過在《[部署手冊第十四冊之四](../deployment/14d-second-visit.md)》，下一次怎麼做寫成新手看得懂的《[第十五冊之三](../deployment/15c-why-1001-failed.md)》。
那一趟另外帶回兩件要資訊室知道的事：主機原本沒有安裝 Git（現場裝了），防毒軟體的排除清單是空的（Q-27）。

### 1004～1005：參考同院另一套系統，決定直接用院方的透析紀錄 API

院內同一處已有另一個團隊的透析中低血壓預警系統在跑，它每幾分鐘就向院方的透析紀錄 API 拿一次資料。
開發端讀完它的程式（不含任何真實資料），整理成《[同院 IDH 系統參考調查](../notes/idh-reference-survey.md)》，使用者 1005 逐項做了決定：

| 決定 | 對臨床端的意義 |
|---|---|
| **直接用那支 API**，預設每 3 分鐘抓一次，護理站可調 | 病人、床位、透析開始與結束、體重、每一筆血壓與脈搏，都從院方紀錄來 |
| 數值名稱照 API 的叫法（理想體重、目標脫水量、結束體重、實際脫水量）；讀到 0 不顯示 | 畫面上的名稱與院方系統一致，不必在兩套說法之間換算 |
| **那支 API 沒有抽血數值**，暫定拿不到 | 用到 BUN 的透析適足性**先關閉**；需要時再談來源（Q-26） |
| 低血壓門檻與處置選擇照同院系統 | 護理記錄的事件範本多一種「透析中低血壓處置」，並帶入院方最近一筆血壓（Q-03、Q-25 仍待臨床端確認） |
| 床號照醫院的編號，不設上限；平板跟著病人走 | 不必先設定幾床；病人換床，平板跟著他 |

這些是**使用者的決定，不是院方的答覆**：本系統能不能用那支 API、要不要報備，要問資訊室（Q-35）。

### 1005 新版需求：院方 API 判斷得出來的事，就不要再讓護理師做

排成迭代 15～17，**同日在開發端的電腦上完成**。開發端連不到院內的 API，驗收用的是一個產生假資料、格式相同的「模擬院方 API」；**真正的院方 API 要第三次進院才看得到**。

| 迭代 | 做什麼 | 對臨床端的意義 |
|---|---|---|
| 15 | 接上院方 API | 護理師**不必再新增病人、不必把病人拖上床、不必按下機**；理想體重與脫水量也不必再輸入。只剩一件事：**每位病人第一次用平板時，把平板配給他一次**（簡易版把平板拖到病人身上），之後他每次透析平板自己開始。院方資料判斷不了的事一律標出來給護理師：過了預計結束很久還沒有結束體重——「待確認下機」；平板沒有自動接上——一個斷開的圖示；院方資料超過 10 分鐘沒更新——床位圖上方一條提示。**護理師改過的（提前結束、換床），系統不會改回去**；每一件自動完成的事，紀錄上都寫著「院方資料同步」 |
| 16 | 病人平板改成「本次透析」 | 中間那一區不再輪播，改成兩張折線圖：**血壓**、**已脫水多少**（畫一條預計脫水的線），再加脈搏與體重，每個數字都標著量測時間。**院方一有新紀錄，圖就自己多一點，病人不必碰螢幕**。**不畫警戒線、不用紅色、不顯示低血壓預測**——病人端只給量測值，不給判讀。衛教與公告變成底部一條跑馬燈，以「標題：內容」整則慢慢跑過，**不必點開**；晚上不出現 |
| 17.1（1006） | 配平板改成每次透析配；停用、名稱整理 | **把病人拖到平板上就配好**，平板自己跑到院方資料說的那一床，護理師不必再把平板拖上床；**每次透析都配**（原本「每位病人配一次、之後自動接上」拿掉）。「鎖定」一律叫「停用」，改到系統管理裡做，**正在透析的平板停用不了**。護理端「跑馬燈內容」改叫「**公告與院內衛教**」、「衛教」改叫「**結束與離院衛教**」，離院衛教併進同一頁（帶回家的方式未定，暫不開放）。**不必進院就看得到病人平板透析到一半的樣子**（開發端一條指令就開出來） |
| 17.2（1007） | 簡易版中間改成平板；病人框好找人 | **畫面中間是一台一台的平板**，把病人拖上去就配好，**平板右上角自動出現院方資料的床號**；右邊只剩「病人」與「公告與院內衛教」兩框（護理師分床到專業版做）。病人框多一顆**重新整理**：按下去馬上向院方資料抓一次，**剛上機的病人排在最上面**；正在透析的越晚開始越上面，沒有在透析的依姓名筆畫排。一般護理師就能按 |
| 17.3（1007） | AI 寫的字一律是台灣的說法 | 系統裡**所有 AI 寫出來的字**——病人看的衛教、離院衛教重點、跑馬燈，護理師看的護理記錄初稿與 SOP 查詢回答——**不會出現簡體字與中國大陸的說法**。AI 寫出來有就退回請它重寫；重寫到最後一次還是有，也照樣交出來（核准前請護理師順手改掉），不會因此「產生失敗」。畫面上看不出重寫過。護理師自己寫的、改的字不受影響 |
| 17.4（1007） | 病人平板加回姓名與現在時間 | 病人平板最上面那一列：**床號旁邊是病人姓名，最右邊是現在時間**（例如 10:42）。原本為了鄰床看得到而只放床號，1007 改成放姓名——**鄰床看得到姓名是知情的取捨**。**病歷號仍不上平板首頁**；中間的圖與數字、底部跑馬燈仍然沒有姓名 |
| 17.5（1007） | 透析一律開始後四小時結束 | **不管院方資料有沒有寫預計結束時間，系統都當成開始後四小時結束**——本透析中心透析一律四小時，是院方規定。病人平板的進度條與中間的圖、護理站簡易版的平板格、專業版的即時總覽與總覽螢幕，**進度全部一樣長**；「待確認下機」也是過了開始後四小時再一段時間還沒有結束體重才標。原本護理站那一格會從平板配上的時間算起，剛配上的病人透析了一個多小時，進度條還幾乎是空的 |
| 17.6（1007） | 護理站畫面整理 | 簡易版公告與院內衛教**一次放一則草稿，現在換得到後面幾則**（原本只看得到第一則）。專業版**拿掉「病人」那一頁**——病人都由院方資料自動建立，護理站不必也不能自己新增；「裝置管理」改叫「**新增裝置**」，只管註冊新平板，底下照樣看得到每一台的狀態；停用與解除佈建都在系統管理。原本「目前有效綁定」那份清單與排班與指派重複，拿掉；**跨午夜的綁定要在排班與指派跳到前一天解除**（畫面上會列出來，按一下就跳過去）。排班與指派選病人時，**順序與簡易版病人框一樣**，旁邊有重新整理 |
| 17.7（1007） | 新增病人留一條備援；衛教拖到平板就播 | **護理師自己新增病人回來了，但預設關著**：院方資料裡沒有的病人才需要，由有權限的人在系統管理開啟「護理師自己新增病人」，**專業版排班與指派、簡易版病人框同時出現**，關掉就同時消失；之後院方資料出現同一個病歷號，以院方資料為準。系統管理的「平板停用」改叫「**平板管理**」（裡面還有解除佈建）。簡易版**公告與院內衛教拖到平板就只在那台播**：原本平板要有床號才放得上，現在**有病人配著就放得上**。開發用的床號改成醫院的寫法（A1、A2、A3、A5…，沒有 4 號床），不再是 1～15 |
| 17 | 跑馬燈內容由 AI 寫 | 護理師**只按核准或退回**，不必再自己寫；**沒核准的病人一個字也看不到**。簡易版右下那一框一次放一張草稿，卡上就是病人會看到的整句，按 ✓ 就上架、按 ⊘ 換下一張，拖到某一床就只在那一床播；要改字到專業版。標題 12 字、內容 60 字以內，超過的不能核准。**送進 AI 的只有主題或公告事由，沒有任何病人資料**。院內還沒有 AI 的這段期間，衛教草稿隨系統一起帶進去、公告由護理師自己寫，一樣要核准 |

病人平板上逐項為什麼留、為什麼不留，見《[軟體需求規格書](../requirements/srs.md)》FR-P09～P11 補充說明的對照表（以同院系統護理端的病人詳細資訊為藍本）。**請護理部看過那張表**（清冊 Q-09），有異議就改。

> **跑馬燈的開關預設關閉。** 速度預設每秒 2 個字，**開啟前想請護理長找一位病人在床上實際看過**，
> 「看得清、跟得上、不覺得累或煩」三題都過才開（Q-31 第 6 題，做法與記錄表在測試手冊迭代 16 分冊 §16.10）。
> 院內的衛教草稿這一版是開發端先備好的，**不是實驗室的 AI 寫的**；連上實驗室之後會重寫一批，核准權仍在護理師。

### 對護理站來說，少了什麼、多了什麼

| | 內容 |
|---|---|
| 少了 | 新增病人、把病人拖上床、按下機、輸入理想體重與脫水量、自己寫衛教與公告 |

### 病人端：首頁只剩三塊，該做的事自己出現

- 首頁只有**基本資訊**（床號、療程進度）、**輪播內容**、**緊急回報**三區，整頁不捲動。**首頁與輪播都不再顯示姓名與病歷號**（1005 迭代 16 起中間那一區改成「本次透析」；**1007 迭代 17.4 起基本資訊區加回姓名與現在時間**，病歷號仍不顯示，見第〇節）
- 透析前問卷、心情問卷、衛教**到了時點就自動全螢幕出現一次**，一題一頁，不必自己去找。病人按「回首頁」就先收起來，變成首頁上的一個小圖示，想做時再點
  （心情問卷預設綁定後 2 小時、衛教 3 小時，護理長可調）
- 求助類別依畫面大小分頁，每一格一樣大；「其他」那一框預設不顯示（14.2），病人仍有一顆「其他，請有人過來一下」可以按
- **主機斷電時，平板最慢約 11 秒就改成「請按床邊呼叫鈴」**（14.3）。以前要等很久才發現，那段時間求助按鈕看起來還能用
- **改成白底**（14.5）。醫師說透析室很暗，病人平板的背景由深色改成白底；字與按鈕的顏色跟著加深，對比仍維持病人端的高標準。晚上輪播區照樣會調暗
- **平板確定是 10 吋**（14.5）。依此調整後，**平板橫放、直放字一樣大**——以前直放時每一種字都小一號

### 護理端：多了一個「簡易版」

- **一個畫面做完日常的事**：一張床位圖，旁邊四個框（病人、護理師、平板、輪播內容）。
  把病人拖到床上就是排班加指派、把平板拖到床上就是換床、拖到停用區就是停用——**九項日常任務，每一項一個動作**。不想拖的，點一下來源、再點一下目的地也可以
- **做錯了 8 秒內可以復原**；下機與求助結案這兩件做了就回不去的事，**延後 8 秒才真的送出**，這 8 秒內可以改處理結果或取消。誤下機之後，病人也排得回床上（14.2）
- 「接下緊急通報」**不提供復原**——按下的時間是事實，不能讓它可以被收回
- **簡易版與專業版寫出的紀錄一模一樣**：簡易版底下呼叫的就是專業版原本那些功能，稽核軌跡不會因為換了畫面而不同
- 原本那一套（專業版）不動，隨時一鍵切換
- **斷線時每一個畫面都會閃紅框**（14.3）。以前只有護理站的常駐總覽螢幕會；其他畫面在主機斷電時停在最後一刻，看起來一切正常
- **很多床同時按求助時，通知不會蓋住整個畫面**（14.4）。以前專業版一則通知一條、往下疊，十則左右就把整個畫面蓋住，連「前往處理」都按不到；現在最多三條，其餘收成一行「還有幾則」，**最緊急的一定排在最前面**，別的護理師已經接起來的也會自己消失

> **想請護理長指定至少一位護理師，在第二次進院前實際操作過簡易版。**
> 簡易版是依開發端對護理站工作的理解做的，**被現場用過一次才算數**（Q-31）。
> 另外兩個數字也需要護理長：**透析室幾床、床號怎麼編、三個時段各從幾點到幾點**（Q-34）；目前先用 15 床與暫定時段。

## 三、系統在做什麼

透析中心採購了 15 台 Android 平板供病人在透析期間使用。本系統的目標，是把護理人員原本靠紙本、口頭、記憶完成的工作，搬到平板與護理站畫面上，減少重複勞動與資訊落差。

### 病人端（平板）

平板**沒有任何登入介面**。病人不需要輸入帳號、密碼，也不需要從清單裡挑自己的名字。

這是刻意的設計，理由有三：

1. 透析中的病人可能虛弱、視力不佳、認知負荷高，不適合承擔身分驗證的責任
2. 平板是機構共用裝置，若允許病人自行選擇身分，會產生資料誤植給錯誤病人的風險
3. 從法規角度，臨床資料的存取授權應該可以追溯到「**哪一位護理師、何時、為哪一位病人核准**」，而不是靠病人自證身分

因此平板在未被指派前，只顯示一句中性的等待文字：「請由護理人員為您開始使用」，畫面上不會出現任何病人可識別資訊。

護理師完成指派後，平板才顯示本次療程的資訊並開放下列功能。**1005 起接上院方 API 時，指派是自動的**：
病人第一次用平板時護理師配一次，之後院方紀錄上他的透析一開始，平板就自己開始（第〇節）。
**首頁只有三區**（基本資訊、本次透析、緊急回報），~~**不顯示姓名與病歷號**，只到床號~~ **1007 起基本資訊區有床號、姓名與現在時間，病歷號仍不顯示**；
問卷、心情、衛教到了時點會自動全螢幕出現一次，一題一頁（第〇之一節）：

| 功能 | 說明 | 上線於 |
|---|---|---|
| **透析前症狀問卷** | 10 題結構化問卷，涵蓋水腫、喘、發燒、血管通路出血等。每題預設為「沒有」，病人只需點選有感覺的那幾題 | 迭代 2 |
| **求助按鈕** | 取代傳統呼叫鈴。病人選擇求助類型（7 種）與急迫度（3 級），護理站立即收到 | 迭代 2 |
| **衛教與小測驗** | 閱讀護理師核可過的衛教內容，按「我看完了」留下完成紀錄；每次 5 題小測驗，答錯的題目下次優先再考 | 迭代 4 |
| **心情與滿意度** | 5 題、每題 5 個選項，每次療程最多填一份，病人自願填寫 | 迭代 4 |

## 五、幾個臨床上值得注意的設計決定

### 1. 求助的分派規則是「固定規則」，不是系統判斷

病人按下求助時，會自己選擇類型與急迫度。系統依照一張**預先訂好的對照表**決定通知誰：

| 急迫度 ＼ 類型 | 臨床類（身體不舒服／打針處或管路有狀況／機器在叫） | 非臨床類（如廁／環境調整／口渴） |
|---|---|---|
| 非常緊急 | 緊急處置團隊 | 緊急處置團隊 |
| 不太舒服 | 護理師 | 護理師 |
| 不急 | 護理師 | 護佐／行政支援 |

這張表的輸入**只有病人自己勾選的兩個欄位**，不讀取任何歷史資料、不做任何推論。這是刻意的：一旦系統開始「依資料判斷病人有多嚴重」，就進入了 SaMD 的範疇。

若臨床端認為這張分派表需要調整（例如某類求助應該一律找護理師），可以隨時修改，成本很低（Q-19）。

### 2. 症狀摘要是「原樣呈現」，不是評估

護理端看到的症狀趨勢摘要，只做兩件事：**把病人自己填過的答案列出來**，以及**數次數**（例如「近 30 天 5 次回報中，有 3 次自述水腫」）。

不加權、不分級、不預測、不產生建議文字。畫面上固定顯示一行提示：

> 以上為病人自行填寫之症狀原樣彙整，僅供決策輔助，非風險評估或診斷結果。

### 3. 離線時，症狀問卷與求助的處理方式相反

透析區網路若不穩定：

- **症狀問卷**：仍可填寫，資料先存在平板上，恢復連線後自動送出，不會遺失
- **求助按鈕**：**直接停用**，並明確告訴病人「目前無法即時通知護理站，請改用床邊呼叫鈴或直接出聲呼叫」

這是刻意的取捨。讓病人**誤以為**護理站已經收到求助，比誠實告知送不出去更危險。

**0929 補了一個缺口：主機斷電時。** 網路斷掉，平板馬上知道；但主機斷電時，平板的請求不會出錯、只會一直等，那段時間求助按鈕看起來還能用。現在每一個請求最多等 8 秒，**最慢約 11 秒就改成「請按床邊呼叫鈴」**；病人剛好按下求助時，最多約 8 秒就告知改按呼叫鈴。若護理站其實已經收到，兩邊都會處理——這是安全的方向。

### 4. AI 只寫草稿，簽核與核可永遠是護理師

迭代 4 所有 AI 產出都停在「草稿」：

| 產出 | AI 做什麼 | 護理師做什麼 | 病人何時看得到 |
|---|---|---|---|
| 護理記錄 | 依範本勾選內容與病人自述草擬敘述初稿 | 從 AI 初稿或預填文字擇一開始，修改後簽核 | 不給病人看 |
| 個人化衛教、離院衛教重點 | 產生衛教文字 | 核可或退回（退回必須填原因） | **護理師核可之後** |
| SOP 查詢 | 依檢索到的原文段落整理回答 | 對照下方列出的原文自行判斷 | 不給病人看 |

- 護理記錄**簽核後不可再改**。系統記下這份記錄「原樣採用 AI 初稿／修改 AI 初稿後採用／未採用 AI 初稿」，日後可以回頭看 AI 初稿實際被用了多少
- 預填文字是把勾選內容與病人自述**直接組成句子，不經過 AI**。AI 總開關關閉時，事件記錄照樣可以建立並從預填文字簽核
- 每一處 AI 產出的下方都固定顯示「本內容由 AI 產生，僅供決策輔助，非診斷結果」
- AI 總開關一關，所有 AI 按鈕與區塊**完全消失**（不是變灰）；已核可的 AI 衛教也同時從病人端撤下
- **AI 寫的字一律是台灣的說法**（1007，迭代 17.3）：含簡體字或中國大陸用語的產出不會交到護理師手上，系統先退回請 AI 重寫；最後一次仍不合格也照樣交出，畫面上看不出這道把關

### 5. SOP 查詢查不到就說查不到

SOP 查詢是先在收錄的文件裡找相符段落，**找得到才請 AI 整理回答；找不到就直接回答「查無資料」，完全不呼叫 AI**。這樣 AI 沒有機會在文件以外自己補內容。回答裡標出處（如 `[S1]`），下方列出被引用的原文段落。

目前收錄的 4 份（透析中低血壓、動靜脈瘻管照護、透析中肌肉抽筋、常用藥品查詢表）是開發端寫的**虛構範例**，畫面上都標「虛構範例」，**不可拿來做任何實際處置參考**。真實 SOP 到位後替換來源即可（Q-17）。

### 6. 心理社會趨勢只陳述事實，不下結論、不自動轉介

SRS 要求「長期趨勢偏離時建議轉介社工」。「偏離」要有說得清楚的定義，否則等於系統在替臨床下判斷。目前的暫定規則是：

> 近 3 次情緒相關題目（心情、睡眠、有人可以幫忙或聊天）的平均，比先前最多 6 次的平均低 1.0 分以上，就列出來；不足 6 份不套用。

列出時只寫事實（例如「近 3 次平均 2.1 分，先前平均 4.0 分，低了 1.9 分」），**不判斷心理狀態、不自動觸發轉介**，病人端也看不到比對結果。這組門檻請護理部與社工確認（Q-24）。

### 7. 透析適足性只算數字、只畫趨勢

URR 與 Kt/V 由公式計算（目前採 Daugirdas 第二代單池公式），不經 AI。計算由護理長或管理者執行，一般護理師可檢視結果。

趨勢圖上**不畫目標線、不標正常範圍、不做預測**——標目標值與預測都會開始接近臨床判斷，預測部分併入迭代 18 的規則引擎處理。每一筆結果都記下所用的公式版本與五筆原始數值，日後換公式時舊結果不會被改寫（Q-26）。

### 8. 常駐總覽螢幕是通報被看見的最後一道保證

推播移除後，護理師離開工作站時就沒有任何東西會「追著」提醒。因此護理站需要一台**不休眠、持續顯示總覽**的固定螢幕：

- 新通報出現時發出提示音，無人接收時每 60 秒再提醒一次
- 網路中斷時，最慢 45 秒內整個畫面出現紅框閃爍與「連線中斷」橫幅；恢復後自動重連，補上斷線期間的通報
- 伺服器暫時連不上時不會掉回登入畫面，恢復後自動回到原本的畫面

這台螢幕放在哪、提示音會不會吵到病人、病人姓名會不會被經過的訪客看到，都需要護理部決定（Q-10）。

**0929 起，斷線的紅框不只這台螢幕有**：護理端每一個畫面（專業版每一頁、簡易版）斷線時都會閃紅框、上緣出現紅底白字，分得出「連線中斷」「這台電腦沒有網路」「登入已失效」。**但系統仍然不會主動通知任何人**（推播已整條移除），所以這台常駐螢幕仍要一直開著、有人看得到。

### 9. 每一個動作都留下紀錄

系統記錄 109 種事件（0909 時為 32 種），每筆都含「誰、何時、對誰、做了什麼、結果如何」。

- 0909 已有：登入成功／失敗、帳號審核、權限異動、平板指派與解除、病人送出問卷與按下求助、護理師接手與處理完成
- **被阻擋的操作也會留下紀錄** — 例如同一位病人被誤指派到第二台平板、功能開關在條件不符時被要求開啟、帶真實病人資料的 AI 請求被擋下，這些失敗的嘗試本身都是一筆稽核紀錄
- 迭代 3、4 新增：功能開關切換、資料庫備份、臨床數值輸入、每一次 AI 呼叫、衛教的產生／核可／退回／病人讀完、測驗與回饋送出、護理記錄的建立／草擬／簽核、適足性計算、SOP 查詢
- 迭代 5 新增：護理師到達床邊、求助結案的處理方式與結果、後續追蹤事項的建立與結束、班表的建立與取消、班表匯入、床位指派、調班申請與核示、成效基準建檔，以及**被擋下的排班**與**被拒的匯入**——班表排不出來時，事後看得到系統擋了幾次、擋的是哪一條
- 迭代 7～14.2 新增：版本更新與備份驗證、內容與版位的調整、平板跳出與回來、平板程式版本變更、床位清單調整、平板換床、輪播內容的播放床位、**結案後補改處理結果**、**重新開啟當日排班**（誤下機之後排回床上）
- 迭代 15～17 新增：療程開始、下機與換床各自一筆，病人資料更新、把平板配給病人；院方資料抓不到、恢復更新、格式不符整次不收、**正式環境收到模擬資料而拒收**、透析開始了平板卻沒有自動接上；跑馬燈內容的草稿產生、核准、退回、撤回與上下架

病人沒有帳號，所以病人的動作記在「平板裝置」名下；系統自動觸發的事件（如逾時失效）記為 `SYSTEM`。**院方資料自動完成的事記為「院方資料同步」**，隨系統帶進去的衛教草稿記為「隨版本帶入」——兩個都是登入不了的系統帳號，紀錄上一眼分得出是人做的還是系統做的。

### 10. 「確認通報」與「到達床邊」為什麼要分開按兩次

護理師處理一筆求助，現在要按兩個按鈕：先「我接手」，到床邊後再按「我到床邊了」。多按一次是額外的操作，這是刻意的，理由值得說清楚。

兩個時間的差距，是這份資料**能不能被信任**的檢查點。

如果只記錄「確認時間」，而這個數字日後被拿去看反應速度，那麼最省力的做法就會變成「先按確認，再慢慢走過去」——數字很好看，病人等的時間一點也沒變短。分開記錄不是為了抓誰，是為了讓這種情況**在資料上看得出來**；真正要比較的「按鈴到到場多久」，也只有這樣才算得出來。

系統因此有一條刻意的規則：直接按「我到床邊了」而沒按過「我接手」時，系統會補上確認時間，但補的是**按下的當下**，不是到達時間——兩個欄位不互相填補。

這也正是 Q-01 成效基準要測的第一項：上線前「按鈴到護理師到床邊」要多久。有那個數字，之後才說得出「從 4.2 分鐘降到 1.6 分鐘」；沒有，就只能說「系統很方便」。

### 11. 班表是管理工具，不是計分板

班表資料很容易被拿去做別的事。系統這一側先劃了幾條線：

- 一般護理師**只看得到自己的班**，而且範圍是後端限制的，不是畫面上少列幾筆
- 資料表裡**沒有**「總分」「排名」這類欄位，也不會有「護理師 × 病人臨床結果」的關聯評分——這是《資料庫使用規範》的明文禁區
- 臨時調動的「候補人選排序」需要用到個人層級的工作負荷資料，**因此刻意沒做**，要等護理部與員工代表的同意流程（Q-04）

本迭代做的是請假與換班的申請與核示，不含任何排序或評分。

### 12. 排班違反勞動條件時是「擋下」，不是「提醒」

排班功能給的多半是建議，護理長可以不採納。只有一件事例外：**系統不得產出違反勞動法規的班表**。因此違反連續工時、班距、單日或單週上限、連續出勤日數時，儲存會被直接擋下，不是跳一個可以忽略的提示。

被擋下時，畫面不會只說「違反規定」，而是逐條列出：違反哪一條、規定的上限是多少、這張班表實際會到多少。護理長要知道怎麼改，才改得動。

目前用的是**勞動基準法的基本條件**（單班 12 小時、班距 11 小時、單日 12 小時、連續七日 46 小時、連續出勤 6 日）。醫院若另有更嚴格的內規，改的是系統設定裡的幾個數字，不必改程式（Q-14）。

至於「要不要讓護理長以『已知悉』覆寫」——這一題還沒做，也刻意先不做。要開這個口子需要護理部明確表態，而且覆寫一定要留紀錄與理由。

## 六、三項高風險功能：由排除改為有條件納入

以下三項在需求規格書中被標註為**高 SaMD 風險**，因為它們的輸出會直接影響臨床判斷：

| 編號 | 需求 | 風險性質 |
|---|---|---|

兩道閘門到齊之前，功能可以開發、可以用合成資料驗收，但**不能對真實病人開啟**。這不是靠人記得，而是寫在系統裡：三項各有獨立的功能開關（預設關閉）；~~**書面確認要由資訊室填進院內主機的設定檔才算開**，畫面上沒有人改得了~~ **1010 迭代 18.1 起，書面確認由系統管理者在系統管理「判斷規則」填上文號與理由才算登記**，每一次登記與取消都留紀錄，護理長以下改不了；每一條規則還要附上臨床端的書面依據才能「標為生效」。兩者缺一，系統只對測試用的合成病人比對，真實病人一律擋下並留紀錄。

開發端的設計取向是讓這三項盡量停在「提供資訊、由專業人員自行判斷」的一側：

- 用可攤開的固定規則計算，**不用 AI**
- 每一則提示都能點開看到依據：引用了哪些歷史資料、套用哪條規則、門檻值、規則版本
- 措辭是事實陳述（「近三次療程第 2 小時後曾回報頭暈」），不是結論（「病人有低血壓風險」）
- 不自動生效：不改醫囑、不改處理順序、不自動通知醫師
- 護理師逐則標記「已檢視」與「是否採納」，未採納可填原因

**分類判定權不在開發端**，上述做法是否足以佐證「非醫療器材」，需要法務判斷。

**院方建議血壓圖加虛線標出正常區間：判斷後不做。** 理由簡述如下，完整的理由與出處在 SRS FR-P11 補充說明「1010：血壓不畫正常區間」：

1. 透析中的血壓**沒有公認的正常區間**。KDIGO 2021 的血壓指引明文不適用透析病人；KDOQI 2005 的「透析前 < 140/90、透析後 < 130/80」證據等級弱，而且是透析前後的目標，不是透析中的區間
2. 透析病人的血壓與存活呈 J 形或 U 形，**死亡率升高的是血壓偏低的病人**；畫一條上限，等於告訴病人「高了就是不好」，與證據相反
3. 下限也畫不成一條線：透析前收縮壓 ≥ 160 的病人，低血壓的門檻是 100 而不是 90（同院 IDH 系統也是這樣分）
4. 線畫在病人自己的圖上，曲線一穿過去，病人看到的就是「我低血壓了」——這是「透析中預警」的範疇，屬高風險功能，要先過法務與臨床的閘門
5. 多數病人的曲線會整段落在線外，焦慮之下多按求助，加重的是護理站的工作

若院方要的是「看得出血壓的變化」，可以考慮只畫**這位病人本次開始時的血壓**當基準線（只是量測值，不是好壞的判準）；這一條沒有做，要院方再提出。

**迭代 7 已於 0919 完成**，對臨床端實際改變的有三件：

- **平板解除不掉的那個狀況修好了。** 大夜班跨過午夜、或前幾天留下的綁定，原本在畫面上整列消失、找不到按鈕可按；現在「裝置管理」有一份不分日期的有效綁定清單，每一列都能直接解除。指派平板時某一台不見了，畫面也會說出是「正綁給某位病人」還是「還沒佈建好」——那是兩件不同的事。

  三個月後比較兩批問卷結果時，系統知道哪一批答的是哪一版的題目，
  **不會拿改過之後的新題目去解讀之前的答案**。求助紀錄同理——病人按下當時螢幕上是哪幾個字，
  那幾個字就留在那一筆紀錄裡，之後改名不會回頭改它。
- **選項只能停用，不能刪除；「其他」連停用都不行。** 刪掉一個用過的選項，
  之前累積的紀錄就會指向一個不存在的東西；而「其他」是病人找不到適合選項時的唯一出路，
  把它關掉等於逼人亂選。另外，**「其他」被選了幾次看得到**——次數一高，代表這份清單不夠用，該回頭檢討。

> 另外，畫面上不再出現需求編號、英文代號或開關的內部名稱。那些字是給開發端看的，
> 出現在護理師面前只會讓人以為自己漏看了什麼。

**迭代 10 於 0920 完成實作與開發端演練**。這一個迭代對畫面幾乎沒有改動，
做的是「怎麼把系統搬進院內，以及搬進去之後怎麼照顧它」。對臨床端實際有感的有四件：

- **平板跳出畫面時，護理端看得到是哪一台。** 螢幕固定被解開、或有人把病人端切走，
  裝置清單那一列會在 30 秒內變成「已跳出」，並寫出什麼時候開始的。
  **護理師不必逐台目視**，交班時看一眼那張清單就知道要去處理哪幾台。
  平板關機或離線則顯示「失去回報」——**那兩件事要分得開**，處置不一樣。
- **網路斷了，平板的畫面仍然開得出來。** 以前網路一斷就是整片空白，連求助按鈕都按不到。
  現在畫面會照常出現、求助區照樣在原來的位置，**而且明白寫出「現在通知不到護理師」**——
  能按而沒有回應，比明說不能用更危險。透析區的 Wi-Fi 覆蓋還沒實測，這一層是為那件事準備的。
- **更新與回退實際演練過一次。** 停服務 → 備份 → **證明那份備份還原得起來** → 換版 → 啟動，
  全程留紀錄；退回去時是還原備份再換回舊版。演練時抓到一個缺陷：
  更新程式在「備份做完、正要動資料庫」那一刻會卡住自己——**而它只會在真的要改資料庫的那一次發作**，
  也就是最需要它成功的那一次。已修正。
- **安裝包做好了，但還沒在院內那台機器上試過。** 系統現在是一份可以用隨身碟帶進院內的檔案，
  自己帶著執行環境，不必在院內安裝任何東西、不必連網路。
  **不過「在開發機上可以」不等於「在院內那台可以」**，那一步要在現場做，
  結果會記進《[部署演練紀錄](../notes/deployment-drills.md)》。

> **每天要多做的那一件事還在**：前一天有重新開機的平板要重新釘一次螢幕固定。
> App 會自己起來，但固定不會自動恢復——**這一點守不住，只能讓它看得見**，
> 所以才有上面那張清單。

## 十一、名詞對照

| 系統用語 | 白話說明 |
|---|---|
| 裝置綁定／指派 | 護理師把某一台平板指定給某一位病人使用 |
| Session Token | 綁定後系統核發的限時通行證，綁定「病人＋平板＋這次療程」三者 |
| 稽核軌跡 | 操作紀錄，可事後追溯誰在什麼時候做了什麼 |
| MDM | 行動裝置管理，用來把平板鎖定成只能開這一個應用程式 |
| SaMD | 軟體醫療器材。若軟體的輸出會影響臨床判斷，可能需要主管機關認證 |
| PWA | 一種網頁式應用程式，可安裝到平板主畫面、具離線快取能力 |
| 常駐總覽螢幕 | 放在護理站、全天顯示總覽的固定螢幕，取代推播通知 |
| 功能開關 | 每一項有條件的功能都有一個開關，預設關閉；開啟要填核准依據並留紀錄，關閉時畫面上完全不出現 |
| 版位 | 某一項功能出現在哪裡：護理端上方那一列、「更多」選單裡，或是整個不提供。護理長可自行調整，每次調整都要寫理由 |
| 內容版本號 | 問卷、題庫、回饋題目每改一次就多一版。舊的作答永遠指向它當時那一版，回頭看數字時才不會張冠李戴 |
| 模擬模型 | 開發用的假 AI，產生固定格式的範例文字，讓畫面與流程先能完整驗收 |
| 院內地端推論 | AI 模型跑在醫院自己的伺服器上，資料不離開醫院網路 |
| 去識別化 | 送進 AI 之前移除姓名、病歷號等可直接識別個人的欄位 |
| 背景佇列 | AI 產生內容較花時間，系統先收下請求、在背後依序處理，畫面顯示進度，不卡住其他操作 |
| SSE | 伺服器主動把新通報送到護理端畫面的連線方式，全程在院內 |
| 簡易版／專業版 | 護理端的兩種畫面。簡易版是一張床位圖、拖一下完成一件事，每次登入預設；專業版是原本那一套。兩者留下的紀錄完全相同 |
| 外殼 App | 病人平板上的那支小程式，把病人端畫面鎖在最上層；另外維護，從院內下載頁安裝 |
| 佈建 QR code | 新平板第一次設定時，掃護理端畫面上的 QR code 就帶入主機位址與這台平板的金鑰 |
| 容器 | 0926 起的安裝方式：院內主機照一份寫好的圖說，把系統組成幾個互不干擾的「貨櫃」；資料放在貨櫃外，換版不會動到它 |
| AI 閘道 | 系統與 AI 機器之間的轉送站；換 AI 機器只改它的一份設定 |
| 院方 API | 院方透析紀錄系統開放給其他系統讀資料的管道。本系統每 3 分鐘去拿一次，只讀、不寫回 |
| 院方資料同步 | 系統依院方 API 自動完成的事（建病人、上床、開始、下機、換床）在紀錄上的操作者名稱；它是登入不了的系統帳號 |
| 模擬院方 API | 開發端用的假院方 API，產生格式相同的假資料；正式環境設定下指向它，系統拒絕啟動 |
| 探測工具 | 第三次進院時看院方 API 長什麼樣的小程式，只印欄位的格式，不印任何值 |
| 本次透析 | 病人平板首頁中間那一區：血壓與脫水量的折線圖、脈搏與體重，跟著院方紀錄自己更新 |
| 跑馬燈 | 病人平板首頁底部，衛教與公告以「標題：內容」整則跑過的一條；只播護理師核准過的 |
| CORS（放行名單） | 後端記著「哪些網址可以來要資料」的名單；護理站的網址不在上面，瀏覽器就不送出登入。1001 卡在這裡 |
