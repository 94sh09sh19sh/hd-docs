這份手冊假設你手上有一台 Windows 或 macOS 開發機與 Chrome。資料庫是一個放在專案目錄外的 SQLite 檔案，全程只在本機執行，不需要任何資料庫伺服器或雲端服務。

## 01 · 從 clone 到跑起來

- [ ] `a1` **［終端機］** Clone 專案並進入目錄。 → 取得 `apps/`、`packages/`、`demand_v1/` 三個資料夾。

```bash
git clone https://github.com/94sh09sh19sh/hd-tablet-care.git
cd hd-tablet-care
```

- [ ] `a2` **［終端機］** 確認 Node 版本 ≥ 20.11。 → `node -v` 顯示 v20.11 以上（開發環境用 v24）。版本太舊會在後續步驟出現語法錯誤。
- [ ] `a3` **［終端機］** 安裝相依套件。 → npm workspaces 會一次裝好 api、兩個 PWA 與 shared 套件，過程無紅字錯誤。

```bash
node -v
npm install
```

> **注意｜npm install 出現權限錯誤（EPERM／EACCES／operation not permitted）**
>
> Windows 上最常見的三個原因，依序排查：**①** 有 node 行程正抓著 `node_modules` — 關掉還在跑的 dev server 與編輯器再重試。**②** 專案放在 **OneDrive／雲端同步資料夾**底下，同步程式會鎖檔 — 把專案移到不同步的路徑。**③** 防毒即時掃描擋住寫入 — 把專案資料夾加入排除清單。都試過還是不行，再**以系統管理員身分**開啟 PowerShell 重跑；若已經裝壞了，先刪掉 `node_modules` 資料夾，執行 `npm cache clean --force` 後重來。

### 建立 .env

- [ ] `a4` **［終端機］** 複製環境變數範本。 → 專案根目錄出現 `.env`（已列入 .gitignore，不會被提交）。

```bash
cp .env.example .env
# PowerShell：Copy-Item .env.example .env
```

> **說明｜資料庫誰來建？你只要決定它放哪裡**
>
> 這一步要填的 `DATABASE_URL` 是「**我希望資料庫檔案出現在哪裡**」，不是「請填入現有資料庫的位置」。本系統的資料庫是**一個 SQLite 檔案**，沒有資料庫伺服器、沒有帳號密碼、不必事先安裝或建立任何東西。 **資料夾與檔案都不必先建**：下一小節的 `npm run prisma:migrate`（`a7`）會依你填的路徑，把中間缺的資料夾與 `hd.db` 一起建出來。所以填完 `.env` 時磁碟上還看不到任何東西，是**正常的** — `a13` 會回頭確認它真的生出來了。
>
> 順序只有一條規則：**先 `prisma:migrate`，再 `npm run dev`。** 跳過 migrate 直接啟動後端，後端不會幫你建檔案，只會噴 `Error code 14: Unable to open the database file`。

以下兩個變數是後端的**硬性必填**（缺了直接拒絕啟動），`SUPER_ADMIN_*` 兩個照本手冊走也等於必填， `BACKUP_DIR` 強烈建議一併填，其餘留空即用預設值：

| 變數 | 怎麼取得 |
|---|---|
| `DATABASE_URL`（**硬性必填**） | SQLite 連線字串：`file:` 加**絕對路徑**，例如 `file:D:/hd-data/hd.db`。路徑必須在**專案目錄外**的本機磁碟（不得為網路磁碟或 OneDrive 等同步資料夾），否則後端與 seed 會拒絕啟動。**資料夾與檔案都不必事先建立**，`a7` 的 migration 會一起建出來 |
| `JWT_SECRET`（**硬性必填**） | 自行產生，見下方指令 |
| `SUPER_ADMIN_WORK_ID` | 初始最高權限帳號的工作ID，例如 `ADMIN001`（英數字、底線、連字號，3–32 字元）。**這兩個留空後端照樣起得來，但資料庫裡不會有任何帳號，護理端登不進去** |
| `SUPER_ADMIN_INITIAL_PASSWORD` | 至少 8 字元。**首次登入後會被強制變更** |
| `BACKUP_DIR`（建議） | 備份輸出目錄，同樣須在專案目錄外的本機磁碟，例如 `D:/hd-data/backups`，目錄不必先建。未填時無法備份：§12 的備份還原演練、[迭代 3 分冊](iteration-3.md) §3.8、`verify:iteration3` 與 `verify:iteration4` 都會卡住 |

*在終端機執行 — 這是指令，不是要貼進 .env 的值*

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

> **注意｜這一行是指令，不是設定值**
>
> 把**整行貼到終端機執行**（PowerShell、cmd、Git Bash 都可以），它會印出一串長長的亂碼。**那串印出來的東西**才是要填進 .env 的值： `JWT_SECRET=印出來的那一串` 不要把 `node -e ...` 這行本身貼進 `.env` — 那樣後端啟動時會把整行當成金鑰，雖然不會壞掉，但等於用了一把人人都猜得到的鑰匙。

> **地雷｜常見地雷**
>
> `DATABASE_URL` 一定要用**絕對路徑**。寫成 `file:./dev.db` 這類相對路徑，後端會直接拒絕啟動——相對路徑會依 `schema.prisma` 所在位置解析，很容易落在專案目錄內，一不小心就把資料庫檔案提交進版控。

- [ ] `a11` **［終端機］** 決定資料庫檔案要放哪裡，把絕對路徑填進 `DATABASE_URL`。 → 挑一個**專案目錄外**的本機路徑即可，例如 `D:\hd-data\hd.db`，`.env` 就寫成 `DATABASE_URL=file:D:/hd-data/hd.db`（路徑用正斜線 `/`，含空白時整串加引號）。**現在不必去建那個資料夾，也不必建檔案**；此刻 `D:\hd-data` 還不存在是正常的。
- [ ] `a12` **［終端機］** 順手把 `BACKUP_DIR` 也填掉，例如 `BACKUP_DIR=D:/hd-data/backups`。 → 同樣不必先建目錄（第一次備份時自動建立）。現在跳過，等走到 §12 或迭代 3 分冊 §3.8 時得回頭改 `.env` 並重新啟動後端。
- [ ] `a5` **［終端機］** 填完 `.env` 後，確認上表的五個變數都有值。 → `DATABASE_URL` 以 `file:` 開頭、後面是專案目錄外的絕對路徑；`JWT_SECRET` 是一串亂碼而不是 `node -e ...`；`SUPER_ADMIN_WORK_ID` 與 `SUPER_ADMIN_INITIAL_PASSWORD` 都有填。

### 建立資料庫與測試資料

- [ ] `a6` **［終端機］** 先編譯共用型別套件（後端與前端都依賴它）。 → `packages/shared/dist/` 產生 cjs 與 esm 兩份輸出。
- [ ] `a7` **［終端機］** 建立資料庫 schema。 → **依 `DATABASE_URL` 建出中間缺的資料夾與 SQLite 檔案**，套用五個 migration（`init`、`iteration3_closed_network`、`iteration4_ai_content`、`iteration5_help_resolution_shifts_baseline`、`iteration6_carousel_file_import`），最後顯示資料庫已同步。資料庫是空的時候 Prisma 會順便跑一次 seed，下一步再跑也不會重複建立。
- [ ] `a8` **［終端機］** 產生合成測試資料。 → 建立 **8 位病人**（`HD-TEST-0001`～`0008`）與 **15 台平板**（`TB-01`～`TB-15`），裝置金鑰寫入 `apps/api/.device-keys.json`。**這 15 台平板預設尚未納入 MDM**，稍後要手動註冊。
- [ ] `a13` **［終端機］** 確認資料庫檔案真的生出來了。 → 你在 `a11` 指定的資料夾已經存在，裡面有 `hd.db`（seed 完約 700 KB 起跳）。看到它就代表「填路徑 → 檔案誕生」這件事完成了，可以往下啟動。後端跑起來之後（`a9`）旁邊會再多出 `hd.db-wal` 與 `hd.db-shm` 兩個 WAL 附屬檔，**要搬移或備份時三個是一組**，不要只拿主檔。

```bash
npm run build:shared
npm run prisma:migrate
npm run db:seed
```

*`a13`：把路徑換成你在 `a11` 填的*

```bash
ls -l /d/hd-data            # Git Bash
# PowerShell：Get-ChildItem D:\hd-data
```

這三行各做一件事，缺一不可：

| 指令 | 在做什麼 | 為什麼需要 |
|---|---|---|
| `npm run build:shared` | 把 `packages/shared` 的 TypeScript 編譯成 JS。裡面是**前後端共用的型別與常數**：求助分派規則、109 種稽核動作的代號、權限碼、導覽版位的預設值。 | 後端與兩個 PWA 都會 import 它。沒編譯過，後端一啟動就找不到模組。**之後每次改動 shared 都要重跑**（`npm run dev` 會自動先跑一次）。 |
| `npm run prisma:migrate` | 讀 `apps/api/prisma/schema.prisma`，把資料表建到 `.env` 的 `DATABASE_URL` 指向的 SQLite 檔案，並產生 Prisma Client。本專案目前有六個 migration（迭代 3～7 各一個）。**這一支是開發用的**，正式環境改用 `npm run db:update`，見[迭代 7 分冊](iteration-7.md) §7.6、§7.7。 | 你的資料庫一開始是**空的**。這步建出 nurses、patients、devices、device_bindings、symptom_reports、help_requests、audit_logs 等資料表。沒跑過，後續任何操作都會失敗。 |
| `npm run db:seed` | 灌入**虛構**測試資料：8 位病人（`HD-TEST-0001`～`0008`）與 15 台平板（`TB-01`～`TB-15`），並把平板金鑰寫到 `apps/api/.device-keys.json`。 | 沒有病人就不能建排班，沒有平板就不能指派。**它不建立任何護理師帳號** — 那是後端啟動時依 `.env` 自動建立的。可重複執行，已有資料時會自動略過。 |

> **地雷｜`.device-keys.json` 只對應「最後一次 seed 的那顆資料庫」**
>
> `db:seed` 寫出的 `apps/api/.device-keys.json` 是**明文金鑰**，而資料庫裡只存雜湊值。拿另一個 `DATABASE_URL` 再跑一次 `prisma:migrate` 或 `db:seed`（例如 §12 換資料庫、或臨時試另一個檔案），這個檔案會被**整份覆蓋**，原本那顆資料庫的平板金鑰就再也拿不回來，病人端只會停在「裝置尚未佈建」。補救只有兩條：在護理端「新增裝置」（1007 以前叫裝置管理）重新註冊幾台新平板（`f20`，會當場給新金鑰），或照 §11 重置資料庫重來。

*Git Bash / cmd.exe*

```bash
curl -i http://localhost:3000/api/overview
```

*PowerShell — 注意是 curl.exe*

```bash
curl.exe -i http://localhost:3000/api/overview
```

> **注意｜PowerShell 要打 curl.exe**
>
> PowerShell 把 `curl` 設成 `Invoke-WebRequest` 的別名，它**不認得 `-i`、`-s`、`-H` 這些參數**，會噴「找不到符合參數名稱 i 的參數」。加上 `.exe` 才會呼叫到真正的 curl。**本手冊後面所有 curl 指令，在 PowerShell 都要改成 `curl.exe`**；Git Bash 與 cmd.exe 直接用 `curl` 即可。

## 03 · 主線 A — 裝置綁定完整流程

這是 Iteration 1 的驗收主線：**登入 → 核准護理師 → 建排班 → 指派平板 → 病人端顯示 → 解除綁定 → 稽核可查**。走完這一段，系統的骨架就確認可用了。

### 身份驗證與審核

- [ ] `c1` **［護理端］** 以 `.env` 的 `SUPER_ADMIN_WORK_ID` 與初始密碼登入。 → 登入失敗跳「工作ID 或密碼錯誤」請看下方的排查框。**全新資料庫**：直接被導到「變更密碼」畫面，藍色提示說明此帳號正在使用 .env 的初始密碼，未變更前不能使用其他功能。
- [ ] `c2` **［護理端］** 設定新密碼（至少 8 字元，兩次輸入需一致）。 → 顯示「密碼已變更 / 所有既有登入階段已撤銷」，必須用**新密碼**重新登入。**請記下新密碼** — .env 裡的舊密碼從此失效。
- [ ] `c3` **［護理端］** 重新登入，確認進入主控台。 → 頂端導覽列出現：即時總覽、緊急通報、排班與指派、帳號審核、病人、裝置管理、稽核軌跡。右上顯示你的工作ID 與 `SUPER_ADMIN`。
- [ ] `c4` **［護理端］** 登出 → 切到「註冊申請」分頁 → 申請一個新帳號，工作ID 用 `N001`、姓名自訂、密碼至少 8 字元。 → 顯示申請已送出、等待審核。
- [ ] `c5` **［護理端］** 立刻用 `N001` 嘗試登入。 → 被拒，訊息「註冊申請尚待審核，核准後才能登入」（HTTP 403）。這是 3.1 節第 2 點的要求。
- [ ] `c6` **［護理端］** 以管理者登入 → 「帳號審核」→ 在「待審核註冊申請」找到 `N001` → 按「核准」。 → 綠色提示「已核准 N001，該帳號現在可以登入」，下方「帳號與權限」表中該列狀態變成 `ACTIVE`。
- [ ] `c7` **［護理端］** 登出，改用 `N001` 登入。 → 登入成功。導覽列**只有**即時總覽、緊急通報、排班與指派、病人、裝置管理 — 沒有「帳號審核」與「稽核軌跡」（一般護理師無此權限）。

> **地雷｜登入一直顯示「工作ID 或密碼錯誤」**
>
> 這個訊息只代表兩件事之一：**工作ID 不存在**，或**密碼不對**（刻意不區分，避免洩漏帳號是否存在）。依序排查： **① 別用打的，用複製貼上。**最常見的兇手是**中文輸入法**：密碼結尾若有 `!`，中文模式下會打成全形的 `！`，長度一樣但完全不同的字元。切到英數模式，或直接從 `.env` 複製貼上。 **② 檢查瀏覽器自動填入**有沒有蓋掉你輸入的值（欄位變黃底就是）。 **③ 你是不是已經改過密碼了？**手冊的 `c2` 步驟會強制變更密碼，**改完之後 .env 裡的初始密碼就永久失效**。 **④ 用下面的指令直接驗**（完全不經過鍵盤與瀏覽器）。

*在專案根目錄執行，用 .env 的原值直接打 API*

```bash
node -r dotenv/config -e "fetch('http://localhost:3000/api/auth/login',{method:'POST',headers:{'Content-Type':'application/json'},body:JSON.stringify({workId:process.env.SUPER_ADMIN_WORK_ID,password:process.env.SUPER_ADMIN_INITIAL_PASSWORD})}).then(r=>Promise.all([r.status,r.text()])).then(([s,t])=>console.log(s,t.slice(0,80)))" dotenv_config_path=.env
```

> **補充｜怎麼判讀上面的結果**
>
> 印出 **200** 加一串 `accessToken` → 帳號與密碼**都是對的**，問題百分之百出在瀏覽器的輸入（回頭看 ① 和 ②）。印出 **401** → 資料庫裡的密碼確實跟 `.env` 不一樣了，多半是已經改過密碼。用你當初設定的**新密碼**登入；真的想不起來，就照 §10 重置資料庫。印出 **403** → 帳號存在但狀態不是 ACTIVE。連不上（ECONNREFUSED）→ 後端沒啟動。

## 05 · 離線韌性

SRS 4.4 對離線行為有兩條**方向相反**的要求：症狀回報必須能暫存並自動補傳；求助則必須明確告知無法通知護理站。這一節同時驗證兩者。

> **注意｜為什麼求助不做離線暫存**
>
> 讓病人**誤以為**護理站已收到，比誠實說明送不出去更危險。因此離線時求助按鈕直接停用並引導改用床邊呼叫鈴。這是刻意的設計取捨，不是缺漏。

- [ ] `e1` **［病人端］** 在病人端按 F12 開 DevTools → Network 分頁 → 把 Throttling 下拉選成「**Offline**」。 → 只影響這個分頁，護理端不受影響。
- [ ] `e2` **［病人端］** 等 3–5 秒觀察主畫面。 → 出現黃字「目前沒有網路連線。症狀問卷仍可填寫並暫存於本平板；求助請改用床邊呼叫鈴。」求助按鈕副標變成「**目前無法即時通知護理站**」。
- [ ] `e3` **［病人端］** 點進「我需要協助」。 → 頂端橘色警示框：「目前無法即時通知護理站。請改用床邊呼叫鈴，或直接出聲呼叫附近的護理人員。」底部按鈕顯示「**離線中，無法通知**」且**停用**。
- [ ] `e4` **［病人端］** 回上一頁 → 點進「填寫透析前症狀問卷」。 → 頂端黃字：「目前沒有網路連線。您仍可以填寫，送出後會暫存在這台平板，恢復連線時自動傳送給護理站。」**問卷本身完全可用**（題庫打包在前端，不需連線）。
- [ ] `e5` **［病人端］** 把「呼吸會喘」點成**嚴重**，按「送出給護理站」。 → 回主畫面顯示綠字「**已暫存在這台平板。恢復連線後會自動送給護理站，資料不會遺失。**」以及「尚有 **1** 筆症狀回報等待傳送」。
- [ ] `e6` **［病人端］** 把 Throttling 改回「No throttling」，等約 10 秒。 → 離線提示消失，出現綠字「**已將 1 筆離線暫存的症狀回報送出給護理站**」，等待傳送的計數歸零。
- [ ] `e7` **［護理端］** 看即時總覽該病人列。 → 病人自述症狀更新為「**呼吸會喘・嚴重**」（顯示的是最新一份回報）。
- [ ] `e8` **［護理端］** 「稽核軌跡」→ 篩選「病人送出症狀問卷」→ 看最新一列的說明欄。 → 包含「送出方式 **離線暫存後補傳**」。系統把即時送出與離線補傳分開記錄，且**保留病人當初填寫的時間**，不會被補傳時間覆寫。

> **說明｜資料為什麼不會掉**
>
> 病人按下送出時，資料是**先寫進 IndexedDB 佇列、再嘗試上傳**，成功才移除。就算平板在上傳途中斷電或被 Kiosk 重新載入，資料仍在。後端再用平板產生的識別碼去重，所以重複補傳也不會變成兩筆。

### 6.10 求助分派規則（FR-N03）

分派只看**病人自選**的類型與急迫度，不讀歷史資料、不做推論 — 所以不落入已排除的風險分層範疇。規則表如下，可逐格驗證：

| 急迫度 ＼ 類型 | 臨床類（身體不舒服／打針處或管路有狀況／機器在叫） | 非臨床類（需要上廁所／環境調整／口渴或肚子餓／其他） |
|---|---|---|
| **非常緊急**，請馬上過來 | 緊急處置團隊 | 緊急處置團隊 |
| **不太舒服**，請盡快過來 | 護理師 | 護理師 |
| **不急**，方便時再過來 | 護理師 | **護佐／行政支援** |

- [ ] `f50` **［病人端］** 送出「機器在叫」＋「不急，方便時再過來」。 → 「分派：**護理師**」。臨床類型即使不急也不會下放給護佐。

## 07 · 自動化驗收腳本

手動走完之後，用這幾支腳本做回歸。它們會建立少量以 `VERIFY` / `V2` / `V4` / `V5` / `V6` 標記的合成資料，並逐項斷言。

> **注意｜前置**
>
> 後端**必須先啟動**（`npm run dev` 或 `npm run dev:api`），腳本才連得上。 `verify:iteration3` 與 `verify:iteration4` 另外**要求 `.env` 有 `BACKUP_DIR`**（`a12`）：兩支都會做一次線上備份再用還原檔驗證，沒設定會直接判定該步驟失敗，而不是略過。

```bash
npm run verify:acceptance   # Iteration 1
```

## 08 · 收工 — 正確關閉與重新啟動

測試告一段落時，把服務關乾淨比想像中重要：Windows 上 `Ctrl+C` 有機會沒把子行程一起帶走，下次啟動就會撞 `EADDRINUSE`，而且你會以為是程式壞了。

### 正常關閉

- [ ] `j1` **［終端機］** 回到執行 `npm run dev` 的那個終端機視窗，按一次 **Ctrl+C**。 → concurrently 會一併停掉後端與兩個 Vite，三色 log 停止輸出，提示字元回到你手上。後端有註冊 shutdown hook，會**正常中斷資料庫連線**後才結束，不是硬砍。
- [ ] `j2` **［終端機］** 如果你另外開了視窗跑 Prisma Studio（§06.7），**那個視窗要各按一次 Ctrl+C**。 → port 5555 釋出。它是獨立行程，不會被 `npm run dev` 的 Ctrl+C 帶走。
- [ ] `j3` **［病人端］** 關掉病人端與護理端的瀏覽器分頁。 → 病人端每 3 秒輪詢一次、護理端持有一條 SSE 長連線。不關不會壞（後端一起來它們會自動接回），但排查問題時這些背景請求會干擾你判讀 log。

### 確認真的關乾淨

這一步別跳過。四個 port 分別是：後端 `3000`、護理端 `5173`、病人端 `5174`、Prisma Studio `5555`。

*PowerShell*

```bash
Get-NetTCPConnection -LocalPort 3000,5173,5174,5555 -State Listen -ErrorAction SilentlyContinue |
  Select-Object LocalPort, OwningProcess
```

*Git Bash / cmd.exe*

```bash
netstat -ano | findstr /R /C:":3000 " /C:":5173 " /C:":5174 " /C:":5555 "
```

- [ ] `j4` **［終端機］** 執行上面任一版本。 → **沒有任何輸出＝已經關乾淨**。若列出 port 與 PID，代表有行程沒被帶走（Windows 上這其實蠻常見的）。
- [ ] `j5` **［終端機］** 有殘留的話，用上一步查到的 **PID** 精準結束它。 → 再查一次應該就沒有輸出了。

*用 PID 結束（把 33244 換成你查到的數字）*

```bash
# PowerShell
Stop-Process -Id 33244 -Force

# cmd.exe
taskkill /PID 33244 /F

# Git Bash 要用雙斜線
taskkill //PID 33244 //F
```

> **地雷｜不要一次砍光所有 node**
>
> `Get-Process node | Stop-Process -Force` 這種寫法**非常危險**。一般開發機上通常同時有十幾個 node 行程 — 編輯器、語言伺服器、其他專案、甚至 Claude Code 本身都可能是 node。**一定要先查出 port 對應的 PID，再針對那個 PID 結束。**

### 關掉之後，哪些東西還在

| 項目 | 關閉服務後會怎樣 |
|---|---|
| **所有資料**（帳號、病人、排班、綁定、問卷、求助、稽核） | 都在 `DATABASE_URL` 指向的 SQLite 檔案裡，**完全不受影響**。要搬移或備份時，主檔與 `-wal`／`-shm` 是一組，不要只拿主檔。 |
| **進行中的綁定** | **不會**因為關掉服務而失效，資料庫裡仍是 `ACTIVE`。下次啟動照常運作；若一直沒人管，超過 `BINDING_MAX_HOURS`（預設 6 小時）後，背景掃描會自動讓它逾時失效。 |
| **病人端未送出的離線回報** | 存在瀏覽器的 IndexedDB，**關掉分頁不會遺失**。下次用同一台平板開啟、且該筆綁定仍有效時會自動補傳。但綁定若已被解除，補傳會被拒絕，資料會在清除流程中一併移除。 |
| `.device-keys.json` | 留在 `apps/api/`，下次還能用。除非你重跑 `db:seed` 或重置資料庫。 |
| **登入權杖** | 存在瀏覽器 localStorage，**下次開啟仍是登入狀態**（除非超過 `JWT_EXPIRES_IN`，預設 8 小時）。 |

### 收工前建議做的兩件事

- [ ] `j6` **［護理端］** 看即時總覽，把還在「療程進行中」的綁定按「下機結束」。 → 不是必要步驟，但下次進來時資料狀態乾淨，也比較貼近真實流程（病人下機才離開）。
- [ ] `j7` **［病人端］** 看病人端有沒有「尚有 N 筆症狀回報等待傳送」。 → 若有，先確認網路正常、等它顯示「已將 N 筆離線暫存的症狀回報送出給護理站」再關 — 否則那筆資料可能會隨著綁定解除被清掉。

### 下次重新啟動

- [ ] `j8` **［終端機］** 在專案根目錄執行 `npm run dev` 就好。 → **不需要**重跑 `prisma:migrate` 或 `db:seed` — 資料都還在。`build:shared` 也不用手動跑，`npm run dev` 會自動先跑一次。
- [ ] `j9` **［終端機］** 若啟動時出現 `EADDRINUSE :::3000`。 → 就是上次沒關乾淨。回到本節「確認真的關乾淨」，查 PID 然後結束它，再啟動一次。

> **補充｜只重新啟動後端**
>
> 改了後端程式碼時，`npm run dev` 用的是 `nest start --watch`，會**自動重新編譯並重新啟動**，不必手動關。此時護理端的即時總覽會短暫顯示「串流中斷，改為定時更新」，後端起來後自動變回「即時連線中」。

### 怎麼帶憑證

*取得護理端權杖並呼叫（bash）*

```bash
TOKEN=$(curl -s -X POST http://localhost:3000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"workId":"ADMIN001","password":"你的密碼"}' | node -pe 'JSON.parse(require("fs").readFileSync(0)).accessToken')

curl -s http://localhost:3000/api/overview -H "Authorization: Bearer $TOKEN"
```

*平板端呼叫*

```bash
curl -s http://localhost:3000/api/device/session \
  -H 'x-device-serial: TB-01' \
  -H 'x-device-key: <金鑰>'

# 寫入資料時再加上 Session Token
curl -s http://localhost:3000/api/device/symptom-reports/mine \
  -H 'x-device-serial: TB-01' \

  -H 'x-session-token: <上一步回應中的 sessionToken>'
```

> **注意｜PowerShell 使用者**
>
> 上面兩段的 `curl` 全部要改成 `curl.exe`，否則 PowerShell 會用 `Invoke-WebRequest` 的別名去解析，參數對不上。取權杖那段用了 bash 語法（`$(...)`、單引號），在 PowerShell 建議改用 Git Bash 執行，或改寫成 `Invoke-RestMethod`。

## 10 · 疑難排解

| 症狀 | 原因與處理 |
|---|---|
| PowerShell 執行 curl 噴「找不到符合參數名稱 i 的參數」 | PowerShell 的 `curl` 是 `Invoke-WebRequest` 的別名。改打 `curl.exe`，或改用 Git Bash。 |
| `prisma:migrate` 噴 `getaddrinfo ENOTFOUND binaries.prisma.sh` | **Prisma 的執行引擎不在 npm 套件裡**，是安裝套件時由安裝後腳本另外下載的（約 40MB）。只要 `node_modules` 是在沒有成功下載引擎的情況下產生的——離線安裝、跳過安裝後腳本、或從別處複製過來而排除了二進位檔——第一次用到 Prisma 指令時就會現場去下載 | **0920 已修，舊版才會遇到。** 迭代 7 的 `PRISMA_ENGINES_DIR` 只接上了**後端啟動**；`prisma migrate`、`prisma generate` 是另外開的行程，不經過那一段，而 **Prisma CLI 不讀 `node_modules/@prisma/engines`**——它只看自己的 `node_modules/prisma/` 與 `node_modules/.cache/prisma`，兩邊都沒有就現場下載。現在所有 prisma 指令都經過 `apps/api/scripts/prisma-cli.mjs`，執行前把路徑指好（見《部署規範》DEP-30）。遇到這個錯誤先確認這一步在不在：`npm run check:offline` 會盤點版本與指令有沒有走這一層。若 `node_modules/@prisma/engines/` 底下真的沒有兩個數十 MB 的執行檔，那是安裝沒裝完，連網重跑一次 `npm install` |
| 病人端在本機開了好幾個分頁，結果只有最後一個認得出自己是哪一台平板 | **同一個瀏覽器的所有分頁共用同一份儲存空間**，後佈建的裝置序號與金鑰會蓋掉先佈建的。這是本機測試環境特有的，正式環境一台平板一支 App、各自獨立 | 每一台模擬平板用**不同的瀏覽器設定檔**（或不同瀏覽器、或無痕視窗各開一個），不要在同一個視窗裡開多個分頁 |
| 護理端找不到「解除綁定」的按鈕，但裝置管理頁看得到那台平板正綁著人 | 解除的入口原本只掛在「當日排班」清單上，而那份清單依**排班日期**篩選（預設今天）。綁定的排班日期不是今天時，那一列不會出現 | **迭代 7 已修**（實作規格書 3.15）：改到「裝置管理」的**目前有效綁定**清單解除，那份清單不分日期。主控台也會在有跨日綁定時明白提示並提供跳過去的連結。驗收步驟見[迭代 7 分冊](iteration-7.md) §7.1 |
| `npm install` 出現 EPERM／權限不足 | ① 關掉還在跑的 node 行程與編輯器；② 專案不要放在 OneDrive 等同步資料夾；③ 把資料夾加入防毒排除清單。仍失敗再以系統管理員身分開 PowerShell 重跑。 |
| 用 .env 的帳密登入卻說「工作ID 或密碼錯誤」 | 最常見是**中文輸入法把 `!` 打成全形 `！`** — 改用複製貼上。其次是你已經走過強制變更密碼那步（.env 的初始密碼從此失效）。用 §03 的 node 指令可直接判斷是哪一種。 |
| 後端起不來，噴 `Error code 14: Unable to open the database file` | **多半是跳過了 `npm run prisma:migrate` 就直接 `npm run dev`。** 建資料夾與建檔案是 migration 在做，後端自己不會建。先補跑 `a7`、`a8`（`a13` 確認檔案出現）再啟動。其次才是 `DATABASE_URL` 打錯：要是**絕對路徑**、用正斜線、含空白時整串加引號。 |
| 後端起來了，但護理端怎麼登都不行，log 有黃字說未設定 `SUPER_ADMIN_*` | `.env` 漏填 `SUPER_ADMIN_WORK_ID` 或 `SUPER_ADMIN_INITIAL_PASSWORD`，資料庫裡沒有任何帳號。補進 `.env` 後重新啟動即可，**資料庫不必重建**（那段邏輯只在「資料庫尚無任何使用者」時執行）。 |
| 病人端一直「裝置尚未佈建」，但金鑰是從 `.device-keys.json` 複製的 | 那份檔案對應的是**最後一次 seed 的那顆資料庫**。中途換過 `DATABASE_URL` 或在別的資料庫上跑過 `prisma:migrate`／`db:seed`，檔案就被覆蓋了，明文金鑰拿不回來（資料庫只存雜湊）。在「裝置管理」重新註冊一台取得新金鑰（`f20`），或照 §11 重置資料庫。 |
| 每個動作都要等好幾秒 | 本機 SQLite 單次往返約 2 ms，慢下來多半是資料庫檔案放在網路磁碟機、OneDrive 之類的同步資料夾，或被防毒即時掃描。換到本機磁碟並加入防毒排除清單。 |
| `prisma migrate reset` 噴 `database disk image is malformed`，資料庫剩 0 byte | 清空成功、建表失敗（多半是後端還開著，WAL 檔被抓住）。照 **§11** 的地雷框：關乾淨 → 把 `hd.db` 與 `-wal`／`-shm` 三個一起刪 → `prisma:deploy` + `db:seed` 重建。 |
| 後端 log 出現 `SQLITE_BUSY` | 有第二個行程在寫同一個檔案（多半是上次沒關乾淨的後端，或開著的 Prisma Studio）。照 §08 查出 PID 收乾淨，後端是唯一的寫入者。 |
| `EADDRINUSE :::3000`（或 5173／5174） | 上次沒關乾淨，有殘留行程佔著 port。照 **§08** 查出 PID 再精準結束；**不要**一次砍光所有 node 行程。 |
| 前端出現 CORS 錯誤 | `CORS_ORIGINS` 沒包含前端網址。預設是 `http://localhost:5173,http://localhost:5174`。 |
| 操作到一半一直跳 401 | 權杖過期（`JWT_EXPIRES_IN` 預設 8h），或你剛變更密碼／被降權 — 兩者都會主動撤銷既有登入階段。重新登入即可。 |
| 病人端一直停在「裝置尚未佈建」 | 序號或金鑰不對，或該平板還沒在後端註冊。用 `.device-keys.json` 的值，或在護理端重新註冊一台取得新網址。 |
| 指派平板的下拉選單是空的 | 平板需**同時**符合：已 MDM 納管、未被鎖定、未被其他病人佔用。seed 出來的 15 台預設**未納管**。 |
| 改了 `packages/shared` 沒生效 | 要重跑 `npm run build:shared`。`npm run dev` 啟動時會自動跑一次。 |
| 稽核軌跡少了某筆記錄 | 稽核寫入失敗**不會中斷**主流程，只在後端 log 留下 error。去終端機找 `稽核軌跡寫入失敗`。 |

## 11 · 重置到乾淨狀態

> **地雷｜會刪除所有資料**
>
> 下面的指令會**清空整個資料庫**並重建。只在測試環境執行。

反覆測試會累積大量帳號、病人與平板。想從乾淨狀態重走一遍手冊時：

```bash
cd apps/api
npx dotenv -e ../../.env -- prisma migrate reset
```

- [ ] `i1` **［終端機］** 先照 §08 把服務關乾淨，再執行重置（會要求你打字確認）。 → 刪除所有資料表 → 重新套用五個 migration → **自動重跑 seed**（8 位病人、15 台平板、新的 `.device-keys.json`）。 **後端沒關就跑，多半會停在下面那個 `malformed`。**
- [ ] `i4` **［終端機］** 重置後確認資料庫檔案不是 0 byte。 → `DATABASE_URL` 指向的位置有一個數百 KB 的 `hd.db`。**若看到 0 byte，代表 `i1` 中途失敗了**，照下方的地雷框收拾。
- [ ] `i2` **［終端機］** 重新啟動後端。 → 因為資料庫已無任何使用者，後端會依 `.env` **重新建立 SUPER_ADMIN**，並且 `passwordChangeRequired` 回到 true — 下次登入會再次強制變更密碼。
- [ ] `i3` **［護理端］** 從 §03 重新走一遍。 → 全新環境，所有步驟的預期結果與手冊一致。

> **地雷｜重置噴 `database disk image is malformed`，資料庫變成 0 byte**
>
> `migrate reset` 是**兩段動作**：先清空、再建表。撞到殘留的 `-wal`／`-shm` 檔時，它會清完才失敗，於是你得到一個 **0 byte 的 `hd.db`**——舊資料已經沒了，新的也還沒建起來。看起來很嚇人，其實只是做到一半。
>
> 最常見的成因是**後端還開著**（SQLite 只容許一個寫入者，WAL 檔還被它抓著），其次是上一次不正常結束留下的 WAL 檔。收拾方式固定三步，資料反正已經沒了，刪掉沒有損失：
>
> ```bash
> # ① 先照 §08 確認 3000／5173／5174／5555 都沒有行程監聽
> # ② 把主檔與兩個附屬檔一起刪掉（路徑換成你的 DATABASE_URL） rm -f /d/hd-data/hd.db /d/hd-data/hd.db-wal /d/hd-data/hd.db-shm
> # PowerShell：Remove-Item D:\hd-data\hd.db*
>
> # ③ 回專案根目錄重建（不必再跑 reset） npm run prisma:deploy -w @hd/api npm run db:seed ```
>
> 跑完的結果與 `i1` 成功時完全相同：五個 migration、8 位病人、15 台平板、新的 `.device-keys.json`。 **三個檔案一定要一起刪**，只刪主檔的話，殘留的 WAL 會再讓下一次建表失敗一次。

> **補充｜你目前這個資料庫**
>
> 2026-09-10 改用本機 SQLite 時是從零開始建立的，Supabase 上的舊資料依《資料庫使用規範》第 15 條不遷移、直接捨棄。之後殘留的少量資料是驗收腳本留下的（工作ID 以 `VERIFY`／`V2`～`V6` 開頭、病歷號以 `HD-VERIFY`／`HD-V2`／`HD-TEST-V3` 之類的前置字開頭），不影響功能。

*步驟 k3–k4*

```bash
npm run prisma:deploy -w @hd/api
npm run db:seed
npm run dev
```

### 線上備份與還原演練

- [ ] `k5` **［護理端］** 以護理站管理者登入 →「系統管理」→「資料庫與備份」→「立即備份」。 → 備份歷程多一列「成功」，有檔名、大小與 SHA-256；稽核軌跡多一筆「資料庫線上備份」。 `BACKUP_DIR` 裡備份檔旁邊多一個同名的 `.sha256`（0929 起）。服務起不來、查不到備份歷程時，雜湊從這個檔拿。
- [ ] `k6` **［終端機］** 把剛才那份備份還原到另一個路徑。 → 依序印出雜湊比對相符、完整性檢查 ok、各資料表筆數。不會碰到使用中的資料庫。
- [ ] `k7` **［終端機］** 把 `DATABASE_URL` 暫時指向還原出來的檔案，重新啟動後端並登入。 → 帳號、病人、稽核紀錄都在。演練完記得把 `DATABASE_URL` 改回正本。

*步驟 k6*

```bash
npm run db:restore -- --from <BACKUP_DIR 裡的備份檔> --to <新的絕對路徑> --sha256 <備份旁邊同名 .sha256 檔的第一欄>
```

> **地雷｜不要直接複製資料庫檔案**
>
> 服務執行中直接複製 `.db` 可能拿到不一致的狀態，而且 WAL 模式的 `-wal`／`-shm` 與主檔是一組，只拿主檔會漏資料。備份一律用上面的線上備份（`VACUUM INTO`），備份檔也不得放到雲端硬碟或個人隨身碟（《資料庫使用規範》8.1）。
