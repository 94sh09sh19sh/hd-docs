> 《[完整手動測試手冊](manual-test-guide.md)》的分冊之一，對應《實作規格書》4.5 節。
> 共用的環境準備、啟動與疑難排解都在主手冊，這一冊只寫迭代 7 的部分。
> 操作端色籤（**護理端**／**病人端**／**終端機**／**資料庫**）的意思見主手冊 §00。

**FR-S12 版本更新不得破壞既有資料、DEP-15 時區、DEP-24 AI 端點可關、DEP-30 引擎隨包攜帶、DEP-31 遷移指令分離，以及《實作規格書》3.15 的解除綁定缺陷。**

**這一冊沒有新功能。** 它驗的是三件「不修就不能部署」的事：解除綁定找不到入口、離線建置失敗、更新會弄壞資料庫。前兩件在畫面與終端機上看得出來，第三件只有在真的走過一次更新流程時才看得出來——**§7.6 是本冊最重要的一節，請不要跳過**。

> **0919 補記**：正式主機由「本專案專用」更正為「與其他專案共用」之後，§7.10 是新加的一節（DEP-37）。
> 共用主機上最常見的失敗不是效能不夠，而是別的專案把磁碟寫滿、或先佔走了本系統要用的連接埠——
> **這兩種情形在測試階段一次都不會出現**，只能靠設定上先擋住。

## 7.1 · 不依日期的「目前有效綁定」清單（3.15 修法 1）

缺陷的原貌：**解除綁定的唯一入口掛在「當日排班」清單的每一列上，而那份清單依排班日期篩選（預設今天）。** 綁定所屬的排班日期不是畫面上選的那一天，那一列根本不會出現，自然沒有按鈕可按。

- [ ] `q1` **［護理端］** 主控台把日期切到**昨天**，建立一筆排班，指派平板給它。
- [ ] `q2` **［護理端］** 日期切回**今天**（或重新整理，預設就是今天）。
  → 剛才那筆排班**不在畫面上**。這是正常的，那份清單本來就依日期篩選——缺陷不在這裡，在於它是唯一的入口。
- [ ] `q3` **［護理端］** 進「裝置管理」，看新的「目前有效綁定」清單。
  → 昨天那筆**在裡面**，而且標示著它屬於哪一天（後面跟著「（不是今天）」）。
- [ ] `q4` **［護理端］** 直接在這一列按「手動解除」。
  → 解除成功，訊息寫出是哪位病人、哪一台平板。**全程沒有改過任何日期**——這就是驗收標準第 1 條。
- [ ] `q5` **［護理端］** 解除後重新整理。
  → 那一列從「目前有效綁定」消失（它只列有效的），平板的「綁定狀態」回到「未綁定」。

## 7.2 · 跨日提示與跳過去的連結（3.15 修法 2）

- [ ] `q6` **［護理端］** 再建一筆昨天的排班並指派平板，然後回到主控台、日期停在今天。
  → 畫面上方出現一則提示：**另有 N 筆有效綁定不在今天**，列出病人、平板與它所屬的日期。
- [ ] `q7` **［護理端］** 讀那段文字。
  → 它說得出**為什麼**會這樣（大夜班跨過午夜之後，綁定的排班日期是前一天），不是只說「有東西在別的日期」。
- [ ] `q8` **［護理端］** 按提示裡的日期連結。
  → 日期切到那一天，那筆排班出現，列上的解除按鈕可以按。
- [ ] `q9` **［護理端］** 把該日期的綁定解除，回到今天。
  → 提示消失。**沒有有效的跨日綁定就不該有這段提示**，它不是常駐說明。

## 7.3 · 指派下拉選單說得出濾掉的原因（3.15 修法 3）

連帶的第二個症狀：那台平板因為還綁著，在指派清單裡被濾掉，於是變成「這台平板不見了」，而畫面上不會說明為什麼。

- [ ] `q10` **［護理端］** 讓 A 平板綁著某位病人，把 B 平板解除註冊（裝置管理 → 解除註冊）。
- [ ] `q11` **［護理端］** 在主控台展開任一筆未指派排班的平板下拉選單。
  → A 與 B **都看得到**，只是選不下去（灰的），而且各自寫著原因：A 是「這台正綁給 ○○○（病歷號），要先解除綁定」，B 是「這台尚未完成佈建納管」。
- [ ] `q12` 確認這兩句**不一樣**。
  → 「這台正綁給某位病人」與「這台還沒佈建」是兩件不同的事，要做的處置也不同。都變成「不見了」就是這個缺陷的本體。
- [ ] `q13` **［護理端］** 裝置管理的平板清單看「可否指派」欄。
  → 同一句原因也在這裡，可以一眼掃過整批平板。
- [ ] `q14` **［護理端］** 把 B 平板重新納管。
  → 兩邊都變回「可指派」，下拉選單裡它可以選了。

## 7.4 · 解除是冪等的（3.15 次要原因 1）

護理師按下解除的那一瞬間，逾時掃描可能剛好先一步把它結束掉。那是**目標狀態已經達成**，不是失敗。

- [ ] `q15` **［護理端］** 任意指派一台平板，然後**開兩個分頁**都停在能按到解除的畫面。
- [ ] `q16` **［護理端］** 在第一個分頁按「手動解除」，成功後到第二個分頁按同一筆的解除（不要重新整理）。
  → **回報成功**，訊息寫「這筆綁定已於 ○時○分 由 ○○○ 因『護理師手動提前解除』結束，不需要再解除一次。」
  → **不是**紅色錯誤，也不是「此綁定狀態為 RELEASED」這種讓人以為壞掉的字。
- [ ] `q17` **［護理端］** 到稽核軌跡查這一刻。
  → 有一筆「解除綁定：目標狀態已達成」。冪等不等於什麼都沒發生——**誰在什麼時候按了那一下，仍然要留下來**。

## 7.5 · 執行環境：時區與服務執行帳號（DEP-15）

時區錯八小時，班表會整張錯開一格，而且錯得很像「排班排錯了」，不像系統設定錯誤——**這種錯誤不會有人回報成程式問題**。

- [ ] `q18` **［終端機］** 看後端啟動時的那幾行。
  → 有一行寫著「伺服器時區：Asia/Taipei（現在 ⋯⋯）｜執行身分：帳號@主機名稱」。
- [ ] `q19` **［護理端］** 系統管理 → 資料庫與備份，最上面的「執行環境」。
  → 時區、現在時間、服務執行身分、執行環境（正式／開發）、監聽連接埠、版本標記、資料庫引擎七項都看得到，時區那一格是勾的。
- [ ] `q20` **［終端機］** 用不符的時區啟動一次（**這一項會讓服務起不來，是預期的**）：
  ```bash
  cd apps/api
  # PowerShell：$env:DEPLOYMENT_ENV='production'; $env:TZ='UTC'; node dist/main.js
  DEPLOYMENT_ENV=production TZ=UTC node dist/main.js
  ```
  → **拒絕啟動**，訊息寫出目前是什麼時區、要求的是什麼、為什麼要管（班表會整張錯開一格），最後附上剛才是用哪個帳號在檢查。
- [ ] `q21` 把 `TZ` 與 `DEPLOYMENT_ENV` 都拿掉，照平常啟動。
  → 正常起來。**開發機的時區不同不會擋啟動**，只會在日誌上提醒一行。
- [ ] `q22` ⚠️ **部署當天才做得到的一項**：在正式主機上，用**服務實際執行的那個帳號**（不是管理員的互動式工作階段）看一次 `q19` 的畫面。
  → 主機時區正確不代表服務執行帳號取得的時區正確，這兩件事要分開確認。這一項同時是部署前置檢查清單第 2 條。

## 7.6 · 更新流程：備份、驗證還原、前滾、紀錄（規範第 18 條）

**第一次正式部署之後，每一次更新面對的都是真實病人資料，而那份資料只有一個檔案。**

> **這一節要先停掉後端**（`Ctrl+C`）。更新流程的第一步就是確認服務已停止；服務還開著時它會擋下來，那是對的。演練時可以加 `--allow-running` 繞過，但**正式更新不要用**。

- [ ] `q23` **［終端機］** 後端還開著時先執行一次：
  ```bash
  npm run db:update
  ```
  → 停在第 1 步，說「後端服務還在執行⋯⋯請先停止服務再執行」。
- [ ] `q24` **［終端機］** 停掉後端，再執行一次。逐步看它做了什麼：
  → `[3]` 產生一份更新前備份（檔名 `hd-before-update-⋯`），印出大小與 SHA-256。
  → `[4]` **把那份備份實際複製到另一個路徑、開起來、跑完整性檢查**，並印出各資料表的筆數。「有備份」和「備份能用」是兩件事。
  → `[5]` 以「套用既有遷移」的方式前滾（沒有待套用的遷移時它就直說沒有）。
  → `[6]` 寫入更新紀錄，最後印出三件人要做的事。
- [ ] `q25` **［終端機］** 檢查備份目錄。
  → 多了一個 `hd-before-update-⋯.db`；**驗證用的那份暫存檔不會留下**（它只是用來證明還原得起來）。
- [ ] `q26` **［護理端］** 啟動後端，進系統管理 → 資料庫與備份 → 最下面的「版本更新紀錄」。
  → 剛才那次在列表上：結果「完成」、版本、更新前備份的檔名、備份驗證「已還原驗證」加各資料表筆數、套用的遷移、執行者（作業系統帳號@主機名稱）。
- [ ] `q27` **［護理端］** 同一頁往上看「備份歷程」。
  → 剛才那份備份也在，方式寫「更新前強制備份」，與手動、排程分得出來。
- [ ] `q28` **［護理端］** 稽核軌跡查這一段時間。
  → 至少四筆：版本更新開始、更新前備份已驗證還原、資料庫線上備份、版本更新完成。**沒有這份紀錄，半年後發現資料對不上時，沒有人答得出是哪一次更新帶進來的。**
- [ ] `q29` **［終端機］** 現在驗最重要的那一條——**備份做不成就不准往下走**。停掉後端，把備份目的地指到一個不存在的磁碟：
  ```bash
  cd apps/api
  # PowerShell：$env:BACKUP_DIR='Z:/no-such-place'; node scripts/db-update.mjs
  BACKUP_DIR=Z:/no-such-place node scripts/db-update.mjs
  ```
  → 停在 `[3]`，訊息寫「備份沒有成功完成，更新到此為止⋯⋯沒有備份的遷移，出事時沒有任何東西可以退回去」，最後一行是「資料庫沒有被改動」。
  → **不會**印出 `[5] 套用既有遷移`。這一條的重點不是它失敗了，是**它失敗在遷移之前**。
- [ ] `q30` **［護理端］** 啟動後端再看一次「版本更新紀錄」。
  → 那次中止也留了一列，結果「中止」、備份欄寫「（沒有做成）」、備份驗證「未通過」、套用的遷移「無」。失敗的更新一樣要留下紀錄。
- [ ] `q31` **［終端機］** 把 `BACKUP_DIR` 設回正常值，確認 `q24` 還能再跑一次。
  → 可以。更新流程可重複執行，每一次都會產生新的備份與新的一列紀錄。

## 7.7 · 開發用遷移指令的防呆（DEP-31）

開發用的 `prisma migrate dev` 在偵測到「資料庫與遷移歷史對不上」時，會提議或直接**重建整個資料庫**。在開發機上那是方便，在正式主機上那是把整個透析中心的紀錄刪掉。

- [ ] `q32` **［終端機］** 用正式環境設定執行開發用的遷移指令：
  ```bash
  cd apps/api
  # PowerShell：$env:DEPLOYMENT_ENV='production'; npm run prisma:migrate
  DEPLOYMENT_ENV=production npm run prisma:migrate
  ```
  → **被擋下**。訊息說得出依據（`DEPLOYMENT_ENV=production`）、為什麼擋（那支指令會重建整個資料庫）、以及該用哪一支（`npm run db:update`）。
  → 擋下的是**指令本身**，Prisma 根本沒有被執行。
- [ ] `q33` **［護理端］** 稽核軌跡查剛才那一刻。
  → 有一筆「遷移指令遭擋下：正式環境不得執行開發用指令」。有人在正式主機上試過開發指令，是值得事後知道的一件事。
- [ ] `q34` **［終端機］** 不帶 `DEPLOYMENT_ENV` 再跑一次同一支指令。
  → 照常執行（沒有 schema 變更時它會說沒有變更）。**開發機上不受影響。**

## 7.8 · 離線可部署性：引擎自帶、版本鎖死（DEP-30）

- [ ] `q35` **［終端機］** `npm run check:offline`
  → 沒有阻擋項。逐項看過：引擎檔已就位（兩個檔、各約 20MB）、Prisma 三者版本一致且**鎖成確定版本**（不是 `^6.x`）、「套用既有遷移」的指令存在、開發用的那支已加上防呆、更新流程有入口、三個建置產物都在。
- [ ] `q35a` **［終端機］（0920 補）** 在開發機上假裝斷網，跑一次遷移：
  ```bash
  # 把 CLI 自己那份引擎與快取清掉，模擬「剛解開的 node_modules」
  rm -f node_modules/prisma/query_engine-*.node
  rm -rf apps/api/node_modules/.cache/prisma
  # 把下載位址指到一個解析不出來的主機，等同於院內的網路狀況
  PRISMA_ENGINES_MIRROR=http://offline.invalid npm run prisma:migrate
  ```
  → 正常跑完，最後的 `Running generate...` 也要成功。**這一步就是迭代 9 末倒下的那一步**：
  遷移本身全數套用完成，倒在它順手跑的 `generate` 上，給的錯誤是 `getaddrinfo ENOTFOUND binaries.prisma.sh`。
  若又出現那個錯誤，是 `apps/api/scripts/prisma-cli.mjs` 沒被用到（檢查 `package.json` 的 prisma 指令）。

- [ ] `q36` **［終端機］** 開啟 `apps/api/package.json`，確認 `prisma` 與 `@prisma/client` 兩個版本號**沒有 `^` 或 `~`**。
  → 引擎與 CLI 的版本必須一致；浮動的版本範圍會在某次重新安裝時悄悄換掉其中一邊，而症狀會是一個看起來毫不相干的錯誤。
- [ ] `q37` **［終端機］** `npm run check:egress`
  → 仍為 0 筆。
- [ ] `q38` ⚠️ **迭代 10 才做得完的一項**：在一台**乾淨的 Windows 機器**上、**全程離線**，從解開安裝包到服務起來、套用遷移、正常運作。
  → `q35` 只驗「這台機器上的東西夠不夠」；在開發機上解壓來測，測到的是開發機，不是安裝包。這一條排在迭代 10（DEP-22）。

## 7.9 · AI 端點完全不通時的四條主線（DEP-24）

第一次部署時 AI 功能預設為關，**這一條在上線第一天就會被實際驗到**。

- [ ] `q39` **［終端機］** 把後端指向一個一定連不上的端點後啟動：
  ```bash
  cd apps/api
  # PowerShell：$env:LLM_PROVIDER='onprem'; $env:LLM_ENDPOINT='http://127.0.0.1:9/v1'; $env:LLM_MODEL_ID='no-such-model'; node dist/main.js
  LLM_PROVIDER=onprem LLM_ENDPOINT=http://127.0.0.1:9/v1 LLM_MODEL_ID=no-such-model node dist/main.js
  ```
  → **服務照常啟動。** 健康檢查失敗是一項狀態，不是啟動條件。
- [ ] `q40` **［護理端］** 指派一台平板給病人。→ 可用（主線一）。
- [ ] `q41` **［病人端］** 送出一次症狀問卷。→ 可用（主線二）。
- [ ] `q42` **［病人端］** 按求助按鈕。→ 可用（主線三）。
- [ ] `q43` **［護理端］** 開總覽。→ 看得到那位病人與剛才那筆求助（主線四）。

  → 畫面**幾秒內**畫得出來，不是卡著等一分鐘。健康檢查的逾時與單次生成分開，而且結果會短暫快取。

  → 回到平常的狀態。

## 7.10 · 共用主機上的隔離：連接埠、目錄、磁碟空間（DEP-37）

正式主機與其他專案共用，院方確保本系統的資源額度足夠。**但「資源足夠」是一句承諾，不是一個設定**——
隔離要自己在安裝包層級做到：自帶執行期、埠登記後固定、目錄是自己的、權限只給服務帳號。
這一節驗得到前三項的設定面；第四項（目錄權限）只有部署當天以實際帳號才確認得了。

**連接埠（DEP-37 第 2 項）**

- [ ] `q50` **［終端機］** 正式環境設定下、不給埠啟動一次（**這一項會讓服務起不來，是預期的**）：
  ```bash
  cd apps/api
  # PowerShell：$env:DEPLOYMENT_ENV='production'; $env:API_PORT=''; node dist/main.js
  DEPLOYMENT_ENV=production API_PORT= node dist/main.js
  ```
  → **拒絕啟動**，訊息說的是「要先向資訊室登記、再寫進主機的 .env 固定下來」，不是只說缺變數。
  沒寫等於賭沒有人先佔走 3000，而那多半在某次重新開機、兩個服務的啟動順序對調時才發作。
- [ ] `q51` 把 `API_PORT` 填回去，照平常啟動。→ 正常起來。**開發機不填照舊用 3000**，只有正式環境設定會擋。
- [ ] `q52` **［護理端］** 系統管理 → 資料庫與備份 → 執行環境的「監聽連接埠」。
  → 看得到埠號，以及它是「主機設定檔指定」還是「程式預設值」。正式主機上必須是前者。

**目錄（DEP-37 第 3 項）**

- [ ] `q53` **［終端機］** 把 `.env` 的 `BACKUP_DIR` 暫時改成 `C:/Temp/hd-backups` 後啟動。
  → **拒絕啟動**，訊息說它位於共用目錄底下：那些位置別的專案的清理腳本掃得到、一般登入者也讀得到。
  把 `DATABASE_URL` 改到 `C:/Users/Public/…` 也是同樣的結果。改回原值後恢復正常。
- [ ] `q54` ⚠️ **部署當天才做得到的一項**：在正式主機上，用**另一個一般登入帳號**去開資料庫目錄與備份目錄。
  → **連讀都不行**。共用主機上別的專案的維運人員也登得進這台機器，預設權限等於把病人資料攤開。
  這一項同時是部署前置檢查清單 9.1 第 9 條。

**磁碟空間（DEP-37）**

- [ ] `q55` **［護理端］** 系統管理 → 資料庫與備份 → 「資料庫磁碟可用空間」。
  → 看得到目前可用空間與下限（預設 1GB，由 `DB_DISK_MIN_FREE_MB` 設定）。
  下限的實際數字待資訊室議定（Q-27）。
- [ ] `q56` **［終端機］** 把 `DB_DISK_MIN_FREE_MB` 暫時設成一個大於目前可用空間的值（例如 `99999999`），
  重新整理 `q55` 的畫面，再執行一次 `npm run db:update`。
  → 畫面上那一格變成 ✗；更新流程在備份**之前**就停下，訊息算得出這次需要多少（備份與驗證複本各一份＋保留下限），
  並提醒主機是共用的，先確認是誰把空間佔掉了。**資料庫沒有被改動。** 改回原值後恢復正常。
