# 迭代 10 手動測試 — 打包、平板佈建與部署演練

> 《[完整手動測試手冊](manual-test-guide.md)》的分冊之一，對應《實作規格書》4.8 節。
> 共用的環境準備、啟動與疑難排解都在主手冊，這一冊只寫迭代 10 的部分。
> 操作端色籤（**護理端**／**病人端**／**終端機**／**資料庫**）的意思見主手冊 §00。

**這一冊與前九冊有一個根本差別：一半的項次不在開發機上做。**

前面的迭代驗的是「功能對不對」，可以在一台機器上驗完。迭代 10 驗的是
「**把它搬到一台什麼都沒有的機器上，還能不能動**」——而開發機正好是那個條件的反面：
有網路、有 Node.js、有一整份套件目錄。在這裡驗過的東西，只證明安裝包內部是完整的。

因此每一節開頭都標了它在哪裡做：

| 標記 | 意思 |
|---|---|
| 🖥 **開發機** | 在你現在這台機器上做得完 |
| 🏥 **乾淨機器／現場** | 要另一台機器、實體平板，或院內主機。**結果要寫進《[部署演練紀錄](../notes/deployment-drills.md)》** |

## 10.1 · 建置離線安裝包（DEP-18）🖥

- [ ] `t1` **［終端機］** `npm run build`，再跑 `npm run check:offline`。
  → 沒有阻擋項。有阻擋項就**不要往下做**：這一步擋下的東西，到院內會變成起不來的服務。
- [ ] `t2` **［終端機］** `npm run package:build -- --zip`
  → 最後印出安裝包目錄、檔案數、總大小、`CHECKSUMS.txt` 的 SHA-256，以及壓縮檔與它的 SHA-256。
  **把那兩個雜湊值抄進交付單**（DEP-27）。
- [ ] `t3` **［終端機］** 看一眼安裝包目錄的最上層。
  → 有 `runtime/`、`app/`、`engines/`、`scripts/`、`VERSION.json`、`CHECKSUMS.txt`、
  `.env.範本`、`安裝說明.md`。
  → **沒有 `.env`、沒有 `.db`、沒有備份檔**（DEP-13）。
- [ ] `t4` **［終端機］** 開啟 `VERSION.json`。
  → 版本、commit、建置時間、Node.js 版本、包內的 Prisma 引擎檔名都在。
  `commitClean` 若是 `false`，表示建置時工作區有未提交的變更——**正式交付的包不接受這個值**。
- [ ] `t5` **［終端機］** `npm run check:egress`
  → 安裝包與外殼 App 兩列都是 0 筆（DEP-14）。

## 10.2 · 安裝包驗收五項（DEP-22、DEP-27）🖥 ＋ 🏥

- [ ] `t6` **［終端機］** `npm run package:verify -- --dir dist-package/<安裝包目錄>`
  → 五項全綠：雜湊值、包內沒有設定檔與資料庫、以包內引擎套用遷移、三個行程起得來、全程沒有對外連線。
- [ ] `t7` **［終端機］** 故意改壞一個檔案（例如在 `安裝說明.md` 尾端加一個字），再跑一次 `t6`。
  → **雜湊值那一項變紅**，並指出是哪一個檔案。改回去再跑一次確認恢復綠色。
  *這一項是在驗「驗收腳本本身會不會說謊」——每個檢查都要有人看過它失敗的樣子。*
- [ ] `t8` 🏥 **［終端機］** 把安裝包與 `scripts/verify-package.mjs` 一起複製到**一台乾淨的 Windows 機器**，
  **拔掉網路線**，用包內的執行期跑：
  `.\runtime\node.exe verify-package.mjs --dir .`
  → 五項全綠。**這一次的輸出才是 DEP-22 的交付物**，整段貼進演練紀錄 §3.2。
- [ ] `t9` 🏥 **［終端機］** 同一台機器上確認沒有全域 Node.js：`node -v`
  → 「不是內部或外部命令」。**如果這台機器上有 Node.js，這次驗收不算數**——
  你驗的是那一份，不是包裡的那一份。

## 10.3 · 服務註冊、啟動與停止（DEP-12）🏥

- [ ] `t10` **［終端機］** 以系統管理員身分：
  `.\scripts\service-install.ps1 -Account "<專用低權限帳號>" -DataDir "<資料目錄>" -BackupDir "<備份目錄>" -LockDownDataDir`
  → 註冊完成。**資料目錄若填在安裝包目錄之內會被擋下**（DEP-08）——請實際試一次，看它擋不擋。
- [ ] `t11` **［終端機］** `.\scripts\service-start.ps1` 再 `.\scripts\service-status.ps1`
  → 排程工作 Running、本安裝包底下 3 個行程、存活檢查 HTTP 200。
- [ ] `t12` **［終端機］** 用**一般登入者**的帳號開啟資料目錄。
  → 拒絕存取。主機是共用的，同一台機器上別的專案的維運人員也有登入權限，
  **而他們不該讀得到病人資料**（DEP-12、DEP-37 第 4 項）。
- [ ] `t13` **［護理端］** 系統管理 → 維運狀態。
  → 伺服器時區是 Asia/Taipei，**執行身分是剛才那個專用帳號**，不是你現在登入的帳號。
  主機時區正確不代表服務執行帳號取得的時區正確（DEP-15）。
- [ ] `t14` **［終端機］** 把機器重新開機。
  → 開機後不必登入，服務自己起來（`service-status.ps1` 確認）。
- [ ] `t15` **［終端機］** `.\scripts\service-stop.ps1`
  → 三個行程都停了。**要確認的是「都」**：剩下任何一個還開著資料庫檔案，
  接下來的備份就是在一個還在被寫入的檔案上做的（DEP-10）。

## 10.4 · 病人端斷網仍開得出畫面（平板管控方案 3.1）⚠ 🖥 ＋ 🏥

**選 PWA 而不是純網頁的唯一理由就是這一節。** 它不成立，這個選型就是假的。

- [ ] `t16` **［終端機］** 用建置產物起一份靜態站：
  `node apps/api/dist/static-server.js apps/patient-pwa/dist 5175`
  *（開發伺服器沒有離線快取，這一節不能用 `npm run dev:patient` 驗。）*
- [ ] `t17` **［病人端］** 開 `http://localhost:5175`，等畫面出來。開發者工具 → 應用程式 → Service Workers。
  → 有一個已啟用的 Service Worker；快取內容包含 `/index.html`、樣式與程式檔、圖示。
- [ ] `t18` **［終端機］** **把 `t16` 那個行程停掉**（不是關瀏覽器分頁）。
- [ ] `t19` **［病人端］** 重新整理。
  → **畫面照樣出得來**。這就是離線能力：伺服器不在了，平板上仍然有一份可以開的畫面。
- [ ] `t20` **［病人端］** 在已綁定病人的平板上重複 `t18`–`t19`。
  → 畫面出得來，求助區在原來的位置、原來的大小，且**明確顯示現在通知不到護理師**——
  能按而沒有回應才是最糟的那一種。
- [ ] `t21` **［病人端］** 開發者工具 → 應用程式 → 快取，逐一點開看內容。
  → **找不到任何一筆病人資料**（姓名、病歷號、症狀回報、求助紀錄）。
  快取裡只有畫面本身；資料請求不進快取，離線要送出的東西由本地暫存佇列負責。
- [ ] `t22` 🏥 **［病人端］** 在實機平板上把 Wi-Fi 關掉，重複 `t19`–`t20`。
  → 同上。**這一項要在實機上做**，桌機瀏覽器的離線模擬與 Android WebView 的行為不完全一樣。

## 10.5 · 逸出偵測：跳出 Kiosk 看得見（平板管控方案 4.4）⚠ 🖥

- [ ] `t23` **［護理端］** 裝置管理 → 平板清單。
  → 多了一欄「固定狀態」。還沒裝外殼 App 的平板顯示**尚未回報**，不是「已跳出」——
  **沒裝 App 與跳出 Kiosk 是兩件事**，護理師要做的處置也不同。
- [ ] `t24` **［病人端］** 用該台平板開啟病人端畫面並停在前景。
- [ ] `t25` **［護理端］** 最多等 15 秒（這一頁自己會重新取得）。
  → 那一列變成**固定中**。
- [ ] `t26` **［病人端］** 把瀏覽器分頁切走（或在實機上退出 App）。
- [ ] `t27` **［護理端］** 不要手動重新整理，看著那一列。
  → **30 秒內**變成**已跳出**，下面一行寫著什麼時候開始的（驗收第 9 條）。
- [ ] `t28` **［病人端］** 切回前景。→ 護理端那一列變回**固定中**。
- [ ] `t29` **［病人端］** 把平板關機或關掉分頁，然後**等 90 秒以上**。
- [ ] `t30` **［護理端］** → 那一列變成**失去回報**，並寫出最後一次回報的時間。
  「已跳出」是平板說的，「失去回報」是它不說話——**要分得開**，後者多半是關機或斷網。
- [ ] `t31` **［護理端］** 稽核軌跡 → 動作選「平板跳出固定畫面」。
  → 查得到 `t26` 那一次。**只有轉折點有紀錄**：平板每 30 秒回報一次，15 台一天四萬多筆，
  每筆都記等於把稽核軌跡淹掉。
- [ ] `t32` **［護理端］** 同一頁看「平板回到固定畫面」。
  → 查得到 `t28`，但**查不到 `t24` 那一次**——那是 App 裝好之後的第一句話，不是跳出去又回來。

## 10.6 · 更新與回退演練（DEP-19、DEP-32）⚠ 🖥

> **在正本上做之前先想清楚。** 這一節要停服務、動資料庫。
> 第一次練習時請先把 `DATABASE_URL` 指到一份複本。

- [ ] `t33` **［終端機］** 停掉後端，然後 `npm run db:update -- --note "演練"`
  → 六步依序完成：確認服務已停 → 開啟更新紀錄 → 備份 → **驗證備份還原得起來** → 套用既有遷移 → 寫紀錄。
  **抄下備份檔名與 SHA-256**。
- [ ] `t34` **［終端機］** 後端還開著的時候再跑一次 `t33`。
  → 被擋下，並說明為什麼（更新期間的寫入會落在備份與遷移之間的空窗裡）。
- [ ] `t35` **［終端機］** 把 `BACKUP_DIR` 指到一個寫不進去的目錄再跑一次。
  → 停在備份那一步，**沒有套用任何遷移**。備份沒做成就不往下走，這是整支腳本的重點。
- [ ] `t36` **［護理端］** 系統管理 → 維運狀態 → 更新紀錄。
  → 查得到 `t33` 那一次：從哪一版到哪一版、備份檔名與雜湊、驗證結果、套用了哪幾個遷移、誰執行的。
- [ ] `t37` **［終端機］** 回退：
  `npm run db:restore -- --from <t33 的備份檔> --to <另一個路徑> --sha256 <t33 抄下的雜湊>`
  → 雜湊相符、完整性檢查 ok、列出主要資料表筆數。
- [ ] `t38` **［資料庫］** 開啟還原出來的那一份，對照更新後的那一份。
  → 還原的那份**沒有**這次遷移新增的欄位，筆數與更新前一致。
  **程式可以退版，資料庫不行退版**——回退是還原備份再換回舊版，不是把遷移倒回去。
- [ ] `t39` 🏥 **［終端機］** 正式更新時，**舊版安裝包目錄改名保留，不要刪**。
  演練時也照做一次，確認退得回去。

## 10.7 · 自簽 CA 與外殼 App（平板管控方案 4.2、4.3）🏥

- [ ] `t40` **［終端機］** `npm run cert:hospital-ca -- --host <院內主機名稱> --ip <院內 IP>`
  → 產出 CA 與伺服器憑證，印出 CA 指紋與憑證有效期。
  → **立刻把 CA 私鑰異地備份**（院內，不出院）並寫進交接文件（DEP-35）。
- [ ] `t41` **［終端機］** 再跑一次同一個指令。
  → 被擋下，不會蓋掉既有的 CA。換 CA 等於 15 台平板都要重發 APK。
- [ ] `t42` **［終端機］** `openssl verify -CAfile <CA> <伺服器憑證>`，並檢查主體別名。
  → 驗證通過，別名涵蓋平板實際要連的那個位址。
- [ ] `t43` 🏥 **［平板］** 把 CA 放進外殼 App 的資源檔，編譯簽名 APK，側載到一台平板。
  → 開啟後不出現憑證警告，Service Worker 正常運作（§10.4 的離線能力在實機上仍然成立）。
- [ ] `t44` 🏥 **［平板］** 首次啟動輸入序號與金鑰。
  → 進入病人端畫面，**網址列不存在**（外殼沒有網址列），病人看不到金鑰。
- [ ] `t45` 🏥 **［平板］** 設定 → 安全性 → 開啟螢幕固定並勾選「解除固定前要求 PIN」，釘住 App。
  → 病人退不出去；解除要輸入 PIN。
- [ ] `t46` 🏥 **［平板］** 把平板重新開機。
  → App 自己起來，**但螢幕固定沒有恢復**（已知取捨，列入每日交班檢查）。
  護理端「固定狀態」這時應顯示固定中——**App 在前景，只是沒被釘住**，
  這正是逸出偵測補不到的那個縫，靠交班檢查補。
- [ ] `t47` 🏥 **［平板］** 在 App 內點一個指向外部網站的連結（測試用）。
  → 不會開啟。長按畫面上的文字 → 不會出現選字選單。

## 10.8 · 路線 A 與路線 B（DEP-25～28）🏥

- [ ] `t48` **［終端機］** 在正式主機上依序試 `git clone`、`npm install`、套用遷移。
  → **每一步的錯誤原文、在哪一步、花了多久，逐項記進《[部署演練紀錄](../notes/deployment-drills.md)》§1.3。**
  紀錄本身就是交付物。
  → **不得為了讓它成功而開對外連線。**
- [ ] `t49` **［終端機］** 路線 B：開發端掃毒 → 隨身碟 → 院內掃描站再掃一次 → 解壓 → 核對雜湊。
  → 兩次掃描結果都留存（DEP-26），雜湊相符（DEP-27）。
- [ ] `t50` **［終端機］** 用完清除隨身碟，在部署紀錄寫明「已清除」與執行者（DEP-28）。
  → **不得帶任何資料出院**——不是備份、不是紀錄檔、不是截圖。
- [ ] `t51` **［全部］** 《部署規範》第 9 章的檢查清單逐條確認。
  → 26 條全部有結果。**缺一條就不算可以部署。**

## 10.9 · 自動化驗收

- [ ] `t52` **［終端機］** `npm run verify:iteration10`（後端要先啟動）
  → 腳本驗得到的部分全部通過，並列出**只有在現場做得到的 5 項**。
  那 5 項不會變綠，也不該變綠——它們在上面的 🏥 節次裡。
- [ ] `t53` **［終端機］** `npm run check:all`
  → 五支盤點全過，含安裝包與外殼 App 兩列。
