1004 取得同院 IDH 預警系統正在用的院方透析清單 API 與那套系統的程式（《[同院 IDH 系統參考調查](../notes/idh-reference-survey.md)》）。1005 使用者據此指示四件事，**判準只有一句：能用 API 判斷的，就不要求護理師操作。**

|---|---|---|---|
| 1 | 病人、床位、療程開始與結束、臨床數值 | 全部由護理師在護理端操作或匯入；院方 API 只預定給輪播第三層的四種數值，介接程式暫不寫 | **院方 API 全面取代手動輸入**：病人主檔、床位、病人在哪一床、療程開始與下機、四種數值、問卷與衛教的時點，一律由 API 判斷；護理師只做 API 判斷不了的事（FR-S15、FR-S16） |

| 4 | 第三次進院 | — | 處理 1001 登不進去的原因，並把主機位址從名稱換成 IP（《[實作規格書](implementation-spec.md)》4.19） |

## 1. 文件目的與範圍

本文件定義「血液透析中心平板照護輔助系統」之軟體需求，涵蓋病人端 15 台 Android 平板、護理端多裝置應用、後端服務、地端 AI 輔助功能、單位管理與營運分析，以及資料治理規範。

系統目標為在不取代任何臨床判斷與侵入性操作的前提下，將可數位化與可數位優化的護理工作流程予以實作（工作區塊盤點見《[FDE 數位化／數位優化評估報告](fde-assessment.md)》）。

本文件**不涵蓋**：透析機台參數整合、藥局／HIS 系統雙向寫入、透析機台硬體通訊協定（列為未來擴充項）。

**與其他文件的關係**：本文件是功能需求的來源（FR 編號出處）。資料治理的強制規則以《[資料庫使用規範](database-policy.md)》為準；實作範圍與技術棧決策以《[實作規格書](implementation-spec.md)》為準；部署形態、環境界線與交付方式以《[部署規範](deployment-spec.md)》為準（`DEP` 編號）。

### 3.2 系統邊界

系統由病人端 PWA、護理端 PWA、管理端介面（與護理端共用應用，以權限區分）、後端 API Gateway、裝置綁定服務、地端 AI 推論服務、規則引擎、臨床資料匯入服務、對外報表服務，以及 SQLite 資料檔所組成。

**0910 的邊界變動**：

- **推播通知服務移除。** 即時通知改由院內 SSE 長連線提供，配合常駐總覽螢幕與音效提示。
- **外部 LLM 服務移除。** AI 推論在院內伺服器完成。過渡期的實驗室 API 為院外服務，因此**過渡期僅得送合成資料**。
- **新增規則引擎。** 三項高風險功能不經語言模型，改以可攤開的規則計算（FR-R01）。
- **資料層改為單一 SQLite 檔案**，即時狀態改由後端記憶體與資料庫共同承擔，不另設快取服務。

**0919 的邊界變動**：

- **地端推論服務移出系統邊界。** 它不再是「本系統跑在同一台機器上的另一個服務」，而是**院內另一台機器（DGX Spark）上的一個 HTTP 端點**。本系統只持有它的位址與模型識別字，不負責它的部署、載入與維運。
- **MDM 服務移出系統邊界。** 平板管控改走免 MDM 路線，系統內留下的只有「裝置佈建狀態的紀錄與稽核」，不再有任何對外的裝置管理通道（FR-S01）。
- **臨床資料來源確定為院方 API。** `HospitalApiAdapter` 成為正式來源，檔案匯入退為備援（FR-S05）。
- **新增一個病人端元件：自包 WebView 外殼 App。** 它不含任何業務邏輯，只負責載入 PWA、信任院內自簽憑證、限制行為邊界，並回報前景狀態（逸出偵測）。

**0926 的邊界變動**：

- **新增 AI 閘道。** 它是本系統的一部分（跑在本系統的容器裡），但不含模型：後端把 AI 請求交給它，由它依設定檔以 LangChain 呼叫推論端點。推論端點本身仍在邊界外（FR-S13）。
- **外殼 App 移到另一個 repo。** 它仍是系統元件，但原始碼不在本 repo；兩邊的界線是一份帶版本號的契約，契約的真本在本 repo（FR-S14）。

**1005 的邊界變動**：

- **院方透析清單 API 由「數值來源」升為「病人、床位與療程的來源」。** 它仍在邊界外（院內另一台 PHP 伺服器，本系統只讀），但本系統的病人主檔、床位、療程開始與結束從此由它驅動（FR-S15）。本系統**不回寫**院方任何資料，HIS 雙向寫入照舊排除。
- **新增「模擬院方 API」。** 開發機與模擬部署連不到院內的 API，因此以一個產生同格式合成資料的模擬服務代替；**正式環境不得啟動它**（FR-S16）。

## 4. 權限模型與裝置綁定

### 4.1 病人端不提供登入介面（維持 v1.0 設計）

**病人端平板不提供任何登入介面**（無帳號、密碼、生物辨識、或病人自選身分清單）。病人於平板上能存取的所有資料與功能，其存取權限之啟用，一律由護理師透過「裝置指派」動作觸發。理由：

1. 病人在透析情境下（可能虛弱、視力不佳、認知負荷高）不適合承擔身分驗證責任
2. 平板為機構共用裝置，若允許病人自行選擇／切換身分，會產生資料誤植給錯病人的風險
3. 從法規遵循角度，臨床資料的存取授權應可追溯到「哪一位護理師、何時、為哪一位病人核准」，而非病人自證身分

### 4.3 裝置與病人綁定流程

**前置條件**：護理站已建立當日排班表（病人—療程時段對應）。

1. 病人到達透析中心，護理師於護理站主控台（或當班護理端裝置）選取當日排班中的病人
2. 護理師選擇欲指派之平板序號（清單選取、掃描病人手環條碼、掃描平板背面 QR 碼三者擇一）
3. 護理師確認指派後，請求送至後端**裝置綁定服務**
4. 裝置綁定服務核發一組**限時 Session Token**，綁定「病人 ID＋平板序號＋當次療程時段」三項，並透過安全通道送至該平板
5. 平板在收到有效 Session 前，僅顯示中性等待畫面（「請由護理人員為您開始使用」），不顯示任何病人可識別資訊、不提供輸入欄位
6. Session 啟用後，平板僅能存取「本次已綁定病人」之資料與功能，無法切換查看其他病人
7. Session 失效條件（三者擇一觸發）：正常下機流程、護理師手動提前解除、超過療程時間上限（預設 6 小時）自動失效
8. Session 失效後，平板本地暫存資料需清除，並回復至「等待指派」狀態
9. 每一次綁定與解除動作，須記錄操作護理師帳號、時間戳、病人 ID、平板序號，寫入稽核軌跡

### 4.4 例外情況

- 平板離線期間無法完成新綁定；若原本已有效 Session 而平板離線，症狀回報可暫存本地（IndexedDB），恢復連線後同步，但求助功能於離線期間需明確提示「目前無法即時通知護理站」
- 若同一病人短時間內被誤指派至兩台平板，系統應偵測並阻擋第二次綁定，提示「該病人已有進行中之綁定」
- **0910 新增**：Session 失效後，閒置輪播中已快取的第三層臨床數值須一併清除，不得殘留給下一位使用者

**FR-P09～P11、P13 補充說明（1005 改寫，取代下方 0916～0926 的輪播說明）**：

藍本是同院 IDH 系統護理端「病人詳細資訊」的第一頁。那一頁是給護理師的，逐項判斷之後，**病人端只留下病人想看、而且看了不會誤解的東西**：

| 藍本第一頁上的東西 | 病人端 | 理由 |
|---|---|---|
| 收縮壓／舒張壓 | **折線圖** | 病人最常問的一句是「我現在血壓多少」；透析中的頭暈、抽筋多半與血壓有關，看得到走勢比只看一個數字安心 |

| 脈搏 | 數字（最新一筆） | 適合看，但病人很少主動問；不值得一張圖 |

- **即時的意思**：後端每次抓院方 API（預設 3 分鐘，FR-S16），有新紀錄就主動推給那一台平板，**病人不必碰螢幕**。曲線多久多一個點，取決於透析室多久量一次——API 有一筆，曲線就多一點。
- **資料時間**：每一張圖、每一個數字都標示最後一筆的時間。API 暫時不通時**照樣顯示上一次成功取得的值與它的時間**，不顯示空白（原 FR-P11 規則沿用）。
- **讀到 0 的不顯示**（1005 使用者決定，沿用）；剛上機還沒有任何一筆量測時，圖的位置留著框，不畫空白座標軸。
- **1010：血壓不畫正常區間**。院方覺得血壓圖太簡潔，建議比照脫水量那張加虛線標出血壓的正常區間。使用者要開發端判斷合不合理；**判斷是不合理，不做**，理由如下（使用者 1010 決定：不合理就寫出原因、不做）：

  | # | 理由 | 出處 |
  |---|---|---|
  | 1 | **透析中的血壓沒有公認的「正常區間」。** 一般成人的正常血壓（例如 120/80）不適用透析病人；KDIGO 2021 的血壓指引**明文排除透析病人**；唯一給過數字的 KDOQI 2005 是「透析前 < 140/90、透析後 < 130/80」，證據等級弱、由一般人口外推，而且是透析前後兩個時點的治療目標，不是透析中的區間；KDOQI 2006 的透析適足性更新就不再建議血壓目標 | KDIGO 2021 Blood Pressure in CKD（Kidney Int 2021;99:S1–S87，適用範圍不含透析）；KDOQI 2005 Cardiovascular Disease in Dialysis Patients, Guideline 12 |
  | 2 | **透析前後量的血壓與存活呈 J 形或 U 形**：觀察研究一致看到死亡率升高在血壓偏低、而不是偏高的病人（DOPPS 的分析中是收縮壓 < 130）。畫一條上限虛線，等於告訴病人「超過就是不好」，與證據相反；歐洲腎臟與高血壓學會的共識因此主張透析病人的高血壓要用非透析日的居家或 24 小時血壓判斷，不用透析時量的 | DOPPS（Kidney Int 2012;82:570–580）；ERA-EDTA EURECA-m／ESH 2017 共識（J Hypertens 2017;35:657–676） |
  | 3 | **下限也畫不成一條線。** 與死亡率最相關的透析中低血壓定義是最低收縮壓 < 90，但透析前收縮壓 ≥ 160 的病人要用 < 100；同院 IDH 系統也是這樣分兩種門檻（《同院 IDH 系統參考調查》6.2）。一條線對一部分病人就是錯的 | Flythe et al., JASN 2015;26:724–734 |
  | 4 | **畫在病人自己的圖上，就是請病人自己判讀。** 曲線往下穿過那條線，病人看到的是「我低血壓了」——這是 FR-P05「透析中預警」的範疇，屬高 SaMD 風險，要先滿足 5.6 節 FR-R 八條（含書面確認閘門），不能以一條虛線的形式從病人端繞進來 | 本文件 5.6 節 |
  | 5 | **對病人與護理師的實際效果是負的。** 透析病人透析前收縮壓高於 140 的很常見，畫了上限，多數人的曲線整段都在線外，每次看都是「不正常」；焦慮之下多按求助、多問護理師，加重的是護理站的工作 | 本系統首頁的設計原則（FR-P11：只呈現量測值、不給評語） |
  | 6 | **與脫水量那條虛線不是同一種東西。** 脫水量的虛線是這位病人本次的**設定脫水量**，是「進度到哪了」的參考；血壓的區間是「好或不好」的判準 | 本節上表「脫水量」一列 |

  **若院方要的是「看得出變化」而不是「看得出好壞」**，可以考慮的是只畫這位病人本次**開始時的血壓**當基準線（只是量測值，不是判準）；這一條沒有做，要院方再提出。
  文獻連結：KDIGO 2021（<https://pubmed.ncbi.nlm.nih.gov/33637203/>）、KDOQI 2005 的目標值與透析病人血壓—死亡率的觀察研究（DOPPS，Robinson et al., Kidney Int 2012;82:570–580，<https://pmc.ncbi.nlm.nih.gov/articles/PMC3891306/>）、Flythe 2015（<https://pmc.ncbi.nlm.nih.gov/articles/PMC4341492/>）、ERA-EDTA／ESH 2017（<https://cris.maastrichtuniversity.nl/en/publications/hypertension-in-dialysis-patients-a-consensus-document-by-the-eur-2>）。
- **抽血數值與 Kt/V 從病人端拿掉**（原輪播第三層）：它們是每月一次的檢驗，不是透析中的即時資訊；而且院方 API 沒有、暫定拿不到。功能開關「需要抽血數值的功能」只剩護理端在用。
- **跑馬燈**（FR-P10，1005 修正：整則跑、不必點開、速度要經長者確認）：
  - 位置在「本次透析」區的底部一條，高度固定，**在求助區的保留範圍之外**（FR-P13 的版位規則照舊）
  - **每一則以「標題：內容」整則跑過去**，例如「國慶日停診：10 月 10 日停診一天，當天的透析改到 10 月 9 日，時間不變。」（範例，不是實際內容）。**不必點開、也不能點開**——碰到跑馬燈不跳出任何東西，病人不必學任何操作
  - **長度有上限**：標題 12 字以內、內容 60 字以內。一則照預設速度跑完約半分鐘；比這長，病人等不到結尾就分心了。上限由 AI 生成時就遵守（FR-N17），超過的草稿不得核准
  - **速度慢到長者看得清、跟得上**：預設**每秒 2 個字**，刻意訂在一般成人閱讀速度的一半以下；做成營運參數，可調範圍每秒 1～3 個字，改了要填理由、寫稽核
  - **不造成壓力**：等速平滑移動，不跳格、不閃爍、不加速、不變色；每一則開頭先**靜止 3 秒**再開始移動，讓人先看清標題；一次只有一則，兩則之間**留 5 秒空白**；全部輪過一遍才重來，不連續重複同一則；全程靜音；字級不小於病人端內文
  - **速度不是開發端說了算**：開啟跑馬燈前，要有長者在病床上的距離實際看過，回答「看得清嗎、跟得上嗎、看了累不累或煩不煩」三題；任一題有人說不行，就調慢再試（實作規格書 4.14 驗收、清冊 Q-31 第 6 題）
  - 只播**護理師核准過**、在上架期間內、指定給這一床或全部床位的內容（FR-N17）；**一則都沒有時整條不出現**，不留一條空白
- 面板與跑馬燈的畫面上**不出現任何可識別病人的資訊**，只到床號（原規則沿用）。
- **晚班時段**：面板調暗；**跑馬燈整條不出現**——暗室裡移動的字最打擾休息，而「標題：內容」整則也塞不進一行靜態顯示（原規則「調暗或改為靜態顯示」的延伸）。
- 原輪播第一層的「今日已回報內容」「衛教完成度」不再顯示：前者病人自己知道，後者是護理端關心的數字；療程進度已在基本資訊區。

**為什麼「確認時間」與「到達床邊時間」要分開**：兩者的差距是資料品質的檢查點。若只記錄確認時間，一旦這個數字被用於績效，最省力的做法會變成「先按確認再慢慢走過去」，指標就失去意義。分開記錄讓這種情況看得見。

**0919：這一條暫時做不到，而且必須承認做不到。** 護理站只有一兩台桌機、護理師手上沒有平板，「到床邊才按」在物理上無法發生；硬留著這顆按鈕，得到的會是「回到護理站後補按」的假資料，比沒有資料更糟。因此首波試用期間**關閉這顆按鈕**，該欄位一律留空，並在成效指標中明確標示「本期間無到達時間資料」。等護理師手上有裝置時，在系統設定開啟即可，資料結構不必改。

**處理方式與處理結果的選項內容**：0919 起改由附錄 C 的預設清單提供，院方已授權採用，並可在護理端系統設定增刪改。

| 格式 | 段落 | 系統預填什麼 |
|---|---|---|
| **DART**（預設） | D 資料 | 病人自述（平板上的自報，標明「病人自述」）；範本裡屬於「資料」的勾選（例如有無症狀）；**事件時間前最近一筆院方量測**，例如「14:05 血壓 88/52 mmHg、脈搏 98 次/分；累積脫水量 1.2 公斤（設定 2.5 公斤）」 |

| **SOAP** | S 主觀 | 病人自述；範本裡屬於「病人主訴」的勾選 |
| | O 客觀 | 院方量測（每一筆附時間）；範本裡屬於「觀察」的勾選 |
| | A 評估 | **只放護理師自己選的事件類別**（例如「透析中低血壓處置」）；系統不加任何評估，其餘由護理師寫 |

- **時間與數值寫在段落文字裡，不另立欄位**：院內的正式紀錄只有格式本來的那幾格，獨立的「時間」「數值」欄位貼不過去。時間一律 24 小時制「時:分」；每一個數值附單位與量測時間；**讀到 0 的不帶**（與面板同一條規則）；只帶院方 API 給的量測值，不帶任何推算出來的數字。

**FR-P16～P19、FR-N19～N20、FR-S17 補充說明（1010，遊戲化）**：

分析與決定的全文在《[透析中的遊戲化](../notes/dialysis-gamification.md)》與《[之一：決定、開關與實作順序](../notes/dialysis-gamification-decisions.md)》，小花園種哪些花、怎麼長大在《[之二：小花園的植物](../notes/dialysis-gamification-garden.md)》（1010 迭代 21）；這裡只列需求本身。兩份與本文件衝突時以本文件為準。

- **目的的順序**：心理支援 > 狀態評估 > 提高使用平板的意願 > 透析體驗。對後兩者有效、卻傷到心理支援的設計一律不做（例如「沒來透析花就會枯」）。
- **十五條硬性限制**照上層文件 2.2 節 H-1～H-15，摘要：只能點一下、目標夠大、完全無聲、低刺激（不計時、沒有「遊戲結束」、不閃爍、不用紅色）、隨時可中斷且零懲罰、求助永遠在且優先、不碰臨床判讀、一個人就能玩完、夜間不打擾、鄰床看得到所以不公開成績、存檔跟人走、離線照樣能玩、不增加護理師的工作、不破壞現有功能、尊重「減少動態效果」。
- **獎勵的是「做了」**：任務完成給小花園的養分，每次療程每種任務最多一次，與答案、輸贏、臨床數值都無關。
- **紅色的替換**：麻將的「萬」字與紅中改深棕（紅色只給求助，《介面設計基準》4.1）。
- **不做的**：換位拼圖、暗棋、透析滿 N 次的里程碑卡、邀請卡、連到真實世界的回饋、跟家人的連結。
- **九個功能開關**（FR-S08）：

  | # | 開關 | 管什麼 | 預設 |
  |---|---|---|---|
  | 1 | 病友小撇步 | FR-P18；護理端核准清單裡的小撇步來源 | 關 |
  | 2 | 護理師回貼圖 | FR-N19 | 關 |
  | 3 | 透析小花園 | FR-P16 的花園；任務完成給養分；**連動開關 4** | 關 |
  | 4 | 送花 | FR-P19、FR-N12 的花瓶 | 關 |
  | 5 | 病人之間的互動 | FR-S17 的三種匿名彙總 | 關 |
  | 6 | 麻將連連看 | FR-P16 的麻將連連看 | 關 |
  | 7 | 狀態評估彙整（護理端顯示） | FR-N20；關掉時照樣記錄 | 關 |
  | 8 | 老台灣記憶相簿 | FR-P16 的相簿，與護理端的聊天話題 | 關 |

  開關 9 預設開啟是 FR-S08「預設全關」的第二個例外（第一個是「本次透析」面板），理由相同：只呈現、不碰臨床判讀、不碰隱私、不增加護理師的工作。**九個全關時，病人端與護理端都回到 1007 迭代 17.7 的樣子**，只有開關中心多了九列。
- **送花與小花園的連動**：開小花園，送花跟著開；關小花園，送花跟著關；小花園開著可以單獨關送花；小花園關著不能開送花。連動造成的切換也寫入稽核軌跡。
- **花園種滿與清空**（1010 第三輪；遊戲化決定 3.6）：
  - **自己的花園**：開好的花一直留著，系統永遠不自動移走；送給護理站或種進共同花園之後，那一格變回空地，圖鑑的紀錄留著。12 格都有植物時不提醒，只在種子區旁安靜寫一句。
  - **共同花園**：每一班每個月一片，**種滿了這個月就不能再種**，花留在自己的花園。下個月的格數：全部種滿就變成 1.5 倍；種下的不到一半，就是種下格數的 1.5 倍，但不少於起始格數；其他不變。格數向上取到 6 的倍數。一座最多 24 格，超過就平均分成幾座，以免格子太密太小（每格至少 96×96px）。起始格數（12）、一座上限（24）、縮減門檻（一半）是營運參數，一座上限不得超過《介面設計基準》算得出來的上限。斷線時只能看、不能種。共同花園歸開關 5，要開關 3 也開著才出現。
  - **每月歸檔**：每個月 1 日起，上個月的花園歸檔、開一片新的；沒人種的月份不歸檔。歸檔不刪，圖鑑的「我們的花園」看得到自己**那個月透析過的班別**的歸檔，只能看。
  - **跨班的病人**（例如一天早班、一天午班）：每朵花種進**當下這一次療程**的班別，由伺服器依療程查出，不用病人平常的班別、不由前端傳班別；種下之後改班也不搬。當月開放中的花園只顯示當下這一班；歸檔則列出那個月所有透析過的班別。逐項做法與禁止寫法見遊戲化決定 3.6「透析時段跨班的病人」。
  - **背景**：每個月一張，兩年一輪共 24 張，由 AI 畫（植物分析子文件）。歸檔的花園保留它那個月的背景。
- **遊戲資料是新的個人資料**：存檔、操作紀錄、花園、送花、共同花園與歸檔、彙總都寫進資料字典；留存與取得同意比照平板的其他資料（《資料庫使用規範》第 19 條）。遊戲盤面快照以 JSON 存，是《資料庫使用規範》6.1 第 2 條的唯一例外。

**FR-S06 的過渡期限制**：實驗室 API 為院外服務，因此在切換至地端推論之前，**系統不得將任何真實病人資料送入 AI 流程**，僅得使用合成資料。此限制以程式強制（設定為 `LabApiProvider` 時，帶有真實病人資料的請求應被擋下），不依賴人的自律。

**0926 補一道防線**：院內網路現在連得出去，「把開發機的設定抄到院內」就足以讓資料往實驗室送。因此**正式環境設定下選用實驗室供應者，後端直接拒絕啟動**（部署規範 DEP-40）。合成資料檢查擋「送了什麼」，這一條擋「送往哪裡」。

**AI 生成內容的用語（1007，迭代 17.3）**：系統中所有 AI 生成的內容——病人看的衛教、離院衛教重點、跑馬燈，護理師看的護理記錄初稿與 SOP 查詢回答——**禁用簡體字與中國大陸用語**，台灣不這樣寫的繁體字形也一樣。
同樣以程式強制：經 AI 閘道的每一次輸出都查一次字表，不合格就請模型依「哪個詞改成什麼」重寫，最後一次仍不合格也照樣交出（交出前仍要經護理師核准或修改）；這道把關**不在任何畫面上留下痕跡或訊息**。**不自動替換**（一個簡體字可能對到兩個繁體字，替換會換錯）。
護理師自己寫的、修改的字不在這一條的範圍。做法與字表見《[迭代 17.3 修正紀錄](../notes/iteration-17-3-fixes.md)》。

**FR-S10 的判準（0919）**：判準不是「有沒有寫技術名詞」，而是**「這個字對使用者有沒有意義」**。護理師需要知道「這個開關管的是什麼功能」，不需要知道它在程式裡叫什麼；病人需要知道「已處理」，不需要看到 `RESOLVED`。因此：

| 不得出現 | 應改為 |
|---|---|
| 卡片標題寫「功能開關中心（FR-S08）」 | 「功能開關」 |
| 狀態欄直接印出 `IN_PROGRESS`、`PENDING` | 「治療中」、「等待審核」 |
| 提示文字寫「待資訊室確認（Q-09）」 | 「此欄位的格式仍在與資訊室確認中」 |
| 說明寫「人工輸入（ManualEntryAdapter）」 | 「人工輸入」 |
| 開關列印出 `PERF_INDIVIDUAL_L3` | 只留中文名稱與一句說明 |

程式碼註解不在此限——**這條規範的範圍是「使用者看得到的字」，不是「原始碼裡的字」**。需求編號仍應留在註解與文件裡，那是可追溯性的來源。

**FR-S11 的三種版位（0919）**：每個功能在導覽上只會是下列三者之一，切換不需要重新部署。

| 版位 | 意思 |
|---|---|
| **主列** | 出現在護理端上方導覽列，每日必用 |
| **選單** | 收在「更多」下拉選單裡，用得到但不是每天 |
| **關閉** | 不出現在任何入口，且**後端端點一併擋下**，不是只把連結藏起來 |

**FR-S12 的四條硬性規則（0919）**：完整規則見《[部署規範](deployment-spec.md)》與《[資料庫使用規範](database-policy.md)》，此處只列需求本身。

1. 更新作業在備份未成功完成前**不得繼續**；備份必須是可還原的，不是複製出一個檔案就算數
2. 遷移一律前滾：已套用過的遷移檔不得修改，要改就新增一個
3. 正式環境不得執行任何「偵測到差異就重建資料庫」性質的指令
4. 舊版本在新版穩定前不得刪除；資料庫已遷移時，回到舊版的方式是還原備份，不是把遷移倒回去

**FR-S15 對照表（1005）：護理師原本要做的事，哪些改由院方 API 判斷**

API 的欄位與格式見《[同院 IDH 系統參考調查](../notes/idh-reference-survey.md)》第 2、3 節。

| 原本護理師要做的 | API 判斷得出來嗎 | 1005 起 |
|---|---|---|
| 新增病人（病歷號、姓名、性別、生日） | 能：第 0～3 欄 | **自動建立與更新**。簡易版拿掉「新增病人」；**1007 起專業版的「病人」那一頁也拿掉**（迭代 17.6），護理端沒有任何新增病人的入口（沒接院方 API 的開發環境，簡易版仍留著它）。**1007 迭代 17.7 補回備援**：「護理師自己新增病人」功能開關，**預設關閉**，開了之後專業版排班與指派、簡易版病人框同時出現新增病人，關著兩邊都沒有（開發環境也一樣）；院方資料缺人時才開，之後院方資料出現同一個病歷號以院方為準 |
| 建立當日排班（哪位病人、哪一班） | 能：當天出現在 API 的病人就是當天要透析；哪一班由透析開始時間判斷（三班起訖待 Q-34，先用暫代值） | **自動** |
| 建床位清單 | 能：第 10 欄床位 | **自動**：API 出現過的床號就是床位；護理長仍可停用某一床。全新環境不再預設 15 床 |
| 把病人放到哪一床 | 能：第 10 欄 | **自動**，每次抓取都跟著 API 更新；病人換床時，他的平板在床位圖上跟過去 |
| 療程開始（把病人拖上床、平板開始這次療程） | **一半**：開始時間判斷得出來；**哪一台平板判斷不出來** | ~~護理師**每位病人配一次平板**，系統記住；之後 API 判定透析開始，就自動建立療程並綁定那台平板~~ **1006 起護理師每次透析把病人拖到一台平板上**；療程、開始時間與床號由 API 決定（配平板早於 API 判定開始時，開始時間以 API 的為準） |
| 下機（解除指派） | 能，但判定方式要第三次進院確認：預定以「結束體重出現」為準 | **自動**；護理師仍可提前結束。過了預計結束時間很久仍判定不了的，床位格標示「待確認下機」，由護理師點一下。**1007**：預計結束一律是開始後 4 小時（院方硬性規定），不看 API 的預計結束時間 |
| 輸入或匯入理想體重、目標脫水量、結束體重、實際脫水量 | 能：第 14、15、20、21 欄 | **自動**。人工輸入與檔案匯入只留在專業版當備援（FR-S05） |
| 輸入抽血數值（血紅素、白蛋白、Kt/V、BUN） | **不能**：API 沒有 | 照舊，功能預設關閉（「需要抽血數值的功能」） |
| 透析前問卷、心情問卷、衛教的時點 | 能：透析開始與預計結束時間 | **自動**（FR-P15） |
| 事件記錄「低血壓處置」範本的當下血壓 | 能：最近一筆紀錄的血壓 | **自動帶入**最近一筆血壓與它的時間，護理師可改 |
| 接求助、結案、護理記錄簽核 | 不能 | 照舊 |
| 護理師排班與床位分配 | 不能：API 沒有護理師資料 | 照舊 |
| 跑馬燈內容 | 不是 API 的事 | AI 生成，護理師只核准（FR-N17） |

**FR-S15 的三條界線**：

1. **自動不等於不能改。** 護理師在專業版改過的東西（例如提前結束療程、手動換床），之後的同步**不得改回去**。同步只補護理師沒動過的地方。
2. **API 判斷不了就不猜。** 例如~~平板正在別人的療程中、~~病人還沒配平板、床號是床位清單裡停用的那一床、目的床的平板正在服務別人——這些情況一律不自動處理，在床位格標示出來，等護理師處理。
   **1006 起平板與病人的配對一律由護理師做，系統不自動接上**；護理師解除配對（換平板、配錯了）不算更正院方資料，第 1 條不適用。
3. **只讀不寫。** 本系統不回寫院方任何資料（HIS 雙向寫入照舊排除，第 1 章）。

**FR-S16 的資料範圍（1005）**：API 每次回傳全中心當天到目前為止的全部紀錄。**病人主檔與床位收全部**（床位圖才會與現場一致）；**每一筆生命徵象紀錄只收「這次療程有綁定平板」的病人**——面板只需要他們的，其餘病人的紀錄留在院方。這不會讓剛配平板的病人少掉前面幾點：下一次抓取本來就回傳當天全部紀錄。原始回應整段**不存檔**，只記抓取時間、筆數、結果與內容雜湊。

### 5.6 高風險功能控制（0910 新增）

本節適用於 FR-P03、FR-P05、FR-N06 三項。**八條全部滿足才得實作與啟用，缺一不可。**

| 編號 | 控制要求 | 對應 |
|---|---|---|
| FR-R01 | 三項功能的計算一律由**規則引擎**執行，不得使用語言模型產生判斷結果 | FDE 報告 R-1 |
| FR-R02 | 規則門檻值由臨床端書面提供並版本化儲存；未取得書面依據前，該規則只得對合成資料執行 | R-2 |
| FR-R03 | 每一則輸出可展開完整依據：所引用的歷史資料、套用的規則條目、門檻值、規則版本 | R-3 |
| FR-R04 | 輸出一律標示「僅供參考，非診斷結果」；措辭須為事實陳述（「符合 X 規則：近三次療程第 2 小時後曾回報頭暈」），不得為結論陳述（「病人有低血壓風險」） | R-4 |
| FR-R05 | 輸出不自動生效、不自動觸發任何動作：不得自動調整醫囑、不得自動改變處理優先順序、不得自動通知醫師 | R-5 |
| FR-R06 | 記錄「誰檢視、是否採納、未採納原因」，寫入稽核軌跡 | R-6，對應 FR-N13 |
| FR-R07 | 三項功能各有獨立開關，護理站管理者可即時關閉；關閉後介面完全不出現相關內容 | R-7，對應 FR-S08 |
| FR-R08 | **書面確認閘門**：未取得醫院法務／資訊室對 TFDA 分類的書面確認前，三項功能不得對真實病人啟用。系統應以設定強制此限制，而非僅寫在文件裡 | R-8 |

**法規立場說明**：以上設計取向是讓這三項功能盡可能停留在「提供資訊、由專業人員自行判斷」的範圍，而非「軟體自行做出臨床結論」。這樣的設計能否使其免於醫療器材管理，判定權在主管機關與醫院法務，開發端不做此判斷。判定完成前，功能可開發、可用合成資料驗證，但不對真實病人啟用。

## 7. 系統架構需求

- 前端採 PWA 架構，病人端搭配 MDM／Kiosk 鎖定；護理端與管理端為響應式設計，涵蓋工作站／平板／手機，另含常駐總覽螢幕模式
- 後端採 API Gateway／BFF 作為唯一對外入口，內部區分裝置綁定服務、AI 推論代理、規則引擎、臨床資料匯入服務、對外報表服務
- 資料層為單一 SQLite 檔案，置於院內伺服器本機磁碟；即時狀態由後端行程內部維護，不另設快取服務
- **無任何主動連向院外的元件**。原架構圖中的推播中繼與外部 LLM 兩條跨院外連線，於本版全部移除
- 地端 AI 推論服務部署於院內伺服器；過渡期改指向實驗室 API，切換方式為設定變更（FR-S06）
- ~~**0912**：正式環境以容器部署於院內 NVIDIA DGX Spark（ARM64、128GB 統一記憶體、與其他專案共用）~~ → **0919 取代**：正式環境為**院內一台 Windows 工作站**（Intel i7-14700、64GB 記憶體、2TB SSD ×2、x86-64，**與其他專案共用**，院方確保本系統資源足夠），以**離線安裝包**部署，資料庫檔案置於該機本機磁碟。容器降為備案，詳見《[部署規範](deployment-spec.md)》
- **0912 新增，0919 強化**：地端推論服務**不由本系統部署或啟動**。它在**另一台機器**（DGX Spark）上，對本系統而言只是一個可設定的 HTTP 端點；本系統不需要 GPU 存取權限，也不需要與它同機（DEP-16）
- **0919 新增**：病人端平板**不經 MDM 管理**。PWA 由一支自包 WebView 外殼 App 載入，Kiosk 靠 Android 內建的螢幕固定，院內自簽 CA 打包進該 App。系統端不含任何裝置管理通道，只保留佈建狀態的紀錄與逸出偵測（FR-S01）
- **0926 改寫部署形態**：上面「以離線安裝包部署」一句作廢。正式環境改以 **Docker 容器**部署，程式由 **git clone** 取得後在院內主機上就地建置；資料庫只放具名資料卷，備份寫到主機目錄。安裝包路線撤除。詳見《[部署規範](deployment-spec.md)》v3.0
- **0926 新增**：後端與推論端點之間多一個 **AI 閘道**（本系統的容器之一，不含模型），依設定檔以 LangChain 呼叫推論端點（FR-S13）。**換推論端點只換閘道的設定檔**
- **0926 新增**：外殼 App 原始碼移到**另一個私人 repo**，APK 在院內主機上以容器建置、由院內下載頁提供給平板，不經任何外部媒介（FR-S14）

## 9. 裝置管理需求（0919 全節改寫：免 MDM）

**改寫原因**：Android Enterprise 有三處必須連往院外（首次佈建連 Google、後端設定政策要呼叫 `googleapis.com`、遠端鎖定命令靠 FCM 送達），只要採用它，第 10 章假設 5「所有資料不得離開醫院網路」當場不成立。選型過程、三種容器的比較與守不住什麼，見《[平板管控：免 MDM 的全院內方案](../notes/mdm-offline-plan.md)》。

- 15 台平板以**自包 WebView 外殼 App** 載入病人端 PWA；該 App 不含業務邏輯，只負責全螢幕、憑證信任、行為限制與前景回報
- **Kiosk 鎖定使用 Android 內建的螢幕固定**（設定 → 安全性 → 螢幕固定，並勾選「解除固定前要求 PIN」），不需要 MDM、不需要 Google 帳號、不需要任何對外連線
- 院內自簽 CA 的根憑證**打包進該 App 的資源檔**，以網路安全設定宣告為院內網域的信任錨點；不採用「手動安裝到裝置信任存放區」的做法
- 裝置身分（序號與金鑰）存在 App 私有儲存，取代一次性佈建網址；**佈建為每台一次的人工作業**，步驟見平板管控方案 6.1
- 「遠端鎖定」以應用層等效做法取代：解除綁定即回到中性等待畫面並清除本地暫存（FR-P01、SRS 4.3 步驟 8）
- **逸出偵測取代逸出防止**：平板定期回報前景狀態，離開前景立即回報，護理端總覽直接顯示哪一台跳出了 Kiosk。守不住「有人解開而沒人發現」這件事，改成「解開了一定被看見」
- 螢幕恆亮由外殼 App 的常亮旗標提供，比網頁的 Wake Lock 可靠；閒置輪播使螢幕長時間亮著，對電池與螢幕壽命的影響仍須追蹤（15 台的汰換成本）
- 常駐總覽螢幕不在本節範圍：它是護理端裝置，不裝這支 App
- **本階段仍不實作任何真 MDM 串接**。院方若已有既有 MDM 方案，再以新增一個實作的方式接上，介面不變（FR-S01）
- **0926**：外殼 App 是**另一個私人 repo**，本 repo 只保留它與本系統之間的契約（FR-S14）。APK 不再由開發端建好帶進院內，而是**在院內主機上建置**，CA 與簽章金鑰都在那台主機上產生、不離開主機；平板從院內下載頁安裝（部署規範第 7 章）

### C.0 這份附錄的法律地位與維護方式

**院方（護理部）於 2026-09-19 授權：先採用以下由 AI 產生的預設內容上線，並要求全部可在護理端「系統管理 → 內容與選項」調整。**

| | 0919 之前 | 0919 之後 |
|---|---|---|
| 這些選項是什麼 | 開發端猜的暫代值，等護理部回覆 | **院方授權採用的現行版** |
| 誰可以改 | 只有改程式才能改 | 護理長與護理站管理者，線上改，即時生效 |

**維護規則（四條，寫在這裡是因為它們決定資料能不能用）**：

1. **識別碼不可改，顯示文字可改。** 每一個選項都有一個固定識別碼；護理部要把「現場處置」改成「床邊處置」，改的是顯示文字，識別碼不動。**識別碼一改，這個選項之前累積的所有紀錄就與之後的對不起來。**
2. **停用不刪除。** 不再使用的選項標為停用，不出現在新的選擇畫面，但既有紀錄仍查得到它的文字。
3. **每一次增刪改寫入稽核軌跡**，記錄誰改的、改了什麼、什麼時候。
4. **新增選項要指定它屬於哪一組**，不得憑空多出一個層級。

### C.1 設計原則：為什麼選項要長成這樣

院方要的不只是「畫面上有東西可以選」。這些選項最終要支撐兩件事：

| 數位優化的方向 | 這些選項要提供什麼 |
|---|---|
| **對個別病人的客製化** | 同一位病人的歷次紀錄要能直接相比。今天抽筋比上次嚴重、這個月第三次因為同一件事求助、上次衛教測驗錯在鉀離子——**這些都只有在選項固定且可比較時才算得出來** |
| **用大量資料優化全體病人的透析** | 要能當成模型的輸入特徵與標註。**求助類別（問題）→ 處理方式（做了什麼）→ 處理結果（有沒有用）→ 有沒有再發**，這四段串起來就是一筆完整的標註資料 |

因此五條設計原則：

| # | 原則 | 不這樣做會怎樣 |
|---|---|---|
| C-1 | **每個選項有固定識別碼，顯示文字與識別碼分離** | 護理部改一次字，歷史資料就斷成兩段，趨勢圖從那天起失真 |
| C-2 | **窮盡且互斥，一律保留「其他」並要求填自由文字** | 沒有「其他」，人會硬塞進最接近的那一格，整批資料被汙染而且看不出來 |
| C-3 | **同一份清單裡粒度一致**，不混「症狀」與「情境」 | 混了之後統計出來的百分比沒有意義——分母不是同一件事 |
| C-4 | **四段可串成因果鏈**，共用同一個事件編號 | 只知道發生過什麼，不知道做了有沒有用，訓練不出任何東西 |
| C-5 | **情境欄位由系統自動帶入，不問人** | 療程第幾小時、脫水進度、班別、距上次透析幾小時——問了會增加操作步驟（前提四），而系統本來就知道 |

**「其他」的使用率本身就是指標**：某一組選項的「其他」超過設定比例（預設 15%），系統要在管理介面標示「這份清單可能不夠用」，提醒回頭檢討。**清單品質不靠一次設計對，靠上線後看得見它哪裡不對。**

### C.2 求助類別（FR-P06，病人端）

**選取依據**：血液透析治療中最常見的併發症，依臨床文獻的常見程度排序，前三項（透析中低血壓、肌肉痙攣、噁心嘔吐）就涵蓋大多數療程中事件。**病人看到的是白話症狀，不是診斷名稱**——病人不會說「我低血壓」，會說「我頭暈想吐」。

| 識別碼 | 病人看到的字 | 對應的常見併發症 | 分派表預設急迫度 |
|---|---|---|---|
| `SX_DIZZY` | 頭暈、冒冷汗、快昏倒 | 透析中低血壓——**最常見** | 緊急 |
| `SX_CRAMP` | 抽筋 | 肌肉痙攣 | 急 |
| `SX_NAUSEA` | 想吐、噁心 | 噁心嘔吐 | 急 |
| `SX_CHEST` | 胸悶、胸痛、很喘 | 胸痛／呼吸困難 | 緊急 |
| `SX_HEADACHE` | 頭痛 | 頭痛／失衡症候群 | 一般 |
| `SX_ITCH` | 皮膚很癢 | 搔癢 | 一般 |
| `SX_CHILL` | 發冷、發抖、覺得發燒 | 發燒畏寒（可能為感染） | 緊急 |
| `SX_ACCESS` | 打針的地方流血、腫、痛 | 血管通路問題 | 緊急 |
| `SX_BLEEDING` | 其他地方流血止不住 | 出血 | 緊急 |
| `SX_OTHER_BODY` | 身體其他地方不舒服 | — | 急 |

非臨床組（**0920 起多一項**）：

| 識別碼 | 病人看到的字 | 分派表預設急迫度 |
|---|---|---|
| `SX_MACHINE` | 機器一直叫 | 急 |
| `NC_TOILET` | 我要上廁所 | 一般 |
| `NC_ENV` | 會冷／會熱／燈太亮／要蓋被子 | 一般 |
| `NC_THIRST` | 口渴、肚子餓 | 一般 |
| `NC_OTHER` | 其他，請有人過來一下 | 一般 |

> **`SX_MACHINE` 於迭代 9.1（0920）由臨床組移到非臨床組**，並排在該組第一個。
> 機台警報不是身體症狀，病人照著「身體不舒服」找不會找到它。
> **預設急迫度與分派規則都沒有變**：非臨床＋急仍然分派給護理師，不會掉到護佐那一條。

**三件必須講清楚的事**：

1. **「分派表預設急迫度」是靜態對照表，不是系統的判斷。** 它只決定「這一則先跳到誰的畫面上」，符合 FR-N03 對分級依據的限制（病人自選急迫度＋靜態分派表，不得摻入模型推論）。**病人仍可自行調整急迫度，病人選的優先於預設值。**
2. **這張表不是分診，畫面上不得出現任何疾病名稱。** 右欄的「對應併發症」只存在於本文件與後端對照資料，**不顯示給病人也不顯示給護理師**——顯示了就變成系統在給診斷提示，那是 FR-P03／P05 的範圍，本階段未實作。
3. **臨床組的順序是刻意的**：最常發生且最需要快速反應的排最前面，讓病人在不舒服時第一眼就看到。**不依字母、不依識別碼排序。**

**1010：圖示要不看字也認得出症狀。** 院方反映部分圖示與文字對不上（例如閃電代表抽筋、波浪代表想吐、大腦代表頭痛）。病人不舒服時不一定看得清楚字，因此每一個類別的圖示改成**畫出那個症狀本身**：人的頭、胸口、小腿、手臂加上症狀的記號（頭暈畫轉圈、抽筋畫小腿與緊繃線、想吐畫摀嘴、頭痛畫頭與痛點、癢畫抓的動作、發冷畫發抖與溫度計、打針處畫手臂與針、流血畫傷口與血滴）；非臨床組的機器一直叫畫機器與聲波、口渴肚子餓畫杯子與碗、環境畫冷熱與被子。圖示一律是自帶的向量圖，**仍然配字**（字是正式的意思，圖是幫忙認）；每一個圖示代表什麼登記在《介面設計基準》4.6，病人端的紅色仍只給求助區。院方新增的類別沒有登記圖示時照舊用替代圖示加字。

### C.3 處理方式（FR-N10，護理端結案時選）

**設計對齊 C.2**：既然求助類別改成以常見併發症為骨架，處理方式就要涵蓋這些併發症實際會做的處置，否則護理師只能一直選「現場處置」，資料等於沒蒐集到。

| 識別碼 | 顯示文字 | 說明（只給護理端的小字提示） |
|---|---|---|
| `M_OBSERVE` | 觀察並記錄生命徵象 | 量血壓、脈搏，記錄下來 |
| `M_POSITION` | 調整姿勢 | 平躺、抬腿、翻身 |
| `M_UF_ADJUST` | 調整脫水（依醫囑） | 降速或暫停 |
| `M_MACHINE_SET` | 調整機台設定（依醫囑） | 血流速、透析液溫度或鈉濃度 |
| `M_SALINE` | 給予生理食鹽水回填（依醫囑） | |
| `M_MEDICATION` | 給藥（依醫囑） | |
| `M_LOCAL_CARE` | 局部處置 | 止血、加壓、冰敷、按摩抽筋處 |
| `M_ACCESS_CARE` | 血管通路處置 | 重新固定、換敷料、檢查震顫 |
| `M_NOTIFY_MD` | 通知醫師 | |
| `M_EARLY_END` | 提前結束療程（依醫囑） | |
| `M_SUPPLY` | 提供物品 | 被子、水杯、尿壺 |
| `M_ASSIST_ADL` | 協助如廁或移位 | |
| `M_ENV_ADJUST` | 環境調整 | 空調、燈光、床位角度 |
| `M_REASSURE` | 說明與安撫 | |
| `M_REFERRAL` | 轉介 | 社工、營養師、感染管制 |
| `M_OTHER` | 其他（請說明） | **選了必須填自由文字** |

**「依醫囑」四個字不是客套話。** 帶著它的選項記錄的是「護理師執行了醫師的指示」，不是「系統建議這樣做」。沒有這四個字，同一批資料日後被拿來訓練模型時，會變成「系統學會了在某某情況下要調降脫水量」——那就跨進 SaMD 了。**這是內容設計層面的風險控制，不是措辭潔癖。**

可複選：一次求助常常做了不只一件事。**複選時要記錄順序**，因為「先平躺再回填食鹽水」和「先回填再平躺」是不同的處置路徑。

### C.5 透析前問卷（FR-P02）

**重新設計的原因有兩個**：原本 10 題全部必答，對躺著、手不能動的長者太長；而且題目全部平行排列，看不出哪幾題是每次都要有的基準。

**新結構：5 題必答（每次都問）＋條件追問（答「有」才展開）＋自動帶入的情境欄位（不問人）。**

必答 5 題——**這 5 題的存在理由是「每次都有同一組欄位，才畫得出這位病人自己的趨勢」**：

| 識別碼 | 病人看到的字 | 白話提示 | 答案尺規 |
|---|---|---|---|
| `Q_FLUID` | 跟上次洗完比，有沒有比較腫 | 腳踝、小腿、眼皮 | 沒有／有一點／腫很多 |
| `Q_DYSPNEA` | 會不會喘 | 走路、平躺、或休息的時候 | 沒有／輕微／中等／嚴重 |
| `Q_DIZZY` | 會不會頭暈 | 站起來的時候或平常 | 沒有／輕微／中等／嚴重 |
| `Q_CRAMP` | 上次洗完到現在有沒有抽筋 | | 沒有／偶爾／常常 |
| `Q_ACCESS` | 打針的地方有沒有狀況 | 瘻管或導管 | 沒有／有 |

條件追問（只在對應必答題答「有」時出現）：

| 觸發 | 識別碼 | 追問內容 |
|---|---|---|
| `Q_ACCESS` = 有 | `Q_ACCESS_DETAIL` | 是哪一種：流血止不住／紅腫熱痛／摸不到震顫／其他（可複選） |
| `Q_DYSPNEA` ≥ 中等 | `Q_ORTHOPNEA` | 晚上睡覺要不要墊高枕頭才睡得著 |
| `Q_CRAMP` ≠ 沒有 | `Q_CRAMP_WHEN` | 抽筋發生在：洗腎中／洗完回家後／半夜 |

每次都問但放在第二頁的 4 題（**分頁是為了第一頁能一眼看完，不是為了少問**）：

| 識別碼 | 病人看到的字 | 答案尺規 |
|---|---|---|
| `Q_FEVER` | 這幾天有沒有發燒、發冷 | 沒有／有 |
| `Q_CHEST` | 有沒有胸悶或胸痛 | 沒有／輕微／中等／嚴重 |
| `Q_ITCH` | 皮膚會不會癢 | 沒有／輕微／中等／嚴重 |
| `Q_EVENT` | 上次洗完到現在，有沒有去急診、住院，或跌倒 | 沒有／有（有→追問哪一種） |

**`Q_EVENT` 是本次新增的最有價值的一題**：透析間期的事件是護理師本來就會口頭問的，但問到的答案留在口頭上。把它結構化，才接得起「上次發生什麼 → 這次的狀況」這條線。

自動帶入、不問病人的情境欄位：

| 欄位 | 從哪來 |
|---|---|
| 距上次透析幾小時 | 前一次療程紀錄 |
| 本次班別 | 排班 |
| 前次療程是否提前結束 | 前一次的求助結案紀錄 |
| 前次透析後回饋分數 | 回饋問卷 |

**題目版本要編號。** 題庫一改就換一個版本號，每一份作答記錄它當時的版本；沒有版本號，改過題目之後的趨勢圖就是把兩種不同的問題畫在同一條線上。

### C.6 透析後衛教題庫（FR-P07）

**七個主題，對應透析族群最常見的自我照護失誤**，每個主題 5 題，共 35 題。每次測驗抽 5 題。

| 識別碼 | 主題 | 為什麼是它 |
|---|---|---|
| `EDU_FLUID` | 水分與體重控制 | 透析間期體重增加過多是最常見也最直接影響療程的問題 |
| `EDU_K` | 鉀離子（高鉀食物） | 高血鉀可致命，且來源多半是吃進去的 |
| `EDU_P` | 磷（高磷食物與磷結合劑） | 長期影響骨骼與血管，病人最容易忽略 |
| `EDU_NA` | 鹽分與口渴的關係 | 病人常以為「少喝水」就好，不知道問題在鹽 |
| `EDU_ACCESS` | 血管通路照護 | 通路失效等於治療中斷，而多數傷害是可預防的 |
| `EDU_MED` | 用藥與返診 | 漏藥、自行停藥、忘記回診 |
| `EDU_WARN` | 什麼情況要馬上找人 | 把「何時該求助」本身當成一個知識點來教 |

**每一題都要標上知識點識別碼**，答錯即累積在那位病人的該知識點上。

**抽題規則（這就是「個人化」的具體做法，不是抽籤）** —— 依序取滿 5 題：

| 順位 | 抽什麼 | 理由 |
|---|---|---|
| 1 | 這位病人**上次答錯**的知識點 | 沒學會的要再問 |
| 2 | **本次療程實際發生過的事**對應的主題 | 今天抽筋又體重增加多 → 抽水分控制題。當天發生的事，當天講最有效 |
| 3 | **最久沒被問到**的主題 | 避免永遠只問同幾題 |
| 4 | 隨機補足 | |

**知識點與題庫的維護**：主題可增刪，題目可改寫，但**知識點識別碼與題目識別碼不可重用**——一個識別碼一輩子只對應一個知識點，否則「這位病人在鉀離子上錯了三次」這句話會變成假的。

### C.7 回饋題目（FR-P08）

**設計取捨**：每次都問太多題，病人會開始亂按，資料反而變髒。因此分成「每次問的 4 題」與「每月加問的 2 題」。

每次療程後（目標一分鐘內答完）：

| 識別碼 | 題目 | 尺規 |
|---|---|---|
| `FB_COMFORT` | 今天洗腎的過程，身體舒不舒服 | 五格表情，很不舒服→很舒服 |
| `FB_MOOD` | 今天的心情 | 五格表情 |
| `FB_CARE` | 有沒有覺得被好好照顧 | 五格表情 |
| `FB_NOTE` | 有沒有什麼想讓我們知道的 | 自由文字，**選填** |

每月加問（同一位病人一個月內只出現一次）：

| 識別碼 | 題目 | 尺規 |
|---|---|---|
| `FB_BURDEN` | 最近會不會覺得洗腎很累、不太想來 | 五格 |
| `FB_SLEEP` | 最近睡得好不好、吃得下嗎 | 五格 |

**「趨勢偏離」怎麼判定（這一條要寫死，因為它最容易滑進臨床判斷）**：

- 比較的是**這位病人自己**近六次的移動中位數，不是跟其他病人比
- 連續兩次低於自己的中位數達設定幅度（預設 2 分）才標示
- **判定由固定算式完成，不經語言模型**
- 輸出是事實陳述：「近兩次的心情分數比自己過去六次的中位數低 2 分以上」。**不得寫成「疑似憂鬱」「建議轉介」之類的結論**
- **不自動觸發任何動作**，不自動通知社工，只在護理端顯示
- 門檻（六次、2 分、連續兩次）全部可在系統設定調整

**1010：遊戲資料照同一套規則**（FR-N20）：只跟本人自己的移動中位數比，**前 10 次只當練習、不列入基準**；固定算式、不經語言模型；輸出是事實陳述，例如「近兩週麻將連連看找一對的時間比自己過去的中位數多 40%」，**不得寫成任何認知或情緒的結論**；不自動觸發任何動作；門檻全部可調。

**這一條的界線**：上面的算式是「把病人自己說的分數拿來相減」，屬於原樣呈現；一旦要把它變成主動警示、或摻入其他臨床資料一起判斷，就進入 5.6 節 FR-R 的範圍，必須先滿足那八條。**本階段不跨過這條線。**

### C.8 這些內容如何被調整

全部集中在護理端「系統管理 → 內容與選項」底下，分成五塊，對應 C.2～C.7：

| 區塊 | 可做的事 |
|---|---|
| 求助類別 | 增刪改、調整順序、調整分派表預設急迫度、停用 |
| 處理方式與處理結果 | 增刪改、調整順序、停用；「其他」不可停用 |
| 透析前問卷 | 改題目文字與提示、調整必答／第二頁、增刪題目、**改動即產生新版本號** |
| 衛教題庫 | 增刪改題目與選項、調整主題、設定抽題規則的權重 |
| 回饋題目 | 改題目文字、調整每月加問的間隔、調整趨勢偏離的三個門檻 |

**四條護欄**（介面上要擋住，不是寫在說明裡）：

1. 識別碼欄位在建立後不可編輯
2. 停用是唯一的移除方式，沒有刪除按鈕
3. 每一組的「其他」不可停用、不可刪除
4. 問卷與題庫改動時，畫面要明白告訴操作者「這會產生新的版本，之前的作答仍以舊版本留存」

**0919 迭代 9 實作方式**：四條都是**後端擋一次、前端擋一次**——只藏前端等於沒擋。
前端那一次的做法是「按鈕不出現」，不是「按了才說不行」：
識別碼那一格在編輯時是純文字而非輸入框（護欄 1）、整頁沒有任何刪除按鈕（護欄 2）、
「其他」那一列沒有停用按鈕（護欄 3）、版本提示寫在按下去之前（護欄 4）。

**「其他」的使用率**也做進同一個畫面：超過設定比例（預設 15%，可調）時，
上方會出現一條提醒「這份清單可能不夠用」。剛部署時資料量不足，這一條不會出現。
