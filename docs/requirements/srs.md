# 血液透析中心平板照護輔助系統 — 軟體需求規格書（SRS）

版本：v1.0　文件狀態：草案　適用對象：FDE工程團隊、醫院資訊室、護理部、法務/法規合規承辦人

---

## 1. 文件目的與範圍

本文件定義「血液透析中心平板照護輔助系統」之軟體需求，涵蓋病人端15台Android平板、護理端多裝置應用、後端服務、AI輔助功能與資料治理規範。系統目標為在不取代任何臨床判斷與侵入性操作的前提下，將可數位化與可數位優化的護理工作流程（詳見附錄A十大工作區塊分類）予以實作。

本文件**不涵蓋**：機台參數整合、藥局/HIS系統雙向寫入、透析機台硬體通訊協定（列為未來擴充項目）。

---

## 2. 名詞定義與縮寫

| 詞彙 | 定義 |
|---|---|
| FDE | Forward Deployed Engineer，本專案之技術實作與現場迭代工程師 |
| PWA | Progressive Web App，具離線快取與安裝能力之網頁式應用 |
| SaMD | Software as a Medical Device，軟體醫療器材，本專案任二、四、九、八任務中之風險分層/預警/劑量建議功能可能觸及此範疇 |
| 裝置綁定 | 將特定病人身分與特定平板序號、當次療程時段建立一次性關聯之機制 |
| 護理站主控台 | 護理端應用中，具備排班管理、裝置指派、緊急總覽等管理功能之介面模組 |
| Session Token | 綁定後由後端核發、限時且限裝置使用之存取憑證 |

## 3. 系統總覽

### 3.1 使用者角色

| 角色 | 說明 |
|---|---|
| 病人 | 使用病人端平板進行症狀回報、衛教學習、求助；**不具備任何登入或身分選擇操作** |
| 護理師 | 使用護理端裝置進行排班指派、即時監看、記錄審閱簽核、緊急處置 |
| 護理站管理者 | 具備額外權限：MDM裝置管理、帳號權限設定、稽核紀錄查詢 |
| FDE工程師 / 系統管理者 | 系統部署、模型與規則調整、資料治理設定，不具臨床資料存取權 |

### 3.2 系統邊界

系統由病人端PWA、護理端PWA、後端API Gateway、AI Proxy Service、裝置綁定服務、推播通知服務、醫院資料庫（匿名化）、即時狀態快取，以及經治理閘道呼叫之外部LLM API所組成。詳細架構見第7章與附圖。

## 4. 使用者角色與權限模型（本版修正重點）

### 4.1 修正原則

**病人端平板不提供任何登入介面（無帳號、密碼、生物辨識、或病人自選身分清單）。** 病人於平板上能存取的所有資料與功能，其存取權限之啟用，一律由護理師在護理站主控台或當班護理端裝置上，透過「裝置指派」動作觸發。此設計理由：

1. 病人在透析情境下（可能虛弱、視力不佳、認知負荷高）不適合承擔身分驗證責任
2. 平板為機構共用裝置，若允許病人自行選擇/切換身分，會產生資料誤植給錯病人的風險
3. 從法規遵循角度，臨床資料的存取授權應可追溯到「哪一位護理師、何時、為哪一位病人」核准，而非病人自證身分

### 4.2 權限矩陣（節錄）

| 功能 | 病人（平板） | 護理師 | 護理站管理者 |
|---|---|---|---|
| 症狀回報、求助 | 可（僅限已被指派之當次療程） | 檢視 | 檢視 |
| 衛教內容瀏覽/測驗 | 可（已指派後） | 檢視完成度 | 檢視完成度 |
| 護理記錄審閱簽核 | 不可 | 可 | 可 |
| 裝置-病人指派/解除 | 不可 | 可 | 可 |
| 多病人即時總覽 | 不可 | 可 | 可 |
| MDM裝置鎖定設定 | 不可 | 不可 | 可 |
| AI規則/模型參數調整 | 不可 | 不可 | 不可（僅FDE） |

### 4.3 裝置與病人綁定流程（取代原「病人自行登入」設計）

**前置條件**：護理站已建立當日排班表（病人-療程時段對應）。

1. 病人到達透析中心，護理師於護理站主控台（或當班護理端裝置）選取當日排班中的病人
2. 護理師選擇欲指派之平板序號（可透過清單選取、掃描病人手環條碼、或掃描平板背面QR碼三種方式擇一）
3. 護理師確認指派後，請求送至後端**裝置綁定服務（Device Binding Service）**
4. 裝置綁定服務核發一組**限時Session Token**，同時綁定「病人ID＋平板序號＋當次療程時段」三項，並透過安全通道推送至該平板
5. 平板在收到有效Session前，僅顯示中性等待畫面（例如「請由護理人員為您開始使用」），不顯示任何病人可識別資訊、不提供輸入欄位
6. Session啟用後，平板僅能存取「本次已綁定病人」之資料與功能，無法切換查看其他病人
7. Session失效條件（三者擇一觸發）：
   - 護理師於主控台執行「下機/結束」正常流程
   - 護理師手動於主控台提前解除綁定（如需更換平板或病人提前離開）
   - 超過療程時間上限（可設定，預設6小時）系統自動失效
8. Session失效後，平板本地暫存資料需清除，並回復至「等待指派」狀態，避免前一位病人資料殘留給下一位使用者
9. 每一次綁定與解除動作，系統須記錄操作護理師帳號、時間戳、病人ID、平板序號，寫入稽核軌跡，供事後追溯與法規稽核

### 4.4 例外情況

- 平板離線期間無法完成新綁定；若原本已有效Session且平板離線，症狀回報可暫存本地（IndexedDB），恢復連線後同步，但求助/緊急功能於離線期間需明確提示「目前無法即時通知護理站」
- 若同一病人短時間內被誤指派至兩台平板，系統應偵測並阻擋第二次綁定，提示護理師「該病人已有進行中之綁定」

## 5. 功能性需求

以下依前期六項「部分協助」任務深度拆解（病人端：任務二/四/五；護理端：任務七/八/九）整理為需求編號，並標註優先權（P0必要／P1次要）與SaMD風險註記。

### 5.1 病人端

| 編號 | 需求描述 | 優先權 | SaMD風險 |
|---|---|---|---|
| FR-P01 | 平板於未綁定狀態僅顯示中性等待畫面，無登入介面 | P0 | 無 |
| FR-P02 | 已綁定後，提供結構化透析前症狀問卷（水腫、喘、發燒、出血等） | P0 | 無 |
| FR-P03 | 系統依病人歷史體重增幅/血壓趨勢，標註當日風險提示供護理師參考 | P1 | **高**（風險分層輸出） |
| FR-P04 | 提供個人化衛教內容（依透析史、衛教完成紀錄動態生成），支援多語言 | P1 | 無 |
| FR-P05 | 透析中定時彈出式症狀問卷，並可依歷史同時段症狀模式提前預警 | P1 | **高**（預警輸出） |
| FR-P06 | 提供求助按鈕，觸發時自動附帶近期症狀趨勢摘要給護理端 | P0 | 中（僅摘要呈現，非診斷） |
| FR-P07 | 下機後提供個人化離院衛教重點與自適應測驗，標記需加強衛教之知識點 | P1 | 無 |
| FR-P08 | 情緒/滿意度回饋問卷，長期趨勢異常時建議轉介社工 | P2 | 中 |

### 5.2 護理端

| 編號 | 需求描述 | 優先權 | SaMD風險 |
|---|---|---|---|
| FR-N01 | 護理站主控台支援當日排班建立與裝置指派（見4.3流程） | P0 | 無 |
| FR-N02 | 多病人即時狀態總覽儀表板，顯示各病人當前療程進度與異常提示 | P0 | 無 |
| FR-N03 | 緊急通報接收，含病人症狀趨勢背景摘要，依嚴重度分級路由 | P0 | 中 |
| FR-N04 | 事件當下快速點選式記錄範本，事後由AI草擬敘述初稿供審閱 | P1 | 無（AI僅草擬，護理師簽核） |
| FR-N05 | 護理記錄自動預填草稿（依病人自報資料），護理師審閱簽核取代重新輸入 | P1 | 無 |
| FR-N06 | 每月/每週抽血與Hb/EPO趨勢儀表板，AI標註異常軌跡病人並提供劑量調整參考建議 | P1 | **高**（劑量建議） |
| FR-N07 | 透析適足性（Kt/V、URR）自動計算與趨勢預測 | P1 | 中 |
| FR-N08 | 心理社會風險趨勢彙總與轉介建議 | P2 | 中 |
| FR-N09 | SOP/藥品劑量查詢介面，僅限醫院既有文件範圍內回答 | P1 | 中 |

### 5.3 系統管理

| 編號 | 需求描述 | 優先權 |
|---|---|---|
| FR-S01 | MDM整合，支援裝置Kiosk鎖定、遠端註冊與解除註冊 | P0 |
| FR-S02 | 所有裝置綁定/解除、資料存取、AI輸出使用情形均需寫入稽核軌跡 | P0 |
| FR-S03 | AI API呼叫一律經後端閘道轉發，平板不持有任何API金鑰 | P0 |
| FR-S04 | 病人可識別資訊不得直接傳送至外部LLM服務 | P0 |

## 6. 非功能性需求

| 類別 | 需求 |
|---|---|
| 效能 | 症狀回報送出至護理端接收延遲需<5秒（正常網路狀況下） |
| 可用性 | 病人端療程期間介面需穩定運作4小時以上不當機；護理端多裝置存取一致 |
| 安全性 | Session Token限時效、限裝置；所有API呼叫需TLS加密；病人資料傳輸與儲存均需符合醫院PHI規範 |
| 離線韌性 | 衛教靜態內容可離線瀏覽；症狀回報可離線暫存並於恢復連線後同步；求助功能離線時需明確告知限制 |
| 多語言 | 衛教內容與介面至少支援中文（繁體）；可擴充其他語言 |
| 可擴充性 | 前後端架構需可延伸支援未來護理站Dashboard，共用同一套API層 |
| 感染管制 | 平板共用需搭配醫院訂定之消毒SOP（非軟體範疇，僅提示） |

## 7. 系統架構需求（摘要，詳見附圖）

- 前端採PWA架構，病人端搭配MDM/Kiosk鎖定；護理端為響應式設計，涵蓋工作站/平板/手機
- 後端採API Gateway/BFF作為唯一對外入口，內部區分裝置綁定服務、AI Proxy Service、推播通知服務
- 資料層區分醫院資料庫（匿名化，含稽核軌跡）與即時狀態快取（供多病人即時總覽使用）
- 外部LLM API為醫院內部網路邊界外之服務，僅由AI Proxy Service單向呼叫，不接收病人可識別資訊
- 詳細軟體全端架構圖與系統實體架構圖見本文件隨附之架構圖

## 8. 資料治理與法規遵循需求

- 任務二、四、五、七、八、九中標註「高」SaMD風險之功能（風險分層、預警、劑量建議），上線前須與醫院法務/資訊室確認是否落入TFDA醫療器材軟體認證範疇
- AI輸出於介面上須明確標示「僅供決策輔助，非診斷結果」
- 所有AI呼叫、資料存取、裝置綁定/解除動作須留存可稽核之操作紀錄，保留期限依醫院規範
- 病人可識別資訊（PII/PHI）不得以任何形式直接傳送至外部LLM服務商，一律經後端閘道去識別化處理

---

## 9. 裝置管理需求

- 15台平板須以MDM（如Android Enterprise/Samsung Knox）納管，鎖定為單一PWA網址之Kiosk模式
- 支援遠端裝置註冊、解除註冊、韌體/應用更新推送
- 裝置遺失或異常時，護理站管理者可遠端鎖定或清除本地暫存資料

---

## 10. 假設與限制

- 假設醫院已同意匿名化資料可用於AI模型訓練與推論
- 假設透析中心具備穩定之院內Wi-Fi網路覆蓋
- 不假設病人具備操作智慧型裝置之熟練度，介面需保持極簡
- 機台參數整合、藥局系統雙向寫入列為未來擴充，本版不實作
