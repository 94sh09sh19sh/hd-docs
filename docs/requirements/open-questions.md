## 0. 怎麼用這份文件

### 0.1 急迫度分級

| 級別 | 定義 | 處理原則 |
|---|---|---|
| **A** | **過期就作廢。** 錯過某個時點，答案永遠拿不到 | 立刻提出，不排隊 |
| **B** | 阻塞「對真實病人或真實資料啟用」。功能做得出來，但不能開 | 開發照做，同時併行催 |
| **C** | 阻塞實作決策或硬體選型。不確認就只能猜，猜錯要重工 | 提出後暫用可替換的介面層頂著 |
| **D** | 可先用暫代值。答案來了替換掉即可，不影響架構 | 一併問，但不擋進度 |

**分級的意思不是重要性，是時間性。** D 級的事項可能對臨床很重要（例如症狀問卷題目要不要改），但它晚兩週回覆不會造成任何重工；A 級只有一項，晚兩週就永久損失。

### 0.2 狀態

| 狀態 | 意思 |
|---|---|
| **待提出** | 開發端尚未正式問出去 |
| **已提出** | 已問，等回覆。記錄提出日期與受詢問單位 |
| **已回覆** | 有答案了，但還沒反映到文件或程式 |
| **已結案** | 答案已反映到對應文件與實作，移到第 7 章 |
| **作廢** | 需求變更或時點已過，不再需要答案。**要寫明為什麼作廢** |

### 0.3 維護方式

- 每週三定版日檢視一次，更新狀態欄
- 新問題隨時加，編號只增不重複使用；已結案的移到第 7 章但**保留原編號**
- 其他文件要引用某個待確認事項時，寫 `Q-0X` 編號，不要複製內容過來（複製就會有兩份不同步的清單）
- 答案回來後，**先改對應的需求文件，再把這裡的狀態改成已結案**，順序不要顛倒

## 2. A 級：過期就作廢

### Q-01 成效基準的量測人力與時程

| | |
|---|---|
| **問誰** | 護理長（量測執行）、護理部（背書） |
| **急迫度** | **A —— 唯一過期作廢的一項** |
| **卡住** | 新增任務一之(1)「向長官與政府展現重要性」的全部說服力 |
| **狀態** | **已排定下週執行（0919）**。FR-M07 的建檔介面早在 0911 完成，系統這一側不再是瓶頸，**只差現場的數字** |

**背景**

成效基準是「系統啟用前，同一件事要花多久」。例如病人按鈴到護理師走到床邊，現在平均幾分鐘。系統上線後這個數字會自動被記錄，但**上線前的數字不存在於任何地方**——它只存在於現在正在發生的紙本與口頭流程裡。

要取得它，需要有人在治療區實測：碼表、紀錄表、三個班次、每項約 20 筆。這佔用護理師工時，是**一次性成本**。

**0919：為什麼「這週部署、下週量測」不算把它放掉。** 第一次部署是**首波試用，只開放少數護理師與少數病人**（DEP-33）。紙本流程對其餘的班次與病人**仍然照舊在跑**，因此「以前要花多久」還量得到。真正關上這扇門的不是第一次部署，是**全單位改用系統的那一天**。

但這不代表可以再拖：首波試用的存在本身就在改變現場的習慣，而且一旦護理長覺得「系統都上了，還量什麼」，這件事就會自然消失。**下週要做，而且要在會議上被指定給一個人。**

**不確認的後果**

系統一上線，紙本流程就消失，再也無從量測「以前要花多久」。屆時所有「省下 X 分鐘」的說法都只能靠估算，經不起長官追問。這會直接掉掉新增任務一的第一個目的——沒有基準，只能說「系統很方便」；有基準，才能說「按鈴到到場從 4.2 分鐘降到 1.6 分鐘」，後者才寫得進評鑑資料。

**先問這一題，可能省掉一半工作**

> 護理部現在有沒有已經在統計的品質指標？例如透析中低血壓事件數、跌倒件數、護理紀錄完成時間、病人滿意度調查。

現成的數字比重新測便宜太多，而且是護理部自己的資料，拿去給長官看時公信力更高。**先撈現成的，撈不到的才實測。**

**具體要問的七題**

| # | 問句 | 為什麼要問 |
|---|---|---|
| 1 | 預計哪一週開始對真實病人試用？ | 從這天往回推，量測必須在這之前做完 |
| 2 | 現行的紙本記錄單、交班表、呼叫鈴流程能不能給一份？ | 測的東西要對得上現行流程，否則數字沒有可比性 |
| 3 | 能不能指定一位種子護理師協助，而不是全員配合？ | 一個人記三個班次就夠，全員配合會變成大家的負擔 |
| 4 | 下面五項要測的事，哪幾項不值得測、或該換成別的？ | 清單是開發端擬的，護理長才知道現場真正的痛點 |
| 5 | 每項 20 筆、分三班取樣，可行嗎？ | 樣本數要當面談，太多做不完、太少沒說服力 |
| 6 | 之後這些數字要給院長室看，誰來背書說「這是本單位認可的基準」？ | 現在講好，比事後被質疑「這數字哪來的」好 |
| 7 | 願不願意同時做一次護理師自陳問卷（紙本記錄有多少是事後補寫的）？ | 這題不用碼表，但很能打動長官——它量的是「以前有多不精確」 |

**建議量測的五項**（第 4 題請護理長刪減）

| # | 要測的事 | 怎麼測 | 建議樣本 |
|---|---|---|---|
| 1 | 病人按鈴到護理師到床邊 | 現場碼表抽測 | 分三班各 20 次 |
| 2 | 一次事件記錄從動筆到完成 | 護理師自記起訖時間 | 20 筆 |
| 3 | 每班口頭重複衛教的次數與時長 | 觀察記錄 | 3 個班次 |

**0911 實作現況**

建檔介面已完成（護理端「成效基準」頁）。五條指標的定義、建議量測方式、建議樣本數都已建好，畫面逐條列出「尚未建檔」與「只有估算值」兩種缺口——上線前只有這個畫面看得出來還差什麼。

建檔時**必須填背書者**（本頁第 6 題的那個人），空著存不進去：沒有出處的數字，被院長室問到「這數字哪來的」就答不出來。同一條指標可以重測重建，舊版保留並標記為已被取代，不會被蓋掉。

**如果來不及測（退路，但要標明）**

可以用回溯式自陳問卷（請護理師估「以前大概要多久」），或從現有紙本紀錄推估。但這種數字在文件與簡報上**必須標明是估算**，不能當實測講。被長官問到來源時遮掩一次，後面所有數字的可信度都跟著沒了。

這條退路已寫進系統：建檔時來源可選「估算（非實測）」，選了之後該筆資料在所有畫面上都會帶著「引用時必須標明是估算，不得當成實測數字陳述」的提示，建檔進度表也會把「只有估算值」的指標另外列出來。**把退路做進系統，是為了讓它留下痕跡，不是為了讓它變得方便。**

**這一項與前提四的輕微衝突**

《[FDE 評估報告](fde-assessment.md)》前提四要求「不得影響主要使用功能」，而基準量測會佔用護理師時間。這是刻意接受的例外：一次性成本，且不做就沒有第一個目的。降低衝擊的做法就是第 3 題——指定一位種子護理師，不要全員配合。

## 3. B 級：阻塞對真實病人或真實資料啟用

這五項的共同特徵是：**功能可以 100% 做完並用合成資料驗收，但不能對真實的人或真實的資料開。** 因此它們不擋開發進度，只擋上線。

### Q-02 三項高風險功能的 TFDA 分類書面確認

| | |
|---|---|
| **問誰** | 醫院法務、資訊室（必要時由醫院向食藥署函詢） |
| **急迫度** | B |
| **卡住** | 迭代 7 的啟用（FR-R08）。實作不受阻 |
| **狀態** | 待提出（0909 已列為待決，尚未取得書面回覆） |

**背景**

三項功能——FR-P03 風險分層、FR-P05 療程中預警、FR-N06 劑量調整參考——一旦其輸出被拿來做臨床判斷依據，在台灣可能落入《醫療器材管理法》的軟體醫療器材（SaMD）範疇。

開發端的設計取向是盡量讓它們停在「提供資訊、由專業人員自行判斷」的一側：用可攤開的規則而非語言模型、輸出可回溯到依據、不自動生效、措辭為事實陳述而非結論。但**分類判定權不在開發端**，本專案自行判斷不具法律效力。

**不確認的後果**

功能做得出來但不能對真實病人開。更糟的情況是先開了、之後才發現需要走查驗登記，屆時已經產生了臨床使用紀錄，處理起來比事前確認麻煩得多。

**具體要問的**

1. 這三項功能，依院方目前的理解，是否落入醫療器材軟體管理範疇？
2. 如果不確定，醫院是否有既有管道向食藥署函詢或申請分類分級諮詢？要多久？
3. 院內是否有其他已上線的臨床決策支援系統走過同樣的判定？走的是哪一條路？
4. 若判定為需要查驗登記，院方的立場是「調整功能設計以避開」還是「走完認證」？
5. 開發端的八條控制措施（規則可攤開、依據可複核、不自動生效、事實陳述式措辭、檢視與採納留痕、可全域關閉）是否足以佐證「非醫療器材」的主張？還缺什麼？
6. 在書面確認到位之前，用合成資料開發與內部驗收是否有任何限制？

**現況／暫代做法**

以功能開關實作硬閘門（`RISK_STRATIFICATION`／`INTRA_DIALYSIS_ALERT`／`DOSE_REFERENCE`），三者預設關閉，開啟需留核准紀錄。閘門未開時，三項功能只對已標記為合成資料的病人執行。

**要帶去談的材料**

《[FDE 評估報告](fde-assessment.md)》第八章的 R-1～R-8 控制措施表，以及《[軟體需求規格書](srs.md)》5.6 節。這兩份就是「我們做了哪些事讓它不像醫療器材」的完整說明。

### Q-03 三項功能的規則門檻值與所依據的 protocol 條文

| | |
|---|---|
| **問誰** | 護理部、透析室主治醫師 |
| **急迫度** | B |
| **卡住** | 迭代 7 的啟用（FR-R02）。規則引擎本身不受阻 |
| **狀態** | 待提出 |

**背景**

規則引擎的形態是「某個數值或次數超過門檻就標註」。門檻值就是臨床判斷本身，**開發端訂它等於在做醫療決策**，因此必須由臨床端書面提供，且系統要記錄依據出處。

**不確認的後果**

規則寫不出來。就算硬寫，那個門檻是開發端猜的，一旦出事無法辯護。

**具體要問的**

| 功能 | 要問到的具體數字 |
|---|---|
| FR-P03 風險分層 | 透析間期體重增幅超過多少（公斤或乾體重百分比）算需要留意？透析前血壓低於多少要標註？要看幾次歷史紀錄？ |
| FR-P05 療程中預警 | 同一病人在過去幾次療程的同一時段回報過同一症狀，才值得提前提醒？「同一時段」的容許範圍是幾分鐘？ |
| FR-N06 劑量調整參考 | 現行的 Hb／EPO 調整 protocol 是哪一份文件？能否提供正本？調整級距與禁忌條件為何？ |
| 三項共通 | 這些門檻的依據是院內共識、學會指引，還是文獻？請提供可引用的出處 |
| 三項共通 | 誰有權修改門檻值？改了之後要不要重新走一次確認？ |

**額外要問的兩題（關於誤報）**

1. 這三項功能誤報（沒事卻提醒）與漏報（有事卻沒提醒）之間，臨床上更能接受哪一種？門檻要往寬還是往嚴設？
2. 提醒的呈現位置與頻率有沒有上限？例如一個班次最多幾則，避免變成雜訊被無視。

**現況／暫代做法**

`rule_versions` 資料表設有「書面依據出處」欄位，**未填該欄位的規則版本無法標為生效**。無依據時規則只能在合成資料模式下執行。

### Q-04 護理師個人層級績效資料是否需經員工代表同意

| | |
|---|---|
| **問誰** | 護理部、人資 |
| **急迫度** | B |
| **卡住** | 迭代 8 的 L3 啟用（FR-M11） |
| **狀態** | 待提出 |

**背景**

新增任務一之(3) 要建立護理師獎勵制度。系統會用既有稽核軌跡算出「誰在承擔比較重的班」這類指標。**同一批資料，用來改善流程是資源，用來考核個人是勞動條件的實質變更。**

**不確認的後果**

L3（個人層級）功能無法啟用。單位聚合（L1）與班次層級（L2）不受影響，仍可用於排班與成效展示。

**具體要問的**

1. 把護理師的回應時間、記錄完成率等指標用於個人獎勵，依醫院規定要走什麼流程？是否需經員工代表或工會同意？
2. 計分規則要不要先公告？公告的管道與前置時間？
3. 個人可以查閱自己的原始計分事件並提出更正，這樣的申訴機制是否足夠？醫院有既有的申訴流程要接上嗎？

5. 開發端已明訂四條禁區——不以病人臨床結果計分、不做公開個人排名、不以回應速度自動派工、不建立護理師與病人臨床結果的關聯評分。護理部還想加哪一條？
6. 獎勵的形式是什麼（獎金、排班優先權、公開表揚）？這會影響指標該怎麼設計。

**現況／暫代做法**

`PERF_INDIVIDUAL_L3` 開關預設關閉。L3／L4 查詢逐次寫入稽核軌跡（誰查了誰、區間、宣告用途）。資料表刻意不設「總分」與「排名」欄位。

### Q-05 資料留存期限

| | |
|---|---|
| **問誰** | 法務、資訊室 |
| **急迫度** | B |
| **卡住** | 刪除與封存機制（《[資料庫使用規範](database-policy.md)》8.2） |
| **狀態** | 待提出 |

**背景**

系統會累積稽核軌跡、病人自報紀錄、AI 呼叫紀錄、績效彙整結果。**無限期堆積本身就是風險**：資料越久，外洩時的損害越大，而多數舊資料早已沒有使用價值。

**不確認的後果**

只能一直堆。且日後真要清理時，會面臨「這些能不能刪」的爭議，而那時資料量已經很大。

**具體要問的**

1. 依《醫療法》的病歷留存規定，本系統的病人自報症狀與求助紀錄算不算病歷的一部分？要留幾年？
2. 稽核軌跡要留多久？醫院既有系統的慣例是多少？
3. AI 呼叫紀錄（提示與輸出）開發端建議留 12 個月，之後只留統計列。可以嗎？
4. 護理師績效彙整結果依人資規定要留多久？
5. 到期後是刪除、還是轉為離線封存？封存放在哪裡（必須仍在院內）？
6. 病人如果要求刪除自己的資料，醫院的處理方式是什麼？本系統要提供什麼介面配合？

**現況／暫代做法**

《資料庫使用規範》8.2 已列建議期限，但明確標示為建議值。**期限未定案前，系統一律只做「標記」不做實際刪除。**

### Q-06 去識別化資料可用於院內 AI 推論的同意範圍

| | |
|---|---|
| **問誰** | 法務、資訊室 |
| **急迫度** | B |
| **卡住** | 所有 AI 功能對真實資料啟用 |
| **狀態** | 待提出 |

**背景**

0909 版的假設是「醫院已同意去識別化資料可用於 AI 模型訓練與推論」。0910 的前提變更後，本專案**只做推論、不做訓練**，且模型跑在院內伺服器。範圍縮小了，但原本的同意究竟涵蓋什麼，需要確認。

**不確認的後果**

AI 功能只能對合成資料執行。所有生成類功能（衛教內容、記錄草擬、SOP 查詢）都無法對真實病人啟用。

**具體要問的**

1. 現有的同意（如果有）是書面的嗎？涵蓋範圍是訓練、推論，還是兩者？
2. 病人的知情同意書裡有沒有提到資料會用於資訊系統或 AI 輔助？需不需要補簽或補公告？
3. 「去識別化」的判定標準由誰認定？開發端的做法是送進模型前移除姓名、病歷號等直接識別欄位，這樣夠嗎？
4. 過渡期會用院外的實驗室 API。開發端已決定過渡期**一律只送合成資料**，這個限制是否足夠？或者院方連合成資料都不希望送出去？
5. AI 生成的衛教內容要給病人看。這些內容需不需要臨床審閱後才能顯示，還是可以直接呈現？
6. 病人可否拒絕 AI 輔助？若可以，拒絕後哪些功能要退回人工版本？

**現況／暫代做法**

`AI_FEATURES` 與 `REAL_PATIENT_DATA_TO_AI` 兩個開關預設關閉。後者只在 provider 為地端推論時才允許開啟。`LabApiProvider` 帶程式強制的合成資料檢查，帶真實病人資料標記的請求會被擋下。

第 5 題的暫代做法（迭代 4）：AI 產生的衛教內容一律「先審後給」——護理師核可前病人端看不到；AI 總開關關閉時，已核可的 AI 內容也一併從病人端消失。答案回來後再調整。

## 4. C 級：阻塞實作決策或硬體選型

### Q-07 院內 AI 伺服器的資源額度與推論服務歸屬

| | |
|---|---|
| **問誰** | 資訊室 |
| **急迫度** | C |
| **卡住** | 迭代 4 的效能目標；哪些 AI 功能可即時、哪些要走背景佇列 |
| **狀態** | **部分已回覆（0912）**，**0919 範圍縮小**。硬體規格已確定；那台機器不再是本系統的應用主機，剩下要問的只有端點本身 |

**背景**

0912 確認正式部署環境為**院內一台 NVIDIA DGX Spark**，原本問的前兩件事因此有了答案：

| 原問題 | 答案 |
|---|---|
| 128GB 是系統記憶體還是顯示記憶體？ | **都是。** 128GB LPDDR5x 為處理器與 GPU 共用的統一記憶體 |
| 有沒有 GPU？ | 有。GB10 Grace Blackwell 內含 Blackwell GPU |

完整硬體規格與據此訂出的部署決策，見《[部署規範](deployment-spec.md)》第 2 章。

**這個答案改變了什麼**：載入量接近原評估的情境 C（70B 級可載入），但記憶體頻寬約 273 GB/s，遠低於資料中心級顯示卡——**載得下大模型，但吐字速度不會快**。加上這台機器同時跑其他專案，可用記憶體還要再打折。

**0919 範圍縮小**：本系統的應用主機改為院內另一台專用的 Windows 工作站，**DGX Spark 與本系統的關係只剩一條 HTTP 呼叫**。原本混在這一題裡的「共用主機上本專案能不能跑容器、佔多少記憶體、跟誰搶連接埠」整組消失，移到 Q-27（那是 Windows 主機的問題）。**這一題現在只問端點本身**：位址、認證、可用模型、額度、誰維運。

這個變化也讓這一題不再擋任何東西：AI 功能在第一次部署時預設關閉（DEP-29），端點沒到齊，主線功能完全不受影響（DEP-24）。

**剩下不確認的後果**

不知道共用狀況下實際拿得到多少記憶體，就無法決定 SOP 查詢這類功能能不能做成即時互動。也不知道推論服務該由誰啟動與維運——這件事若沒有歸屬，上線時會卡在「大家都以為對方會處理」。

**具體要問的**

1. 這台機器上還有哪些專案？共用狀況下本系統可用的記憶體額度是多少？有沒有排擠時的優先順序？
2. **地端推論服務由誰提供與維運？** 是資訊室統一起一個共用端點，還是各專案自理？本專案的設計是**不自行載入模型、只呼叫端點**（DEP-16）。
3. 端點位址、認證方式、可用模型清單為何？繁體中文能力實測過嗎？
4. 這台機器什麼時候可以給開發端測試？可以先給一個小規模的試用時段嗎？
5. 若評估後發現額度不夠，有沒有追加機器的可行性與時程？

**開發端可以先提供的資訊**（有助於資訊室評估）

15 床、三班、每位病人每次療程估 5～10 次 AI 呼叫，**尖峰同時請求數不會超過個位數**，換算下來每秒請求數遠低於 1。因此本系統的瓶頸是單次回應延遲，不是吞吐量，**不需要昂貴的高併發推論架構**，也不需要獨佔整台機器。

**現況／暫代做法**

所有模型呼叫走 `LlmProviderPort`，預設 `MockLlmProvider`。額度確認後只需改設定指向端點，不動業務邏輯。

**形態確定之後，剩下的問題換了一批**（見下方「具體要問的」第 3′～5′ 題）：欄位定義、認證方式、抓取頻率、失敗時怎麼重試而不重複寫入。

**不確認的後果**

輪播只能做第一、二層。這不影響功能上線，但少掉對病人最有價值的那一層。

**具體要問的**

| # | 問句 | 給誰 |
|---|---|---|
| 1 | 這些數值目前存在哪個系統裡？HIS、透析專用系統，還是護理站自己的 Excel？ | 資訊室 |
| 2 | 能不能開唯讀 API？如果不行，能不能定期匯出檔案？ | 資訊室 |
| 3′ | **（0919 取代第 3 題）** API 的位址、認證方式、回傳格式、每個欄位的定義與單位為何？ | 資訊室 |
| 4′ | **（0919 取代第 4 題）** API 回傳的病人識別是病歷號嗎？跟本系統的病人主檔怎麼對得起來？ | 資訊室 |
| 5′ | **（0919 新增）** 多久抓一次？可以主動查詢還是只有定時推送？抓取失敗時要怎麼重試？有沒有速率限制？ | 資訊室 |
| 5 | 哪些數值適合直接給病人看？哪些不適合（例如某些抽血項會引起不必要的焦慮）？ | 護理部 |
| 6 | 數值要不要附上「正常範圍」或白話解釋？由誰提供文案？ | 護理部 |
| 7 | 資料多舊就不該顯示？例如三週前的體重還要不要播？ | 護理部 |

**現況／暫代做法**

`ClinicalDataSourcePort` 介面層已定，三個實作（手動輸入、檔案匯入、院方 API）共用同一組內部資料表。無論最後走哪一條，輪播與病人端程式碼都不需要改動。

**0912 更新（迭代 6 完成）**：`FileImportAdapter` 已完成，Excel 與 CSV 都收得進來，而且**欄位名稱不寫死在程式裡**——對應設定在「臨床數值 → 匯入欄位對應」，一列一個欄位。上面第 3、4 題的答覆回來時，改的是那幾列設定；第 5～7 題（哪些數值適合給病人看、要不要附正常範圍、資料多舊就不該播）仍待護理部回覆，目前第三層播的是 SRS FR-P11 所列的五種數值，每一筆都標示資料時間。

**如果最後走 Excel，要一併提醒院方的風險**

欄位名稱與順序會被人手動改動、日期格式不一致、同一份檔案被重複上傳。開發端的對策是欄位對應可設定、格式驗證、重複偵測，以及**任何一筆解析失敗就擋下整批**——臨床數值只對一半，比完全沒有更危險。

### Q-27 正式主機的容器執行方式與映像檔傳入管道

> **0919 整組改寫。** 主機由共用的 DGX Spark 改為院內一台專用的 Windows 工作站，部署形態由容器改為離線安裝包（DEP-07）。原本問的六題有四題是容器與 Linux 特有的，已不適用；本節保留原標題以維持既有連結，內容換成 Windows 版本。**傳入管道那一題另立 Q-29**，因為它牽涉的是資安流程而不是主機設定。

| | |
|---|---|
| **問誰** | 資訊室 |
| **急迫度** | C |
| **卡住** | 正式部署當天能不能把服務跑起來 |
| **狀態** | 待提出（0912 新增，0919 改寫） |

**背景**

正式環境為院內一台專用的 Windows 工作站（Intel i7-14700、64GB、2TB SSD ×2），本專案以離線安裝包部署、以 Windows 服務常駐（DEP-07）。但「這台機器上我們能做什麼」還是空白：有沒有安裝服務的權限、服務用哪個帳號跑、重開機後誰確認服務有起來。**這三件任何一件不成立，交付當天就會卡在最後一步。**

**不確認的後果**

安裝包送進去了，但註冊不了服務、或註冊了卻沒有權限讀寫資料目錄。這種問題發現得晚會直接延後上線，而且都不是改程式能解決的。

**具體要問的**

1. 本專案在那台機器上有沒有**系統管理員權限**？安裝 Windows 服務需要它
2. 服務要用哪一個帳號執行（DEP-12）？是本機帳號還是網域帳號？密碼由誰保管、會不會定期強制更換（會的話服務要跟著改）？
3. 資料庫與備份目錄放在哪一顆 SSD 的哪個路徑？該目錄的權限怎麼設？
4. **那台機器的防毒軟體是哪一套？誰能加排除清單？**（DEP-21 第 1 項，這一題最容易被忽略而最會出事）
5. 本專案可以使用哪幾個連接埠？主機的防火牆規則要怎麼開，才能讓護理站電腦與透析區平板連得進來？
6. 服務要不要設成開機自動啟動？重開機後由誰負責確認服務有起來？
7. 那台機器的系統更新政策為何？重新啟動時段會不會落在透析班次中？
8. 備份要送到院內哪一台機器（DEP-06）？那台的存取方式與保管責任歸屬為何？

**現況／暫代做法**

安裝包的路徑、連接埠、執行帳號全部由設定提供，不寫死。答覆回來時改的是 `.env` 與服務註冊腳本的幾個參數，不是安裝包本身。

|---|---|
| **問誰** | 資訊室 |

| **卡住** | 第一次部署能不能把安裝包送進那台主機 |

6. 可以接受的部署與更新時段是什麼時候？（要避開透析班次，見 DEP-32）

**現況／暫代做法**

### Q-30 護理師的行動裝置

| | |
|---|---|
| **問誰** | 護理長（需求）、資訊室（採購與納管） |
| **急迫度** | D |
| **卡住** | 需手持裝置的功能什麼時候能開 |
| **狀態** | 待提出（0919 新增） |

**背景**

目前護理端只會在護理站的一兩台電腦上開啟，護理師手上沒有平板或手機。這讓一整類功能在物理上無法成立——最具體的是「我到床邊了」這顆按鈕（FR-N10）：它要在床邊按才有意義，而護理師走到床邊時手上沒有東西可以按。

**0919 的處理方式**：這類功能**先關閉**，可在系統設定開啟（DEP-29、FR-S11）。關閉期間「到達床邊時間」留空，不以確認時間頂替，並在成效指標上明確標示「本期間無到達時間資料」。

**不確認的後果**

「確認通報」與「到達床邊」分開記錄是刻意的設計（SRS 5.2），它量的是資料品質。沒有行動裝置，這個檢查點就一直是空的；而成效基準裡最有說服力的那一條「病人按鈴到護理師到床邊」正好需要它。

**具體要問的**

1. 護理師在班上有沒有可能配發行動裝置？共用幾台就夠（一班一台？一人一台？）
2. 如果短期內沒有，有沒有替代做法——例如床邊固定一台小螢幕、或用病人端平板上的一個護理師專用畫面？
3. 感染管制上，護理師隨身帶著裝置在治療區移動，消毒規範怎麼訂？（與 Q-22 同一場談）
4. 若之後配發，是否納入與病人端平板相同的管控方式？

**現況／暫代做法**

功能已實作、資料欄位已存在，只是關著。配發之後在系統設定開啟即可，**不必改程式、不必重新部署、資料結構不必改**。

## 5. D 級：可先用暫代值

這十四項的共同特徵是：**開發端先用一組合理的暫定值往下做，答案回來後替換即可，不影響架構。** 因此它們一併問，但不擋任何進度。

新增任務四要蒐集每次求助的處理方式與結果。目前 `help_requests` 只有一個自由文字結案備註，要升級成結構化欄位才能統計。

列出來的病人可能太多（被當成雜訊而無視）或太少（該注意的沒被看見）。系統不會自動轉介，所以不會造成任何臨床動作，但會影響護理師對這項功能的信任。

**具體要問的**

1. 5 題題目（心情、睡眠、有人可以幫忙或聊天、對照護的滿意度、對環境的滿意度）合適嗎？院內有沒有既有的量表應該改用？
2. 多久填一次？目前是每次療程最多一份、病人自願填。
3. 「低 1.0 分以上」「近 3 次比先前 6 次」這組門檻合適嗎？
4. 列出來之後，轉介社工的流程是什麼？要不要在系統裡記錄「已評估、是否轉介」？
5. 病人寫的文字意見要不要有人定期看？誰看？

**現況／暫代做法**

規則放在共用常數並標版本；比對結果只以事實陳述呈現給護理師（例如「近 3 次平均 2.1 分，先前平均 4.0 分，低了 1.9 分」），不對心理狀態下結論，也不自動觸發任何轉介。病人端看不到比對結果。

### Q-25 事件記錄快速範本的事件類型與欄位

| | |
|---|---|
| **問誰** | 護理部 |
| **急迫度** | D |
| **卡住** | 迭代 4 的 FR-N04（已用暫定值實作） |
| **狀態** | 待提出 |

**背景**

FR-N04 要求「事件當下快速點選式記錄範本」。開發端先擬了 5 種事件：病人不適處置、管路或穿刺處滲血、機器警報處理、跌倒或滑倒、其他事件，每種有 1～3 個勾選欄位，只記錄「發生了什麼、做了什麼」，不含任何判讀。

**具體要問的**

1. 這 5 種事件是透析室最常需要記錄的嗎？漏了哪些？
2. 各欄位的選項（例如「處置」的調整姿勢、測量生命徵象、通知醫師、依醫囑處置、心理安撫、持續觀察）要怎麼增減？
3. 記錄格式要不要對得上院內既有的護理記錄或病人安全事件通報系統？（本階段不做雙向寫入）
4. 跌倒這類事件院內另有通報流程嗎？系統的記錄能不能當作通報的底稿？

**現況／暫代做法**

範本放在共用常數並標版本（`EVENT-TEMPLATES-v1`），記錄只存欄位與選項代號加上範本版本。確認後改常數並升版即可。

### Q-26 透析適足性的計算公式與輸入來源

| | |
|---|---|
| **問誰** | 透析室醫師（公式）、資訊室（輸入來源） |
| **急迫度** | D |
| **卡住** | 迭代 4 的 FR-N07（已用暫定值實作） |
| **狀態** | 待提出 |

**背景**

FR-N07 的 URR 與 Kt/V 計算，開發端先採用常見的 Daugirdas 第二代單池公式（spKt/V），輸入為透析前後 BUN、透析後體重、實際脫水量、透析時間。

**具體要問的**

1. 院內慣用的是哪一個公式（單池 spKt/V、平衡 eKt/V，或其他）？
2. 透析後抽血的時間點有沒有院內規定？會影響要不要做校正。
3. 這五個輸入值目前放在院方的哪個系統？能不能跟輪播第三層的數值一起由院方提供（Q-09）？
4. 院方已經有算好的 Kt/V 時，要以院方的為準，還是兩者並列？（目前並列、分開呈現）

**現況／暫代做法**

每一筆結果都記下公式版本（`DAUGIRDAS2-SPKTV-v1`），換公式時新結果用新版本，舊結果不改。畫面只呈現數值與趨勢，不標示目標值，也不做預測（預測屬迭代 7）。

### Q-28 輪播第二層的衛教與公告內容

| | |
|---|---|
| **問誰** | 護理部 |
| **急迫度** | D |
| **卡住** | 迭代 6 第二層的開關。第一、三層不受影響 |
| **狀態** | 待提出（0912 新增） |

**背景**

閒置輪播的第二層是「靜態衛教與中心公告」——中心自己要放的內容，不是系統既有資料，也不是院方給的數值。
管理介面已完成（護理端「輪播內容」頁可新增、排序、設定上下架時間），但**內容本身只有護理部寫得出來**。

**不確認的後果**

第二層開關開不起來（開啟條件就是「至少有一則在架上的內容」），輪播只播第一、三層。
這不影響上線，只是少了一個現成的衛教管道。

**具體要問的**

| # | 問句 |
|---|---|
| 1 | 中心現在有哪些貼在牆上或發給病人的衛教單張？可以直接改寫成輪播卡片嗎？ |
| 2 | 一張卡片只放得下一句話與一段說明，優先放哪幾則？ |
| 3 | 公告（例如消毒日、休診日）由誰負責上架與下架？需不需要排定期限？ |
| 4 | 需不需要多語言版本？若要，誰提供譯文？ |

**現況／暫代做法**

**沒有暫代內容，這是刻意的**——開發端自己編的衛教文字會直接被病人看到，那不是可以「先擺著之後再改」的東西。
開關的開啟條件因此直接判定有沒有在架上的內容：沒有內容就開不起來，不會出現空白的輪播。

## 7. 已結案

**0919 有四項一次結案，但結案方式與一般情形不同**，欄位上要看得出來：它們是**院方授權採用**，不是**逐條審閱同意**。授權的意思是「先用，有問題再改」；審閱的意思是「看過了，就是這樣」。把前者當成後者，日後被問到「這些題目誰審的」就答不出來。
