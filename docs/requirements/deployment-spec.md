## 0. 本文件與其他文件的關係

本文件把「這套系統最後要跑在哪裡、用什麼形態跑、怎麼交到院方手上」收斂成可執行的決策。

- 《[軟體需求規格書](srs.md)》：功能需求來源
- 《[資料庫使用規範](database-policy.md)》：資料治理強制規則。**資料庫檔案、備份、加密與版本更新的規定以該文件為準**，本文件只補「在這台主機上怎麼落實」
- 《[實作規格書](implementation-spec.md)》：範圍界定與技術棧。**功能範圍與技術選型衝突時仍以該文件為準**
- 《[FDE 數位化評估報告](fde-assessment.md)》：選型理由與背景脈絡
- 《[平板管控：免 MDM 的全院內方案](../notes/mdm-offline-plan.md)》：病人端平板的管控路線，本文件第 8 章的佈建步驟以它為準
- 《[尚待確認事項清冊](open-questions.md)》：本文件的待確認事項一律指回 Q 編號，不在此另立清單

**本文件擁有最終決定權的範圍只有三件事**：部署形態、環境界線（哪個環境可以放什麼資料）、交付方式（程式怎麼進到院內主機）。這三件事以外的爭議一律回到上列文件。

本文件的強制規則以 `DEP-xx` 編號，其他文件引用時寫編號，不複製內容。**作廢的編號保留原位並標明作廢，不重複使用。**

### 0.1 v2.0 → v3.0 異動摘要（0926）

**交付方式整條換掉。** 0922 第一次進院與之後的確認帶回三件事，v2.0 的「隨身碟帶入離線安裝包」因此不再成立：

| | v2.0（0919） | v3.0（0926） |
|---|---|---|
| 院方要求 | 未表態 | **以容器部署，程式以 `git clone` 取得** |
| 院內主機對外連線 | 假設為零 | **院內網路可以連出去，外面連不進來** |
| 外接儲存媒體 | 路線 B 的必經管道 | **不允許使用隨身碟** |
| 主機帳號 | 假設可建專用低權限服務帳號 | **Administrator 不允許設定密碼；能登入這台主機的使用者一律視為可信任** |
| 部署形態 | 離線安裝包＋Windows 排程工作常駐，容器為備案 | **Docker 容器（`docker compose`），安裝包路線全面撤除** |
| 交付物 | 壓縮安裝包＋雜湊值 | **git tag**：院內主機 `git clone` 後就地建置映像檔 |
| AI | 實驗室 API 未取得 | **實驗室 GPU 伺服器使用規範已取得**，經本系統自己的 AI 閘道呼叫（第 5 章） |
| 病人端外殼 App | 放在本 repo 的 `apps/kiosk-shell/` | **獨立為另一個私人 repo**，APK 在院內主機上以容器建置（第 7 章） |
| 開發端演練 | 一台乾淨的 Windows 機器 | **開發機（Docker）＋開發手機（外殼 App）實測整套部署**（第 9 章） |

**安裝包路線不是降為備案，是撤除。** 院內不准用隨身碟，安裝包就沒有進院的管道；留著它只會讓下一個人以為還有兩條路可選。要撤除的東西列在 3.5。

**DEP 條款異動**：DEP-02（保留，範圍縮到日常開發）、DEP-04（改寫）、DEP-07（改寫）、DEP-08～DEP-11（改寫）、DEP-12（**作廢**）、DEP-13～DEP-17（改寫）、DEP-18～DEP-19（改寫）、DEP-21～DEP-22（改寫）、DEP-23（由備案條款升為主規則）、DEP-25～DEP-28（**作廢**）、DEP-30（改寫）、DEP-35（改寫）、DEP-37（改寫）。新增 DEP-38～DEP-45。

### 0.2 v1.0 → v2.0 異動摘要（0919，歷史）

正式主機由院內 ARM64 的 DGX Spark 改為院內一台 x86-64 的 Windows 工作站（仍與其他專案共用），DGX Spark 只剩「地端推論端點」一個身分；平板管控改走免 MDM；臨床數值確定走院方 API。v2.0 當時因「容器在 Windows 上會撞到資料庫規範」改走安裝包；v3.0 改以 DEP-23 解決這個顧慮（資料庫只放具名資料卷），而不是以換形態迴避。

## 1. 三個環境

| | 開發環境 | 過渡環境（實驗室） | 正式環境 |
|---|---|---|---|
| 機器 | FDE 的 Windows 開發機 | 實驗室 GPU 伺服器上的**個人容器**（院外） | **院內一台共用 Windows 工作站** |
| 作業系統 | Windows | Linux（容器內） | Windows ＋ Docker Desktop（WSL2） |
| 執行形態 | 日常開發 `npm run dev`；**部署實測用 `docker compose`**（第 9 章） | 只跑 AI 閘道，不跑本系統其他部分 | **`docker compose`，程式由 `git clone` 取得並就地建置** |
| 資料庫 | 日常開發：本機 SQLite 檔案；部署實測：具名資料卷 | **不放資料庫** | 具名資料卷裡的 SQLite 檔案 |
| 可用資料 | 合成資料 | **僅合成資料** | 真實病人資料 |
| AI 供應者 | `mock`，或經 SSH 通道接實驗室的 AI 閘道（`lab`） | AI 閘道 → 實驗室 Ollama | `onprem`：院內 AI 閘道 → 正式 GPU API |
| 對外連線 | 開發工具、SSH 至實驗室 | 有 | **部署與更新時可以連出**（git、映像檔、套件）；**執行期不得把任何資料送出院外** |

**DEP-01｜三個環境的資料界線不得跨越。**（保留）過渡環境在院外，任何真實病人資料不得進入；此限制由 AI 呼叫前的合成資料檢查以程式強制（FR-S06），並由 DEP-40 在正式環境直接擋掉 `lab` 設定，不靠人的自律。

**DEP-02｜日常開發不容器化。**（保留，範圍縮小）`npm run dev` 的熱重載與除錯效率是容器給不了的。**但部署實測一律用容器**（DEP-22），而且要跟院內一模一樣的指令——開發機上測過而院內跑不起來，最常見的原因就是兩邊跑的不是同一種東西。

## 2. 正式環境：院內一台共用 Windows 工作站

### 2.1 已確認的事實

| 項次 | 內容 |
|---|---|
| 處理器／記憶體／儲存 | Intel Core i7-14700、64GB、2TB SSD ×2（0922 現場看到的磁碟規格與此對不太上，是否為同一台待確認，Q-27） |
| 架構 | x86-64 |
| 作業系統 | Windows，**已安裝 Docker**（0922 現場確認） |
| GPU | 不需要。本系統不做任何本機推論（DEP-16） |
| 網路 | **院內網路可以連出去，外面連不進來**（0926 確認） |
| 外接儲存媒體 | **不允許**（0926 確認） |
| 帳號 | **Administrator 不允許設定密碼**；能登入此主機的使用者一律視為可信任（0926 確認） |
| 共用狀況 | 與其他專案共用，院方確保資源足夠；0922 現場看到主機上已有其他專案的容器與被佔用的連接埠 |

**「連得出去、連不進來」剛好是本系統需要的形狀。** 部署與更新要連出去（GitHub、映像檔來源、套件來源）；本系統沒有任何一個功能需要被院外連進來。**但連得出去不等於資料可以出去**——那一條（FR-S04、FR-S07）是在程式裡擋的，不是靠網路擋的。v3.0 起它只剩程式這一道防線，見 DEP-14。

### 2.2 共用主機上的隔離

**DEP-04｜（0926 改寫）本系統對主機的要求只有兩樣：Git 與 Docker（含 Compose）。** 其餘一律在映像檔裡。不得要求院方安裝 Node.js、Python、Android SDK 或任何執行期相依，也不得要求調整全域設定。主機上既有的 Docker 若版本不足要先問（Q-27），不得自行升級——那一套 Docker 也在跑別的專案。

**DEP-37｜（0926 改寫）共用主機上的隔離在容器層級做到。** 五件事一起做：

| # | 要做到 | 不做會怎樣 |
|---|---|---|
| 1 | **Compose 專案名稱固定為 `hd-tablet-care`**，容器、網路、資料卷全部帶這個前綴 | 與別的專案的同名資源互相覆蓋；`docker compose down` 關到別人的東西 |
| 2 | **連接埠向資訊室登記後固定**，值寫在主機的 `.env`，不寫死在 compose 檔 | 0922 現場就撞到：想用的埠已經有人在用 |
| 3 | **只繫結掛載兩個主機目錄：備份輸出目錄與設定目錄**，兩者都在本系統自己的路徑底下 | 0922 的 `-v /c:/app` 把整顆 C 槽掛進容器——容器裡任何一個程式都讀寫得到主機上別的專案與系統檔案（部署手冊第十冊 F-02） |
| 4 | **不使用 `--privileged`、不掛 Docker socket、不用 host 網路模式** | 等於把主機整台交給容器 |
| 5 | **磁碟空間下限**（`DB_DISK_MIN_FREE_MB`）照舊，量的是 Docker 資料所在的那顆磁碟 | 具名資料卷放在 WSL2 的虛擬磁碟裡，別的專案的映像檔寫滿同一顆磁碟時，本系統寫入直接失敗 |

**DEP-38｜（0926 新增）信任邊界是「能登入這台主機的人」。** 院方決定 Administrator 不設密碼、能登入者一律可信任。本系統**接受這個前提，不在作業系統層級另設防線**：

| 原本的要求 | v3.0 |
|---|---|
| 服務以專用低權限帳號執行（DEP-12） | **作廢**。沒有密碼就建不了「以指定帳號執行」的排程工作，而容器路線本來也不需要 |
| 資料庫與備份目錄的權限只給服務帳號（原 DEP-37 第 4 項） | **作廢**。資料庫在具名資料卷裡，備份目錄的權限不另設 |
| 容器內以非 root 執行 | **保留**。這一條防的不是登入者，是容器裡的程式遭入侵時能動到多少東西 |

**這個前提要寫進交接文件**：日後院方若改變帳號政策（例如開始有外包人員能登入），這張表要重新評估。本系統自己的護理端帳號、權限矩陣與稽核軌跡（SRS 第 4 章）不受這一條影響，照舊。

### 2.3 仍然是一台桌上型 Windows 機器

**DEP-06｜備份目的地必須是院內另一台機器。**（保留）容器把備份寫到主機的備份目錄是第一落點，但**不得是唯一落點**。

**DEP-21｜（0926 改寫）Windows 與 Docker Desktop 特有的事，部署前逐項確認：**

| # | 要做的事 | 不做會怎樣 |
|---|---|---|
| 1 | **Docker Desktop 的資料目錄（WSL2 虛擬磁碟）加入防毒排除清單** | 即時掃描一個持續被寫入的虛擬磁碟，會拖慢整個容器環境，最壞的情形是資料庫寫入間歇失敗 |
| 2 | 備份目錄與設定目錄不在雲端同步資料夾、不是網路磁碟機代號 | 同步資料夾等同把備份送出院外 |
| 3 | 關閉自動休眠；系統更新的重新啟動時段不落在透析班次 | 同 v2.0 |
| 4 | **開機後 Docker Desktop 會自己起來** | Docker Desktop 是隨使用者登入啟動的程式，不是系統服務。沒有人登入，容器就不會起來，`restart: unless-stopped` 也救不了（Q-27） |

**主機是共用的，這幾件事更容易被推翻。** 部署紀錄上要寫明是誰設的，改動前要知會誰。

## 3. 部署形態：容器＋git clone

**DEP-07｜（0926 改寫）正式環境以 `docker compose` 部署，程式碼以 `git clone` 取得，映像檔在院內主機上就地建置。離線安裝包路線撤除。**

### 3.1 為什麼換回容器

v2.0 選安裝包的兩個理由，0926 都不存在了：

| v2.0 的理由 | 0926 |
|---|---|
| 主機沒有對外連線，只能帶一個自帶執行期的包進去 | **不成立。** 院內網路可以連出去，`git clone` 與建置映像檔都能在主機上直接做 |
| 容器的 SQLite 檔案只有兩個落點，兩個都有問題 | **以 DEP-23 解決**：資料庫只放具名資料卷；「院方看不到、備份軟體掃不到」那一半，由備份寫到主機目錄解決（3.3） |

**而安裝包路線反過來失去了進院的唯一管道**——隨身碟不准用。加上院方明確要求容器，這一題沒有要取捨的地方。

### 3.2 組成

```
git clone 下來的原始碼（主機上，本系統自己的目錄）
└── docker compose（專案名稱 hd-tablet-care）
    ├── api            後端，唯一開啟資料庫做寫入的行程（DEP-10）
    ├── nurse-web      護理端 PWA 靜態資源
    ├── patient-web    病人端 PWA 靜態資源（HTTPS）、`/api/` 轉送給 api、外殼 APK 的院內下載頁（DEP-45）
    ├── ai-gateway     AI 閘道（第 5 章）。AI 功能關閉時不必啟動
    └── shell-builder  一次性工作：建置外殼 APK（第 7 章），平時不跑

具名資料卷（WSL2 內，compose down -v 也刪不掉）   主機目錄（繫結掛載，只有這兩個）
├── hd-tablet-care-data   SQLite 與 -wal、-shm      ├── 備份輸出目錄
└── hd-tablet-care-keys   CA、伺服器憑證、APK 簽章金鑰、下載頁   └── 設定目錄（.env、AI 閘道的 config.yaml）
```

**DEP-08｜（0926 改寫）資料庫只放具名資料卷；備份與設定只放本系統自己的主機目錄；兩者都不在 git clone 的目錄裡。** 原本的理由不變：某一次「把舊目錄整個刪掉重新 clone」會把放在裡面的東西一起刪掉。

**DEP-09｜`-wal` 與 `-shm` 必須與主檔在同一個掛載點。**（保留）掛的是目錄，不是檔案。

**DEP-10｜後端仍然是唯一開啟資料庫檔案做寫入的行程。**（保留）compose 裡 `api` 只能有一個執行個體；資料修補與遷移用 `docker compose run --rm --no-deps api …`，在 `api` 停止時執行。

**DEP-11｜（0926 改寫）建置只在映像檔裡做。** 主機上不得直接執行 `npm install`、`npm run build` 或任何建置步驟——那會要求主機裝 Node.js（違反 DEP-04），而且會在主機上留下一份與映像檔不一致的 `node_modules`。

**DEP-13｜（0926 改寫）映像檔與 git repo 都不得包含 `.env`、資料庫檔案、備份檔、金鑰或任何真實資料。** 設定一律由主機的設定目錄提供；compose **不使用 `env_file`**，容器要什麼變數就逐一列出（開發機的 `.env` 夾帶與系統無關的權杖）。

**DEP-14｜（0926 改寫）執行期不得連往院外。** v2.0 靠「主機沒有對外連線」兜底，v3.0 這一層沒了，只剩程式本身：

- `npm run check:egress` 的掃描範圍改為**映像檔會帶進去的全部內容**，外加 compose 檔與 AI 閘道
- 例外只有一條，而且只在開發環境成立：AI 閘道經 SSH 通道連實驗室（DEP-40）
- 建置階段連出去（git、映像檔、套件、Prisma 引擎、Android 建置相依）是允許的，**但建置階段不得掛載任何資料卷**——建置時碰不到資料，資料就出不去

### 3.3 資料庫落點

**DEP-23｜（0926 由備案條款升為主規則）資料庫檔案不得落在 Windows 目錄的繫結掛載上，只能放在具名資料卷裡。** 繫結掛載在 WSL2 底下是跨檔案系統的轉譯層，SQLite 的檔案鎖不可靠（《資料庫使用規範》7.2）。**0922 院方那句「似乎允許鏡像到容器外」若指的是資料庫放 Windows 目錄，答案仍然是不行**；能放到容器外的是備份，不是資料庫本身。

具名資料卷的代價是「院方在檔案總管裡看不到資料庫」，由兩件事補上：

1. **備份寫到主機的備份目錄**：每日排程備份與更新前備份都落在那裡，院方看得到、備份軟體掃得到，再由它送往院內另一台機器（DEP-06）
2. **資料卷標為 `external`**：compose 不建立它，`docker compose down -v` 也刪不掉它。刪不刪整個透析中心的照護紀錄，不該取決於有沒有人多打了一個 `-v`

### 3.4 映像檔建置

**DEP-30｜（0926 改寫）Prisma 引擎在映像檔建置時取得，執行期不得下載任何東西。** 版本仍鎖成確定版本（引擎與 CLI 要一致）。v2.0 那套「安裝包自帶引擎、以環境變數指向」的機制隨安裝包一起撤除；映像檔裡的 `prisma generate` 在與執行階段相同的基底映像上執行即可。

**DEP-31｜正式環境一律使用「套用既有遷移」的指令，不得使用開發用的遷移指令。**（保留）

**DEP-39｜（0926 新增）兩個 PWA 的後端位址在建置時寫進產物，因此映像檔一律在院內主機上、以院內的位址建置。** 開發機建好的映像檔不得搬進院內使用——那裡面寫死的是開發機的位址。這也是「就地建置」而不是「推映像檔過去」的另一個理由。

### 3.5 撤除安裝包路線

**0926 起以下全部移除，不留作備案**（《實作規格書》4.9 迭代 11 的工作項）：

| 類別 | 項次 |
|---|---|
| 腳本 | 安裝包建置、安裝包驗收、服務註冊與啟停（排程工作）腳本、安裝包範本目錄 |
| npm 指令 | `package:build`、`package:verify` |

## 5. AI：推論端點與 AI 閘道

**DEP-16｜（0926 改寫）本系統不載入模型、不需要 GPU，但包含一個 AI 閘道。** 推論端點（實驗室 Ollama 或正式 GPU API）永遠在別台機器上；本系統自己跑的是一個不含模型的轉接服務。

```
後端 ai 模組 ──HTTP（chat completions 相容格式）──▶ AI 閘道 ──LangChain──▶ 推論端點
（LlmProviderPort，不變）                          （config.yaml 決定連誰）  實驗室 Ollama／正式 GPU API
```

**DEP-17｜（0926 改寫）模型、端點與參數一律由設定提供。** 後端的 `LLM_ENDPOINT` 永遠指向 AI 閘道；閘道要連哪個推論端點、用哪個模型、溫度與上下文長度，全部寫在閘道的 `config.yaml`。

### 5.1 為什麼要多一個閘道

實驗室規範要求**以 LangChain 呼叫模型，並建議以 config 檔管理模型與參數**。本系統後端是 Node.js，規範的寫法是 Python。與其在後端另造一份不符規範的呼叫方式，不如把「怎麼呼叫模型」整個收進一個照規範寫的 Python 服務：

| 好處 | 說明 |
|---|---|
| **照規範做** | 閘道內部就是規範裡的 `config.yaml` ＋ `llm_factory` 寫法，`provider` 可選規範的兩種方法（`langchain-ollama` 或 OpenAI 相容介面） |
| **換成正式 GPU API 只改一個檔** | 同一個閘道映像檔，實驗室與院內各一份 `config.yaml`。後端、業務邏輯、資料庫一律不動 |
| **後端介面不變** | 後端對閘道說的是 chat completions 相容格式，`LlmProviderPort` 與 `HttpLlmProvider` 沿用 |
| **實驗結果可重現** | 規範的理由之一：比較模型時只要留存 config |

**DEP-41｜（0926 新增）後端不得直接連推論端點，一律經 AI 閘道。** 閘道以外的地方出現推論端點的位址、模型名稱或 LangChain 呼叫，都算違規。

### 5.2 過渡期：實驗室 GPU 伺服器

**DEP-42｜（0926 新增）使用實驗室資源一律遵守實驗室的使用規範與流程**，唯一的差異是**以 Terminal 的 `ssh` 連線取代 VS Code 的遠端視窗**：

| # | 規範 | 本專案的做法 |
|---|---|---|
| 1 | 以 SSH 連線到實驗室伺服器 | 開發機 Terminal 下 `ssh`；連線位址、連接埠、帳號與密碼**不寫進 repo 與文件**，只存在開發者本機 |
| 2 | 在指定路徑建立個人資料夾，**資料與程式碼只存自己的資料夾，不得動用別人的** | 閘道程式碼、`config.yaml` 與紀錄檔都在個人資料夾裡；**不修改共用帳號的任何設定檔**（含 SSH 金鑰設定） |
| 3 | 建立個人容器，**所有工作與套件安裝都在容器內** | 閘道跑在個人容器裡，LangChain 等套件只裝在容器裡；個人資料夾掛進容器 |
| 4 | 查看可用模型在**容器外**的 Terminal 操作；確認連線在**容器內**以 `curl` 測 | 照做。選用的模型名稱寫進 `config.yaml` |
| 5 | 以 LangChain 呼叫，建議以 config 檔管理設定 | 見 5.1 |
| 6 | **只能呼叫模型，不可管理模型**；需要新模型要聯絡學長姐 | 閘道不提供任何下載、刪除、載入模型的功能 |
| 7 | 第一次回應慢是模型正在載入；一直慢可能是別人在用大型模型 | 後端健康檢查逾時與生成逾時分開（沿用），AI 功能一律走背景佇列 |

**開發機怎麼連到實驗室容器裡的閘道**：閘道的連接埠只綁在實驗室伺服器的本機介面上，開發機以 SSH 本機轉送把它接到自己的 `127.0.0.1`，後端的 `LLM_ENDPOINT` 指向那個本機位址。**閘道不對實驗室網路開放**，別人的容器連不到它。

**DEP-40｜（0926 新增）正式環境設定下 `LLM_PROVIDER=lab` 拒絕啟動。** 實驗室在院外，院內網路又連得出去——只要有人把開發機的設定抄到院內主機，真實病人資料就會開始往院外送。這一條與 FR-S06 的合成資料檢查是兩道防線，缺一不可：合成資料檢查擋的是「送了什麼」，這一條擋的是「送往哪裡」。

### 5.3 正式：院內 GPU API

| 項次 | 狀況 |
|---|---|
| 推論端點 | 院內的正式 GPU API（DGX Spark 或院方另行指定，Q-07） |
| AI 閘道放哪裡 | **院內主機的 compose 裡**（`ai-gateway` 服務），與後端在同一個私有網路，不對外開埠 |
| 切換要改什麼 | 閘道的 `config.yaml`（`provider`、`base_url`、`model`、參數）與後端 `.env` 的 `LLM_PROVIDER=onprem`。**不改程式、不重建後端映像檔** |
| 端點不通時 | AI 功能顯示為暫時無法使用；**主線功能完全不受影響**（DEP-24） |

**DEP-24｜AI 必須可以整個關掉，而且關掉之後系統要能完整運作。**（保留）首波部署 AI 功能預設為關（DEP-29），`ai-gateway` 可以根本不啟動。

**正式 GPU API 若不是 Ollama**：規範的方法二（OpenAI 相容介面）涵蓋大多數推論伺服器，`config.yaml` 的 `provider` 改成相容介面那一種即可；若連相容介面都不是，改的是閘道的 `llm_factory`，仍然不動後端。

## 6. 交付與更新

**DEP-18｜（0926 改寫）交付物是 repo 上的一個 git tag 加一份設定範本。** 不是一份安裝包，也不是一份安裝手冊。

### 6.1 取得程式碼

**DEP-43｜（0926 新增）院內主機以唯讀的部署金鑰 clone 兩個私人 repo（本系統、外殼 App），金鑰在主機上產生，私鑰不離開主機。**

| 做法 | 理由 |
|---|---|
| 在主機上產生 SSH 金鑰對，**只把公鑰**登記為該 repo 的唯讀部署金鑰 | 私鑰不必經過任何人或任何媒介；0922 那種臨時建立、事後要記得刪的個人權杖不再需要 |
| 兩個 repo 各一把 | 部署金鑰一把只能對應一個 repo |
| 唯讀 | 院內主機不需要、也不該能推任何東西回去 |

**DEP-44｜（0926 新增）部署與更新一律 checkout 一個 tag，不部署分支的最新狀態。** 0922 的失敗原因之一（F-04）正是院方 clone 到的 `master` 不是開發端以為的那一版。tag 要在開發端第 9 章的實測通過後才打。

### 6.2 第一次部署

```
主機上：產生部署金鑰 → 登記公鑰 → git clone → checkout tag
      → 建立設定目錄與備份目錄 → 由範本填 .env
      → docker volume create（資料、金鑰兩個）
      → docker compose build → 套用遷移 → docker compose up -d
      → 建置外殼 APK（第 7 章）→ 平板佈建（第 8 章）
```

步驟、每一步的成功判準與出錯處置寫在部署手冊，本節不複製。

### 6.3 更新

**DEP-19｜（0926 改寫）每次更新都要能回到上一版，而且更新不得破壞既有資料。** 完整規則在《[資料庫使用規範](database-policy.md)》第 18 條：

| 順序 | 動作 | 不做會怎樣 |
|---|---|---|
| 1 | `git fetch`，確認新 tag 存在 | |
| 2 | 以新 tag 建置映像檔，**映像檔標籤帶版本號**，舊版映像檔不刪 | 沒有可以退回去的東西 |
| 3 | 停止 `api` | 資料庫還有寫入時做的備份不可靠 |
| 4 | **執行備份並驗證它還原得起來** | 「有備份」和「備份能用」是兩件事 |
| 5 | 套用遷移（DEP-31 那支指令） | |
| 6 | 以新版映像檔啟動，確認主線功能 | |
| 7 | 寫進更新紀錄（規範 18.4），含新舊兩個 tag | 半年後沒有人答得出資料是哪一次更新弄壞的 |

**回到上一版**：checkout 舊 tag、改用舊版映像檔標籤、還原第 4 步的備份。**資料庫已遷移時不得把遷移倒回去**（FR-S12）。

**DEP-32｜更新排在非透析時段，且更新後的第一個班次要有人在。**（保留）

**DEP-20｜前端更新不需要逐台處理平板。**（保留）外殼只是載入器，網頁改了不必重發 APK；只有改動外殼本身才需要重新側載。

### 6.4 作廢的交付條款

DEP-25（路線 A 的失敗紀錄）、DEP-26（進院前後各掃毒一次）、DEP-27（安裝包雜湊值）、DEP-28（隨身碟單向）**0926 作廢**：它們保護的是一條已經不存在的交付路線。**「不帶任何資料出院」的精神由 DEP-14 與 DEP-40 接手**，而且比隨身碟時代更需要程式擋——院內網路現在連得出去。

## 7. 病人端外殼 App：獨立的私人 repo

**DEP-45｜（0926 新增）外殼 App 是另一個私人 repo，與本系統以「契約」整合，不以複製程式碼整合。**

| 項次 | 規則 |
|---|---|
| 放在哪裡 | 獨立的私人 repo。本 repo 的 `apps/kiosk-shell/` 搬過去後刪除，**不留兩份** |
| 契約的真本 | **在本 repo**：載入網址格式、序號與金鑰格式、前景回報、版本回報、憑證信任方式，寫成共用型別與一份契約文件，帶**契約版本號** |
| 外殼怎麼對齊 | 外殼 repo 宣告它實作的契約版本；後端提供目前的契約版本與「最低可用外殼版本」 |
| 版本不合時 | 外殼每次回報都帶自己的版本；**護理端裝置管理直接標出版本過舊的平板**，不靠逐台檢查 |
| 本 repo 釘住哪一版外殼 | 設定裡寫外殼 repo 的 tag；`shell-builder` 只建那一個 tag |

**APK 在院內主機上建置。** 沒有隨身碟，APK 與簽章金鑰都得有一條進院的路；最乾淨的做法是讓它們根本不必進院：

| 東西 | 在哪裡產生 | 為什麼 |
|---|---|---|
| 院內 CA 與伺服器憑證 | 院內主機，`shell-builder` 首次執行時產生，存 `hd-tablet-care-keys` 資料卷 | 私鑰不離開主機 |
| APK 簽章金鑰 | 同上 | 同上。開發端另有一把**開發用**簽章金鑰，兩者簽出的 APK 不能互相覆蓋安裝，不會搞混 |
| APK | `shell-builder` 以 Android 建置映像檔，從主機上的外殼 clone 取出釘住的 tag、嵌入院內 CA 後建置 | 建置用的 SDK 全在映像檔裡，主機不必裝（DEP-04） |
| 平板怎麼拿到 APK | 病人端靜態服務提供一個院內的下載頁 | 平板連院內 Wi-Fi 即可下載側載，不經任何外部媒介 |

> **0927 迭代 12 已實作**（實作規格書 4.10），落實方式有四處要記下來：
>
> | 項次 | 做法 | 理由 |
> |---|---|---|
> | 外殼原始碼怎麼進 `shell-builder` | **主機上**以外殼 repo 的部署金鑰 clone（`.env` 的 `HD_SHELL_SRC_DIR`），compose 以 `additional_contexts` 帶進映像檔建置，映像檔自己 checkout `shell.pin` 釘住的 tag | 部署金鑰不進映像檔；DEP-43 本來就是主機 clone 兩個 repo |
> | 建置與執行分兩段 | 映像檔建置時下載 SDK 與全部相依、**不掛資料卷**；執行時 `network_mode: none`，以離線模式建置與簽章 | DEP-14：掛著 CA 與簽章私鑰的那一刻一條網路都沒有 |
> | 伺服器憑證用在哪 | 病人端靜態服務以它提供 HTTPS，並把 `/api/` 轉送給 api；病人端與後端同一個來源 | 外殼只信任院內 CA、只准 HTTPS，HTTPS 頁面不准呼叫 HTTP 的後端；同源之後只要一張憑證、不必設 CORS |
> | 下載頁 | 同一個埠接 HTTPS 與 HTTP，HTTP 只留 `/shell/` 下載頁，其餘轉到 HTTPS | 平板第一次下載 APK 時還不信任院內 CA；不另開埠（DEP-37 第 2 項） |
>
> 金鑰資料卷的內容、權限與 `shell-builder` 的四個指令（`build`、`keys-info`、`keys-backup`、`keys-verify`）見
> `services/shell-builder/README.md`，步驟見部署手冊第十二冊。

**DEP-35｜（0926 改寫）CA 與 APK 簽章金鑰遺失即無法補救。** 金鑰資料卷的內容與資料庫一併備份到院內另一台機器，每年驗證一次還原得回來。簽章金鑰遺失的後果不變：再也發不出更新版，只能換套件名重新側載全部平板。

0927 起的做法：`shell-builder keys-backup` 把金鑰寫到備份目錄底下的 `keys\`，隨資料庫備份一起送走；`shell-builder keys-verify` 核對某一份備份還原得回來。**`shell-builder` 絕不覆蓋既有的 CA 與簽章金鑰**，資料卷不完整時拒絕執行，要從備份還原。

## 8. 病人端平板的佈建

完整方案見《[平板管控：免 MDM 的全院內方案](../notes/mdm-offline-plan.md)》。

### 8.1 伺服器端（做一次）

1. 啟動本系統（第 6 章）
2. 執行 `shell-builder`：產生 CA、伺服器憑證、簽章金鑰（僅首次），建置 APK 並放上下載頁
3. 備份金鑰（`keys-backup`，DEP-35）；重新啟動 `patient-web`，讓病人端改走 HTTPS
4. 在護理端裝置管理建立平板，取得各台的序號與金鑰

### 8.2 平板端（每台各做一次）

1. 設定裝置 PIN，關閉新增使用者
2. 開啟允許安裝不明來源應用程式
3. **以平板瀏覽器開院內下載頁（`http://<院內主機>:<病人端埠>/shell/`），下載並安裝 APK**
4. 開啟螢幕固定，勾選「解除固定前要求 PIN」
5. 首次啟動，輸入主機位址（`https://` 開頭）與該台的序號、金鑰
6. App 詢問是否固定畫面時按「確定」（0927 起外殼每次啟動都會請求一次）
7. 記錄序號與床號的對應，核對護理端裝置清單

**DEP-36｜首波試用只佈建實際會用到的台數。**（保留）先兩三台跑完一個完整班次，再佈建其餘。

**每日要做的一件事**：前一天有重新開機的平板要重新釘選——App 開機後會自己起來並跳出固定確認框，按一下即可。

## 9. 開發端實測部署：開發機＋開發手機

**DEP-22｜（0926 改寫）每一個要交給院方的 tag，都要先在開發機上以院內的同一套指令從零部署一次，並以開發手機當平板走完一輪。** 「從零」的意思：

- **全新的 clone**，不是平常開發的那個工作目錄
- **全新的資料卷**，不沿用開發用的資料庫
- **只用 Git 與 Docker**，指令與院內一字不差；開發機上的 Node.js 在這一輪裡不得被用到
- 開發手機裝的是 `shell-builder` 在開發機上建出來的 APK（開發用簽章），**從下載頁安裝**，不是從 Android Studio 直接裝

**要走完的一輪**（任一項不過，tag 不得交出去）：

| # | 驗什麼 |
|---|---|
| 1 | 從 clone 到服務起來全程沒有人工補步驟，且每一步的輸出都存下來 |
| 2 | 開發手機從下載頁安裝外殼、輸入序號與金鑰、釘住 |
| 3 | 護理端簡易版把病人拖到那支手機的床位，手機出現病人畫面 |
| 4 | 手機上送出透析前問卷、按緊急回報，護理端即時看到 |
| 5 | 手機跳出螢幕固定，護理端 30 秒內看得到 |
| 6 | 更新一次：打一個測試 tag，照 6.3 走完，再回到上一版，資料完整 |
| 7 | AI：`LLM_PROVIDER=lab` 經 SSH 通道接實驗室閘道，以合成病人跑一次 AI 草擬；**再把設定改成正式環境，確認後端拒絕啟動**（DEP-40） |

**這一輪取代 v2.0 的「乾淨 Windows 機器」**：v2.0 要乾淨機器，是因為安裝包要證明它不依賴開發機上的東西；容器本身就是那個乾淨環境，要證明的變成「院內那一套指令真的走得完」。

## 10. 第一次部署的範圍

**DEP-33｜第一次部署為首波試用，不是全單位上線。**（保留）少數護理師、少數病人；首波的效能數字不得當成全單位上線的依據。

**DEP-34｜尚未實作的功能一律不提供服務，而不是提供一個停用的入口。**（保留）

**DEP-29｜下列功能於第一次部署時關閉，之後可在護理端系統設定開啟（FR-S11），不需要重新部署。**（保留，AI 一列改寫）

| 關閉的東西 | 什麼時候開 |
|---|---|
| 三項高風險功能（FR-P03／P05／N06） | 實作完成，且法務書面確認與臨床門檻值到齊 |
| 所有需手持裝置的功能 | 護理師配發行動裝置後（Q-30） |
| 班表、成效基準 | 成效基準量測排定後 |
| 離院衛教 | 護理部確認流程後 |
| L3 個人層級績效 | 護理部書面同意後（FR-M11） |
| AI 生成功能 | **院內正式 GPU API 就位且健康檢查通過**（Q-07）。實驗室不算——它在院外（DEP-40） |
| 輪播第二層 | 內容上架後 |
