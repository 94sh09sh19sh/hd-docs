# 實作規格書 4.13 迭代 15：院方 API 介接與自動化（1005 新增）

上層文件：《[實作規格書](../../implementation-spec.md)》第 4 章

## 摘要

- 範圍：迭代 15 院方 API 介接與自動化（1005），寫 `HospitalApiAdapter`，讓 FR-S15 對照表每一列「能」都不再需要護理師；設計見 3.5
- 工作項：探測工具（最先做）、模擬院方 API、抓取解析去重、病人與床位與療程同步、四種數值與生命徵象寫入、即時推送、護理端簡易版調整
- Schema 只做加法；病人、床位、療程全走與護理師拖曳相同的服務，操作者記為「院方資料同步」
- 狀態：1005 實作完成，驗收 10 條全數通過（後端與前端腳本全綠）
- 待做：模擬部署走一次部署規範第 9 章、第三次進院在院內跑探測工具（4.19）、1001 院內主機接上院方資料後拿掉 01～15 預設床位
- 對真實資料啟用要第三次進院的探測結果，實作本身沒有外部依賴
- 內含開發端判斷表（簡易版人工流程、系統帳號、模擬部署明示、床位圖捲動、累積量當公升等），使用者要推翻時改右欄那一處

**目標**：寫 `HospitalApiAdapter`，讓 SRS FR-S15 對照表上每一列「能」都不再需要護理師。設計見 3.5 的 1005 段落。

**Schema 變更**：只做加法。新表 `dialysis_vital_records`、`hospital_api_fetch_runs`；`patients` 加配給他的平板；`treatment_sessions` 加來源、預計結束時間、護理師改過的時間；`beds` 加來源。

**驗收標準**：

1. 全新環境開著模擬院方 API，**完全不碰護理端**：病人、床位、當日療程自動出現，床位圖與模擬資料一致
2. 配過平板的病人，模擬資料開始透析後**一個抓取週期內**平板自動進入這次療程；結束體重出現後一個週期內自動下機
3. 護理師提前結束或手動換床之後，下一次同步**不改回去**
4. 回應格式不對（少欄、字串數字、空字串、開頭的 `<meta>`、0）不寫入錯的資料，也不讓其他病人的同步中斷
5. 模擬院方 API 停掉：面板保留舊值與時間；護理端在門檻後出現未更新提示；恢復後自動續抓、補齊中間的紀錄
6. 同一份回應抓兩次，不產生任何重複紀錄
7. 正式環境設定下 `HOSPITAL_API_BASE_URL` 指向模擬，後端拒絕啟動
8. 探測工具的輸出**不含任何一個欄位值**：模擬資料裡刻意放一組標記字串，輸出裡找不到它
9. 稽核軌跡分得出「院方資料同步」與人的操作
10. 既有驗收腳本全綠；專業版的新增病人、人工輸入、檔案匯入照樣可用

**外部依賴**：實作沒有。對真實資料啟用要第三次進院的探測結果（1.4）。

> **2026-10-05 實作完成。** 手動測試在《[迭代 15 分冊](../../../testing/iteration-15.md)》（`y1`～`y47`）。

**1005 迭代 15 實作結果**：

1. **探測工具**（`npm run probe:hospital-api`；院內主機在 `api` 容器裡 `node apps/api/dist/hospital-api-probe.js`）：打一次 `?date=今天`，印出連線結果、開頭有沒有 `<meta>`、每列欄數、依病歷號＋開始時間分組的透析次數與格式不符的原因、51 欄各自的型態分布、床位的格式樣式、姓名欄有沒有「〇」、透析進行中的列結束時間與結束體重長什麼樣、**本系統用到的數字欄的數值大小分布** （只分 0、0～10、10～1000、1000 以上幾段，用來判斷累積量是公升還是毫升）。**不印任何一個值、不印位址、不寫任何檔案**。指令寫進部署手冊[《從零部署本系統》](../../../deployment/ref-fresh-install-6.md) V-30a；位址當場輸入，不寫進 `.env`——探測不等於啟用。
2. **模擬院方 API**（`hospital-api-sim`，`apps/api/src/hospital-api-sim.ts`，同一個映像檔、`simulation` 設定檔）： 12 位虛構病人分三組——快結束、進行中、還沒開始，**以服務啟動的時間為準排**，開發機什麼時候開都看得到三種； `HOSPITAL_API_SIM_SCHEDULE=fixed` 改照透析室鐘點。邊界值照 3.5 放：字串數字、空字串、理想體重 0、透析中結束時間空白與已填預排值各半、一位病人每列少兩欄。每一列的「透析器」欄有一串標記字（驗收第 8 條用）。驗收腳本可以把它切成「原樣回傳指定的列」或「停掉（503）」。
3. **抓取、解析、去重、逾時與重試**（`modules/hospital-sync/`）：30 秒逾時、失敗再試 3 次；從第一個 `{` 開始解析；每一欄都容許數字與字串，十進位一律以字串換成整數最小單位（多出的小數位四捨五入，例如體重 62.45 kg 存 62.5——那是顯示精度，不是格式錯誤）。 **一位病人的一次透析是全有或全無的單位**：少欄、數字欄寫了文字、時間格式不對，那一次透析整個不寫入、寫一筆稽核（原因不含欄位值），其他病人照常。原始回應不存，`hospital_api_fetch_runs` 只記時間、筆數、結果、內容雜湊與錯誤原因（錯誤原因不含位址）。四個營運參數：抓取頻率（3 分鐘）、未更新提示門檻（10 分鐘）、待確認下機門檻（60 分鐘）、床號正規化（0 原樣／1 改字母在前／2 改數字在前，預設 0）。
4. **病人、床位、療程**全部走**與護理師拖曳相同的服務**（`ScheduleService.create`、`BindingService.create`、`DevicesService.setBed`、 `ClinicalDataImportService.import`），操作者是「院方資料同步」：
   - 病人：以病歷號對應，沒有就建立，有就以院方資料為準更新姓名、性別、生日（本系統沒有修改病人主檔的畫面，所以沒有「護理師改過的欄位」要避開）
   - 床位：院方出現過、床位清單沒有的床號就加在最後面；**只新增，停用的床不會再啟用**，病人也不自動放上停用的床。全新環境不再預設 15 床
   - 療程：當天出現就排班；開始時間已過且至少一筆紀錄才判定開始，**開始時間記院方資料的透析開始時間**；結束體重大於 0 即下機
   - 配了平板的病人，透析開始時平板在線上、沒有別的進行中綁定，就接上並把平板放到院方資料說的那一床；任一條件不成立就不接，標示原因
   - 病人換床（院方資料的床位變了），有平板的平板跟著過去；目的床的平板正在服務別人就不搬
5. **四種數值**經 `HospitalApiAdapter`（`ClinicalDataSourcePort` 的第三個實作）與原本的匯入服務寫入：0 不建立、公升換毫升；透析前兩種記在開始時間，**結束兩種等結束體重出現才寫**、記在結束時間。同一資料時間已有相同的值就跳過，值變了才覆蓋並保留前一版。
6. **生命徵象紀錄**（`dialysis_vital_records`）只收這次療程有綁定平板的病人；去重鍵（病人、透析開始時間、紀錄時間）。下機前先寫，最後幾筆不會掉。院方不通期間的紀錄，恢復後下一次抓取補齊（院方每次回傳當天全部）。
7. **即時推送**：護理端走原本的串流，同步改到的那幾列推一次，每次抓取後另推一則同步現況；平板新增 `GET /device/stream`，推「療程變了」「有新紀錄」兩種事件（**不帶任何數值**），平板收到就重問一次。推送只是加速，輪詢照舊。
8. **Schema 變更**照規劃，只做加法（遷移 `20261005090000_iteration15_hospital_api`，`check:migration` 通過）：新表 `hospital_api_fetch_runs`、`dialysis_vital_records`；`patients.preferred_device_id`； `treatment_sessions` 加 `source`、`bed_no`、`expected_end_at`、`nurse_modified_at`、`bed_nurse_modified_at`；`beds.source`。 **比規劃多一欄 `treatment_sessions.bed_no`**：沒有平板的病人也要在床位圖上，「病人在哪一床」不能只看他那台平板。「護理師改過」分成兩欄：改狀態（提前結束、取消、重新開啟、確認下機）與換床是兩件事，換了床的病人結束體重出現時照樣要自動下機。
9. **護理端**：簡易版接了院方 API 時拿掉「新增病人」與「把病人拖上床」，病人框改放「今天要透析、還沒配平板的病人」與平板沒有自動接上的病人， **把平板放到病人身上就是配平板**（可一步復原）；床位圖上方的「院方資料已 N 分鐘未更新」、床位格的「待確認下機」（點一下、延後 8 秒送出）、沒有自動接上的原因（斷開圖示）。專業版：病人頁多一欄「配給的平板」、排班頁沒有平板的病人可以「下機結束」、系統管理多一張「院方資料同步」卡片（現況、最近幾次抓取、立即同步）。事件記錄選「透析中低血壓處置」時自動帶入最近一筆院方血壓與時間（補充說明空著時才帶，護理師可改）。
10. **病人端**：任務時點從院方資料的透析開始時間起算（沒有院方資料時退回綁定時間）；療程進度條用預計結束時間。訂閱平板推送。

**開發端在實作時做的判斷**（使用者要推翻時改右欄那一處即可）：

| 判斷 | 理由 | 寫在哪 |
|---|---|---|
| **沒接院方 API 的環境，簡易版照迭代 14 的人工流程**（1006 迭代 17.1 起改成兩種環境都是「病人拖到平板」，使用者決定） | 位址空白就是不抓（3.5），那時沒有任何事能由 API 判斷；拿掉新增病人，護理師只能切到專業版。接了才換成配平板 | `simple/Workbench.tsx` 的 `hospitalApi` |
| **代表「院方資料同步」的是一個登入不了的系統帳號** | 療程、綁定、匯入批次的建立者都是必填的護理師外鍵；改成可空要重建資料表（減法）。帳號狀態停用、密碼丟掉、帳號清單與「有沒有使用者」都不算它；畫面與稽核顯示「院方資料同步」 | 共用常數 `HOSPITAL_SYNC_WORK_ID`、《資料庫使用規範》第 13 條 |
| **模擬部署以 `HD_SIMULATION_DEPLOYMENT=yes` 明示** | compose 把後端固定成正式環境設定，模擬部署也一樣；不明示就連模擬部署都用不了模擬院方 API。院內主機一律留空，留空時指向模擬就拒絕啟動 | 部署規範 DEP-46、《`.env` 怎麼填》與之一 |
| **床位圖排不下就捲動**，床位格最矮 196px | 1005 床數不設上限（同院 IDH 系統是 41 床）；不設最矮高度，41 床會把格子壓到放不下內容。1366×768 一次看 15 床（與迭代 14 同密度），1920×1080 約 40 床；整頁仍不捲 | 《介面設計基準》3.5、`design-tokens.css` 的 `--bed-min-h` |
| **院方的開始時間跨過班別界線時，換班別不另建** | 預排值與實際值可能跨過 12 點或 17 點；同一次透析不該變成兩筆療程。只動院方帶進來、還沒開始、護理師沒碰過的那一筆 | `hospital-sync.service.ts` |
| **累積量（第 46 欄）當公升讀** | 與其他容量欄同單位；探測工具印出它的數值大小分布，第三次進院看一次就知道對不對，錯了改一行換算 | 《資料字典》`dialysis_vital_records` |
| **衛教時點不改成「預計結束前」** | 起點換成透析開始、參數不變（本節工作項）；預計結束時間可能是預排值，第三次進院確認之後再談 | SRS FR-P15 補充說明的那一句保留為之後的選項 |
