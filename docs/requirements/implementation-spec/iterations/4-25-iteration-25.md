**1018 迭代 25 實作結果**（三次子迭代同一天做完，程式一筆 commit）：

- **25.1 頂端求助橫幅**：`realtime-context.tsx` 多一支 `pruneAlerts`，開場快照（`HELLO`）、狀態推送（`PATIENT_STATE`）、求助推送（`HELP_REQUEST`，先修剪再加上新的那一則）、輪詢補位快照四處都呼叫。拿掉的條件三個同時成立：那一則的療程**在這份狀態裡**（推送只涵蓋它自己那一次；快照涵蓋當日每一次，跨過午夜換成隔天的快照不算）、`pendingHelpRequests` 裡找不到它、狀態的 `serverTime` 晚於它的 `receivedAt` **超過 5 秒**（`PRUNE_GRACE_MS`）。`HelpRequestAlerts` 一行都沒改，14.4 的「快照裡明確不是待處理的不畫」照舊在元件裡
- **動手前的重現（工作項第 1 列）**：開發端先做了修正才回頭重現，做法是把 `realtime-context.tsx` 暫時換回 25 以前的版本、開著專業版跑規畫文件 2.5 的第 1～4 步：**結案之後橫幅冒回來（第 3 步 0 → 1）、取消之後也留著（第 4 步 2 則都在），重新整理前一直在**，對上第 2.2 節的原因；第一個現象（按我接手之後橫幅沒消失）在這一次的步驟裡沒有出現——接手當下橫幅照 14.4 藏起來，所以規畫文件 2.3 的推論成立：使用者看到的是**更早幾次已經結案、冒回來的那幾則**。換回新版再跑一次，四步都是 0。第 5 步（斷線）留在手動測試
- **25.2 院方 API 多收的欄位**：`HospitalApiColumn` 多十二個位置；`hospital-api.format.ts` 每一筆多讀血流速、透析液流速、靜脈壓（整數）與透析液溫度（乘 10），每次透析多讀體溫（乘 10）、輸液（毫升）、食物（公克）、Ca（乘 100——院方可能寫到 2.75）、傳導度（乘 10）與三個文字欄（各截到 64 字）。**這幾欄認不出就當沒有值、不擋整次透析**（開發端判斷①）；空白存空值、0 照實存，顯示時才擋（與既有的生命徵象同一條規則）。每一筆的四欄加在 `dialysis_vital_records`；每次透析一個值的放新表 `dialysis_session_settings`（一次療程一列，值變了才覆蓋並記下那一次抓取）。範圍照舊只有這次療程有配平板的病人；**不上病人平板**（`verify:iteration16:api` 的「不顯示的欄位一個都找不到」照樣通過）。探測工具多印這幾欄的數值大小分布（只印分布）；模擬院方 API 的靜脈壓隨透析升高、透析液溫度 36.0、第 3 位的體溫回 0
- **25.2 背景端點**：`GET /api/help-requests/:id/bedside`（權限「看病人」，`help-bedside.service.ts`），一次帶齊這一次求助、床號、透析開始時間、本次透析每一筆量測（**讀到 0 的欄改成 null，全是 0 的那一筆不送**）、院方資料最後一筆的時間、透析前體重、理想體重（`DRY_WEIGHT`）、目標脫水量（`UF_TARGET`，只認這一次透析當天的）、設定脫水量、透析設定、本次療程的透析前問卷（只列答「有」的）、本次與前 3 次療程（不算取消的）的每一則求助、這位病人還沒結束的追蹤事項。**只讀，不寫稽核、不改狀態**
- **25.2 速覽元件** `bedside-brief.tsx`（兩版共用）：上面一列床號、姓名、這一次求助、「我接手」與 ×；左欄一列一件事（沒有值的那一列不出現），右欄兩張折線圖、近期求助（最多 6 列，其餘寫「還有 N 則」）、待追蹤（最多 3 列）。折線圖自己畫 SVG：四條線同一種顏色（`--c-ink`），收縮壓實線、舒張壓虛線、靜脈壓點線、脈搏點虛線，線尾寫名稱與數值；脈搏用右邊的軸；橫軸從透析開始到開始後四小時（`plannedDialysisEndMs`）；求助時間一條直的虛線、設定脫水量一條橫的虛線，都是 `--c-line`。Esc、點外面、×、按完「我接手」都關
- **25.2 簡易版**：紅框與格子上還沒人接的求助點下去 `setBriefId`，**不呼叫確認通報**；速覽裡的「我接手」是整個簡易版唯一呼叫 `actions.acknowledge` 的地方。已接手的格子多一顆 `id-card`（`.bed-brief`）。速覽蓋在平板區那一格（`.wb-brief-layer`，最後一列、左欄）；平板區與右邊兩框改成寫明自己的格子（`.wb > .wb-map`、`.wb > .wb-rail`）——不寫的話速覽一出現，自動排版會把平板區擠到右欄、右邊兩框擠到下一列（第一次截圖就是這樣）。速覽開著的那一則結案或取消、不在格子上了，速覽跟著關
- **25.2 專業版**：緊急通報頁每一筆多一顆「病人簡介」（`id-card`＋字），開同一個元件，蓋在頁面中間（`.brief-pro-layer`）；卡片上的「我接手」照舊
- **25.3 資料**：`nursing_records.source_help_request_id`（可空、唯一，以 `ADD COLUMN … REFERENCES` 加上，不重建資料表）；記錄類型多 `HELP_RESPONSE`（「求助處置」）。遷移一支 `20261018090000_iteration25_emergency_quick_view`，五個欄位、一張新表，只做加法
- **25.3 結案時建立**：`HelpResponseDraftService.shouldAutoCreate`——附錄 C.2 臨床組、結果不是「病人自行取消」（`O_PATIENT_CANCELLED`）。段落在交易之前組好（要讀院方量測與問卷），`resolveWithFollowUps` 在同一個交易裡多建一筆草稿；**唯一鍵擋下時整筆結案不成立、回 409**。組法在 `nursing-records/help-response.ts`：事件時間＝按下求助；D／S 是「HH:MM 病人以平板求助：<病人看到的那行字>，附註：「…」」、按下前填的透析前問卷答「有」的題目、按下前最近一筆量測；A／P 的時間線是按下、接手、（有登記才寫）到達床邊，接處理方式（依點選順序）與護理師的補充；R 是處理結果與**按下之後、結案為止**的每一筆量測；T 只在追蹤事項有「需加強衛教」（`F_EDU`）時帶一句；SOAP 的 A 是空字串。稽核照「護理紀錄建立」記一筆，歸結案的護理師
- **25.3 補改**：`amendOutcome` 改完結果呼叫 `regenerate`——**只重組草稿、而且還沒改套範本的**（開發端判斷②）；重組時 AI 初稿作廢（呼叫紀錄照留）。稽核的「補改處理結果」後面寫明「求助處置草稿已跟著重組」。簡易版 8 秒內改結果本來就是在送出之前改，不經過補改
- **25.3 護理紀錄頁**：卡片多「來自 HH:MM 的求助」（點了開那一則的速覽，唯讀）；右上「依病人自報預填」底下多「依求助建立」（`GET /nursing-records/help-candidates`、`POST /nursing-records/help-responses`，列出這次療程已結案、沒有記錄的，包括非臨床組與病人自行取消的）；手動事件記錄的事件時間底下寫「請改成發生的時間」；求助處置草稿多「改套範本」（`POST /nursing-records/:id/template`，事件時間與量測不動，D／S 段最前面留病人說的那一句，寫稽核 `NURSING_RECORD_TEMPLATE_APPLIED`）。編輯框在預填變了的時候跟著換：護理師沒動過的段落換成新的、只在後面補一句的接在護理師的字後面、整段重組的換成新的
- **圖示**：護理端多 `id-card`（床邊前速覽），從 lucide-static 1.48.0 照 `sync-icons.mjs` 的做法取
- 後端路由 210 → 214 條、稽核動作 150 → 151 種、資料表 91 → 92 張

**開發端判斷**（使用者要推翻時改這幾條）：①院方多收的欄位只給速覽看，認不出就當沒有值、不擋這位病人的血壓與下機；②求助處置草稿改套範本之後，結果補改不再重組它（內容已經是護理師的勾選，重組會蓋掉）；③「依求助建立」也列非臨床組與病人自行取消的（規畫文件 4.6 寫「非臨床組但護理師想記的」），自動建立仍只建臨床組；④近期求助列 6 則、待追蹤列 3 則之後寫「還有 N 則」，換來速覽在 1366×768 不捲動；⑤頂端橫幅的修剪有 5 秒寬限，在那 5 秒內就取消的那一則最晚等下一次輪詢（15 秒）才拿掉。

**驗收現況（1018）**：`npm run verify:iteration25`（不需要後端，七步全部通過：實際跑橫幅修剪七種情形、院方欄位解析、求助處置的組段落，再查兩版的接法、速覽的版面與用字、遷移只做加法、14／14.4／17.2／17.8 回歸與三支介面檢查）；`npm run verify:iteration25:api`（模擬院方 API＋後端，八步全部通過：速覽與院方資料逐欄一致、看完仍是待處理、接手時間與稽核、DART 與 SOAP 各一次、非臨床組／病人自行取消／取消的不建、一則一筆與交易、補改與簽核後不動、依求助建立與改套範本）。回歸：`verify:iteration15:api`、`16:api`、`17-8:api`、`14:api`、`14-1:api`、`19:api` 與 8～24 的不需要後端的腳本都通過（`verify:iteration13` 有一項在 25 以前就不通過，抓到的是它自己那支後端腳本裡的字樣，與本迭代無關）。開發機截圖（1366×768、1920×1080）：簡易版開速覽不捲動、紅框列與右邊兩框都在；已接手的格子與 `id-card`；專業版病人簡介；護理紀錄頁的求助處置草稿。頂端橫幅照 2.5 第 1～4 步在開著的專業版上實際跑過（見上面「動手前的重現」）。**還沒做的**：2.5 第 5 步（斷線期間的求助）；護理師實際用速覽走一次；多收的院方欄位在真實資料裡的格式（第三次進院探測，4.19）。

**目標**：護理師手上沒有裝置（Q-30），離開護理站前要看得到病人的背景，回來結案的那一下就把護理紀錄的草稿建好，不再事後回想；順手修掉求助橫幅結案後冒回來的缺陷。

| 結案（簡易版點處理方式、專業版結案登記）與建立草稿同一個交易：附錄 C.2 臨床組才建；非臨床組、病人自行取消、取消的不建；事件時間取按下求助的時間；段落照規畫文件第 4.4 節組，SOAP 的 A 段留空；到達時間沒有就不寫 | FR-N10、N18 |

| 護理紀錄頁：卡片標「來自 HH:MM 的求助」並連到那一則；「依求助建立」列出這次療程已結案但沒有記錄的求助；手動事件記錄的事件時間提示改成「請改成發生的時間」；草稿可以改套既有範本，事件時間與量測保留 | FR-N04、N05 |

**驗收標準**：

1. 臨床組求助結案後，護理紀錄頁那次療程多一筆草稿，事件時間等於按下求助的時間；非臨床組、病人自行取消、取消的沒有
2. D／S 段的量測是按下前最近一筆，R 段只有按下之後的；換 DART、SOAP 各走一次，A（SOAP）段是空的
3. 同一則求助不會有兩筆；結案交易失敗時草稿也不存在
4. 補改結果後未簽核的草稿跟著改，已簽核的一個字都沒變
5. 文字裡沒有姓名、病歷號、病名；到達時間關著時沒有任何「到達」字樣
6. AI 總開關關著時整條照樣走完；開著時 AI 潤飾不得新增勾選以外的事實

**三次都做完時的文件收尾**：資料字典（新欄位、新記錄類型）、手動測試分冊 `ai`、API 路由表子文件、兩份進度報告、架構圖，照維護指南（`docs/weekly/AGENT.md`）迭代收尾那一條逐項對。

**沒有外部依賴。** 多收的院方欄位在真實資料裡是什麼格式，要等第三次進院的探測（4.19）；在那之前照模擬院方 API 驗。
