## 4.27 迭代 27：病人平板固定橫放——外殼鎖橫向、拿掉直放排法、麻將放寬（1017 新增）

**沒有外部依賴**；實機重拍等 Q-33 的型號。

**1018 迭代 27 實作結果**（程式一筆 commit，不切子迭代）：

- **外殼：原本就鎖橫向，不改版**。動手前讀外殼 repo，`AndroidManifest.xml` 的 `MainActivity` 與 `ProvisioningActivity` **從迭代 10 的第一版（v0.2.0 之前）就是 `android:screenOrientation="sensorLandscape"`**，釘住的 v0.3.0 也是；Kotlin 裡沒有任何地方改畫面方向，掃 QR code 的畫面 `setOrientationLocked(true)` 鎖在開啟時的方向（佈建畫面已經是橫的）。1014 寫「外殼還會跟著平板轉向」是沒查外殼就下的判斷。所以上面工作項第 1、2 列**不做**：外殼版本不加一、不打 tag、`shell.pin` 不動、已佈建的平板不必重裝（開發端判斷①）。`verify:iteration27` 第 1 步直接讀釘住的那個 tag 核對，往後誰把它改掉會被擋下
- **病人端**：`styles.css` 的 `@media (orientation: portrait)` 拿掉——**實際是七段**（首頁基本資訊區、本次透析面板、遊戲圖示、自己的花園、植物與訪客的大圖、共同花園、相簿圖卡；規格寫八段是數錯），沒有哪一條規則只有直放用得到而留在外面。`design-tokens.css`、`styles.css`、`GardenBoard.tsx` 與營運參數「共同花園一座最多幾格」的說明裡寫「直放…」「800×1280」的地方改掉。字級、邊距照舊 `vmin`、求助區照舊 `vh`，數值都沒動
- **1280×800 前後比對**：開發機 `demo:patient` 上以無頭 Chrome 截首頁、求助、遊戲選單、花園、選種子、相簿封面、相簿圖卡、麻將開局與牌桌，改之前、改之後**逐像素比對完全一樣**（首頁只差數值與時間這些即時資料）；每一頁都不捲動、可點的都至少 64px、求助區頂端都在 664px
- **麻將放寬**：1280×800 的牌桌內容區實量 **1192×528px**（扣掉頂列、求助區 136px、邊距與牌桌自己的 12px 內距）——一列最多放 13 張 80px、取偶數 **12**；四列 452px 高、放得下。`MAHJONG_LEVELS` 在原本五級之後**加兩級：4×10、4×12（都要連線）**，`MAHJONG_MAX_COLS` 8 → 12（開發端判斷②）；前五級的編號與內容不動，存檔格式版本不變（存的是級數編號，舊存檔讀回來還是同一級）；升降規則、今日牌局 4×6 都不變。後端收的格子編號上限本來就照 `MAHJONG_MAX_ROWS × MAHJONG_MAX_COLS` 算，不必改。實際畫出來：4×12 每張 88×115px、4×10 每張 95×123px，都不捲動
- **發牌的保險改了一處**：實際畫出 4×12 才看到**每一對都左右相鄰**——照原本「倒著排」的亂序放 40 次都放不下時會落到「左右相鄰」的最後保險，量出來 4×12 有 81%、4×10 有 59% 的牌桌落到它，**4×8 也有 35%**（迭代 22 起就是這樣，`verify:iteration22` 只驗有解、沒驗這個）。落到保險的一桌照任何順序都消得完，等於最難的一級反而最簡單。改成：原本的亂序試 40 次都不行，**改「離邊緣越遠的格子越先放」再試 40 次**，外圈留到最後、靠外圍那一圈連得起來，還是不行才用保險。量過：五個連線級各一千次發牌，**沒有一桌再落到保險**；左右相鄰的比例 4×12 約 17%；最慢的一桌 10 毫秒。**原本放得下的那些桌牌面一模一樣**（同一個種子，4×4、4×6、4×8 各 300 桌比對，變的只有原本落到保險的那幾桌；卡住時的重排 200 次比對全部一樣）（開發端判斷③）
- **驗收腳本**：`verify:iteration16`、`verify:iteration17-4` 的直放檢查改成「病人端沒有直放的樣式」，`verify:iteration22` 的「一桌最多 4×8」改成 4×12 且前五級不動（實作規格書之一第二十一次）；新增 `npm run verify:iteration27`（不需要後端，七步）
- **工具**：`demo:patient` 拿掉 `--portrait`，截圖只有 1280×800
- 後端路由、資料表、稽核動作、開關都沒有增減

**開發端判斷**（使用者要推翻時改這幾條）：①外殼本來就鎖橫向，不為了「版本加一」而發一版沒有任何改變的外殼——發版要重建 APK、核對、逐台換裝，換不到任何東西；②加兩級而不是一步跳到 4×12：4×8 到 4×12 張數多一半，一級一級加比較平順；之後要再加只能加在最後，前面的編號不能動；③發牌只在原本放不下時改法，原本放得下的牌面不變——同一個種子同一桌的承諾照舊，今日牌局在新舊兩版之間也只有原本落到保險的那幾天不一樣；④`verify:iteration14-5` 有一句輸出寫「直放時高一點沒有壞處」，那是說明文字、檢查的內容（求助區依 `vh`）沒錯，不動那支腳本；⑤舊測試分冊驗直放的步驟照舊留著、補註「迭代 27 起不適用」，不刪，項次才不會亂。

**驗收現況（1018）**：`npm run verify:iteration27`（不需要後端，七步全部通過：釘住的外殼 tag 兩個畫面都是 `sensorLandscape`、程式沒有改方向、契約仍是第 1 版；病人端樣式與程式沒有依方向分的排法；前五級不動、新兩級要連線、每一級在 1192×528 放得下；新兩級各一千次發牌加窮舉都可解、五個連線級一千次發牌都沒落到保險、一千桌亂玩都玩得完；4×8 玩到一半的舊存檔讀回來玩得完、接著升到第 6 級；一路順利一級一級升到第 7 級就停、一路要提示一級一級退回第 1 級；最高一級的今日牌局仍是 4×6；`demo:patient` 沒有直式、基準兩份沒有直放的寫法；介面檢查、零院外連線與 8、14.5、16、17.4、22 回歸）。回歸：3～27 不需要後端的 36 支腳本 35 支通過（`verify:iteration13` 那一項照舊，與本迭代無關）；後端 `verify:acceptance`、`verify:iteration22:api` 通過；`npm run build` 通過；`check:ui`、`check:ui:design`、`check:egress` 通過。開發機 `demo:patient` 1280×800 截圖前後比對見上；4×10、4×12 在展示用的資料庫把級數改成第 6、7 級實際開一桌。**還沒做的**：平板（或開發手機）實際轉直、倒過來各一次（驗收 1，手動測試分冊 `ak`）；長者在床上看 4×12 的牌（每張 88px，比 4×8 的 95px 小一點）。
