## 8.1 共同設計

| 決定 | 為什麼 |
|---|---|
| **一律可重複執行，不改任何檔案** | 它們是量尺，不是修理工具。會自動改東西的工具，出錯時沒有人看得出它改了什麼 |
| **都支援 `--json`** | 要接進驗收腳本或 CI 時不必解析人看的輸出 |
| **有發現就回傳非零狀態** | 才擋得住「跑了但沒人看輸出」 |
| **每一筆都附「要改成什麼」** | 只說哪裡錯不夠——這幾類問題的正確做法都不只一種寫法，要講清楚選哪一種 |
| **`check:all` 每一支都跑完才算帳，不用 `&&` 串** | 0919 用 `&&` 串時，`check:ui` 必然是紅的（清除排在迭代 9），後面三支從來沒跑到，畫面上卻只像「check:ui 有 22 筆」 |
| **遷移安全只掃基準點之後的遷移** | 已經套用出去的遷移改不動（《資料庫使用規範》18.1），掃出來只會是一份永遠紅的清單。基準點寫在 `scripts/check-all.mjs` 的 `MIGRATION_BASELINE`，每次實際部署出去之後往前移到當次的最後一份 |

## 8.2 `check:ui` 的界線：註解不算

- FR-S10 管的是「使用者看得到的字」，不是原始碼；需求編號留在註解與文件裡是對的，那是可追溯性的來源
- 所以先剝註解再比對，用認得字串與樣板字串的狀態機剝，不用 `replace(/\/\/.*$/)`——後者會把網址裡的 `//` 當成註解開頭，把整行後半段吃掉，真正的違規反而掃不到
- 例外逐行寫在腳本裡並寫明理由，不開放整個檔案、不接受「加個註解就跳過」。目前唯一的例外：「系統管理 → 內容與選項」那一頁看得到識別碼——依附錄 C.0 第 1 條「識別碼不可改，顯示文字可改」，護理長看不到識別碼，就分不出自己是改文字（安全）還是新增選項（歷史資料會斷開）
- 0919 首次執行 22 筆（5 類），迭代 9 清到 0；基準線同步降到 0（`verify:iteration8` 的棘輪），之後只能往下

## 8.3 `check:offline` 抓過的真問題：浮動版本

- 0919 首次執行時 `prisma`、`@prisma/client` 宣告 `^6.5.0`，實際裝到 6.19.3；浮動範圍讓引擎與 CLI 有機會在某次重新安裝後對不起來，症狀會是看起來毫不相干的錯誤
- 迭代 7 鎖成 `6.19.3`（DEP-30 第 3 點），同一支多了遷移指令防呆與更新入口兩項檢查

## 8.4 腳本涵蓋不到、要靠人的事

寫出來是為了不要假裝腳本涵蓋了全部。

| 要驗什麼 | 為什麼腳本驗不到 | 怎麼辦 |
|---|---|---|
| 實際繪製出來的顏色 | `check:ui:design` 算的是語彙裡的色值；被父層半透明、`filter` 疊過之後的顏色要畫出來才知道 | 截圖驗證（介面設計基準第 7 節），或在瀏覽器開發者工具量 |
| 觸控目標的實際尺寸 | 腳本只查選擇器有沒有寫最小尺寸，排版後的最終尺寸要繪製才知道 | 同上，或用瀏覽器自動化量測 |
| 求助區在輪播中有沒有被蓋住 | 要真的畫出來才看得到 | 輪播中與非輪播各截一張圖比對（介面設計基準 2.3） |
| 部署在院內那一套指令下走不走得完 | 開發機上有開發環境 | 每個要交出去的 tag 照 DEP-22 在開發機上從零走一輪 |
