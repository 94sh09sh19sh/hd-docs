# 血液透析中心平板專案：FDE 數位化／數位優化評估報告

**專案背景**：醫院採購 15 台 Android 平板，供病人透析時使用；FDE 工程師可呼叫語言模型、醫院資料庫（去識別化）、自訓模型，目標為最大程度數位化與數位優化護理人員工作。

---

## 〇、本版改寫緣由（0910）

0909 定版之後，專案前提有五項實質變動，其中三項推翻了原評估的結論基礎，因此本文件不是小修，是重新評估：

| # | 變動 | 推翻了什麼 |
|---|---|---|
| 1 | **三項高 SaMD 風險功能解除封存**，本階段要做（風險分層、療程中預警、劑量調整參考） | 原評估把它們列為「待法規確認再議」，整份文件的功能邊界因此重畫 |
| 2 | **所有資料不得離開醫院網路**，因此不做推播功能 | 原評估選 PWA 的四項理由中，「支援推播通知」這一項失效；對外 LLM 呼叫這條線整條消失 |
| 3 | **AI 改為跑在院內一台 128GB 伺服器**，正式部署前先接實驗室 API（尚未取得）。**0912 具體化為 NVIDIA DGX Spark，且該機與其他專案共用** | 原評估的資料治理章節整段建立在「呼叫外部 LLM 服務商」的假設上，該假設已不存在 |
| 4 | **資料庫改用 SQLite**，測試階段與正式部署皆是，不接醫院既有資料庫 | 原評估未涵蓋；細節見《[資料庫使用規範](database-policy.md)》 |
| 5 | **新增四類需求**：管理層與對外展示、護理人力排班與獎勵、平板閒置輪播、求助處理結果蒐集 | 原評估只盤點護理臨床工作，未涵蓋單位管理與對外揭露 |

第 5 項有一半不屬於原本的十大護理工作區塊，硬塞進去會扭曲原分類，因此另立第五章處理。

### 0919 追加：第一次正式部署前的三項前提修正

0916 定版之後又有三件事變了，都是**部署前的最後一哩**，動到的是「跑在哪裡、平板怎麼管、選項誰決定」，不動功能邊界：

| # | 變動 | 推翻了什麼 |
|---|---|---|
| 6 | **應用主機改為院內一台 Windows 工作站**（Intel i7-14700、64GB 記憶體、2TB SSD ×2）。DGX Spark 不再是本系統的執行主機，**只剩「透過 API 呼叫的地端推論端點」這一個身分** | 7.4 的容器化理由有兩條（共用主機、ARM64）當場失效，部署形態必須重評 |
| 7 | **平板管控改走免 MDM 路線**（PWA 裝在自包 WebView 外殼裡，Kiosk 靠 Android 內建螢幕固定），結論見《[平板管控：免 MDM 的全院內方案](../notes/mdm-offline-plan.md)》 | 7.1 的「PWA 加 MDM Kiosk 鎖定」只講了第一層（網頁用什麼做），沒講第二層（誰負責載入與顯示） |
| 8 | **院方授權先採用 AI 產生的預設選項與題庫**，並要求在護理端系統設定中提供更改途徑 | 第四章多處「內容待護理部確認」的暫代狀態改為「已授權採用、可線上調整」 |

**這三項的共同性質**：它們都不改「要做什麼」，只改「怎麼交付、怎麼管、由誰定內容」。功能範圍仍以 0910 那五項變動為準。

### 0926 追加：第一次進院失敗之後的四項修正

0922 第一次進院失敗，之後確認了院方的部署條件；同週使用者另外定下介面與 AI 的方向：

| # | 變動 | 推翻了什麼 |
|---|---|---|
| 9 | **院方要求容器＋git clone；院內網路可以連出、外面連不進來；不准用隨身碟；Administrator 無密碼、能登入者一律可信任** | 7.4 的「離線安裝包」結論整條撤回，改回容器（見 7.4 的 0926 段）；前提一的落實方式由「網路擋」改為「程式擋」 |
| 10 | **實驗室 GPU 伺服器的使用規範已取得**，規定以 LangChain 呼叫、以設定檔管理模型 | 7.3 的「過渡期 API 尚未取得」；並多出一個本系統自己的 AI 閘道（7.3 的 0926 段） |
| 11 | **外殼 App 獨立為另一個私人 repo**，APK 在院內主機上建置 | 7.1 第二層的交付方式 |
| 12 | **介面以極簡為目標全面重新設計**；護理端分簡易版（預設）與專業版 | 第四章「面對護理師」各任務的呈現方式：簡易版把日常六項合併成一個畫面 |

**前提一的文字不變，但它的守法換了**：以前院內主機連不出去，程式寫錯了也送不出去；現在連得出去，**擋住資料的只剩程式本身**。因此 0926 多了兩條以程式強制的規則：執行期零院外連線的盤點範圍擴大到整個映像檔，以及正式環境不得選用實驗室供應者（部署規範 DEP-14、DEP-40）。

## 二、本專案的四項硬前提（0910 起）

這四項不是偏好，是限制條件，後面所有選型都要能通過它們：

### 前提一：資料出不了醫院網路

沒有任何一條主動打向院外的連線。這帶來三個直接後果：

- **不做推播通知。** Web Push 必經 FCM／APNs 等院外中繼，違反前提。護理端的即時通知改以院內 SSE 長連線加音效提示，並且**必須有一台常駐不休眠的護理站螢幕當總覽牆**——推播沒了之後，這台螢幕就是唯一保證看得到通報的地方，屬於部署必要條件而非選配。
- **對外 LLM 服務商整條移除。** 原本兩條跨院外的線（AI Proxy 呼叫外部 LLM、推播服務呼叫中繼）現在都不存在。
- **對外展示的資料必須另走釋出流程。** 新增任務一要「讓外部機構判斷團隊實力」，這與前提一天然衝突，處理方式見第九章。

### 前提二：AI 跑在院內一台 128GB 伺服器

**0912 具體化**：那台機器確定是 **NVIDIA DGX Spark**——ARM64、128GB 統一記憶體、與其他專案共用。

**0919 修正——這件事只剩半條成立。** 本系統的**應用主機不再是 DGX Spark**，改為院內另一台 Windows 工作站（Intel i7-14700、64GB 記憶體、2TB SSD ×2，**同樣與其他專案共用**，院方確保本系統資源足夠）。DGX Spark 退回它本來就該有的位置：**一個透過 API 呼叫的地端推論端點**，與本系統不同機、不同架構、不同維運者。

這個修正把 0912 據此訂出的限制條件拆成兩半：

| 0912 的限制條件 | 0919 之後 |
|---|---|
| 正式環境是 ARM64，與開發筆電不同 | **不成立。** 應用主機是 x86-64 Windows，與開發筆電同架構 |
| 正式主機與其他專案共用 | **仍成立。** 換掉的是機器，不是共用這件事——新的應用主機一樣與其他專案共用，差別只在院方確保本系統資源足夠 |
| 院內主機沒有對外連線 | **仍成立**，且是三者中唯一撐得起交付形態決策的一條 |

三條裡只有「ARM64」那一條失效，另外兩條仍在。但失效的那一條正是 0912 用來逼出容器的兩個主要理由之一，因此 7.4 的結論仍必須重寫，不能沿用。

過渡期先用實驗室 API（尚未取得）。因此模型呼叫必須從第一天就走可替換的介面層，見第七章。**前提二換機器不影響這一層**：不論端點在 DGX Spark、實驗室還是別處，對本系統而言都只是 `LLM_ENDPOINT` 的值——這正是當初設 `LlmProviderPort` 的目的，今天它第一次真的派上用場。

### 前提三：資料庫是 SQLite，測試與正式皆同

不接醫院既有資料庫。這反而簡化了原評估中「未來要遷移到 Oracle／MSSQL」的顧慮，但換來另一組問題（單檔、單寫入者、備份即檔案），全部規範在《[資料庫使用規範](database-policy.md)》。

### 前提四：不得影響主要使用功能

新增任務一與任務二都是「額外」的：多蒐集資料、多顯示內容。這兩者都可能排擠到病人回報症狀與求助這條主線。**本評估一律以主線優先**，任何新增功能若會遮蔽求助按鈕、延後通報送達、或增加護理師的操作步驟，即使能達成管理目的也不採用。

## 五、第十一區塊：單位人力與績效管理（0910 新增）

新增任務一有四個目的。它們表面上是四件事，實際上共用同一組底層資料，只是切法不同：

| 目的 | 誰是讀者 | 要回答的問題 | 資料從哪來 |
|---|---|---|---|
| (1) 向醫院主管與政府長官展現系統重要性 | 院長室、護理部、衛福部／地方衛生局訪視 | 這套系統替醫院省下什麼、避免了什麼 | 稽核軌跡的時間戳＋成效基準對照 |
| (2) 協助護理師排班、調動與安排 | 護理長、當班負責人 | 這個班該排幾人、誰該顧哪幾床、臨時有人請假怎麼補 | 排班表＋當班工作量實測 |
| (3) 建立護理師獎勵制度 | 護理部、人資 | 誰在承擔比較重的班、誰的照護品質穩定 | 與 (2) 同一批資料，換一種彙整 |
| (4) 讓外部公司或機構判斷 FDE 團隊實力 | 潛在合作方、評選委員 | 這個團隊做得出什麼、做得多可靠 | 工程證據＋去識別化成效摘要，見第九章 |

### 5.1 四個目的共用的資料底盤

**關鍵洞察：這四件事有九成的資料需求，用現有稽核軌跡就能滿足，不必新增蒐集動作。**

系統從 Iteration 1 起就在記「誰、何時、對誰、做了什麼」。把這批既有紀錄換個角度彙整，立刻可以算出：

| 既有紀錄 | 換算出的指標 |
|---|---|
| 求助送出時間 → 護理師確認時間 | 回應時間（中位數、95 百分位、最久的那幾筆） |
| 確認時間 → 結案時間 | 處理時長，依求助類型分開看 |
| 綁定／解除時間戳 | 每床實際週轉、換床空檔 |
| 症狀問卷送出筆數與時間 | 病人參與率、哪些時段最常回報不適 |
| 稽核軌跡的操作者欄位 | 每班每人實際處理的事件數 |
| 離線暫存後補傳的筆數 | 網路穩定度，可回頭跟資訊室要求改善 |

因此**「額外資料蒐集」的實際增量很小**，符合前提四。真正要新增的只有三項：

1. **成效基準（Baseline）** — 見 5.2，這是唯一有時效性的一項
2. **求助處理方式與結果**（新增任務四）— 把 `help_requests` 已有的自由文字結案備註升級成結構化欄位
3. **排班與人力配置**（新增任務一之(2)）— 目前系統只有病人排班，沒有護理師排班

### 5.2 成效基準：唯一有時效性的一件事

**這件事錯過就永遠補不回來。** 系統上線後，紙本流程就消失了，再也無從量測「以前要花多久」。因此在正式上線前，必須先用最土法的方式取得基準：

| 要測的事 | 怎麼測 | 建議樣本 |
|---|---|---|
| 從病人按鈴到護理師到床邊 | 現場碼表抽測 | 分三班各測 20 次 |
| 一次事件記錄從動筆到完成 | 護理師自記起訖時間 | 20 筆 |
| 每班口頭重複衛教的次數與時長 | 觀察記錄 | 3 個班次 |
| 交班時查找病人資訊耗時 | 觀察記錄 | 3 個班次 |
| 紙本記錄補寫的比例（當下寫 vs 事後補） | 護理師自陳問卷 | 全單位 |

樣本數不大，抽測而非普查，目的是取得一個**可辯護的概略數字**，不是做學術研究。沒有這一步，之後所有「省下 X 分鐘」的說法都只是估算，經不起長官追問。

**風險提示**：基準量測本身需要護理師配合，會佔用他們的時間。這與前提四有輕微衝突，但屬一次性成本，且不做就沒有第 (1) 個目的。建議由護理長指定一位種子護理師協助，而非全員配合。

### 5.3 排班、調動與安排（任務一之 2）

現況：系統已有「病人—療程時段」排班（`treatment_sessions`），但沒有護理師端的班表。要協助排班，至少要補三張表：護理師班表、當班床位分配、以及臨時調動紀錄。

| 層次 | 做法 | 分類 |
|---|---|---|
| 班表數位化 | 把紙本／Excel 班表搬進系統，當班誰在、負責哪幾床一目瞭然 | 數位化 |
| 工作量可視 | 用 5.1 的既有紀錄算出「這個班實際發生了幾次求助、集中在哪些時段」，讓排班有實測依據而非憑印象 | 數位優化 |
| 配置建議 | 依歷史同時段負荷，建議該時段的人力配置與床位分配 | 數位優化 |
| 臨時調動 | 有人請假時，依技能標記、連續工時、近期負荷提出候補人選排序 | 數位優化 |

**設計禁區**：

- 系統只提出建議，**排班決定權完全在護理長**，不得自動生效
- 連續工時、休息間隔等勞動條件必須是**硬性擋下**而非建議，系統不得產出違反勞基法或醫院規定的班表
- 不得以「誰回應比較快」作為派工依據——那會讓護理師學會避開難處理的床位

### 5.4 獎勵制度（任務一之 3）

這是四個目的中風險最高的一項。同一批資料，用來改善流程是資源，用來考核個人是壓力來源。以下是設計上必須守住的界線：

| 原則 | 具體做法 | 為什麼 |
|---|---|---|
| **團隊優先於個人** | 預設以班次／小組為計算單位，個人層級的數字預設不呈現 | 透析照護是協作，回應時間短可能只是離得近 |
| **不以病人臨床結果計分** | 獎勵指標限於流程面（記錄完整度、衛教完成率、通報處理完整率），不含病人的血壓、體重達標與否 | 用臨床結果考核護理師，會誘發挑病人、少記錄、報喜不報憂 |
| **不做公開排名** | 個人只看得到自己的數字與單位中位數的相對位置 | 公開排名的副作用遠大於激勵效果 |
| **指標公開且可申訴** | 計分規則寫成文件公告，任何一筆計分都能點開看到原始事件，護理師可提出更正 | 黑箱計分等於不可信任 |
| **先觀察後計分** | 上線後至少累積一個完整週期只看不算，確認資料沒有系統性偏差再啟用獎勵 | 早期資料常反映的是誰比較熟系統，不是誰做得好 |
| **需要同意才啟用** | 個人層級的績效彙整，須經護理部與員工代表同意後才開啟 | 這是勞動條件的實質變更，不是技術決定 |

**必須向使用者說明的一件事**：一旦護理師知道回應時間被記錄，行為就會改變——這是必然，不是可能。設計上要讓「行為改變的方向」是好的（更快確認通報），而不是壞的（先按確認再慢慢走過去）。因此**確認時間與實際到達床邊時間應該分開記錄**，前者由護理端點擊產生，後者由護理師在床邊平板上完成處置登記產生，兩者的差距本身就是資料品質的檢查點。

## 六、平板閒置資訊輪播（0910 新增，新增任務二）

### 6.1 需求本質

病人在平板前坐 4 小時，大部分時間沒有操作。這段空白目前是浪費掉的：牆上的公告沒人看，護理師口頭講的注意事項轉頭就忘。輪播是把這段空白變成低成本的衛教與資訊管道。

### 6.2 內容分層

輪播內容依「資料從哪來」分三層，各自的取得難度差很多：

| 層 | 內容 | 資料來源 | 現在做得到嗎 |
|---|---|---|---|
| **第一層：系統自己就有** | 本次療程已進行多久、預計還剩多久、今天已回報過哪些不適、衛教完成進度 | 本系統資料庫 | **做得到**，不依賴任何外部 |
| **第二層：靜態內容** | 飲食水分衛教、透析常識、中心公告、下次返診提醒 | 護理部提供的文字／圖片，人工上架 | **做得到**，只要護理部給內容 |
| **第三層：院方提供的臨床數值** | 乾體重、本次超過濾目標、最近一次抽血結果、Kt/V | 院方系統，格式尚未確定（API 或 Excel） | **待確認**，見 6.4 |

**建議的推進順序：第一層先上線，第二層跟上，第三層等院方確定格式。** 這樣不會因為單一個未確定項卡住整個功能。

### 6.3 不得踩到的界線（前提四的具體化）

| 界線 | 規則 |
|---|---|
| 求助按鈕永遠可見 | 輪播不得覆蓋、縮小或延後求助按鈕的反應；按鈕維持固定位置與尺寸 |
| 觸控立即讓位 | 螢幕任何一處被觸碰，輪播立刻停止並回到主畫面，不做「確定要離開嗎」這種攔截 |
| 只在閒置後啟動 | 建議閒置門檻 60 秒起跳，實際值由臨床端試用後決定 |
| 症狀問卷優先 | 到了該填問卷的時間，問卷蓋過輪播，不是輪播蓋過問卷 |
| 鄰床看得到 | 平板螢幕在治療區是半公開的。輪播若含病人可識別資訊，只顯示到床號層級，姓名與病歷號一律不進輪播畫面 |
| 不得有音效 | 治療區有病人休息，輪播一律靜音 |
| 夜間降低亮度 | 晚班時段輪播應調暗或改為靜態顯示，避免影響休息 |

### 6.4 資料來源（0919：已確定走 API）

**0919 更新**：院方確認病人臨床資料的那份 Excel **可以透過 API 取得**，不必靠人工匯出檔案再上傳。三個實作裡的 `HospitalApiAdapter` 因此從「之後再說」變成**正式來源**，`FileImportAdapter` 退為備援（API 不通或院方臨時改給檔案時仍可用），`ManualEntryAdapter` 維持保底。

這件事之所以不造成任何返工，正是因為下面這個介面層當初就先定好了——三種來源收斂成同一組內部資料表，換來源只是換一個實作，輪播與病人端一行都不用改。**0919 是這個設計第一次真的被兌現。**

原本的評估過程保留如下，作為「先定介面、後補實作」這個做法的實例：

院方尚未確定會給 API 還是 Excel。**這不應該成為阻塞點**，處理方式與 MDM 相同——先定介面，後補實作：

```
ClinicalDataSourcePort（抽象介面）
├── FileImportAdapter    ← 先做這個。護理師手動上傳 Excel／CSV，系統解析後存入
├── HospitalApiAdapter   ← 院方給 API 後補上，介面不變
└── ManualEntryAdapter   ← 保底方案。護理師直接在管理介面輸入少數幾個欄位
```

三種來源都收斂成同一組內部資料表，輪播模組只認內部資料表，不認來源。這樣院方最後決定用哪一種，都不需要改動輪播與病人端程式碼。

**Excel 來源的額外風險**（若最後走這條路）：欄位名稱與順序會被人手動改動、日期格式不一致、同一份檔案被重複上傳。匯入層必須做欄位對應設定、格式驗證、以及重複匯入的偵測，並且**任何一筆解析失敗都要擋下整批而不是部分寫入**——臨床數值只對一半，比完全沒有更危險。

**走 API 之後，上面這串風險少掉一半，但沒有全消**：欄位名稱仍可能在院方系統改版時變動，日期格式與病人識別對應仍要驗，只是「有人手動改了欄位順序」與「同一份檔案上傳兩次」這兩項不再發生。**「全有或全無」那一條一字不改**——一次抓取裡任何一筆驗不過，整批不寫入。API 另外帶來兩個 Excel 沒有的問題：抓取失敗要怎麼重試而不重複寫入，以及端點暫時不通時輪播第三層要顯示什麼（答案是顯示上一次成功抓到的值並照常標示資料時間，不是顯示空白）。

## 七、開發模式與 AI 部署選型（0910 重新評估）

### 7.1 前端模式：PWA 的四個理由，現在只剩三個

0909 版列了四項選 PWA 的理由，其中一項因為不做推播而失效。重新檢視：

| 0909 的理由 | 0910 是否仍成立 |
|---|---|
| 開發與迭代速度符合 FDE 工作型態 | **仍成立**，且因需求量大增而更重要 |
| 前後端可與護理站 Dashboard 共用同一套 API 層 | **仍成立**，且新增任務一的管理儀表板讓這點更划算 |
| 更新只需部署伺服器端，不必逐台重裝 15 台 | **仍成立** |
| 具備推播通知能力 | **已失效**，封閉網路不做推播 |
| （新增）Service Worker 離線快取 | **仍成立**，且輪播的靜態內容正好適合預先快取 |

**結論：第一層選型不變，仍為 PWA。** 但推播失效帶來一個必須補上的部署要求——護理站的常駐總覽螢幕（見前提一）。這台螢幕從「錦上添花」升級為「沒有它系統不成立」。

原生 App／混合式的比較結論與 0909 相同，此處不重複；升級為 Flutter 混合式的觸發條件仍是「要做機台資料直接整合」。

**0919 補上第二層：這個 PWA 由誰負責載入與顯示。** 0909 到 0916 這幾版都只答了第一層（病人端的內容用什麼技術做），把第二層當成理所當然是「Chrome 加 MDM Kiosk」。實際盤點之後，MDM 那條路走不通——Android Enterprise 有三個地方必須連外（首次佈建連 Google、後端設定政策要打 `googleapis.com`、遠端鎖定靠 FCM 送達），只要採用它，前提一當場不成立。

| 層 | 在問什麼 | 結論 |
|---|---|---|
| 第一層 | 病人端的內容用什麼技術做 | **PWA**（本節，理由三條仍成立） |
| 第二層 | 這個 PWA 由誰負責載入與顯示 | **自包 WebView 外殼 App**，Kiosk 靠 Android 內建的螢幕固定 |

**選了 PWA 不代表就得用 Chrome 開。** 自包外殼讓自簽 CA 可以打包進 APK，TLS 正常驗證、沒有警告、Service Worker 正常運作——而 Service Worker 正是 3.1 選 PWA 而非純網頁的唯一理由，用 Chrome 加自簽憑證反而會把它弄丟。完整的三方比較、要做哪些事、守不住什麼，見《[平板管控：免 MDM 的全院內方案](../notes/mdm-offline-plan.md)》。

**MDM 在本系統實際做的五件事裡，只有「防止病人跳出應用程式」需要作業系統權限**，其餘四件（納管狀態、Kiosk 網址、遠端鎖定、螢幕恆亮）本來就在應用層，或可在應用層做到。因此本次修正拿掉的是一整條對外相依，換來的只是「重新開機後要人工再釘一次螢幕固定」這一件每日工作。

### 7.2 AI 部署：地端 128GB 伺服器

> **0919 先講清楚一件事**：本節談的是**推論端點那台機器**（DGX Spark），不是本系統的應用主機。應用主機是另一台 Windows 工作站，兩者之間只有一條 HTTP 呼叫（見前提二與 7.4）。本節的載入量、頻寬、共用額度討論全部只影響「AI 功能回應多快」，不影響本系統怎麼部署、資料庫放哪裡、備份怎麼做。

**0912 更新：0910 版在這裡列的三個未知數，前兩個已有答案。**

| 0910 的問題 | 0912 的答案 |
|---|---|
| 128GB 是系統記憶體還是顯示記憶體？ | **都是**。GB10 Grace Blackwell 的 128GB LPDDR5x 由處理器與 GPU 共用 |
| 有沒有 GPU？ | 有，Blackwell 架構，與處理器共用同一塊記憶體 |
| 專用還是共用？ | **共用**。那台機器上不只本專案，可用額度仍待確認（Q-07） |

對照 0910 版列的三個情境，實際落點如下：

| 情境 | 可跑的模型規模 | 實際體感 | 是否為實況 |
|---|---|---|---|
| **A：純 CPU＋128GB 系統記憶體** | 7B～14B 的 4-bit 量化模型 | 每秒數個到十幾個字，對話會有明顯等待 | 否 |
| **B：有中階 GPU（24～48GB 顯示記憶體）** | 8B～32B 量化模型可全載入 | 接近即時 | 否 |
| **C：128GB 為顯示記憶體總和** | 70B 級 4-bit 可載入 | 接近即時且品質明顯較好 | **載入量接近 C，速度不到 C** |

**為什麼「載入量接近 C，速度不到 C」**：DGX Spark 的記憶體頻寬約 273 GB/s，遠低於資料中心級顯示卡。大模型載得進去，但每秒吐出的字數受頻寬限制。再加上機器是共用的，實際可用額度還要再打折。

**結論：功能分流的判準不變，但要往保守方向壓。** SOP 查詢這類即時互動仍有機會，衛教生成與記錄草擬繼續走背景佇列，不要因為「載得下 70B」就假設它會快。實際延遲必須在拿到端點後實測，不能從規格表推算。

**負載估算（重要）**：15 床、三班、每位病人每次療程估 5～10 次 AI 呼叫，尖峰同時請求數不會超過個位數，換算下來每秒請求數遠低於 1。**這代表本系統的瓶頸是單次延遲，不是吞吐量**，因此不需要昂貴的高併發推論架構；情境 A 的規格若搭配「非即時功能走背景佇列」的設計也能撐住。

**模型候選方向**（實際選型待硬體確認後另行評估）：

- 繁體中文能力是硬指標。病人端的衛教內容直接面對長者，用詞不自然會影響信任
- 國科會 TAIDE 系列為台灣本土訓練的繁中模型，用在公立醫院場域另有政策上的說服力，值得優先評估——這一點對新增任務一之(1)（向政府長官展現）有直接加分
- 開放權重的通用模型（Llama、Qwen、Gemma 等系列）在繁中表現差異大，須實測而非看規格表
- 三項高風險功能**不使用語言模型做判斷**（見第八章 R-1），因此模型能力不足不會直接造成臨床風險

### 7.3 過渡期：實驗室 API

> **0926 更新：實驗室 GPU 伺服器的使用規範已取得**，本節以下的形態描述與規範相符。規範另外規定兩件事，改變了串接方式：
> **以 LangChain 呼叫模型**（`langchain-ollama` 或 OpenAI 相容介面兩種方法），以及**建議以設定檔集中管理模型與參數**。
> 本系統後端是 Node.js，因此多做一個照規範寫的 Python **AI 閘道**：後端只跟閘道說話，閘道依 `config.yaml` 呼叫推論端點。
> 實驗室與院內共用同一個閘道，**換成正式 GPU API 只換 `config.yaml`**——這比 0910 設想的「兩個 provider 共用一份 HTTP 實作」又少了一層要改的東西。
> 串接時照規範流程做（個人資料夾、個人容器、只呼叫不管理模型），唯一差異是以 Terminal 的 SSH 取代 VS Code 遠端視窗（部署規範 DEP-42）。

~~實驗室 API 尚未取得。~~已知的實驗室資源形態如下（見 Q-08）：單張 RTX 3090（24GB 顯示記憶體）、以 SSH 遠端開發、**規定所有工作都在個人容器內進行**、推論服務為 Ollama 並提供相容於 chat completions 的端點。

**這件事有一個直接的好處**：實驗室給的是相容端點，院內推論服務大多也是同一組相容介面，因此 `LabApiProvider` 與 `OnPremiseProvider` 可以共用同一份 HTTP 實作，切換真的只是改設定。**也有一個要注意的地方**：3090 的 24GB 只跑得動 7B～14B 量化模型，而正式環境載得下大得多的模型——**過渡期跑得順，不代表正式環境跑得快；反過來也一樣**。提示詞與輸出格式的驗收要在兩邊都跑過。

與 MDM 相同，一律走可替換介面層：

```
LlmProviderPort（抽象介面）
├── MockLlmProvider       ← 現在就能用，回傳固定範例，讓其餘功能先開發
├── LabApiProvider        ← 取得實驗室 API 後接上
└── OnPremiseProvider     ← 正式部署，指向院內伺服器
```

**Agent 行為規則**：任何呼叫語言模型之處，一律透過 `LlmProviderPort`，不得在業務邏輯中寫死任何一家的 SDK 或端點。切換 provider 只能是設定變更，不能是改程式碼。

**過渡期的資料界線**：實驗室 API 在院外。因此**過渡期一律只能送合成資料**，真實病人資料要等地端推論就位後才能進入 AI 流程。這一條沒有例外。

### 7.4 部署形態（0912 訂為容器，0919 依主機變更重評）

**0912 的推論過程**：前提二具體化之後多出三個限制條件，三者合起來指向容器。

| 限制條件 | 0912 認為它為什麼逼出容器 | 0919 是否還在 |
|---|---|---|
| **正式主機與其他專案共用** | Node.js 版本、系統套件、連接埠都可能被別的專案動到 | **仍在。** 新的應用主機同樣與其他專案共用；但這件事用安裝包層級的隔離就處理得了（部署規範 DEP-37），不必動用容器 |
| **正式主機是 ARM64，開發筆電是 x86-64** | 「在我機器上可以跑」完全不成立，要有一個在目標架構上驗證過的確定產物 | **消失。** 兩邊都是 x86-64 |
| **院內主機沒有對外連線** | 不能在現場 `npm install`，交付的必須是自帶執行期的完整產物 | **仍在** |

**三條剩兩條，結論仍不能照抄。** 跨架構那一條消失了；隔離與離線交付都還在，但**兩者都不是非容器不可**——離線交付用一個自帶執行期的安裝包就做得到，隔離則落在安裝包層級：自帶執行期、登記過的固定連接埠、專用低權限帳號、自己的目錄（部署規範 DEP-37）。在 Windows 上這樣做比容器乾淨。

**更關鍵的是，容器在新主機上會撞到資料庫規範。** Windows 上的容器執行環境走 WSL2：SQLite 檔案若掛在 Windows 目錄的繫結掛載上，檔案鎖行為不可靠，正是《資料庫使用規範》7.2 明文禁止的情形；若改放進 WSL2 的 Linux 檔案系統，檔案就躲進一個院方看不到也不會備份的虛擬磁碟裡。**這不是設定調一調的問題，是形態選錯了。**

**0919 結論：正式環境改以「離線安裝包」部署在 Windows 主機上，交付物是一份自帶 Node.js 執行期與 Prisma 引擎的壓縮檔，不是容器映像檔，也不是一份安裝手冊。** 容器設定不刪除，降為備案——院方資訊室若要求容器化，改走那條路時必須一併解決上面那個資料庫落點問題。完整規則、兩條交付路線與部署前置檢查清單見《[部署規範](deployment-spec.md)》。

**開發環境同樣不容器化**，理由與 0912 相同，且現在開發與正式的執行形態終於一致（都是 x86-64、都直接跑在作業系統上、資料庫都在本機檔案系統），少掉一組「兩種環境各驗一次」的成本。

**0926：結論再翻一次，改回容器，而且這次是院方的條件逼出來的。** 0922 進院與之後的確認帶回四件事：院方要求容器、程式以 `git clone` 取得；院內網路**可以連出去**、外面連不進來；**不准用隨身碟**；Administrator 無密碼、能登入者一律可信任。對照 0919 的推論：

| 0919 選安裝包的理由 | 0926 |
|---|---|
| 院內主機沒有對外連線，必須帶自帶執行期的產物進去 | **不成立**：連得出去，就地 clone、就地建置 |
| 容器的 SQLite 落點會撞資料庫規範 | **有解**：資料庫只放具名資料卷，備份寫到主機目錄（部署規範 DEP-23） |
| （隱含）隨身碟是進院管道 | **反過來成為安裝包的死路**：不准用隨身碟，安裝包沒有路進去 |

**所以這一次不是「容器比較好」，是「安裝包沒有路」。** 安裝包路線因此撤除而不是降為備案。代價寫清楚：日常開發與正式環境的執行形態又不一樣了（開發本機直跑、正式在容器），因此每個交出去的版本都要在開發機上以院內同一套指令從零實測一次，並以開發手機當平板走完一輪（部署規範第 9 章）。

**維持不變的一個刻意決定：本專案不部署推論服務。** 0912 的理由是「DGX Spark 是共用的，自行載入模型等於跟其他專案搶記憶體」；0919 之後理由更直接——**那台機器根本不是本系統的主機**。對本系統而言地端推論只是一個 HTTP 端點，不需要 GPU、不需要 NVIDIA 容器工具鏈。代價不變：「誰維運那個端點、額度多少」仍是必須問清楚的事（Q-07）。

## 八、三項高風險功能的控制措施（0910 新增）

三項功能解除封存，但不是無條件放行。以下八條是它們的實作前提，缺一不可。

| 編號 | 控制措施 | 理由 |
|---|---|---|
| **R-1** | **一律用可攤開的規則，不用語言模型做判斷。** 風險分層、療程中預警、劑量調整參考三者的計算，必須是能寫成 if-then 條文、能逐條印出來給醫師看的規則 | 語言模型的輸出無法逐次複現，也無法向法規承辦人解釋「為什麼這次說高風險」。用規則不是技術倒退，是可辯護性的必要代價 |
| **R-2** | **規則的門檻值由臨床端書面提供，不由開發端自訂。** 未取得書面依據前，該規則只能跑合成資料 | 門檻值就是臨床判斷本身，開發端訂它等於在做醫療決策 |
| **R-3** | **每一則輸出都要能點開看到完整依據**：用了哪幾筆歷史資料、套用了哪一條規則的哪一個門檻、規則版本編號 | 這是讓功能停在「決策支援」一側的核心條件——臨床人員必須能獨立複核依據，而非只能相信結論 |
| **R-4** | **輸出一律標示「僅供參考，非診斷結果」**，且不得使用會被誤讀為結論的措辭（不寫「病人有低血壓風險」，寫「符合 X 規則：近三次療程第 2 小時後曾回報頭暈」） | 措辭本身就是分類判定的考量因素 |
| **R-5** | **不自動生效、不自動觸發任何動作。** 不得自動調整醫囑、不得自動改變處理優先順序、不得自動通知醫師 | 一旦自動生效，人在迴路就不成立 |
| **R-6** | **記錄「誰看過、是否採納、不採納的話為什麼」**，寫入稽核軌跡 | 這批紀錄同時是三件事的依據：法規查核的證據、規則調校的資料來源、以及新增任務一之(1)的成效證明 |
| **R-7** | **可全域關閉。** 三項功能各自有獨立開關，護理站管理者可即時關閉，關閉後介面上完全不出現相關內容 | 出事時要有一個立刻停損的動作，而不是等改版部署 |
| **R-8** | **書面確認閘門。** 未取得醫院法務／資訊室對 TFDA 分類的書面確認前，這三項不得對真實病人啟用 | 分類判定權不在開發端 |

**給臨床端與法務的一段話**：這八條的目的，是讓這三項功能盡量落在「提供資訊、由專業人員自行判斷」的範圍，而不是「軟體自己做出臨床結論」。這樣的設計取向能不能讓它免於醫療器材管理，需要主管機關或醫院法務判定，開發端不做這個判斷。在判定出來之前，功能可以做、可以用合成資料測，但不碰真實病人。

## 九、對外揭露與資料釋出（0910 新增，新增任務一之 4）

「讓外部公司或機構判斷 FDE 團隊實力」與「資料出不了醫院網路」直接衝突。解法不是在兩者之間妥協，而是**分清楚哪些東西根本不是病人資料**。

### 9.1 三類可對外的證據，風險由低到高

| 類別 | 內容 | 含病人資料嗎 | 釋出難度 |
|---|---|---|---|
| **甲、工程證據** | 架構設計、資料治理規範、測試手冊、稽核機制設計、迭代節奏、程式碼品質指標 | 完全不含 | 低。本專案的需求文件本身就是最好的證據 |
| **乙、系統能力展示** | 跑在合成資料上的展示環境，功能可實際操作 | 不含（全為 faker 產生） | 中。需確認展示環境與正式環境完全隔離 |
| **丙、成效數字** | 回應時間改善、記錄完成時間縮短等統計量 | 間接含有（由真實營運資料彙總而來） | 高。須走 9.2 的釋出審核 |

**建議的對外策略：把重心放在甲與乙。** 工程證據與可操作的展示環境，對判斷團隊實力的說服力其實高於幾個成效數字——後者外部無從驗證，前者可以當場檢視。

### 9.2 資料釋出審核（任何數字要離開院內都要走）

系統應內建一個釋出流程，而不是靠人記得規矩：

1. 要釋出的內容一律經由系統的「對外報表」功能產生，不得直接查資料庫匯出
2. 對外報表只能輸出**聚合後**的統計量，且設下最小分母門檻（例如少於 5 筆的分組一律不呈現，避免反推到個人）
3. 一律不含：姓名、病歷號、床號、可定位到單一療程的時間戳、護理師工作 ID
4. 每一次產生對外報表，寫入稽核軌跡：誰產的、要給誰、包含哪些指標
5. 由指定的核准角色（建議為護理部主管加資訊室）確認後才能取出

細部規則寫在《[資料庫使用規範](database-policy.md)》的資料釋出章節，此處只寫原則。

### 9.3 給長官看的與給外部看的，是兩份東西

不要用同一份簡報應付兩種讀者：

| | 給院內長官與政府 | 給外部公司／機構 |
|---|---|---|
| 主軸 | 這套系統替本院解決了什麼 | 這個團隊有能力解決什麼 |
| 主要素材 | 成效數字＋基準對照＋病人與護理師的實際回饋 | 架構與治理文件＋可操作的展示環境 |
| 敏感度 | 可含院內細節 | 一律去識別化，且經 9.2 審核 |
| 誠實度要求 | **未達成的事要一起講。** 長官會問，遮掩一次就失去後續所有數字的可信度 | 同左 |

## 十、資料治理（0910 改寫）

0909 版的治理重點是「防止資料流向外部 LLM 服務商」。封閉網路前提之下，這個風險消失了，但風險並沒有變少，只是換了位置：

| 0909 的主要風險 | 0910 的主要風險 |
|---|---|
| 病人資料流向院外服務商 | **內部誤用**：績效資料被拿去做非原始目的的考核 |
| API 金鑰外洩 | **單檔資料庫的實體風險**：SQLite 檔案被整份複製帶走 |
| 外部服務商留存輸入內容 | **長期累積**：稽核軌跡與 AI 輸出無限期堆積，卻沒有留存期限規定 |
| — | **對外釋出的反推風險**：聚合統計量在小樣本下可被反推到個人 |

四項新風險的具體規範全部落在《[資料庫使用規範](database-policy.md)》，本文件只標示它們存在。以下三條是不能因為「反正都在院內」而放鬆的：

1. **去識別化仍然要做。** 送進 AI 流程的內容一律最小揭露——病人的姓名與病歷號從來就不是生成衛教內容所需的資訊。理由從「防外流」變成「最小必要原則」，做法不變。
2. **測試資料仍然一律合成。** 開發機不是院內環境，這一點沒有因為資料庫換成 SQLite 而改變。
3. **稽核軌跡仍然是不可否認的紀錄。** 不得因為它同時被拿去算績效，就開放修改或刪除。
