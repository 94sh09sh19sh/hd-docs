## 2. 技術棧

| 層 | 選擇 |
|---|---|
| 前端 | React（病人端PWA、護理端PWA共用元件庫，分兩個應用進入點）|
| 後端 | NestJS（API Gateway/BFF、裝置綁定服務、AI Proxy Service、推播通知服務，可先以NestJS module劃分，未來視負載決定是否拆微服務）|
| ORM | Prisma |
| 測試階段資料庫 | Supabase（PostgreSQL）——僅作為暫時PostgreSQL主機，嚴格遵守《資料庫使用規範》全部條款 |
| 正式環境資料庫（未來） | MSSQL（Microsoft SQL Server，醫院既有資料庫）|
| AI模型 | Anthropic Claude，預設 `claude-sonnet-4-6`（介面顯示為「Sonnet 5」），使用者可於介面切換模型與思考程度（thinking budget/effort）|
| MDM | Android Enterprise（本階段僅做可替換介面層，見3.3節）|

**Prisma與未來MSSQL遷移的特別提醒**：

- Prisma schema設計時避免使用PostgreSQL方言專屬型別（如非必要不使用`jsonb`承載結構化關聯資料，改用正規化資料表），這點與《資料庫使用規範》第6條一致。
- Prisma支援多種資料庫provider（含SQL Server），設計schema時儘量使用兩邊都支援的標準型別與關聯設計，降低未來切換`provider`與資料型別對照的工作量。
- 不使用Supabase專屬功能（RLS、Realtime訂閱、Edge Functions）作為核心邏輯，僅能作為defense-in-depth的輔助（見《資料庫使用規範》第4條）。

## 3. 關鍵機制設計

### 3.1 護理端身份驗證機制（取代Supabase Auth，自建）

**設計原則**：不使用Supabase Auth，身份驗證邏輯完全自建於NestJS後端。

**流程**：

1. **初始最高權限帳號**：系統啟動時，後端讀取`.env`中設定的初始帳密（`SUPER_ADMIN_WORK_ID`、`SUPER_ADMIN_INITIAL_PASSWORD`），若資料庫中尚無任何使用者，自動建立第一個「最高權限使用者」（角色：`SUPER_ADMIN`）。
2. **一般護理師註冊**：護理師於護理端PWA以「工作ID」（醫院員工編號）提出註冊申請，狀態為`PENDING`，此時不可登入使用任何功能。
3. **審核**：具備權限的使用者（`SUPER_ADMIN`，或被授予審核權限者）於管理介面看到待審核清單，核准後該工作ID狀態轉為`ACTIVE`，之後即可用該工作ID＋密碼登入。
4. **權限分享**：`SUPER_ADMIN`可將「審核權限」（或未來擴充的其他管理權限）指派給已核准的一般護理師帳號，使其也具備核准他人註冊的能力（對應SRS中「護理站管理者」角色）。
5. **登入態管理**：一般護理師/護理站管理者登入後由後端核發JWT或session token（自建簽發與驗證邏輯，不使用Supabase Auth的user表與機制），token需可設定過期時間並可主動撤銷。

**資料表初步規劃**（供Agent設計Prisma schema參考，實際欄位在動工前應對照SRS 4.1/4.2權限矩陣與稽核軌跡需求補齊）：

- `Nurse`（work_id、password_hash、role、status、created_by、approved_by、approved_at...）
- `NurseRole`（`SUPER_ADMIN` / `NURSE_MANAGER`（對應護理站管理者）/ `NURSE`（一般護理師），可分別設計為enum或獨立權限表）
- 每一次審核/權限指派動作都必須寫入稽核軌跡（誰、何時、對誰、做了什麼），對應《資料庫使用規範》第6條與SRS FR-S02。

**Agent行為規則**：

- 不得將此機制與Supabase Auth混用或部分依賴（例如不可用`supabase.auth`的user表存放work_id）。
- 密碼一律雜湊儲存（如bcrypt/argon2），不得明碼儲存。
- 初始帳密僅用於「首次啟動建立第一個帳號」，建立後應提示（或強制）變更密碼，避免長期使用`.env`中的預設密碼。

### 3.2 裝置綁定與Session Token（依SRS 4.3、4.4完整實作）

依SRS第4.3節九步驟與第4.4節例外情況完整實作，重點提醒：

- Session Token由裝置綁定服務核發，綁定「病人ID＋平板序號＋當次療程時段」三者。
- 三種失效觸發條件（正常下機、手動提前解除、超時自動失效）皆須實作，失效後平板本地暫存資料需清除並回到「等待指派」狀態。
- 同一病人短時間內被誤指派至兩台平板需被偵測並阻擋（見4.4節）。
- 每一次綁定/解除動作皆須寫入稽核軌跡（操作護理師帳號、時間戳、病人ID、平板序號）。

### 3.3 MDM整合（Android Enterprise）——本階段做介面層

**本階段決策**：不串接真實Android Enterprise控制台API（需醫院資訊室提供權限），改為設計一個**可替換的MDM介面層（Interface/Adapter Pattern）**：

- 定義抽象介面（如`MdmProviderPort`），涵蓋「裝置註冊」「解除註冊」「遠端鎖定」「Kiosk模式設定」等方法簽章。
- 本階段實作一個`MockMdmProvider`，行為模擬真實MDM回應（可直接回傳成功、或用本地假資料模擬裝置清單/狀態），讓其餘系統邏輯（護理站管理者操作裝置管理介面、稽核軌跡記錄等）可以在沒有真實MDM的情況下開發與測試。
- 未來取得Android Enterprise Management API權限後，只需新增一個`AndroidEnterpriseProvider`實作同一介面，替換依賴注入的provider即可，不需更動其餘商業邏輯。

**Agent行為規則**：任何呼叫MDM功能之處，一律透過`MdmProviderPort`介面呼叫，不得直接在業務邏輯中寫死Mock或未來廠商SDK的呼叫細節。

### 3.4 AI/LLM整合規範

- 後端AI Proxy Service封裝所有LLM呼叫，前端（病人端/護理端PWA）不持有任何API金鑰（對應FR-S03）。
- 預設模型：`claude-sonnet-4-6`。
- 使用者（護理端管理介面，或系統設定）可切換模型與調整思考程度（reasoning effort/thinking budget），此設定應存於後端設定或資料庫，供AI Proxy Service呼叫時讀取。
- 呼叫外部LLM API前，AI Proxy Service必須執行PII/PHI過濾或去識別化處理，確保病人可識別資訊不直接送出（對應FR-S04、SRS第8章）。
- 本階段所有會呼叫AI的功能（FR-P04、FR-P07、FR-N04、FR-N05、FR-N09等）皆為「非高風險」項目，僅限草擬/生成輔助內容，不做臨床判斷輸出；介面上仍需標示「僅供決策輔助，非診斷結果」等提示文字（若功能性質涉及此需求）。
- FR-N09（SOP/藥品劑量查詢）本階段使用**虛構的SOP文件**作為知識來源（Agent應先生成一份格式合理、內容虛構但結構完整的血液透析相關SOP文件作為測試資料），待未來取得醫院真實SOP文件後再替換來源，查詢邏輯僅限於此文件範圍內回答。

### 3.5 Supabase連線資訊

以下環境變數由使用者自行填入，Agent產生`.env.example`時應保留空值，**不得寫入任何真實金鑰**：

```
SUPABASE_PROJECT_URL=
SUPABASE_SERVICE_ROLE_KEY=
DATABASE_URL=   # Prisma連線字串，格式依Supabase Postgres連線資訊組成
```

目前Supabase專案中沒有任何資料表，Prisma schema與migration由Agent從零開始設計並執行`prisma migrate`建立。

### 3.6 部署環境

本階段部署於使用者Windows本機環境。Agent應提供：

- 本機開發啟動說明（`npm run dev`等指令、必要的Node.js版本需求）
- 若使用Docker Desktop簡化環境一致性，應在README中註明為可選項，不強制
- 不需設計正式雲端部署流程（CI/CD、容器編排等），本階段聚焦本機可執行、可測試

## 4. 三階段迭代規劃

### Iteration 1：基礎建設＋核心綁定完整流程

**目標**：建立可運作的骨架——護理師能登入、能建立排班、能指派裝置給病人、病人平板能收到綁定並顯示對應畫面。此階段完成後應有一條「從護理師登入到病人平板顯示等待/已綁定畫面」的完整可展示流程。

**涵蓋需求**：

| 項目 | 內容 |
|---|---|
| 專案基礎建設 | NestJS專案初始化、Prisma連線Supabase、Repository/DAO抽象層建立（依《資料庫使用規範》第5條，此為後續一切資料操作的必要前提）|
| 護理端身份驗證 | 3.1節所述完整機制：初始最高權限帳號、工作ID註冊、審核流程、權限分享 |
| FR-N01 | 護理站主控台：當日排班建立與裝置指派 |
| 裝置綁定服務 | SRS 4.3節完整九步驟＋4.4節例外情況（重複綁定阻擋、離線例外）|
| FR-P01 | 病人端平板未綁定時之中性等待畫面（無登入介面）|
| FR-S02 | 稽核軌跡（本階段先涵蓋登入/註冊審核、裝置綁定/解除兩類事件，之後每個迭代新增功能時同步擴充）|
| FR-S01（介面層） | MDM抽象介面＋MockMdmProvider（3.3節）|
| 前端骨架 | React病人端PWA、護理端PWA兩個進入點的基礎頁面結構與路由 |

**驗收標準參考**：最高權限帳號可用.env設定值登入 → 核准一位新護理師 → 該護理師建立排班 → 指派平板序號給病人 → 平板端顯示已綁定畫面 → 護理師手動解除綁定 → 平板端資料清除並回到等待畫面 → 全程可在稽核軌跡中查到記錄。

---

### Iteration 2：症狀回報與即時護理站運作

**目標**：讓病人端能實際回報症狀與求助，護理端能即時看到多病人狀態並接收緊急通報，並補上離線情境的韌性設計。

**涵蓋需求**：

| 項目 | 內容 |
|---|---|
| FR-P02 | 已綁定後之結構化透析前症狀問卷（水腫、喘、發燒、出血等）|
| FR-P06 | 求助按鈕，觸發時自動附帶近期症狀趨勢摘要給護理端（此處僅為「摘要呈現」，非風險判斷，符合中風險而非高風險定義）|
| FR-N02 | 多病人即時狀態總覽儀表板 |
| FR-N03 | 緊急通報接收，含病人症狀趨勢背景摘要，依嚴重度分級路由 |
| 即時狀態快取層 | 供多病人總覽與緊急通報使用的即時資料同步機制 |
| 離線韌性 | 病人端離線時症狀回報暫存本地（IndexedDB），恢復連線後同步；求助功能離線時明確提示「目前無法即時通知護理站」|
| 稽核軌跡擴充 | 新增症狀回報、求助觸發、緊急通報處理等事件的稽核記錄 |

**驗收標準參考**：病人端填寫症狀問卷並送出 → 護理端總覽儀表板即時顯示更新 → 病人按下求助按鈕 → 護理端收到通報並看到症狀趨勢摘要 → 模擬離線情境，症狀回報暫存於本地，恢復連線後成功同步且無資料遺失。

---

### Iteration 3：AI輔助內容與護理記錄（僅非高風險項目）

**目標**：接入AI Proxy Service與Anthropic模型，完成所有「生成/草擬輔助」性質但不涉及臨床判斷分級的功能。

**涵蓋需求**：

| 項目 | 內容 |
|---|---|
| AI Proxy Service | 完整版：模型切換、思考程度選擇、PII過濾機制（FR-S03、FR-S04）|
| FR-P04 | AI生成個人化衛教內容（依透析史、衛教完成紀錄），支援繁體中文 |
| FR-P07 | 下機後個人化離院衛教重點＋自適應測驗，標記需加強衛教之知識點 |
| FR-P08 | 情緒/滿意度回饋問卷，長期趨勢異常時建議轉介社工 |
| FR-N04 | 事件當下快速點選式記錄範本＋AI事後草擬敘述初稿供審閱 |
| FR-N05 | 護理記錄自動預填草稿（依病人自報資料），護理師審閱簽核 |
| FR-N07 | 透析適足性（Kt/V、URR）自動計算與趨勢預測 |
| FR-N08 | 心理社會風險趨勢彙總與轉介建議 |
| FR-N09 | SOP/藥品劑量查詢介面，先以虛構SOP文件為知識來源，僅限文件範圍內回答 |
| 稽核軌跡擴充 | 新增所有AI呼叫事件（含使用的模型、是否觸發PII過濾）之稽核記錄，對應SRS第8章 |

**驗收標準參考**：護理端可切換AI模型與思考程度並生效 → 病人端可產生個人化衛教內容 → 護理師可審閱AI草擬的事件記錄初稿並簽核 → SOP查詢僅回答虛構文件範圍內的內容，範圍外提問應明確告知查無相關資料 → 稽核軌跡可查到每一次AI呼叫記錄。

## 5. 每次迭代開始前，Agent應自我檢查（沿用資料庫使用規範精神）

在動工前，Agent應確認：

- [ ] 本次要新增的資料表/欄位是否已對照SRS需求與稽核軌跡欄位需求
- [ ] 是否有任何前端程式碼企圖直接呼叫Supabase SDK（禁止，見資料庫使用規範第2條）
- [ ] 是否有任何邏輯企圖依賴Supabase Auth（禁止，見3.1節與資料庫使用規範第3條）
- [ ] 是否有任何存取控制邏輯寫在RLS/Edge Functions（禁止，見資料庫使用規範第4條）
- [ ] 本次功能是否誤觸及已排除的高風險項目（FR-P03、FR-P05、FR-N06），若有疑慮應先詢問使用者
- [ ] 測試資料是否為虛構合成資料（禁止使用任何接近真實病人的資訊）
- [ ] MDM相關呼叫是否皆透過`MdmProviderPort`介面，未直接寫死Mock細節
