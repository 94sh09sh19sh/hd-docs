### 2.1 Prisma 改用 SQLite 的注意事項

- **`provider` 改為 `sqlite`，移除 `directUrl`。** migration 檔與 PostgreSQL 不相容，`migrations/` 整組重建（既有資料為合成資料，直接捨棄，見《資料庫使用規範》第 15 條）。
- **連線行為必須實測確認。** SQLite 只允許一個寫入者，Prisma 的連線設定（如連線字串上的 `connection_limit`）要驗證實際行為，不要照抄 PostgreSQL 的設定。
- **`PRAGMA` 設定要在連線建立時套用**：`journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout>=5000`、正式環境 `synchronous=FULL`。這四項是《資料庫使用規範》第 7 條的必開項，缺一個都會在多人同時操作時出問題。
- **不得用 `Float` 承載任何臨床數值**（劑量、體重、超過濾量）。改用整數最小單位或 `String`，見《資料庫使用規範》6.2。
- **部分批次操作在 SQLite provider 上的支援與 PostgreSQL 不同**，使用前先確認當前 Prisma 版本的實際支援，不要假設兩邊一樣。
- 既有的六條 schema 約束（不用 enum、不用 JSON 承載關聯資料、不用資料庫專屬預設值、snake_case、稽核欄位不省略、級聯路徑只留一條）**全部保留**。

#### 0919 新增：離線環境下的 Prisma 引擎與遷移指令

**這兩件事在第一次部署時會同時撞上，而且都會毀掉當天的進度。**

**（一）引擎不在 npm 套件裡。** Prisma 的 schema engine 與 query engine 約 40MB，由 `@prisma/engines` 的安裝後腳本另外下載。全程離線的建置測試因此失敗：

```
request to https://binaries.prisma.sh/... failed, reason: getaddrinfo ENOTFOUND binaries.prisma.sh
```

只要 `node_modules` 是在沒有成功下載引擎的情況下產生的（離線安裝、跳過安裝後腳本、或從別處複製而排除了二進位檔），第一次用到 Prisma 指令時就會現場去下載。

**Agent 要做到的三件事**：

1. **建置安裝包時把引擎檔收進包裡**，來源是開發端 `node_modules` 裡已下載好的那份
2. **啟動與遷移時以環境變數指向包內的引擎路徑**，不讓 Prisma 自己去找
3. **把 `prisma` 與 `@prisma/client` 鎖成確定版本**（拿掉版本範圍前綴）。引擎版本與 CLI 版本必須一致，浮動的版本範圍會在某次重新安裝時悄悄換掉其中一邊，而症狀會是一個看起來毫不相干的錯誤

**（二）正式環境不得用開發用的遷移指令。** 目前 `npm run prisma:migrate` 對應的是開發用的那支，它在偵測到「資料庫與遷移歷史對不上」時會提議或直接**重建整個資料庫**。在開發機上那是方便，在正式主機上那是把整個透析中心的紀錄刪掉。

**正式環境一律用「套用既有遷移」的那支**（`prisma:deploy`，已存在）。這一條與《資料庫使用規範》第 18 條、DEP-31 是同一件事，此處不重複。

**驗收方式**：離線建置測試改成「連網只發生在建置安裝包的那台機器上」，院內端從解壓到服務起來不得出現任何一次對外請求。

### 3.4 模型供應者介面層 `LlmProviderPort`（改寫）

**取代 v1.0 的「AI Proxy Service 直接呼叫外部服務商」設計。**

```
LlmProviderPort（抽象介面）
├── MockLlmProvider      ← 預設。回傳固定範例，讓所有 AI 功能可先開發與測試
├── LabApiProvider       ← 過渡期。實驗室 API（院外），僅得送合成資料
└── OnPremiseProvider    ← 正式。院內 DGX Spark 上的推論端點（不由本專案部署，見 DEP-16）
```

介面至少涵蓋：`generate(prompt, options)`、健康檢查、可用模型清單。

**硬性規則**：

1. **任何呼叫語言模型之處，一律透過 `LlmProviderPort`。** 不得在業務邏輯中出現任何一家廠商的 SDK、端點或模型名稱。切換 provider 只能是設定變更。
2. **模型識別字串、端點、金鑰全部由設定提供**，`.env.example` 保留空值。院內推論服務的端點與可用模型未確認（Q-07）、實驗室的可用模型會變動（Q-08），因此**不在程式或文件中寫死任何模型名稱**。0926 起模型名稱只寫在 AI 閘道的 `config.yaml`（實驗室那一份不進 repo，repo 只放範本）。
3. **`LabApiProvider` 必須帶「合成資料檢查」**：當目前 provider 為 `LabApiProvider` 時，帶有真實病人資料標記的請求要被擋下並記錄（FR-S06）。這是程式強制，不是靠人的自律。
4. **去識別化在寫入資料庫之前完成**，不是查詢時才遮蔽（《資料庫使用規範》第 14 條）。
5. **AI 呼叫一律寫入 `ai_invocations`**：provider、模型、參數、耗時、是否觸發去識別化、成功或失敗。提示與輸出留存 12 個月，原始（未去識別化）提示不存。
6. **非即時功能走背景佇列。** 衛教生成、記錄草擬這類「可以等」的工作不得阻擋 HTTP 請求，也不得在資料庫交易中呼叫模型（會佔住 SQLite 唯一的寫入位置）。

**0926：介面之下多一層 AI 閘道**（FR-S13、部署規範第 5 章）。`LlmProviderPort` 不動，`LabApiProvider` 與 `OnPremiseProvider` 的 `LLM_ENDPOINT` 都指向**閘道**，不指向推論端點：

```
LlmProviderPort ── HttpLlmProvider ──▶ AI 閘道（services/ai-gateway，Python ＋ LangChain）
  ├── MockLlmProvider                      │ config.yaml：provider／base_url／model／參數
  ├── LabApiProvider   ─┐                  ├─▶ 實驗室 Ollama（過渡期，經 SSH 通道，只送合成資料）
  └── OnPremiseProvider ┘ 同一份 HTTP 實作 └─▶ 院內正式 GPU API（正式）
```

硬性規則再加四條：

7. **後端不得直接連推論端點**（DEP-41）。Ollama 的位址、模型名稱、LangChain 只准出現在閘道裡
8. **閘道照實驗室規範寫**：`config.yaml` 管 `provider`（`ollama` 或 `openai` 相容介面）、`base_url`、`model`、`temperature`、`num_ctx`；`llm_factory` 集中建立物件。**不提供任何管理模型的端點**（規範：只能呼叫、不能管理）
9. **換正式 GPU API 的驗收標準是「只改 `config.yaml` 與 `LLM_PROVIDER`」**。若做不到，改的是閘道，不是後端
10. **正式環境設定下 `LLM_PROVIDER=lab` 拒絕啟動**（DEP-40），與第 3 條的合成資料檢查並存

**閘道對後端的介面**：`/v1/chat/completions`、`/v1/models`（回傳 `config.yaml` 設定的模型，不列推論端點上的全部模型）、`/health`。後端的 `HttpLlmProvider` 因此一行都不必改；0919 那句「院內伺服器規格與實驗室 API 端點格式確認前這只是暫定」到此定案——**格式由我們自己的閘道決定**，外面怎麼變都關在閘道裡。

### 3.5 臨床資料來源介面層 `ClinicalDataSourcePort`（新增）

對應 FR-S05。院方尚未確定給 API 還是 Excel，因此先定介面。

```
ClinicalDataSourcePort（抽象介面）
├── ManualEntryAdapter   ← 保底。護理師在管理介面手動輸入少數欄位
├── FileImportAdapter    ← 迭代 6 完成。0919 起退為備援（API 不通或院方臨時改給檔案時用）
└── HospitalApiAdapter   ← 0919 起為正式來源。院方確認 Excel 可透過 API 取得
```

**0919 的變動只有一行程式的位置，沒有一行業務邏輯**：這個介面層當初就是為了這一刻設的，換來源只是換一個實作。**這是「先定介面、後補實作」第一次真的被兌現**，值得記下來。

`HospitalApiAdapter` 另外要處理三件檔案匯入沒有的事：

| 要處理的 | 做法 |
|---|---|
| 抓取失敗 | 記錄失敗、下次排程重試。**重試不得造成重複寫入**——以批次編號與資料時間做冪等 |
| 端點暫時不通 | 輪播第三層顯示**上一次成功取得的值**並照常標示資料時間，**不顯示空白**。病人看到舊的值加上舊的時間，比看到空白好 |
| 欄位在院方系統改版時變動 | 沿用 `import_field_mappings` 那套可設定的對應表，不寫死 |

三種來源一律收斂成同一組內部資料表，輪播與儀表板只讀內部資料表，不認來源。

**硬性規則**：

- **全有或全無。** 一批匯入中任何一筆解析失敗或驗證不過，整批不寫入。臨床數值只對一半比完全沒有更危險。
- **來源可追溯**：每筆資料記錄批次編號、來源（檔名或端點）、匯入時間、匯入者。
- **欄位對應可設定**，不寫死在程式裡（Excel 欄位名稱會被人改動）。
- **每筆數值都要有「資料時間」**，呈現時必須一併顯示，避免病人看到三週前的體重以為是今天的。
- 重複匯入要被偵測並擋下，或明確標記覆蓋並保留前一版。

### 3.6 規則引擎（新增）

對應 FR-R01。三項高風險功能的計算**由規則引擎執行，不經語言模型**。

**為什麼自建而不用第三方規則引擎套件**：需求是「能逐條印出來給醫師看、能版本化、能指出這次套用了哪一條的哪一個門檻」。第三方套件的表達能力遠超需求，卻讓可解釋性變差。本專案的規則形態很窄——都是「某個數值或次數超過門檻」，自建一個小型評估器即可。

**資料模型**：

| 資料表 | 用途 |
|---|---|
| `rule_definitions` | 規則的身分：識別字串、名稱、適用需求（FR-P03／P05／N06）、狀態 |
| `rule_versions` | 每一版的門檻值與條件、生效期間、**臨床端書面依據的出處**、建立者 |
| `rule_evaluations` | 每一次執行：對哪位病人、哪次療程、套用哪個規則版本、輸入了哪幾筆歷史資料、結果 |
| `rule_evaluation_reviews` | 誰檢視、是否採納、未採納原因（FR-R06、對應 FR-N13） |

**硬性規則**：

1. 規則版本一經使用即不可修改，要改就新增版本。`rule_evaluations` 永遠指向當時的版本。
2. **未附書面依據出處的規則版本不得標為生效**（FR-R02）。無依據時規則只能在「合成資料模式」下執行。
3. 每一則輸出必須可展開完整依據：引用的歷史資料、規則條目、門檻值、版本編號（FR-R03）。
4. **輸出措辭為事實陳述，不是結論陳述。** 寫「符合 HYPO-01 規則：近三次療程第 2 小時後曾回報頭暈」，不寫「病人有低血壓風險」（FR-R04）。文案不得由模型生成，一律由規則版本內的範本組出。
5. **不自動觸發任何動作**（FR-R05）：不改醫囑、不改處理優先順序、不自動通知醫師。
6. 三項功能各有獨立開關（FR-R07），走 3.7 的功能開關中心。

### 3.7 功能開關中心（新增）

對應 FR-S08。以下每一項都要能獨立開關，切換寫入稽核軌跡並記錄核准依據：

| 開關 | 預設 | 開啟條件 |
|---|---|---|
| `RISK_STRATIFICATION`（FR-P03） | 關 | FR-R08 書面確認＋規則版本有依據 |
| `INTRA_DIALYSIS_ALERT`（FR-P05） | 關 | 同上 |
| `DOSE_REFERENCE`（FR-N06） | 關 | 同上 |
| `AI_FEATURES` | 關 | provider 已設定且健康檢查通過 |
| `REAL_PATIENT_DATA_TO_AI` | 關 | provider 為 `OnPremiseProvider` |
| `CAROUSEL_LAYER_1` / `_2` / `_3` | 關 | 各層內容就緒 |
| `PERF_INDIVIDUAL_L3`（FR-M11） | 關 | 護理部書面同意＋計分規則公告＋觀察期完成 |
| `REWARD_SCORING` | 關 | 觀察期完成（FR-M09） |

**開關的顯示名稱**：功能開關清單在護理端是給人看的，**不得印出上表左欄那些識別字**（FR-S10）。識別字留在後端與稽核紀錄裡。

**硬性規則**：開關為關閉時，相關介面元素**完全不出現**，而不是顯示為停用。後端端點也要一併擋下，不能只靠前端隱藏。

### 3.8 即時通知與常駐總覽螢幕（改寫，取代推播）

**推播服務整條移除。** 現有實作為護理端 SSE 長連線加病人端輪詢，維持不變，並補上兩件事：

1. **FR-N12 常駐總覽螢幕模式**：護理端的一個獨立路由，特徵為不進入休眠、字級放大、可從數公尺外辨讀、新通報有聲音提示、斷線時明顯示警並自動重連。這是 P0——推播沒了以後，這台螢幕是唯一保證通報被看見的地方。
2. **FR-S07 零院外連線盤點**：迭代 3 要跑一次全專案盤點，確認沒有任何程式、套件設定、Service Worker 或前端資源指向院外網域（含字型、CDN、分析工具）。這一項要寫成可重複執行的檢查腳本，而不是一次性人工檢視。

### 3.9 SQLite 連線與運作設定（取代原 Supabase 連線資訊）

`.env` 由使用者填入，Agent 產生 `.env.example` 時保留空值，**不得寫入任何真實金鑰或路徑**：

```
DATABASE_URL=              # Prisma SQLite 連線字串，指向專案目錄外的本機檔案
SUPER_ADMIN_WORK_ID=
SUPER_ADMIN_INITIAL_PASSWORD=
LLM_PROVIDER=mock          # mock / lab / onprem
LLM_ENDPOINT=
LLM_API_KEY=
LLM_MODEL_ID=
BACKUP_DIR=                # 備份輸出目錄，須與資料庫檔案同機
```

**必須做到的事**（《資料庫使用規範》第 7、8 條）：

- 連線建立時套用四項 `PRAGMA`（見 2.1）
- 資料庫檔案放在**專案目錄外**，並確認已被 `.gitignore` 涵蓋
- 後端是唯一的常駐寫入行程；跑資料修補腳本前先停掉後端
- 統計與報表查詢走唯讀連線，不與臨床寫入競爭
- 備份用 SQLite 線上備份機制（`VACUUM INTO`），不用檔案複製；WAL 模式的 `-wal`／`-shm` 與主檔是一組

### 3.10 績效資料分級的實作方式（新增）

對應《資料庫使用規範》第 11 條的 L1～L4。**這不是前端顯示問題，是後端授權問題。**

| 實作要求 | 說明 |
|---|---|
| 分級標在端點上 | 每個統計端點宣告自己回傳的最高級別，由 middleware 依角色與開關判定，不在 service 內部零散判斷 |

### 3.13 導覽版位與功能可設定（FR-S11，0919 新增）

**每個功能在導覽上只會是三種版位之一**：主列、選單、關閉。版位存在資料裡，不寫死在前端。

**硬性規則**：

1. **關閉不只是隱藏連結，後端端點要一併擋下。** 只藏前端等於沒關——知道網址的人直接打得進去
2. **尚未實作的功能與已實作但關閉的功能要分得出來**：前者連路由都不存在，後者回傳「功能未啟用」。兩者在稽核軌跡上是不同的事件
3. **版位改動寫入稽核軌跡**，記錄誰改的、從哪個版位改到哪個版位
4. **預設值寫在共用常數裡，不是寫在資料庫的 seed 裡**。全新環境第一次啟動時要能長出正確的預設版位
5. **「需手持裝置的功能」是一個群組，不是一個一個的開關。** 護理師拿到行動裝置那天要能一次開啟，不是去找七個地方各開一次

**0919 迭代 9 實作結果**：版位存在 `nav_placement_settings`，17 項功能各一列；
守衛 `NavItemGuard` 掛在全域，控制器標上 `@RequireNavItem()` 即納管。
第 2 條實作出來是這樣：**關閉的功能回 404 並寫一筆稽核，未實作的功能連路由都沒有**
——前者在軌跡上查得到，後者查不到，因為它從來沒有被呼叫過。
另外補了一條規格沒寫、但寫程式時才看得出來的限制：**主列滿 7 項時，第 8 項移不進去**，
會被擋下並說「請先把其中一項改到更多選單」。上限若只寫在文件裡，半年後主列就會有 9 項。

### 3.14 選項與題庫改為資料（0919 新增）

對應 SRS 附錄 C。**院方授權先採用 AI 產生的預設內容，並要求可在護理端調整**，因此這些內容必須從程式常數搬進資料表。

| 內容 | 現況 | 要變成 |
|---|---|---|
| 求助處理方式與結果 | **已經是資料**（迭代 5 就做成可設定） | 只需依附錄 C.3／C.4 更新預設內容 |
| 求助類別 | 共用常數 | **資料表**，依附錄 C.2 重新設計，含分派表預設急迫度 |
| 透析前問卷題目 | 共用常數 | **資料表＋版本號**，依附錄 C.5 |
| 衛教題庫 | 共用常數 | **資料表＋版本號＋知識點標記**，依附錄 C.6 |
| 回饋題目 | 共用常數 | **資料表＋版本號**，依附錄 C.7 |

**硬性規則**：

1. **識別碼不可改，顯示文字可改。** 識別碼欄位建立後在介面上不可編輯
2. **停用是唯一的移除方式**，沒有刪除按鈕；既有紀錄仍查得到停用選項的文字
3. **問卷與題庫改動即產生新版本號**，每一份作答記錄它當時的版本。**沒有版本號，改過題目之後的趨勢圖就是把兩種不同的問題畫在同一條線上**
4. **「其他」不可停用、不可刪除**，且選了必須填自由文字
5. **共用常數改為「首次啟動時寫入資料表的預設值」**，之後一律以資料表為準。**不得留下「程式讀常數、介面讀資料表」的雙軌**
6. 每一次增刪改寫入稽核軌跡

**為什麼要連問卷題目都資料化**：附錄 C.1 的兩個目的（對個別病人客製化、用大量資料訓練）都要求選項固定且可比較。**寫在程式裡的題目，每改一次就要重新部署一次；而重新部署的門檻高到最後大家就不改了**——不改的結果不是穩定，是護理部放棄使用這個系統的這一部分。

**0919 迭代 9 實作結果**：

| 硬性規則 | 實作在哪裡 |
|---|---|
| 1、2 | 識別碼是 upsert 的 where 條件，改了就是新增一個；服務層沒有任何 delete |
| 3 | 三組帶版本號的內容各有一張版本表。**改一題＝整份複製成新版本再套上改動，在同一個交易裡完成**——半成品的版本比沒有版本更難查 |
| 4 | `is_other` 欄位。後端擋（回 409）、前端不出現那顆按鈕 |
| 5 | 舊常數只剩一個用途：把迭代 9 之前那一版補寫成第 1 版，讓既有作答還原得出當時的題目。**全新環境不會寫入那一份**，版本號直接從 2 起算——同一個版本字串在任何一套環境裡都要指同一份題目 |
| 6 | 每一次增刪改都要填理由，理由連同新舊值進稽核軌跡 |

**三件規格沒寫、實作時才浮出來的事**：

1. **平板拿著舊版題目送出時要擋下。** 默默拿新版的題目去解讀舊版的答案，比拒收更危險——
   同一個識別碼在兩版之間可能換過選項，對不起來的是資料本身
2. **求助類別的顯示文字要留一份快照在紀錄上。** 識別碼不變、文字可改是對的，
   但事後回頭看那一筆求助時，要知道病人按的是哪一個按鈕上的**哪幾個字**
3. **回饋的冪等要排在題目檢查之前。** 第一次送出之後每月加問的兩題就不再到期，
   拿當下該問的題目去檢查重送的那一份，會把自己的成功回應判成錯誤

### 3.15 已知缺陷：解除綁定在某些條件下找不到入口（0919，**當日修正**）

> **2026-09-19 已於迭代 7 修正。** 三件修法全數完成，次要原因 1 的冪等解除也一併做了；
> 驗收方式那一條已寫進 `verify:iteration7`，不是只寫在手動測試手冊裡。
> 次要原因 2 依原判斷不改程式，改在測試手冊寫明要用不同的瀏覽器設定檔。
> 以下保留缺陷的定位過程——**同一個入口設計再出現時，要認得出它**。


**回報症狀**：在本機測試時，護理端有時無法解除某個綁定。懷疑的情境有很多種——未解除就關閉病人端或護理端、斷網、伺服器重新啟動、在本機綁定多台病人端裝置。

**定位結果：主因只有一個，而且與上面列的情境都無關。**

**解除綁定的唯一入口，掛在「當日排班」清單的每一列上，而那份清單是依排班日期篩選的（預設今天）。** 因此只要一筆有效綁定所屬的排班日期不是畫面上選的那一天，**那一列根本不會出現，自然沒有按鈕可按**。會踏進這個狀況的情境至少三種：

| 情境 | 為什麼綁定還在，但按鈕不在 |
|---|---|
| **跨日** | 大夜班 23:00 起，過了午夜之後，那筆綁定的排班日期是「昨天」，而畫面預設顯示今天 |
| **前幾天測試留下的綁定** | 綁定的有效期上限預設 6 小時，但**逾時掃描沒跑到之前它仍是有效狀態**；而就算過了 6 小時，那幾個小時內只能手動解除，按鈕卻在另一個日期底下 |
| **看得到卻解不掉** | 裝置管理頁面**看得到**某台平板正綁著誰，但那一頁只有遠端鎖定與解除註冊，**沒有解除綁定** |

**連帶的第二個症狀**：那台平板因為還綁著，在指派清單裡被濾掉，於是變成「這台平板不見了」，而畫面上不會說明為什麼。

**次要原因兩個，一併修掉**：

| # | 問題 | 修法 |
|---|---|---|
| 1 | 解除時若該綁定剛好已被逾時掃描結束掉，後端回傳錯誤，畫面顯示成失敗 | **改為冪等**：目標狀態已經達成就回報成功，並說明「這筆綁定已於某時因逾時結束」 |
| 2 | 本機測試時多個病人端分頁共用同一份瀏覽器儲存空間，後佈建的裝置會覆蓋先佈建的，造成「某台平板的綁定沒有任何分頁在輪詢」 | 這是**本機測試環境特有的**，不是正式環境的問題（正式環境一台平板一支 App、各自獨立）。修法是在測試手冊寫明要用不同的瀏覽器設定檔，並在病人端佈建時顯示目前這台的序號，讓人一眼看出被換掉了 |

**修法（三件事，缺一不可）**：

1. **新增一個不依日期的「目前有效綁定」清單**，放在裝置管理頁，每一列都有解除按鈕。後端的清單端點已經存在（`GET /bindings`），目前沒有任何畫面用它
2. **排班清單加上「顯示其他日期的有效綁定」提示**：當有效綁定的排班日期不等於目前選的日期時，在畫面上明白說出來並提供跳過去的連結
3. **裝置指派下拉選單濾掉某台平板時要說明原因**，不是默默不顯示。「這台正綁給某位病人」與「這台已停用」是兩件不同的事

**驗收方式**：建立一筆昨天日期的排班並綁定 → 護理端預設畫面（今天）→ **要能在不改日期的情況下解除它**。這一條寫進迭代驗收腳本，不是只寫在手動測試手冊裡。

### 4.0 為什麼是這個順序

排序不是照需求編號，也不是照「哪個看起來最重要」，而是照四條原則。順序若違反其中任一條，代價都是重工或永久性的損失：

| # | 原則 | 具體後果 |
|---|---|---|
| 1 | **會動到所有既有程式的事情先做** | SQLite 遷移碰到每一個資料存取點。先做新功能再遷移，等於把新功能也重工一遍 |
| 2 | **有時效性的先做** | 成效基準（FR-M07）只能在系統正式啟用前量測。紙本流程一消失，「以前要花多久」永遠補不回來 |
| 3 | **不需要等別人回答的先做** | AI 生成功能用 `MockLlmProvider` 今天就能做完；規則引擎要等臨床端給門檻值。把等待中的項次排前面，只會讓進度停在原地 |
| 4 | **產生資料的先做，吃資料的後做** | 管理儀表板與獎勵制度（新增任務一）需要求助處理紀錄、班表、成效基準累積過一段時間才有東西可看 |

**原則 4 需要特別說明，因為它看起來像是把新增任務一的優先權往後放。** 實際相反：新增任務一的目的是「向長官與外部展現成效」，而**空的儀表板比沒有儀表板更傷**。先把產生資料的三件事（求助處理結果、班表、成效基準）做完並實際跑一段時間，儀表板上線時才有真實數字。因此新增任務一被拆成兩半——產生資料的部分排在迭代 5（很前面），呈現與計分的部分排在最後（0919 重排後為迭代 12）。

**另一個刻意的決定**：三項高風險功能（原本週任務二）排在後面，而非最前面。理由是它同時卡在兩個外部答覆上（法務的分類確認、臨床端的門檻值），而且規則引擎本身不長。把它排在前面，最可能的結果是引擎寫好了、門檻值還沒到，然後空等。排在後面，前面幾個迭代的時間正好是等答覆的時間。**若門檻值與書面確認提早到齊，這個迭代可以隨時往前插隊**——它與其他迭代沒有相依。

**0919 補上第五條原則，而且它的優先權高於前四條**：

| # | 原則 | 具體後果 |
|---|---|---|
| 5 | **要交到使用者手上的事，排在所有新功能之前** | 第一次部署擋在四件事上：解除綁定找不到入口、離線建置失敗、更新會弄壞資料庫、介面不堪用。這四件每一件都不是新功能，但每一件都能讓部署當天停擺。**做完第五個新功能而系統交不出去，等於零** |

> **與原定計畫不同、或規格沒寫到而補上的五處**：
>
> 1. **病人端改走 HTTPS，並與後端同一個來源。** 規格要外殼「憑證信任」，外殼因此只信任院內 CA、只准 HTTPS；
>    但 HTTPS 頁面不准呼叫 HTTP 的後端，而規格沒寫伺服器憑證用在哪裡。做法是病人端的靜態服務以伺服器憑證提供 HTTPS，
>    並把 `/api/` 轉送給 api——外殼只需要信任一張憑證，病人端不必再設 CORS。護理端不動。
> 2. **同一個埠同時接 HTTPS 與 HTTP，HTTP 只留下載頁。** 平板第一次下載 APK 時還不信任院內 CA；不另開埠是因為每個埠都要向資訊室登記（DEP-37）。
> 3. **外殼原始碼從主機上的 clone 帶進 `shell-builder` 的映像檔建置**（compose 的 `additional_contexts`），不是在容器裡 clone。
>    部署金鑰因此不進映像檔；映像檔自己 checkout 釘住的 tag。執行時 `network_mode: none`，以預先下載的相依離線建置——
>    DEP-14「建置時碰不到資料」延伸成「掛著私鑰的時候沒有網路」。
> 4. **外殼回報「是否釘選」，網頁把它併進前景判定。** 解開螢幕固定之後 App 常常還停在前景，只看畫面可不可見會誤報成「固定中」，

> 5. **金鑰的備份、核對與還原做成 `shell-builder` 的指令**（`keys-backup`、`keys-verify`、`keys-restore`），落實 DEP-35 的「每年驗證一次」。

## 5. 每次迭代開始前，Agent 應自我檢查

在動工前確認：

- [ ] 本次要新增的資料表／欄位是否已對照 SRS 需求與稽核軌跡欄位需求
- [ ] 是否有任何前端程式碼企圖直接碰資料庫檔案（禁止，《資料庫使用規範》第 2 條）
- [ ] 存取控制是否寫在後端應用層（禁止依賴檔案權限或前端隱藏，第 4 條）
- [ ] 是否在業務邏輯中直接寫 SQL 或 SQLite 方言（改走 Repository／ORM 層，第 5 條）
- [ ] 新增的臨床數值欄位是否誤用浮點數（一律整數最小單位或字串，6.2）
- [ ] 是否新增了第二個會寫入資料庫的常駐行程（不允許，第 7 條）
- [ ] 是否有任何相依指向院外網域（FR-S07，跑檢查腳本）
- [ ] 呼叫語言模型是否一律透過 `LlmProviderPort`（3.4）
- [ ] 呼叫 MDM 是否一律透過 `MdmProviderPort`（3.3）
- [ ] 取用院方臨床數值是否一律透過 `ClinicalDataSourcePort`（3.5）
- [ ] 本次功能是否觸及 1.4 的有條件納入項；若是，開關是否預設關閉
- [ ] 本次功能是否會產生 L3 個人層級績效資料；若是，是否已擋在 `PERF_INDIVIDUAL_L3` 之後
- [ ] 本次的輸出是否可能離開院內；若是，是否走對外報表模組（FR-X01）

### 8.1 三支盤點腳本的共同設計

| 決定 | 為什麼 |
|---|---|
| **一律可重複執行，不改任何檔案** | 它們是量尺，不是修理工具。會自動改東西的工具，出錯時沒有人看得出它改了什麼 |
| **都支援 `--json`** | 要接進驗收腳本或 CI 時不必解析人看的輸出 |
| **有發現就回傳非零狀態** | 才擋得住「跑了但沒人看輸出」 |
| **每一筆都附「要改成什麼」** | 只說哪裡錯不夠——這幾類問題的正確做法都不只一種寫法，要講清楚選哪一種 |

### 8.2 `check:ui` 的一個關鍵界線

**程式碼註解不算違規。** FR-S10 管的是「使用者看得到的字」，不是原始碼——
需求編號留在註解與文件裡是對的，那是可追溯性的來源。
因此這支腳本**先把註解剝掉再比對**，而且是用一個認得字串與樣板字串的狀態機剝，
不是 `replace(/\/\/.*$/)`——後者會把網址裡的 `//` 當成註解開頭，
把整行後半段吃掉，於是真正的違規反而掃不到。

**0919 首次執行的結果：22 筆，分成 5 類。** 這 22 筆就是迭代 9 那一項工作的清單。

**0919 迭代 9 完成後：0 筆。** 基準線同步降到 0（`verify:iteration8` 裡那條棘輪也改了），
之後只能往下，不能往上。

**唯一的例外寫在腳本裡，而且逐行列出。** 「系統管理 → 內容與選項」那一頁看得到識別碼，
這是刻意的：依附錄 C.0 第 1 條「識別碼不可改，顯示文字可改」，
**護理長看不到識別碼，就不知道自己改的是文字（安全）還是新增了一個選項（會讓歷史資料斷開）**。
例外一律逐行列出並寫明理由——不開放整個檔案，也不接受「加個註解就跳過」那種寫法。

### 8.3 `check:offline` 首次執行就抓到一個真的問題

`prisma` 與 `@prisma/client` 宣告的是 `^6.5.0`，**實際安裝到的是 6.19.3**。
浮動的版本範圍讓引擎與 CLI 有機會在某次重新安裝後對不起來，而症狀會是一個看起來毫不相干的錯誤。

**0919 已於迭代 7 鎖成 `6.19.3`**（DEP-30 第 3 點），同一支腳本另外多了兩項檢查：
開發用的遷移指令有沒有加上防呆、更新流程有沒有可執行的入口。目前 0 項阻擋。

### 8.4 還沒有工具、要靠人的四件事

**寫出來是為了不要假裝腳本涵蓋了全部。**

| 要驗什麼 | 為什麼腳本驗不到 | 怎麼辦 |
|---|---|---|
| 對比度 | 要實際算色值，而顏色來自 CSS 自訂屬性與繼承 | 在瀏覽器的開發者工具裡量 |
| 觸控目標尺寸 | 要實際繪製才知道最終尺寸 | 同上，或用瀏覽器自動化量測 |
