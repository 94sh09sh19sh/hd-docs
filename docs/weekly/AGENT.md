# 文件維護作業指示（agent 用）

給接手維護 `docs/` 的 AI agent。人用的完整說明在 [HOWTO.md](HOWTO.md)，本頁只寫可執行的規則。

---

## 前提

- 文件真本在 `docs/`；對外是 **GitHub Pages 文件站**，由公開鏡像 repo `94sh09sh19sh/hd-docs` 建出來。
  鏡像是**單向的**（repo → 鏡像 → 站台），不要以站上的內容為準。
- `.docs-mirror/`（鏡像的本機 clone）與 `.docs-preview/`（預覽暫存）是產物，不進版控，不要手動編輯。
- 同步是**整份覆蓋**。有人若曾直接在鏡像 repo 上編輯，那些字會被蓋掉；發現這種情形要先問。
- **改完 docs 直接推，不必每次問。** 使用者已於 2026-09-10 常態授權：
  動過 `docs/` 底下任何已鏡像的檔案，就接著跑 `npm run docs:sync`，推完把清單回報給使用者。
  三種情形例外，仍要先問：
  - 鏡像 repo 上疑似有人手動編輯過（同步是整份覆蓋，會蓋掉那些字）
  - 這次會建立**凍結版**（定版日的 `docs:freeze`），凍下去改不回來
  - 推送出錯，或清單裡出現預期外的檔案
- **建立鏡像 repo 本身要先問**（那是把內容變成公開網址的動作）。之後的例行同步照上面的授權自動跑。
- 需要登入網頁的一次性設定（鏡像 repo 的 Settings → Pages 選 `gh-pages` 分支）**agent 一律不做**，
  交給使用者，步驟寫在 HOWTO.md「一次性設定」。

## 改完文件，回頭檢查這兩份指南

使用者於 2026-09-12 指示：**動過 `docs/` 底下任何文件，收尾前都要判斷 HOWTO.md 與本頁要不要跟著改。**
兩份指南是流程的真本，文件結構一變、指南沒跟上，下一個接手的人就會照過期的規則做事。

判斷方式——出現下列任一情形就要改指南，兩份都要看（人用的講為什麼，agent 用的講怎麼做）：

| 這次的改動 | 要同步的地方 |
|---|---|
| 新增或刪掉一份文件 | 本頁「目錄結構」樹、「目錄職責」表、「首頁硬性上限」的列序清單；HOWTO 的列序清單；`docs-site/mkdocs.yml` 的 `nav` |
| 首頁兩張表的列序或欄位變了 | 兩份指南的列序清單與 `nav`，逐字對齊首頁現況 |
| 定版、凍結、修訂中標記的規則變了 | 本頁「定版規則」與「週中改文件」；HOWTO 的流程圖與兩段式說明 |
| 新增或改掉一個 npm 指令 | 兩份指南所有出現該指令的地方，含「驗收」段 |
| 冒出新的踩坑或誤用 | HOWTO「踩過的坑」表補一列；若 agent 會踩，本頁「其他硬性規則」也補 |
| 使用者給了新的常態授權或禁令 | 本頁對應段落，寫上日期與範圍 |

判斷完沒有要改，就不必動——但要在回報裡明講「維護指南無需更動」，讓使用者知道這一步做過了。
指南本身沒有「版本歷程」表，改了不補、不出凍結版（見下方「版本歷程的適用範圍」），
但改完一樣要 `npm run docs:sync` 把鏡像推上去。

## git：commit 自動，push 等指令

使用者於 2026-09-10 常態授權：

- **`docs/` 底下的檔案改完就直接 commit，不必問。** 一件事做完 commit 一次，不要累積成一大包。
  訊息用台灣繁體中文，句首照既有慣例寫 `docs: `。
- **私有 repo 的 `git push` 一律等使用者開口。** 沒有例外，即使 commit 已經堆了好幾筆。
- 這與鏡像的推送是兩件獨立的事：`docs:sync` 推的是**鏡像 repo**，照舊改完就推，不受私有 repo 的 push 規則影響。
- `docs/` 以外的檔案（`apps/`、`scripts/`、設定檔）不在這條授權範圍內，照原本的規矩問過再 commit。

## 定版規則

每週三開會日定一次版。站台有兩種網址：

- **現行版** `…/hd-docs/latest/`：永遠指向最新，首頁只掛這個，網址不變
- **凍結版** `…/hd-docs/0916/`：該週定版的樣子，建立後不再更新

硬性規則：

- **只有那週真的改過的文件才補版本歷程。** 沒改就不補，首頁的日期停在上一次
- **週中改文件不算定版。** 一週分兩段：週中隨時改隨時推，週三才收成定版。
  週中改過的文件，首頁該列定版欄標成 `MMDD · 修訂中`（MMDD 是上一次定版的週次），
  頂部標成 `**本週定版**：0909｜**0916 修訂中**`。定版日再把標記拿掉、日期換成新週次
- **週中禁止補版本歷程、禁止跑 `npm run docs:freeze`。** 一旦打了週次 tag，那一週就定型了，
  凍結版建立後不再更新，救不回來
- **定版日的順序是先 `docs:sync` 再 `docs:freeze`**，不可顛倒。tag 釘住的是鏡像上當下的 commit，
  內容沒先推上去就凍，凍到的是舊內容。（HackMD 時代是相反的，不要照舊記憶做事）
- 凍結版的來源是「版本歷程」表：文件末尾那張表新增一列，`docs:freeze` 才掃得到
- 版本歷程第一欄**只寫四位數週次**，絕不寫網址；同步時 `docs-mirror.mjs` 會自動換成該週凍結版的連結。
  尚未建立凍結版的週次維持純文字，不留死連結
- 凍結版的網址由週次推導（`…/hd-docs/<週次>/<該篇路徑>/`），不需要任何對應表
- 已建立的凍結版視為既成紀錄，不回頭改。要修正就在新的一週寫明
- **凍結版只存在於鏡像 repo**：`main` 上的週次 tag（內容來源）＋ `gh-pages` 裡建好的 `/<週次>/`。
  **本地 repo 只留現行版，不得再收一份舊版目錄**——同一份內容擺兩處，遲早有人改了其中一處，
  之後就分不出哪一份才是當初定版的。要看某一版開站上的 `/<週次>/`；要原始檔就從鏡像的 tag 取：
  `git -C .docs-mirror show <週次>:docs/<路徑>`
- 換站之前的 0909 是特例：它原本只在舊站上，已用 `scripts/snapshot-import.mjs` 取回當時真正
  發佈出去的那一份，推成 `snapshot/0909` 分支加 `0909` tag。取回的檔案**不留在本地 repo**，
  工具的產出落在 `.docs-snapshots/`（已 gitignore），推完即可刪
- **舊週次一律不得用 `docs:freeze` 補建。** 那支會把鏡像 main（今天的內容）打上舊週次，
  生出掛著舊週次、裝著今日內容的贗品。也不要從 git 歷史重建：定版制度是 0910 才建立的，
  當天的 commit 樹未必等於那週發佈出去的內容。正確做法只有一條——匯入該週發佈出去的版本

### 版本歷程的適用範圍

有「版本歷程」表的只有**需求文件（六份）、架構圖、進度報告（兩份）、參考文件（兩份）、`notes/` 的單篇方案評估、設計基準與修正紀錄（三份）、測試手冊（主手冊與七本分冊）**這二十二份，改了就要補一列。
以下五種沒有這張表，改了**不補、也不出凍結版**，但一樣要同步：

- `index.md`（狀態靠「本週定版」與修訂中標記表達）
- `weekly/YYYY-MM-DD.md`（週報本身就是某一週的紀錄）
- `weekly/archive.md`、`weekly/_template.md`
- `weekly/HOWTO.md`、`weekly/AGENT.md`（維護指南，不進定版週期）

### 還沒有第一次定版的新文件

首頁定版欄先寫 `新增 · 修訂中`。到它第一次定版的那一週，才換成該週次，
並在文末版本歷程寫下第一列（異動摘要寫「首次定版。<建立時做了什麼>」）。

## 週中改文件

不是定版日時（週四到週二）改 `docs/` 底下任何文件，只做這三件事：

1. 改文件內容。
2. `docs/index.md`：頂部標成 `**本週定版**：<上次週次>｜**<本週週次> 修訂中**`；
   兩張表格中**這次動過的那幾列**，定版欄改成 `<上次週次> · 修訂中`，沒動過的不要碰。
3. `npm run docs:sync`，推完把清單回報給使用者。不確定會推到什麼時，先跑
   `npm run docs:sync -- --dry-run` 看清單。

**不要補版本歷程，不要跑 `docs:freeze`。** 這兩件事只在定版日做。

### 週中可以先開週報草稿

進度多到週三一次補寫會漏，就週中先把該週週報建起來，當草稿維護（0916 那篇就是 0910 起這樣走的）：

1. 檔名照樣用**該週開會日（星期三）**的 ISO 日期，不是動筆那天。
2. 檔頭狀態寫成「進行中（YYYY-MM-DD 週中草稿，MMDD 定版時收尾）」，
   「對應 commit」可以先寫到目前的迭代並註明定版前會再補。
3. `docs-site/mkdocs.yml` 的 `nav`「每週紀錄」底下就先加那一列，否則站上側欄看不到。
4. `docs/index.md`「最近三週」該段標題後面加 ` · 修訂中`，定版日拿掉。
5. 一樣**不補版本歷程、不跑 `docs:freeze`**，推送照跑。

定版日剩下的事就只有收尾：拿掉修訂中、改狀態、補版本歷程、sync、freeze。

## 新增一篇週報

1. `cp docs/weekly/_template.md docs/weekly/<該週開會日（星期三）的 ISO 日期>.md`，填內容。
   第一行必須是 `# MMDD 週報 — <標題>`，它會成為站上那一頁的標題。
2. `docs/index.md` 改三處：
   - 開頭改回單一週次 `**本週定版**：MMDD`，把「｜MMDD 修訂中」整段拿掉
   - 「我要找…」與「需求文件」兩張表的「本週定版」欄，**只改這週動過的那幾列**，
     把 `MMDD · 修訂中` 換成新的週次；沒動過的維持原樣
   - 「最近三週」最上方（`<!-- 新的一週… -->` 註解上方）插入：
     ```markdown
     ### [MMDD — <標題>](weekly/<檔名>)

     進度：

     - <三到五條>
     ```
   - 插完若超過三段，刪掉最舊的一段，並在 `docs/weekly/archive.md` 表格最上方補一列
3. `docs-site/mkdocs.yml` 的 `nav`「每週紀錄」底下最上方加一列：
   `- MMDD — <標題>: weekly/<檔名>`。
4. 這週改過的每份文件，末尾「版本歷程」表最上方加一列 `| MMDD | YYYY-MM-DD | <異動摘要> |`。
5. `npm run docs:sync -- --dry-run`，把清單交給使用者確認。
6. 使用者同意後 `npm run docs:sync`。
7. `npm run docs:freeze`，確認新週次都建立到。**定版日這一步要先問使用者**——凍下去不再更新。
8. 再跑一次 `npm run docs:sync`：版本歷程第一欄的新週次，要等該週凍結版存在，同步時才換得成連結。
9. commit（訊息 `docs: 週報 MMDD`）。**私有 repo 的 git push 要等使用者指令**（見上方 git 規則）。

## 新增其他文件

同上，差別只在放置目錄，並在 `docs/index.md` 的「我要找…」或「需求文件」表格加一列。
**那一列要按上述列序插進對的位置，不要一律加在表尾**；放哪一格拿不準就先問使用者。
`docs-site/mkdocs.yml` 的 `nav` 也要對應加一列。新文件末尾要一併加上「版本歷程」表，
第一次定版前定版欄寫 `新增 · 修訂中`（見上方「還沒有第一次定版的新文件」）。

最近一次的實例是 0912 的《部署規範》（`requirements/deployment-spec.md`）：
插在實作規格書之後、清冊之前，角色欄寫「優先權等同實作規格書」，前五份需求文件同步改掉部署相關敘述。
**新增一份需求文件會連帶動到首頁列序，所以本頁、HOWTO.md 與 `nav` 的列序清單也要跟著補。**

## 測試手冊的分冊

`docs/testing/` 是一本主手冊加迭代分冊（0912 起）。主手冊放共用的部分：環境建置、兩條主線、
離線韌性、迭代 1／2 的細節功能、收工、API 附錄、疑難排解、重置、資料庫附錄，
最後一章是分冊索引。迭代 3 之後每個迭代一本 `iteration-N.md`。

硬性規則：

- **分冊不進首頁。** 「我要找…」表永遠只有「完整手動測試手冊」那一列，分冊從主手冊 §13 的索引進去。
  首頁只放連結與一句話，四個分冊各占一列會把入口變成目錄（見下方「首頁硬性上限」）。
  那一列的說明要寫出目前是幾本分冊、共幾項。
- 分冊要在 `docs-site/mkdocs.yml` 的 `nav`「手動測試」底下補一列。
- 分冊末尾要有「版本歷程」表（見上方「版本歷程的適用範圍」），第一次定版前表內沒有列是正常的。
- **項次編號跨冊不重複**：主手冊用 `a`–`k`，迭代 3 用 `l`、`m`，迭代 4 用 `n`，迭代 5 用 `o`，迭代 6 用 `p`，迭代 7 用 `q`，迭代 8 用 `r`，迭代 9 用 `s`，迭代 10 用 `t`。

## 首頁硬性上限

`docs/index.md` 在 2026-09-10 從 100 行砍到 51 行。它是讀者的入口，不是索引全集。
**行數不是判準**（新增文件與換週都會讓它長短變動），下面幾條才是：

- **只有五塊**：現在到哪／最近三週／我要找…／需求文件／其他文件。**不准新增第六塊**
  （第五塊「其他文件」由使用者於 2026-09-19 指示新增，掛 `docs/notes/` 底下的單篇方案評估。
  它刻意排在需求文件之後、維護連結之前，且表格只有三欄、每份一句話——**不准長成第三張索引表**）
- **兩張表的列序照讀者的思考順序固定（2026-09-10 定），不准重排，新增也要插進對的位置**：
  - 「我要找…」：臨床端進度報告 → 技術端進度報告 → 架構圖 → 資料字典 →
    這套系統是用什麼蓋的 → 完整手動測試手冊
  - 「其他文件」：平板管控：免 MDM 的全院內方案 → 介面設計基準 → 迭代 9.1 修正清單 → 部署演練紀錄。新增的排在表尾即可，這塊沒有閱讀動線
  - 「需求文件」：FDE 數位化評估報告 → SRS → 資料庫使用規範 → 實作規格書 → 部署規範 →
    尚待確認事項清冊。
    **前五份是閱讀順序，不是優先權順序**：從為什麼要做，讀到做什麼、資料怎麼管、怎麼實作，
    最後是怎麼部署。衝突時仍以實作規格書為準（部署規範與資料庫使用規範優先權等同它），
    優先權只寫在「角色」欄，不要改成依優先權排，也不要在表格外另加一段講順序
- 「最近三週」**最多三段**，每段三到五條，更早的一律進 `weekly/archive.md`
- 細節一律留在該文件裡，首頁只放連結與一句話
- 目錄結構、維護說明、踩坑紀錄**不准搬回首頁**，它們屬於本頁與 HOWTO.md
- 維護文件的連結只准出現在首頁最後一行

使用者要求在首頁加東西而會突破上述任一條時，先說明會破壞什麼，再問要不要改放別處。

## 舊站（HackMD）

2026-09-17 換站之後，HackMD 不進每週流程，但工具與權杖都留著（使用者 2026-09-17 指示）：

- **只有使用者明確指示時才同步舊站。** 例行的 `docs:sync` 只推新站，不要順手推 HackMD
- 指令：`npm run docs:hackmd` 產生 `.hackmd-build/`；`npm run docs:hackmd:push` 推送
  （`-- --dry-run` 先看清單）；`npm run docs:hackmd:freeze` 把新週次登記進 `docs/hackmd-map.json`
- **`docs:hackmd:push` 收到 `429 quota_exceeded` 就停手，不要重試。** 那是免費方案每月 400 次的
  月額度用完了（訊息裡的 `Resets at` 是下個月一日），重試只會再吃掉配額還是失敗。
  要據實回報「repo 已改、舊站尚未更新」，由使用者決定怎麼處理
- **交給使用者手動貼上舊站的內容，一律取自 `.hackmd-build/`，絕不能給 `docs/` 原始檔。**
  兩者只差連結改寫與 front matter，肉眼難辨，貼錯也不會有錯誤訊息，但內部連結會全部變成死連結。
  分辨法：**build 版第一行必為 `---`**，原始檔第一行必為 `#`。複製到剪貼簿時：

  ```powershell
  Get-Content -Raw -Encoding UTF8 .hackmd-build\<路徑> | Set-Clipboard
  ```

  省略 `-Encoding UTF8` 會依系統預設編碼頁（本機為 big5）讀取，中文全部變亂碼。
- 0909 的凍結版留在舊站；0916 那批因額度用盡未推成功，新站的凍結版自 0916 起算
- `docs/hackmd-map.json` **不要刪**：舊站的上述指令要用，`scripts/snapshot-import.mjs` 也靠它的
  `snapshots` 查出某一週在舊站有哪些凍結版 note 可以取回。它不會上新站（同步時略過 `.json`）

## 其他硬性規則

- **連結一律用相對路徑**寫在 `docs/` 裡。站台會自己處理，不要把 `https://…github.io/…`
  直接寫進 `docs/` 的內文（版本歷程那一欄由腳本代勞，原始檔只寫週次數字）。
- **根目錄 `README.md` 不上站，`docs/` 裡也不要連它、不要提它。**
  它含環境變數清單、資料庫連線設定與內部取捨，站台網址等同公開連結，不適合放這些內容。
  同步腳本只複製 `docs/` 與 `docs-site/`，這是結構上的保證；正確做法仍是一開始就不要寫這個連結。
  需要指路時寫「見專案 repo」即可，不要放路徑。
- **鏡像 repo 是公開的**。任何寫進 `docs/` 的東西都等同公開，真實病人資料、權杖、內網主機名稱
  一律不得出現。這條比 HackMD 時代更要緊：公開 repo 有完整的歷史紀錄，刪掉也留在 commit 裡。
- **介面設計基準有兩份，改了要一起改**：`docs/notes/uiux-design-baseline.md`（人用，理由）與 `.claude/skills/hd-uiux/`（agent 用，可執行）。
  使用者於 2026-09-19 指示介面設計不是一次性修正，日後所有介面工作都要依它做；**兩份漂移就等於沒有基準**。
  skill 不在 `docs/` 底下，因此不上站、不進定版週期，但它是 agent 實際會讀的那一份。
- **`HACKMD_API_TOKEN` 不准出現在 `.env` 以外的任何地方**，包含文件、commit、終端機輸出、
  給使用者的訊息。要驗證權杖只跑 `npm run docs:hackmd:push -- --dry-run`，不要把權杖印出來。
- 底線開頭的檔案（`_template.md`）不會上站，是刻意的。
- 改了 `docs/` 底下任何檔案，**只改 repo 不算完成**：要重新同步，該補版本歷程的就補
  （哪些要補見「版本歷程的適用範圍」），並回頭確認這兩份維護指南要不要跟著改。
- 已發佈的週報與凍結版視為既成紀錄。要修正就在新的一週寫明，不要靜默改寫歷史。

## 驗收

```bash
npm run docs:sync -- --dry-run   # 列出會推什麼，不送出
npm run docs:freeze -- --dry-run # 應回報「沒有新的定版要建立」
git status --short               # 應只有預期中的檔案

# 站台真的建得起來（本機，需先 pip install -r docs-site/requirements.txt）
python -m mkdocs build -f .docs-preview/mkdocs.yml

# 這次動過的文件，維護指南是否需要同步？改動屬於「改完文件，回頭檢查這兩份指南」表裡任一列就要改
# 首頁列序、兩份指南的列序清單、mkdocs.yml 的 nav，三處是否逐字一致
grep -n '](requirements/\|](reports/\|](reference/\|](testing/' docs/index.md
```

> **這一段只驗文件。** 專案另有五支與文件無關的盤點腳本（`check:egress`、`check:ui`、
> `check:ui:design`、`check:offline`、`check:migration`，可用 `npm run check:all` 一次跑完；
> 0919 起它們**全部都會跑完再一起算帳**，不會因為其中一支回非零就停住）。
> 它們不屬於文件維護流程，**不要把它們加進上面的驗收段**；
> 它們的用途與輸出寫在《[實作規格書](../requirements/implementation-spec.md)》第 8 章，
> 介面那一支另見《[介面設計基準](../notes/uiux-design-baseline.md)》第 6 節。

相對連結是否還指得到檔案，可用：

```bash
cd docs && for f in $(find . -name '*.md'); do d=$(dirname "$f"); \
  grep -o '](\([^)]*\))' "$f" | sed 's/.*](//;s/)$//' | while read -r l; do \
    case "$l" in http*|\#*) continue;; esac; t="${l%%#*}"; [ -z "$t" ] && continue; \
    [ -e "$d/$t" ] || echo "MISS $f -> $l"; done; done
```

（`weekly/YYYY-MM-DD.md` 是說明文字裡的佔位字串，出現在結果裡屬正常。）
