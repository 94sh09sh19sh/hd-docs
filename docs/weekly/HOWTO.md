# 每週紀錄維護流程（人用）

這頁寫給隔了一週回來、細節已經忘光的自己。從「這週做完了」到「別人點得到」，全部步驟在這裡。
給 AI agent 執行的精簡版在 [AGENT.md](AGENT.md)。

---

## 一次講完的全貌

文件的**真本在 repo**（`docs/`），對外看得到的是 **GitHub Pages 文件站**。
所有內容都先改 repo，再同步過去，不要反過來去改鏡像 repo 或站台——同步是整份覆蓋。

```
週中  改 docs/<文件>.md
      首頁那幾列標「0909 · 修訂中」
        ↓  npm run docs:preview        本機先看長什麼樣（可略）
        ↓  npm run docs:sync           讀者看得到進行中的內容
        ↓
週三  寫 docs/weekly/2026-09-16.md
      首頁拿掉修訂中、日期換 0916、最近三週插一段
      改過的文件補版本歷程一列        ← 只有這天做
        ↓  npm run docs:sync           先把內容推上去
        ↓  npm run docs:freeze          再凍結，建立該週凍結版
        ↓
GitHub Pages                            別人看到的
```

**順序不能顛倒：先 `docs:sync` 再 `docs:freeze`。** 凍結版是在鏡像上打一個週次 tag，
tag 釘住的是當下那個 commit——內容沒先推上去，凍到的就是舊的。
（HackMD 時代是相反的，別照舊記憶做事；腳本會擋，但別靠它擋。）

## 三個網址，各自負責一件事

| | 網址 | 內容 | 誰在用 |
|---|---|---|---|
| **現行版** | `…/hd-docs/latest/` | 永遠是最新的 | 首頁的連結、你給別人的連結 |
| **凍結版** | `…/hd-docs/0916/` | 0916 那天定版的樣子，之後不再變 | 回頭對帳「當初談定的是哪一版」 |
| **鏡像 repo** | `github.com/94sh09sh19sh/hd-docs` | 站台的原始內容 | 只有工具在用，人不必進去 |

站台右上角有**版本下拉選單**，讀者可以自己在各週定版之間切換。
凍結版只會往回指：它凍的是當時的內容，當時還不存在的後續版本，它的版本歷程裡自然沒有那一列。
要從舊版跳到新版，用那個選單。

> **凍結版住在鏡像 repo，本地只留現行版。**
>
> 每一版 = 鏡像 `main` 上的一個週次 tag（內容來源）＋ `gh-pages` 裡建好的 `/<週次>/`。
> **本地 repo 不再收任何舊版目錄**——同一份內容擺兩處，遲早有人改了其中一處，
> 之後就分不出哪一份才是當初定版的那一份。
>
> 要看某一版，開站上的 `/<週次>/`；要原始檔，從鏡像的 tag 取：
> `git -C .docs-mirror show <週次>:docs/<路徑>`。
首頁只掛現行版，所以**你給出去的連結永遠不會過期**，也不必每週重發。

**公開範圍**：鏡像 repo 是 public、站台是公開網址，知道網址就看得到（跟以前的 HackMD 自訂網址一樣）。
`robots.txt` 擋掉搜尋引擎收錄。程式碼、`README.md`、`.env` 都留在私有 repo，
同步腳本只複製 `docs/` 與 `docs-site/` 兩個目錄，這條界線是結構上的，不是靠記得。

## 一次性設定

做過就不必再做。

1. **鏡像 repo**（只做一次）：

   ```bash
   gh repo create hd-docs --public --description "血液透析平板照護輔助系統 文件鏡像"
   npm run docs:sync
   ```

   第一次 `docs:sync` 會把鏡像 clone 到 `.docs-mirror/`（已 gitignore），之後每次沿用。

2. **GitHub Pages 來源**：第一次 `docs:freeze` 或 `docs:sync` 跑完，Actions 會建出 `gh-pages` 分支。
   到鏡像 repo 的 Settings → Pages，Source 選 `Deploy from a branch`、分支選 `gh-pages` / `(root)`。
   這一步只做一次，之後都自動。

3. **本機預覽用的工具**（可略，不預覽就不必裝）：

   ```bash
   pip install -r docs-site/requirements.txt
   ```

**新站不需要任何 API 權杖**，同步走的是 `git push`，沒有每月額度這回事。
`.env` 裡的 `HACKMD_API_TOKEN` 刻意留著——舊站還在，你開口時還要用它同步（見下一段）。

## 舊站（HackMD）

換到新站之後，HackMD 不再是每週流程的一部分，但**沒有廢掉**：

| | |
|---|---|
| 什麼時候同步 | **只有你明確開口時**。每週例行流程只推新站 |
| 指令 | `npm run docs:hackmd` 產生 `.hackmd-build/` → `npm run docs:hackmd:push` 推上去（加 `-- --dry-run` 先看清單）。要出凍結版再跑 `npm run docs:hackmd:freeze` |
| 權杖 | `HACKMD_API_TOKEN` 留在 `.env`，不要刪，也不要貼進任何文件、截圖或訊息 |
| 額度 | 免費方案每月 400 次，**目前已用盡**，訊息裡寫 `Resets at 2026-10-01`。收到 `429 quota_exceeded` 就停手，重試只會再吃掉配額 |
| 凍結版 | 0909 那批已取回並發佈到新站（只存在於鏡像 repo，本地不留），版本歷程一律指向新站，**不再依賴舊站**；0916 那批因額度用盡沒有推成功，不影響新站 |

手貼舊站時**一律貼 `.hackmd-build/` 底下的檔案，不要貼 `docs/` 原始檔**——兩者肉眼難辨，
貼錯不會有任何錯誤訊息，但那篇的內部連結會全部變成死連結。
分辨法：build 版第一行一定是 `---`，原始檔第一行一定是 `#`。

## 每週怎麼走

分兩段：**週中隨時改、週三收成定版**。差別只有一件事——版本歷程與 `docs:freeze` 只在定版日做。

### 週中：改到哪推到哪

1. 改 `docs/` 底下的文件。
2. 首頁標上修訂中，讓讀者知道這幾份正在動：
   - 頂部改成 `**本週定版**：0909｜**0916 修訂中**`
   - 表格裡**動過的那幾列**，定版欄改成 `0909 · 修訂中`（沒動的維持原樣）。
     全新的文件還沒有過第一次定版，那一欄先寫 `新增 · 修訂中`
3. 進度多的時候，該週週報可以**週中就先建起來當草稿維護**，不必等到週三一次補寫。
   檔名照樣用該週的星期三，檔頭狀態寫「進行中（…週中草稿，MMDD 定版時收尾）」，
   首頁「最近三週」那段標題後面加 ` · 修訂中`。**版本歷程與 `docs:freeze` 一樣不能碰。**
4. `npm run docs:sync`

> 交給 agent 改的話，這一步它會自己跑完再回報清單，不會停下來等你點頭（2026-09-10 起）。
> 定版日建立凍結版那次仍會先問，因為凍下去改不回來。

想先看長什麼樣就跑 `npm run docs:preview`，瀏覽器開 <http://127.0.0.1:8000>，存檔會自動重整，
按 Ctrl+C 結束。預覽完全在本機，不會推任何東西出去。

讀者這時點進去看到的是進行中的內容，但表格明白標著修訂中，不會被日期誤導。

> ⚠️ **週中絕對不要補版本歷程那一列，也不要跑 `npm run docs:freeze`。**
> 一旦打了 tag，那一週的凍結版就定型了，而凍結版建立後不再更新，救不回來。
> 定版是週三的事。

### 週三：收成定版

#### 1. 開一份新的週報

```bash
cp docs/weekly/_template.md docs/weekly/2026-09-16.md
```

檔名用**該週開會日（星期三）的 ISO 日期**。開會日就是報告日，這樣檔案列表的排序就是時間序。
內容照範本填。第一行 `# MMDD 週報 — 一句話標題` 很重要，它會成為站上那一頁的標題。

#### 2. 首頁收尾

開啟 `docs/index.md`：

1. 頂部改回單一週次：`**本週定版**：0916`，把「修訂中」整段拿掉
2. 兩張表格：這週動過的那幾列，`0909 · 修訂中` 換成 `0916`；沒動過的維持原樣
3. 「最近三週」最上方插入一段（新的排在上面），檔案裡有註解標出插入點：

   ```markdown
   ### [0916 — 一句話標題](weekly/2026-09-16.md)

   進度：

   - 三到五條重點
   ```

   插完如果超過三段，把**最舊的那一段整段刪掉**，同時在 `docs/weekly/archive.md` 的表格
   最上方補一列。首頁永遠只有三週，這是這套結構最需要自律的地方。

#### 3. 新的一頁要進側欄

站台側欄的列序寫在 `docs-site/mkdocs.yml` 的 `nav`。**新增一篇週報或一份文件，這裡要跟著加一列**，
否則站上點不到（頁面仍會建出來，但沒有入口）。列序照首頁那兩張表的讀者思考順序，不要重排。

這一步取代了 HackMD 時代「在對應表裡加一行網址」。差別是：現在忘了加只是側欄少一列，
不會像以前那樣整篇連結失效。

#### 4. 改過的文件補版本歷程

這週動過的每份文件末尾都有「版本歷程」表，在**最上面**加一列：

```markdown
| 0916 | 2026-09-16 | 補上 FR-N08 的離線重送規則 |
```

第一欄只寫四位數週次，**不要寫網址**——同步時會自動換成該週凍結版的連結。
異動摘要寫「改了什麼」，不是「改了哪一節」，這一欄是給半年後的人看的。

#### 5. 先同步，再凍結

```bash
npm run docs:sync     # 內容先推上去，現行版更新
npm run docs:freeze   # 再打週次 tag，建立凍結版
```

`docs:freeze` 會掃過所有文件的版本歷程，把出現過、鏡像上還沒有同名 tag 的週次建出來。
已經存在的一律不動，它只會印一行「凍結版已存在，不動」。

不確定會做什麼就先看：`npm run docs:freeze -- --dry-run`。
只想處理某一週：`npm run docs:freeze -- 0916`。

凍結版建好之後**再跑一次 `npm run docs:sync`**：版本歷程第一欄的週次，要等該週凍結版真的存在，
同步時才會換成連結；還不存在的維持純文字，不留死連結。

#### 6. Commit

```bash
git add docs docs-site scripts package.json && git commit -m "docs: 週報 0916" && git push
```

`.docs-mirror/` 與 `.docs-preview/` 已經 gitignore，不會進版控——它們隨時可以重新產生。

## 踩過的坑

| 症狀 | 原因 | 解法 |
|---|---|---|
| 站上看不到剛加的那一頁 | `docs-site/mkdocs.yml` 的 `nav` 沒加那一列 | 補一列再 `docs:sync`。頁面其實建出來了，只是側欄沒有入口 |
| 凍結版的內容是舊的 | 先跑了 `docs:freeze` 才跑 `docs:sync` | 順序一律是先 sync 再 freeze。腳本會擋下沒同步就凍結的情況，但別靠它 |
| 週次 tag 打錯了 | 版本歷程那一欄寫錯週次 | **趁還沒 push 才救得回來**。已經建出去的凍結版視為既成紀錄，要修正就在新的一週寫明 |
| 改了 `docs/` 但站上沒變 | 只改了 repo，沒跑 `docs:sync` | 跑 `npm run docs:sync`。跑完 Actions 還要一兩分鐘才建完 |
| `docs:sync` 說找不到鏡像 repo | 鏡像還沒建立 | `gh repo create hd-docs --public`，再跑一次 |
| 在鏡像 repo 或站台上改的字不見了 | 同步是整份覆蓋，鏡像是單向的 | 內容一律改 `docs/`，鏡像只當展示 |
| 預覽起不來，說找不到 mkdocs | 本機沒裝建站工具 | `pip install -r docs-site/requirements.txt`。只影響預覽，不影響同步 |
| 版本歷程的週次沒有連結 | 那一週的凍結版還沒建立 | 跑 `npm run docs:freeze`。沒有對應凍結版時刻意維持純文字，不留死連結 |
| 想知道 0909 那一版是怎麼來的 | 換站之前它發佈在 HackMD 上，repo 裡只有當天的 commit 樹，兩者不一定相同 | 已用 `node scripts/snapshot-import.mjs 0909 --from-commit <sha>` 從舊站取回發佈出去的那一份，推成 `snapshot/0909` 分支＋`0909` tag 建成新站的該版。取回的檔案不留在本地 |
| 想在本地找某一版的原始檔 | 本地只有現行版，凍結版的家在鏡像 repo | `git -C .docs-mirror show <週次>:docs/<路徑>`；或直接開站上的 `/<週次>/` |
| 想補建更早的週次 | 那幾週的內容不在鏡像的 main 上 | **不要用 `docs:freeze`**——它會把 main（今天的內容）打上舊週次。照上一列的做法匯入該週真正發佈出去的版本 |
| PowerShell 讀出來的中文是亂碼 | 系統預設編碼頁是 big5 | 讀檔一律 `Get-Content -Raw -Encoding UTF8`，省略 `-Encoding` 就會壞 |
| 改了介面，但下一個人又改回去 | 只改了程式，沒改設計基準；或只改了文件，沒改 skill | 兩份一起改（見下方清單）。基準沒更新，下次就會再發明一組新的顏色與字級 |
| 編輯某一行時被支語 hook 擋下，但那行看起來沒問題 | 詞庫收了一些在醫學與公文語境屬正常用法的詞，整行寫入就會被擋 | 縮小編輯範圍，只改那個片段；或把該行從 `~/.claude/hooks/zhiyu-words.txt` 註解掉 |

## 什麼時候不只是加一篇週報

- **週中改了需求文件或進度報告** → 首頁那一列標修訂中 → `docs:sync`。**不要碰版本歷程與 `docs:freeze`**
- **週三定版** → 拿掉修訂中、版本歷程加一列 → `docs:sync` → `docs:freeze`，缺一步凍結版就不會出現
- **新增一種文件**（不是週報）→ 建檔（文末要有「版本歷程」表）→ 首頁表格加一列
  （不屬於需求、報告、參考、測試四類的單篇方案評估，放 `docs/notes/`，掛到首頁「其他文件」那塊）
  （**照下面的列序放進去，不要一律加在最後**；定版欄先寫 `新增 · 修訂中`）
  → `docs-site/mkdocs.yml` 的 `nav` 加一列 → `docs:sync`
- **改架構圖** → 改 `requirements/architecture-diagrams.src.html`（不要單獨修 PNG）→ 照
  `architecture-diagrams.md` 文末的指令重新產生 PNG → `docs:sync`。
  **圖片走 repo 相對路徑，不必再另外上傳、不必換任何網址**（這是換掉 HackMD 之後少掉的一整條規則）
- **測試手冊又長出一個迭代** → 在 `docs/testing/` 開一本 `iteration-N.md`，內容只寫該迭代新增的部分，
  共用的環境與主線留在主手冊，再到主手冊最後一章的分冊索引補一列，並在 `nav` 加一列。
  **不要把分冊掛到首頁**——七本分冊各占一列，首頁就從入口變成目錄了；讀者要動手驗收時
  點進主手冊，第一眼就看得到索引。項次編號跨冊不重複，抽出既有章節時沿用原編號，
  因為那些編號已經寫進週報與驗收紀錄。細節規則在 [AGENT.md](AGENT.md) 的「測試手冊的分冊」
- **改了介面設計基準** → `docs/notes/uiux-design-baseline.md` 與 `.claude/skills/hd-uiux/` **兩份一起改**。
  前者寫給人看（為什麼這樣設計），後者寫給 AI agent 看（實際數值與檢查步驟）。
  skill 不在 `docs/` 底下，所以不上站、不出凍結版，但它才是動介面時真正被讀的那一份
- **改了維護流程本身**（這頁講的規矩變了、文件多一份少一份、npm 指令改名、又踩到新的坑）
  → 這頁與 [AGENT.md](AGENT.md) **兩份一起改**。詳細的判斷表在 AGENT.md 的
  「改完文件，回頭檢查這兩份指南」。這兩份沒有版本歷程、不出凍結版，改完只要 `docs:sync`
- **那週沒進度** → 不要建空頁，首頁直接跳過該週。時間序有斷點沒關係，硬湊出來的空白紀錄才難讀

## 首頁不准長回去

首頁在 2026-09-10 從 100 行砍到 51 行，砍掉的是目錄結構與附錄——那些是維護者的東西，
不是讀者要的。**行數本身不是上限**（之後新增文件、換新的一週都會讓它長短變動），
真正不准破的是下面這幾條。想加東西之前先讀一次：

- **只有五塊**：現在到哪／最近三週／我要找…／需求文件／其他文件。不要開第六塊。
  第五塊「其他文件」是 2026-09-19 加的，放不屬於前四塊的單篇方案評估（檔案在 `docs/notes/`）。
  它是**刻意留的小出口**，免得每有一份技術決策就要硬塞進需求文件、或是沒地方放就不寫；
  但正因為是出口，最容易長歪——**表格只有三欄、每份一句話，一旦開始寫內容就等於首頁又長回去了**
- **兩張表的列序是照讀者的思考順序排的，不要動**（2026-09-10 定）：
  - 「我要找…」：臨床端進度報告 → 技術端進度報告 → 架構圖 → 資料字典 → 這套系統是用什麼蓋的 → 完整手動測試手冊。
    先知道進度到哪，再看系統長什麼樣、蒐了哪些資料，最後才是名詞解釋與動手驗收。
    **測試手冊的迭代分冊不另占一列**：它們從主手冊最後一章的索引進去，理由見下一段
  - 「其他文件」沒有閱讀動線，新增的排在表尾即可（目前兩份：平板管控、介面設計基準）
  - 「需求文件」：FDE 數位化評估報告 → SRS → 資料庫使用規範 → 實作規格書 → 部署規範 →
    尚待確認事項清冊。
    前五份是從為什麼要做，讀到做什麼、資料怎麼管、怎麼實作，最後是怎麼部署；
    第六份（清冊）是進行中的問題總表，不在這條動線上，固定排最後一列。
